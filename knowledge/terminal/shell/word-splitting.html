IFS and splitting

This page shows how IFS decides where an unquoted value is divided into separate arguments.

A list of separators

IFS is a small list of characters stored by the shell. The shell uses the characters in that list as places where an unquoted value can be cut into pieces. The usual list contains a space, a tab and a new line. If you change the list to a comma, the shell cuts at commas instead.

This page records commands that were already run, so you can read it without typing anything. The dollar sign at the start of a line is a prompt, not part of the command.

Why it matters

Data often arrives with separators built in: a comma-separated line, a list of names on one line, or a filename with a space. IFS determines how the shell interprets those separators.

How to think about it

Picture a row of beads joined by different kinds of string. IFS tells the shell which string colour means “cut here”. Change the colour and the same row breaks in different places.

Change the separators

Goal: you will be able to split a comma-separated value with IFS and keep a value whole with quotes.

Worked example

$ IFS=,; v=',a,,b,'
$ printf '[%s]\n' $v
[]
[a]
[]
[b]
$ printf '[%s]\n' "$v"
[,a,,b,]
$ printf 'one,two,three\n' | { IFS=, read -r a b c; printf 'a=<%s> b=<%s> c=<%s>\n' "$a" "$b" "$c"; }
a=<one> b=<two> c=<three>

Captured on Arch Linux, 2026-11-22. The brackets make the number of fields visible; the empty brackets are real empty fields.

What just happened

  1. Setting IFS to a comma made comma the only separator for this shell.
  2. The leading and trailing commas produced empty fields, and so did the pair of commas in the middle.
  3. Double quotes protected the whole value from splitting.
  4. IFS=, read -r applied the comma separator to one input line instead of changing the shell's IFS.

Try it

Repeat the example with a value such as one,,three. Predict how many fields the unquoted expansion will produce. Then add double quotes around the expansion and confirm that the number changes to one.

If it goes wrong

Empty fields disappear
Spaces, tabs and newlines in IFS are treated as runs, so repeated whitespace does not create empty fields. Use a non-whitespace separator such as a comma when empty fields matter.
Every test command now splits at commas
You changed IFS in the current shell. Start a new shell or restore the default with IFS=$' \t\n'.

The usual interactive shell on Tamlinux is bash, described in Tamlinux components. It starts with IFS set to space, tab and newline; the portable rules are in POSIX Shell Command Language.

Check yourself

Decide before revealing the explanation.

Why does a comma-separated expansion produce empty fields where a space-separated one does not?

Comma is a non-whitespace IFS character. Each occurrence terminates a field, so two adjacent commas leave an empty field between them. Runs of IFS whitespace are collapsed instead.

Why put IFS=, on the read command instead of setting it for the whole shell?

A prefix assignment applies to that command only, so later commands keep the normal separators. It avoids surprising behaviour elsewhere in the script.

The splitting algorithm

Reference

IFS stateEffect on unquoted expansion
UnsetSplitting behaves as if IFS held space, tab and newline
Default whitespaceRuns of separators are collapsed; leading and trailing runs produce no empty fields
Non-whitespace character such as commaEach character terminates a field; adjacent separators can produce empty fields
Empty stringNo splitting, but a field made entirely from an empty expansion is removed
Mixed whitespace and other charactersEach kind follows its own rule above

How it works

The shell scans only the parts of a field that came from unquoted expansion. Literal characters from the original word stay attached to the candidate. An IFS whitespace character ends the current candidate and is discarded; more whitespace is skipped before a new candidate begins. A non-whitespace IFS character also ends the candidate, but it delimits a field even when the candidate is empty. At the end of the input, a non-empty candidate becomes a field. If no field was delimited at all, the result is zero fields rather than one empty field.

Advanced usage

$ show() { printf 'unquoted $*: '; printf '[%s]' $*; printf '\n'; printf 'quoted "$*": '; printf '[%s]' "$*"; printf '\n'; }
$ show 'a b' c
unquoted $*:  [a][b][c]
quoted "$*":   [a b c]

Captured on Arch Linux, 2026-11-22. Unquoted $* loses the boundary between the original arguments and is split again using IFS. Quoted "$*" joins the arguments with the first character of IFS. Only "$@" preserves one argument per original argument.

Edge cases

  • Only space, tab and newline are always IFS whitespace; other locale whitespace is implementation-defined.
  • IFS is also used by read and by the unquoted expansion of *, so changing it affects more than command arguments.
  • A value containing bytes that are not valid characters gives unspecified results during field splitting.
  • NUL bytes cannot be stored in a shell variable or passed in an argument, so splitting cannot represent them.

Check yourself

A comma-separated line ends with a comma. Why is the final field empty rather than absent?

A non-whitespace IFS character terminates a field when it is seen. The candidate after it is empty, but the delimiter still caused a field to be emitted.

Why is "$@" the safe form when forwarding arguments to another command?

Quoted "$@" produces one field per original argument, including arguments that contain IFS characters. Unquoted $* joins and then resplits them, losing the original boundaries.
