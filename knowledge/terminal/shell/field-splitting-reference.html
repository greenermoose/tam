This reference records how IFS splitting treats whitespace, empty fields and quoted expansions in portable shell behaviour.

A separator with rules

IFS is the set of characters the shell treats as separators when an unquoted expansion is split. Whitespace separators collapse runs; a non-whitespace separator such as a comma can produce genuine empty fields.

Think of a row of beads on a string. Spaces between beads may be ignored as padding, while commas mark exact places where an empty bead can exist.

Rules worth keeping precise

Splitting applies to unquoted expansion results after parameter expansion, command substitution and arithmetic expansion. Field splitting is not pathname expansion: globbing happens after splitting. Quoting suppresses splitting for the quoted part, and NUL cannot appear in a shell argument. Locale-dependent whitespace behaviour is implementation-defined in portable shells.

Scope

Field splitting applies to the results of unquoted parameter expansion, command substitution and arithmetic expansion. It does not apply to literal characters from the original word, nor to any result that was quoted when the word was tokenized. It runs after those expansions and before pathname expansion; quote removal happens last. The normative source is POSIX Shell Command Language, section 2.6.5, with the IFS variable defined in section 2.5.3.

What IFS contributes

ConceptPrecise meaning
IFSA string whose characters, as byte sequences, are used as delimiters for field splitting, for the unquoted expansion of *, and for the read utility.
IFS white spaceSpace, tab and newline whenever they occur in IFS, plus any other white-space characters the implementation chooses to treat as IFS white space. The three portable characters count regardless of locale.
Non-whitespace IFS characterAny other character in IFS. Each occurrence terminates a field, including when the candidate field is empty.
Unset IFSFor splitting and read, behaves as if the value were space, tab and newline; the variable itself is not changed.
Empty IFSNo field splitting occurs. A field consisting entirely of an expansion result that is empty is still removed before quote removal.

The algorithm

Each input field is processed in order. Bytes that did not come from an expansion are appended to the candidate field unchanged. For bytes that did come from an expansion:

  1. If the byte sequence is not a character in IFS, append its first byte to the candidate and continue.
  2. If it is an IFS white-space character, discard it and continue scanning.
  3. If it is a non-whitespace IFS character, discard it but remember that a delimiter was seen.
  4. After skipping a run of white space, or on seeing a non-whitespace delimiter, emit the candidate as a field if the candidate is non-empty or a non-whitespace delimiter was seen. Then reset the candidate.
  5. When the input is exhausted, emit the candidate only if it is non-empty.

If no field was delimited, the result is zero fields rather than one empty field. A field with no expansion results is passed through unaltered. The ordered output replaces the input field list.

Consequences worth memorizing

  • Repeated IFS whitespace between values collapses to one boundary; repeated non-whitespace delimiters produce empty fields.
  • Leading and trailing IFS whitespace produces no empty fields; leading and trailing commas do.
  • A quoted null string participates in the word even though it expands to no characters, so it can keep an otherwise empty field alive.
  • Pathname expansion runs on the fields this algorithm produces, so a delimiter that survives splitting can become a pattern character.

Special parameters

The parameters @ and * start with one field per positional parameter. In a context where splitting will happen, empty fields may be discarded and the non-empty ones are split again. When no splitting will happen, * joins the values using the first character of IFS, a space if IFS is unset, or no separator if IFS is null. Quoted "$@" is the only form that reliably produces one field per original argument, even when an argument contains IFS characters or is empty.

Interaction with read

The read utility uses IFS to divide a line into fields, with the same distinction between whitespace and non-whitespace characters. A leading or trailing run of IFS whitespace is ignored; a non-whitespace delimiter can produce an empty field. The -r option disables backslash interpretation, which is separate from splitting. Prefixing a command with an assignment, as in IFS=, read -r a b c, changes IFS for that command only.

Limits and unspecified behaviour

  • If IFS contains bytes that do not form valid characters, the results of splitting, * expansion and read are unspecified.
  • It is implementation-defined whether locale white-space characters other than space, tab and newline count as IFS white space; if they do, it is unspecified whether the locale is read at assignment time or at split time.
  • Shell variables and arguments cannot contain a NUL byte, so no splitting rule can preserve one.
  • Extensions such as brace expansion and Bash arrays go beyond the portable rules; scripts depending on them need the corresponding shell manual.
