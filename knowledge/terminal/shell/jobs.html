Giving your computer written instructions

What is a process?

A process is a running program. A shell is a program that reads typed instructions; it can manage one or more processes as a job. Your own short practice tasks are safe to start and wait for; other people's processes are not practice material.

Why it matters

Work can continue while a command runs in the background, but you still need to know what belongs to your shell and when it has finished.

How to think about it

Think of each process as a worker you hired for one task. The shell keeps a list of the workers it started. Waiting for a worker is checking that they finished; sending a signal is asking them to pause or stop.

New words

Process
A program that is currently running.
PID
A process identifier; it can be reused after the process exits.
Job
A shell's command or pipeline, which may include more than one process.

If it goes wrong

If a worker is already gone, wait still reports its status; use that evidence rather than guessing.

Check yourself

Why save the child PID?

So wait and any signal target only the process you started.

Distinguish existence, identity and health

Reference: signals target processes or process groups according to kill's PID argument. Dispositions and masks differ; SIGKILL and SIGSTOP cannot be caught, blocked or ignored. A PID can be reused after exit. Existence alone is not identity or health.

How it works

The shell records its children and reaps their termination statuses with wait interfaces. Process groups organize terminal jobs, so terminal-generated signals need not target only one process. Zombie processes have exited but retain status until reaped.

Edge cases and cost

Terminal closure, shell hangup policy, session management, open descriptors and application behavior all matter. disown and nohup are not universal workload-survival guarantees. Do not poll process existence in a busy loop when waiting or service supervision provides the needed lifecycle event.
