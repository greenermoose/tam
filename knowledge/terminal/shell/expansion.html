What changes before a command runs

This page explains the order in which a shell changes what you typed before it starts a command.

An assembly line for words

When you type an instruction, the shell does not hand your text straight to a program. It works through the text in steps. Some steps replace a name with the value stored in it. One step can turn a single piece of text into several words. A later step looks for filenames that match a pattern. Only after all of that does the shell remove the quote marks and run the command.

You do not need to type anything on this page. The examples are printed records of commands someone else ran, included so you can see what each step does.

Why it matters

The same text can produce different arguments depending on the order of these steps. Knowing the order tells you why quoting changes the result.

How to think about it

Picture an assembly line with several stations. A parcel goes through each station in turn. A station can only work on what earlier stations left behind, so the order decides the final shape.

New words

Expansion
The shell replacing a short notation, such as $name, with the value it stands for.
Word splitting
Dividing an expansion result into separate words.
Glob
A pattern such as *.txt that matches filenames.

Worked example

$ scratch=$(mktemp -d); cd "$scratch"
$ touch 'red one.txt' 'red two.txt'
$ var='red *'
$ printf '[%s]\n' "$var"
[red *]
$ printf '[%s]\n' $var
[red]
[red one.txt]
[red two.txt]

Captured on Arch Linux, 2026-11-22. The scratch directory held only the two named files, which were removed after the capture.

What just happened

  1. The variable was replaced by the text red *.
  2. With quotes, that text stayed one field, so the asterisk was never treated as a pattern.
  3. Without quotes, field splitting divided the text at the space into red and *.
  4. Pathname expansion then replaced the asterisk with the two matching filenames.

Try it

In a fresh scratch directory, create two files whose names share a prefix. Store a value with that prefix and an asterisk in a variable, then print it once quoted and once unquoted with printf '[%s]\n'. Predict the number of lines before you press Enter. Remove the scratch directory when you are done.

If it goes wrong

No files match the pattern
Most shells leave an unquoted asterisk as literal text when nothing matches. Check the directory and the spelling of the prefix.
A filename with a space appears split
The value was left unquoted. Wrap the expansion in double quotes before repeating the command.

The usual interactive shell on Tamlinux is bash, described in Tamlinux components; it follows this order and adds its own extensions. Scripts that must run under other shells should stay within the portable rules in POSIX Shell Command Language.

Check yourself

Decide before revealing the explanation.

Why does "$var" not expand an asterisk into filenames?

The quotes keep the expansion result as one field and protect pattern characters, so the pathname expansion stage has no unquoted pattern to match.

Which happens first: field splitting or pathname expansion?

Field splitting. It can create a field that consists of an asterisk, which the next stage then expands to matching filenames.

The expansion pipeline

Reference

StageWhat it does
Dollar-single-quote processingDecodes C-style escapes before word expansion
Tilde, parameter, command and arithmetic expansionReplaces names, commands and expressions with values, working from the start of the word to the end
Field splittingSplits unquoted results using IFS
Pathname expansionMatches unquoted pattern characters against filenames
Quote removalRemoves the quote characters that were present in the original word

How it works

Each stage sees the output of the previous one. Tilde, parameter, command and arithmetic expansion can be interleaved from left to right, but field splitting always follows them and precedes pathname expansion. Quote removal is last. A quoted expansion result is protected from both splitting and pattern matching because the token still carries its quoting information; removal only deletes the quote characters, not the protection they provided.

Advanced usage

$ value=$(printf 'a\nb\n\n')
$ printf '<%s>\n' "$value"
<a
b>

Captured on Arch Linux, 2026-11-22. Command substitution removes all trailing newlines. If a value must retain them, append a sentinel character and strip it after substitution.

Edge cases

  • Alias substitution happens at tokenization, before any expansion described here.
  • Brace expansion, where supported, happens before the other expansions and can create entire new fields.
  • With set -f, pathname expansion is skipped and an unquoted asterisk stays literal.
  • Redirections and assignment words have their own expansion rules, so their values are not always subject to splitting.

Check yourself

Why can a variable containing a filename pattern never match a file if it is always double-quoted?

Because quoting keeps the expansion result as a single protected field, and pathname expansion ignores quoted pattern characters.

What does command substitution do to trailing newlines, and what consequence does that have for reading data?

It strips them all, so a value read this way cannot preserve an empty final line. Use a read loop instead when exact line boundaries matter.
