The great Emacs versus vi debate

This page explains why two text editors became symbols of two ways to work, what the jokes mean, and which differences are real enough to guide a choice.

Before this

The ex line editor, The vi screen editor, and GNU Emacs describe the programs themselves. This page is about the argument around them.

Two editors, two habits

vi and Emacs were both written in the 1970s, both edit plain text, and both are still maintained. Their users have argued about them for almost as long. The argument is called the editor war, and it is mostly a cultural argument rather than a technical emergency.

The disagreement starts with a design choice. vi is modal: keys are commands until you enter insert mode. Emacs is modeless: typing inserts text, and commands use modifier keys or names. Each choice makes some tasks feel natural and others feel clumsy. From that small difference grew two styles of working, two communities, and a great many jokes.

Why it matters

You will meet both editors on real systems, and you will meet advice from people who love one and dislike the other. Knowing the history helps you separate a testable claim ("this starts faster") from a preference ("this feels better"). That distinction is useful well beyond editors.

How to think about it

Imagine two workshops. In the first, every tool has a short command: d for delete, w for word, and the tools combine into sentences. In the second, every tool has a name and a labelled hook; you can call a tool by name, read its manual, and build a new tool while you work. Neither workshop is the right one for every job. The argument begins when someone claims that their workshop is the only sensible way to build anything.

New words

Modal editing
An editing design where the same keys mean different things depending on the current mode.
Modeless
An editing design where typing inserts text and commands are separate actions.
Editor war
The long-running cultural argument over which editor is better, often conducted with jokes and overstated claims.
Extensibility
The degree to which users can add or change the editor's behaviour, rather than only changing its settings.

How the argument started and what it is about

Goal: you will be able to describe the two lineages, explain the best-known jokes without repeating them as facts, and judge a claim about the editors by asking whether it is testable.

The short history

TimeWhat happened
Early 1970sKen Thompson's ed establishes the line-editor model at Bell Labs: addresses, commands, and a buffer.
Mid-1970sBill Joy at UC Berkeley writes ex and then vi, adding a full-screen view to the ex command language. BSD distributions spread it.
Mid-1970sAt the MIT AI Lab, Richard Stallman, with Guy Steele and David Moon, turns TECO macros into EMACS. The 1981 AI Memo 554 describes an extensible, self-documenting display editor.
1985GNU Emacs is released as part of the GNU Project, with Emacs Lisp as its extension language.
1980s and 1990sUsenet turns the disagreement into a recurring flame war. The Jargon File calls it a holy war and notes that such arguments are often about cultural attachment rather than large technical differences.

2010s and laterNeovim forks Vim; Emacs adds package management, use-package, and native compilation; both remain actively developed.

The Jargon File is blunt about the genre. Its entry on holy wars lists "EMACS vs. vi" among the hardy perennials and says that in a holy war "most of the participants spend their time trying to pass off personal value choices and cultural attachments as objective technical evaluations." That is the most useful sentence ever written about the editor war.

The jokes and what they mean

The Jargon File records several spoof expansions of EMACS: "Escape Meta Alt Control Shift", "Eight Megabytes And Constantly Swapping", and "EMACS Makes A Computer Slow". Each encodes a real criticism. Emacs commands use modifier keys heavily; it was large for the memory of its early machines; and a fully loaded Emacs can take noticeable time to start. The joke is not evidence that Emacs is unusable. It is a compressed complaint about a trade-off.

vi has its own jokes. Because VI is the Roman numeral for six, "vi vi vi" reads as 666, and the editor has long been called the editor of the beast in mock horror. The more practical joke is that vi "will neither take commands while expecting input text nor vice versa", as the Jargon File puts it. That is mode confusion, and it is a real cost for a beginner.

A common quip calls Emacs "a great operating system lacking a decent editor". It is a joke about scope: Emacs contains mail, news, a file manager, a calendar, and much more. Whether that is a feature or a distraction depends on what you want from an editor. The quip is a preference dressed as a verdict.

Try it

Take three claims you have heard about the editors and label each as testable or a preference: "vi starts faster", "Emacs is more extensible", and "modal editing is confusing". For each testable claim, write down the measurement that would settle it. For each preference, write down who might reasonably disagree. This exercise is more useful than winning the argument.

If it goes wrong

You open vi and cannot type text
You are in command mode. Press i to enter insert mode, type, then press Esc to return to commands and :wq to save and quit. If you are lost, press Esc a few times and type :q! to quit without saving.
You open Emacs and a key combination does nothing
Your terminal may not deliver Meta. Use Esc followed by the key, or run the command by name with M-x. Start with emacs -Q -nw to rule out your init file.
Someone says one editor is objectively better
Ask "better for which task, on which machine, with how much configuration?" The answer usually turns a verdict into a comparison.
Someone quotes a joke as evidence
Ask what trade-off the joke points to. "Eight megabytes and constantly swapping" points to memory use; it does not prove that Emacs is slow today.
Someone says the other editor is unusable
Both have been used for decades by people doing serious work. The useful question is which costs less for the work in front of you.

Tamlinux does not take a side. Its baseline editor is micro, chosen for familiar shortcuts and a small default footprint. vi, Vim, Neovim, and Emacs are optional packages. The pages in this section describe them so you can use a system that already has one, not to pressure you to replace the default.

Check yourself

Decide your answer before you reveal it.

Why does the Jargon File call the editor argument a holy war rather than a technical dispute?

A holy war is a dispute in which people present personal and cultural preferences as objective technical facts. The editors do differ technically, but many of the loudest claims are about identity and taste. The Jargon File's point is that the substantive differences are often smaller than the rhetoric suggests.

Is "Emacs is more extensible than vi" a testable claim?

Partly. You can compare what each editor exposes to users: a full Lisp environment with hooks and advice versus ex commands, macros, and a plugin API in Vim or Neovim. But "more extensible" also depends on what you want to change and how much complexity you will accept. The measurable part is the mechanism; the overall verdict includes a value judgement.

Why can a vi user still be productive on a system where Emacs is installed, and the reverse?

Both edit plain text, and both are available on most systems. A vi user can use Vim, Neovim, or a vi clone; an Emacs user can install Emacs or use it over a terminal. The choice affects fluency and workflow, not whether the file can be edited at all.

How it works

The deepest difference is where the program expects change to happen. vi began as a screen interface to a line editor and kept a compact command language. Its extensions arrive as commands, mappings, plugins, and, in Vim and Neovim, a scripting layer around a core that remains recognizably vi. Emacs began as a set of macros in another editor and grew into a Lisp machine for text. Its extension language is not an add-on; it is the substrate. That is why an Emacs configuration can redefine almost anything, and why a broken configuration can break startup before the editor is usable.

Availability follows from history. vi and ex were part of BSD and then POSIX, so a conforming system has a vi-shaped editor even when nothing else is installed. Emacs spread through the GNU project and academic and programmer culture, but it was never the minimal editor guaranteed by a standard. A rescue image is more likely to contain BusyBox vi than Emacs. A developer workstation is likely to have either or both.

Performance comparisons need a stated configuration. A bare vi or Vim with no plugins starts in milliseconds; a heavily configured Vim with many plugins does not. A default Emacs starts in a fraction of a second on modern hardware; a large init file with packages and native compilation can take much longer, while an Emacs daemon amortizes startup across many edits. "Emacs is slow" and "Vim is fast" are therefore claims about particular setups, not about the programs in the abstract.

Extensibility is also a matter of kind, not only amount. Emacs Lisp can inspect and change the editor's own behaviour while it runs; Vim's plugin system and Neovim's Lua API expose a great deal, but the core remains a C program with a compatibility contract. Neither is a superset of the other. A user who wants to rewrite the editing model will find Emacs more accommodating; a user who wants vi's grammar with modern language tooling will find Neovim more direct.

Keyboard ergonomics is the least settled axis. Emacs relies on modifier chords, which some users find efficient and others find punishing. vi keeps the hands on the letter keys but requires mode switches and a large command vocabulary. Neither design has a proven health advantage across users; keyboard, posture, technique, and configuration matter more than the editor's legend. Treat strong claims about repetitive strain as anecdotes until they come with evidence about the specific setup.

Advanced usage

The same three tasks look different in each tradition. This table is a reference for reading other people's instructions, not a recommendation to memorize all of it.

Taskvi or VimEmacs
Delete the current lineddC-a C-k (beginning of line, kill line)
Save and quit:wq or ZZC-x C-s then C-x C-c
Replace every match in the file:%s/old/new/gM-x replace-string or a Lisp form with save-buffer
Run a shell command:!commandM-! or M-x shell
Add a new behaviourWrite a function in Vimscript or Lua and map itEvaluate a Lisp form or load a package

The commands reveal the philosophies. vi's dd is a sentence in a small grammar. Emacs's C-a C-k is two named commands invoked by their default bindings, and either can be replaced or called by name. One design optimizes for terse composition; the other optimizes for discoverability and redefinition.

Edge cases and trade-offs

  • Compatibility is not identity. Vim in compatible mode is not a 1970s vi, and GNU Emacs is not the MIT TECO macros. Claims about "the original" editor often describe a particular clone or a particular configuration.
  • Standards cover less than users assume. POSIX specifies vi and ex behaviour, but most people use Vim or Neovim extensions without noticing. A script written for Vim may fail in nvi or BusyBox vi.
  • Ecosystem gravity. Most modern language tooling targets Vim, Neovim, and VS Code first. Emacs often has excellent support through packages, but the package may lag or require configuration. The reverse is also true: Org mode, Magit, and Dired have no exact equivalent in the vi world.
  • Configuration debt. A large Emacs init file or a large Vim plugin set becomes a program to maintain. The editor war rarely discusses the maintenance cost of the winning setup.
  • Licensing and governance. GNU Emacs is a GNU project program under the GPL. Vim is charityware with a GPL-compatible license and a single long-time maintainer's legacy; Neovim is a community fork with a different governance model. These differences affect contributions and long-term direction, not daily editing.
  • The argument is not zero-sum. A team can standardize on one editor for shared workflows while individuals use another for their own work. File formats and version control matter more than the editor that produced them.

Check yourself

A team proposes a rule that every member must use the same editor so that pair programming and documentation stay consistent. Argue both sides, then propose a policy that addresses the real risks without turning the editor into an identity test.

The case for one editor is real: shared keybindings make pairing smoother, plugins and formatting can be standardized, and onboarding has one path. The case against is also real: forcing a tool on skilled users costs productivity and morale, and the editor is rarely the source of inconsistent output. The risks that matter are formatting, line endings, encoding, and reproducible builds. A better policy standardizes those with a formatter, an editorconfig file, and a pre-commit check, then lets people choose their editor. Pairing can use a shared screen or a common keybinding layer without mandating one program. The debate becomes a tooling decision instead of a loyalty test.
