The ex line editor

This page explains ex, an editor that changes a file by naming lines and giving commands instead of moving a cursor around a screen.

Editing by line number

A line editor works on a numbered list of lines. You do not point at a character and type over it. You say which line you mean and what should happen to it: print line 2, delete lines 3 to 5, replace every "beta" with "BETA", write the file, quit.

ex is the line editor that grew out of an earlier program called ed. When Bill Joy added a full-screen display at Berkeley in the 1970s, he kept the ex command language underneath it. That is why a vi user types a colon and then commands such as :wq or :%s/old/new/g: the colon hands the rest of the line to ex.

Why it matters

ex is useful when there is no screen to draw on, when the edit must happen inside a script, or when a remote connection is too slow or too small for a full-screen editor. It is also the fastest way to understand what vi is doing: vi is a visual front end to the same buffer and the same commands.

How to think about it

Imagine a numbered shopping list on a clipboard and an assistant who only takes instructions. "Cross out line 2." "Add eggs after line 4." "Change the word milk to oat milk on every line." You never touch the paper. You read the numbers, speak a command, and the assistant edits the list. ex works the same way, with the file held in a buffer in memory until you write it back.

New words

Line editor
An editor that works on numbered lines with commands rather than a movable cursor.
Buffer
The in-memory copy of the file that changes are made to before they are written back.
Address
The line or range of lines a command applies to, such as 2, 1,3, . for the current line, or $ for the last line.
Regular expression
A pattern that describes text to find, such as ^# for a line beginning with a hash mark.

Change a file with ex commands

Goal: you will be able to open a file in ex, change one line, print a range of lines, save the result, and quit without saving when you change your mind.

Worked example

The -s option puts ex into batch mode. It suppresses prompts and ordinary messages, which keeps the capture readable. The commands between the EOF markers are typed into ex's standard input, one per line.

$ printf 'alpha\nbeta\ngamma\n' > colours.txt
$ ex -s colours.txt <<'EOF'
2s/beta/BETA/
1,2p
wq
EOF
alpha
BETA
$ cat colours.txt
alpha
BETA
gamma

Captured with Vim 9.2 in ex mode on an Arch-based system, 2026-11-16. The commands are POSIX ex; other implementations print the same two lines.

What just happened

  1. ex -s colours.txt opened the file into a buffer and read commands from standard input.
  2. 2s/beta/BETA/ addressed line 2 and substituted beta with BETA. Because address 2 names one line, only that line changed.
  3. 1,2p printed lines 1 through 2. Printing does not change the buffer.
  4. wq wrote the buffer back to colours.txt and quit. The trailing colon is not needed in ex itself; it belongs to vi's command line.

Try it

Make a scratch directory and a three-line file. Use ex to change the second line, print all three lines with 1,$p, then quit with q! so the change is discarded. Run the same session again and end with wq; check the file with cat. Finally, delete the directory.

If it goes wrong

E486: Pattern not found: delta
The search or substitution pattern matched nothing. Check spelling and case; ex patterns are case-sensitive unless the pattern or an option says otherwise. With -s, ex exits with a nonzero status instead of leaving you at a prompt.
E37: No write since last change
You asked to quit while the buffer still had unsaved changes. Use wq to save them, or q! to discard them deliberately.
E325: ATTENTION and a swap file name
Another ex or vi session may still be editing the same file, or an earlier session crashed. Do not delete the swap file until you know which case it is; the vi page explains recovery.
Nothing appears after a command
Many ex commands print nothing when they succeed. In batch mode there is also no prompt. Check the file with cat or ask ex to print a range.

On the Arch-based system checked for this page they come from the optional ex-vi-compat package, which depends on vim and supplies edit, ex, vedit, vi, and view. Ask before installing packages, and read Packages and updates first.

Check yourself

Decide your answer before you reveal it.

What is the difference between 2d and 2,4d?

2d deletes only line 2. 2,4d deletes lines 2, 3, and 4 as one range. After either command the remaining lines are renumbered, so a later 2p may print a different line than you expect.

Why did 1,2p print BETA instead of beta?

The substitution ran first and changed the buffer. p prints the current contents of the buffer, not the file on disk. The file changes only when w or wq writes it.

You run ex -s notes.txt and feed it s/draft/final/. The pattern is not on the current line but is on line 4. What happens?

The command fails because a substitution without an address applies to the current line, which starts at line 1. Use 4s/draft/final/, %s/draft/final/ for every line, or g/draft/s//final/ to act only on matching lines.

ex as a language

Reference

POSIX ex reads a command line in the form [address[,address]]command[arguments]. A missing address usually means the current line; a missing second address means the same line as the first.

AddressMeaning
3Line 3.
.The current line.
$The last line in the buffer.
%All lines; shorthand for 1,$.
1,4The inclusive range from line 1 to line 4.
/pattern/The next line matching a basic regular expression.
?pattern?The previous line matching the pattern.
'aThe line marked with the vi command ma.
.+2, $-1An offset from another address.
CommandEffect
pPrint the addressed lines. = prints a line number instead.
dDelete the addressed lines from the buffer.
s/pat/repl/flagsSubstitute in the addressed lines. Without g, replace the first match on each addressed line; with g, every match.
g/pat/cmd, v/pat/cmdRun cmd on every line matching, or not matching, the pattern.
m target, t targetMove or copy the addressed lines to after target.
r fileRead another file into the buffer after the current line.
w file, wqWrite the buffer, optionally to another file, and quit after writing.
e fileReplace the buffer with another file, refusing if there are unsaved changes.
q, q!Quit, or quit and discard unsaved changes.
[addr]!cmdFilter the addressed lines through a shell command, or run the command when no lines are addressed.

How it works

ex holds the file in an edit buffer and keeps a current line. Every command updates that current line, which is why a sequence of edits can be written without repeating an address. That statefulness is the main difference from a filter such as sed: ex is a session with a cursor line, a buffer, marks, and options; sed is a stream transform.

vi is not a separate editing model. POSIX describes vi as the screen-oriented utility and ex as the line editor; the vi specification covers only open and visual modes and sends the reader to ex for the remaining editing capabilities. Inside vi, Q enters ex mode and visual returns to the screen. The colon command line in vi accepts the same ex commands.

Startup files follow POSIX rules. If EXINIT is set, ex executes the commands it contains. Otherwise it reads $HOME/.exrc, subject to ownership checks. Vim's compatibility wrapper used for ex on Arch also reads ./.exrc when the home file is absent. The -s option suppresses prompting and informational messages, but diagnostic errors still go to standard error.

The exit status is 0 for success and greater than 0 after an error. POSIX adds a sharp edge: when standard input is not a terminal and an error occurs, ex must not write the file and must terminate with a nonzero status. A script that pipes commands into ex therefore fails closed rather than saving a half-edited buffer.

Advanced usage

This capture deletes comment lines with g, then substitutes without the g flag. Each line changes at most once, which is why only the first letter of each word is capitalized.

$ printf '# note\nalpha\nbeta\ngamma\n' > lines.txt
$ ex -s lines.txt <<'EOF'
g/^#/d
%s/a/A/
1,$p
wq
EOF
Alpha
betA
gAmma

Two details are easy to miss. g/^#/d runs d on line 1 first; ex adjusts the line numbers as it goes, so a global command does not leave dangling addresses. And %s/a/A/ without g replaces one match per line. Add g as the final flag to replace every match on each line. A different delimiter avoids escaping slashes: s#/usr/local#/usr#.

Edge cases

  • Basic versus extended regular expressions. POSIX ex uses basic regular expressions, where grouping is \( and \) and alternation is not portable. Vim also accepts \| and other extensions; a script meant for another ex implementation should stay with the portable subset.
  • An empty pattern repeats the last one. s//replacement/ reuses the previous search pattern. That is useful in a g/pat/s//new/ command and surprising when the previous pattern was set somewhere else.
  • Global commands and line shifts. Commands that delete or move lines interact with g in implementation-defined ways beyond the simple cases. Prefer one pass for selection and another for editing when a script must be portable.
  • No terminal, no recovery prompt. In batch mode a failed command ends the session. Check ex's exit status in the calling script instead of assuming the file was written.
  • Write failures. A full disk, a read-only file, or a lost permission makes w fail. ex reports the error and does not pretend the write succeeded; a script must still check the exit status.
  • Binary data and encodings. ex is a text editor. NUL bytes and invalid byte sequences in the current encoding are not safely round-tripped. Use a binary-aware tool for those files.
  • Swap files and concurrent sessions. Vim-based ex creates a swap file next to the edited file. Two sessions on one file can collide; recovery is covered on the vi page.
  • Naming the file. Without a file operand, w needs a name. In a pipeline, pass the path as an argument rather than relying on interactive state.

Check yourself

A deployment script runs printf '%s\n' 'g/^#/d' 'wq' | ex -s service.conf and exits 0 even though the file was not changed. Give two plausible explanations and the evidence you would collect.

First, the command stream may have failed before the write, for example because the file was not writable or a startup file changed the working state; POSIX says a nonterminal error must prevent the write and return nonzero, so an exit status of 0 argues against that branch. Second, the pipeline may report the status of the last command rather than ex, depending on the shell and options; without set -o pipefail, a successful printf can mask ex's failure. Collect the pipeline's individual statuses, ex's standard error, the file's ownership and mode, and the file's modification time. The design lesson is to run ex with its input redirected from a here-document or file and to check ex's own status, not to trust a pipeline's final status.
