Guide / Terminals and shells / Classic text editors / The vi screen editor

This page explains vi, the screen editor whose letters are commands until you deliberately switch into a mode where typing inserts text.

A screen with two jobs

Most editors have one job: whatever you type appears in the file. vi has two. In modal editing, the same keys mean different things depending on the current mode. In command mode, d means delete, w means word, and i means insert. In insert mode, d, w, and i are just letters.

That sounds inconvenient until you see the trade. Commands compose. dw deletes a word, d2w deletes two words, dd deletes a line, and 3dd deletes three lines. The keyboard becomes a small language for changing text, and your hands rarely leave the main letter keys.

Why it matters

vi is the common editor on Unix-like systems and inside many tools that borrow its keys. If you administer a machine with no graphical desktop, or open a file in a rescue environment, vi or one of its clones is often what exists. Learning a few commands turns a stuck moment into a two-second edit.

How to think about it

Think of a craftsperson at a bench. In command mode you are naming actions: "delete this word", "change inside the quotation marks", "go to the end". In insert mode you have picked up a pencil and are writing. Pressing Escape puts the pencil down and returns you to naming actions. The confusion beginners feel comes from not noticing which of the two states they are in.

New words

Modal editing
Editing in which the meaning of a key depends on the editor's current mode.
Command mode
The mode where keystrokes are editing commands, such as dd or p.
Insert mode
The mode where ordinary typing becomes file text. Escape returns to command mode.
Motion
A command that moves the cursor, such as w for the next word or $ for the end of a line.
Operator
A command that acts on the text a motion reaches, such as d for delete or y for copy.
Buffer
The in-memory copy of the file being edited.

Open, change, save, and quit

Goal: you will be able to open a file in vi, insert text, delete and restore a line, save the file, quit without saving when you must, and get out of a mode you did not mean to enter.

Worked example

The capture below replays normal-mode keystrokes through ex's normal! command so the output stays readable in a noninteractive session. In a real vi session you type the same keys directly, without the word normal!.

$ printf 'one\ntwo\nthree\n' > words.txt
$ ex -s words.txt <<'EOF'
normal! 1Gdd
normal! Gp
1,$p
wq
EOF
two
three
one

Captured with Vim 9.2 in ex mode on an Arch-based system, 2026-11-16. The keys are standard vi.

What just happened

  1. 1G moved to line 1. dd deleted that line into the unnamed buffer.
  2. G moved to the last line. p put the deleted line below it.
  3. 1,$p printed the whole buffer through the ex command line, showing the new order.
  4. wq wrote the file and quit.

For ordinary interactive editing, the core sequence is:

KeysEffect
vi fileOpen the file. The cursor starts in command mode.
iEnter insert mode before the cursor. Type your text.
EscLeave insert mode and return to command mode.
h j k lMove left, down, up, right.
x, ddDelete one character, or one whole line.
uUndo the last change. In classic vi this is one level; Vim keeps more.
/text then EnterSearch forward. n finds the next match.
:w, :wqWrite the file, or write and quit.
:q!Quit and discard unsaved changes.

Try it

In a scratch directory, create a file with three lines. Open it with vi, move to the second line with j, delete it with dd, undo with u, then delete it again. Save with :wq and confirm with cat. Reopen the file, type i, add a line, press Esc, and quit without saving with :q!. Check that the file is unchanged. Remove the scratch directory afterwards.

If it goes wrong

Typing letters produces text instead of commands
You are in insert mode. Press Esc once, then try the command again. If the screen beeps or flashes, Esc was already pressed and you are in command mode.
A command does nothing, or : appears as text
You are still in insert mode. Press Esc first. In Vim the bottom line often says -- INSERT --; classic vi gives no such indicator, which is why the mode is easy to lose track of.
E37: No write since last change
You asked to quit with unsaved changes. Use :wq to save them or :q! to discard them. Decide which one you mean before pressing Enter.
E325: ATTENTION and a .file.swp name
A swap file exists, usually because another session is editing the file or an earlier session crashed. Check whether another terminal has the file open. If the old session is gone, open the file and use :recover to inspect the recovered buffer, then write it and remove the stale swap file only after you are sure.
Arrow keys print A, B, C, D
This is classic vi behaviour: the terminal sends escape sequences and vi does not interpret them as arrows. Use h, j, k, and l. Vim usually understands the arrow keys, so this symptom points to a strict vi or a terminal mismatch.
The screen is garbled after a resize
Press Ctrl + L to redraw. If the terminal is still confused, save your work, quit, and run reset at the shell prompt.

Tamlinux provides micro as its baseline editor, not vi. On the Arch-based system checked for this page, the vi command comes from the optional ex-vi-compat package. Its vi is a small wrapper that runs vim -C: Vim in vi-compatible mode, ignoring Vim configuration except EXINIT and .exrc. You therefore get Vim's bug fixes and terminal handling with vi's defaults, not a historical vi binary. Other systems may provide nvi, BusyBox vi, or another clone.

Check yourself

Decide your answer before you reveal it.

You press dd, then p. Where does the deleted line go?

dd removes the line and stores it in the unnamed buffer. p puts that text after the current line, so the line reappears one line lower. P would put it before the current line.

Why does d2w delete two words rather than a word and then something else?

A count before a motion multiplies the motion: 2w reaches two words forward. The operator d then deletes everything from the cursor to that destination. Counts and operators compose instead of being separate commands.

What is the safest first action when vi shows a swap-file warning?

Stop and find out whether another session is editing the file. If one is, quit this session and use the other one. If the other session crashed, use :recover and compare the recovered text with the file on disk before overwriting anything. Deleting the swap file first destroys the evidence.

Grammar, buffers, and implementations

Reference

vi's command language takes an optional count, an operator, another optional count, and a motion: [count] operator [count] motion. A doubled operator works on whole lines: dd, cc, yy. A handful of commands take a text object or a search target instead of a simple motion.

PartExamplesMeaning
Motionsh j k l w b e 0 ^ $ GCharacter, word, line, and buffer movement. gg is a Vim extension for the first line.
Search motionsf x, t x, %Move to or before a character; % jumps to the matching bracket.
Operatorsd c yDelete, change, or yank the text a motion reaches.
Put and undop P u .Put after or before, undo one change, repeat the last change.
Registers"a, "1, "_Named, numbered, and, in Vim, black-hole registers used before a command.
Marksma, 'aSet and return to a named position.
Ex command line:Run ex commands such as :s, :g, and :w.
Visual selectionv, V, Ctrl + VVim extensions for character, line, and block selection. POSIX "visual mode" means the full-screen mode, not this selection.

How it works

vi keeps an edit buffer, a cursor position, a set of registers, marks, and an undo state. The screen is a view of the buffer, not the file. Changes accumulate in memory until :w writes them. In Vim, the undo tree also records branches, and an optional undo file can persist that history across sessions.

vi and ex are two interfaces to the same state. POSIX specifies the screen editor in the vi utility and the command language in the ex utility; the vi specification covers only open and visual modes and refers to ex for the rest. Q enters ex mode; the ex command visual returns to the screen. A colon in vi starts an ex command line, which is why the same s, g, and w commands work in both.

Compatibility is an implementation choice, not a single behaviour. Vim starts with nocompatible when it finds a vimrc, and with compatible when invoked as vi or with -C. The compatible option changes many small defaults, including the behaviour of some commands and options. vim -u NONE skips your vimrc; --noplugin also skips plugins. Neither makes Vim identical to a 1970s vi, and neither is needed just to edit a file.

Swap files are a Vim feature, not part of POSIX vi. Vim writes .filename.swp in the same directory by default, updating it after a period of inactivity and after a number of typed characters. If the process dies, the swap file holds enough information to recover. :recover reads it; vim -r file does the same from the shell; :preserve forces a swap write; :set noswapfile or -n disables the protection. The trade is explicit: no swap file means no crash recovery for that session.

Advanced usage

Operators compose with counts and motions rather than forming a fixed list. These examples are illustrative Vim commands, not exercises:

d2w      delete two words
ci"      change the text inside the next double quotes
yap      yank the current paragraph, including surrounding blank lines
>>       indent the current line one shiftwidth
3dd      delete three lines
:g/TODO/d    delete every line containing TODO
:%s/old/new/gc   replace every old with new, asking before each change

ci", yap, and >> are Vim text-object and operator extensions. A strict POSIX vi does not provide them. Macros are likewise implementation-specific: Vim records with qa, ends with q, and replays with @a. POSIX vi instead has the @ command for executing a named buffer, which is powerful but less convenient for recording.

Edge cases

  • Modelines are executable input. Vim can read settings from a comment in the first or last few lines of a file. A malicious file can therefore try to set options when opened. Use :set nomodeline for untrusted files, or start Vim with modelines disabled. Do not treat a modeline as harmless metadata.
  • Encodings and BOMs. :set encoding controls Vim's internal encoding; fileencoding and fileencodings control conversion on read and write. Reopen a wrongly decoded file with :e ++enc=latin1 instead of retyping it. A byte-order mark can survive a round trip and surprise the next tool.
  • Very large files. Swap files add disk writes, syntax highlighting costs memory and time, and one enormous line is slow to redraw. -n, :syntax off, and a larger updatetime can help, at the cost of crash recovery and feedback.
  • Concurrent editing. Two Vim sessions on one file can both write and silently lose one set of changes. The swap warning is the protection, not an obstacle; do not disable it just to silence the message.
  • Read-only files. view and vim -R open read-only. :w still fails if the file permissions forbid writing; use the proper ownership or a deliberate save-as, not a workaround that leaves a root-owned file behind.
  • Terminal and locale assumptions. vi assumes a terminal that can address the screen and a locale whose encoding matches the file. A mismatch produces broken accents, wrong cursor positions, or a corrupted display. Ctrl + L redraws; reset repairs the terminal after exit.
  • Undo is not a backup. Vim's undo history can be lost with the process, and a write can overwrite a good file with bad text. Keep important files under version control or take a copy before a large mechanical edit.

Check yourself

A colleague opens a downloaded file in Vim and reports that the editor "changed settings by itself" before any key was pressed. What mechanism explains this, and what would you inspect and change?

Vim's modeline feature reads specially formatted comments near the start or end of a file and applies the options they name. Opening the file is enough; no keystroke is required. Inspect the first and last few lines for a vim: modeline, check :set modeline?, and disable modeline processing for untrusted content with :set nomodeline or a startup rule. Treat the file as untrusted input, not as a harmless text document. The broader lesson is that an editor which executes file-provided configuration has a larger attack surface than one that only displays bytes.
