Truthful System Diagnostics and Logs

A log records what a program reported. Start with the symptom and its time, then find messages that can explain it. A frightening line alone does not establish a cause; an empty query does not establish health.

Read a small piece of the journal

Goal: you will be able to read recent messages and report what happened without changing the system.

Why it matters: “the display went dark after waking at 14:10” gives a helper a place to start. “Linux is broken” does not.

Before you start: open a terminal. Read First steps if needed. These commands only read logs; they do not restart services or remove evidence.

The journal is a collection of recorded messages. A unit is a named systemd component, such as a service. Type the command after $, without typing that prompt. --no-pager prints the result and returns to your shell.

Worked example: Read one service message

$ journalctl -b -u systemd-journald.service -n 1 --no-pager -o cat
Received client request to flush runtime journal.

Captured on an Arch Linux workstation, 2026-10-22. Your message may differ, or you may have no accessible matching entry.

  1. -b selects the current boot.
  2. -u selects the journal service; -n 1 limits the result to its latest entry.
  3. -o cat prints only message text. This message reports a request; it does not prove every service is healthy. For diagnosis, keep timestamps by leaving out -o cat.

Try it

Read the last two messages from the same unit, with their normal timestamps:

journalctl -b -u systemd-journald.service -n 2 --no-pager

Tell a helper your symptom, the time and timezone, the command you used, and what you actually saw. Review excerpts for private information before sharing.

If it goes wrong

No entries can mean there are no retained messages matching that boot and unit, or your account cannot read them. A permission notice means access is limited; it is not evidence that the service failed. Keep the notice and ask for help with access rather than changing log permissions. Nothing needs undo.

Check yourself

What does -b select here?

The current boot. It does not mean every saved boot or every login session.

Does one error message prove why your application stopped?

No. Match its boot, time and component to the observed symptom, then check surrounding evidence. An unrelated error can occur nearby.

New words

Journal
A collection of structured log entries.
Unit
A named component managed by systemd.
Boot
One run of the kernel, from startup until shutdown or restart.

A filter selects entries from a larger collection.

Select a useful evidence window

Goal: you will be able to choose a boot, component and time window, and explain what a filtered result can and cannot show.

Mental model

accessible retained journal
  -> boot -> unit or kernel -> time window -> optional priority filter

These constraints narrow the result together. Start with time and component; add priority later. Informational messages often describe the transition just before a failure. Boot offsets move after a restart: use journalctl --list-boots --no-pager to find and record a stable boot ID.

Worked example: An empty result has limits

This deliberately invented unit name lets you inspect an empty selection without causing a service failure.

$ journalctl -b -u tam-lesson-example.service -n 5 --no-pager
-- No entries --

Captured on an Arch Linux workstation, 2026-10-22.

  1. The query reads up to five entries for that name in this boot.
  2. It finds none in the accessible journal. It does not test whether a unit exists, runs successfully or has ever failed.
  3. For a real symptom, use the actual component and time. For example, this reads a fixed five-minute window; replace the dates with your event:
journalctl -b -u systemd-journald.service \
  --since '2026-10-22 14:00:00' --until '2026-10-22 14:05:00' \
  --no-pager

These are example query bounds, not a report of an incident. Local times use the machine's timezone unless specified otherwise.

Completion task

To select the previous retained boot and messages at error priority or more severe, fill in journalctl -b ___ -p ___ -n 20 --no-pager.

Use -1 and err. -p err includes priorities 0 through 3; it does not mean only priority 3. The previous boot must still be retained and accessible.

Independent task

A system service stopped during a known five-minute window in a saved boot. Write a read-only query using its boot ID and real unit name. Then say how you would widen the query if it returned nothing. No failure needs to be reproduced for this exercise.

Use -b BOOT_ID -u UNIT with --since, --until and --no-pager, replacing the uppercase placeholders. Check available boots and access, confirm the unit name and timezone, then widen the time bounds. Remove a priority filter before assuming that no useful messages exist.

Check yourself

A previous-boot query returns nothing. Can you conclude the crash left no evidence?

No. First check boot retention, permissions, scope, unit and time bounds. The query only describes entries it could select.

A message says a device failed after wake. What strengthens a causal explanation?

A matching boot and time window, the observed symptom, preceding transition messages, and a prediction that separates competing causes. Mere proximity or a priority label is weaker evidence.

Separate missing evidence from competing causes

Reference and how it works

Different journal fields combine as AND; alternative values for the same field combine as OR. A separate + combines match groups as OR. Use journal fields when a unit selector is too broad. Preserve the query with the boot ID and time bounds so another investigator can repeat the selection.

The kernel's printk messages occupy a bounded ring buffer. dmesg reads kernel messages, not saved prior boots. Journald can retain kernel messages beyond that buffer's lifetime. Volatile storage under /run/log/journal does not survive reboot; persistent storage is under /var/log/journal. Configuration, access and retention determine which history a query can actually read.

journalctl --verify checks internal journal-file consistency. Authenticity verification additionally requires a journal created with Forward Secure Sealing and the matching verification key supplied with --verify-key. A structural pass does not prove that all events were recorded or that a message's causal interpretation is correct.

Think through a diagnosis

Suppose a display is dark after wake. I first separate “the machine never resumed” from “the machine resumed but the display did not.” I match the reported time to kernel sleep/resume messages and session evidence. Evidence that a session process continued after resume weakens the first explanation; it does not prove the monitor link is healthy. If the journal ends abruptly, I leave both a hard hang and missing/unflushed evidence open. Each branch needs an observation that could disprove it.

Edge cases and cost

Rate limiting, retention, unavailable disks and unflushed writes can leave gaps. Wall-clock adjustments complicate time matching; compare monotonic timestamps within the same boot using -o short-monotonic when needed. Broad scans and continuous follow mode add work and noise. Prefer a bounded query, then widen it deliberately.

Keep evidence before proposing a storage change. Vacuuming removes archived journal files and cannot be undone without a separate copy; it is not a diagnostic step. Nothing in this lesson changes retention or requests cleanup.

Explore

For a known event, write two explanations, the evidence each predicts and a bounded query that could contradict each one. Distinguish an absent message from a message that explicitly reports failure. Do not trigger a crash to fill an evidence gap.

Check yourself

Why is “the last error before the crash caused it” an incomplete conclusion?

The last retained message may be unrelated, delayed, or followed by messages that were never flushed. Correlate component state, timestamps and a discriminating prediction. State what remains unknown and what observation would change the explanation.
