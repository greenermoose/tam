Emergency Disaster Recovery

This page helps you decide what to do when your computer stops responding.

First notice what still responds. A frozen window, an unavailable desktop, and a computer that cannot start need different responses.

Record the symptom before escalating

Goal: you will be able to record what stopped responding, identify your terminal and recognize when recovery needs help.

Why it matters: restarting the whole machine can discard unsaved work and the evidence needed to understand a single stuck application.

Before you start: read The shell. Use a working terminal for this read-only exercise. Do not reproduce a freeze, end a real application, change consoles or reboot as practice.

Type the command after the terminal prompt, without $, and press Enter. A terminal emulator is a window containing a shell. A Linux virtual console is a different terminal surface; neither guarantees that a machine with a graphics or kernel fault will respond.

Worked example

$ tty
/dev/pts/0

Captured in a pseudo-terminal on an Arch Linux workstation, 2026-10-21. Your output will differ. A /dev/pts/N path identifies a pseudo-terminal, not the virtual-console number of the graphical session.

What just happened

  1. tty reported the terminal attached to standard input.
  2. It did not diagnose the desktop or change sessions.
  3. A path such as /dev/tty2 would describe a virtual console instead. Do not assume your graphical session is on tty1 or tty7.

Try it

On paper, record a hypothetical symptom, which inputs still work, the approximate time and your terminal type. Mark hypothetical observations as such. If you have a second terminal window, query its terminal too; closing that extra window undoes opening it.

If it goes wrong

not a tty
Input may be a pipe or redirected file. Try from a terminal you opened yourself; do not add privileges.
No usable terminal
Do not keep launching programs. A separate virtual console or already-configured remote access may help only if its input, kernel, display and login services still work.

Recognize the next boundary

If the machine never reaches login, record the last visible stage: firmware selects a bootloader, the loader starts a kernel, the kernel gains access to the root filesystem, then login and desktop services start. A failure before login is different from one application freezing afterwards.

On many Linux systems Ctrl+Alt+F2 through F6 can select another console; key handling and login availability vary. Before an emergency, learn the actual graphical console and return key on your system. A GPU fault can prevent even text-console display. Stop and seek a documented recovery procedure if you cannot establish those details.

New words

Virtual console
A kernel terminal surface; it may have a login service.
Process
A running program instance. A window and the whole desktop need not share one.

Next step: choose level 2 to compare recovery options and inspect SysRq availability without using it.

Check yourself

Does /dev/pts/0 tell you which function key returns to the desktop?

No. It identifies a pseudo-terminal. Determine the actual graphical console separately; do not infer it from the trailing number.

One window stopped drawing but the terminal works. Should the first step be an emergency reboot?

No. Record the symptom and scope, save reachable work and use the application's documented recovery. A whole-machine reset affects much more.

Choose escalation from evidence

Goal: choose the appropriate recovery layer and check which keyboard SysRq operations are enabled without triggering them.

Mental model

one application --> application evidence and saved work
whole desktop --> console or configured remote access, if usable
kernel unresponsive --> emergency procedure, if supported
cannot boot --> retained fallback or verified rescue medium

Worked example

$ cat /proc/sys/kernel/sysrq
244

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ. This reads keyboard SysRq policy; it tests neither the physical key combination nor whether the kernel can handle an emergency.

For this setting, 0 disables keyboard operations, 1 allows all supported operations, and other positive values select categories by bits. The bits needed for REISUB are 4, 16, 32, 64 and 128, together 244.

Completion task

A hypothetical machine reports 16. Does it allow the full sequence? Classify that mask using the table, without changing it.

16 permits sync only. It does not enable keyboard mode changes, process signals, read-only remount or reboot. Do not treat that mask as proof that REISUB will work.

Independent task

Read your own mask. Record allowed categories and what remains untested: keyboard support, a responsive kernel, console visibility and disk completion. If the file is unavailable, record that limitation instead of enabling anything.

For 244, the needed categories are allowed; for 1, all supported categories are allowed. Neither proves successful disk sync or a working keyboard during a fault. For another mask, check each required bit. No configuration write or emergency keypress belongs in this task.

REISUB reference, not an exercise

On supported PC keyboards the combination is Alt+SysRq (often PrtSc) plus one lower-case letter at a time. Hardware handling varies. Do not try it while reading this lesson.

LetterActionPolicy bit
rRestore translated keyboard mode4
eSend TERM to processes except init64
iSend KILL to processes except init64
sAttempt filesystem sync16
uAttempt read-only remount32
bImmediate reboot, without its own sync or unmount128

Signals can lose unsaved work. Wait for sync and remount completion before rebooting; a fixed pause proves neither completed. An unresponsive kernel may handle none of these operations.

A product regression uses the recorded tam-deploy recovery procedure and the developer's instruction for that exact candidate. Boot, login, disk and firmware changes need a recorded rollback point and separate approval for each step. This read-only lesson provides no authorization to change policy, restart services or repair disks.

Check yourself

A machine allows 244. Does that prove it can recover from a kernel lockup?

No. The mask permits categories; it does not prove that keyboard input, the kernel or I/O will respond during a fault.

Is b by itself a clean reboot, and do three seconds after s prove sync completed?

No to both. b immediately reboots without syncing or unmounting. Completion requires evidence, not a fixed delay; a prepared emergency procedure must account for the available console and I/O state.

Prepare a rescue dependency record

Reference: a chroot changes pathname resolution for a process; it does not boot the installed kernel or recreate its running services. A rescue environment's running kernel and available drivers matter.

How it works

Before proposing a mount or repair, identify firmware mode, usable boot entry, rescue medium, storage driver, encryption mapping, filesystem and subvolume, root mount and separate boot/ESP mounts. Use the actual UUIDs, mount policy and retained recovery record. A sample device name from another machine is not an acceptable target.

Explore without repair

Read lsblk(8), findmnt(8) and chroot(1). Build a dependency table from existing inventory and the mount queries in Rollback. Leave inaccessible or unknown entries blank. Do not mount, unlock, chroot, rebuild images or reinstall packages to fill a cell.

Why Tamlinux uses recorded recovery

The deployment contract keeps package identity and generation evidence together while naming separate mutable and native state. Tamlinux currently provides read-only installation inspection and checks, not an installer apply/repair workflow. There is no Tamlinux installation medium to assume available.

Edge cases and cost

An encrypted root needs working credentials and mapping before access. A console can share the failed GPU path. Repeated rebooting can lose volatile evidence, and broad scans add I/O during a storage fault. Collect the smallest useful evidence that is still available. Preserve later data before any restore.

Think through a diagnosis

For a hypothetical post-update boot failure, first locate the last visible stage and retained fallback. If firmware cannot load it, investigate that boundary before proposing a chroot. If the kernel starts but cannot mount root, compare storage, encryption and root-selection evidence. Only after identifying the target and recording rollback should a specific repair be reviewed. This is a method, not a reported incident or ready-to-run procedure.

Check yourself

Why can a correct chroot still fail to repair the next boot?

The wrong boot filesystem may be mounted, the loader may select different files, or the rescue kernel may lack needed storage support. A chroot alone proves neither the next kernel nor the root subvolume selection.

What would justify replacing a guessed repair with an approved procedure?

A verified target and dependency chain, retained rollback evidence, a specific failure explanation and an explicit verification step. Then seek the required approval for each state-changing operation; unknown layout must stay unknown rather than becoming a copied command.
