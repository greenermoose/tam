Snapper: Btrfs Snapshots for System Rollbacks

Snapper adds configuration, numbering and metadata to filesystem snapshots. Learn to identify what a checkpoint covers before choosing it for recovery. Practice here is read-only inspection or a scratch metadata model; it creates, deletes and restores no real snapshot.

Identify the configured subvolume

Goal: you will be able to distinguish a Snapper configuration from a snapshot and state what a configuration query proves.

Why it matters: a configuration named root does not mean all your files are protected or that a bootable checkpoint exists.

Before you start: read the snapshot definition and rollback orientation. Snapper must already be installed and its configuration readable. Do not install it or create a configuration to complete this lesson.

Type after the dollar sign in your terminal. The first line printed names the columns; each following line names a configuration and its subvolume. This command lists configuration, not your saved checkpoints.

Worked example: List configuration without a service request

$ snapper --no-dbus --csvout list-configs --columns config,subvolume
config,subvolume
root,/

Captured with Snapper 0.13.2 on an Arch Linux workstation, 2026-10-21. Your configuration and output may differ.

  1. --no-dbus reads directly instead of contacting snapperd.
  2. --csvout uses plain comma-separated output.
  3. root,/ identifies a config for the root subvolume; it does not recursively include nested subvolumes or separately mounted data.

Try it

Run the query if Snapper is available. Name the config and subvolume from your own result. Then answer whether that result alone proves a usable snapshot exists. Change no settings.

It identifies only configuration. A snapshot inventory and checks of its data, boot dependencies and intended restoration procedure are still required.

If it goes wrong

If Snapper is absent, stop at the paper example. If access is denied or a configuration is missing, record that limitation; do not create a config or escalate privileges as practice. Direct operation bypasses D-Bus, not filesystem permissions.

Check yourself

Decide before revealing the explanation.

Does a root configuration prove your home directory is included?

No. Nested subvolumes and separate mounts are outside the root snapshot boundary. Check the actual layout and independent backup coverage.

Does --no-dbus grant administrator access?

No. It changes the communication mode. Filesystem permissions still apply; record an access limit rather than changing it.

Read checkpoint relationships before choosing recovery

Goal: you will be able to select comparison endpoints from an inventory and distinguish checkpoint creation from restoration.

Mental model

configuration -> numbered snapshot + metadata -> optional boot-menu entry
                                                -> optional snapshot boot
                                                -> separate restore procedure

Each arrow needs its own evidence. The words “pre:” in a description do not make a snapshot type pre. Snapper types are single, pre and post; a post refers to its pre number. They describe relationships, not different Btrfs snapshot mechanisms.

Worked example: Derive comparison endpoints

Create this fictional inventory in scratch space. Its columns are number, type and pre-number; it is deliberately smaller than real Snapper CSV.

snapshot_lab=$(mktemp -d)
printf '41 pre 0\n42 post 41\n43 single 0\n' > "$snapshot_lab/inventory"

$ awk '$2 == "post" { print $3 ".." $1 }' "$snapshot_lab/inventory"
41..42

Captured in a scratch directory on Arch Linux, 2026-10-21.

  1. Find the post row.
  2. Read its corresponding pre number.
  3. Construct the range from the relationship, rather than assuming adjacent numbers always form a pair. These numbers are not targets on your computer.

Completion task

Add another fictional pair to your scratch inventory:

printf '44 pre 0\n45 post 44\n' >> "$snapshot_lab/inventory"

Complete awk '$2 == "___" { print $3 ".." $1 }' with the type that supplies a pre-number, passing your inventory file.

$ awk '$2 == "post" { print $3 ".." $1 }' "$snapshot_lab/inventory"
41..42
44..45

The post rows carry the relationships. A single snapshot with a description starting “pre:” would still not be a pre/post pair. Output captured in a scratch directory on Arch Linux, 2026-10-21.

Independent task

Write a comparison plan naming config, confirmed endpoints, files of interest and data outside the snapshot. State why the scratch range must not be copied into a live command. Clean up:

rm -- "$snapshot_lab/inventory"
rmdir -- "$snapshot_lab"
unset snapshot_lab

Read a real accessible inventory for the chosen configuration and verify both endpoints. Record excluded mounts and later writes. Only a documented operation may use those actual IDs. The teaching file creates no snapshots and supplies no real recovery evidence.

The current native updater requests a snapshot with description “pre: Tamlinux native update” after its recovery gates and before the native transaction. It does not specify type pre, so the ordinary create default is single; it is not an automatic pre/post pair. A failed creation stops that transaction. Limine snapshot-menu generation belongs to the separately selected boot provider. Neither a description nor successful creation proves a boot entry or successful restore.

Check yourself

Decide before revealing the explanation.

The description says pre: but the inventory type is single. Is it half of a pre/post pair?

No. Description text is independent of type and pair linkage. Read the type and pre-number metadata; do not infer a relationship from the label.

A snapshot appears in the menu. What must still be verified before relying on it?

Its loader/image/root dependencies, usable data and credentials, excluded mounts, later-write preservation and exact restoration procedure. Menu visibility is one observation, not complete recovery acceptance.

How it works

In the usual root Btrfs layout, Snapper keeps /.snapshots/N/info.xml metadata beside the snapshot subvolume at /.snapshots/N/snapshot. Configured subvolume and filesystem layout are authoritative. D-Bus coordinates requests through snapperd; direct mode uses filesystem access without granting permissions; direct mutations can also bypass snapperd's coordination. A live environment's root is not the installed root: --root needs an already verified, appropriately mounted target. It does not unlock or discover the installation.

Number cleanup selects checkpoints by policy; timeline creation/retention and empty-pre-post cleanup have separate rules. Inspect the config, cleanup assignment and enabled timers before making a retention claim. Deleting or cleaning checkpoints can remove a needed recovery source; apparent free-space savings depend on shared extents. File comparisons across large trees can cost substantial I/O, so bound them to relevant paths where possible.

In classic Btrfs mode, Snapper rollback creates new snapshots and changes the default subvolume. A loader with an explicit root subvolume need not follow that default. Therefore a generic rollback command is not a universal Tamlinux restore recipe. Likewise, undoing selected files is not a whole-system restore.

Why Tamlinux separates the provider

Checkpoint management and boot entry generation have different owners and failure boundaries. The current Arch selection includes limine-snapper-sync; its exact package and consumer policy determine the generated entries and boot behavior. Root snapshots do not by themselves retain EFI files on a separate filesystem or firmware state.

Edge cases and failure modes

Excluded subvolumes, stale entries, changed encryption support and mixed-version data mounts can invalidate a recovery assumption. A snapshot can preserve crash-consistent filesystem data without application-level consistency. Booted read-only state may use an overlay; identify where writes go and preserve them before leaving it. Same-device snapshots do not survive device loss and are not independent backups.

Explore

Using a paper inventory, trace one snapshot from config and metadata to provider entry, image and root selection. Write separate checks for snapshot existence, menu generation, boot access and persistent restoration. Identify the evidence and rollback point needed before any future retention or restore change. Do not run cleanup, delete or rollback to complete the exercise.

Check yourself

Decide before revealing a model answer.

Why can a successful Snapper rollback leave the next boot using another subvolume?

The loader may pass an explicit subvolume selector, while classic rollback changes the filesystem default. Inspect both selectors and the provider contract; do not assume one controls the other.

How would you assess a proposal to keep only the newest snapshot?

Identify which recovery case each retained checkpoint covers, its boot-image dependencies, external backups and later-write policy. Confirm cleanup assignments and shared-space costs. A recent timestamp is not evidence of a known-good or bootable state; keep deletion pending until those needs are satisfied.
