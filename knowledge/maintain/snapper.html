Snapper: Btrfs Snapshots for System Rollbacks

Snapper manages Btrfs subvolume snapshots with metadata, numbering, and configurable retention. On Tamlinux, Snapper works alongside Btrfs snapshots and generation rollbacks to create read-only checkpoints of the root subvolume, and integrates with the bootloader via limine-snapper-sync so those checkpoints appear as bootable entries in Limine.

What is Snapper and how does it relate to Tamlinux?

Summary: Understand Snapper vs raw btrfs subvolume snapshot, how tam-update uses it, and how to inspect configs and existing snapshots.

Prerequisites: Basic familiarity with filesystems and snapshots.

What is Snapper?

  • Snapshot manager: Snapper is a tool for managing Btrfs subvolume snapshots, storing metadata (timestamps, descriptions, cleanup info) in /.snapshots/<N>/info.xml.
  • Built on Btrfs: Snapper creates subvolume snapshots; it does not replace Btrfs. You can still use btrfs subvolume snapshot directly, but Snapper adds naming, bookkeeping, cleanup policies, and (optionally) pre/post pairs.
  • Configs per subvolume: Snapper can track multiple configurations (e.g. root for /, others for home if configured).

Automatic snapshots on Tamlinux

Before performing native system upgrades, tam-update automatically creates a pre-update snapshot of the root subvolume:

snapper -c root create -d "pre: Tamlinux native update"

This creates a numbered snapshot entry under /.snapshots/<N>/snapshot (read-only by default for root checkpoints) with a description so you can identify it later.

Inspecting Snapper on your system

Check which Snapper configs exist:

snapper list-configs

List snapshots for the root config (note: some operations may require elevated privileges):

sudo snapper -c root list

Key points

  • Snapshots are cheap on Btrfs CoW: they share blocks until data changes.
  • Root snapshots are typically read-only checkpoints for rollback/boot selection, not for live mutation.
  • tam-update uses Snapper as part of its safe update flow; see Non-disruptive updates for context.

Creating, inspecting, and cleaning up snapshots

Summary: Create manual snapshots (single or pre/post), inspect differences with snapper status and snapper diff, and manage retention via cleanup algorithms and timers.

Creating manual snapshots

Create a single read-only snapshot with a description:

sudo snapper -c root create -d "manual: before testing changes"

Create a pre/post pair around an operation to track what changed between them:

sudo snapper -c root create --print-number -d "pre: config edit"
# ... make changes ...
sudo snapper -c root create -d "post: config edit" --pre-number <N>

Omitting -r allows writable snapshots in some configs; for system root checkpoints, treat as read-only and use descriptions to make them identifiable.

Inspecting differences

Show files changed between snapshots (or since last snapshot):

sudo snapper -c root status
sudo snapper -c root diff 1..2

These show added/modified/deleted files; you can diff individual files as needed.

Listing and understanding metadata

Each snapshot has a numeric ID N and lives under /.snapshots/<N>/ with:

  • snapshot/ — the read-only view of that subvolume state
  • info.xml — metadata (date, description, user, cleanup info, pre/post linkage)

Use sudo snapper -c root list to see numbers, dates, descriptions, and types (pre/post/single).

Cleanup and retention

Snapper supports cleanup algorithms controlled by config and timers:

  • number: keep a fixed number of snapshots
  • timeline: keep snapshots by age (hourly/daily/weekly/monthly/yearly)
  • empty-pre-post: remove pre/post pairs with no changes

Configuration lives in /etc/snapper/configs/root (and /etc/snapper/config-templates/ for defaults). Systemd timers handle automated cleanup:

  • snapper-timeline.timer — creates timeline snapshots (if enabled)
  • snapper-cleanup.timer — runs cleanup according to retention rules

You can also run cleanup manually:

sudo snapper -c root cleanup number
sudo snapper -c root cleanup timeline
sudo snapper -c root cleanup empty-pre-post

Deletion

Delete specific snapshots when no longer needed:

sudo snapper -c root delete <N>

Deleting a pre snapshot may affect its post pair; follow Snapper's behavior and ensure you don't delete snapshots you intend to boot.

D-Bus, recovery operation, and Limine boot integration

Summary: Use Snapper in recovery environments (without D-Bus), understand limine-snapper-sync and how snapshots appear in Limine, and be aware of boundaries (excluded subvolumes, read-only snapshots, rollbacks).

snapperd, D-Bus, and recovery operation

Snapper normally communicates with snapperd via D-Bus for coordination. In recovery/chroot environments (live media, or when the rootfs is mounted differently), D-Bus may not be available. Snapper supports direct operation:

  • --no-dbus: bypass D-Bus and operate directly on the filesystem
  • --root <mountpoint>: operate on a mounted root (e.g. when chrooted from rescue media)

Examples from a recovery context (adjust mountpoints):

sudo snapper --no-dbus --root /mnt list-configs
sudo snapper --no-dbus --root /mnt -c root list

Be careful to operate on the correct mounted root; mistakes can affect the wrong filesystem.

On-disk layout

Under each config's subvolume, Snapper maintains:

  • /.snapshots/ directory (subvolume) containing numbered snapshot dirs
  • /.snapshots/<N>/info.xml — structured metadata
  • /.snapshots/<N>/snapshot/ — read-only subvolume snapshot of root state at that time

The info.xml includes fields like description, date, type (SINGLE/PRE/POST), cleanup algorithms, and userdata. This metadata is what Snapper uses for listing and cleanup.

Limine integration via limine-snapper-sync

To make snapshots bootable from the Limine boot menu, Tamlinux uses limine-snapper-sync. It synchronizes Snapper snapshots into Limine boot entries so you can select a previous root snapshot at boot time.

How it works:

  • Service: limine-snapper-sync.service (and associated tooling) runs after snapshots are created/updated to regenerate Limine menu entries for available snapshots.
  • Config/recipe: Provided via limine-snapper-sync package; Tamlinux's boot-selection contract integrates it with Limine configuration generation.
  • Output: Updates /boot/limine.conf (and any UKI/snapshot boot entries as configured) to include entries like "Boot from snapshot N: ..." pointing to the corresponding /.snapshots/N/snapshot root.
  • Boot behavior: Booting a snapshot means the kernel/initramfs is loaded as normal, but the root filesystem is mounted from the read-only snapshot subvolume. This gives you a known-good state without modifying the current active root.

See Boot Process, UKIs, and Kernel Updates for details on how Limine and UKIs are generated; limine-snapper-sync extends that by adding snapshot-based boot entries.

Boundaries and safety

  • Read-only snapshots: Root snapshots created as checkpoints are typically read-only. Do not expect to persist changes to a booted read-only snapshot; changes go to the active root subvolume (or CoW layer) depending on mount options. To "rollback" persistently, you would replace/restore the active root subvolume from a snapshot — follow established Tamlinux rollback procedures (see Snapshots and generation rollbacks and Linux boot fallbacks and rescue routes).
  • Excluded subvolumes: Snapper tracks the configured subvolume (usually root). /home, /var/log, /var/cache, or other subvolumes may be separate and not rolled back by booting a root snapshot. Be aware of what is included/excluded in your Snapper config.
  • Not a replacement for backups: Snapshots protect against broken updates/config changes but do not protect against hardware failure, full-disk corruption, or deletion of the Btrfs filesystem itself. Maintain external backups.
  • Recovery context: In emergency recovery (live media), use --no-dbus --root to inspect/list snapshots safely. Do not blindly delete snapshots you might need to boot into.
