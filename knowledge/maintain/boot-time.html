Why startup took as long as it did

This page shows how to find out where the time went between pressing the power button and being ready to work.

The tam-boot command reads the record the system keeps of each startup and explains it. It only reads; it changes nothing and needs no administrator rights.

What tam-boot tells you

Startup happens in phases: the computer's own firmware, then the program that picks what to start, then Linux, then the services that bring you to a login prompt. tam-boot shows how long each phase took.

Why it matters

A startup can feel slow because the computer is busy, or because it is waiting for you. If your disk is encrypted, the computer waits while you type the unlock passphrase, and it waits again at the login prompt. tam-boot keeps those two kinds of time apart, so you know whether there is anything to fix.

How to think about it

Think of a train journey. Some of the trip is the train moving; some is the train standing at a station while passengers board. Making the train faster does not shorten the time people take to board. tam-boot labels each part either machine (the train moving) or waiting for you (boarding).

New words

Firmware
Software built into the computer that starts the hardware before any operating system runs.
Kernel
The core of the operating system, which manages hardware and runs programs.
Passphrase
The words or characters you type to unlock an encrypted disk.
Journal
The system's log, where startup messages are recorded with their times.

Read a startup report

Goal: you will be able to read a tam-boot report, separate machine time from waiting time, and look at an earlier startup.

Worked example

$ tam-boot
Boot da1124be  kernel 7.2.11-arch1-1.1

  firmware       9.98 s   machine
  loader         1.95 s   machine
  kernel        13.62 s   = 5.47 s machine + 8.16 s waiting for you (disk passphrase)
  userspace      5.19 s   machine, to multi-user.target
  text login    17.05 s   getty@tty1 ready
  sign-in       43.73 s   waiting for you (26.69 s since prompt)
  user session  43.94 s   user@1000 default.target ready
  desktop      1133.24 s   graphical-session.target ready

  Machine time to text login: 22.6 s  (30.7 s total minus 8.2 s waiting)

Captured on an Arch Linux workstation running Tamlinux 0.6.18, 2026-11-07, with tam-boot 0.1.0. The report also lists kernel pauses, shown at Expert. Your numbers will differ.

What just happened

  1. The first four rows are durations: how long the firmware, the loader, the kernel and the startup services each took.
  2. The kernel row is split. About 8 seconds of it was the computer waiting for the disk passphrase, so the kernel itself worked for about 5.5 seconds.
  3. From text login on, each number is a point in time counted from when the kernel started, not a duration. The text login prompt appeared at 17 seconds; someone signed in 26.7 seconds after that.
  4. The desktop row is late because Tamlinux starts at a text console and the graphical desktop starts only when you ask for it with tam-desktop. That number mostly measures when you asked.
  5. The last line subtracts the passphrase wait from the total that the init system reports, which leaves the time the machine itself spent.

Try it

Run tam-boot, then tam-boot list to see which startups the journal still holds, then tam-boot -1 to explain the startup before this one. Compare the two machine-time lines. Every command here only reads.

If it goes wrong

Only boot 0 is listed
The journal may be kept only in memory, so earlier startups were lost at shutdown. See log evidence for how the journal is stored.
tam-boot: failed to analyze boot
The journal did not return the messages for that startup. Check that the boot exists with tam-boot list, and that your account may read the system journal; journalctl(1) explains which groups can.
A row is missing
A row appears only when the journal holds its message. Firmware and loader times need firmware that reports them, and the passphrase split appears only when the disk was unlocked during startup.

tam-boot ships with the Tamlinux commands. --json prints the same analysis for scripts, and --top K sets how many kernel pauses to list (5 by default).

Check yourself

Decide your answer before you reveal it.

The kernel row reads 14 s = 4 s machine + 10 s waiting for you (disk passphrase). Will a faster kernel fix it?

Mostly not. Ten of the fourteen seconds were spent waiting for you to type the passphrase; only four were kernel work. Typing sooner shortens it; a faster kernel could save part of four seconds at most.

Why can the desktop time be many minutes on a healthy machine?

Because it is the moment the graphical session became ready, counted from kernel start, and the desktop starts only when you run tam-desktop. A long gap usually means you worked at the console first, not that something was slow.

Where the numbers come from

Reference

RowSource in the journal
firmware, loader, kernel, userspace, totalThe init system's Startup finished in … message for that boot
passphrase waitKernel message timestamps from Key type encrypted registered to the next kernel message that contains mapped to, BTRFS or PM: Image not found
text logingetty@tty1.service started
sign-inThe first new login session; the wait is measured from the text login prompt
user session, desktopThe user manager reaching default.target and graphical-session.target for UID 1000
slowest stepsGaps of 0.3 s or more between consecutive kernel messages, excluding the passphrase wait

How it works

tam-boot runs journalctl with the boot selector and reads its export format; it does not open journal files itself. A boot argument is either a relative number (0, -1, …) or a boot ID from tam-boot list.

Edge cases

  • The user-session and desktop rows read only UID 1000, the first account created on a typical install. Other accounts' sessions are not reported.
  • In version 0.1.0 the Slowest steps list shows the first qualifying pauses in boot order, not necessarily the longest. Use --top with a larger number, or --json, to see more.
  • A kernel pause names the messages on either side of it. The message before a pause is not proof of its cause; a driver can wait on hardware that logs nothing.
  • The passphrase split depends on the wording of kernel messages. A different storage layout can leave the wait counted as kernel machine time.

Check yourself

A pause of 1.4 s sits between a clock-watchdog message and a graphics-driver message. What do you do before blaming either?

Treat the pair as a location, not a verdict. Compare the same gap across several boots with tam-boot -1, -2 and so on; a gap that moves or vanishes is likely timing noise. If it is stable, read the full kernel log around it with journalctl -k -b and look for the driver that was initializing, then change one thing at a time with a recorded way back.
