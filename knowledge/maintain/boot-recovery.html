When your computer cannot start

This page explains ways to start or repair your computer when its usual startup fails.

If the usual startup fails, you may be able to start with a different set of system files or use separate recovery tools. The name shown in a menu does not tell you which problems an option can solve.

Before you start: read the boot chain. Use the fictional scenario below; no restart or boot-menu selection is needed.

A bootloader menu appears before Linux login. A text console is a login supplied by Linux. Write down what you actually saw, including the error text; “won't boot” is too broad.

Mental model

installed route: firmware -> internal EFI / loader -> image -> root -> login
snapshot route:  firmware -> internal EFI / loader -> image -> snapshot root
external route:  firmware -> external loader / image -> rescue environment
                                                        -> installed storage

These are models, not inventories. Snapshot entries may select different images; external media still needs working firmware, hardware support and credentials to access encrypted installed storage.

Worked example: A desktop failure

Scenario: the machine reaches a text login, but the graphical session fails.

  1. Record “text login reached; graphical session fails” and the time.
  2. Firmware, loader and enough of Linux to offer that login worked.
  3. Choose session evidence and the console recovery lesson before proposing a boot-file change.

This is a paper diagnosis, not captured host output or a claim that a console will always be available.

If it goes wrong

If you cannot distinguish firmware from loader, preserve the exact screen text and seek help with that evidence. Do not guess a disk number or overwrite an EFI file to see whether the message changes. If storage may be physically failing, prioritize a suitable data-recovery procedure rather than repeated repairs.

The current Arch provider combines Limine, generated images and snapshot entries. A second menu item is not evidence of independence. The boot-provider contract calls for retained native artifacts and an independent rescue route; product generation return has a different boundary.

Check yourself

Decide before revealing the explanation.

Does “fallback” always mean an older kernel?

No. It can mean another loader pointer, broader initramfs, another kernel or another system. Read the documented entry dependencies.

Does booting rescue media restore your files?

No. It starts a separate environment. Data restoration needs an identified backup or snapshot and a specific procedure.

Audit independence and recovery evidence

Reference

On x86-64 UEFI removable media, the default EFI program name is \EFI\BOOT\BOOTX64.EFI. This names an EFI program, not another Linux installation. Availability and fixed-disk fallback behavior must be verified against the firmware and platform procedure.

How it works

Model each route with firmware entry, EFI device and program, loader configuration, kernel/initrd, root selector, unlock policy and required data mounts. Two routes are independent only with respect to a named failure: different EFI files on one disk avoid a missing-file fault but share a device-loss fault. Record verified facts separately from inferred edges.

Why Tamlinux requires a separate boot handoff

Software generation selection does not cover native packages, boot artifacts, firmware state or all mutable data. Keeping exact old archives, configuration and generated files makes those restoration boundaries inspectable before a change.

Edge cases and failure modes

Snapshot and normal roots can share storage, external media can lack an encryption tool, and a root snapshot can exclude a later data mount. An entry can load an intact image whose modules cannot read the intended root. Rescue media can also become stale; verify its capabilities before relying on it. Larger images and duplicate payloads cost space and update time; repeated boots can waste time and stress failing storage.

Explore

Extend the scratch model on paper with loader configuration, image identity, encryption support and backup location. Name a specific failed component, remove every dependent route, then identify the remaining unknowns. Before a real boot repair, retain a verified rollback point and later writes, and approve a single specific operation with a success check.

Check yourself

Decide before revealing a model answer.

What evidence would justify “independent rescue route”?

Name the failure it avoids and record the separate loader/image/environment, firmware access, storage support and required credentials. A tested external boot can demonstrate startup; it still does not demonstrate that an intended backup restores correctly. State each acceptance boundary.

How would you distinguish an image failure from root-state failure without changing both?

Preserve the exact error and selected entry, compare documented image/root dependencies, and choose a separately approved diagnostic that changes one suspect dependency. If no safe discriminator exists, retain both explanations and prepare external inspection rather than claiming certainty.
