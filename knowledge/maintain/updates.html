Non-Disruptive Updates and Package Lifecycle

Updates have different owners across the base operating system, Tamlinux product packages, and user tools. Check each layer with its owner, and follow the recorded Tamlinux package assembly and deployment workflow for product changes.

Safe updates and package status

Summary: Check native Arch package updates without changing the system, and identify the separate owners for Tamlinux and user-tool updates.

Prerequisites: Basic command execution (The Shell and Streams) and the System Maintenance overview.

Command sequence

tam-update --check

What just happened

  • tam-update --check asks Arch's checkupdates for the native repository upgrade preview; it does not report Home Manager or Mise updates.
  • Applying native system updates is a separate operation with recovery-readiness requirements and a package transaction. Follow the system update guide before running it.
  • Update Tamlinux product software only through a recorded tamlinux-packages assembly and tam-deploy.

Best practice

Follow the appropriate update path for each layer: use the system update guide for native package transactions and the Tamlinux lifecycle for product deployments. Treating all layers as one update command can miss steps—whether a reboot is required depends on what changed.

Worked example

Trace which package management layer owns a specific command or file on your workstation:

pacman -Qo /usr/bin/bash
command -v tam
readlink -f "$(command -v tam)"

Package versions and executable locations vary by machine and deployment. Use the local output to identify the owner; a command's presence on PATH alone does not show which package or deployment supplied it.

Completion task

Identify which package manager and repository provides the curl binary on your system. Complete the command below by filling in the missing flag (marked with ___):

pacman ___ /usr/bin/curl

Target output: /usr/bin/curl is owned by curl <version>.

Verification hints

  • The -Q option queries the local package database, and -o (owns) resolves a filesystem path to its owning package.
  • Check the availability of package managers on your host with tam inspect.

Inode unlinking mechanics and running process tracking

Summary: Examine the filesystem mechanics of unlink(2), directory entry deletion versus active inode reference counts, and identify processes holding replaced binaries.

POSIX inode unlinking semantics

In Unix and Linux filesystems, a directory entry is merely a hard link associating a filename with an underlying inode number. When a package manager installs an updated executable (e.g. /usr/bin/nvim):

  1. The package manager unpacks the new file to a temporary name in the same filesystem.
  2. It calls rename(2) or unlink(2) to point /usr/bin/nvim to the new inode.
  3. Any process currently running the old executable still retains an open file descriptor or memory mapping to the previous inode.
  4. The kernel maintains the previous inode data on disk as long as its open reference count exceeds zero. Storage space is freed only when the last running process closes the file or exits.

Inspecting unlinked files held open in memory

To detect running daemons or user processes that continue executing deleted or upgraded code on disk, query open file references with lsof:

lsof +L1

Any entry marked with a link count of 0 ((deleted)) indicates an active process running an unlinked inode. Restarting the specific service (via systemctl restart <unit>) or closing and re-opening the application smoothly migrates execution to the newly installed binary without disturbing other workstation workloads.
