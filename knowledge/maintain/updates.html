Checking and updating your software

This page explains how to check your software and prepare for updates safely.

Understanding software updates

Programs on your computer need periodic updates. Updates fix security vulnerabilities that could put your data at risk, repair bugs that cause crashes, and ensure tools remain compatible with modern standards.

Why it matters

A well-maintained system stays dependable. Before applying an update, however, it is important to know what version you currently have installed and how updates work, so you do not accidentally change software during a critical task.

How to think about it

Think of software updates like routine maintenance on a car. You inspect the vehicle regularly to check fluid levels and tire pressure before setting out on a long trip. Inspection is completely safe and changes nothing; replacement of parts is a deliberate step performed when you are prepared.

New words

Package
A bundle containing a program, its documentation, and supporting files managed as a single unit.
Rollback
Returning software to a recorded, previously working state if an update causes problems.

Inspect a package without changing it

Goal: you will be able to read an installed package version and distinguish inspection from an update.

Worked example

$ pacman -Q bash
bash 5.3.20-1

Captured on an Arch Linux workstation, 2026-10-21. Output differs when a different version is installed.

What just happened

  1. The -Q option tells the package manager to query the local database of installed software.
  2. The command prints the package name followed by its exact installed version.
  3. No files were downloaded, changed, or deleted.

Try it

In your terminal, query the installed version of coreutils using pacman -Q coreutils. Compare the reported version with the worked example.

If it goes wrong

package '...' was not found
Check the exact package name. The tool may not be installed as a system package or may be managed by another tool.
command not found
Pacman is the native package manager on Tamlinux's base system. If pacman is absent, check your shell environment.

Tamlinux organizes software into rootstock (the base Linux distribution) and cultivar (Tamlinux desktop and agent tools). Inspection queries are read-only and require no administrator privileges.

Check yourself

Answer before revealing the explanation.

Does pacman -Q bash update Bash or report its installed version?

It reports the installed version. Querying the local database is read-only and does not contact remote servers or modify files.

Can a single package query confirm that all system software is up to date?

No. It only checks the specific queried package against the local installation database.

Illustrative reference

$ pacman -Qo /usr/bin/bash
/usr/bin/bash is owned by bash 5.3.20-1

Captured on an Arch Linux workstation, 2026-10-21. -Qo identifies the package responsible for a specific filesystem path.

To compare a filesystem name against an open file descriptor (explaining how an already-running process keeps old code after an on-disk replacement), run this read-only-to-system scratch experiment:

$ work=$(mktemp -d)
$ printf 'old\n' > "$work/active.txt"
$ exec 3< "$work/active.txt"
$ printf 'new\n' > "$work/next.txt" && mv "$work/next.txt" "$work/active.txt"
$ cat "$work/active.txt"; cat <&3
new
old
$ exec 3<&-; rm -- "$work/active.txt" && rmdir -- "$work"

Captured on Arch Linux. Descriptor 3 still refers to the unlinked original inode while opening active.txt by name reaches the replacement inode.

Why must the rollback boundary match the layer being updated?

Reverting a user configuration generation cannot undo changes made to the root filesystem packages, and vice versa. Each layer requires its corresponding recovery tool.

What does an immutable generation omit?

Mutable documents/settings and potentially other native or boot state; recovery planning must identify each affected boundary.
