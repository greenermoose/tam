Updates and Package Ownership

First identify which layer owns the software. Updating the wrong layer can leave the running command unchanged or bypass its recovery procedure.

Inspect a package without changing it

Goal: you will be able to read an installed package version and distinguish inspection from an update.

Why it matters: a version report is evidence you can share before deciding whether anything needs to change.

Before you start: read Shell and streams. This is a read-only Arch package query, with no privilege prompt.

Open a terminal. Type the command after its prompt and press Enter; do not copy the leading $. Output is a report, not another command. Do not add administrator privileges to a query.

Worked example

$ pacman -Q bash
bash 5.3.20-1

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ when a different Bash package is installed.

What just happened

  1. -Q queried the installed package database.
  2. The first field names the package, followed by its installed version.
  3. No package was downloaded, installed or restarted.

Try it

Query the installed coreutils package the same way. Record what your machine reports; no scratch files are needed.

If it goes wrong

Package was not found
Check the package name. It may be absent or belong to a different manager; do not install it just to complete a query.
Command not found
This example assumes Arch's pacman. Stop and identify the host's manager instead.

New words

Package
A manager's named unit of installed software.
Rollback
Restoring a known earlier software state using its recorded recovery procedure; it does not automatically restore documents.

Check yourself

Answer before revealing the explanation.

Does pacman -Q bash update Bash or report its installed version?

It reports the installed version. Querying the database is not an update and says nothing about remote update availability.

Can one native package query prove that every tool is current?

No. It covers that installed native package only; Tamlinux product software and user tools have separate owners.

Choose the owner and recovery boundary

Goal: identify the owner of a program and write an update plan with a matching rollback boundary.

Mental model

command name --PATH lookup--> selected executable
selected executable --owner check--> manager or package assembly
change that owner --> verify running version --> recover at the same layer

Worked example

$ pacman -Qo /usr/bin/bash
/usr/bin/bash is owned by bash 5.3.20-1

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ with the installed version. -Qo queries which native package owns a path; it is not a repository-origin query.

Completion task

Find the native owner of /usr/bin/ls using pacman ___ /usr/bin/ls.

$ pacman -Qo /usr/bin/ls
/usr/bin/ls is owned by coreutils 9.12-2

The missing flags are -Qo. Captured on an Arch Linux workstation, 2026-10-21; your output will differ with its package version.

Independent task

Choose one tool you use. Locate it with command -v, resolve its path with readlink -f if appropriate, then identify its owner. A function, alias, wrapper or Mise shim requires another step; a Nix store path alone does not identify which deployment selected it.

Record the typed name, selected path, resolved path, owner and installed version. Query pacman only for native files; inspect the tracked Home Manager declaration, Mise tool selection or recorded Tamlinux assembly for the other layers. If ownership remains unclear, leave the update pending rather than changing several managers.

Choosing

LayerOwnerRecovery evidence needed
Base OS and driversNative Arch packages; separately reviewed AUR packagesNative recovery checkpoint and boot recovery where relevant
Tamlinux productRecorded tamlinux-packages assembly via tam-deployRetained exact package assembly and generation, plus mutable state recovery
User toolsTracked Home Manager or Mise declarationPrior declaration and available generation or tool version

tam-update --check previews native repository upgrades using checkupdates; it does not cover Home Manager or Mise. It can refuse while inherited repositories remain active, and it needs the native pacman-contrib tool. A refusal is not permission to bypass the guard. Applying an update is a separate operation with recovery prerequisites.

Tamlinux product Test, Run and return operations use a recorded package assembly and the developer's instruction for that exact candidate. Direct activation of an arbitrary Home Manager generation is not that workflow.

Check yourself

Answer before revealing the explanation.

A native update preview is empty, but a Mise-managed tool is old. What follows?

The preview only covers native repository packages. Check the tracked Mise declaration and installed tool version; do not assume an empty native preview covers it.

A new Tamlinux package breaks the desktop. Is any old Home Manager activation an equivalent return?

No. Identify the recorded retained assembly and generation and use the approved tam-deploy return procedure, preserving mutable data as required. A generation alone does not establish the full candidate identity.

Separate a path from an open file

Reference: replacing a directory entry does not redirect existing open descriptors or mappings to the replacement inode. An unlinked file's data remains available while it is referenced. This does not imply that every updater uses the same replacement algorithm.

How it works

Compare rename(2) with unlink(2). Replacing a name and truncating an existing inode are different operations. Truncation can affect existing readers; renaming another file over the name preserves the old open file.

Explore

For this section, make a new temporary directory and enter it. These commands print nothing when they succeed. Keep this terminal open while you work through the section.

work=$(mktemp -d)
cd "$work"

$ printf '%s\n' old > active.txt
$ exec 3<active.txt
$ printf '%s\n' new > replacement.txt
$ mv replacement.txt active.txt
$ cat active.txt
$ cat <&3
$ exec 3<&-
new
old

Captured on Arch Linux, 2026-10-21. Descriptor 3 sees old; reopening the name sees new. No package, service or real application was changed.

Why this boundary matters on Tamlinux

The package assembly records exact component revisions and output paths. The deployment contract retains a previous package and generation before activation. That ties recovery to known bytes; restoring mutable settings or documents remains a separate responsibility.

Edge cases and cost

A process can mix old mappings with newly opened plugins or configuration. Detecting an unlinked file does not prove that a process is faulty or that a restart is sufficient. Replaced files can retain disk space until their last reference closes; broad scans and unnecessary restarts have costs. Scope inspection to the affected process and version first. Kernel or firmware changes need their own recovery procedure and may require rebooting.

Finish the exercise

Remove only the exercise files you created, then leave and remove the temporary directory. If a named file is missing, remove its name from the first command; if the directory is not empty, inspect it before removing more.

rm -- active.txt
cd /tmp
rmdir -- "$work"

Think through a diagnosis

First verify what command PATH selects. If it resolves to the expected package but an existing application reports its old version, compare a new invocation with the existing process. Only then examine mappings and descriptors. This separates wrong selection from an old process without repeating the update. This is a diagnostic method, not an observed incident.

Answer before revealing the explanation.

Why can a correct on-disk version coexist with an old running version, and when is restarting insufficient?

The running process can retain the old executable or mappings after replacement. Restarting may load the new version, but does not fix a wrong PATH selection, restore mutable state, or substitute for kernel/firmware recovery. Establish the affected layer first.
