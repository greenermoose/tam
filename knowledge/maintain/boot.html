Boot Process, UKIs, and Kernel Updates

This page explains the UEFI boot path and the current Arch-based Tamlinux provider setup. Bootloader and initramfs choices are base-system integration, not universal properties of every system that can run Tamlinux; the planned Void base may use different tools. Treat boot-image regeneration as a system-maintenance operation, not as a practice exercise.

Beginner: How a Linux System Boots (UEFI)

Summary: Understand the boot sequence from firmware to userspace on a UEFI system.

Prerequisites: Basic filesystem knowledge.

The UEFI boot sequence

  1. Firmware (UEFI): On power-on, UEFI firmware initializes hardware, checks NVRAM boot entries, and loads the bootloader from the EFI System Partition (ESP).
  2. ESP: The ESP (often mounted at /boot or /boot/efi) contains EFI executables (.efi files). UEFI looks for a boot entry pointing to a specific .efi file.
  3. Bootloader: On the current Arch-based Tamlinux deployment, Limine presents boot options, loads the kernel and initramfs into memory, and passes kernel command-line parameters.
  4. Kernel and initramfs: The kernel starts with the temporary initramfs, which provides the tools and modules needed to locate and mount the real root filesystem.
  5. Userspace: The configured init system takes over, starts services, mounts filesystems, and launches the display manager and desktop.

Key directories

  • EFI System Partition (ESP): Its mount point is system-specific. Inspect the active mounts and boot entries rather than assuming it is /boot.
  • Bootloader config: The current Arch-based provider uses Limine configuration under /boot; exact paths and generated entries depend on the installed provider.
  • Initramfs build config: The current Arch-based setup uses mkinitcpio configuration under /etc; another base may use a different image generator.
  • Package hooks: The active package manager and boot provider determine which hooks regenerate boot artifacts after package changes.

Intermediate: Bootloaders, UKIs, and mkinitcpio

Summary: Understand Limine, Unified Kernel Images, and how initramfs is built with mkinitcpio hooks.

Bootloaders on Tamlinux

The current Arch-based Tamlinux provider uses Limine. Limine can boot kernels directly or boot Unified Kernel Images (UKIs). The provider integrates its generated entries with configuration under /boot. This does not specify the bootloader for the planned Void base.

What is a Unified Kernel Image (UKI)?

A Unified Kernel Image (UKI) is a single UEFI PE executable that bundles the kernel, initramfs, kernel command line, and optional metadata (signatures, SBAT, etc.) into one .efi file. Benefits include:

  • Simplified boot entries: One file instead of separate kernel+initramfs+cmdline.
  • Secure Boot readiness: Easier to sign as a single unit.
  • Atomic updates: The whole boot payload is versioned together.
  • Discoverability: UKIs placed in /boot/EFI/Linux/*.efi can be discovered by some bootloaders/firmware.

The current Arch-based provider supports UKI generation through its Limine configuration and package hooks. Whether UKIs are enabled, their exact paths, and the command line they contain are properties of the installed provider configuration; inspect those sources before diagnosing a particular machine.

Initramfs and mkinitcpio hooks

The initramfs (initial RAM filesystem) is a minimal rootfs loaded with the kernel for early boot. The current Arch-based Tamlinux setup builds it with mkinitcpio; the planned Void base may use a different image generator. It needs the components required by that system's storage and root-filesystem configuration, such as:

  • Kernel modules needed to access storage (block, filesystem, encryption, LVM, etc.)
  • Userspace tools to mount the real root
  • Any necessary firmware files

Tamlinux builds initramfs using mkinitcpio. The HOOKS array in /etc/mkinitcpio.conf defines the boot process inside initramfs. Hooks run in order and each adds scripts/modules. Common hooks include:

  • base: Core initramfs functionality (required)
  • systemd: Use systemd inside initramfs instead of busybox
  • udev: Device detection via udev
  • autodetect: Only include modules needed for this hardware
  • microcode: Load CPU microcode updates early
  • modconf: Apply module configuration
  • kms: Kernel Mode Setting (GPU) early initialization
  • keyboard/sd-vconsole: Keyboard/console setup
  • block: Block device handling
  • sd-encrypt/encrypt/lvm2: Disk encryption/LVM support
  • filesystems: Filesystem support and mounting
  • fsck: Filesystem checks on boot

Current mkinitcpio configuration can include drop-ins under /etc/mkinitcpio.conf.d/. Changes to hooks or modules affect boot artifacts and must follow the system's boot-maintenance and recovery procedure; do not experiment on a running installation.

Hook lifecycle and ordering

Hook order is critical. For example, encryption hooks must run before filesystems, and block device detection before mounting. Run mkinitcpio -H <hook-name> for help on a specific hook.

Expert: Kernel Updates, Image Regeneration, and Safety

Summary: How the current Arch-based provider coordinates kernel packages, mkinitcpio, Limine and UKI generation.

What happens on kernel update

On the current Arch-based deployment, a native kernel package transaction can invoke provider hooks to regenerate the initramfs and boot entries. Exact packages, destinations and hook behavior depend on the installed provider and configuration; do not infer them from this general sequence.

  1. Kernel files: The native package manager installs the kernel and modules.
  2. Initramfs: The active image generator and its package hooks build the early-boot image.
  3. Boot entries: The installed boot provider updates entries or UKIs at its configured destinations.
  4. Verification: The transaction and provider checks must confirm the expected artifacts and recovery route before considering the update complete.

Key packages and hooks

  • mkinitcpio: Builds initramfs from kernel and config.
  • Limine provider hooks: The current provider set includes mkinitcpio integration and snapshot-entry synchronization; installed package versions and configuration determine their exact behavior.
  • Package hooks: Native package hooks may regenerate boot artifacts during a transaction. Review the transaction output and the provider's own documentation.

UKI generation specifics

When the installed provider is configured to build UKIs:

  1. The tooling bundles vmlinuz-*, the corresponding initramfs (initramfs-*.img or initramfs-*-fallback.img), and the kernel command line into a single PE executable.
  2. Resulting UKIs are typically written to /boot/EFI/Linux/<name>-<kernel-version>.efi (naming depends on the provider's configuration).
  3. Limine's config is updated to reference these UKI files. UKIs embed the cmdline, so the bootloader entry may be simpler.

Safety considerations

  • Never edit in-place blindly: Tools that rewrite boot images can corrupt them if used incorrectly. Certain objcopy invocations that rewrite files in-place can break checksum validation (e.g., breaking Limine BLAKE2B hashes). Always work on copies when inspecting/modifying UKIs.
  • Verify after updates: Use the documented provider checks to confirm boot entries point to present artifacts and a known recovery route remains available.
  • Keep a recovery route: Confirm the installed provider's fallback artifacts and recovery procedure before changing kernel or boot configuration.
  • Configuration changes: Changes to initramfs or boot configuration can prevent startup. Follow the dedicated boot-maintenance procedure; do not regenerate boot artifacts as an experiment.
  • Boot recovery readiness: Keep a known-good boot entry and understand which dependencies each route shares. See Linux Boot Fallbacks and Rescue Routes.

Troubleshooting tips

  • Check initramfs errors: Review the native package transaction and provider logs. Repair generation only through the documented boot-recovery procedure.
  • Verify UKI contents: Use tools like objdump, readpe, or inspect UKI sections if available (avoid in-place destructive operations).
  • Limine integrity errors: If Limine reports an artifact mismatch, preserve the error and follow the provider's recovery procedure; do not edit generated files by hand.
  • Check package hooks: Review the installed provider's documented hook locations and package state before changing them.
