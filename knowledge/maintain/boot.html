How your computer starts

This page explains what happens when your computer starts and where to look if startup fails.

These exercises look at information without changing startup files. This page also describes tools used by the current Arch Linux system; another system may use different tools.

Recognize the startup stages

Goal: you will be able to name the last observed boot stage and report what remains unknown.

Why it matters: a broken desktop and an absent boot menu need different evidence. Changing early boot files because a window is blank can introduce a second failure.

Before you start: open a terminal on a working Linux session; review filesystem paths. The query below only checks whether Linux exposes its UEFI interface.

Type the command after $, without the dollar sign, then press Enter. This is one line. It asks a question about a directory; it does not select a boot entry.

Worked example: One observable fact

$ if test -d /sys/firmware/efi; then printf 'Firmware interface: UEFI\n'; else printf 'Firmware interface: not exposed\n'; fi
Firmware interface: UEFI

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ if the interface is unavailable, including in some containers.

  1. test -d checks for a directory exposed by the kernel.
  2. The shell prints which branch it took.
  3. UEFI exposure says nothing about which loader file ran, the ESP mount point or whether a fallback works.
firmware -> EFI loader / boot menu -> kernel + early userspace (initramfs)
         -> real root filesystem -> services -> login -> desktop

Firmware starts the EFI program; the loader selects a boot payload. The kernel and its early userspace find the root filesystem, including unlocking storage when configured. The installed init system starts services and login. Some stages can be combined: a UKI packages boot components in one EFI file.

Try it

Run the query again. Then classify this paper scenario: a login screen appears, accepts credentials, and the desktop exits. Which stages were reached? Keep the scenario on paper; do not reboot to reproduce it.

Firmware, loader, kernel, root and login were reached. Investigate session startup next. That observation does not certify that every kernel driver or storage device is healthy.

If it goes wrong

“Not exposed” is not proof of a broken firmware entry. Record whether you are in a container, live environment or the installed session. If the computer cannot start a terminal, record the last visible message and use fallback orientation.

Check yourself

Decide before revealing the explanation.

Does a visible login screen prove that the desktop started?

No. Login and desktop startup are different stages. Report the screen reached and the next observed failure.

Does the UEFI query identify the EFI System Partition?

No. It tests kernel interface exposure. The actual partition and loader need separate configuration and mount evidence.

The machine code that starts before the operating system.

EFI System Partition: a partition containing EFI boot programs; its mount point varies.

Separate boot payload from installed state

Goal: you will be able to choose which configuration and artifact evidence a startup symptom needs before proposing a change.

Mental model

A boot choice ties together an EFI loader, configuration, a kernel and early userspace, root selection and later mounts. A Unified Kernel Image (UKI) combines a UEFI stub and kernel with optional initrd, command line and other sections. One file simplifies distribution and signing; it does not make an entire package transaction or root-filesystem update atomic.

Worked example: Bound a mount observation

$ findmnt -n -o FSTYPE /
btrfs

Captured on an Arch Linux workstation, 2026-10-21; your output will differ.

  1. findmnt asks about the mount covering /.
  2. FSTYPE selects the filesystem type.
  3. The result does not identify the boot image, loader or whether other paths are separate subvolumes.

On a mkinitcpio system, the effective configuration can include /etc/mkinitcpio.conf, drop-ins under /etc/mkinitcpio.conf.d/ and presets under /etc/mkinitcpio.d/. Build hooks assemble content; runtime hooks, or early systemd units, act during boot. Hook order and required storage modules depend on that system. Read its installed manuals and effective configuration without sourcing shell configuration files as commands.

Completion task

Complete the diagnosis: “Root is Btrfs, so the UKI must be at ___.”

No path follows from that fact. Inspect the active provider configuration, selected loader entry and image destination. A filesystem type does not specify an ESP mount or a UKI pathname.

Independent task

For a hypothetical failure after storage unlock but before login, write three facts needed before regenerating images: the last reached stage, the selected kernel/root identity, and evidence about the failing service or mount. State which findings would move attention back to early boot.

Record the exact last message and time, the selected entry and kernel/root parameters, then the relevant service/mount failure. A missing root device or mismatched image points earlier; a session service failure with root mounted points later. Leave unobserved facts unknown.

Check yourself

Decide before revealing the explanation.

A new kernel package is installed but uname still reports the previous release. Is generation proven broken?

No. The running kernel is the one already booted. Compare the installed image and package records before drawing a conclusion; an approved boot verification is separate.

Two UKIs share one ESP. What failure remains common to them?

Loss or corruption of that ESP can make both inaccessible. Separate image names do not establish an independent rescue environment.

How it works

Native transaction hooks may run the image generator and loader integration. Trace the actual installed hooks and provider recipes, not a presumed generic sequence. In mkinitcpio, an explicit config option can change which drop-ins are used; presets can override generation inputs. A fallback preset commonly omits autodetect to broaden modules, but the effective preset is authoritative. It need not contain an older kernel.

For a UKI, distinguish embedded sections from any runtime overrides and trust policy. A coherent single artifact is useful, but its replacement, loader configuration and separate root update still have separate failure points. Inspection must preserve the original bytes and metadata; rewriting an image can invalidate hashes or signatures.

Why Tamlinux separates this work

Native boot files and firmware state extend beyond the per-user product selection. The boot-provider contract retains exact native archives, effective configuration, generated images, EFI destinations and an independent rescue route before changing them. That makes recovery scope explicit rather than promising it from a package generation.

Edge cases and failure modes

A shadowing Limine configuration can select a different image from the file you inspected. An unmounted ESP can leave a convincing image in the underlying directory. Encryption keys or resume/root parameters can make a byte-valid image unusable. Broader fallback images cost space and build time; generation may also exhaust a small ESP. Avoid repeated regeneration while the target and capacity are unknown.

Explore

On paper, trace one provider update from package archive through hooks to image, loader and root. List the evidence required at each edge. Before any future system change, retain a verified rollback point and later writes, then authorize one specific operation. This lesson performs no image generation.

Check yourself

Decide before revealing a model answer.

How would you investigate a menu entry loading an unexpected kernel?

Retain the exact selected entry and running-kernel observation. Verify which EFI program and configuration actually supplied it, then trace the referenced image and generation inputs. Competing explanations include stale generation, a shadowing configuration and selection of another entry; do not rewrite every image to erase the distinction.

Why is a signed UKI insufficient to prove recoverability?

Signing can establish an artifact trust relationship. It does not preserve root data, supply missing unlock credentials, guarantee compatible modules or retain an independent boot route. Recovery needs those dependencies and a verified retained state.
