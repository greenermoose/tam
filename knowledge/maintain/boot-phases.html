Boot phases

This page names the parts of startup from turning on a computer to reaching a text login.

Tamlinux calls these parts boot phases. The exact screens and order depend on the machine and its configuration; some phases are combined or invisible.

From power on to login

  1. Firmware initialization: the computer's firmware starts hardware and prepares to find something to boot.
  2. Firmware boot selection: the firmware chooses a boot entry, automatically or from a menu opened by a machine-specific key.
  3. Bootloader selection: a bootloader may offer operating systems, kernels or recovery choices, then load the selected Linux boot image. Some machines use more than one bootloader.
  4. Kernel and early userspace: the Linux kernel starts hardware and runs the initramfs, a temporary early environment that prepares the installed system. If the root disk is encrypted, this environment may ask for its unlock password.
  5. Resume or normal startup: after required storage is available, a valid hibernation image can restore the earlier session. Otherwise the installed root filesystem is mounted and the init system starts services and a text login prompt.

A changing font or a blank screen can accompany a console or display-driver change. It does not by itself identify which program is running. A unified kernel image can package the kernel, initramfs and settings in one file.

After the boot phases

Signing in authenticates a user and starts a text session, usually with a command shell. Disk unlock and user login are separate steps. A resumed session may return directly to its previous state rather than show a fresh login.

Tamlinux's text-first startup plan provides terminal work after login and starts the graphical desktop only when requested with tam-desktop. The virtual console remains a way to work with text. A graphical session is optional; it is not a separate boot phase.

Remember the difference

Unlocking lets the computer access encrypted storage. Signing in identifies the user. You may need to do both.

Boot phases and runlevels

A boot phase describes part of the startup sequence. A runlevel is a configuration of services for a running system, traditionally identified by a number. The current Arch-based setup uses systemd targets to group units. Runit can also support named service sets called runlevels; its three initialization, operation and shutdown stages are a different use of the word stage. Neither runlevels nor targets are the firmware and bootloader sequence described above.

Handoffs and evidence

The firmware selects an EFI program; a loader may pass control to another loader before starting a kernel and initramfs. Early userspace prepares the root device and either resumes a hibernated system or switches to the installed root. Observe the actual entry and boot artifacts before attributing a screen to a particular program. A console font change alone is not that evidence.
