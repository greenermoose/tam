Checkpoints and Rollback Points

A checkpoint is a recorded state of a system component captured before making a change. It provides a known rollback point so you can return safely if an update or configuration change fails.

Understand What a Checkpoint Protects

Goal: you will be able to distinguish a recorded checkpoint from an application update or backup, and verify a scratch rollback point.

Why it matters: making a change without a known rollback point leaves you guessing if something breaks. A checkpoint records exact state at a point in time so you can return safely.

Before you start: read snapshot and generation rollbacks. This exercise writes only in a scratch directory; it makes no system changes.

Open a terminal window. Type commands without the leading $. A silent return usually means success. Stop if creating or entering the scratch directory fails.

Worked example

Create a temporary directory, record an initial state file, make a change, and restore from the checkpoint:

lab=$(mktemp -d)
cd "$lab"

$ printf '%s\n' 'port=8080' > service.conf
$ cp -p -- service.conf service.conf.checkpoint
$ printf '%s\n' 'port=9090' > service.conf
$ cat service.conf
port=9090
$ cp -p -- service.conf.checkpoint service.conf
$ cat service.conf
port=8080

Captured on Arch Linux, 2026-10-23.

What just happened

  1. You established a known-good configuration in service.conf.
  2. You created a checkpoint copy (service.conf.checkpoint) before mutating the configuration.
  3. After modifying the live configuration, you returned directly to the recorded checkpoint.
  4. Only the targeted file was restored; unrelated system state was unaffected.

Try it

Simulate an unexpected modification by appending an invalid setting timeout=bad to service.conf. Restore it again from service.conf.checkpoint and confirm the file is clean.

$ printf '%s\n' 'timeout=bad' >> service.conf
$ cp -p -- service.conf.checkpoint service.conf
$ cat service.conf
port=8080

Captured on Arch Linux, 2026-10-23.

If it goes wrong

cannot stat 'service.conf.checkpoint'
The checkpoint was not created or you changed directories. Run pwd and ls to verify your location.
Permission denied
Ensure you are inside the scratch directory created by mktemp -d.

Clean up the scratch environment when finished:

rm -f -- service.conf service.conf.checkpoint
cd /tmp
rmdir -- "$lab"
unset lab

Check yourself

Decide your answer before you reveal it.

Does creating a checkpoint automatically undo your mistakes while editing?

No. A checkpoint records state at a fixed moment. Restoration is a separate, deliberate action.

Does a file checkpoint replace an external backup?

No. Checkpoints on the same disk do not protect against storage hardware failure.

Match Checkpoints to the Changed Layer

Goal: you will be able to select the appropriate checkpoint type for a given system change and avoid false coverage assumptions.

Mental model

Different system operations modify different storage boundaries. A checkpoint must cover the specific layer being changed:

Layer               Boundary                 Checkpoint Mechanism
===================================================================
Root OS             / (root subvolume)       Btrfs snapshot via Snapper
Boot Chain          /boot (ESP & loader)     Quiescent boot-state archive
User Environment    ~/.config, dotfiles      Mutable settings checkpoint
User Packages       Nix store profiles       Home Manager generation

Taking a snapshot of the root subvolume does not capture files on a separate /boot filesystem, nor does switching a user package generation restore modified application database files.

Worked example

Inspect whether a proposed change crosses filesystem boundaries:

$ findmnt --noheadings --output TARGET,FSTYPE / /boot
/     btrfs
/boot vfat

Captured on an Arch Linux workstation, 2026-10-23. Your output may differ depending on partition layout.

  1. The root filesystem / is Btrfs, which supports Snapper snapshots.
  2. The boot filesystem /boot is VFAT, which does not support Btrfs subvolumes or snapshots.
  3. A root snapshot protects /usr and /etc, but a kernel or bootloader change requires a separate boot-state capture.

Completion task

Complete the check to find which mount point owns /home/alex/.config:

findmnt --noheadings --output TARGET,FSTYPE ___

$ findmnt --noheadings --output TARGET,FSTYPE /home/alex/.config
/home btrfs

Captured on Arch Linux, 2026-10-23. Passing the configuration path reveals whether user settings reside on the root subvolume or a dedicated /home subvolume.

Independent task

Write a three-line recovery plan for an update that changes both a native Arch package and a user application theme. Name which checkpoint covers the native package, which covers the user configuration, and what happens to personal documents.

A native package change is covered by a pre-update Snapper snapshot of /. The application theme is covered by a mutable settings checkpoint or Home Manager generation. Personal documents remain outside both boundaries and must be protected by independent backups.

Tamlinux organizes recovery by layer. The native updater requests a Snapper snapshot before host package updates, while user deployments via tam-deploy track package generations and mutable dotfile state. Software return alone does not restore modified databases or root-owned login files.

Check yourself

Decide your answer before you reveal it.

If an update only modifies a user CLI package in Home Manager, is a new boot-state checkpoint required?

No. User package changes do not touch /boot or kernel files. Creating boot checkpoints for user-layer changes is unnecessary churn.

Does rolling back a root filesystem snapshot restore files deleted from a separate /home mount?

No. Btrfs snapshots do not cross subvolume boundaries. Separate mounts require their own recovery checkpoints or backups.

Quiescence, Boundary Verification, and Avoiding Churn

Reference

Boot archiveWriters stopped; ESP unmounted or remounted read-onlySHA-256 digest of captured archive and specCapture immediately before firmware, loader, or kernel updates

How it works

A reliable checkpoint requires three properties:

  1. Quiescence: Background processes writing to the target scope must be stopped or flushed. Capturing a database or boot tree during active writes produces crash-inconsistent or corrupt archives.
  2. Explicit Boundaries: Checkpoints define precise path inclusion and exclusion lists. Sockets, FIFO pipes, temporary cache trees, and mounted shared volumes must be excluded.
  3. Integrity Verification: Upon capture, the checkpoint record stores cryptographic checksums (such as SHA-256) of the archive and its constituent files. Verification inspects the digest before any rollback operation is initiated.

Why Tamlinux chose this

Checkpoints are protective tools, not ritual barriers. Tamlinux captures a checkpoint immediately before an actual mutation of that specific layer, verifying integrity and coverage rather than generating repeated captures for unchanged components.

Untested intermediate builds are historical steps, not rollback targets. Long-term fallback returns to the trusted recovery anchor—the last version the user has lived on in normal daily operation. When testing a candidate, reusing the existing anchor material and one shared recovery procedure prevents checkpoint churn while guaranteeing a safe, tested route back.

Edge cases

  • Live-linked symlinks: Checkpoints capturing user dotfiles must record whether targets are real files or symbolic links pointing into store paths, preserving original permissions and link destinations.
  • Later-write preservation: Restoring a settings checkpoint after an unsuccessful trial must avoid blindly overwriting newer documents or mail delivered during the trial. Selective restore separates configuration from data.
  • Shared extent overhead: While Btrfs snapshots share extents upon creation, subsequent heavy write churn causes rapid disk space consumption. Checkpoints must be audited and retired once their associated stage move is complete.

Explore

Inspect the integrity of a candidate transaction or checkpoint manifest using standard verification utilities:

$ sha256sum -c <<'EOF'
d99e955535514a9fff82e7e54121e5f677f844ed592a1fd202153241f1368faa  package.tar.zst
EOF

Verifying recorded digests before initiating state restoration ensures that rollback targets have not suffered silent corruption or partial writes.

Check yourself

Why is it counterproductive to create fresh boot and root checkpoints when preparing an unactivated user-space candidate?

Unactivated candidates make no physical changes to boot or root storage. Generating checkpoints for unchanged layers creates disk overhead, risks displacing valid older checkpoints, and confuses build history with tested recovery anchors. Checkpoints belong immediately before actual mutations of that layer.

What distinguishes a recovery anchor from an arbitrary intermediate checkpoint?

A recovery anchor is a known-good system state that has been verified through sustained daily use. Intermediate checkpoints represent transient pre-change states of untested candidates. If a trial fails, rolling back to the recovery anchor guarantees a working system, whereas rolling back to an untested intermediate build leaves stability unproven.
