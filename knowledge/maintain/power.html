When your computer rests or sleeps

This page explains what happens when your computer rests, sleeps, or saves its state before turning off.

Turning off the screen, putting the computer to sleep, and saving its state before power-off are different choices. This page explains what each preserves.

Tell display blanking from system sleep

Goal: you will be able to name the three states and read which sleep labels your kernel offers, without putting the machine to sleep.

Why it matters: turning off a monitor does not stop a download. Losing power during ordinary suspend can lose the session held in RAM.

Before you start: use a terminal; the examples only read information from the kernel (the operating system's core). See First steps for terminal help and resources for an introduction to memory.

RAM is working memory used by running programs. It needs power to retain data. The files below are kernel interfaces: reading them asks a question; writing to them can change system behavior. This lesson uses cat to read only.

Worked example: Read available labels

$ cat /sys/power/state
freeze mem disk

Captured on an Arch Linux workstation, 2026-10-22. Your list may differ.

  1. freeze names suspend-to-idle.
  2. mem requests the suspend variant selected through mem_sleep, explained at Intermediate.
  3. disk names hibernation. Its presence is a kernel capability, not proof that storage, resume setup and drivers can complete a round trip.
StateWhat continues or survives?What to remember
Display blanking (DPMS)The session and programs can keep running.A dark screen is not proof of sleep or a secure lock.

Try it

Read the list on your own machine. Then classify these two descriptions: “the display is off but music still plays” and “the session is saved to disk before power-down.” No sleep experiment is needed.

The first is consistent with display blanking; it does not prove the precise desktop policy. The second describes hibernation.

If it goes wrong

A missing file or missing label can reflect kernel or platform support. Record exactly what you read; do not add a label by writing into the file. If a display is already dark, try a modifier such as Shift rather than Enter, then wait until you can see the focused window. Whether that input can wake the machine depends on its configuration and hardware. Nothing read here needs undo.

Check yourself

Does turning off a monitor stop a background download?

No. Display blanking affects the display. A separate system-sleep action can stop normal program execution.

Does disk in the list prove hibernation is ready to use?

No. The kernel offers the interface, but storage capacity, resume configuration, policy and driver behavior still matter.

New words

DPMS
Display Power Management Signaling; display power control, distinct from system sleep.
Suspend
A low-power system state retaining the session in RAM.
Hibernation
Saving a memory image to storage so the session can be restored later.

A process is a running instance of a program; display blanking alone does not suspend it.

Compare capability, selection and observed behavior

Mental model

The lines are separate. Kernel capability, a selected mode, policy approval and a successful wake are four different claims.

Worked example: Which suspend variant is selected?

$ cat /sys/power/mem_sleep
s2idle [deep]

Captured on an Arch Linux workstation, 2026-10-22. Your output may differ.

  1. Both listed variants are available on this machine.
  2. Brackets identify deep as the variant selected for the kernel's mem request. On ACPI systems it corresponds to suspend-to-RAM (S3).
  3. s2idle is suspend-to-idle. Its presence does not prove that the platform reaches a particular hardware residency or energy target.

Completion task

Complete cat /sys/power/___ to read what the kernel will do after writing a hibernation image, rather than selecting the suspend variant.

Use disk. The bracketed choice identifies the selected hibernation mode, such as platform or shutdown. Merely reading it does not hibernate the system.

Independent task

A display stays dark after a reported wake. Make an evidence plan that can distinguish a display problem from a system that never resumed. State the observation, the boot and time window, and which layers to inspect. Do not repeat the sleep cycle as part of this exercise.

Record the visible symptom and time. Compare kernel transition messages with session/service activity after the expected wake, using the log filters. Continued session activity weakens “never resumed” but does not identify a particular display fault. A missing log alone does not prove a hang.

Check yourself

Does [deep] prove that the last wake used S3 successfully?

No. It identifies the currently selected kernel variant for a mem request. Establish the actual request, policy and transition outcome from evidence.

Can a passing graphics-device check establish hibernation readiness?

No. DRM is Linux's graphics subsystem. Detecting a DRM device is only evidence that the device is present. It does not test image allocation, resume storage, firmware or driver restoration.

Reason about image allocation and resume boundaries

Reference and how it works

Hibernation freezes activity, prepares a memory image and saves it to storage. The final mode can use firmware-assisted ACPI S4 or power down. A restore kernel must locate and load the image before handing control back to the saved kernel. Image creation, storage write, power-down and device restoration are separate failure boundaries.

/sys/power/image_size is a best-effort upper limit in bytes, not a preallocated buffer or a report of the last image's size. If the target cannot be met, the kernel can still try the smallest possible image. Zero requests the smallest possible image; it does not guarantee allocation, successful resume, or reclamation of every clean cache page.

Zram swap consumes RAM. Hibernation also needs memory while preparing its image, as well as usable persistent swap for the image. Plenty of free disk space does not establish enough allocation headroom in RAM. Conversely, a small image target does not establish enough free space on the resume device. Inspect each budget separately.

Think through a failure

If image allocation fails, I first locate that stage in kernel and sleep service evidence. I compare RAM pressure, zram use and persistent swap headroom before proposing a parameter change. If the image was written and the desktop later remains dark, I instead investigate resume and device restoration. A display-link failure cannot be repaired by assuming every hibernation problem is an image-size problem.

Edge cases, energy and recovery

Wake sources, suspend residency and standby draw depend on firmware, devices and policy. Neither a watt figure nor a fixed wake time follows from a sleep label. Measure energy and latency on the actual hardware, and keep display power, platform standby and external peripherals in the measurement's scope. Hibernation permits RAM to lose power after the image is saved, but does not promise literal zero wall-plug draw.

Do not modify filesystems from another operating system and then resume an old hibernation image that still describes their earlier state. Resume needs a compatible, intact storage and boot path. The image preserves a session; it does not replace independent data backups.

Explore

Prepare a read-only failure matrix with four rows: image allocation, image write, image load and device restore. For each, name one observation that locates failure there and one competing explanation. Record unknowns instead of forcing an empty journal query into a verdict.

Any later system-changing trial needs its own agreed procedure, saved work and recorded rollback point before changing one parameter. This exercise does not change sysfs values, swap, boot parameters or sleep policy.

Check yourself

Why might image_size=0 fail to fix an allocation error even with abundant disk swap?

It asks for a minimal image, rather than guaranteeing sufficient working RAM. Unsavable or unreclaimable memory, zram pressure and allocation requirements can still prevent image preparation. Locate the failing stage and test a specific explanation; disk space and RAM headroom are different budgets.

What would a claim of successful hibernation and wake need beyond the available-state list?

Evidence of the requested policy, completed image write and restore, working devices and session after resume, and an explicit hardware/configuration scope. Energy and wake-time claims additionally need measurements. One successful cycle does not establish reliability across workloads.
