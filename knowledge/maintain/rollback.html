Snapshots and Generation Rollbacks

Choose recovery at the layer that changed. Software, documents and boot files can need different recovery evidence.

Separate software from your work

Goal: you will be able to distinguish a saved data copy from a return to an earlier software selection.

Why it matters: an older application can still open today's edited document. Returning software does not necessarily undo your edits.

Before you start: read Files and directories. This exercise writes only in a new temporary directory. It makes ordinary copies; it creates no snapshot or software generation.

Open a terminal and keep it open for this section. Type commands without the leading $. Copying or writing a file usually prints nothing on success. Stop if making or entering the temporary directory fails; this exercise needs no administrator privileges.

Worked example

Make and enter the exercise directory; these commands print nothing on success.

work=$(mktemp -d)
cd "$work"

$ printf '%s\n' before > note.txt
$ cp -- note.txt saved.txt
$ printf '%s\n' after > note.txt
$ cat saved.txt note.txt
before
after

Captured on Arch Linux, 2026-10-21.

What just happened

  1. You saved a separate copy before editing a file.
  2. The second write changed only note.txt; the copy kept the earlier text.
  3. No application version changed. Data and software have different histories.

A status or version query reads evidence without applying an update. An update changes the managed software; restoring our copied note changes data. Neither is accomplished just by reading a status report.

A snapshot records a filesystem subvolume's state. A Home Manager generation selects managed software and configuration. Neither automatically saves every document and boot file. An external backup provides a copy on separate storage.

Try it

Restore the exercise note from its saved copy, then read it.

$ cp -- saved.txt note.txt
$ cat note.txt
before

Captured on Arch Linux, 2026-10-21. Only the exercise note is overwritten.

If it goes wrong

cannot stat 'saved.txt'
The copy is missing or you are in a different directory. Check pwd and ls; do not restore a real document to complete the exercise.
Permission denied
Stop and check that you entered your own new temporary directory.

Finish the exercise

Remove only these exercise files, leave the directory, then remove it. Inspect anything unexpected before deleting more.

rm -- note.txt saved.txt
cd /tmp
rmdir -- "$work"

New words

Snapshot
A saved subvolume state; not automatically an independent backup.
Generation
A managed software and configuration selection, with boundaries.
Rollback
A return to a known earlier state through its recovery procedure.
Checkpoint
A recorded component state providing a specific rollback point.

Check yourself

Will yesterday's application necessarily restore yesterday's document?

No. Identify the document's own recovery source and preserve later edits before overwriting it. Software and data histories can be separate.

Can a snapshot on the same drive replace an external backup?

No. Drive failure can destroy both the working data and its snapshot. Recovery needs a usable independent copy.

Match the recovery boundary

Goal: prepare a recovery note naming what returns, what stays mutable and what evidence is missing.

Mental model

change --> owning layer --> retained recovery evidence
                       --> excluded state --> separate recovery

Filesystem type is a starting observation. It proves neither that a snapshot exists nor that it includes the changed files or can boot.

Worked example

$ findmnt --noheadings --output FSTYPE --target /
btrfs

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ on other filesystems. --target finds the mount containing the path. No recovery point was created.

  1. Root reports Btrfs.
  2. A Btrfs snapshot covers its source subvolume; nested subvolumes need separate consideration.
  3. This query says nothing about available snapshots, independent backups or restore tests.

Completion task

Find the filesystem containing /boot: findmnt --noheadings --output FSTYPE --target ___.

$ findmnt --noheadings --output FSTYPE --target /boot
vfat

Captured on the same workstation and date. Your output will differ with the mount layout. Here boot files live on a separate filesystem, outside a root subvolume snapshot. On a host without a separate boot mount, the query may report the root filesystem instead.

Independent task

Choose a hypothetical application update and document edit. Write four lines: owner, retained recovery identifier, excluded state, verification after return. Leave unknown identifiers pending. Create or activate nothing.

For Tamlinux product software: identify the retained assembly and matching generation; name the document/settings backup separately; propose checking installed package paths and affected behavior. If an identifier or data copy is unknown, the real change remains pending. A native package needs its own checkpoint and boot requirements.

Check yourself

Root is Btrfs and /boot is VFAT. Is a root snapshot a complete kernel recovery plan?

No. It omits the separate boot filesystem. Identify matching kernel, modules, boot files and the recovery procedure before changing anything.

An old generation exists but its assembly identity is unknown. Is product return ready?

No. Establish the recorded previous package selection, retained outputs and mutable-state recovery. A generation's age proves none of these.

Prove what the restored system selects

Reference: Btrfs snapshots initially share extents, need metadata space and do not recursively capture nested subvolumes. Software recovery and application-data consistency remain distinct concerns.

How it works

A Btrfs mount can select a named subvolume with subvol= or an ID with subvolid=. Setting the default subvolume does not override explicit selection. Top-level ID 5 is not necessarily what a mount without explicit selection exposes. Reconcile boot parameters, mounts, subvolume IDs and kernel/module versions before proposing a repair.

Explore

$ findmnt --noheadings --output TARGET,FSTYPE,FSROOT --target /
/ btrfs /@

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ. Here the filesystem root is /@. Compare the observation with recorded boot selection and fstab, without editing either. This is not an instruction to rename a subvolume or assume that layout on another host.

Why Tamlinux records the assembly

The deployment contract ties candidates to revisions and installed outputs and retains the previous package/generation. The product's commands/tam-deploy/tam-deploy restores the recorded selection. That makes software return checkable while keeping mutable-state recovery explicit.

Edge cases and cost

A snapshot may omit another mount, nested subvolume or store. Applications can require their own consistent backup protocol. Shared storage failure can affect original and snapshot together. Retained generations keep store objects reachable but do not back up personal data. Retaining divergent data consumes space; identify required recovery sources before proposing any pruning.

Think through a diagnosis

Suppose a restored root still boots the wrong kernel. First compare the selected entry with the retained kernel and modules. Then check the boot filesystem boundary and explicit subvolume options. Do not repeat a root restore just because its timestamp looks right. This is a diagnostic scenario, not an observed Tamlinux incident.

Check yourself

Why might changing the default subvolume leave the next boot unchanged?

An explicit subvol or subvolid option can still select another root. Trace actual boot and mount configuration and confirm retained kernel, modules and boot files. A default change alone proves no complete return.

What evidence makes a recovery claim credible?

Name retained software, included and excluded state, intended boot selection and the matching procedure. Record post-return selection and behavior in an authorized trial. A build or snapshot listing alone is insufficient.
