Returning to an earlier working state

This page explains how to return to an earlier working state after a change causes trouble.

What does rollback mean?

Different changes may require different recovery steps. A problem can affect software you installed, documents you edited, or the files used to start the computer. Returning one of those does not automatically undo the others.

Why it matters

An older application can still open today's edited document. Returning software does not necessarily undo your edits, and a snapshot on the same drive is not the same as an independent backup.

How to think about it

Think of three separate diaries: one for software versions, one for your documents, and one for boot files. Rolling back means opening the right diary and following its recovery procedure, not assuming one undo button covers everything.

New words

Snapshot
A saved filesystem subvolume state; not automatically an independent backup.
Generation
A managed software and configuration selection, with boundaries.
Rollback
A return to a known earlier state through its recovery procedure.

Separate software from your work

Goal: you will be able to distinguish a saved data copy from a return to an earlier software selection.

Before you start: read Files and folders. This exercise writes only in a new temporary directory. It makes ordinary copies; it creates no snapshot or software generation.

Open a terminal and keep it open for this section. Type commands without the leading $. Copying or writing a file usually prints nothing on success. Stop if making or entering the temporary directory fails; this exercise needs no administrator privileges.

Worked example

Make and enter the exercise directory; these commands print nothing on success.

work=$(mktemp -d)
cd "$work"

$ printf '%s\n' before > note.txt
$ cp -- note.txt saved.txt
$ printf '%s\n' after > note.txt
$ cat saved.txt note.txt
before
after

Captured on Arch Linux, 2026-10-21.

What just happened

  1. You saved a separate copy before editing a file.
  2. The second write changed only note.txt; the copy kept the earlier text.
  3. No application version changed. Data and software have different histories.

Try it

Restore the exercise note from its saved copy, then read it.

$ cp -- saved.txt note.txt
$ cat note.txt
before

Captured on Arch Linux, 2026-10-21. Only the exercise note is overwritten.

If it goes wrong

cannot stat 'saved.txt'
The copy is missing or you are in a different directory. Check pwd and ls; do not restore a real document to complete the exercise.
Permission denied
Stop and check that you entered your own new temporary directory.

Clean up

rm -- note.txt saved.txt
cd /tmp
rmdir -- "$work"

Check yourself

Will yesterday's application necessarily restore yesterday's document?

No. Identify the document's own recovery source and preserve later edits before overwriting it.

Can a snapshot on the same drive replace an external backup?

No. Drive failure can destroy both the working data and its snapshot.

Prove what the restored system selects

Reference: Btrfs snapshots initially share extents, need metadata space and do not recursively capture nested subvolumes. Software recovery and application-data consistency remain distinct concerns.

How it works

A Btrfs mount can select a named subvolume with subvol= or an ID with subvolid=. Setting the default subvolume does not override explicit selection. Reconcile boot parameters, mounts, subvolume IDs and kernel/module versions before proposing a repair.

Illustrative reference

$ findmnt --noheadings --output TARGET,FSTYPE,FSROOT --target /
/ btrfs /@

Captured on an Arch Linux workstation, 2026-10-21. Your output will differ. Compare the observation with recorded boot selection and fstab, without editing either.

Check yourself

Why might changing the default subvolume leave the next boot unchanged?

An explicit subvol or subvolid option can still select another root. Trace actual boot and mount configuration.
