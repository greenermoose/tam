Checking and managing the host firewall

This page explains what a host firewall does on your workstation, how Tamlinux inspects whether incoming network connections are blocked or allowed, and how firewall rules interact with SSH.

Closing unused doors on the network

Whenever your computer joins a Wi-Fi or wired network, other devices on that network can probe your machine's numbered network ports. A host firewall drops unexpected incoming traffic while still letting your web browser and updates connect outward.

Why it matters

Default-drop incoming rules protect local services and shared workspaces from accidental exposure on untrusted networks.

How to think about it

Think of outgoing connections as requests you initiated yourself—replies to your requests are allowed back in automatically, while unsolicited knocks on closed ports are ignored.

New words

Firewall
A kernel filter that inspects packets and drops or allows traffic according to policy rules.
Port
A numbered endpoint (such as 22 for SSH or 443 for HTTPS) identifying a network service on a host.

Inspect firewall state before changing rules

Goal: verify whether Tamlinux's nftables policy or transitional ufw frontend owns the firewall before touching rules or services.

Before you start: checking systemd service status is read-only. Changing live firewall rules on a remote machine can lock out your connection; prepare local console access and a rollback checkpoint first.

Worked example

Check read-only whether nftables.service is active on the workstation:

$ systemctl is-active nftables.service 2>/dev/null || echo "nftables inactive"

With administrator privileges, inspect the active owned tamlinux-filter table (or check transitional ufw status on systems before full nftables cutover):

$ sudo nft list table inet tamlinux-filter

The owned host template installs from ~/.local/share/tamlinux/nftables/tamlinux-host.conf.template into /etc/nftables.conf. Its input chain defaults to policy drop, permits established/related connections, loopback, ICMP/ICMPv6, and restricts SSH (port 22), mDNS (5353), and LocalSend (53317) to your local home subnet.

Try it

Run systemctl is-active nftables.service without sudo to see whether the kernel ruleset service is running on your workstation. Remember that Docker keeps its own chains via iptables compatibility rather than modifying tamlinux-filter.

If it goes wrong

tam-setup-security-sshd says it skipped automatic firewall rules
Neither an active tamlinux-filter policy nor ufw was detected. Verify /etc/nftables.conf syntax safely with nft -c -f during an approved maintenance step.
Closing a service port after setup
When ufw owns the transitional rule, tam-remove-security-sshd removes its SSH limit rule; when nftables owns /etc/nftables.conf, edit the owned file intentionally rather than mixing temporary runtime deletes.

Tamlinux avoids running two conflicting firewall frontends together: nftables with table inet tamlinux-filter is the target owned firewall policy, replacing legacy ufw rules cleanly.

Check yourself

Answer before revealing the explanation.

What happens to replies for websites you open when the input chain uses policy drop?

They are accepted automatically by the ct state { established, related } accept rule because your workstation initiated the connection.

Why should you check whether nftables or ufw owns the firewall before adding rules?

Mixing rules across two firewall managers causes conflicts or silent overrides when services reload.
