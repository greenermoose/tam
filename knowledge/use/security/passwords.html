Passwords, sudo, and keeping secrets safe

This page explains how to change your sign-in password, handle administrator password prompts safely, and avoid leaking private passwords into shell history or text files.

Why your normal account has limits

Most programs you open run under your ordinary user account. That account can edit your documents, settings, and notes, while system files and updates require extra permission.

Why it matters

Separating ordinary work from system changes prevents an everyday mistake or buggy program from quietly altering core system files or another person's data.

How to think about it

Think of your user password as the key to your own desk, and an administrator prompt (such as sudo or a desktop policy prompt) as signing at the front desk before changing shared building wiring.

New words

Password
A secret string used to verify who is signing in or asking for permission.
sudo
A terminal tool that checks your permission before running a system-changing command.
Privilege
Permission granted by the operating system to change protected files or hardware state.

Verify privilege rules and secrets hygiene

Goal: distinguish read-only account checks from privilege prompts and keep typed passwords out of plain text commands.

Before you start: changing your password requires knowing your current password. Inspecting your privilege settings read-only changes nothing.

Worked example

Check your current account identity and whether you are in a privileged group such as wheel without invoking sudo:

$ id -un
$ id -Gn

When you run passwd in an interactive terminal, Linux disables terminal echo so your characters do not show on screen or get saved in shell history:

$ passwd --status

passwd --status reads status information without prompting for a new password. Never pass a password on the command line (for example as an argument to another tool), because command arguments can appear in process listings and shell history.

Try it

Run id -Gn in a terminal to see your groups, and run tam-sudo-passwordless --help only if you want to check usage — note that enabling passwordless sudo grants temporary root access to every process running under your user for the timer window, so leave it off unless needed for bounded maintenance.

If it goes wrong

Typing your password shows nothing on screen
That is normal terminal security behavior. Type the password carefully and press Return.
Too many wrong attempts lock sudo briefly
Tamlinux sets passwd_tries=10 in sudoers defaults; wait a moment and verify Caps Lock before trying again.

Commands like tam-sudo-passwordless [MINUTES: 1..120] create a timed systemd-run cleanup rule (15 minutes by default) so temporary root convenience does not persist silently.

Check yourself

Answer before revealing the explanation.

Why should you avoid putting passwords or API tokens inside regular command arguments?

Command lines can be saved in shell history files and observed in process lists while running; interactive hidden prompts or dedicated secret stores keep them off disk and out of sight.

When a desktop or terminal prompt asks for your password before installing software, should you type it automatically without reading what is asked?

No. Stop and read which command or action requested elevation and what files it intends to modify.

Shadow password KDFs, sudoers tickets, and secret-handling mechanics

Reference

Local Linux passwords are stored as salted, memory-hard digests in /etc/shadow (mode 0640 or 0000, owned by root), typically using yescrypt ($y$) or Argon2id ($argon2id$) via pam_unix and libcrypt. Memory hardness bounds offline GPU/ASIC guessing by requiring megabytes of RAM per candidate evaluation.

How it works

When sudo authenticates a user, it verifies credentials through /etc/pam.d/sudo, drops or switches uid/euid/suid via setresuid(0, 0, 0), sanitizes environment variables (env_reset, stripping LD_PRELOAD via kernel AT_SECURE), and records a per-TTY timestamp ticket under /run/sudo/ts/. Timed helpers such as tam-sudo-passwordless schedule a transient systemd-run unit to remove the temporary drop-in rule automatically.

Edge cases

Shared-TTY or same-UID ticket reuse
Any process running under your UID in the same session can inherit cached sudo tickets or inspect /proc/PID/environ unless ptrace_scope (kernel.yama.ptrace_scope >= 1) and tty_tickets isolate them.
Secrets in swap or core dumps
Password managers and agents call mlock() and prctl(PR_SET_DUMPABLE, 0) so plaintext keys are neither paged to unencrypted swap nor written to core dumps.
Research frontier: How do hardware-backed passkeys and kernel keyrings reduce reliance on user-memorized passwords?

Passkeys bind asymmetric credentials to origin and hardware attestation, eliminating server-side password databases, while the Linux kernel keyring (keyctl) isolates cryptographic keys from user-space process memory.
