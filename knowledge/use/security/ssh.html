SSH keys and remote access

This page explains how SSH uses paired public and private keys to connect securely between computers, and how Tamlinux enables or removes incoming SSH access.

Signing in without sending your password across the network

SSH (Secure Shell) lets you open a terminal on another computer over the network. Instead of typing a shared password on the remote machine, you keep a private key on your computer and copy only its matching public key to machines you want to access.

Why it matters

Key-based sign-in stops attackers from guessing weak passwords over the network, and keeps incoming remote access off completely on laptops that do not need it.

How to think about it

Your public key is like a padlock you give to another computer; your private key never leaves your machine and is the only key that opens that padlock. Keeping a passphrase on your private key protects it even if someone copies the file.

New words

SSH key
A cryptographic key pair where the public half authorizes access and the private half proves ownership.
Passphrase
A multi-word secret that encrypts a stored key on disk.

Inspect SSH keys and server state safely

Goal: verify existing SSH keys or server status read-only, generate a modern key safely, and understand how to undo incoming SSH server access.

Before you start: checking ~/.ssh and sshd.service is read-only. Enabling incoming SSH access modifies firewall and daemon configuration and requires administrator approval.

Worked example

Check what SSH public keys already exist in your home directory and whether the incoming SSH daemon is enabled:

$ ls -la ~/.ssh/*.pub 2>/dev/null
$ systemctl is-enabled sshd.service 2>/dev/null || echo "sshd disabled"

When creating a new key pair for connecting out to remote servers or code hosts, prefer Ed25519 with a passphrase:

$ ssh-keygen -t ed25519 -C "workstation-key"

Your public key sits in ~/.ssh/id_ed25519.pub (safe to share); never share ~/.ssh/id_ed25519.

Try it

Run ssh -G localhost | head -n 5 read-only to see how your SSH client resolves configuration without opening a network connection. Only turn on incoming SSH if you intentionally manage this machine remotely: tam-setup-security-sshd --help prints usage without changing settings.

If it goes wrong

Permission denied (publickey) when connecting
Verify that you copied the .pub file content (not the private key) into the target machine's ~/.ssh/authorized_keys and that ~/.ssh has mode 700.
Incoming SSH was turned on by mistake
Disable the service cleanly with tam-remove-security-sshd, which stops and disables sshd.service and cleans transitional rules.

tam-setup-security-sshd writes drop-in 10-tamlinux-hardening.conf to disable password logins after adding an authorized key, and checks whether nftables (inet tamlinux-filter) or transitional ufw owns the host firewall.

Check yourself

Answer before revealing the explanation.

Which file of an SSH key pair is safe to paste into a remote server or web forge?

The public key file ending in .pub. Keep the matching private key file on your own machine with mode 600.

What reverses tam-setup-security-sshd when you no longer want incoming SSH access?

Run tam-remove-security-sshd to disable sshd.service and remove or review the SSH firewall rule.

OpenSSH key formats, privilege separation, and agent-forwarding risks

Reference

Modern OpenSSH keys (ssh-ed25519, sk-ssh-ed25519@openssh.com for FIDO2 hardware-backed keys) store private keys encrypted with AES-256-CTR + bcrypt KDF. Server host keys authenticate the server during the SSH key-exchange transcript signature.

How it works

sshd enforces privilege separation: an unprivileged pre-authentication sandboxed child parses untrusted network packets and performs key exchange, while the privileged monitor holds host private keys and spawns the user session only after authentication succeeds. For multi-hop connections, ProxyJump (-J) tunnels end-to-end encrypted SSH over an intermediate hop's TCP forwarding channel without exposing your local ssh-agent Unix socket to the jump host.

Edge cases

Why ForwardAgent yes is dangerous on untrusted hosts
Agent forwarding exposes your SSH_AUTH_SOCK socket to root on the intermediate server, allowing an attacker there to request signatures from your local keys for as long as the session stays open.
StrictModes and file permissions
sshd refuses public-key login if ~, ~/.ssh, or ~/.ssh/authorized_keys is group- or world-writable, preventing local users from injecting keys.
Research frontier: How do hybrid post-quantum key exchanges like mlkem768x25519-sha256 protect SSH sessions against Harvest Now, Decrypt Later?

Combining X25519 with ML-KEM-768 in a single key exchange ensures session keys remain confidential unless an adversary breaks both classical ECDH and Module-LWE, thwarting passive capture of today's SSH traffic.
