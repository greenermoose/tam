System Resources and Performance

Tamlinux extracts maximum responsiveness from your hardware, from modest older laptops up to high-core workstations, with zero background telemetry and minimal memory footprint.

Check memory headroom and disk capacity

Goal: you will be able to check available memory and storage headroom without confusing cache with memory exhaustion.

Why it matters: Linux aggressively uses idle RAM for disk buffers and page cache, so seeing low "free" memory is normal. Checking the wrong number leads people to terminate healthy applications or panic about nonexistent memory exhaustion.

Before you start: open a terminal. These commands only read system memory and disk metrics; they do not kill processes or alter storage. See First steps if you are new to the command line.

A terminal is where you type commands. The prompt $ means the shell is waiting for input; do not type the $. free reports RAM, and df reports disk space. Silence or plain tables mean the query succeeded.

Worked example: Check available memory

$ free -h
               total        used        free      shared  buff/cache   available
Mem:            28Gi       6.0Gi        16Gi        97Mi       7.2Gi        22Gi
Swap:           56Gi       3.0Gi        53Gi

Captured on an Arch Linux workstation, 2026-10-25. Your output will differ.

  1. free -h prints memory metrics in human-readable units (GiB, MiB).
  2. total shows physical RAM installed (28Gi).
  3. free is completely unallocated memory (16Gi).
  4. buff/cache (7.2Gi) is memory holding temporary filesystem buffers and cached disk blocks.
  5. available (22Gi) is the crucial metric: memory that can be allocated immediately to new applications by reclaiming buffer and cache space without swapping.

Try it

Check disk capacity and headroom on your root filesystem using df -h /:

$ df -h /
Filesystem                Size  Used Avail Use% Mounted on
/dev/mapper/omarchy_root  650G  145G  504G  23% /

Check the Avail column and the Use%. No changes are made to your files. You can also run tam inspect to audit host CPU architecture, RAM, storage mounts, and graphics adapters in a single read-only view.

If it goes wrong

Low "free" memory with high "available"
This is healthy behavior. The Linux kernel uses otherwise idle memory to cache disk blocks. It frees cache instantly when applications request RAM.
Low "available" memory
Applications are consuming most physical RAM. Check running tasks before starting heavy workloads. Nothing needs undo.

Check yourself

Decide your answer before you reveal it.

If free memory is 200Mi but available memory is 8Gi, is the system running out of RAM?

No. Linux caches disk data in buff/cache, which is reclaimed instantly when an application asks for memory. Always check available memory.

Does running free -h or df -h modify anything on disk?

No. Both commands are strictly read-only diagnostics.

Diagnose CPU load and process memory

Goal: you will be able to interpret 1, 5, and 15-minute load averages against logical core counts and profile per-process resident memory.

Mental model

load average > logical cores  --> processes queuing for CPU or disk I/O
load average <= logical cores --> system has compute headroom

A load average is an exponential moving average of processes in runnable or uninterruptible sleep state (waiting for CPU or disk). Compare load to nproc: on a 16-core machine, a load of 1.4 means substantial spare headroom; on a 2-core machine, a load of 4.0 means tasks are actively queuing.

Worked example: Compare load average against core count

$ nproc
16
$ uptime
 06:28:47 up 1 day, 16:13,  1 user,  load average: 1.41, 1.10, 0.94

Captured on an Arch Linux workstation, 2026-10-25. Your numbers will differ.

  1. nproc reports 16 available hardware processing threads.
  2. uptime reports 1, 5, and 15-minute load averages of 1.41, 1.10, 0.94.
  3. Because 1.41 is far below 16, the system has abundant compute headroom and no CPU queue.

Completion task

List the top 5 memory-consuming processes ordered by resident set size (RSS). Complete the missing sort flag below (marked with ___):

ps -eo pid,rss,comm ___ | head -n 6

Fill in --sort=-rss. The leading minus sign sorts descending (largest first). ps -eo pid,rss,comm --sort=-rss | head -n 6 prints the header row followed by the 5 largest processes currently in physical RAM.

Independent task

Inspect swap utilization to verify whether memory pressure is forcing pages to swap space. Run cat /proc/swaps or free -m. Observe whether swap devices (including compressed ZRAM devices) are active while available RAM remains plentiful.

Run cat /proc/swaps. It lists each active swap partition or ZRAM device, its total size, and currently consumed space in kilobytes.

Check yourself

Decide your answer before you reveal it.

On a 4-core machine, what does a 1-minute load average of 8.0 indicate?

The system is overloaded: on average, 4 processes were running on CPUs while another 4 were queuing for CPU time or uninterruptible disk I/O.

Does high resident set size (RSS) alone prove that an application has a memory leak?

No. Many applications (like web browsers or compilers) legitimately hold large working sets in RAM. A leak is indicated by continuous monotonic growth over time under steady workload.

How it works

Linux virtual memory architecture separates anonymous memory (application heap and stack) from file-backed memory (page cache, mmap files). When memory pressure mounts, the kernel's kswapd daemon reclaims clean file pages and compresses anonymous pages into ZRAM swap devices backed by lz4 or zstd algorithms. Dirty page flushing is governed by vm.dirty_ratio and vm.dirty_background_ratio in sysctl(8). Pressure Stall Information (PSI) in /proc/pressure/memory provides leading indicators of memory stalls before thrashing occurs.

Why Tamlinux chose this

Tamlinux avoids persistent disk swap files on flash storage to prevent SSD write wear and eliminate the catastrophic latency spikes associated with reading swapped pages from disk. In-RAM compression with ZRAM delivers near-memory speeds while effectively doubling usable RAM on memory-constrained systems, with zero background telemetry daemons.

Edge cases

  • Direct reclaim stalls: when allocation rate exceeds kswapd reclaim speed, allocating processes block in direct reclaim, causing perceptible micro-stutters.
  • ZRAM incompressible payload: data that cannot be compressed (e.g. encrypted files or already-compressed media) yields a 1:1 ratio, consuming physical RAM without space savings.
  • OOM killer latency: without user-space memory monitors, the kernel OOM killer may trigger only after prolonged swap thrashing has degraded desktop interactivity.

Explore

Inspect real-time memory pressure stalls without third-party monitoring daemons:

$ cat /proc/pressure/memory

Read the some and full metrics. full=0.00 means no processes have stalled completely waiting for memory.

Check yourself

What is the trade-off of compressing swap in RAM via ZRAM?

ZRAM trades CPU cycles (for compression and decompression) to gain extreme I/O speed and eliminate disk latency. On CPU-bound systems under severe memory pressure, compression CPU overhead can compete with running workloads.
