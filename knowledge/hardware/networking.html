Network connections and DNS

This page explains how your computer reaches the internet and how to tell which part of that path is failing.

What makes a network connection work?

A working connection needs a network card that is up, an address and a route to a router, and a way to turn names such as example.com into addresses. Each layer can fail on its own, so check them in order instead of guessing.

Why it matters

When a web page or an update fails, the useful first question is whether the computer is offline, connected to the wrong network, or online but unable to look up a name. One status command separates those cases and gives you something specific to report.

How to think about it

name (example.com)
  |  DNS lookup
  v
address (203.0.113.10)
  |  routing table chooses a gateway
  v
link (ethernet or wifi) --> router --> internet

The kernel owns the link and the routing table. NetworkManager asks the kernel to configure them. The DNS resolver turns names into addresses.

New words

Interface
The kernel's name for a network device, such as enp1s0 or wlp3s0.
IP address
The number that identifies this computer on a network.
Gateway
The router that carries traffic from your local network to other networks.
DNS
The Domain Name System, which turns a name such as example.com into an IP address.
SSID
The public name of a Wi-Fi network.

Identify the connection you are using

Goal: you will be able to identify the connection your computer is using and report whether it has an address and can reach the internet.

Before you start: open a terminal. The commands below only read network state. tam-network-status --verbose also sends one small test message to 1.1.1.1 to measure internet round-trip time. See First steps if you are new to the command line.

Type the command after the $ prompt and press Enter. Do not type the $. Your interface name, address and timings will differ from the example. Success means the command finishes and prints a list; it does not change your connection.

Worked example

$ tam-network-status --verbose
iface             enp1s0
ip                192.168.1.26
prefix            24
gateway           192.168.1.1
rx_bytes          1134306807
tx_bytes          2264645693
type              ethernet
speed             1000
duplex            full
router_ping_ms    0.684
internet_ping_ms  20.2

Captured on a wired Arch Linux workstation on 2026-10-31. Your output will differ.

What just happened

  1. iface is the network interface in use.
  2. ip and prefix are the computer's address and local network size.
  3. gateway is the router beyond your local network.
  4. type is ethernet or wifi.
  5. router_ping_ms and internet_ping_ms are round-trip times; a blank value means no reply arrived.

Try it

Run the short form, tam-network-status, and then ip -4 -br addr. Match the interface name in both outputs. This is read-only and safe to repeat.

If the short form looks healthy but a browser still fails, separate layers with read-only checks: nmcli device status, ip route, getent ahosts example.com, and ping -c 1 -W 2 1.1.1.1.

If it goes wrong

The output says disconnected and the fields are empty
No interface has a route to the internet. Check that the Ethernet cable is seated, or open the network panel with Meta + CTRL+W and connect to a Wi-Fi network.
tam-network-status: command not found
The command ships with Tamlinux. Use ip route and nmcli device status instead, and report that the Tamlinux command is missing.
router_ping_ms or internet_ping_ms is blank
No reply arrived. Some networks block ICMP even when web traffic works. Compare with a name lookup and a browser before concluding the connection is down.
A name fails while a numeric address replies
The link and route layers work; check DNS with getent ahosts example.com or resolvectl query example.com.

Tamlinux ships NetworkManager for connection state and systemd-resolved for name resolution. The desktop panel binding is Meta + CTRL+W. DNS changes go through tam-dns, which preserves previous settings before writing.

Check yourself

Which field in the detailed output names the network card?

iface. The ip field is the address assigned to that card, and gateway is the router beyond it.

A computer can ping 1.1.1.1 but cannot open example.com. Which layer should you check first?

Name resolution. A successful ping to a numeric address proves the link, address and routing layers work.

Predict the output when the computer has no connection at all.

tam-network-status prints disconnected with empty fields.

How it works

NetworkManager owns device and connection state. The desktop panel in the public tamlinux repository at desktop/shell/panels/network/Panel.qml uses Quickshell's Networking module for devices and Wi-Fi networks, and calls tam-network-status, tam-network-band, tam-network-qr and tam-network-speedtest for details the module does not expose.

tam-network-status finds the device that would carry traffic to 1.1.1.1 with ip route get 1.1.1.1. It treats the device as wireless when /sys/class/net/<device>/wireless exists. Wi-Fi details come from nmcli -t and iw dev <device> link. The verbose path reads ip -j route get, the interface's addr_info, and the kernel counters under /sys/class/net/<device>/statistics. Ping samples run in parallel with a one-second deadline.

DNS has two possible authorities. tam-dns first reads the NetworkManager global-DNS drop-in at /etc/NetworkManager/conf.d/20-tamlinux-dns.conf. If that file has no servers, it reads DNS= from /etc/systemd/resolved.conf. If neither names a server, the provider is DHCP. A change preserves the original files through dns_recovery.py under /var/lib/tamlinux/network-recovery, writes or clears the drop-in and rewrites resolved.conf, reloads NetworkManager's configuration, reapplies the active wired and wireless profiles, reloads or restarts systemd-resolved, and asks NetworkManager to publish DNS again. The privileged half runs only from the read-only Nix-store copy of the command.

resolvectl talks to systemd-resolved, which usually listens on the stub address 127.0.0.53. The kernel sends DNS packets there, and resolved forwards them to the per-link or global servers. A link can have its own DNS scope and default-route flag; resolvectl status shows both.

Why Tamlinux chose this

Tamlinux keeps connection management in NetworkManager and DNS changes in one command that records the previous state before writing. The panel does not keep a second copy of connection state; it reads NetworkManager and calls the same commands a terminal user calls. The effect is one owner for the link and one recorded undo path for DNS changes, and the authorization prompt appears in the session instead of relying on a passwordless rule.

Edge cases

  • Enterprise Wi-Fi (EAP or 802.1X) has no shareable password. tam-network-password and tam-network-qr refuse it rather than printing a misleading secret.
  • NetworkManager models WEP as key management none plus a WEP key. Both sharing commands read that key so the QR code does not claim the network is open.
  • A band pin only takes effect after reassociation. If the radio cannot reconnect on the requested band, tam-network-band restores the previous value and reconnects.
  • A DNS change is not complete until the active profiles are reapplied and resolved rereads its configuration. Reloading only one side can leave a menu selection one step behind the live resolver.
  • Multiple interfaces can carry default routes with different metrics. ip route get names the winner for a specific destination, which is why the status command asks about 1.1.1.1 rather than listing every route.
  • A VPN or a captive portal can intercept traffic without changing the default route. Compare resolvectl status with the browser's actual failure before changing DNS.
  • ICMP replies are sometimes blocked. A blank ping is evidence, not proof, that the internet is down.

Explore

Read the route decision as data: ip -j route get 1.1.1.1 | jq .. Compare the resolver's view with the kernel's view using resolvectl query example.com and getent ahosts example.com. On Wi-Fi, compare iw dev with nmcli -f IN-USE,SIGNAL,FREQ dev wifi list --rescan no. All of these are read-only.

Check yourself

What breaks if a DNS change writes the NetworkManager drop-in but never reapplies the active connection?

The new file is on disk, but the running profile still carries the old per-connection DNS settings. The next reconnect may pick up the new value, which makes the change look delayed or inconsistent. Reapplying the active profiles and asking NetworkManager to publish DNS closes that gap.

Why does the status command test 1.1.1.1 instead of a name such as example.com?

Testing a numeric address isolates the link, address and routing layers from name resolution. If the numeric address replies and a name fails, the remaining fault is in DNS. Using a name would mix two layers in one result.
