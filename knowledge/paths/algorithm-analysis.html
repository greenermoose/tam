Guide / Learn step by step / Analyzing algorithms

This path teaches you how to measure and categorize algorithms by running time and memory required. You will learn asymptotic notation, common complexity classes, and how to check theory against real measurements.

Each stage gives a lens to read with. Start with the gentle explanation, then use the practice or reference lens. Answer the checkpoint before moving on.

Stage 1: Why analysis matters

Read Algorithm analysis first: understand why growth rates matter. Then read the practice lens for input size, cases, and worked examples, and the reference lens for cost models and limits.

Checkpoint

Why can a stopwatch measurement of one input be misleading?

It tells you what happened for that input, machine, and moment. It may not predict how the algorithm scales as input grows, and it can be affected by noise. Analysis gives growth trends; repeated measurement across sizes gives evidence.

Stage 2: Categorize running time

Read Time complexity and Big-O notation first: learn common growth classes. Then read the practice lens to estimate complexity from code, and the reference lens for O/Ω/Θ and analysis caveats.

Checkpoint

What does O(n log n) tell you, and what does it not tell you?

It tells you the running time grows no faster than a constant times n log n for large enough n in the chosen model. It does not tell you exact seconds, constant factors, memory behavior, or which algorithm is faster for small n.

Stage 3: Categorize memory use

Read Space complexity and memory use first: learn why memory matters. Then read the practice lens for auxiliary space and recursion stack, and the reference lens for conventions and time-space trade-offs.

Checkpoint

Why can a recursive solution have O(n) space complexity even without allocating an array?

Each recursive call consumes stack space. If recursion depth grows linearly with n, the call stack uses O(n) space in the usual model, even when no explicit heap array is allocated.

Stage 4: Measure real performance

Read Measuring algorithm performance first: learn why measurement matters. Then read the practice lens for simple benchmarks and pitfalls, and the reference lens for profilers, counters, and rigorous reporting.

Checkpoint

What should you change when comparing two algorithms in a benchmark?

Change only the algorithm/implementation under test while keeping input, hardware, runtime settings, warmup, and measurement method as comparable as possible. If you change multiple variables, you cannot attribute the difference reliably.

Capstone: Analyze and measure a choice

Scenario: you need to check whether a list of user IDs contains duplicates. One implementation compares every pair; another uses a hash set.

Task: state the expected time and auxiliary space complexity of each approach, name one case where the pairwise approach might still be acceptable, and describe a simple benchmark that would test the growth trend.

Model approach:

  1. Pairwise comparison: O(n^2) time, O(1) auxiliary space in the simple form. Acceptable for very small n or when memory is extremely constrained and simplicity matters.
  2. Hash set: O(n) average time, O(n) auxiliary space. Better for large n, but depends on hash quality and memory availability; worst-case adversarial inputs can degrade behavior.
  3. Benchmark: generate lists of several sizes (e.g., 10k, 20k, 40k, 80k), include duplicate and no-duplicate cases, run multiple trials, report median and spread, and compare observed growth to the expected O(n^2) vs O(n) trend.

The key is to combine asymptotic categorization with empirical evidence on representative inputs.
