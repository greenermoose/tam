Guide / Learn step by step / From first text to research-level messaging

This path follows one text from the person who writes it to the research questions that remain after it arrives. Each stage tells you which lens to read with: Novice for the idea, Learner for a worked sample, and Expert for standards and failure modes.

All examples live in labelled teaching sandboxes. Nothing here sends a real text, changes a SIM or installs a messaging app.

Outcome: After this path, you can explain cellular access, SMS, MMS, RCS, internet apps, encryption, delivery and open research questions.

Prerequisites: none beyond reading

Time: About 60 minutes, including checkpoints and the capstone.

If you're stuck: read the program manuals with tam man <command>, list built-in help with tam help, or search this guide with tam search -- <term>.

Stage 1: The whole journey

  1. What is texting? — name the person-side app and the background services.
  2. How a phone joins a cellular network — separate the radio hop from the core and service layers.

Checkpoint

Answer before you go on.

Why can a text arrive after both people have left their current locations?

A service stores it and forwards it later. The radio link only carries one hop; the core tracks where to send it and the message service keeps it until delivery or expiry. Reread What is texting? if the store-and-forward idea is unclear.

Checkpoint

Answer before you go on.

Why does moving a SIM to a new phone not change the subscriber?

The subscription credential moves with the SIM; the equipment identity belongs to the phone. Reread SIM cards and subscriber identity, then compare it with Addresses, numbers and routing.

Checkpoint

Answer before you go on.

Why is a delivery receipt not proof that a person read a text?

It reports a system event such as handoff to a network or device. Reading is a separate client event.

Checkpoint

Answer before you go on.

Why can an end-to-end encrypted message still be delivered late?

Encryption changes who can read the content, not how queues, paging, retries and push notifications behave. Reread Encryption and key management and Delivery, retries and reliability.

Answer before you go on.

Why does encryption not stop a convincing request for a one-time code?

The attacker targets the reader rather than the transport. Reread Spam, smishing and abuse, then read the threat-model guidance in Texting research frontiers.

Capstone

Design, on paper, a messaging service for a small volunteer group. Some members have only a basic phone, some use a chat app, and a few work in areas with poor coverage. State how a message is addressed, stored and delivered; what each status label means; which parts are encrypted; how a new device joins; and how the group handles spam and a suspected SIM swap. Write the design as a one-page table with a column for what can still fail.

A sound answer separates four planes. Access: a phone registers with a cell; poor coverage means longer queueing and paging delays. Identity: the basic phone uses a subscription and a public number; app users have accounts bound to devices, with a strong re-registration check. Transport: the basic path uses SMS store-and-forward, while the app path uses a data connection and push wake-up; rich chat may use RCS where both sides support it and fall back explicitly. Trust: content is end-to-end encrypted where possible, safety numbers are verified out of band, and no one-time code is accepted over the same channel that requested it. Status labels distinguish accept, deliver and read. A suspected SIM swap triggers out-of-band confirmation and a temporary hold on sensitive actions. Remaining failures include expiry, duplicates after retries, metadata exposure, push delays and social engineering.
