Guide / Learn step by step / Inside a font file

This path follows one character from a number in a file to coloured pixels on a display. It opens the font container, names the fonts built into a cited Linux kernel, and shows where shaping and rasterization happen. The final stage turns that knowledge into a diagnostic routine.

All examples are teaching samples in labelled sandboxes. No font is installed and no system setting is changed.

Outcome: You can describe the tables in an OpenType file, name the kernel's built-in bitmap fonts and their selection symbols, explain shaping and rasterization, place the main Linux text libraries in one pipeline, and locate the layer behind a text problem.

Prerequisites: Font formats, complete map and Anatomy of a letterform

Time: About 60 minutes, including checkpoints and the capstone.

If you're stuck: read the program manuals with tam man <command>, list built-in help with tam help, or search this guide with tam search -- <term>.

Stage 1: The container

  1. Inside OpenType and TrueType files — read a table directory and tell glyf outlines from CFF charstrings.

Checkpoint

Answer before you go on.

Why can two fonts share the sfnt container but need different rasterization code?

Because TrueType stores quadratic outlines and instructions in glyf, while OpenType CFF stores cubic charstrings. The container is shared; the outline language differs. Reread Inside OpenType and TrueType files.

Expected sandbox state: The sample table listing is filtered to required tables; no real font file is modified.

Stage 2: Fonts inside the kernel

  1. Fonts built into the Linux kernel — name all thirteen built-in bitmap fonts in Linux 6.12 and the Kconfig symbols that include them.

Checkpoint

Answer before you go on.

Why does the virtual console use a bitmap font while a desktop application uses an outline font?

The console draws a fixed character cell directly into a framebuffer with no shaping library; bitmap tables are small and predictable there. A desktop scales outlines through FreeType and shapes runs with HarfBuzz. Reread Fonts built into the Linux kernel.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Stage 3: Shape the run

  1. From characters to shaped glyphs — predict when a ligature or joining form will appear.

Checkpoint

Answer before you go on.

Why does changing the font sometimes change the order of marks in a complex script?

Because the font's GSUB and GPOS tables supply the substitutions and anchor positions; the shaper applies them to the character sequence. Reread From characters to shaped glyphs.

Expected sandbox state: The sample shaping transcript shows glyph IDs before and after substitution; no system font is touched.

Stage 4: Make pixels

  1. From outlines to pixels — explain why the same letter looks different at two sizes or pixel densities.

Checkpoint

Answer before you go on.

What does hinting try to preserve when an outline is scaled to a small pixel grid?

It adjusts outlines or instructions so stems and edges land consistently on pixels, keeping horizontal rhythm and legibility at the cost of exact outline geometry. Reread From outlines to pixels.

Expected sandbox state: The sample pixel grid is read from the page; no simulated files or output are expected.

Stage 5: Put the layers together

  1. The Linux text stack — trace a string through Fontconfig, FreeType, HarfBuzz, Pango and the toolkit.

Checkpoint

Answer before you go on.

Which library answers "which font file should this application use"?

Fontconfig. FreeType loads and rasterizes the chosen face and HarfBuzz shapes the run; none of them chooses the family from a generic name. Reread The Linux text stack.

Expected sandbox state: The sample fc-match output names a family; no real font cache is rebuilt.

Stage 6: Diagnose

  1. A typography diagnostic workbench — choose the responsible layer from a symptom and a first check.

Checkpoint

Answer before you go on.

A document shows boxes for one character only. Which layer do you check first?

Font coverage and selection: ask whether the chosen family contains that code point and whether fallback is configured. Shaping and rasterization come later. Reread A typography diagnostic workbench.

Expected sandbox state: The sample coverage list stays in the sandbox; grep narrows it to one code point. No machine state changes.

Capstone

A report displays a heading in one font, body text in another and a code block with odd spacing. Write a one-page diagnosis: name the layer responsible for each difference, list one read-only check per layer, and say which change would be reversible. Keep the console path separate from the graphical path.

A sound answer separates selection (Fontconfig rules and generic families), shaping (GSUB/GPOS and ligature settings), rasterization (hinting, pixel density, antialiasing) and the console path (a fixed bitmap font loaded by fbcon or setfont). Checks include fc-match, a shaping transcript and a rendered specimen; reversible changes are user-level configuration or a scratch copy, never a package removal or a boot setting. The reader verifies the answer by matching each symptom to the workbench table.
