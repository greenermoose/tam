Guide / Learn step by step / People and security

This path covers accounts, secrets, keys, network boundaries, privileges and trusted updates through small read-only audits and change notes.

Outcome: After this path, you can audit accounts, secrets, keys, privileges, network and disk boundaries, and trusted updates read-only.

Prerequisites: none beyond reading

Time: About 50 minutes, including checkpoints and the capstone.

If you're stuck: read the program manuals with tam man <command>, list built-in help with tam help, or search this guide with tam search -- <term>.

Every exercise here is read-only: no account, password, key, firewall rule or disk is changed. Changing authentication or disk settings is privileged work that needs its own recovery point and explicit approval.

People, secrets and boundaries

Security is built from boundaries: who you are, what secret proves it, which devices hold keys, and which programs may cross a privilege boundary. A read-only audit names those boundaries before a change is proposed.

Think of it as a diary with a lock, a key and a guest list. Knowing which drawer the key opens matters more than merely knowing that a key exists.

Read an account boundary

Goal: interpret a fixed identity report without exposing secrets

Practice notes. uid=1000(alex) gid=1000(alex) groups=1000(alex),998(wheel) alex wheel A fixed report shows the user, group and wheel membership. Groups describe membership; they do not grant a passwordless privilege window. The same groups can be listed by name. Type id, or type help.

What just happened

The report names an ordinary user and the groups it belongs to. The output shown in this sandbox is a sample from fixed teaching data, not a reading from your machine. Group membership is evidence about account boundaries, not proof that privilege escalation is enabled.

Try it

Run id -Gn and compare the named groups with the numeric report.

If it goes wrong

If your own output differs, record the values you actually saw; do not copy teaching identities into a real change note.

Check yourself

Does wheel membership prove passwordless privilege?

No. Configuration and policy decide how a group is used.

Expected sandbox state: id prints uid=1000(alex) gid=1000(alex) groups=1000(alex),998(wheel) and id -Gn prints alex wheel; no account is changed.

Checkpoint

Why do daily work as an ordinary user rather than root?

Mistakes and buggy programs then cannot silently rewrite system binaries or boot files. Privilege is requested only for the action that needs it.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Which command lists the groups your account belongs to?

id -Gn prints group names; id also shows the numeric user and group IDs.

What does LUKS protect, and when?

Data at rest while the machine is powered off or the drive is locked. Once unlocked, the running system can read the files normally.

Why does a privilege prompt appear for some actions but not others?

The action needs to change system-wide state. Ordinary work inside your home folder does not, so it runs as your user.

Does a file's mode alone decide who can open it?

No. Owner, group and other bits combine with directory traversal permission, and a privileged process can bypass ordinary checks.

Checkpoint

What must exist before a real update changes installed software?

A verified recovery point for the affected boundary, plus a way to check the new version afterwards. Without it, the change stays pending.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Does restoring a software generation also restore an edited document?

No. Package recovery and your own data are separate. Documents need their own backup or documented recovery method.

Capstone: Audit your account and write a change note, read-only

Collect a short, read-only picture of your account and this machine's security boundaries: your identity and groups, whether a password is set, how many public SSH keys exist, whether the SSH server is enabled, whether the firewall is active, and whether a disk is encrypted. Then write a four-line note for a future software update.

Run these commands as your ordinary user. None of them changes anything, and none prints a private key.

uid=1000(alex) gid=1000(alex) groups=1000(alex),998(wheel) alex wheel alex P 2026-09-03 -1 -1 -1 -1 -rw-r--r-- 1 alex alex 102 Sep 4 10:09 /home/alex/.ssh/id_ed25519_work.pub enabled inactive NAME FSTYPE FSVER LABEL nvme0n1 ├─nvme0n1p1 vfat FAT32 EFI └─nvme0n1p2 crypto_LUKS 2 Try: id Read the sample output and compare it with the task. These commands are simulated; nothing runs on the host. Type one of the sample commands, or type help.

The sandbox uses fixed sample output and does not run commands on your system.

The sandbox uses fixed sample data. your output will differ. P in the password status means a password is set. crypto_LUKS identifies an encrypted device; it does not mean the disk is unlocked or that the passphrase is known.

Now write the note. Keep it to four lines:

  1. Current state: the values you just collected, one per line or grouped.
  2. Owner: who or what supplies the change, for example the native package manager or a recorded Tamlinux assembly.
  3. Verification: the command you will run afterwards and the value you expect.
  4. Recovery: the exact checkpoint or backup you would need, or unknown.

If the recovery line says unknown, the real change stays pending. Do not invent a checkpoint identifier, and do not enable a passwordless privilege window to make the exercise easier. The audit itself is the deliverable.
