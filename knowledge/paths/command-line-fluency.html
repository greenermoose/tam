Guide / Learn step by step / Getting comfortable with written instructions

This path builds confidence with written instructions: what the shell reads, how tools pass text, and how to inspect results before changing anything.

Outcome: After this path, you can read, combine and adapt shell commands, then inspect their results before changing anything.

Prerequisites: First steps

Time: About 50 minutes, including checkpoints and the capstone.

If you're stuck: read the program manuals with tam man <command>, list built-in help with tam help, or search this guide with tam search -- <term>.

Instructions, tools and evidence

A shell reads a written instruction, expands it, and starts a program. The program does the work; a pipe passes the program's printed text to the next tool. Seeing those boundaries makes command output easier to predict.

Think of the shell as a workshop coordinator and the tools as small hand tools. You do not need one huge machine when a filter, a counter and a file can be connected for the job in front of you.

Count matching lines in a tiny report

Goal: use a pipeline to count only the lines that match a pattern

red blue red 2 1 red blue red Three colour lines wait in colours.txt; only two are red. The pipe carries the two matching lines into wc -l. Changing the pattern changes which lines survive the filter. Try cat colours.txt, then grep with a pipe into wc -l.

What just happened

The pipe moves printed bytes, not a filename. grep discards the blue line and wc -l counts the two lines that remain.

Try it

Predict the count for blue before running the second rule, then check the file with cat.

If it goes wrong

If the count is zero, check the spelling and case of the pattern; red and Red are different lines.

Check yourself

What does the pipe pass between grep and wc?

The bytes grep printed, not a filename or an argument list.

Expected sandbox state: colours.txt contains red, blue and red; the red pipeline prints 2, the blue pipeline prints 1, and cat colours.txt shows the three lines.

Capstone

In a scratch directory, create a three-line red/blue/red input, write a private executable report script that counts red lines in its file argument, start it in the background, wait for that child, then inspect its report and mode. Remove only your exercise files.

Make and enter a fresh temporary directory for this capstone.

work=$(mktemp -d)
cd "$work"
2 700 report.sh Try: printf '%s\n' red blue red > colours.txt Read the sample output and compare it with the task. These commands are simulated; nothing runs on the host. Type one of the sample commands, or type help.

The sandbox uses fixed sample output and does not run commands on your system.

The sandbox uses fixed sample data. The report contains 2 and the script mode is 700. wait connects the readback to this shell's completed report task. This demo assumes the readable fixed input you created. A general-purpose report must also handle input errors; successful wc alone does not establish producer success.

cd /tmp
rmdir -- "$work"

Reading map for command-line fluency

Work through the linked stages in order when you need depth: shell reading and editors, paths and permissions, streams and jobs, manual lookup, then descriptor semantics. Keep production files out of practice; use scratch files and read-only queries until a command is familiar.
