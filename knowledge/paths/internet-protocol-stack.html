Guide / Learn step by step / Internet protocol and the stack

This path takes a reader who has never studied networking from the idea of a layered message to explaining every step of one web request.

Each stage gives a lens to read with. Start with the gentle explanation where offered, then use the practice or reference lens. Answer the checkpoint before moving on; if it is unclear, reread the stage at the earlier lens. All commands in this path only read state.

Stage 1: Why layers exist

The internet protocol stack first: learn why a message is wrapped in labels, and name the application, transport, internet and link layers. Then read the same page at the practice lens to find the addresses and ports on your own machine.

Checkpoint

Which layer adds an address, which adds a port, and why does the receiver need both?

The internet layer adds the address so routers can forward the packet to the right machine. The transport layer adds the port so that machine can hand the data to the right program. Reread the Learner section of the first page if either job is unclear.

Stage 2: Packets and next hops

IP packets and forwarding first: picture a packet as a parcel passed between routers with a counter that stops it circling forever. Then read the practice lens to ask the kernel which next hop it chooses and to read a hop count from a reply.

Checkpoint

A packet's hop limit reaches zero. What happens, and what command deliberately uses that behaviour?

The router drops the packet and sends an internet control message back to the source. Traceroute sends packets with increasing hop limits to collect those messages and learn the routers along the path. Reread the Learner quiz on the forwarding page if needed.

Stage 3: Many conversations on one machine

Ports and sockets first: use the apartment-building picture to see why a port picks a program inside a machine. Then read the practice lens to identify a listening service and the four values that name one conversation.

Checkpoint

Two browser tabs reach the same website on port 443. Why do their connections stay separate?

Each tab gets a different local port. The pair of local and remote addresses and ports identifies a conversation, so the four values differ even though both tabs use the same remote port. The Expert section of this page gives the exact range of local ports.

Stage 4: A reliable stream

Transmission Control Protocol at the practice lens: read a live connection's round-trip time, segment size and congestion window. Then read the reference lens for the handshake, sequence numbers, retransmission and the trade-offs behind those numbers.

Checkpoint

Why can a connection with a quick round trip still send too slowly to fill a link?

The sender may have only a small congestion window of unacknowledged data in flight, or the application may not be feeding it enough bytes. Check both the window and the counters that show how much data the application wrote. The Expert section explains the bandwidth-delay limit.

Stage 5: Messages without a conversation

User Datagram Protocol at the practice lens: find DNS and multicast DNS by their port numbers and see that no connection state is kept. Then read the reference lens for the eight-byte header and what an application must supply when it needs reliability.

Checkpoint

A name lookup gets no reply. Why can't UDP say whether the request or the reply was lost?

UDP keeps no connection state and sends no acknowledgements, so the sender sees only silence. The application must retry or try another server. Contrast this with the acknowledgement numbers you read in Stage 4.

Stage 6: One request, end to end

From packets to applications at the practice lens: follow a name lookup, a route decision and a live socket. Then read the reference lens for the full path from resolver through TLS to an HTTP reply, and for what changes with HTTP/3.

Checkpoint

A numeric address replies to a ping but the page will not open. Which layers are proved, and what do you check next?

Link, addressing, routing and basic control messages work. Check the TCP connection to the web port, then TLS and the HTTP response. The reference table on the final page lists one read-only check for each stage.

Capstone: Trace a slow page from name to bytes

Scenario: a web page opens but takes several seconds. Work only with read-only commands in your normal session; nothing here changes a connection or a setting.

Task: measure the name lookup, the route decision and the live connection. State which stage contributes the delay, name one piece of evidence for that conclusion, and say which stage the evidence rules out. Then explain what would change if the site used HTTP/3 instead.

Model approach:

  1. time getent ahosts example.com shows how long name resolution takes and which addresses were returned. A long pause here points at the resolver, not the website.
  2. ip route get <address> answers where a packet would go without sending one. An unreachable answer would stop the process before any connection is attempted.
  3. ss -ti state established '( dport = :443 or sport = :443 )' reports the round trip, retransmission timer, congestion window and bytes sent. A growing rto points to loss; a small window points to a rate limit or an idle application.
  4. With the network stages healthy, the remaining delay belongs above transport: TLS negotiation, a slow server, or application content. A browser trace separates those.
  5. HTTP/3 carries the request over QUIC and UDP, so the TCP table would show no connection; the same name, route and encryption stages still apply, with reliability provided inside QUIC.

The point is the order: each check eliminates a layer, so the final answer names the smallest remaining set of causes.
