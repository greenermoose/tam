From first page to full-stack web developer

This path takes a reader who has never written a web page from the idea of a script to building, securing, testing and shipping a small full-stack application.

Each page has a novice, learner and expert lens. The stages name the lens to start with; after you finish, reread the pages at the expert lens to turn practice into reference knowledge. Work in a scratch directory. Nothing here changes your system, and the worked examples use local servers that you stop with Ctrl+C.

Stage 1: The language and the page

JavaScript: language, history and engines first: learn what the language is, where it came from, and why one language now runs in browsers, servers and desktop apps. Then read HTML and CSS foundations to see the structure and presentation that a page is made of.

Checkpoint

Which part of a page comes from HTML, which from CSS, and which from JavaScript?

HTML describes the structure and meaning of the content. CSS describes how that structure looks. JavaScript reads and changes the page after it loads. Reread the novice sections of both pages if you would describe all three as "the code".

Stage 2: How the browser runs a page

Browser engines and the DOM first: follow markup into a document tree that script can change. Then read Browser APIs and asynchronous JavaScript at the practice lens to react to events, fetch data and keep the page responsive while work is pending.

Checkpoint

Why does a line printed after await appear later than a line written after the whole async function call?

await pauses only the async function that contains it. The event loop carries on with other work, then resumes that function when the promise settles. The Learner example on the async page shows the exact order.

Stage 3: The server half

Node.js and npm at the practice lens: run JavaScript outside a browser and manage project scripts and packages. Then read Full-stack web architecture to connect a client, HTTP requests, a server and a database into one application.

Checkpoint

What can the server enforce that browser code cannot?

The server runs where the data lives. It can check identity and permission, omit private fields and refuse a request before replying. Anything sent to the browser can be read or changed by the person using it, so client-side rules are feedback, not a security boundary.

Stage 4: Safety and larger codebases

Web security at the practice lens: keep untrusted text as text and understand cookies, CORS and injection. Then read Frameworks and tooling at the reference lens to see what a framework, module system and bundler actually do underneath.

Checkpoint

A private API succeeds from curl but fails in the browser with a CORS message. What do you check first?

Read the status and headers, not just the console message. A 401 or 403 is an authentication problem; a successful reply hidden by the browser is a CORS problem. Never loosen authentication to fix a CORS error. The Expert quiz on the security page walks through the evidence.

Stage 5: Verification and delivery

Testing, debugging, and performance at the reference lens: check behaviour, read traces and measure change. Then read Deployment and Electron desktop apps to publish the application or package the same interface as a desktop program.

Checkpoint

What did serving a page from a local folder prove, and what did it not prove?

It proved that the files could be returned with the right status and content type. It did not prove public reachability, encrypted transport, behaviour under load or a safe rollback. Those belong to a deployment plan.

Capstone: Build and hand over a small notes application

Scenario: a friend wants a private notes app that works in a browser and can later be packaged as a desktop program. Work in a scratch directory; use only local servers and stop them when you finish.

Task: build a page with an input and a list, a Node server that stores notes in memory, a JSON endpoint, output that stays as text, one automated test, and a short handover note that says how to run it, how to deploy it and how to undo a bad release. Add a second test that checks the failure path for an empty title.

Model approach:

  1. Create a folder with package.json, index.html, server.mjs and notes.test.mjs. Set "type": "module" so import works.
  2. In the page, use a form and fetch('/api/notes', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ title }) }). Render returned titles with textContent, never with innerHTML.
  3. In the server, use node:http. Accept GET /api/notes for the list and POST /api/notes for a new note. Reject an empty title with status 400. Serve index.html for / with content type text/html.
  4. Keep the notes array in a module with addNote and listNotes exports. Validate and cap the title length on the server as well as in the page.
  5. Add Content-Security-Policy: default-src 'self'; script-src 'self' to responses. The inline script in the practice page would need a separate file to satisfy this policy; making that change is part of the task.
  6. Write two tests with node:test: one asserting a valid title is stored, one asserting an empty title is rejected. Run node --test --test-reporter=dot and require two dots before continuing.
  7. Start the server, open the local address, add a note in the browser and confirm the list updates. Stop the server with Ctrl+C. For an Electron version, move the page into a renderer and expose only a named read:notes operation from the main process.
  8. The handover note records the Node version, the command to run, the command to test, the exact files shipped, and the previous working directory to restore if a release fails.

The point is that each stage of the path appears once: markup and style, DOM and async, server and JSON, escaping and headers, tests and a reversible release.
