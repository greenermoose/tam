Shell text, quoting and IFS

This path takes a reader who has never used a shell from the idea of one word to the precise rules that split expansion results, and on to scripts that keep real data intact.

Each stage gives a lens to read with. Start with the gentle explanation where offered, then use the practice or reference lens. Answer the checkpoint before moving on. All commands in this path are safe in a fresh scratch directory.

Stage 1: Words in a shell

Giving your computer written instructions first: meet the shell, a prompt and the standard streams. Then read the same page at the practice lens to send a command and see its output.

Checkpoint

What does a shell do with the line you type after the prompt?

It reads the text, identifies words and operators, starts the requested command, and connects the command's normal output and error messages to streams. Reread the first page if the prompt or the stream numbers are unclear.

Stage 2: Keeping text together

Keeping words together first: see why a name with a space needs quotes. Then read the practice lens to compare single quotes, double quotes and a backslash, and the reference lens for how quoting is decided before expansion.

Checkpoint

Why does a value with spaces become two arguments when it is left unquoted?

The shell uses spaces as word boundaries. Quotes mark the value as one word; without them the spaces inside the value become separators. The worked capture on the quoting page shows the argument count with brackets.

Stage 3: The expansion order

What changes before a command runs at the practice lens: follow a variable containing an asterisk through quoting, splitting and filename matching. Then read the reference lens for the full pipeline and the position of quote removal.

Checkpoint

Why can an unquoted variable containing an asterisk match filenames?

Parameter expansion puts the asterisk into the word, field splitting can leave it in its own field, and pathname expansion then treats that unquoted field as a pattern. Double quotes stop the field from being split or matched.

Stage 4: IFS and splitting

IFS and splitting at the practice lens: change IFS to a comma, watch empty fields appear, and use a prefix assignment with read. Then read the reference lens for the table of IFS states and the special parameters.

Checkpoint

Why do adjacent commas give empty fields but adjacent spaces do not?

Comma is a non-whitespace IFS character, so each one terminates a field even when the candidate is empty. Space, tab and newline are IFS white space in the portable set; runs of them collapse into one boundary.

Stage 5: The precise rules

Field splitting rules at the reference lens: read the algorithm step by step, including IFS white space, empty fields, the special parameters, read, the unspecified cases and the captured example.

Checkpoint

What is the difference between an unset IFS and an empty IFS?

An unset IFS behaves as if it held space, tab and newline, so splitting and read still use those separators. An empty IFS performs no splitting, although an entirely empty expansion field is still removed before quote removal.

Stage 6: Data that survives

Handling real data safely at the practice lens: replace a fragile command substitution loop with a while IFS= read -r loop. Then read the reference lens for arrays, NUL-delimited streams and the injection risk in unquoted data.

Checkpoint

Why is a NUL-delimited stream safer than a newline-delimited one for arbitrary filenames?

A pathname cannot contain a NUL byte, so NUL is an unambiguous separator. Newlines, spaces and shell metacharacters can all appear in a filename and need quoting or a read loop to stay intact.

Capstone: Handle names that fight back

Scenario: a scratch directory holds three files with difficult names: one with a space, one starting with a space, and one containing a dollar sign. You must produce a list that shows each name inside brackets, with one name per line and no splitting or expansion of the data.

Task: create the three files in a fresh temporary directory. First try a for loop over unquoted command output and record how it fails. Then use find . -type f -print0 piped into while IFS= read -r -d '' path and print each name as [<path>]. Explain what IFS=, -r, -d '' and the quotes around "$path" each protect. Remove the scratch directory when you have checked the result.

Model approach:

  1. Create a scratch directory with mktemp -d and change into it. Create the files with quoted names, for example touch 'Quarterly Report.pdf' ' leading.txt' 'odd$name.txt'.
  2. Run for f in $(printf '%s\n' *); do printf '[%s]\n' "$f"; done. The unquoted command output is split again, so the name with a space appears as two bracketed pieces.
  3. Run find . -type f -print0 | sort -z | while IFS= read -r -d '' path; do printf '[%s]\n' "$path"; done.
  4. Check that you see exactly three bracketed lines and that the dollar sign in odd$name.txt did not expand. It stayed literal because it came from data, not from the shell's input.
  5. IFS= stops the read command trimming leading IFS characters, -r keeps backslashes literal, -d '' makes NUL the record separator, and the quotes around "$path" pass the whole field as one argument.
  6. Return to your previous directory and remove the scratch directory only after the output is correct.

The point is that every stage protects a different boundary: the stream separates records, the read command preserves one record, and the quotes preserve one argument.
