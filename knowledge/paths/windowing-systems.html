Guide / Learn step by step / From pixels to desktop applications

This path takes a reader who has never thought about how a window reaches the screen to a clear explanation of X11, Wayland, desktop environments and toolkits.

Each stage uses the lens shown on its links. Novice gives the idea, Learner adds worked practice, and Expert gives the reference detail. The checks are read-only; nothing here changes your desktop.

Outcome: After this path, you can explain X11, Wayland, desktops, toolkits and your own graphical session from the idea of a window.

Prerequisites: none beyond reading

Time: About 40 minutes, including checkpoints and the capstone.

If you're stuck: read the program manuals with tam man <command>, list built-in help with tam help, or search this guide with tam search -- <term>.

Checkpoint

Answer before you go on.

In X11, is the window manager the same program as the X server?

No. The X server owns the screen and input; the window manager is a client that places and decorates windows. Reread the novice section of How X11 draws windows if that distinction is new.

Checkpoint

Answer before you go on.

Why does a keylogger have less access in a Wayland session than in an X11 session?

The compositor routes input only to the focused client. X11 lets a client with display access request global key events. Reread the Learner section of Why Linux moved from X11 to Wayland.

Checkpoint

Answer before you go on.

A desktop notification never appears, but input and windows work. Which layer would you check first?

The shell or notification service, not the compositor. The compositor is still presenting surfaces and routing input. Reread the Learner section of GNOME, KDE Plasma and other desktops.

Checkpoint

Answer before you go on.

You see both WAYLAND_DISPLAY and DISPLAY in a terminal. What is the safest conclusion?

Native Wayland clients have a socket, and X11 clients have an address that may be XWayland. Use XDG_SESSION_TYPE and a login-manager query to identify the session. Reread the Learner section of Check your graphical session.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Capstone

Explain a graphical problem in your own words without changing the desktop: name the session type, the application's toolkit, the layer that presents its window, and the layer that routes input. Use read-only checks and say which evidence supports each claim.

A sound answer includes: the session type from XDG_SESSION_TYPE and loginctl show-session; whether DISPLAY is an XWayland compatibility address; the toolkit that draws the visible controls; the compositor that commits surfaces and presents the screen; and the compositor or X server that routes input. It separates a shell or toolkit fault from a display-server fault and avoids claiming that a variable proves more than it does. Check the result by explaining the same problem on the other display protocol: the window, controls and input path should still be named correctly.
