Set up a network connection

This path takes a reader with no networking knowledge from the first idea of a network to configuring a connection, reading the routing and name decisions, and finding devices that announce themselves locally.

Each stage has a checkpoint. Answer it before moving on; if a checkpoint is unclear, reread the stage at the suggested lens. The capstone is a whole task in a reversible setting, so no mistake changes a working connection.

Stage 1: The four questions

How networks fit together: learn that every connection answers a link, address, route and name question, and that these layers fail independently. Read the four answers from a real machine with ip -br addr, ip route and getent ahosts.

Checkpoint

A machine has an address but no default route. Which destinations still work?

Destinations inside the directly connected prefix still work, because the kernel creates a route from the interface address. Anything outside that prefix has no next hop and fails.

Stage 2: Numbers on the wire

Addresses and subnets: work out a subnet, broadcast address and usable range from an address/prefix pair, and see how ARP and NDP turn an address into a hardware neighbor.

Checkpoint

Why can two machines on one cable fail to talk if their prefix lengths differ?

Each machine decides independently whether the other is local. If one treats the destination as remote it sends the frame to a gateway instead of directly, and with no gateway on that link the packet has no usable path.

Stage 3: Save a connection

Adding a connection: distinguish a device from a saved profile, read the DHCP or manual method, and learn the undo for a profile you create. Record the profile name before changing anything.

Checkpoint

What is the undo for a connection profile you just created?

nmcli connection delete '<name>' removes the saved profile. The live configuration then comes from whichever profile remains active on that interface.

Stage 4: Routes and names

Gateways and routing and Name resolution: ask the kernel which interface a destination would use, then follow a name to an address through the local resolver. Keep the two questions separate: a numeric address isolates routing, and a name adds resolution.

Checkpoint

A numeric address replies but the name fails. Which layer is at fault, and which command isolates it?

Name resolution. The successful numeric reply proves link, address and route are working. resolvectl query <name> reports the resolver's error, such as NXDOMAIN, SERVFAIL or a timeout.

Stage 5: Find devices without an address

Avahi and Zeroconf: publish a temporary service, read avahi-browse output, resolve a .local name and understand the mDNS and DNS-SD records behind the result.

Checkpoint

Why does a .local name fail through a global DNS server, and what answers it instead?

.local is reserved for link-local names and is not delegated in the global DNS hierarchy. Multicast DNS on the local link answers it, using a Name Service Switch module such as nss-mdns on Linux.

Capstone: Bring a new device online and find its service

Scenario: a computer has a wired connection, a new printer was plugged into the same network, and the printer does not appear in the print dialog. Work in a reversible setting: use only read-only checks until you know what to change, and write down the profile name and setting before any edit.

Task: check the interface and address, confirm a default route, verify that a public name resolves, then browse for printing services and resolve the printer's .local name. State which layer each observation proves and what single change would fix the remaining fault.

Model approach:

  1. ip -br addr and nmcli device status establish that the interface has carrier and an address. Without an address, no service discovery or routing can work.
  2. ip route get 1.1.1.1 proves the default route and names the gateway. A failure here confines the problem to the local prefix.
  3. getent ahosts example.com separates name resolution from routing. A numeric reply with a failed name points at the resolver; a failed numeric reply points at the route or link.
  4. avahi-browse _ipp._tcp -t -r -p shows whether the printer announces itself. No result with a healthy network points at the printer, its VLAN or a firewall on UDP 5353.
  5. avahi-resolve -4 -n '<printer>.local' confirms the name-to-address step. If a profile change is needed, note its current values and the delete command that undoes a newly created profile.

The point is not the exact output but the order: each check eliminates a layer, so the final change is the smallest one that can help.
