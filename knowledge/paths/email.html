Guide / Learn step by step / From first message to reliable delivery

This path follows one message from the person who writes it to the mailbox that receives it. Each stage names the lens to read with: Novice for the idea, Learner for a worked sample, and Expert for the standards and failure modes.

Examples live in teaching sandboxes. Nothing here installs a mail server, configures an account or sends mail from your machine.

Stage 1: See the whole journey

Begin with the boundary between the client a person uses and the servers that carry mail. Keep the store-and-forward model in mind: each server may accept, hold and later forward the message.

  1. What is email? — messages, addresses and the client/server boundary.
  2. How a mail server works — submission, queues, relays and mailbox delivery.
Why can a sender finish before the receiver is online?

Servers store the message and forward it later. Email does not need both people connected at the same moment.

Stage 2: Build and send a message

Read the message as layers and then watch the SMTP conversation that carries it. The envelope used by servers is not the same as the visible header a person reads.

  1. Addresses and message format — header, body, MIME parts and internationalised addresses.
  2. SMTP and submission — envelope commands, ports and encrypted submission.
If SPF passes, must the visible From domain be authorised?

No. SPF checks an envelope domain. DMARC is the mechanism that requires alignment with the visible From domain.

Stage 3: Read mail from the client side

Now change viewpoint. The retrieval protocol decides where folders and flags live, and the client may keep a local copy that is not the authoritative mailbox.

  1. POP, IMAP and JMAP — local download, shared server state and modern structured access.
  2. Mail clients and mailboxes — account setup, flags, aliases, offline work and encryption.
Which protocol best supports the same folders on a phone and a laptop?

IMAP, because folders and flags are kept on the server. POP normally centres on a download to one device.

Stage 4: Follow DNS and trust signals

Connect the network lookup to the records that publish policy. Notice that DNS can route mail, help authenticate a domain and describe how servers should encrypt a hop.

  1. DNS and email — MX, addresses, reverse names, DNSSEC and record prefixes.
  2. Identity and transport security — SPF, DKIM, DMARC, ARC, DANE, MTA-STS and reports.
Why does DANE for SMTP need DNSSEC?

A TLSA record states which certificate to expect. DNSSEC validation stops an attacker from replacing that record along with the address records.

Stage 5: Filter abuse and repair delivery

Finish with the receiving side's hardest choices. No single signal proves that mail is wanted, and no single log line proves where a message went.

  1. Spam and abuse — reputation, lists, filters, limits, allowlists and user reports.
  2. Deliverability and troubleshooting — bounces, queues, deferrals, blocks and header evidence.
Why might a legitimate message land in quarantine while a phishing message passes DMARC?

Authentication and content safety are different questions. Filtering also uses reputation, list, content and feedback signals, each of which can be wrong.

Capstone: explain a failed delivery

Imagine this report: a message to bo@example.org was accepted by your submission server, queued, deferred once with a 451 reply, then accepted by a remote MX host. A DMARC report later shows a failure for the visible domain, and the recipient says the message is in quarantine.

Write a short explanation that names the role at each stage, separates a temporary deferral from a permanent failure, states what the 250 acceptance proves, and lists two checks before resending. Say explicitly why DMARC failure does not prove the message is malicious and why quarantine is not the same as rejection.

Reveal a sample answer

The submission agent accepted the message and queued it; a transfer agent attempted relay. The 451 reply was temporary, so retry was appropriate. The later 250 reply proves only that one receiving server accepted responsibility for that hop; it does not prove inbox delivery or that a human read the message. DMARC failure means SPF or DKIM did not align with the visible From domain; it does not judge the content. Quarantine is a holding state that a user or administrator may review, not a rejection. Before resending, check the queue outcome and bounce or DSN, inspect authentication results and Received headers from the bottom upward, and compare with provider reports or ask the receiving postmaster.
