Guide / Learn step by step / From first query to very large data sets

This path takes a reader who has never designed a database from the idea of saved records to choosing between an embedded engine, a server database, a browser store and a distributed data system.

Every stage names the lens to read with. The examples live in teaching sandboxes; this path installs no database software and asks you to change nothing on your own machine.

Outcome: After this path, you can choose, query and justify a storage system for a real workload.

Prerequisites: none beyond reading

Time: About 50 minutes, including checkpoints and the capstone.

If you're stuck: read the program manuals with tam man <command>, list built-in help with tam help, or search this guide with tam search -- <term>.

Stage 1: See why stored data needs a system

  1. Why databases exist — understand what a database keeps and what a plain file cannot do for you.
  2. The relational model and SQL — meet tables, rows, keys and questions written in SQL.

Checkpoint

Answer these before you go on.

Why not keep every application record in one hand-written file?

A file has no schema enforcement, safe concurrent updates or indexed lookup. As records and readers grow, an application must rebuild all three by hand; a database supplies them as its job.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Stage 2: Ask questions and keep changes safe

  1. The relational model and SQL — read a join, then write a SELECT with a filter.
  2. Indexes, transactions and storage — see how lookup aids and transactions change the cost of a query.

Checkpoint

Answer these before you go on.

An index makes a read fast. What is the price?

Extra storage and extra work on every write, because the index must stay in step with the table. A query plan shows whether the gain is worth it for a particular query.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Stage 3: Compare an embedded engine with a server

  1. SQLite — work through a local, single-file database and note where locking applies.
  2. PostgreSQL — compare roles, schemas and client/server operation with the embedded case.

Checkpoint

Answer these before you go on.

When is SQLite the better fit, and when do you need a server?

SQLite fits a local application, a test or a small site with one writer. A server fits concurrent writers, shared access, central backups and role-based administration.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Stage 4: Widen the choice beyond relational tables

  1. MySQL and InnoDB — inspect another server engine and its clustered primary-key storage.
  2. Non-SQL databases — classify document, key-value, column-family and graph stores by access pattern.

Checkpoint

Answer these before you go on.

What question helps you choose a non-relational store?

Start with how the application will read and write data. Embedded documents suit whole-record access, key-value suits direct lookup, wide columns suit partition-local scale and graphs suit traversals.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Stage 5: Put data at the edge and at scale

  1. IndexedDB — see transactional browser storage for offline work.
  2. GraphQL — separate an API contract from the store that answers it.
  3. Very large data sets — follow partitioning, columnar files, batch and streams beyond one machine.

Checkpoint

Answer these before you go on.

Is IndexedDB a replacement for a shared server database?

No. It belongs to one browser profile on one device. A server database is shared, authorized and backed up centrally; IndexedDB supports an offline or local-first client.

Expected sandbox state: No sandbox in this stage; no simulated files or output are expected.

Capstone

Design storage for a small reading app that lets a person save bookmarks offline, sync them later and produce a monthly report of the most-read topics. Work on paper or in a scratch file; do not install a database.

One sound answer: keep browser records in IndexedDB with an object store keyed by bookmark ID and an index on topic, so offline edits remain transactional. Sync through a server API (a GraphQL contract is fine) into PostgreSQL, using a transaction for each batch and a topic index for the report. If the report grows beyond a single database, write raw events to Parquet in an object store and run a batch summary with Spark; use a stream only if the app needs answers within seconds. State which trade-off you are making: local availability, transactional safety, analytical scan cost or operational simplicity. The result is a design, not a claim that one product always wins.
