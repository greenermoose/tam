People and security

This path explains who you are on the machine, how secrets and keys work, which doors are open, and how to keep software changes recoverable. It suits anyone who uses a shared or portable computer.

Every exercise here is read-only: no account, password, key, firewall rule or disk is changed. Changing authentication or disk settings is privileged work that needs its own recovery point and explicit approval.

Stage 1: Identity and secrets

  1. Passwords, sudo, and keeping secrets safe — why your daily account has limits, and where secrets must not be written.
  2. User accounts and groups — identify your account, home folder and groups, and plan a second account.

Checkpoint

Answer these before you go on.

Why do daily work as an ordinary user rather than root?

Mistakes and buggy programs then cannot silently rewrite system binaries or boot files. Privilege is requested only for the action that needs it.

Which command lists the groups your account belongs to?

id -Gn prints group names; id also shows the numeric user and group IDs.

Stage 2: Keys and hardware tokens

  1. SSH keys and remote access — generate a key, connect to another machine, and inspect the local server state.
  2. Fingerprints and FIDO2 security keys — check hardware readiness and see which PAM modules are enrolled.

Checkpoint

Answer these before you go on.

What crosses the network when you sign in with an SSH key?

A proof signed with your private key. The private key itself stays on your machine; only the public key is installed on the server.

Which files show whether a fingerprint or FIDO2 module is enrolled for privilege prompts?

The PAM stacks under /etc/pam.d/, for example sudo and polkit-1. Reading them needs no change.

Stage 3: Network and disk boundaries

  1. Checking and managing the host firewall — inspect the active firewall before changing a rule.
  2. Disk encryption and LUKS passphrases — what full-disk encryption protects and when the drive is unlocked.

Checkpoint

Answer these before you go on.

What does LUKS protect, and when?

Data at rest while the machine is powered off or the drive is locked. Once unlocked, the running system can read the files normally.

Which command reports whether the host firewall service is active?

systemctl is-active nftables.service. It prints the state and exits non-zero when the service is not active.

Stage 4: Privilege and file permissions

  1. Hardware Security and Privilege Management — how tokens, PAM and polkit authorize an administrative action.
  2. Who can use a file — read, write and execute bits, and directory traversal.

Checkpoint

Answer these before you go on.

Why does a privilege prompt appear for some actions but not others?

The action needs to change system-wide state. Ordinary work inside your home folder does not, so it runs as your user.

Does a file's mode alone decide who can open it?

No. Owner, group and other bits combine with directory traversal permission, and a privileged process can bypass ordinary checks.

Stage 5: Trusted change

  1. Checking and updating your software — identify the owner and prepare recovery before changing software.

Checkpoint

Answer these before you go on.

What must exist before a real update changes installed software?

A verified recovery point for the affected boundary, plus a way to check the new version afterwards. Without it, the change stays pending.

Does restoring a software generation also restore an edited document?

No. Package recovery and your own data are separate. Documents need their own backup or documented recovery method.

Capstone: Audit your account and write a change note, read-only

Collect a short, read-only picture of your account and this machine's security boundaries: your identity and groups, whether a password is set, how many public SSH keys exist, whether the SSH server is enabled, whether the firewall is active, and whether a disk is encrypted. Then write a four-line note for a future software update.

Run these commands as your ordinary user. None of them changes anything, and none prints a private key.

$ id
uid=1000(alex) gid=1000(alex) groups=1000(alex),998(wheel)
$ id -Gn
alex wheel
$ passwd --status
alex P 2026-09-03 -1 -1 -1 -1
$ ls -la ~/.ssh/*.pub
-rw-r--r-- 1 alex alex 102 Sep  4 10:09 /home/alex/.ssh/id_ed25519_work.pub
$ systemctl is-enabled sshd.service
enabled
$ systemctl is-active nftables.service
inactive
$ lsblk -f -o NAME,FSTYPE,FSVER,LABEL
NAME        FSTYPE      FSVER LABEL
nvme0n1
├─nvme0n1p1 vfat        FAT32  EFI
└─nvme0n1p2 crypto_LUKS 2

Captured on an Arch Linux workstation, 2026-11-13; your output will differ. P in the password status means a password is set. crypto_LUKS identifies an encrypted device; it does not mean the disk is unlocked or that the passphrase is known.

Now write the note. Keep it to four lines:

  1. Current state: the values you just collected, one per line or grouped.
  2. Owner: who or what supplies the change, for example the native package manager or a recorded Tamlinux assembly.
  3. Verification: the command you will run afterwards and the value you expect.
  4. Recovery: the exact checkpoint or backup you would need, or unknown.

If the recovery line says unknown, the real change stays pending. Do not invent a checkpoint identifier, and do not enable a passwordless privilege window to make the exercise easier. The audit itself is the deliverable.
