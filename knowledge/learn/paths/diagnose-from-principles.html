Diagnose from first principles

These readings help you name the failing layer of a workstation problem before you change anything.

Prerequisites: From atoms to bits, How software runs, and Session and desktop.

Stage 1: Pick the symptom class

Start at the symptom index. Record time, last action, and whether text VTs still work.

Check yourself

Why record VT success or failure early?

It roughly separates early boot and basic input/GPU text paths from graphical session faults.

Stage 2: Physical and link layers

Cables and protocols and Display and GPU: decide whether media, framing, or display protocol is in play.

Check yourself

When is a cable reseat better evidence than restarting a service?

When the panel, link light, or connector state is unproven. Software restarts can destroy session evidence.

Stage 3: OS and delivery layers

Logs, boot recovery, package versions.

Check yourself

What separates a wrong PATH binary from a failed update transaction?

Path resolution and ownership evidence. A development prefix can hide a packaged binary without any failed transaction.

Capstone

Take one real past incident (or a paper scenario): blank screen after login with working VTs. Write competing explanations at three layers and the next read-only check for each. Do not apply a fix in this exercise.

Example competitors: (1) compositor/session not started after console login — check processes and tam-desktop docs; (2) DRM mode/connector — check connector state from VT; (3) cable/panel input — known-good cable and input selection. Rank by cheapest decisive evidence. Restarting display stacks is not the first check.
