Understand the design

These readings explain how the parts of Tamlinux fit together.

Fred Horch, the Tamlinux developer, uses rootstock for the third-party base system (today Arch Linux) and cultivar for Tamlinux's own release software. Planned rootstock moves are under distributions and rootstocks.

Stage 1: Why Tamlinux exists

Philosophy names the three commitments: free software, open standards and resource efficiency. Sustainability turns the third into a practice: hardware longevity, less e-waste, and capability-based profiles rather than a new machine per release.

Check yourself

Which commitment makes a software choice a long-term hardware decision?

Resource efficiency, read through sustainability: a heavier stack shortens the useful life of the machine it runs on.

Stage 2: Rootstocks and delivery

Rootstocks: Arch Linux today, Void next and antiX Core as fallback, and why the base can move without changing what you use. Then how software is delivered: distinguish rootstock packages, the user assembly and mutable settings.

Check yourself

Does a user-generation rollback necessarily restore personal files?

No. Mutable files need their own recovery method.

Stage 3: Trace a version

Trace a version: distinguish a source revision from a selected package output. Then Nix and Home Manager: a description becomes an immutable store path, and modules become a switchable user generation.

Check yourself

Does a source commit alone prove what is running?

No. Establish the selected package and runtime as separate evidence.

Stage 4: Login and session

Current Tamlinux cultivars use console-first login: you authenticate at a text prompt, then start the desktop with tam-desktop when you want graphics. Read TTYs and virtual consoles for the text route, then display managers to understand graphical greeters as an optional or historical alternative. Compare authentication, session launch and desktop startup as separate boundaries.

Check yourself

Does successful authentication prove the desktop is working?

No. Authentication, session launch and rendering have separate failure boundaries. On console-first systems, the desktop starts only when you run tam-desktop.

Stage 5: Kernel, init and the desktop

Read Kernel and processes, Init and Compositors. Then the bar and menus: Quickshell, Qt Quick and QML draw the shell around your windows. Name which layer owns a stuck GUI versus a wrong package binary.

Check yourself

Which layer owns arranging windows on screen today?

The Hyprland compositor (Wayland), not Nix itself.

Stage 6: Change software safely

Carried patches explain why Tamlinux publishes fixes on public forks, verifies the build and retires the patch when upstream lands. Virtualization gives you a clean room to try a change without touching the installed system.

Check yourself

What makes a carried patch temporary?

It retires when the upstream release contains the fix. Until then it is published, verified and carried, not treated as a permanent fork.

Capstone

Explain where you would investigate a changed application setting, a missing native service and an unexpected command version. Name the evidence you would seek without changing the system.

For a changed theme, first identify the active user configuration and its previous value. For a missing system service, inspect its unit and system journal. For a command version, resolve the executable path and identify its package; inspect a running process separately. A user-generation rollback need not restore mutable files.
