Rescue

These readings help you prepare to recover your computer when it cannot start or an update goes wrong.

If you are already facing a failure, start with the last visible stage and record what you do not know. Do not guess a repair command from a menu label. For an introduction, read how to recover when startup fails, then return here.

The exercises inspect information without changing the system or use temporary files. A real repair needs a separately approved procedure suited to the affected computer.

Stage 1: Locate the failure boundary

  1. Read Boot artifacts and installed state.
  2. Work through the dependency model in Boot fallbacks and rescue routes.
  3. Record the symptom, time, last observed stage and the next unknown. Name a route that avoids the suspected failure and its remaining shared dependencies.

Check yourself

Decide before revealing the explanation.

A menu offers two kernels but the partition holding both images is unreadable. What route should you investigate?

An independently prepared route that avoids that partition, such as verified external rescue media. Another kernel name on the same unreadable partition does not cross the failure boundary.

Stage 2: Identify what can actually be recovered

  1. Work through Snapper inventory and checkpoint relationships.
  2. Read Snapshots and generation rollback boundaries.
  3. For your paper scenario, name the software layer, retained recovery source and data outside it. Keep checkpoint IDs, image hashes and assembly identifiers unknown unless you have actual evidence. Never substitute the teaching IDs.

Check yourself

Decide before revealing the explanation.

A known-good root snapshot excludes home and EFI files. Which parts of recovery are still separate?

Home data and later writes need their own preservation/recovery plan. EFI files and native boot dependencies need the provider procedure. Selecting a software generation or booting a snapshot does not restore all those parts.

Stage 3: Plan access before a repair

  1. Work through Emergency recovery planning.
  2. Choose an access method appropriate to the reached stage: configured text login for a session failure, or independently prepared rescue media when installed startup cannot work.
  3. Write the exact procedure you would consult, how target identity would be verified, where later writes would be preserved, and the stop condition if storage, credentials or recovery source cannot be confirmed.

Check yourself

Decide before revealing the explanation.

A live environment starts successfully. Is mounting the first listed disk a valid next step?

No. First establish device identity, encryption state, subvolume/mount layout and the chosen procedure. Live startup proves access to that environment, not identification or recoverability of installed storage.

Stage 4: Audit shared dependencies

  1. Switch to Fallback independence.
  2. Read Boot generation dependencies and Snapper metadata and restoration semantics.
  3. Audit the paper plan for an intact image with wrong root parameters, explicit subvolume selection, excluded mounts and a shared failed device. Before a real change, retain a verified rollback point and approve one specific operation. Define checks for normal boot/unlock, required mounts, login and preserved data, with an abort route if any check fails.

Check yourself

Decide before revealing a model answer.

What does a successful snapshot boot establish, and what does it leave open?

It establishes that one selected route reached the observed environment. Persistent normal-root restoration, excluded data, later writes and future boot behavior remain separate checks. Record exactly what was observed rather than calling the whole plan accepted.

Capstone: Reject an unsafe recovery shortcut

Scenario: after an update, the internal EFI partition containing the loader and boot images is unreadable. A recent root snapshot exists on the internal disk. A document in a separate home subvolume was edited afterward. You have an external rescue device, but its storage-unlock support has not been verified.

Use a private scratch directory to represent the candidate routes. These are fictional labels, not boot entries, verified artifacts or mount targets.

rescue_plan=$(mktemp -d)
printf 'normal internal-esp installed-root\nsnapshot internal-esp snapshot-root\nusb external-media rescue-root\n' > "$rescue_plan/routes"

Filter out routes needing the unavailable internal ESP. Then write five lines in your own notes: observed failure; candidate access; unknown dependency; later-write preservation; verification/stop condition. Do not write to installed storage, repair a loader, mount a snapshot or perform a rollback.

$ awk '$2 != "internal-esp" { print $1 }' "$rescue_plan/routes"
usb

Captured in a scratch directory on Arch Linux, 2026-10-21.

  1. Observed failure: internal boot images are inaccessible; the root snapshot alone cannot supply a working loader/image path.
  2. Candidate access: external media avoids that boot-file dependency in the model. It has not been proven ready.
  3. Unknown dependency: confirm firmware startup, device identity, filesystem/unlock support and credentials through the chosen procedure. Keep installed-storage operations pending while any required fact is unknown.
  4. Later writes: the edited home document is outside the root snapshot. Preserve and verify it using a suitable data-recovery procedure and independent destination before any destructive restoration.
  5. Verification/stop condition: retain the original error and native recovery artifacts. A future approved repair must check intended boot/unlock, root and data mounts, login and the document. Stop if the target, backup, credentials or procedure cannot be verified. Suspected device failure requires a data-recovery plan before repeated boot/repair attempts.

A good result is a bounded plan with honest unknowns. The scratch filter has neither tested external media nor recovered this scenario's system.

Remove only your scratch file and directory:

rm -- "$rescue_plan/routes"
rmdir -- "$rescue_plan"
unset rescue_plan
