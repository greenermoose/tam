Systems programming in C11

This path is for readers who will read or change C code: portable ISO C11, how the compiler and linker turn source into a native binary, how sanitizers find memory bugs, and why Tamlinux writes its core utilities in C11. It assumes you can compile and run a program from a terminal.

Every exercise builds in a fresh temporary directory. Nothing installs, and no system binary is replaced.

Stage 1: Write portable C11

  1. The C11 programming language and portable systems code — the standard, compiler flags, libc portability and native systems programming.

Checkpoint

Answer these before you go on.

Which value of __STDC_VERSION__ identifies C11?

201112L. Compile with -std=c11 and inspect the macro with gcc -dM -E.

Why does the build define _DEFAULT_SOURCE and _XOPEN_SOURCE?

They expose the POSIX interfaces the code needs while keeping the language target portable ISO C11. They are feature-test macros, not compiler extensions.

Stage 2: Compile, inspect and link

  1. Object files, static libraries, and compilation stages — source to .o to .a, ELF sections, and selective linking.

Checkpoint

Answer these before you go on.

What does gcc -c stop before?

Linking. It produces an object file with unresolved references that the linker resolves later.

Which tools list archive members and ELF sections?

ar -t libNAME.a lists members; readelf -S FILE.o lists sections such as .text, .rodata and .rela.text.

Stage 3: Find memory bugs and weigh the trade-offs

  1. Compiler sanitizers, AddressSanitizer, and memory safety in C — redzones, shadow memory, and a sanitized build.
  2. Systems programming philosophy and language choices — binary size, dependencies, startup, and why C11.

Checkpoint

Answer these before you go on.

What does AddressSanitizer place around each object, and where does it record the result?

Redzones around allocated and stack objects, tracked in shadow memory. A read or write into a redzone is reported with the source line.

Does a warning-free build prove there is no memory bug?

No. Warnings catch some static problems; out-of-bounds or use-after-free behaviour needs a sanitizer run or a test that exercises the path.

Capstone: Build, catch and fix an out-of-bounds read

Create a two-file program whose loop reads one element past a three-element array. Build it with AddressSanitizer and UndefinedBehaviorSanitizer, read the report, fix the loop bound, and rebuild until the run is clean.

Work in a temporary directory. The first file holds the bug; the second supplies the data and calls it.

int total(const int *values, int count)
{
    int sum = 0;
    for (int i = 0; i <= count; i++)
        sum += values[i];
    return sum;
}

#include <stdio.h>

int total(const int *values, int count);

int main(void)
{
    int values[3] = {2, 4, 6};
    printf("total: %d\n", total(values, 3));
    return 0;
}

Save the first as total.c and the second as main.c, then build and run:

$ gcc -std=c11 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -g -O1 main.c total.c -o stats
$ ./stats
=================================================================
==3686666==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7b41da0f002c
READ of size 4 at 0x7b41da0f002c thread T0
    #0 0x55d5d030645e in total /tmp/.../total.c:5
    #1 0x55d5d03062cc in main /tmp/.../main.c:8
...
    [32, 44) 'values' (line 7) <== Memory access at offset 44 overflows this variable

Captured with GCC 16.2.1 on Arch Linux, 2026-11-13; addresses and process IDs differ on every run. The report names the function, the source line and the object that overflowed. The compiler had accepted the code without a warning, so only the sanitized run exposed it.

Change the loop condition in total.c from i <= count to i < count, then rebuild and run:

$ gcc -std=c11 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -g -O1 main.c total.c -o stats
$ ./stats
total: 12
$ echo "exit=$?"
exit=0

The sum is 2 + 4 + 6 = 12 and the process exits 0 with no sanitizer output. A clean run is the check; silence alone would not prove correctness, but a nonzero exit or a report does prove a problem. Remove the temporary directory when you are done.
