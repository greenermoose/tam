Security protocols and access control

This path starts from everyday ideas—locks, secrets, and trust boundaries—with zero prior technical knowledge assumed, and builds step by step to Linux kernel credentials, TLS 1.3, SSH internals, and formal protocol verification.

If any page feels too advanced, step back one stop along the path until the terms feel familiar. Every exercise uses read-only commands.

Stage 1: Security principles and threat modeling

  1. Computer Security Principles and Threat Modeling — CIA triad, STRIDE, Saltzer–Schroeder principles, Lampson's matrix, Bell–LaPadula, and side channels.

Checkpoint

Answer before moving to Stage 2.

What are the three core properties of the CIA triad, and why does a threat model come before choosing tools?

Confidentiality (keeping secrets), Integrity (preventing tampering), and Availability (keeping systems usable). A threat model identifies what you are protecting and who might attack it so defenses match real risks.

Stage 2: Passwords, authentication, and authorization

  1. Passwords, sudo, and keeping secrets safe — normal accounts vs. administrator elevation and secrets hygiene.
  2. Authentication, Authorization, and Linux Access Control — Argon2id, PAM stacks, DAC/MAC/RBAC/ABAC/ReBAC, Linux UIDs, capabilities, and seccomp-bpf.

Checkpoint

Answer before moving to Stage 3.

How do Discretionary Access Control (DAC) and Mandatory Access Control (MAC) differ?

In DAC, resource owners choose who gets access; in MAC, system-wide kernel policies restrict subjects and objects in ways even resource owners cannot override.

Stage 3: Filesystem permissions and POSIX ACLs

  1. Who can use a file — read/write/execute bits, directory search rights, POSIX ACLs, and dynamic-linker hardening.

Checkpoint

Answer before moving to Stage 4.

Why does Linux require execute (x) permission on a directory to read a file inside it?

On directories, x grants traversal/search permission to resolve names to inodes; r alone only lists filenames without letting you open them.

Stage 4: Hardware authentication and privilege helpers

  1. Hardware Security and Privilege Management — tam-setup-security-* helpers, tam-sudo-docker, and bounded privilege elevation.

Checkpoint

Answer before moving to Stage 5.

Why does hardware FIDO2 authentication resist phishing better than a typed password?

A FIDO2 authenticator signs a challenge bound cryptographically to the exact origin/Relying Party ID, so a lookalike site cannot replay the signature elsewhere.

Stage 5: Transport security: TLS, HTTPS, and SSH

  1. SSL, TLS, and HTTPS — TLS 1.3 1-RTT handshake, HKDF key schedule, X.509 PKI, and HTTP/1.1–HTTP/3.
  2. The SSH Protocol Internals — RFC 4251–4254 binary packet protocol, TOFU host keys, strict-kex, and agent-forwarding risks.

Checkpoint

Answer before moving to Stage 6.

Why is ssh -J (ProxyJump) safer than ForwardAgent yes when crossing an intermediate host?

ProxyJump tunnels end-to-end encrypted SSH traffic through the jump host without exposing your local ssh-agent signing socket to root on that intermediate machine.

Stage 6: Network, messaging, and identity protocols

  1. Network, Messaging, and Identity Security Protocols — WireGuard (Noise), IPsec, Signal Double Ratchet, Kerberos, OAuth 2.0/OIDC, DNSSEC, FIDO2, and ProVerif/Tamarin.

Checkpoint

Answer before moving to the capstone.

What two properties does Signal's Double Ratchet combine to protect long-lived messaging conversations?

A Diffie–Hellman ratchet and a symmetric KDF chain ratchet, providing both forward secrecy for past messages and post-compromise (future) secrecy after a temporary state leak.

Capstone: Inspect your session's security boundaries read-only

Check your own Tamlinux session's security posture read-only: process isolation flags (/proc/self/status), capability sets (capsh --print), SSH client negotiation defaults (ssh -G localhost), and firewall service status to see how kernel access control and cryptographic protocols work together.

Run these read-only commands in a terminal:

$ grep -E '^(Uid|NoNewPrivs|Seccomp|CapEff):' /proc/self/status
$ capsh --print | head -n 4
$ ssh -G localhost | grep -E '^(kexalgorithms|ciphers|macs) '
$ systemctl is-active nftables.service 2>/dev/null || echo "nftables inactive"

Verify that your shell runs as an unprivileged UID with zero ambient capabilities, confirm modern post-quantum/AEAD SSH algorithms, and check host firewall state before enabling any network service.
