The tam Command

This page explains how the program that displays this guide is built and maintained.

For reader-facing entry points, see Using the tam guide command. This page documents the command's implementation, build system, and development lifecycle. tam is the terminal entry point, offline navigator, and flagship utility for Tamlinux. Its command is written in C (C11 standard) and built against the reusable libtam foundational library. It is designed to start in under 5 milliseconds, consume less than 4 megabytes of resident memory, operate completely offline without background daemons, and run reliably from circa-2006 legacy laptops up to modern multi-core workstations.

Inspect subcommands and compile a local build

Goal: you will be able to inspect installed tam version metadata, compile the standalone C binary from source with Make, and test the newly compiled binary safely without altering system packages.

Why it matters: tam is Tamlinux's core offline navigation and diagnostic command. Unlike interpreters or browser engines, it compiles to an ultra-fast, native C binary that starts in under 5 milliseconds. Understanding how to compile it locally allows you to test fixes and improvements safely under your user development prefix without root permissions or risks to production software.

Before you start: open a terminal inside the tam repository checkout. Compiling locally requires standard developer tools (GCC or Clang, Make, and header libraries). Inspecting versions is read-only. See Terminal and editor ergonomics and Native toolchains and multi-agent workflows for environment prerequisites.

Make is a build automation tool that reads a Makefile to compile source code into executable programs. Running make command compiles only the C executable under build/tam. In terminal sessions, $ represents your shell prompt; do not type it.

What just happened

  2. make -C ~/Code/tamlinux/tam command invoked the C compiler (cc) with C11 flags (-std=c11 -O2 -Wall -Wextra -Wpedantic), producing the standalone executable at build/tam linked with libtam and zlib.

Try it

Execute single-lane command tests on the newly built binary to verify CLI arguments and pager navigation without touching the corpus index:

$ make test-command

You can also run the built binary directly with ./build/tam --help to inspect the full list of available subcommands.

If it goes wrong

fatal error: tam/fs.h: No such file or directory
The libtam header files are not installed under /usr/include or your configured LIBTAM_PREFIX (e.g. ~/.local/dev/include). Pass LIBTAM_PREFIX=$HOME/.local/dev when invoking Make.
fatal error: zlib.h: No such file or directory
The zlib compression development headers are missing. On Arch Linux, install native zlib using pacman -S zlib.
build/tam: error while loading shared libraries: libtam.so
The dynamic linker cannot locate libtam.so at runtime. Verify that the RPATH was set during compilation or export LD_LIBRARY_PATH=$HOME/.local/dev/lib.

Which Makefile target compiles the C command binary without rebuilding the knowledge index?

make command compiles only build/tam from src/*.c. make all compiles both the binary and the corpus index.

Why does tam --version report separate versions for the command and the knowledge corpus?

Because tam uses decoupled versioning: the C command binary (parser and pager engine) and the documentation corpus evolve independently, allowing documentation pages to be added or revised without recompiling the binary.

The tam repository is organized into two independent workstream lanes: the Command lane (C source code under src/) and the Corpus lane (HTML documentation under knowledge/). Two agents can work concurrently if each claims one lane. The command binary links libtam and zlib and dynamically discovers corpus metadata at runtime.

On Tamlinux, development builds and production releases adhere to strict lifecycle boundaries. Developers and AI coding agents build and test candidates locally using user prefixes (~/.local/dev) or transactional generation directories (~/.local/dev/opt/tam/generations/). However, production software never reaches the system from ad-hoc checkouts or copied payloads; it arrives solely through recorded tamlinux-packages assemblies deployed via Home Manager and tam-deploy. See the Tamlinux package deployment contract.

Why does running hash -r matter after invoking tam switch or installing to a development prefix?

Bash caches the absolute path of executed commands in its internal hash table. If you previously ran tam from /nix/store/... or another directory, the shell will continue invoking the cached binary path until you run hash -r to flush the table.

When developing in the corpus lane, why should you run make corpus-and-test rather than make test?

make corpus-and-test tests only the documentation corpus, metadata indices, and guide rendering without running the extensive, slower interactive pager PTY test suite in tests/run.sh, keeping authoring feedback fast.

How it works

  1. C11 Architecture and Sub-5ms Startup: tam is written entirely in ISO C11. It avoids heavy runtimes, JIT compilation pauses, and dynamic module loading. At launch, the binary initializes terminal state via libtam, parses command-line arguments using a single-pass scanner, loads index structures via zero-copy memory mapping or sequential TSV streaming, and draws the first screenful of formatted text in under 5 milliseconds with resident memory below 4 megabytes.
  2. Decoupled Versioning and Dynamic Runtime Resolution: The binary version (src/version.h) is decoupled from the corpus version (knowledge/version). When invoked, src/tam.c discovers the corpus root by checking $TAM_KNOWLEDGE_DIR, followed by the user prefix ~/.local/dev/share/tamlinux/knowledge, and finally the compiled datadir /usr/share/tamlinux/knowledge. It reads knowledge/version dynamically at runtime. This allows documentation fixes and new lessons to land without recompiling the C executable, and guarantees multi-agent concurrency across command and corpus lanes.
  3. Transactional Development Generations and Atomic Switching: tam switch STAGE compiles candidates into isolated, timestamped directories: 
    ~/.local/dev/opt/tam/generations/<version>-<commit>-<hash>/
    Each successful generation writes a local receipt recording source pins, versions, checks, and previous targets. Once verified, the command switches the current symlink atomically. If a candidate fails verification, the active generation is untouched. tam switch --rollback restores the prior generation from local receipts without requiring network connectivity.
  4. The Develop -> Test -> Run -> Release Lifecycle: In Tamlinux, software moves across four disciplined stages governed by the generation and packaging model: 
    Develop (tam.git @ develop)
   │
   ▼  Fast-forward promotion
Test (tam.git @ test ──► pinned in tamlinux-packages flake)
   │
   ▼  Workstation acceptance & verification
Run (tam.git @ main ──► tamlinux-packages main)
   │
   ▼  Cultivar release tag & generation snapshot
Release (Tamlinux release)
    • Develop: Engineers and AI coding agents work in one shared clone on develop, claiming paths with tam-work and verifying changes with make check.
    • Test: Candidate commits are fast-forward promoted to test and pinned in tamlinux-packages via flake hashes. Home Manager builds the package outputs into /nix/store.
    • Run: After daily-driver acceptance, the tested commit promotes to main. Crucially, package outputs are not rebuilt: the identical byte-for-byte artifacts verified in Test are deployed to Run.
    • Release: On explicit developer instruction, accepted commits on main receive paired release tags (e.g. tam-0.31.0-corpus-0.32.1). If defects occur, rollback to the prior Home Manager generation restores the earlier working state.

Why Tamlinux chose this

A flagship system utility must remain available when the workstation is in distress. By compiling to a standalone C11 binary linked against libtam with zero background daemons, tam operates reliably in single-user recovery consoles even if Wayland compositors, graphics drivers, or package managers are broken. Decoupling command and corpus versioning allows documentation to evolve rapidly without recompilation churn, and the 4-stage lifecycle guarantees byte-for-byte reproducibility from development to release.

Edge cases and failure modes

Dirty working tree during install
make install refuses to proceed if any command or corpus path has uncommitted changes. This prevents partial, untracked development state from polluting installed prefixes.
Forward-compatible metadata parsing
The HTML tag scanner and index generators parse metadata additively. If an older command binary encounters newly added meta attributes (such as kind or skills), it ignores unrecognized fields gracefully without crashing or failing to display page content.
Dynamic library ABI shifts
Because Arch Linux is a rolling-release distribution, system libraries (such as libncursesw or libz) occasionally receive soname updates. Packaging via Home Manager pins dependencies in immutable Nix store paths, isolating production tools from rolling ABI disruptions.

Decide your answer before you reveal it.

Why does the Tamlinux lifecycle mandate that package outputs are NOT rebuilt when promoting from Test to Run?

Rebuilding introduces the possibility of non-deterministic differences, compiler toolchain changes, or unintended timestamp variations. Promoting the exact byte-for-byte package output tested during the Test stage guarantees that what was verified in daily use is identical to what runs in production.

How does the transactional generation architecture in tam switch protect against broken development builds?

Each build compiles into an isolated, timestamped generation directory under ~/.local/dev/opt/tam/generations/. The active generation link (current) is updated atomically only after the candidate passes verification tests and writes a complete receipt. If the build or tests fail, the symlink remains pointing to the previous functional generation, and tam switch --rollback can restore the earlier state without network access.
