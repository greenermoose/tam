Measuring algorithm performance

Asymptotic analysis predicts growth; measurement shows what actually happens on real hardware with real inputs. Good performance work uses both: analysis to choose candidates, measurement to confirm behavior.

Measure, don't guess

Two algorithms with the same Big-O class can have very different real speeds. One may use memory in a cache-friendly way; another may do extra allocations. The only way to know for your case is to measure carefully.

What to measure

  • Time: how long it takes (wall-clock or CPU time).
  • Memory: peak or typical memory use.
  • Input size: how cost changes as n grows.

Simple benchmarking

Goal: run a small, repeatable timing check and interpret it cautiously.

Worked example

$ python3 - <<'PY'
import time

def work(n):
    total = 0
    for i in range(n):
        total += i
    return total

for n in [100000, 200000, 400000]:
    t0 = time.perf_counter()
    work(n)
    t1 = time.perf_counter()
    print(n, f"{(t1-t0)*1000:.2f} ms")
PY
100000 2.31 ms
200000 4.62 ms
400000 9.10 ms

Illustrative timing; your numbers will vary. The useful signal is the trend: doubling n roughly doubled time, consistent with O(n).

Check yourself

Why is one timing run not enough?

Because runtime is affected by noise: CPU scheduling, caches, background processes, thermal state, and allocator behavior. Multiple runs give a more reliable picture.

How it works

Measure across input sizes and plot or compare growth. Use representative data distributions: worst-case, average, and adversarial inputs can differ sharply. Keep the environment stable, pin versions/configuration, and record hardware, compiler/interpreter, and flags. For asymptotic claims, show that measured ratios follow the expected growth over large enough n.

Edge cases

  • Compiler/interpreter optimizations: dead code elimination can make a benchmark "too fast" because no work was observed.
  • GC/runtime effects: managed runtimes may pause at unpredictable times.
  • I/O-bound vs CPU-bound: algorithmic improvements may not matter if disk/network dominates.
  • Latency vs throughput: mean time can hide tail latency spikes (p95/p99).

Check yourself

How do asymptotic analysis and benchmarking complement each other?

Asymptotic analysis predicts scaling behavior and rules out algorithms that cannot meet growth requirements. Benchmarking validates real constants, memory behavior, and system effects on representative inputs. Together they prevent choosing an algorithm that looks good in theory but performs poorly in practice, or one that wins on a tiny benchmark but collapses at scale.
