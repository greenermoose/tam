Guide / Systems and computing / Important algorithms for modern computing / Time complexity and Big-O notation

Time complexity describes how an algorithm's running time grows with input size. Big-O notation is the most common way to write that growth.

Growth rates, not seconds

A fast computer can make any small test look good. Time complexity asks a different question: if the input becomes much larger, does the cost grow slowly, steadily, or explosively?

Common growth classes

How to read and estimate Big-O

Goal: estimate time complexity from simple code patterns.

Rules of thumb

  • Constants drop: O(2n) is O(n).
  • Lower-order terms drop: O(n^2 + n) is O(n^2).
  • Sequential steps add, then simplify: O(n) then O(n) is O(n).
  • Nested loops multiply: a loop of n inside a loop of n is O(n^2), if body is O(1).
  • Halving loops are logarithmic: i *= 2 or n /= 2 often gives O(log n).

Worked example

$ python3 - <<'PY'
# O(n): one pass
def find_max(xs):
    m = xs[0]
    for x in xs:
        if x > m: m = x
    return m

# O(n^2): all pairs
def has_duplicate(xs):
    for i in range(len(xs)):
        for j in range(i+1, len(xs)):
            if xs[i] == xs[j]:
                return True
    return False

print(find_max([3,1,4,1,5]))
print(has_duplicate([3,1,4,1,5]))
PY
5
True

Illustrative example. The duplicate check is easy to read but scales poorly for large n; a hash set can make it O(n) average time with extra space.

Check yourself

Is O(n log n) better or worse than O(n^2) for large n?

Better for large n. As n grows, n^2 grows much faster than n log n. For small n, constants and implementation details can still matter.

How it works

Formally, f(n) ∈ O(g(n)) if ∃c,n0>0 such that f(n) ≤ c·g(n) for all n ≥ n0. Time complexity depends on the machine/cost model. The word-RAM model is common for in-memory algorithms; bit complexity matters for arbitrary-precision integers; I/O complexity matters for external memory.

Edge cases

  • Amortized analysis: dynamic array append is O(1) amortized though occasional resize is O(n).
  • Expected vs worst case: quicksort average O(n log n), worst O(n^2); hash tables average O(1) lookup, adversarial worst O(n).
  • Input representation: factoring algorithms are analyzed in bit length of the number, not its numeric value.
  • Hidden costs: comparisons, allocations, hash functions, and cache behavior can dominate in practice.

Check yourself

Why can an O(n) algorithm be slower than an O(n log n) algorithm in a real program?

Asymptotic notation drops constants and lower-order terms and assumes large n. For the actual input size, the O(n) algorithm may have large constants, poor cache behavior, expensive per-element work, or memory allocation overhead. Always combine asymptotic analysis with measurement.
