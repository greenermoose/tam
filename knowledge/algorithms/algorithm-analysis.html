Algorithm analysis is how we predict the cost of an algorithm as the input grows. Instead of asking only "is it fast on my machine?", we ask "how does its running time and memory use grow when the problem gets bigger?"

Why counting steps matters

Two programs can solve the same problem, but one may become unusably slow on large input. A stopwatch can tell you what happened for one test, but analysis helps you predict what will happen when the input is ten times, a thousand times, or a million times larger.

Two costs to watch

CostQuestionExample
Time complexityHow does running time grow?Checking every item takes longer as the list grows.
Space complexityHow much memory grows?Making a copy of a list uses extra memory proportional to the list.

How to think about it

Imagine looking for a name in a phone book. Scanning every page works, but a smarter method that halves the search area each step scales much better. Analysis gives you the vocabulary to compare those strategies before you run them on huge data.

Input size, cases, and growth

Goal: understand what algorithm analysis measures and what it ignores.

What "n" means

Analysis usually expresses cost as a function of input size, often written as n. For a list, n might be the number of items. For a number, it might be the number of digits or bits. For an image, it might be the number of pixels. The right n depends on the problem.

Cases

CaseMeaningWhen useful
Best caseLeast work for some input of size nOptimistic; rarely enough alone
Average caseExpected work over a distribution of inputsUseful when input distribution is realistic
Worst caseMost work for any input of size nSafe bound; common in guarantees
AmortizedAverage cost per operation over a sequenceUseful for dynamic arrays, hash tables, etc.

Worked example

$ python3 - <<'PY'
def linear_search(items, target):
    steps = 0
    for x in items:
        steps += 1
        if x == target:
            return steps
    return steps

items = list(range(10))
print(linear_search(items, 0))   # best case
print(linear_search(items, 9))   # worst case in this list
print(linear_search(items, 99))  # not found
PY

10
10

The same algorithm does different amounts of work depending on the input. Analysis usually reports the growth pattern, not just one lucky case.

Check yourself

Why is worst-case analysis common?

It gives a guarantee: the algorithm will not do worse than that bound for inputs of size n. This is useful when you need reliability, security, or predictable limits, even if typical inputs are easier.

How it works

Asymptotic analysis chooses a cost model (often the RAM model: simple operations and memory accesses cost O(1)) and counts how many such operations occur as a function of n. It then simplifies using Big-O notation and related notations. This gives machine-independent growth trends, but not exact seconds.

Edge cases

  • Small n: constants matter; an O(n^2) algorithm can beat O(n log n) for tiny inputs.
  • Memory hierarchy: cache misses can dominate runtime even when operation counts look good.
  • Input model: "n" may be value, count, bits, or graph size (V+E); be explicit.
  • Amortized vs worst-case: occasional expensive operations may be acceptable if average cost is bounded.
