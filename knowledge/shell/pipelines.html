Connecting programs

This page explains how to pass the output of one program to another.

A pipeline connects programs so that information produced by one becomes input for the next. The examples use known input so you can check the result.

Filter and count lines

Goal: you will be able to connect two filters and predict their result.

Why it matters: a command may print more than you need. A filter keeps the useful lines, and a counter tells you how many remain.

Before you start: open a terminal and read Shell and streams. This example only reads and prints text; it does not change files.

Type commands after the terminal's prompt. A leading $ below marks that prompt: do not type it. Press Enter after the complete command. The vertical bar is a pipe; on US QWERTY it is Shift+Backslash. The lines without a prompt are output, not commands.

Worked example

$ printf '%s\n' apple pear apple | grep '^apple$' | wc -l
2

Captured on Arch Linux, 2026-10-21. This fixed input gives the same count.

What just happened

  1. printf prints three lines: apple, pear, apple.
  2. | connects its standard output to the next command's standard input.
  3. grep '^apple$' keeps only whole lines equal to apple. ^ marks the start and $ the end.
  4. wc -l counts the two remaining newline characters.

Try it

Change only the pattern to '^pear$'. Predict the count, then run it. No scratch directory is needed because this writes no files.

If it goes wrong

The terminal shows a continuation prompt, often >.
You may have left a quote open or ended with a pipe. Press Ctrl+C and retype the complete line.
The count is zero.
Check spelling and letter case; apple and Apple are different patterns.

New words

Stream
Bytes a program reads or writes in order.
Filter
A command that selects or transforms its input.

Next step

It passes the printed bytes. A filename would need to be an argument or opened with a redirection.

What count will the pear variation print?

Choose filters and find failures

Goal: adapt a pipeline to new input and separate data errors from diagnostic messages.

Mental model

producer --stdout--> filter --stdout--> consumer
             stderr --> terminal

The usual pipe carries standard output (descriptor 1), not standard error (descriptor 2). A successful final command does not prove that the producer succeeded.

Worked example

$ printf '%s\n' pear apple pear | sort | uniq -c
      1 apple
      2 pear

Captured on Arch Linux, 2026-10-21, with LC_ALL=C. Sorting makes equal lines adjacent before uniq -c counts them. Locale can change ordering on other inputs.

Completion task

Using the same input, fill in the filter that must precede uniq -c: printf '%s\n' pear apple pear | ___ | uniq -c.

Use sort, as in the worked example. Without it, the two pear lines remain separated and are counted separately.

Independent task

Count distinct lines in red, blue, red, green, blue, rather than total lines or repetitions. Use a pipeline; do not hard-code the answer.

$ printf '%s\n' red blue red green blue | sort | uniq | wc -l
3

uniq without -c emits one line per adjacent run. Sorting first groups repeats; the result is three distinct lines. Captured on Arch Linux, 2026-10-21.

Check yourself

Answer before revealing the explanation.

A script ends with producer | wc -l and exits successfully, but producer reported an error. What do you check?

Run the producer alone and inspect its exit status and stderr. By default Bash reports the last command status; wc can succeed on empty input. pipefail helps detect a failing stage but does not repair it.

Why is uniq -c alone wrong for pear, apple, pear?

uniq combines adjacent equal lines only. Sort first if all repeated values should be counted together.

Descriptor order and pipeline status

Reference: descriptor 0 is standard input, 1 standard output and 2 standard error. Bash establishes pipe connections before command redirections, then applies redirections from left to right.

ExpressionEffect
>file 2>&1Open file on 1, then duplicate 1 onto 2
2>&1 >fileDuplicate the old 1 onto 2, then replace 1
|&Bash shorthand for a pipe with stderr merged after explicit redirections
PIPESTATUSBash array of statuses from the last foreground pipeline; inspect immediately

How it works

A Linux pipe is a finite byte buffer, without message boundaries. Writers may block when it is full; readers see EOF only when all write descriptors are closed. Writes up to PIPE_BUF have an atomicity guarantee; that limit is distinct from capacity. Do not assume a fixed capacity.

Explore

For this section, make a new temporary directory and enter it. These commands print nothing when they succeed. Keep this terminal open while you work through the section.

work=$(mktemp -d)
cd "$work"

$ bash -c 'printf "out\n"; printf "err\n" >&2' >both.txt 2>&1
$ cat both.txt
out
err

$ bash -c 'false | cat; printf "default: %s\n" "$?"; set -o pipefail; false | cat; printf "pipefail: %s\n" "$?"'
default: 0
pipefail: 1

Captured on Arch Linux, 2026-10-21. Predict the result of reversing the redirections before trying it. The separate Bash invocation confines pipefail to the experiment.

Edge cases and cost

Bash normally runs pipeline elements in subshell environments; the lastpipe option can change the last element's environment when job control is inactive. A consumer that exits early can give a writer SIGPIPE. Extra filters create processes and move bytes; prefer a direct file argument when it expresses the task clearly. Avoid polling pipelines when a single query answers the question.

Check yourself

Answer before revealing the explanation.

A reader hangs after the writer exits. Which evidence would you seek?

Check for another process holding a write end, including inherited descriptors. EOF depends on all writers closing, not just the original producer exiting. Inspect descriptor ownership before assuming a buffering bug.
