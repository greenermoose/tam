Connecting programs

This page explains how to pass information from one program into another so tools can work together.

What is a pipeline?

When you use a computer from the command line, programs are like small, specialized tools in a workshop. One tool might list names, another tool might search for a word, and a third tool might count lines. A pipeline is the way you connect these tools together in a row: the text produced by the first tool flows directly into the second tool as its input, without you needing to copy and paste or save a temporary file.

Why it matters

Instead of needing one massive program that does everything, Linux gives you hundreds of small, reliable tools that do one job well. Pipelines let you combine them to solve problems that no single tool could handle alone.

How to think about it

Think of an assembly line or a series of connected water pipes. Water flows from a pump, through a filter that cleans it, and finally into a tap. In the terminal, text flows from the first program, through a filtering program that discards what you do not want, and into a final program that formats or displays the result.

New words

Stream
A continuous flow of text or data traveling between programs.
Filter
A program that takes text in, removes or changes parts of it, and sends the remaining text onward.

Filter and count lines

Goal: connect two filters using a pipe and predict their combined output.

Worked example

$ printf '%s
' apple pear apple | grep '^apple$' | wc -l
2

Captured on Arch Linux, 2026-10-21. This fixed input gives the same count on every system.

What just happened

  1. printf prints three lines: apple, pear, apple.
  2. The vertical bar (|) passes the text printed by printf into grep.
  3. grep '^apple$' keeps only lines that match apple exactly, discarding pear.
  4. The second pipe sends those matching lines into wc -l, which counts the two remaining lines.

Try it

In your terminal, run the same pipeline but change the pattern from '^apple$' to '^pear$'. Predict the count before you press Enter.

If it goes wrong

The terminal shows a continuation prompt, often >.
You may have left a quote open or ended the command with a pipe. Press Ctrl+C and retype the complete line.
The count is zero.
Check spelling and letter case; apple and Apple are different patterns.

Check yourself

Answer before revealing the explanation.

Does the pipe pass a filename or the bytes printed by printf?

It passes the printed bytes. A filename would need to be an argument or opened with a redirection.

What count will the pear variation print?

1. Only the middle line is pear; the two apple lines are discarded.

Why sort before uniq when counting all repeats?

uniq groups adjacent equal lines only; sorting first brings identical lines together across the whole stream.

Descriptor order and pipeline status

Reference: descriptor 0 is standard input, 1 standard output and 2 standard error. Bash establishes pipe connections before command redirections, then applies redirections from left to right.

ExpressionEffect
>file 2>&1Open file on 1, then duplicate 1 onto 2
2>&1 >fileDuplicate the old 1 onto 2, then replace 1
|&Bash shorthand for a pipe with stderr merged after explicit redirections
PIPESTATUSBash array of statuses from the last foreground pipeline; inspect immediately

How it works

A Linux pipe is a finite byte buffer, without message boundaries. Writers may block when it is full; readers see EOF only when all write descriptors are closed. Writes up to PIPE_BUF have an atomicity guarantee; that limit is distinct from capacity. Do not assume a fixed capacity.

Illustrative reference

These commands illustrate descriptor duplication and pipeline status in a temporary directory.

work=$(mktemp -d)
cd "$work"

$ bash -c 'printf "out
"; printf "err
" >&2' >both.txt 2>&1
$ cat both.txt
out
err

$ bash -c 'false | cat; printf "default: %s
" "$?"; set -o pipefail; false | cat; printf "pipefail: %s
" "$?"'
default: 0
pipefail: 1

Captured on Arch Linux, 2026-10-21. Predict the result of reversing the redirections before trying it. The separate Bash invocation confines pipefail to the experiment.

Edge cases and cost

Bash normally runs pipeline elements in subshell environments; the lastpipe option can change the last element's environment when job control is inactive. A consumer that exits early can give a writer SIGPIPE. Extra filters create processes and move bytes; prefer a direct file argument when it expresses the task clearly. Avoid polling pipelines when a single query answers the question.

Clean up

rm -- both.txt
cd /tmp
rmdir -- "$work"

Check yourself

Answer before revealing the explanation.

Does reversing two redirections necessarily preserve their destinations?

No. Bash applies redirections from left to right; duplicating a descriptor records whichever destination was active at that point.

A reader hangs after the writer exits. Which evidence would you seek?

Check for another process holding a write end, including inherited descriptors. EOF depends on all writers closing, not just the original producer exiting. Inspect descriptor ownership before assuming a buffering bug.
