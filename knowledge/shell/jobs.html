Processes, Jobs, and Signals

A process is a running program instance. A shell job is one command or pipeline managed by that shell; it can contain several processes. Start practice processes yourself, and wait for them before finishing.

Start and wait for your own task

Goal: you will be able to run a short background task and recognize when it finishes.

Why it matters: work can continue while a command runs, but you still need to know what belongs to your shell and when it is done.

Before you start: read Shell and streams. This example creates only a one-second sleep process in a separate Bash shell.

Type after the terminal prompt; omit the leading dollar sign in a session. The ampersand starts a command in the background. Ctrl+C normally interrupts a foreground terminal job; it is not an undo key and does not select an arbitrary background task.

Worked example

$ bash -c 'sleep 1 & worker=$!; wait "$worker"; printf "worker finished\n"'
worker finished

Captured on Arch Linux, 2026-10-21. The output is fixed; job identifiers and notifications in an interactive shell can look different.

What just happened

  1. bash -c confines this exercise to a separate shell.
  2. sleep 1 & starts a short background task.
  3. $! gives its process ID; wait waits for that child.
  4. The final printf runs after the wait and prints the confirmation.

Try it

Change sleep 1 to sleep 2. The same message should arrive about a second later. Do not substitute another person's process.

If it goes wrong

Continuation prompt instead of execution
A quote is likely unfinished. Ctrl+C cancels that input; retype the complete command.
wait says the PID is not a child
The PID belongs to another shell or was copied incorrectly. Rerun the complete example in one shell.

New words

PID
A process identifier; it can be reused after the process exits.
Job
A shell's command or pipeline, which may include more than one process.

Check yourself

Decide before revealing the explanation.

Does a shell job always contain exactly one process?

No. A pipeline is one shell job but commonly contains several processes.

Why does this example save $! rather than searching by the name sleep?

It identifies the child just started by this shell. A name search could include unrelated tasks.

Choose a signal for an owned task

Goal: terminate a disposable child and inspect its status without signaling unrelated processes.

Mental model

shell --starts--> child PID
shell --signal request--> child
shell --wait--> termination status

A signal requests a disposition. SIGTERM can be caught or ignored; whether an application saves data depends on that application. SIGKILL cannot be caught and prevents user-space cleanup.

Worked example

$ bash -c 'sleep 30 & worker=$!; kill -TERM "$worker"; wait "$worker" 2>/dev/null; printf "wait status: %s\n" "$?"'
wait status: 143

Captured on Arch Linux, 2026-10-21. Bash reports 128 + 15 = 143 for this SIGTERM-terminated child. The wait's expected termination notification is redirected; its status is printed immediately, before another command replaces it.

Completion task

Explain the purpose of the saved worker PID, then fill the signal in kill -___ "$worker" to request ordinary termination of that same disposable child.

Use TERM. Keep the complete worked example in one shell. Do not replace it with pkill sleep: the latter selects every matching accessible process, including tasks outside this exercise.

Independent task

Adapt the beginner example to wait for a two-second task normally. Compare its successful wait with the signaled case; explain what evidence distinguishes completion from termination.

Use sleep 2 in the beginner example. A successful wait returns 0; the SIGTERM example prints 143 in Bash. Save or print the status immediately. Neither a process name nor absence from a later ps snapshot establishes how it ended.

Check yourself

Decide before revealing the explanation.

Is pkill sleep a safe replacement for the saved worker PID?

No. It can signal unrelated matching processes. The disposable child PID limits this exercise to the process it created.

Does successful kill prove the application saved its data?

No. It reports the signal request result, not completed application cleanup. Check the documented shutdown behavior and wait or service status.

Distinguish existence, identity and health

Reference: signals target processes or process groups according to kill's PID argument. Dispositions and masks differ; SIGKILL and SIGSTOP cannot be caught, blocked or ignored. A PID can be reused after exit. Existence alone is not identity or health.

How it works

The shell records its children and reaps their termination statuses with wait interfaces. Process groups organize terminal jobs, so terminal-generated signals need not target only one process. Zombie processes have exited but retain status until reaped.

Explore

$ bash -c 'kill -0 "$$"; printf "existence check: %s\n" "$?"'
existence check: 0

Captured on Arch Linux, 2026-10-21. Signal 0 performs existence/permission checking without sending a signal. It is not a health check and does not remove a PID-reuse race. Compare it with a verified child's wait status.

Edge cases and cost

Terminal closure, shell hangup policy, session management, open descriptors and application behavior all matter. disown and nohup are not universal workload-survival guarantees. Do not poll process existence in a busy loop when waiting or service supervision provides the needed lifecycle event.

Why can kill -0 succeeding still be insufficient evidence to signal a previously observed PID?

The check is a point-in-time existence/permission result. The original process may exit and the PID may be reused before the next operation. Use an appropriate stable process handle or lifecycle owner when identity matters, and preserve the recovery boundary.
