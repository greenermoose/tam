IP packets and forwarding

This page explains how an IP packet carries its destination, how routers decide where to send it next, and what happens when a packet is too large for one link.

What is an IP packet?

An IP packet is a small parcel of data with a sender address and a destination address written on it. Each router along the way reads the destination and hands the parcel to the next router, a bit like a sorting office reading a postcode.

Why it matters

No single machine needs to know the whole route. Every router only needs to know the next step. A counter on the packet stops it from circling forever if the routes are wrong.

How to think about it

Imagine a parcel passed along a chain of desks. Each desk looks at the town on the address, chooses the next desk, and crosses off one square on a ten-square travel card. When the card is empty, the parcel is thrown away instead of going around in circles.

New words

Packet
A small piece of data with addressing information attached.
Router
A machine that forwards packets between networks.
Gateway
The router a computer uses to reach destinations outside its local network.
MTU (Maximum Transmission Unit)
The largest packet a link can carry.

Read a route decision and a hop count

Goal: you will be able to ask the kernel which next hop it chooses, and explain what the hop count in a reply tells you.

Worked example

$ ip -4 route show default
default via 192.168.1.1 dev enp1s0 proto dhcp src 192.168.1.26 metric 100

$ ip route get 1.1.1.1
1.1.1.1 via 192.168.1.1 dev enp1s0 src 192.168.1.26 uid 1000
    cache

$ ping -c 2 -W 2 1.1.1.1
PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.
64 bytes from 1.1.1.1: icmp_seq=1 ttl=48 time=20.1 ms
64 bytes from 1.1.1.1: icmp_seq=2 ttl=48 time=20.0 ms

--- 1.1.1.1 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1001ms
rtt min/avg/max/mdev = 20.034/20.067/20.101/0.033 ms

Captured on a Tamlinux workstation, 2026-11-21. Your gateway, interface and hop count will differ.

What just happened

  1. The default route says: for anything not on a more specific local route, send to the gateway 192.168.1.1 through enp1s0.
  2. ip route get applies that rule to one destination and reports the same next hop and source address.
  3. The reply's ttl=48 started at 64 when it left the remote host. Each router subtracted one, so the packet crossed 16 routers on the way back.
  4. The round trip of about 20 milliseconds is the time for the whole exchange, not a property of any single router.

Try it

Run ip route get 1.1.1.1 and then ping -c 2 -W 2 1.1.1.1. Compare the starting hop limit (usually 64 on Linux) with the value in the reply. If your machine has IPv6 connectivity, repeat with ip -6 route get 2606:4700:4700::1111.

If it goes wrong

RTNETLINK answers: Network is unreachable
No route matches that destination. Check ip route for a default route and ip -br addr for an address on the outgoing interface.
A ping reply shows a very low hop count
The path has many routers, or another host is rewriting the hop limit. Use traceroute to see the individual routers.

Check yourself

Decide your answer before you reveal it.

A packet's hop limit reaches zero at a router. What happens, and who finds out?

The router drops the packet and sends an ICMP Time Exceeded (or ICMPv6 Time Exceeded) message back to the source. traceroute deliberately sends packets with increasing hop limits to collect those messages and learn each router on the path.

Why does a computer send a packet for a distant address to its gateway instead of directly to the destination?

The destination is outside the local prefix. The kernel has no on-link route for it, so it uses the default route: the gateway's hardware address goes in the frame, while the original destination IP stays in the packet.

How it works

Forwarding is a longest-prefix match over the kernel's routing table. For each candidate destination the router compares the packet's destination with the route's prefix; the route with the most matching leading bits wins, and the zero-length prefix is the default. The router decrements the hop limit, recomputes the header checksum for IPv4, resolves the next hop to a hardware address with ARP or NDP, and sends the frame onward. The original source and destination IP addresses do not change; only the link-layer addresses change at each hop, except when a NAT device rewrites them.

Path MTU discovery starts with a packet sized to the interface MTU and sets the Don't Fragment bit. A router that cannot forward it sends ICMP "Fragmentation Needed" (IPv4) or ICMPv6 "Packet Too Big" (IPv6) with the smaller MTU. The sender caches that result per destination. IPv4 routers may fragment when the bit is clear; IPv6 routers never do, so the sender must fragment in an extension header before sending.

Advanced usage

$ ip -j route get 1.1.1.1 | jq .
[
  {
    "dst": "1.1.1.1",
    "gateway": "192.168.1.1",
    "dev": "enp1s0",
    "prefsrc": "192.168.1.26",
    "flags": [],
    "uid": 1000,
    "cache": []
  }
]

Illustrative route decision from the workstation used above. Policy routing with ip rule selects among multiple tables before the longest-prefix match, and equal-cost multipath routes spread packets across several next hops.

Edge cases

  • Blocking all ICMP in a firewall breaks path MTU discovery, so small packets work while large transfers stall. This applies to ICMPv6 as well.
  • A tunnel adds outer headers, so the effective MTU for inner packets shrinks. Clamp the TCP maximum segment size or lower the tunnel interface MTU.
  • Asymmetric paths make a reply take a different route from the request, which reverse-path filtering can mistake for spoofing.
  • Offloading can make a packet appear larger in a capture than the application wrote; the NIC performs segmentation after the capture point.

Check yourself

Why can't an IPv6 router fragment a packet that is too large for the next link, and how does the sender recover?

IPv6 removes in-path fragmentation to keep router forwarding simple and fast. The router drops the packet and returns an ICMPv6 Packet Too Big message naming the link's MTU. The sender lowers its estimate for that destination, fragments at the source if needed, and retransmits. A firewall that drops Packet Too Big breaks this loop and leaves large transfers hanging.
