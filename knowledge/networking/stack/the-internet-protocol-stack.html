The internet protocol stack

This page explains how a message is split into layers so that a program on one computer can reach a program on another without either one knowing how the cable or radio works.

What is a protocol stack?

A protocol stack is a set of small jobs stacked on top of each other. Each job adds its own label to your message and passes it down to the next job. At the other end, the labels are read and removed in the reverse order until the original message arrives.

Why it matters

Layers let different kinds of equipment work together. A web page can travel from a laptop over Wi-Fi, through a router, across fiber, and into a server without the browser or the web server caring which cable carried each part. If one layer changes, the others do not have to be rewritten.

How to think about it

Think of sending a parcel. You write a note, put it in a box with a name on it, put the box in a mailbag with a route label, and hand the bag to a driver. The driver only reads the route label. When the parcel arrives, each wrapper is opened in reverse until the note is back in your friend's hands.

New words

Protocol
An agreed set of rules that two communicating programs follow.
Packet
A small piece of data with the addresses needed to deliver it.
IP address
The number that says which machine a packet is for.
Port
A number that says which program on that machine should receive the data.
Socket
The endpoint a program uses to send or receive network data.

Name the layers and find them on your machine

Goal: you will be able to name the four layers of the internet model and find the addresses and ports each layer adds on a running Linux system.

The four layers

  1. Application: the program's data and rules, such as DNS for names or HTTP for web pages.
  2. Transport: TCP or UDP, which adds port numbers so the right program receives the data.
  3. Internet: IP, which adds source and destination addresses so routers can forward the packet.
  4. Link: Ethernet or Wi-Fi, which turn the packet into signals on the local cable or radio link.

Worked example

$ ip -br addr show enp1s0
enp1s0           UP             192.168.1.26/24 fe80::80d1:99bb:b99:2848/64

$ ss -tan | head -4
State     Recv-Q Send-Q Local Address:Port     Peer Address:Port
LISTEN    0      128          0.0.0.0:22            0.0.0.0:*
LISTEN    0      4096      127.0.0.54:53            0.0.0.0:*
LISTEN    0      4096      127.0.0.1:45701         0.0.0.0:*

Captured on a Tamlinux workstation, 2026-11-21. Your interface names and addresses will differ.

What just happened

  1. ip -br addr shows the internet-layer address on the link named enp1s0: an IPv4 address and an IPv6 link-local address.
  2. ss -tan shows transport-layer endpoints. 0.0.0.0:22 means program listening on port 22 on every local address.
  3. The pair of an address and a port is a socket endpoint. A conversation is identified by the local and remote ends together.
  4. Nothing here shows the application data; that is added above the transport layer and is hidden by encryption for many web services.

Try it

Run ip -br addr and ss -tan on your own machine. Then run getent ahosts example.com to see the address an application gets after DNS resolves a name. All three commands only read state.

If it goes wrong

ss: command not found
The iproute2 tools are not installed. Use cat /proc/net/tcp to read the same kernel table in raw form.
No lines after the header in ss -tan
No TCP sockets are open right now. Open a web page and repeat the command.

On Tamlinux: NetworkManager owns connection state and systemd-resolved answers name lookups. The connection panel and tam-network-status read the same kernel and resolver state shown here; see Network connections and DNS for the command source and limits.

Check yourself

Decide your answer before you reveal it.

Which layer adds the IP address 192.168.1.26, and which adds the port 22?

The internet layer adds the address so routers can forward the packet. The transport layer adds the port so the receiving machine knows which program to hand the data to. The link layer then wraps both in a frame for the local cable or radio link.

Why can one IP address serve many web connections at once?

Because each conversation is identified by the local address, local port, remote address and remote port together. Different local port numbers keep the conversations separate inside the same machine.

The seven-layer OSI reference model splits the application layer into application, presentation and session, and splits the link layer into data link and physical. The four-layer internet model merges those pairs. Both describe the same exchange; neither is a separate implementation.

How it works

[ application data ]
[ TCP header ][ application data ]              segment
[ IP header  ][ TCP header ][ application data ] datagram
[ Ethernet header ][ IP header ][ TCP ][ data ][ FCS ] frame

Each layer reads only the header meant for it and passes the rest upward or downward. On the receive path a network interface places frames into memory, the driver raises an interrupt and the kernel's NAPI loop polls in batches to avoid an interrupt per packet. Each sk_buff carries header offsets that let layers add or remove headers without copying the payload. Netfilter hooks sit at PREROUTING, INPUT, FORWARD, OUTPUT and POSTROUTING, which is why a firewall rule can see a packet before or after a routing decision.

Advanced usage

$ ip -j route get 1.1.1.1 | jq .
[
  {
    "dst": "1.1.1.1",
    "gateway": "192.168.1.1",
    "dev": "enp1s0",
    "prefsrc": "192.168.1.26",
    "flags": [],
    "uid": 1000,
    "cache": []
  }
]

This shows the same route decision as data, including the source address the kernel would choose. Illustrative output from the workstation used above; your values will differ.

Edge cases

  • Checksums exist at several layers. A link-layer frame can be valid while the IP or transport checksum fails, so each layer reports its own errors.
  • A tunnel wraps an entire packet inside another one, adding another header pair and reducing the payload space available to the application.
  • Checksum offload and segmentation offload can make a captured frame look different from what the application wrote, because hardware fills in fields after the capture point.
  • A single physical interface can hold several addresses, and a network namespace gives each container its own stack with a separate loopback device.

Check yourself

A numeric address replies to a ping but a web page fails. Which layers are proven, and which still need checking?

The link, internet and ICMP parts of the stack work, because a ping reached the numeric destination and came back. Name resolution, the TCP connection, TLS and the HTTP application are still open. Test them in that order so each check eliminates one layer.
