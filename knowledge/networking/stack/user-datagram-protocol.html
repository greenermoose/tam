Guide / Networking / Internet protocol stack / User Datagram Protocol

UDP sends independent datagrams without setting up a connection, which suits small questions and live media where a fresh message matters more than a delayed one.

What is UDP?

UDP is a set of rules for sending a single message to another program. Each message carries its own destination, so nothing has to be set up beforehand. UDP does not check that the message arrived and does not resend it; the program using UDP decides what to do if a reply never comes.

Why it matters

Some jobs are short enough that setting up a reliable conversation would cost more than simply asking again. Looking up a name is like that: you send one question and usually get one answer. Skipping the setup makes the exchange faster and uses less network traffic.

How to think about it

Think of a postcard compared with a phone call. A postcard is quick to write and send, but it can be lost, and you do not know it arrived unless someone writes back. A phone call takes time to set up, but both people know the other is there. UDP is the postcard; TCP is the phone call.

Why do DNS and mDNS often use UDP?

A small question and answer fit in one datagram, avoiding the setup cost of a TCP connection.

Reference

Checksum16 bitsCovers a pseudo-header, the UDP header and the data; optional in IPv4, required in IPv6

The eight-byte header is the entire transport overhead. There are no sequence numbers, acknowledgements, window fields or connection states.

How it works

UDP is specified in RFC 768. A program creates a socket, binds an address and port if it expects replies, and sends each datagram with sendto(2). The kernel adds the UDP header and hands the result to the internet layer. On receipt, the kernel looks up the destination address and port, verifies the checksum when it is present, and places the datagram in the socket's queue. Message boundaries survive: one send produces one datagram, and one receive returns one whole datagram, provided the buffer is large enough.

Because there is no handshake, a UDP sender can transmit immediately. Because there is no retransmission, correctness belongs to the application: DNS retries a question and falls back to TCP when an answer is too large; multicast DNS repeats announcements; real-time media simply accepts some loss; QUIC builds its own reliability over UDP.

Advanced usage

Edge cases

  • A receive buffer that is smaller than the datagram truncates it. The application must notice the truncation flag and use a larger buffer.
  • A large UDP datagram is fragmented at the internet layer. Losing one fragment loses the whole datagram, so applications keep datagrams small.
  • A service that answers a small request with a much larger reply can be used for reflection attacks. Good implementations rate-limit or verify the source.
  • An unconnected UDP socket accepts datagrams from any source. An application that cares who sent a message must authenticate it at its own layer.
  • A path that drops UDP entirely breaks name lookup and local discovery even though TCP connections still work; test with dig rather than a browser.
