User Datagram Protocol

This page explains how UDP sends one self-contained message at a time, without setting up a conversation first.

What is UDP?

UDP is a set of rules for sending a single message to another program. Each message carries its own destination, so nothing has to be set up beforehand. UDP does not check that the message arrived and does not resend it; the program using UDP decides what to do if a reply never comes.

Why it matters

Some jobs are short enough that setting up a reliable conversation would cost more than simply asking again. Looking up a name is like that: you send one question and usually get one answer. Skipping the setup makes the exchange faster and uses less network traffic.

How to think about it

Think of a postcard compared with a phone call. A postcard is quick to write and send, but it can be lost, and you do not know it arrived unless someone writes back. A phone call takes time to set up, but both people know the other is there. UDP is the postcard; TCP is the phone call.

New words

UDP (User Datagram Protocol)
A transport protocol that sends independent messages without a connection.
Datagram
A self-contained message that carries its own addressing information.
Port
A number that picks the program that should receive a message.
Checksum
A short value that lets the receiver notice damaged data.

Find UDP services on a running machine

Goal: you will be able to read the UDP socket table, identify well-known services by their port numbers, and explain why a service would choose UDP.

Worked example

$ ss -uln | head -6
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
UNCONN 0      0         172.17.0.1:53        0.0.0.0:*
UNCONN 0      0         127.0.0.54:53        0.0.0.0:*
UNCONN 0      0      127.0.0.53%lo:53        0.0.0.0:*
UNCONN 0      0            0.0.0.0:5353      0.0.0.0:*
UNCONN 0      0               [::]:5353         [::]:*

Captured on a Tamlinux workstation, 2026-11-21. Your sockets and addresses will differ.

What just happened

  1. UNCONN means no connection state is kept. Each datagram is handled on its own.
  2. Port 53 is the DNS service. The 127.0.0.53%lo entry is the local resolver that applications on this machine ask first.
  3. Port 5353 is multicast DNS, which answers questions about devices on the local link.
  4. [::]:5353 is the same service listening for IPv6 datagrams; 0.0.0.0 and [::] mean all local addresses of that family.

Try it

Run ss -uln, then getent ahosts example.com while watching the table again. Name resolution usually begins with one UDP question to the local resolver. These commands only read state.

If it goes wrong

Port 53 is missing
No local resolver is listening on that address. Check resolvectl status to see which resolver the system is configured to use.
A service listens only on 127.0.0.1
It will not answer requests from other machines. That is normal for a local-only resolver; an uncovered address is needed for network-wide service.
A UDP reply never arrives
UDP cannot tell you why. Check whether a firewall drops the datagram, the service is running, or the request went to the wrong address.

On Tamlinux: the local resolver address 127.0.0.53 and the multicast DNS service on 5353 come from systemd-resolved and Avahi. The same setup pages explain how the name lookup reaches them; see Name resolution and Avahi and Zeroconf.

Check yourself

Decide your answer before you reveal it.

A name lookup gets no reply. Why can't UDP tell the program whether the request or the reply was lost?

UDP keeps no connection state and sends no acknowledgements. The sender sees only silence, which could mean the request never arrived, the service did not reply, or the reply was dropped. A program that needs to know retries, times out or switches to another transport.

Why do two UDP services on one machine use different port numbers?

The kernel uses the port to choose which socket receives an incoming datagram. Without distinct ports it could not deliver a packet to DNS rather than multicast DNS. The address and port together form the endpoint that the program binds.

Reference: datagram semantics and the UDP header

Reference

FieldSizeMeaning
Source port16 bitsEndpoint that sent the datagram, used for replies
Destination port16 bitsEndpoint that should receive it
Length16 bitsLength of the UDP header and data in bytes
Checksum16 bitsCovers a pseudo-header, the UDP header and the data; optional in IPv4, required in IPv6

The eight-byte header is the entire transport overhead. There are no sequence numbers, acknowledgements, window fields or connection states.

How it works

UDP is specified in RFC 768. A program creates a socket, binds an address and port if it expects replies, and sends each datagram with sendto(2). The kernel adds the UDP header and hands the result to the internet layer. On receipt, the kernel looks up the destination address and port, verifies the checksum when it is present, and places the datagram in the socket's queue. Message boundaries survive: one send produces one datagram, and one receive returns one whole datagram, provided the buffer is large enough.

Because there is no handshake, a UDP sender can transmit immediately. Because there is no retransmission, correctness belongs to the application: DNS retries a question and falls back to TCP when an answer is too large; multicast DNS repeats announcements; real-time media simply accepts some loss; QUIC builds its own reliability over UDP.

Advanced usage

$ ss -ulnp | head -6
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
UNCONN 0      0         172.17.0.1:53        0.0.0.0:*
UNCONN 0      0         127.0.0.54:53        0.0.0.0:*
UNCONN 0      0      127.0.0.53%lo:53        0.0.0.0:*
UNCONN 0      0            0.0.0.0:5353      0.0.0.0:*
UNCONN 0      0               [::]:5353         [::]:*

Captured on the same workstation, 2026-11-21. The -p flag would add the owning process, but an unprivileged reader sees no process column here; processes owned by other users need elevated privileges. ss -uap also shows UDP sockets that are not listening, which matters when diagnosing an application that sends requests but never receives replies.

Edge cases

  • A receive buffer that is smaller than the datagram truncates it. The application must notice the truncation flag and use a larger buffer.
  • A large UDP datagram is fragmented at the internet layer. Losing one fragment loses the whole datagram, so applications keep datagrams small.
  • A service that answers a small request with a much larger reply can be used for reflection attacks. Good implementations rate-limit or verify the source.
  • An unconnected UDP socket accepts datagrams from any source. An application that cares who sent a message must authenticate it at its own layer.
  • A path that drops UDP entirely breaks name lookup and local discovery even though TCP connections still work; test with dig rather than a browser.

Check yourself

What does an application give up by choosing UDP, and what must it provide itself if it needs reliable delivery?

It gives up the handshake, ordered delivery, retransmission, flow control and congestion control that TCP supplies. If it still needs reliable delivery, it must number its messages, detect gaps, retry, and back off when the path is congested. QUIC does exactly this in user space; DNS instead keeps its requests small and simply retries on timeout.
