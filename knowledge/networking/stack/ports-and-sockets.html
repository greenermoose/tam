Guide / Networking / Internet protocol stack / Ports and sockets

This page explains how a single computer can run many network conversations at once without mixing them up.

What is a port?

A port is a small number attached to a network message that says which program should receive it. An IP address identifies the computer; a port identifies the particular service or conversation inside it.

Why it matters

Without ports, a computer could only run one network program at a time. Ports let a web browser, a mail program and a printer service all use the same connection at the same time.

How to think about it

Think of a large apartment building. The street address gets a letter to the building; the apartment number gets it to the right household. The IP address is the street address and the port is the apartment number. A socket is the doorway that a program stands at to hand letters in and out.

New words

Port
A number from 0 to 65535 that identifies a service or conversation endpoint.
Socket
The endpoint a program uses to send and receive network data.
TCP
A transport protocol that keeps a reliable, ordered conversation.
UDP
A transport protocol that sends independent messages without a connection.

Read listening sockets and identify a conversation

Goal: you will be able to read a socket table, name the four values that identify a conversation, and explain why local port numbers are reused by different remote connections.

Worked example

$ ss -tan | head -5
State     Recv-Q Send-Q Local Address:Port     Peer Address:Port
LISTEN    0      128          0.0.0.0:22            0.0.0.0:*
LISTEN    0      4096      127.0.0.54:53            0.0.0.0:*
LISTEN    0      4096      127.0.0.1:45701         0.0.0.0:*
LISTEN    0      128        127.0.0.1:35577         0.0.0.0:*

$ ss -uln | head -6
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
UNCONN 0      0         172.17.0.1:53        0.0.0.0:*
UNCONN 0      0         127.0.0.54:53        0.0.0.0:*
UNCONN 0      0      127.0.0.53%lo:53        0.0.0.0:*
UNCONN 0      0            0.0.0.0:5353      0.0.0.0:*
UNCONN 0      0               [::]:5353         [::]:*

Captured on a Tamlinux workstation, 2026-11-21. Your open ports will differ.

What just happened

  1. LISTEN means a program is waiting for new connections on that address and port. Port 22 is the usual SSH service; port 53 is DNS.
  2. 0.0.0.0:22 listens on every IPv4 address on the machine; 127.0.0.54:53 listens only on a local loopback address.
  3. UNCONN in the UDP table is a socket with no connection state: it accepts independent datagrams.
  4. Port 5353 is multicast DNS, which announces local printers and devices; it appears once for IPv4 and once for IPv6.

Try it

Run ss -tan, then ss -uln. Open a web page and run ss -tan state established: each line is one live conversation with its local and remote address and port. These commands only read kernel state.

If it goes wrong

ss: command not found
The iproute2 tools are missing. Read /proc/net/tcp and /proc/net/udp instead; the port numbers are in hexadecimal.
An address and port you expect is missing
The service may not be running, or it may listen only on IPv6. Check ss -tlan for all listening TCP sockets on both families.

Check yourself

Decide your answer before you reveal it.

Two browser tabs connect to the same website on port 443. Why don't the connections collide?

Each connection gets its own local port from the ephemeral range. A conversation is identified by local address, local port, remote address and remote port together, so two tabs have different four-tuples even though the remote port is the same.

Linux actually draws ephemeral ports from /proc/sys/net/ipv4/ip_local_port_range, which usually defaults to a narrower range than the conventional one. Root privileges are needed only to bind a port below 1024, unless the process holds the CAP_NET_BIND_SERVICE capability.

How it works

A program calls socket(2) to create a socket, bind(2) to choose a local address and port, listen(2) to accept TCP connections, and accept(2) to obtain a new socket for each client. The original listening socket stays open. The kernel matches an incoming segment to a socket by hashing the four-tuple, with separate lookup tables for listening and established sockets. UDP uses sendto(2) and recvfrom(2), and preserves message boundaries: one send becomes one datagram. A socket appears in the process's file descriptor table, so /proc/<pid>/fd and lsof -i show which program owns it.

Captured on a Tamlinux workstation, 2026-11-21; the remote addresses and local ports depend on which sites are open. ss -ti adds TCP timer and congestion information. SO_REUSEPORT lets several processes share one listening port, and the kernel distributes incoming connections among them.

Edge cases

  • A closed TCP connection spends time in TIME_WAIT so delayed duplicates cannot be mistaken for a new connection on the same four-tuple.
  • Two sockets cannot normally bind the same address and port. A wildcard 0.0.0.0 bind conflicts with a specific address bind on the same port unless options permit sharing.
  • Network namespaces each have their own port space, so containers can reuse the same ports without conflict.
  • A UDP socket with no peer receives datagrams from any source; an application that cares about identity must authenticate the sender itself.

Check yourself

What breaks if two processes bind the same address and port without SO_REUSEPORT, and why does the second bind fail?

The kernel has no way to decide which socket should receive an incoming segment, so the second bind returns EADDRINUSE. With SO_REUSEPORT the kernel accepts both sockets and spreads incoming connections among them, which is how multi-process servers balance load on one port.
