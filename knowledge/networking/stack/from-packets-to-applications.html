From packets to applications

This page follows one request for a web page through every layer, from the first lookup of a name to the moment the page appears on screen.

What happens when you open a web page?

Your computer first turns the name you typed into a number, then works out where to send a message to that number, then opens a reliable conversation, then asks for the page. The reply travels back through the same kinds of steps in reverse.

Why it matters

When a page will not load, each step gives a different clue. A failure at the name step means the number was never found. A failure at the route step means there is no path. A failure at the conversation step means the two programs could not agree or exchange data.

How to think about it

Think of asking a librarian for a book. You look up the shelf number in a catalogue, find the aisle, walk to the shelf, and hand over your request. The book comes back through your hands. If the catalogue, the aisle or the shelf is missing, you know exactly where to look for the problem.

New words

DNS (Domain Name System)
The service that turns a readable name into a network address.
TCP
The protocol that keeps the conversation reliable and in order.
TLS (Transport Layer Security)
The protocol that encrypts the conversation and checks the server's identity.
HTTP (Hypertext Transfer Protocol)
The rules for asking a web server for a page and receiving it.
IP address
The number that identifies a machine on the network.

Follow a request with read-only commands

Goal: you will be able to name the stage each command checks, and say which layer a failure belongs to.

Worked example

What just happened

  1. getent ahosts asks the system resolver for a name. It returns addresses with the socket types that can use them: STREAM for TCP, DGRAM for UDP and RAW for direct internet-protocol use.
  2. ip route get asks the kernel where a packet to a numeric destination would go. The answer names the gateway and the source address, without sending anything.
  3. ss -tan state established shows real TCP conversations. Each line is a pair of endpoints: a local address and port, and a remote address and port.
  4. TLS and the web request itself run inside those conversations. They add encryption and page semantics above the transport layer, so the socket table cannot show them.

Try it

Run the three commands while a web page is open. Then close the page and run the last one again: the finished connections disappear or move to a closing state. All three commands only read state.

If it goes wrong

The name lookup returns nothing
Check resolvectl status. A failed name lookup stops the process before any route or connection is attempted.
Network is unreachable from ip route get
No route matches the destination. Check the interface address and the default route before blaming the website.
An address resolves and a route exists, but no connection appears
The remote service may refuse the connection, a firewall may drop it, or TLS or the web application may fail after the connection opens. Test the port before inspecting the page contents.

On Tamlinux: name lookup goes through systemd-resolved and the connection's DNS settings; the browser does not read DNS servers directly. The Name resolution page shows what to check when that hand-off fails.

Check yourself

Decide your answer before you reveal it.

A numeric address replies to a ping, but the page will not open. What have you ruled out, and what do you check next?

Link, addressing, routing and basic internet control messages work. Check that a TCP connection to the web port can be established, then TLS and the HTTP response. Each check isolates one layer above the one the ping proved.

Why can the socket table not tell you whether TLS succeeded?

TLS data travels inside the TCP stream as ordinary bytes from the transport layer's point of view. The socket table reports addresses, ports, queues and timers, not the meaning of the bytes. A browser or a tool such as openssl s_client must inspect the application data.

How it works

A resolver reads the system's name-service configuration, queries a local cache and, on a miss, sends a UDP question to a configured DNS server. The answer is a set of addresses. The kernel then performs a longest-prefix route lookup for the chosen address, selects a source address, and creates a TCP socket with an ephemeral local port. The three-way handshake establishes sequence numbers and windows. The application writes an encrypted TLS record containing an HTTP request into the socket; TCP segments it, IP addresses it, and the link layer frames it for the next hop. At the far end each layer removes its own header before handing the data upward.

Modern browsers prefer HTTPS and often negotiate HTTP/2 over TCP. HTTP/3 instead uses QUIC over UDP, moving the handshake and reliability into user space so a lost packet does not block unrelated streams. Both reach the same application result through different transport choices.

Captured on the same workstation, 2026-11-21. The JSON form is useful when a script needs the route decision; a human usually prefers the plain form shown in the Learner section. curl -v adds the name lookup, connection, TLS and HTTP lines in one trace, which is the quickest way to see all four stages at once.

Edge cases

  • A name can resolve to several addresses. Happy Eyeballs tries both families so a broken path does not stall the page while the host waits for a timeout.
  • A CNAME or a load balancer can change the address between two lookups, so a new connection need not reach the same machine as an old one.
  • DNS over HTTPS hides the lookup inside a TLS connection to a resolver, which changes what a local packet capture can reveal.
  • TLS session resumption shortens a later handshake, so a short connection can carry data almost immediately.
  • Early replies and cached content can complete before a firewall or a path-MTU problem shows up in a large transfer.

Check yourself

A page loads over HTTP/3 while ss -tan shows no connection for it. Explain why.

HTTP/3 uses QUIC, which runs over UDP rather than TCP. The connection appears in ss -uan or in the QUIC implementation's own state, not in the TCP table. The layers above still perform name lookup, route selection, encryption and an HTTP request, but the transport that carries them has changed.
