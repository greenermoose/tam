Guide / Networking / Internet protocol stack / Transport layer

The transport layer is the part of the network stack that carries data between programs on different machines, usually by adding port numbers and choosing how delivery should behave.

What the transport layer does

The internet layer can deliver a packet to the right machine. The transport layer helps deliver it to the right program on that machine. It also decides whether the conversation should be careful and ordered, like a phone call with confirmations, or quick and simple, like sending postcards.

Why it matters

Your computer can run many network programs at once: a browser, chat app, and update service. Transport-layer ports keep those conversations separate.

How to think about it

If an IP address is the building address, a port number is the apartment number. The transport layer makes sure the message reaches the right apartment.

Worked example

$ ss -tan
$ ss -uan

ss -tan shows TCP sockets; ss -uan shows UDP sockets. The local and peer address:port pairs identify endpoints.

What just happened

TCP and UDP are the two common transport protocols. TCP provides a reliable, ordered byte stream. UDP sends independent datagrams with less overhead and no built-in delivery guarantee. Both use ports so multiple programs can share one IP address.

Try it

Run ss -tlnp with appropriate permissions to see listening TCP ports. Compare with ss -ulnp for UDP listeners.

If it goes wrong

A port is not listening
The service may not be running, or it may be listening on a different address or interface.
Connection refused
The machine was reachable, but no program accepted the transport connection on that port.

Check yourself

Why does the transport layer need ports if IP already has addresses?

An IP address identifies a host or interface, but many programs can use the network at the same time. Ports let the transport layer multiplex and demultiplex data to the correct program.

How it works

The transport layer demultiplexes incoming packets to sockets using the 5-tuple: source IP, source port, destination IP, destination port, and protocol. TCP adds sequence numbers, acknowledgements, flow control, and congestion control. UDP provides a minimal header with ports, length, and checksum. QUIC builds reliable, encrypted transport features in user space over UDP.

Advanced usage

$ ss -ti state established

TCP info exposes round-trip time, congestion window, retransmissions, and other transport state useful for diagnosing performance.

Edge cases

  • NAT and firewalls: Middleboxes may rewrite ports or drop packets, making transport behavior depend on path state.
  • Ephemeral ports: Clients usually use temporary local ports chosen from a configured range.
  • Head-of-line blocking: TCP's ordered stream can delay later bytes when an earlier segment is lost; some applications avoid this with UDP/QUIC.

Check yourself

When is UDP a better fit than TCP?

UDP fits when an application can tolerate or handle loss, needs low overhead, or manages its own timing/retransmission semantics, such as DNS, real-time media, or QUIC-based protocols.
