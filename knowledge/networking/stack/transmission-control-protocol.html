Guide / Networking / Internet protocol stack / Transmission Control Protocol

TCP turns an unreliable stream of packets into a reliable, ordered byte stream by numbering data, acknowledging it and retransmitting what was lost.

What is TCP?

TCP is a set of rules for sending data in a way that recovers from loss. The sender numbers every piece, and the receiver confirms what arrived. Missing pieces are sent again, and the receiver puts the pieces back in order before giving them to the program.

Why it matters

Networks lose, delay and reorder messages. A web page or a file would be damaged if pieces went missing or arrived in the wrong order. TCP hides those problems so a program can read a steady stream, much as you read a book without caring how the pages were printed and delivered.

How to think about it

Imagine reading a long message to a friend over a noisy phone line. You number each sentence. Your friend says which sentences arrived. When one is missed, you say it again. Your friend waits before showing you a gap, so the story always appears in the right order, even though the words travelled one by one.

What does TCP retransmit?

Bytes that were not acknowledged within the expected time, so the receiver still gets an ordered stream.

How it works

TCP is specified in RFC 9293. A connection begins with a three-way exchange: the client sends SYN with an initial sequence number, the server replies SYN-ACK with its own number, and the client acknowledges it. Data then flows in both directions. Each acknowledgement names the next byte expected, so loss is inferred from a gap or from several duplicate acknowledgements.

The sender keeps a retransmission timer whose value is computed from the smoothed round-trip time and its variance; rto:214 in the example is that timer in milliseconds. Flow control protects the receiver: its advertised window limits how much unacknowledged data the sender may keep in flight. Congestion control protects the network: the sender grows cwnd as acknowledgements arrive and reduces it when loss or delay signals a bottleneck. Linux uses cubic by default; other algorithms such as BBR estimate bandwidth and delay instead of treating loss as the main signal.

Advanced usage

Edge cases

  • A connection in TIME_WAIT deliberately keeps its four-tuple for a while so delayed duplicate segments cannot join a new connection with the same endpoints.
  • Head-of-line blocking: if one segment is lost, the receiver withholds later bytes from the application even though they arrived, because the stream must stay ordered.
  • A notification based only on packet loss mistakes wireless interference for congestion; delay-based algorithms and explicit congestion notification try to separate the two.
  • Offloaded segmentation can hide the real segment count from a packet capture: the NIC splits a large write after the capture point.
  • A black-holed path MTU makes large transfers stall while small requests succeed, because ICMP \"Fragmentation Needed\" messages are dropped by an overzealous firewall.
