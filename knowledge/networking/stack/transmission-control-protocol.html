Transmission Control Protocol

This page explains how TCP makes a conversation over an unreliable network feel like one reliable, ordered stream of bytes to the programs at each end.

What is TCP?

TCP is a set of rules for sending data in a way that recovers from loss. The sender numbers every piece, and the receiver confirms what arrived. Missing pieces are sent again, and the receiver puts the pieces back in order before giving them to the program.

Why it matters

Networks lose, delay and reorder messages. A web page or a file would be damaged if pieces went missing or arrived in the wrong order. TCP hides those problems so a program can read a steady stream, much as you read a book without caring how the pages were printed and delivered.

How to think about it

Imagine reading a long message to a friend over a noisy phone line. You number each sentence. Your friend says which sentences arrived. When one is missed, you say it again. Your friend waits before showing you a gap, so the story always appears in the right order, even though the words travelled one by one.

What just happened

  1. ESTAB is implied by the filter: the connection has finished its opening handshake and is carrying data.
  2. rtt:13.118/0.807 is the smoothed round-trip time in milliseconds and its variation. It is the time for a byte to reach the far end and an acknowledgement to come back.
  3. mss:1400 is the largest piece of application data in one segment; pmtu:1500 is the largest packet the path carries. The gap is room for headers.
  4. cwnd:10 is the congestion window, measured in segments. TCP may have about ten segments in flight before it waits for more acknowledgements.
  5. cubic names the congestion-control algorithm; wscale:8,10 shows the window-scaling factors that let both ends advertise large buffers.
  6. Nonzero Send-Q would mean data is waiting in the kernel, which can point to a slow receiver or a congested path.

Try it

Open a web page, then run ss -ti state established '( dport = :443 or sport = :443 )'. Reload the page and run it again: bytes_sent, rtt and cwnd change as the connection learns about the path. All these commands only read state.

If it goes wrong

No lines after the header
No HTTPS connection is open at that moment. Open a page and repeat; a plain HTTP connection uses port 80, so the filter above will not show it.
rto grows much larger than rtt
The retransmission timeout is rising because acknowledgements are missing. Look for loss on the path or a receiver that is overwhelmed.
Large Send-Q that does not drain
The kernel has data it cannot deliver. Check the receiver's advertised window and whether the network is dropping packets.

On Tamlinux: TCP settings come from the Linux kernel, not from the connection panel. On the workstation used above, sysctl net.ipv4.tcp_congestion_control reports cubic, which matches the cubic label in ss -ti.

Check yourself

Decide your answer before you reveal it.

Why does TCP use sequence numbers as well as a checksum?

A checksum detects damaged data but says nothing about order or loss. Sequence numbers let the receiver place each piece correctly, spot a missing piece and ask for it again. A checksum alone would tell you that a piece was bad, not which piece should come before another.

A connection has a small round-trip time but a tiny congestion window. What does that suggest?

A small window despite quick replies suggests the sender recently saw loss and cut its rate, or the application has little data to send. Check bytes_sent and app_limited: if the application is not feeding data, the window is not the bottleneck.

How it works

TCP is specified in RFC 9293. A connection begins with a three-way exchange: the client sends SYN with an initial sequence number, the server replies SYN-ACK with its own number, and the client acknowledges it. Data then flows in both directions. Each acknowledgement names the next byte expected, so loss is inferred from a gap or from several duplicate acknowledgements.

The sender keeps a retransmission timer whose value is computed from the smoothed round-trip time and its variance; rto:214 in the example is that timer in milliseconds. Flow control protects the receiver: its advertised window limits how much unacknowledged data the sender may keep in flight. Congestion control protects the network: the sender grows cwnd as acknowledgements arrive and reduces it when loss or delay signals a bottleneck. Linux uses cubic by default; other algorithms such as BBR estimate bandwidth and delay instead of treating loss as the main signal.

Advanced usage

$ sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_rmem
net.ipv4.tcp_congestion_control = cubic
net.ipv4.tcp_rmem = 4096	131072	33554432

Captured on the same workstation, 2026-11-21. The three tcp_rmem values are the minimum, default and maximum receive buffer sizes in bytes; auto-tuning grows the buffer toward the maximum on fast paths. ss -ti exposes the negotiated receive window and scaling factor that result.

Edge cases

  • A connection in TIME_WAIT deliberately keeps its four-tuple for a while so delayed duplicate segments cannot join a new connection with the same endpoints.
  • Head-of-line blocking: if one segment is lost, the receiver withholds later bytes from the application even though they arrived, because the stream must stay ordered.
  • A notification based only on packet loss mistakes wireless interference for congestion; delay-based algorithms and explicit congestion notification try to separate the two.
  • Offloaded segmentation can hide the real segment count from a packet capture: the NIC splits a large write after the capture point.
  • A black-holed path MTU makes large transfers stall while small requests succeed, because ICMP \"Fragmentation Needed\" messages are dropped by an overzealous firewall.

Check yourself

Why might a flow with a very high bandwidth and a long round trip still fail to fill the link, even with no loss?

The sender can have at most one congestion window of unacknowledged data in flight. If the window is small relative to the bandwidth-delay product, the sender runs out of permission to send and waits for acknowledgements. Window scaling and a suitable congestion algorithm let the window grow large enough; so does having enough application data to send in the first place.
