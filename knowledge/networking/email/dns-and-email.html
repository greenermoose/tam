Guide / Networking / Email / DNS and email

DNS does more for email than translate names to numbers. It says which servers accept mail, carries authentication policy, helps protect connections and provides places to send reports.

Finding the right server

When a sender has an address such as bo@example.org, it looks up the part after the @ sign. A special DNS entry called an MX record names the servers that accept mail for that domain. DNS also supplies the network addresses needed to connect to them.

Why it matters

Web service and mail service can live on different machines. Looking specifically for mail records lets a domain keep its website and its inbox in different places.

How to think about it

DNS is like a directory at a building entrance. One entry says which desk handles parcels; another says where that desk is. The sender follows the directory instead of guessing.

New words

MX record
A DNS record naming a server that accepts mail for a domain.
A and AAAA records
DNS records that give a name an IPv4 or IPv6 address.
PTR record
A reverse DNS record that maps an address back to a name.
DNSSEC
A set of records and signatures that lets a resolver verify DNS answers.

If it goes wrong

You thought the higher MX number was preferred.
Lower preference values are tried first. Equal preferences allow selection among equivalent hosts.
You treated a matching PTR name as proof the sender is genuine.
Reverse DNS is a weak signal. Authentication systems publish and check specific records instead.

The guide teaches DNS records as portable standards. Tamlinux does not add a special DNS system for mail; readers use the resolver and tools already present on their system.

Check yourself

Decide your answer before you reveal it.

Why does a sender look up MX rather than only the domain's web address?

Mail service may be hosted separately from the website. MX records name the hosts designated to accept mail, with preference ordering.

Can a PTR record replace SPF or DKIM?

No. A PTR name is only reverse mapping. SPF and DKIM use defined TXT records and validation rules tied to the envelope or message signature.

How it works

A sending server resolves MX for the recipient domain, sorts by preference and resolves A or AAAA for a target. RFC 5321 defines an implicit MX at the domain itself when no MX record exists and an address record is present. An MX target is a host name; it should not be an alias record, so the address records belong at that name. DNSSEC lets a validating resolver detect forged or modified DNS data; DANE's TLSA checks are meaningful only when the chain to that TLSA record validates.

Advanced usage

CNAME rules deserve care: a domain with other records, such as SPF or DMARC, should not be a CNAME to another name because the related records would be hidden. SPF uses TXT records and an ordered set of mechanisms; DKIM places the public key under a selector chosen by the signer; DMARC uses a TXT record at a fixed prefix and requests aggregate or forensic reports. MTA-STS adds an HTTPS-hosted policy with a TXT marker, while TLS-RPT names an address for failure reports.

Edge cases

  • Caching and TTLs mean a DNS change may not be visible everywhere at once.
  • A PTR record is controlled by the address owner, not necessarily by the domain in the message header.
  • Multiple MX hosts share traffic by preference and availability; DNS alone does not prove a host is reachable.

Check yourself

Why does DANE for SMTP depend on DNSSEC?

A TLSA record states which certificate should be trusted. Without DNSSEC validation, an attacker who can alter DNS could replace that record along with the address records.
