Guide / Networking / Email / Identity and transport security

Email security answers two different questions: is a message allowed to claim a domain, and is the connection between servers protected? DNS records and signatures provide the evidence for both.

Two jobs, not one

SPF, DKIM and DMARC help a receiver decide whether a domain really stands behind a message. TLS protects the connection while mail moves between servers. A passing check does not make the content safe: a genuine sender can still send a bad message.

Why it matters

A visible From: line is easy to write and easy to fake. Domain checks give the receiver something harder to forge. Encryption stops a network observer from reading or changing a connection in transit.

How to think about it

Think of an identity badge and a sealed delivery van. The badge says which organisation sent the parcel; the van protects it on the road. A real badge does not prove the parcel's contents are harmless.

New words

SPF
A DNS record listing hosts allowed to send for a domain.
DKIM
A signature in the message verified with a public key in DNS.
DMARC
A policy that connects SPF or DKIM results to the visible sender domain.
STARTTLS
An SMTP extension that upgrades a connection to TLS.

What just happened

  1. SPF passed for the envelope domain, and DKIM passed for a signing domain.
  2. Neither domain aligned with the visible From: domain, so DMARC failed.
  3. TLS protected one hop but said nothing about the sender's identity.
  4. The content signal remained separate: a message can pass technical checks and still be a phishing attempt.

If it goes wrong

You assumed SPF pass means the visible sender is genuine.
SPF authorises the envelope domain. DMARC adds the alignment requirement for the visible domain.
You assumed TLS makes the sender trustworthy.
TLS protects a hop. It does not authenticate the human author or approve the content.

The guide presents these as internet standards, not settings unique to Tamlinux. A reader's mail provider decides which checks it applies and how strictly it enforces them.

Check yourself

Decide your answer before you reveal it.

Can SPF pass and DMARC fail for the same message?

Yes. SPF may authorise the envelope domain while that domain does not align with the visible From: domain required by DMARC.

Does STARTTLS guarantee an encrypted hop?

No. It is often opportunistic. If the extension is stripped or negotiation fails and the sender continues in plaintext, the hop may be unencrypted.

How it works

RFC 7208 defines SPF and its ordered evaluation; RFC 6376 defines DKIM signing and verification. RFC 9989 is the current DMARC specification and obsoletes RFC 7489; it requires SPF or DKIM to align with the visible domain and requests aggregate and forensic reports. ARC is defined by RFC 8617 so a receiver can see which hop broke authentication. SRS is a widely used convention rather than an IETF standard. BIMI group specification is an industry specification, not an IETF RFC.

Advanced usage

Transport protection has three complementary approaches. Opportunistic STARTTLS, defined by RFC 3207, encrypts when both sides negotiate successfully. DANE for SMTP, built on RFC 6698 and RFC 7672, uses a DNSSEC-validated TLSA record to pin the expected certificate. MTA-STS, defined by RFC 8461, publishes an HTTPS policy with a DNS marker; RFC 8460 defines TLS-RPT reporting for connection failures.

Edge cases

  • Forwarding can break SPF because the forwarding host is not the original authorised sender; DKIM often survives forwarding unchanged.
  • DMARC pass is an identity result, not a safety judgement. Malware and phishing from an authorised domain can pass.
  • DANE requires end-to-end DNSSEC validation at the relying server; MTA-STS has its own fetch and caching rules.

Check yourself

Why do ARC and SRS exist if SPF and DKIM already exist?

Forwarding changes the path. SRS rewrites the return path so SPF can still be meaningful, while ARC records a verifiable chain of authentication results across hops.
