Guide / Networking / Email / How a mail server works

A mail server is a set of jobs rather than one magic action. It accepts a message, keeps it in a queue, chooses a next hop, and eventually writes the message into a mailbox or passes it to another server.

Accept, carry, deliver

When you send mail, a server accepts it from your client. Another server may carry it part of the way. At the end, a server puts it into the receiver's mailbox. Each step can happen at a different time.

Why it matters

If the next server is busy or offline, the current server can keep the message and try again. That is why a message can be sent successfully even when the receiver cannot yet read it.

How to think about it

Imagine a sorting office. A counter accepts your parcel, a sorter chooses the next office, a truck carries it, and a local delivery worker puts it in a letter box. The parcel may wait at more than one desk.

New words

Submission agent
The server role that accepts a new message from a client.
Transfer agent
A server role that relays mail toward the receiver.
Delivery agent
The role that places mail into a mailbox.
Queue
A held list of messages waiting for a later step.

What just happened

  1. The message was accepted during submission, not delivered immediately.
  2. A queue entry kept it safe while the server chose a next step.
  3. A temporary failure produced another queue entry. The message was retried rather than discarded.
  4. The delivery agent finished the journey by writing to the mailbox.

If it goes wrong

The trail seems to go backwards.
A retry can return a message to a queue after a relay attempt fails. That is normal store-and-forward behaviour.
You expected one server to do everything.
Small systems may combine roles in one program, but the sample separates them so each boundary is visible.

Check yourself

Decide your answer before you reveal it.

A message is queued after a temporary failure. Was it rejected?

No. A temporary failure leaves the message eligible for retry. A permanent rejection ends that delivery attempt and normally produces a bounce.

Which role puts a message into a mailbox?

A mail delivery agent, or the delivery stage of a combined server. Transfer agents hand the message onward; they do not normally write the final mailbox.

How it works

RFC 5598 names the functional roles; RFC 5321 defines the SMTP session and status codes that drive queue decisions. A two-digit class in a reply code separates a temporary 4xx condition from a permanent 5xx condition. A transfer agent records the envelope recipient and attempts each recipient separately, because one recipient can fail while another succeeds.

Advanced usage

Relay selection uses DNS MX records, address records and connection policy. Delivery may pass through a local LMTP service or a filtering stage before the message store. Alias expansion can change the final recipient without changing the visible header.

Edge cases

  • A queue can hold a message for a long time if every retry is temporary; operators watch queue age and retry counts.
  • Loop prevention relies on hop counts and recipient tracing. A misconfigured relay can still create a mail loop.
  • Accepting a message does not prove the final mailbox stored it. Later filtering or a downstream failure can still produce a bounce.

Check yourself

Why is queue age a useful signal but not proof of loss?

An old queued message may be waiting on a deliberate retry interval or a downstream outage. Loss needs evidence such as a final bounce or missing queue entry after the retry policy ends.
