Avahi and Zeroconf

Local service discovery lets a printer, screen or file share announce itself on a network so a computer can find it without being told its address first.

Before this

Name resolution explains ordinary DNS, which answers names from a configured server. This page begins where that server is not needed.

Finding things on a network with no central list

Imagine walking into a room where everyone wears a name badge and calls out what they can do. You do not need a directory of the room; you listen. A network can work the same way: a device calls out "I am a printer called Demo Printer at this address and port", and your computer hears it.

Why it matters

You rarely type a printer's address. A browser shows a list of nearby screens, a print dialog shows nearby printers, and a file manager shows nearby shares. That works because the devices announced themselves on the local network. Understanding the announcement lets you explain why a device appears on one network but not another.

How to think about it

Device with a service     --- announces --->  everyone on the local link
Your computer             --- asks -------->  everyone on the local link
                          <--- answers -----  the device that offers it

Several names describe the same idea. Zeroconf is the general set of "zero configuration" techniques. Bonjour is Apple's name for its implementation. Avahi is the free implementation used on Linux. Underneath, mDNS answers names on the local link and DNS-SD describes services using DNS record types.

New words

Avahi
The Linux daemon and tools that publish and discover local services.
Zeroconf
Zero-configuration networking: connecting devices without a central configuration service.
Bonjour
Apple's name for its Zeroconf implementation, compatible with Avahi.
mDNS
Multicast DNS, which resolves names by asking every device on the local link.
DNS-SD
DNS-Based Service Discovery, which lists service instances and resolves each to a host and port.

Publish and find a service

Goal: you will be able to publish a temporary test service, read the discovery output, resolve the resulting local name and stop the test cleanly.

Before you start: the Avahi daemon must be running on your machine. The example creates a short-lived service in your own session and then removes it. It does not install anything or change configuration files.

Worked example

$ avahi-publish -s 'Demo Printer' _ipp._tcp 631 &
Established under name 'Demo Printer'
$ avahi-browse _ipp._tcp -t -r -p
+;enp1s0;IPv4;Demo\032Printer;Internet Printer;local
+;lo;IPv4;Demo\032Printer;Internet Printer;local
=;enp1s0;IPv4;Demo\032Printer;Internet Printer;local;workstation.local;192.168.1.26;631;
=;lo;IPv4;Demo\032Printer;Internet Printer;local;workstation.local;127.0.0.1;631;
$ avahi-resolve -4 -n "$(hostname).local"
workstation.local       192.168.1.26

Captured on a wired Arch Linux workstation on 2026-11-21 with Avahi 0.9-rc5. The host name is shortened to workstation.local here; your name, interfaces and addresses will differ. Stop the publisher with kill %1 or Ctrl+C in the shell that started it.

What just happened

  1. avahi-publish -s registers a service instance named Demo Printer of type _ipp._tcp on port 631. The ampersand puts it in the background so the next command can run.
  2. avahi-browse -t asks for instances of that type and terminates after collecting them; -r resolves each one; -p prints semicolon-separated fields suitable for scripts.
  3. Lines beginning + announce that a service was found. Lines beginning = give the resolved host name, address and port.
  4. \032 is the DNS text escape for a space. Service instance names can contain spaces; the parsable output escapes them so fields stay separated.
  5. The same service appears on enp1s0 and lo because Avahi listens on both interfaces. The loopback copy resolves to 127.0.0.1; the wired copy resolves to the LAN address.
  6. avahi-resolve resolves the machine's .local name to an address using multicast DNS rather than a configured DNS server.

Try it

Repeat the example with a name of your own, then run avahi-browse -a -t -r -p to see all advertised types on the link. End with avahi-browse -D -t to list discovery domains. Stop every publisher you started; a forgotten one keeps announcing a service that no longer exists.

If it goes wrong

No services appear
Check systemctl is-active avahi-daemon. If it is inactive, start it with systemctl start avahi-daemon, which needs privilege; then browse again.
A service appears but cannot be resolved
The publisher may have stopped, or a firewall may block UDP port 5353. The Tamlinux host firewall template permits mDNS from the local home subnet.
avahi-resolve fails for a .local name
Ordinary DNS does not answer .local. Check that a Name Service Switch module such as nss-mdns is installed and that the resolver is not claiming the domain first.
Services appear only from this machine
Multicast traffic may be confined by a switch, a guest-network setting or a firewall. Discovery is a link-local mechanism and does not cross a router by default.

Tamlinux's host firewall template permits mDNS on UDP 5353 from the local home subnet, and its connection pages direct DNS changes through a command that records a snapshot. The template is documented in the public product repository; the enabled protocols on a given machine can be checked with resolvectl status, where -mDNS means systemd-resolved is not answering .local and the Avahi stack handles it instead.

Check yourself

Why does the same service appear twice in the browse output?

Avahi listens on more than one interface. It sees its own announcement on the wired interface and through loopback, each with a different address. Device lists normally hide the local copies, but the parsable output shows both.

What does the _ipp._tcp part identify?

A DNS-SD service type: Internet Printing Protocol over TCP. It is a label used to group instances of the same kind of service, not the printer's name or its address.

Predict what happens if the firewall drops UDP 5353 on the wired interface.

Local announcements still appear on loopback, but no other machine is heard and no announcement from this machine reaches the network. Browse shows little or nothing while the daemon itself remains active.

How it works

mDNS uses the DNS wire format without a configured server. A query is sent to the multicast group with a destination port of 5353 and IP TTL 255; every host on the link receives it, and the host that owns the answer multicasts a response. Responses are delayed by a random interval of 20 to 120 milliseconds so that several hosts answering at once do not collide. A host choosing a name first probes for it with tentative records, then announces it with unsolicited responses; a later claimant that wins a conflict sends its own announcement while the loser picks a new name. A withdrawal is announced with a record whose TTL is zero, called a goodbye packet.

Unique records, such as an address record for a host name, carry a cache-flush bit so receivers discard older copies; shared records do not. Negative answers use NSEC records to prove that a name or type does not exist, which avoids repeated multicast queries for missing names. Known-suppression keeps a host from repeating an answer it recently heard from someone else, at the cost of losing some redundancy.

DNS-SD adds naming structure to those DNS records. A service instance is named <Instance>.<Service>.<Domain>, for example Demo Printer._ipp._tcp.local. A PTR query for _ipp._tcp.local enumerates instances; resolving an instance fetches its SRV record, which gives host and port, and its TXT record, which carries small key/value attributes. Every DNS-SD service has a TXT record even when it is empty. Service type enumeration uses _services._dns-sd._udp.local, and subtypes such as _printer._sub._ipp._tcp.local narrow a browse.

Avahi is the Linux implementation: avahi-daemon owns multicast responses and records, applications talk to it over D-Bus, and avahi-browse, avahi-resolve and avahi-publish are clients of that interface. Its configuration file controls host-name, domain-name, use-ipv4, use-ipv6, allow-interfaces, deny-interfaces, enable-dbus, the publish-* switches and enable-wide-area. Host-name resolution for applications uses a Name Service Switch module such as nss-mdns, which is separate from the daemon.

Advanced usage

# /etc/avahi/services/printer.service - published by the daemon at start
<service-group>
  <name replace-wildcards="yes">Printer on %h</name>
  <service>
    <type>_ipp._tcp</type>
    <port>631</port>
    <txt-record>txtvers=1</txt-record>
  </service>
</service-group>

A static definition publishes a service even when no application is running. Reload the daemon after a change. This is an illustrative file, not an exercise; a typo in /etc/avahi/services/ can publish a misleading service to the whole link.

Edge cases

  • mDNS has no built-in authentication. Any host on the link can claim a name or service, so it is unsuitable as a security boundary.
  • The .local suffix is for link-local use. Sending those queries to a global DNS server, or using .local inside a corporate DNS domain, creates conflicts.
  • Multicast does not cross routers by default. A printer on another VLAN will not appear unless a repeater or a conventional DNS-SD deployment bridges the domains.
  • Hosts with several interfaces can answer on all of them. Interface allow and deny lists keep a service off a guest or VPN network.
  • Name conflicts are resolved by probing, so two devices with the same factory name will change one another's names; the name a user saved may not be the name that appears tomorrow.
  • DNS-SD TXT records are meant to be small. Large records are expensive on wireless links and may be truncated; a missing key must be handled as unknown, not as an error.
  • Wide-area mode changes how queries and responses are framed for unicast DNS. It is not the normal home-network setting and needs deliberate configuration.

Check yourself

Why does DNS-SD use PTR records for browsing instead of SRV records alone?

A query for an SRV record assumes the instances are interchangeable and returns targets directly. DNS-SD needs a user-visible list of named instances to choose from, so a PTR query returns instance names first; the client then resolves the chosen instance with SRV and TXT queries.

What does the cache-flush bit accomplish, and why is it only set on unique records?

It tells receivers to discard older data for that name and type, which is correct when exactly one host owns the record. Shared records can legitimately have several owners, so flushing would erase valid answers from other hosts.

Sources
