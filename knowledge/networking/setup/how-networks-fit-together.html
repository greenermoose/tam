How networks fit together

A network is a set of devices that can exchange messages, and every working connection answers the same four questions: how to reach the wire or radio, what address to use, where to send traffic for other networks, and how to turn a name into an address.

Before this

Giving your computer written instructions helps if you want to try the commands yourself.

The four questions of every connection

Imagine sending a letter. You need a way to hand it to the postal service, a street address for the recipient, knowledge of which sorting office handles other towns, and a way to look up an address from a person's name. A computer asks the same four questions.

Why it matters

When something breaks, these four layers fail independently. A cable can be unplugged while the address is still assigned; an address can be correct while the router is wrong; the router can work while a name lookup fails. Answering the questions in order turns a vague "the internet is down" into a specific fault.

How to think about it

1. LINK     which door does traffic leave?        a network interface
2. ADDRESS  what number identifies this machine?  an IP address
3. ROUTE    where do other networks live?         a gateway and a routing table
4. NAME     what number belongs to this name?     a DNS resolver

The kernel owns the first three. A service such as NetworkManager tells the kernel what to put there. The DNS resolver answers the fourth question by asking other machines.

New words

Network interface
The named doorway a computer uses to send and receive traffic, such as enp1s0 for wired Ethernet or wlp3s0 for Wi-Fi.
IP address
A number that identifies a machine on a network, much as a street address identifies a house.
Gateway
The router that carries traffic leaving your local network for other networks.
DNS
The Domain Name System, which turns a name such as example.com into an IP address.
DHCP
A service that hands out addresses and other settings automatically when a device joins a network.
Packet
A small block of data sent across the network, carrying part of a message and the addresses needed to deliver it.

Read the four answers from a running system

Goal: you will be able to name the active interface, its address, the gateway and the DNS server, and say which command revealed each one.

Before you start: the commands below only read network state. They do not change a connection. Open a terminal and run them one at a time.

Type what follows the $ and press Enter; do not type the $. Your interface names, addresses and timings will differ from the example. Success means the command prints something useful, not that the numbers match.

Worked example

$ ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp1s0           UP             192.168.1.26/24 fe80::80d1:99bb:b99:2848/64
enp2s0           DOWN
wlp3s0           DOWN
docker0          DOWN           172.17.0.1/16 fe80::14cd:83ff:febb:9e4b/64
$ ip route
default via 192.168.1.1 dev enp1s0 proto dhcp src 192.168.1.26 metric 100
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 linkdown
192.168.1.0/24 dev enp1s0 proto kernel scope link src 192.168.1.26 metric 100
$ getent ahosts example.com
104.20.23.154   STREAM example.com
104.20.23.154   DGRAM
104.20.23.154   RAW
172.66.147.243  STREAM

Captured on a wired Arch Linux workstation on 2026-11-21. The name lookup is shortened here; your resolver will return its own addresses.

What just happened

  1. ip -br addr answers the link and address questions. UP means the interface is enabled; DOWN means it is not. lo is the loopback interface the machine uses to talk to itself.
  2. 192.168.1.26/24 is an IPv4 address with a prefix length; fe80::…/64 is an IPv6 link-local address valid only on this cable or radio link.
  3. ip route answers the route question. The default line names the gateway for everywhere outside the local 192.168.1.0/24 network.
  4. proto dhcp records where the setting came from: DHCP supplied it. proto kernel marks a route the kernel added from an address on the interface.
  5. getent ahosts answers the name question through the system's normal lookup rules and prints the addresses in the order it tried them.

Try it

Run nmcli device status and compare its DEVICE and CONNECTION columns with the interfaces you saw above. Then run ip route get 1.1.1.1: it tells you which interface and source address the kernel would choose for a numeric destination, without sending a packet.

If it goes wrong

The interface shows DOWN or NO-CARRIER
There is no link. Check the cable or join a Wi-Fi network before changing any address.
No line begins with default
The machine has no route to outside networks. Local addresses may still work; remote traffic cannot leave.
An address is present but getent prints nothing
The link, address and route layers work while name resolution fails. Check the resolver with resolvectl status.
command not found
The tool is not installed on this system. ip comes from iproute2 and getent from the C library tools; on Tamlinux both are present.

On Tamlinux, NetworkManager owns connection state and systemd-resolved answers ordinary DNS questions. The Tamlinux panel reads NetworkManager and calls the same tam-network-* commands a terminal user calls; tam-network-status --verbose prints the interface, address, gateway and ping times together. Those behaviors are recorded in the public tamlinux repository under commands/ and desktop/shell/panels/network/.

Check yourself

A machine has an address on enp1s0 but no default route. What still works?

Traffic to destinations on the local 192.168.1.0/24 network still works, because the kernel added a route for that prefix from the interface's address. Traffic to the wider internet has no next hop, so it fails.

Why does the example use a numeric address with ip route get?

A numeric destination avoids a DNS lookup, so the result describes only the routing decision. Using a name would mix the route and name questions in one answer.

Which layer produces the line proto dhcp in the routing table?

The address-configuration layer. A DHCP client supplied the address and default route; the kernel installed them in the table and recorded the origin as dhcp.

How it works

Outgoing data is wrapped as it descends. An application writes bytes to a socket; TCP or UDP adds a header with port numbers; IP adds source and destination addresses; the link layer adds a frame header with neighbor addresses. The routing table decides which interface carries each packet, and the neighbor table turns the next-hop IP address into a hardware address. On receive, the reverse happens.

NetworkManager does not implement the stack. It computes a desired configuration from saved profiles and pushes it into the kernel through netlink, then monitors the interface for changes. systemd-resolved listens on a local stub address and answers getent queries through the Name Service Switch, forwarding to the servers listed per link or globally. Keeping the authorities separate is why a broken resolver does not corrupt routes, and why a link flap does not erase saved profiles.

Advanced usage

$ ip -j route get 1.1.1.1 | python3 -m json.tool
{
    "1.1.1.1": {
        "via": "192.168.1.1",
        "dev": "enp1s0",
        "src": "192.168.1.26",
        "uid": 1000,
        "cache": true
    }
}

The JSON form is the machine-readable version of the same decision. It is useful when a script must check which interface would carry a destination without sending traffic.

Edge cases

  • Loopback is a real interface with its own address. Traffic to 127.0.0.1 never leaves the machine, which makes it a safe place to test a service.
  • A link-local IPv6 address (fe80::/10) needs a scope identifier, written fe80::…%enp1s0, because the same prefix can exist on several interfaces.
  • A virtual interface such as docker0 or a VPN tunnel appears in the same lists as hardware. It may carry a route without any physical cable.
  • An address can be present while its route is marked linkdown. The kernel keeps the configuration, but no carrier means nothing can be delivered.
  • Name resolution is not a single service: /etc/hosts, NSS modules, mDNS and DNS each answer some names. The order is set in /etc/nsswitch.conf.

Check yourself

Why can NetworkManager and the kernel both be said to "own" an address?

NetworkManager owns the desired configuration in a saved profile and applies it; the kernel owns the live address and routing table that actually forward packets. They are authorities at different layers, which is why nmcli and ip addr can briefly disagree during a reconnect.
