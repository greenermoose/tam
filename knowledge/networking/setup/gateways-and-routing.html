Guide / Networking / Network setup / Gateways and routing

A routing table tells a computer which door to use for each destination; the default route is the door used when no more specific rule applies.

Before this

Adding a connection shows where the gateway setting comes from.

The signpost at every crossroads

When a computer sends a packet, it asks a simple question: is the destination on my own local network? If yes, it delivers the packet directly using the destination's hardware address. If no, it hands the packet to a gateway, usually the router that connects the local network to the wider internet.

Why it matters

A machine can have a correct address and still be unable to reach the internet if it has no default route. It can also have two default routes and send traffic out the wrong one. Reading the table tells you which case you have.

How to think about it

destination on 192.168.1.0/24  --> deliver directly on enp1s0
any other destination          --> send to gateway 192.168.1.1 on enp1s0

The first rule is more specific than "any other destination", so it wins. That is the whole idea behind routing: pick the most specific matching rule.

New words

Gateway
The router that carries traffic from the local network to other networks.
Router
A device that forwards packets between networks.
NAT
Translation of private addresses at the network boundary, often performed by the same router.
IP address
The number used as both the destination and the source in an IP packet.
Network interface

Ask the kernel which path it would take

Goal: you will be able to read a routing table, explain each column, and use ip route get to find the path for a destination without sending traffic.

Before you start: both commands below only read the table and compute a decision. Nothing is added or removed.

Worked example

$ ip route
default via 192.168.1.1 dev enp1s0 proto dhcp src 192.168.1.26 metric 100
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 linkdown
192.168.1.0/24 dev enp1s0 proto kernel scope link src 192.168.1.26 metric 100
$ ip route get 1.1.1.1
1.1.1.1 via 192.168.1.1 dev enp1s0 src 192.168.1.26 uid 1000
    cache
$ ip route get 192.168.1.1
192.168.1.1 dev enp1s0 src 192.168.1.26 uid 1000
    cache

Captured on a wired Arch Linux workstation on 2026-11-21. Your addresses, interface names and metrics will differ.

What just happened

  1. The default route has no prefix restriction, so it matches every destination that no other route claims.
  2. via 192.168.1.1 is the next hop: the packet carries the remote destination but is sent to the gateway's hardware address on the wire.
  3. The 192.168.1.0/24 route was added by the kernel from the interface's own address; it needs no gateway because that prefix is on the link.
  4. proto dhcp on the default route means a DHCP server supplied the gateway; proto kernel means the kernel derived the route from an address.
  5. metric 100 is a preference. When two routes match equally, the lower metric wins.
  6. ip route get 1.1.1.1 uses the default route; ip route get 192.168.1.1 shows a direct delivery because the gateway is on the local prefix.

Try it

Run ip route get 8.8.8.8 and ip -6 route. The first reports the chosen next hop for a public IPv4 address. The second shows IPv6 routes, including a default route learned from a router advertisement when one is present. Both are read-only.

If it goes wrong

No line begins with default
There is no route outside the directly connected prefixes. Check the profile's gateway or whether DHCP supplied one.
Two default routes appear with different metrics
Both are valid; the lower metric is preferred. This is normal when a wired and a wireless connection, or a VPN, are active at once.
The gateway is not on any local prefix
The kernel cannot reach the next hop, so the route cannot be used. Correct the gateway or the prefix length.
A route shows linkdown
The configuration exists but the interface has no carrier. Reconnect the cable or Wi-Fi; the route becomes usable when the link returns.

Tamlinux leaves routing to NetworkManager and the kernel. The connection status command chooses the device by asking ip route get 1.1.1.1 rather than guessing from the first interface in a list; that detail is recorded in the public tamlinux repository under commands/tam-network-status.

Check yourself

Why does a packet to a remote address carry the gateway's hardware address?

Ethernet delivers frames within one link using hardware addresses. The IP destination stays the remote server, but the frame must be addressed to the next hop that can forward it, which is the gateway.

A host has routes for 10.0.0.0/8 and 10.1.2.0/24. Which wins for 10.1.2.5?

The /24 route, because longest-prefix match chooses the most specific network that contains the destination.

Predict the route get output when no default route exists.

A numeric public destination such as 1.1.1.1 produces a "Network is unreachable" result, while a destination on the local prefix still resolves to a direct delivery.

How it works

Route lookup walks the relevant tables and applies longest-prefix match, then route type, metric and protocol as tie-breakers. The main table is number 254; ip rule selects which tables are consulted and in what order, which is how source-based routing sends traffic from one address out a particular interface. The source address chosen by ip route get comes from the preferred address on the outgoing interface, not from the destination.

Routing and NAT are different functions. A router forwards a packet without changing its addresses; a NAT gateway rewrites the source or destination as it crosses a boundary. A VPN adds a virtual interface and usually a more specific set of routes plus a default route with a lower metric, while leaving the physical interface's local route intact.

Advanced usage

$ ip -j route get 1.1.1.1 | python3 -m json.tool
{
    "1.1.1.1": {
        "via": "192.168.1.1",
        "dev": "enp1s0",
        "src": "192.168.1.26",
        "uid": 1000,
        "cache": true
    }
}
$ ip rule
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default

The JSON form and the rule list show the same decision from two angles: the route that was chosen, and the tables that were eligible to supply it.

Edge cases

  • Asymmetric routing occurs when a packet leaves by one interface and the reply would leave by another. Stateful firewalls and NAT break when paths differ.
  • Equal-cost multipath installs several next hops for one prefix; the kernel chooses among them by hash, which keeps a flow on one path.
  • A default route supplied by DHCP can disappear when the lease is lost, even though manually added routes remain.
  • Router advertisements can supply a default route with a lifetime. An expired advertisement leaves the prefix reachable but removes the default route.
  • Reverse-path filtering drops packets whose source address would not be reachable through the interface they arrived on; it is a defense against spoofing that can surprise users of multiple interfaces.

Check yourself

Why might a VPN connection work for some destinations but not others?

The VPN may add specific routes for its own networks without replacing the default route, or its default route may have a higher metric than the local one. Check ip route and ip route get for the failing destination to see which path was selected.
