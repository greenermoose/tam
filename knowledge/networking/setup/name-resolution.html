Name resolution

Name resolution turns a name people remember, such as example.com, into the address a network actually uses.

Before this

Gateways and routing explains the address that the resolver's answer is used to reach.

A phone book that asks other phone books

DNS is a distributed phone book. Your computer asks a local resolver; the resolver asks other servers, starting near the root of the name tree, until it finds the server responsible for the name. The answer is an IP address that the routing layer can use.

Why it matters

Names change address when a service moves. Using a name means a bookmark keeps working; using a hard-coded address breaks. When a name fails but a numeric address works, you know the link and the route are fine and only the lookup needs attention.

How to think about it

example.com
  --> local resolver (often your router or a public server)
  --> root server: "ask the .com servers"
  --> .com server: "ask the servers for example.com"
  --> authoritative server: "104.20.23.154"

A DNSSEC signature can prove an answer has not been altered, but it does not make the lookup private. Ordinary DNS queries travel in clear text unless an encrypted transport is configured.

New words

DNS
The Domain Name System, a hierarchical service that maps names to data such as addresses.
Host name
A label for a machine, which may be resolved locally or through DNS.
DHCP
The service that often tells a computer which resolver to use when it joins a network.
DNSSEC
Signed DNS records that let a resolver verify the origin and integrity of an answer.
mDNS
Multicast DNS, which answers names on the local link without a central server.

What just happened

  1. getent ahosts uses the system's Name Service Switch rules, so it answers exactly as an application would. It prints IPv4 and IPv6 addresses in the order the resolver supplied.
  2. resolvectl status shows that this machine uses a stub resolver: applications send queries to a local address and systemd-resolved forwards them to the servers listed per link.
  3. The active link has DNS scope and +DefaultRoute, so its server handles names without an explicit routing domain; other links have no DNS scope.
  4. resolvectl query asks the resolver directly and reports which link supplied each address, how long the query took, and whether the data was authenticated.
  5. -mDNS in the protocol line means systemd-resolved is not handling multicast DNS here; that job belongs to a separate local-discovery stack.

Try it

Run getent hosts localhost and then getent ahosts example.com. The first answer comes from the local hosts file; the second from DNS. Both are read-only.

If it goes wrong

A name returns no addresses
Check resolvectl query <name> for the exact error. NXDOMAIN means the name does not exist; SERVFAIL means a server failed; a timeout often means the resolver is unreachable.
A new DNS setting appears in the profile but not in the resolver
The connection must be reapplied and the resolver reloaded. Compare nmcli with resolvectl status.
A short name resolves in one application but not another
Search domains differ between tools. Try the fully qualified name and check resolvectl status for the domain associated with the link.
A .local name fails through DNS
That is expected: .local names are answered by multicast DNS on the local link, not by the global DNS hierarchy.

Check yourself

Why can getent and resolvectl disagree about the order of addresses?

getent follows NSS and may consult local files and caches before DNS, while resolvectl query goes straight to systemd-resolved. Different sources or cache states produce different ordering.

What does a stub resolver actually do?

It listens on a local address, accepts queries from applications, forwards them to configured upstream servers, and caches the answers. The applications need no knowledge of which upstream server is in use.

Predict what happens to a name lookup when a VPN is connected with split DNS.

Names in the VPN's routing domain go to the VPN's DNS server and other names continue to the local server. A name outside the domain is not answered by the VPN even though the tunnel is up.

How it works

A recursive resolver follows delegations from the root through top-level domains to an authoritative server, caching each answer for its time to live. An iterative client does that walk itself; most applications ask a recursive resolver instead. systemd-resolved exposes the result through a local stub and through the Resolve D-Bus API, while /etc/nsswitch.conf decides whether an application consults files, mDNS or DNS first.

Search domains append a suffix to a short name. A link marked +DefaultRoute is eligible for all queries; a link with a routing domain is used only for names inside that domain, which is how split DNS keeps a corporate name inside the tunnel. DNSSEC validation, when enabled, verifies signatures from the root down; it proves integrity and origin, not confidentiality. DNS over TLS and DNS over HTTPS address confidentiality by encrypting the query.

Advanced usage

$ getent ahostsv4 example.com
104.20.23.154   STREAM example.com
172.66.147.243  STREAM
$ resolvectl query --legend=no --cache=no example.com
example.com: 104.20.23.154 -- link: enp1s0
             172.66.147.243 -- link: enp1s0
             2606:4700:10::6814:179a -- link: enp1s0
             2606:4700:10::ac42:93f3 -- link: enp1s0

Reading the cache-free form distinguishes a fresh answer from one the resolver remembered. Compare it with a normal query to see the cache in action.

Edge cases

  • /etc/hosts is consulted first on many systems, so an old entry can shadow a DNS answer that has changed.
  • A CNAME chain can return several names; the final address is what the application connects to, while the alias stays useful.
  • Resource records have a time to live. A cached answer can outlive a change made at the authoritative server until the timer expires.
  • Multiple addresses in one answer let a client try another if the first is unreachable; a single-address answer has no such fallback.
  • .local is reserved for link-local names. Sending it to a global DNS server is a common misconfiguration that produces NXDOMAIN.
  • DNS over UDP can lose a large answer; EDNS0 allows larger messages and TCP fallback handles truncation.

Check yourself

Why does split DNS need a routing domain instead of only a list of servers?

Without a domain, the system cannot tell which names belong to the tunnel and which belong to the local network. A routing domain labels the link so queries for private names go to the VPN resolver while public names stay local.
