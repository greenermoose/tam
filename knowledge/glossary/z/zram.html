Guide / Glossary A–Z / Terms beginning with Z / ZRAM (Z in UNIX means compressed)

A Linux kernel feature that creates a compressed block device in RAM, commonly used as high-speed swap space or temporary storage.

When your computer’s active memory (RAM) fills up, the system normally moves idle items out to your SSD or hard drive (“swapping”), which is much slower than RAM. ZRAM instead squeezes those idle items down inside RAM—much like vacuum-sealing winter clothes in a suitcase—so more fits in fast memory without spilling onto disk as often. In Unix tradition, the letter Z denotes compression (seen in the classic compress utility, .Z files, and gzip) in honor of computer scientist Jacob Ziv, co-inventor of the Lempel-Ziv family of compression algorithms.

On Linux, ZRAM exposes virtual block devices such as /dev/zram0 backed by dynamically allocated compressed memory pages, trading a small amount of CPU work to avoid slow disk swap I/O and reduce SSD write wear. Administrators typically choose fast algorithms like zstd or lz4, assign ZRAM a higher swap priority than disk swap so the kernel uses it first, and monitor live memory savings with zramctl. Unlike zswap—which acts as a compressed RAM cache sitting in front of a disk swap file—ZRAM is a standalone block device that needs no backing disk.

Why does swapping to ZRAM usually feel much faster than swapping to an SSD, even though compression uses CPU time?

Compressing and decompressing a 4 KiB page in RAM takes only a few microseconds on modern CPUs, whereas SSD or hard-drive swap I/O takes tens of microseconds to milliseconds and wears out flash cells with repeated writes.

ZRAM stores variable-length compressed pages using the kernel’s zsmalloc allocator, which packs compressed objects across non-contiguous physical pages (zspages) to limit internal fragmentation. Per-device sysfs controls under /sys/block/zramN/ govern comp_algorithm (for example lzo-rle, lz4, or zstd, plus multi-stream recompression in newer kernels), logical disksize, and physical mem_limit. An optional backing_dev enables writeback of idle or incompressible pages so uncompressible data cannot pin RAM indefinitely. Key tuning and failure modes include incompressible workloads (encrypted buffers, compressed media) driving the effective ratio near 1:1 plus allocator overhead, and setting vm.page-cluster=0 because random 4 KiB reads in RAM incur no seek or readahead benefit.
