ZFS (Zettabyte File System)

A filesystem and storage-pool manager that protects data with end-to-end checksums, never overwrites live blocks in place, and supports instant snapshots.

ZFS is a way of organizing files across one or more drives with built-in protection against data corruption. Instead of erasing old data and writing new data in the same spot—which can leave files half-written if the power goes out—ZFS writes the updated version to a blank area first and switches over only when it is safely saved. It also stamps a mathematical fingerprint onto every piece of data so it can spot silent drive errors and, when you use mirrored or redundant drives, repair them automatically.

Originating on Solaris and now developed as OpenZFS (on BSD, illumos, and Linux), ZFS combines volume management (zpool) and the filesystem (zfs datasets) into a single layer, unlike the traditional Linux stack of mdadm, LVM, and ext4. It shares copy-on-write concepts and snapshot workflows with in-tree Btrfs, though OpenZFS is CDDL-licensed and therefore shipped as an out-of-tree kernel module on Linux—meaning kernel updates must stay matched with compatible ZFS packages.

Why does ZFS recover quickly after a sudden power loss without needing a full-disk fsck scan?

Because ZFS uses copy-on-write transactions, new data and metadata are written to free space before a single atomic pointer switch commits the update. Live blocks are never overwritten in place, so the on-disk structure remains consistent even after an unexpected shutdown.

ZFS maintains a Merkle tree of block checksums (such as Fletcher4, SHA-256, or BLAKE3) stored in each parent pointer rather than alongside the data block, catching silent bit rot as well as phantom or misdirected writes. Copy-on-write updates batch into Transaction Groups (TXGs) committed atomically via the uberblock ring, while synchronous writes are logged to the ZFS Intent Log (ZIL, optionally offloaded to a dedicated SLOG device) for low-latency fsync() durability. Reads and writes use the Adaptive Replacement Cache (ARC) in kernel memory—bypassing the Linux page cache, which affects memory-pressure accounting and O_DIRECT semantics—with optional SSD-backed L2ARC. RAID-Z (1/2/3 parity) eliminates the RAID-5/6 write hole through variable-width stripes tied to TXGs, but imposes trade-offs: ashift (sector alignment, e.g., ashift=12 for 4 KiB sectors) is immutable per vdev at creation, small random IOPS scale with vdev count rather than disk count, and pool fragmentation degrades allocation speed once utilization exceeds roughly 80%.
