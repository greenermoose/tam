X.509

The standard digital certificate format used by TLS, HTTPS, and public-key infrastructure to bind an identity to a public key.

Think of an X.509 certificate as a website’s digital passport. When your browser connects to a bank or store, the server shows this passport so your computer can check who issued it, whether it has expired, and which public key belongs to that site—preventing an impostor from pretending to be the real service.

On Linux, X.509 certificates usually appear as Base64-encoded PEM files (.pem, .crt) under /etc/ssl/certs/ or binary DER files (.der). Modern TLS clients match the server’s hostname against the Subject Alternative Name (SAN) extension rather than the older Common Name (CN) field, and you can inspect a certificate’s fields directly with openssl x509 -in cert.pem -noout -text.

Why do modern browsers reject a certificate that only lists the hostname in the Common Name (CN) field?

Standards deprecated CN matching because it was ambiguous and poorly typed. Clients require the Subject Alternative Name (SAN) extension, which explicitly tags DNS names and IP addresses so a hostname cannot be confused with a human name or organizational label.

Specified in ITU-T X.509 and profiled for the Internet by RFC 5280, a v3 certificate is an ASN.1 DER sequence containing tbsCertificate (version, serialNumber, signature algorithm, issuer, validity window, subject, subjectPublicKeyInfo, and v3 extensions), signatureAlgorithm, and signatureValue. Path validation checks cryptographic signatures up to a trusted root, validity bounds, BasicConstraints (CA:TRUE and pathLenConstraint), KeyUsage/ExtendedKeyUsage, and revocation status (CRL or OCSP stapling). Common failure modes include clock skew breaking validity checks, missing intermediate certificates in the TLS chain, and non-critical or misconfigured NameConstraints.
