Guide / Glossary A–Z / Terms beginning with X / XTS (XEX-based Tweaked-Codebook with Ciphertext Stealing)

A block-cipher encryption mode designed specifically for sector-level disk and storage encryption.

Unlike a message sent from start to finish, a hard drive or SSD needs to read and update any small chunk of data in any order at any time. XTS is a way of scrambling each disk sector using its location on the drive as an extra ingredient, so two identical files saved in different places still look completely different on disk—without making the encrypted data any bigger than the drive’s sectors.

On Linux, cryptsetup/LUKS2 defaults to aes-xts-plain64, where the sector number acts as the per-sector tweak. Notice that an XTS key size like 512 bits (-s 512) actually splits into two 256-bit AES keys: one for encrypting the data and one for computing the sector tweak. Unlike authenticated modes such as AES-GCM, XTS does not store an integrity tag, because disk sectors have no spare room for extra metadata.

Why does cryptsetup use a 512-bit key when configuring aes-xts-plain64 for AES-256 encryption?

XTS splits the supplied key into two equal halves: one 256-bit key encrypts the sector data blocks, and the second 256-bit key encrypts the sector number (tweak) before mixing it into each block. Passing 256 bits would only give AES-128 strength.

Standardized in IEEE 1619 (and NIST SP 800-38E), XTS-AES derives per-block masks via T = E(K2, i) ⊗ α^j in GF(2^128) (where i is the 128-bit tweak/sector index, j is the 16-byte block offset within the sector, and α is the primitive element x), computing C = E(K1, P ⊕ T) ⊕ T with ciphertext stealing for non-multiple-of-16-byte units. Because XTS provides no authentication tag, it is vulnerable to 16-byte block-level ciphertext manipulation/malleability and cannot detect offline tampering without a separate integrity layer such as dm-integrity or dm-verity.
