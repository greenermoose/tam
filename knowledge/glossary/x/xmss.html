Guide / Glossary A–Z / Terms beginning with X / XMSS (eXtended Merkle Signature Scheme)

A stateful, hash-based post-quantum digital signature scheme standardized in RFC 8391.

Future quantum computers could break today’s common digital signatures, which rely on hard math problems like factoring large numbers. XMSS instead builds signatures purely out of one-way cryptographic scrambling (hashes). The catch is that each signing key comes with a fixed book of single-use tickets—once you tear out a ticket to sign a file, you must remember never to reuse that same ticket again.

Because XMSS requires tracking a monotonically advancing key index across reboots and backups, it is poorly suited to general-purpose TLS servers or copied VM images. Instead, it shines in controlled environments such as hardware-backed firmware signing (standardized alongside LMS in NIST SP 800-208), where a single signing device can enforce state updates atomically before releasing a signature.

Why is restoring an XMSS signing key from a backup or cloning a VM dangerous?

Restoring an older state causes the signer to reuse a previously spent leaf index with a different message. Because XMSS’s underlying one-time signatures reveal parts of the secret key when used twice, even a single index reuse can let an attacker forge future signatures.

RFC 8391 defines XMSS (single-tree) and XMSSMT (multi-tree) as Merkle trees whose leaves are WOTS+ (Winternitz One-Time Signature Plus) keypairs, hardened against multi-target attacks with randomized hashing and per-node bitmasks/ADRS domain separation. Security reduces to second-preimage resistance and PRF assumptions of the underlying hash (SHA-256, SHA-512, or SHAKE). Practical trade-offs include large signatures (typically ~2.5 KB for height 10–20 trees) and stateful index management (often mitigated by reserving index blocks in non-volatile memory before signing), contrasting with stateless hash-based schemes like SLH-DSA (SPHINCS+).
