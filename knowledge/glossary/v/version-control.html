Version control

Version control is software that records changes to files over time so you can inspect history, compare versions, undo mistakes, and collaborate safely.

Imagine writing a report and saving files named report_v1, report_final, and report_final_REAL—and then accidentally deleting a paragraph you needed. Version control replaces that messy folder of copies with a smart time machine. Every time you save a milestone, it records who changed what and why, lets you jump back to any earlier state, and helps two people edit the same project without silently overwriting each other’s work.

Modern systems like Git are distributed version control systems (DVCS): every clone has the full commit history locally, so you can inspect logs (git log), compare changes (git diff), and work on isolated branches (git switch -c) without needing network access. Older centralized systems like Subversion (SVN) keep history on one central server. Version control shines for plain-text source code, configuration files, and documentation; large binary files (videos, disk images) bloat history unless handled by extensions like Git LFS.

Why do teams create a separate branch in Git instead of committing unfinished experiments directly to main?

A branch isolates in-progress changes from the shared stable line of work, allowing developers to test, review, and discard or merge changes without breaking builds for everyone else.

Distributed VCSs such as Git model history as a content-addressed Directed Acyclic Graph (DAG) of immutable tree/blob/commit objects keyed by cryptographic hashes (SHA-1/SHA-256), with mutable refs (branches, tags) pointing to commit nodes—whereas delta-based systems store forward or reverse diffs. Three-way merges compute a common ancestor (merge base) via lowest common ancestor (LCA) in the DAG (using recursive/ort strategies for criss-cross merges) and flag overlapping hunks as conflicts; rebasing replays commits onto a new base, rewriting commit hashes and breaking shared history if force-pushed carelessly. Failure modes include history bloat from committed secrets or binaries, shallow/partial clone edge cases, and non-atomic working-tree vs. index state during interrupted operations.
