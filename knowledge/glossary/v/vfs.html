Guide / Glossary A–Z / Terms beginning with V / VFS (Virtual File System)

The VFS (Virtual File System) is the Linux kernel layer that gives every filesystem—from local drives like ext4 and Btrfs to virtual trees like /proc—a single, uniform interface.

Your computer might read files from a Linux drive, a Windows-formatted USB stick, a network share, and even virtual system folders that only exist in memory. Without the VFS, every program would need separate code to understand each of those formats. Instead, the VFS acts like a universal translator: apps just ask the kernel to “open” or “read” a file path, and the VFS quietly routes that request to the right driver underneath.

Because of the VFS, standard system calls like open(), read(), write(), and stat()—and everyday tools like ls, cp, and cat—work identically whether the target is on ext4, Btrfs, XFS, FAT32, NFS, /proc, or a userspace FUSE mount. The VFS also maintains the kernel’s dentry cache (remembering path-to-inode lookups) and inode cache, which makes repeated file accesses fast. Notice that while the VFS provides a common API, individual filesystems still differ in capabilities: FAT32 lacks POSIX permissions and symlinks, so VFS mount options synthesize defaults.

Why can cat read both a text file on an SSD and /proc/cpuinfo in memory using the exact same system calls?

Both paths go through the kernel’s VFS layer, which dispatches open() and read() to the backing filesystem’s operations—whether that is an on-disk driver like ext4 or the virtual procfs driver.

The Linux VFS implements an object-oriented C abstraction built around four core structures and their operation tables: struct super_block (super_operations for a mounted filesystem instance), struct inode (inode_operations for metadata, permissions, and lookup), struct dentry (dentry_operations linking names to inodes in the RCU-walkable dcache), and struct file (file_operations for open file descriptions, offsets, and read_iter/write_iter/mmap). Path resolution uses lockless RCU-walk in the fast path, falling back to ref-walk on cache misses, mount-point crossings, or permission changes. Edge cases include negative dentries consuming slab memory under workloads probing nonexistent paths, cross-filesystem rename() returning EXDEV, and O_DIRECT or fsync() semantics varying subtly across concrete filesystems and FUSE.
