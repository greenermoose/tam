MAC2 (WireGuard DoS-mitigation cookie)

MAC2 is a field in WireGuard VPN handshake packets that carries a rate-limiting cookie when a server is under heavy packet-flood load.

Starting an encrypted VPN tunnel takes heavy math, which attackers can abuse by flooding a server with fake connection requests until the server slows to a crawl. WireGuard defends against this with a quick pass called mac2: when the server gets busy, it hands back a small coded ticket instead of doing the heavy math right away. Only a real client that actually receives and echoes that ticket in mac2 gets to proceed.

Normally, WireGuard clients send handshake initiation packets with mac2 set to all zeros, authenticated only by mac1 (which proves knowledge of the server’s static public key). When a responder’s handshake queue exceeds its load threshold, it replies with a stateless cookie-reply message encrypted for the client; the client decrypts the cookie and resends its handshake with mac2 populated. This blocks spoofed-IP amplification and CPU-exhaustion floods without the server having to track per-IP state.

Why does WireGuard only require mac2 when the server is under load instead of on every handshake?

Requiring a cookie-reply round trip on every connection would add an extra network round trip to normal handshakes. Keeping mac2 zeroed during normal traffic preserves a fast single-round-trip handshake while still letting the responder shed spoofed or flood traffic instantly when load spikes.

In WireGuard’s Noise_IKpsk2 handshake, the responder computes a rotating 2-minute secret key R_m and issues a 16-byte cookie τ = MAC(R_m, sender_IP || sender_port), delivered inside a Type 3 Cookie Reply packet encrypted with XChaCha20-Poly1305 using H(LABEL_COOKIE || S_pub^r) as the key and mac1 as associated data (binding the cookie to the initiation). The client’s subsequent Type 1/2 packet sets mac2 = MAC(τ, packet_up_to_mac2) using keyed BLAKE2s, verified in constant time before any Curve25519 scalar multiplication is performed.
