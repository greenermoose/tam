Guide / Glossary A–Z / Terms beginning with M / Merge

A merge combines two separate lines of development in version control—such as a feature branch and a main branch—into one unified history.

Imagine two people copy the same recipe, and one adjusts the spices while the other changes the baking time. Merging is the step where you combine both sets of edits into one updated recipe, deciding what to keep if both people changed the same line.

In git, running git merge feature from main either fast-forwards (if main has no new commits since the split, simply moving the pointer) or creates a two-parent merge commit (if both branches moved forward). When both branches edit the same lines differently, Git pauses and writes conflict markers (<<<<<<<, =======, >>>>>>>) for you to resolve before committing.

When does git merge create a merge commit instead of fast-forwarding?

It creates a merge commit when the branches have diverged—meaning the receiving branch gained new commits after the feature branch split off. Because a simple pointer move cannot represent both histories, Git records a new commit with two parents.

Git’s default ort (“Ostensibly Recursive’s Twin”) strategy finds the lowest common ancestor (merge base) in the commit DAG and performs a three-way tree merge across base, ours, and theirs. In criss-cross merge topologies with multiple merge bases, ort recursively merges the bases into a virtual base. Unlike git rebase, which replays diffs onto a new base and rewrites commit hashes, merging preserves original commit IDs and branch topology, though non-linear history can require git bisect --first-parent when isolating regressions.
