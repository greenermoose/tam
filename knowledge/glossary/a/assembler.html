Guide / Glossary A–Z / Terms beginning with A / Assembler

A program that translates human-readable assembly language into binary machine code that a CPU can execute.

A processor only understands patterns of ones and zeros, which are nearly impossible for humans to write directly. An assembler acts like a direct translator: you write short, readable instruction names like ADD or MOV, and the assembler turns each line into the exact binary numbers the processor expects.

On Linux, as (the GNU Assembler, often invoked automatically by gcc or clang) and nasm convert .s or .asm source files into relocatable object files (.o), not finished executables. Unlike a compiler for C or Rust, an assembler generally maps each mnemonic one-to-one to a CPU instruction, while also handling labels, macros, and section directives (.text, .data) before the linker (ld) stitches object files together.

Why is an assembler’s output usually passed to a linker before you can run it?

An assembler produces an object file with unresolved external symbols and relative addresses; the linker resolves references across object files and libraries and assigns final program layout.

An assembler parses ISA mnemonics, addressing modes, and assembler directives into ELF/COFF/Mach-O object files containing machine-code sections (.text, .rodata, .data), symbol tables (.symtab), and relocation entries (.rela.*) for addresses unknown at assembly time. Modern two-pass or relaxation-capable assemblers (such as GNU as or LLVM MC) perform branch-displacement relaxation (choosing short vs. near encodings as section offsets stabilize) and emit DWARF debug/CFI (.eh_frame) metadata alongside instructions.
