ABAC (Attribute-Based Access Control)

An access-control model that decides whether to allow an action by evaluating attributes of the user, the resource, the requested operation, and the surrounding environment.

Instead of relying only on a fixed job title or a static list of names, ABAC checks the full situation before saying yes or no. Think of a building security desk that checks not just your ID badge, but also which room you want to enter, what time of day it is, and whether you are physically at the front door. By combining those details, the system can allow access only when all the right conditions are met.

On Linux desktops and servers, Polkit rules and policy engines like Open Policy Agent (OPA) apply ABAC by inspecting attributes such as whether a session is local and active (subject.local && subject.active), which systemd unit is being restarted, or the source IP and time of an API request. Unlike RBAC (Role-Based Access Control), which groups permissions under static roles like admin or editor, ABAC avoids role explosion when permissions depend on dynamic context.

When is ABAC more practical than simple role-based access control (RBAC)?

ABAC is more practical when access depends on dynamic or fine-grained context—such as owning a specific file, being logged in at the physical console rather than over SSH, or accessing a service during maintenance hours—because encoding every combination of conditions as separate RBAC roles would be unmanageable.

Formally, ABAC evaluates a policy predicate P(S, O, A, E) over subject (S), object (O), action (A), and environment (E) attribute sets, typically split into a Policy Enforcement Point (PEP) that intercepts requests, a Policy Decision Point (PDP) that evaluates rules, and Policy Information Points (PIPs) that supply verified attributes (such as X.509 SANs, OIDC claims, or kernel peer credentials via SO_PEERCRED). Key failure modes include stale or spoofable PIP attributes, non-monotonic rule conflicts across combining algorithms (deny-overrides vs. permit-overrides), and latency or availability coupling when PDP evaluation depends on external attribute lookups.
