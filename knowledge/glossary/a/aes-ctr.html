AES-CTR (AES Counter Mode)

Stream-cipher mode that turns AES into a parallelizable keystream using an incrementing counter.

A block cipher like AES normally locks data in fixed 16-byte chunks. AES-CTR turns it into a flexible stream by encrypting a sequence of counting numbers—like stamping page numbers 1, 2, 3 and locking each number with your secret key—then blending those locked numbers with your message. Because each chunk’s mask depends only on its counter value, you can encrypt or decrypt different parts of a file at the same time without padding the end.

Part of AES variants; unlike CBC mode, CTR requires no padding and supports parallel encryption and random-access decryption at arbitrary byte offsets, which makes it fast for network streams and large files. However, CTR provides confidentiality only—an attacker can flip bits in the ciphertext to flip the exact same bits in the plaintext—so real protocols pair it with a message authentication code (as in AES-GCM).

Why does reusing the same (key, nonce) pair in AES-CTR break confidentiality completely?

CTR encrypts by XORing plaintext with a keystream derived from (key, nonce, counter). Two messages sharing the same key and nonce use the exact same keystream; XORing their ciphertexts cancels the keystream out, leaving the XOR of the two plaintexts, which attackers can often separate.

AES in Counter mode (NIST SP 800-38A) computes keystream blocks via the forward cipher AES_K(nonce || counter)—typically a 96-bit nonce and 32-bit big-endian block counter (RFC 3686, AES-GCM)—and XORs them with plaintext. Decryption uses the same forward AES_K operation rather than the inverse cipher, simplifying hardware and constant-time code. Critical failure modes: any (key, nonce) reuse or 32-bit counter wrap-around past 2^32 blocks (64 GiB) repeats keystream blocks, and XOR malleability requires an authentication tag (such as GHASH in GCM or Encrypt-then-MAC).
