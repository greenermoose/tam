Guide / Glossary A–Z / Terms beginning with A / AVX2 (Advanced Vector Extensions 2)

An x86_64 processor extension that expands 256-bit SIMD support to integer operations and adds gather instructions.

While the original AVX extension focused mostly on decimal (floating-point) numbers used in graphics and science, AVX2 brings that same 256-bit wide-lane speedup to whole-number math. That makes everyday tasks like encrypting files, compressing archives, and decoding modern video formats noticeably faster.

Introduced in 2013 (Intel Haswell, AMD Excavator), AVX2 is a core requirement of the x86-64-v3 microarchitecture level. Because pre-2013 CPUs lack AVX2, distributed packages target baseline x86_64 while local -march=native builds can enable AVX2 (often paired with FMA3 for fused multiply-add). In practice, libraries like OpenSSL, FFmpeg, and glibc use runtime CPUID dispatch (IFUNC) to select AVX2 routines only when supported.

Why do Linux distributions rarely require AVX2 for all base packages, even though most post-2013 CPUs have it?

Requiring AVX2 in the baseline ABI would break booting and running on older x86_64 hardware and low-power CPUs (such as older Atom or Celeron models) that lack AVX2, causing SIGILL crashes. Runtime dispatch lets hot libraries use AVX2 without breaking compatibility.

AVX2 promotes nearly all legacy 128-bit SSE integer instructions (packed byte/word/dword/qword arithmetic, shifts, shuffles, and comparisons) to 256-bit YMM registers under VEX encoding, and adds VGATHER* instructions for non-contiguous indexed memory loads, variable bit-shifts (VPSLLV*/VPSRLV*), and cross-lane permutes (VPERMD/VPERMQ). Note that YMM lanes remain largely split into two 128-bit halves for many shuffles, and VGATHER* does not guarantee speedups over scalar loads unless cache locality is favorable, as it still issues multiple micro-ops per element.
