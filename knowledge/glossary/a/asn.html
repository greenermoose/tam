ASN.1 (Abstract Syntax Notation One)

A standard language for describing structured data—such as cryptographic keys and digital certificates—and encoding it into bytes across different computer systems.

Different computers store numbers and text in slightly different ways, so they need a shared packing format when sending important documents like website security certificates. ASN.1 is the blueprint and packing rulebook that lets any computer read a digital certificate and know exactly which part is the owner’s name, which part is the expiration date, and which part is the cryptographic key.

When you inspect an X.509 TLS certificate or an SSH/RSA key with openssl, you are looking at data defined in ASN.1 and usually serialized in binary DER (Distinguished Encoding Rules) or Base64-wrapped PEM format. Unlike JSON, ASN.1 separates the schema (what fields exist) from the wire encoding rules (BER, DER, PER), and DER guarantees one unique byte sequence per value so digital signatures over certificates stay deterministic.

Why do X.509 certificates use DER rather than general BER encoding?

BER allows multiple valid byte representations for the same data (such as indefinite-length encodings), which would break cryptographic signature verification; DER enforces a single canonical byte representation.

Specified in ITU-T X.680 (syntax) and X.690 (BER/CER/DER), ASN.1 uses Type-Length-Value (TLV) triples where tags encode class, constructed/primitive bit, and tag number, followed by definite or indefinite length octets and payload. DER restricts BER to definite-length forms, minimal-length encodings, and sorted SET OF elements to ensure canonical serialization for hashing and signing (e.g., TBSCertificate in RFC 5280). Historically, ASN.1 parsers have been a frequent source of memory-safety and integer-overflow vulnerabilities (such as length-field mismatches and tag confusion) because of recursive nested structures and context-specific implicit/explicit tagging.
