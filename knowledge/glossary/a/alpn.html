ALPN (Application-Layer Protocol Negotiation)

Application-Layer Protocol Negotiation: a TLS extension that lets a client and server agree on which application protocol (such as h2 or http/1.1) to use during the encrypted handshake.

When your browser connects to a secure website, it first sets up an encrypted TLS tunnel before sending any webpage data. Without ALPN, the browser and server would have to finish locking the tunnel and then spend extra messages asking whether to speak newer HTTP/2 or older HTTP/1.1. ALPN tucks that quick agreement inside the very first security greeting so the connection starts without extra delay.

ALPN (RFC 7301) avoids an extra network round trip by carrying the client’s supported protocol list inside the TLS ClientHello, replacing older methods like HTTP Upgrade headers or NPN. On Linux, you can test ALPN negotiation with openssl s_client -connect example.com:443 -alpn h2,http/1.1; reverse proxies also use the negotiated ALPN token (such as h2 or acme-tls/1) to route traffic on port 443.

What problem does ALPN solve compared to negotiating HTTP/2 after the TLS handshake?

Negotiating the application protocol after the TLS handshake would add at least one extra network round trip before requests can start. Carrying the protocol list inside the handshake lets the server select the protocol immediately, saving latency.

Defined in RFC 7301, TLS extension application_layer_protocol_negotiation (0x0010) carries an ordered list of IANA-registered protocol IDs (e.g., h2, http/1.1, or h3 over QUIC) in ClientHello. In TLS 1.2, the server returns its single selected protocol in ServerHello; in TLS 1.3 (RFC 8446), the server returns it inside EncryptedExtensions, hiding the selection from passive observers (though the client’s offered list remains cleartext unless ECH is used). If no offered protocol is supported, the server aborts with a fatal no_application_protocol (120) alert.
