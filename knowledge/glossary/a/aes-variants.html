AES variants (AES-128, AES-256, AES-CTR, AES-NI, AES-XTS)

Key sizes, block modes, and hardware acceleration options for the Advanced Encryption Standard (AES).

AES is the standard modern cipher used to lock data, but you will see it with different suffixes depending on the job. Some suffixes name the key size—longer keys like 256-bit add extra margin over 128-bit—while others name the method used to handle whole files, network streams, or hard drives. AES-NI is different: it names a built-in CPU feature that makes any of these variants run much faster.

The AES family spans key lengths (AES-128, AES-256), operating modes (AES-CTR, AES-XTS), and hardware acceleration (AES-NI). In everyday Linux use, HTTPS and SSH typically pick AES-128 or AES-256 in GCM mode (which pairs CTR with authentication), whereas LUKS2 full-disk encryption defaults to AES-XTS so every disk sector keeps its exact size.

If a system uses AES-XTS-256 for LUKS disk encryption, why does cryptsetup report a 512-bit key size?

XTS mode splits its key into two equal halves: one key encrypts the data blocks and the second key encrypts the sector tweak. Getting 256-bit AES strength for the data therefore requires two 256-bit keys, totaling 512 bits.

Under FIPS 197, AES is always a 128-bit (16-byte) block cipher; AES-128, AES-192, and AES-256 select 10, 12, or 14 rounds respectively (256-bit adds ~40% round cost for higher post-quantum Grover margin and related-key resistance). Mode choice governs parallelism, padding, and integrity: AES-CTR yields a parallelizable keystream (extended to AEAD in GCM via GHASH), whereas AES-XTS implements a dual-key tweakable block cipher for fixed-geometry storage. AES-NI (and ARMv8 Crypto) implements these rounds in constant-time silicon, eliminating software T-table cache-timing side channels.
