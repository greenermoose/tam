Authorization

Deciding what an authenticated user, program, or service is allowed to read, change, or run.

Proving who you are—like showing an ID card at a building’s front desk—is authentication. Authorization is what happens next: checking which rooms your badge is allowed to unlock. Even when a system knows who you are, it still needs rules to stop you from accidentally deleting system files or reading someone else’s private documents.

Once Linux or a service knows who is making a request (for example, user alex or a process holding a signed API token), authorization checks a policy before granting access. On a Linux system, this includes traditional file permissions (rwx for owner, group, and others), POSIX ACLs, Linux capabilities, and Mandatory Access Control systems like SELinux or AppArmor.

If you log in with the right password, why might a command still fail with “Permission denied”?

Because logging in only proves your identity (authentication). The system still checks authorization rules—such as file ownership, mode bits, or access control policies—and denies the action if your account lacks permission for that specific file or operation.

In access control architecture, authorization is the Policy Decision Point (PDP) and Policy Enforcement Point (PEP) evaluating a (subject, object, operation, context) tuple against an access control model—DAC (POSIX mode bits/ACLs), MAC (SELinux TE/MLS, AppArmor), RBAC, or ABAC. Subtle failure modes include confused-deputy bugs (where a privileged service acts on behalf of an unprivileged caller without re-checking subject authority), TOCTOU races between check and use (access() followed by open()), and capability inheritance across execve() boundaries.
