ASLR (Address Space Layout Randomization)

A kernel security mitigation that randomizes where a program’s code, stack, heap, and libraries sit in virtual memory each time it starts.

Imagine a burglar trying to rob a house in the dark by memorizing where the safe is. If the homeowner rearranges the rooms every night, the burglar’s memorized map becomes useless. ASLR does the same thing for a program’s memory: by shuffling where pieces of the program live each time it runs, attackers who rely on fixed memory addresses can’t easily aim their attacks.

On Linux, ASLR is controlled by /proc/sys/kernel/randomize_va_space (0 = off, 1 = randomize stack/mmap/VDSO, 2 = also randomize the brk heap). However, ASLR alone does not move the main program’s own code unless the binary was compiled as a Position-Independent Executable (PIE), which is why modern distributions enable both PIE and ASLR together.

Why is ASLR much weaker if a binary is not compiled as a Position-Independent Executable (PIE)?

Without PIE, the main executable’s code and global data load at fixed virtual addresses, giving attackers known gadget addresses for return-oriented programming even when libraries and the stack are randomized.

On x86_64 Linux, ASLR applies kernel-chosen random offsets to mmap_base, stack top, brk heap, vDSO, and ET_DYN (PIE) ELF mappings (typically ~28–32 bits of entropy for mmap on 47-bit user virtual address spaces, tunable via vm.mmap_rnd_bits). ASLR does not prevent memory corruption itself and can be bypassed by information leaks (exposing a single pointer to defeat the slide), partial pointer overwrites, heap spraying, or brute-forcing on 32-bit architectures or fork()-based servers where child processes inherit the parent’s randomized layout.
