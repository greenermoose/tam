APIC - Advanced Programmable Interrupt Controller

The hardware interrupt controller in modern x86 PCs that routes signals from devices and timers to specific CPU cores.

When you press a key or a network packet arrives, the hardware needs to tap the processor on the shoulder—an “interrupt”—so it handles the event right away. Old PCs had a simple switchboard that only worked with one processor. The APIC is a smart switchboard built for modern multi-core computers, making sure each hardware tap goes to an available core instead of jamming a single one.

On Linux, you can inspect how the APIC distributes hardware interrupts across CPU cores by reading /proc/interrupts, which lists per-CPU interrupt counts alongside IO-APIC or PCI-MSI sources. On multi-core systems, the irqbalance daemon (or manual writes to /proc/irq/<N>/smp_affinity) uses APIC routing so network or disk interrupts do not overwhelm CPU 0 while other cores sit idle.

What problem would occur on an 8-core Linux server if all network card interrupts were routed to a single core via the APIC?

That single core could become saturated handling interrupt service routines and softirqs, causing packet drops and high latency even while the other seven cores remain mostly idle.

The x86 APIC architecture splits into per-core Local APICs (LAPIC)—handling local timers, thermal/performance interrupts, and Inter-Processor Interrupts (IPIs) used for SMP TLB shootdowns and scheduler rescheduling—and system I/O APICs, which map legacy pin-based IRQ lines to 8-bit interrupt vectors (vectors 32–255, prioritized by vector >> 4 Task Priority) with programmable destination modes. Modern PCIe devices bypass I/O APIC pins via Message Signaled Interrupts (MSI/MSI-X), writing directly to the LAPIC’s 0xFEE00000 memory-mapped address range. x2APIC replaces MMIO LAPIC registers with MSR accesses (IA32_X2APIC_*), extends APIC IDs from 8 bits to 32 bits for topologies above 255 CPUs, and avoids serializing MMIO fences on End of Interrupt (EOI).
