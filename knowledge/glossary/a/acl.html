ACL - Access Control List

A list of fine-grained access rules attached to a file, directory, or resource that specifies which users or groups are allowed or denied specific operations.

Standard file permissions only let you set rules for three broad categories: the file’s owner, one group, and everyone else. An ACL is like a detailed guest list at the door: it lets you say “alex can read and edit this folder, the backup group can only read it, and sam cannot open it at all,” without having to create new system groups for every combination.

On Linux filesystems like ext4, XFS, and Btrfs, POSIX ACLs extend traditional rwx mode bits and are managed with getfacl and setfacl (noticeable as a + after the mode string in ls -l, such as -rw-r-----+). A common pitfall is the ACL mask entry: when you run chmod on a file that has an ACL, chmod updates the ACL mask rather than just the owning group’s bits, which can unexpectedly cap the effective permissions of named users and groups.

After setting a POSIX ACL on a file, you see a + in ls -l output and run chmod 640 file. What does that chmod command actually change?

On a file with extended POSIX ACLs, the group portion of chmod modifies the ACL mask entry rather than just the owning group, which caps the maximum effective permissions for all named users and named groups in the ACL.

POSIX.1e draft ACLs are stored in filesystem extended attributes (system.posix_acl_access and system.posix_acl_default for inherited directory defaults) as ordered entries (ACL_USER_OBJ, ACL_USER, ACL_GROUP_OBJ, ACL_GROUP, ACL_MASK, ACL_OTHER). Evaluation matches the most specific entry (owner, then matching named user, then union of matching group/named-group entries masked by ACL_MASK, then other) and stops without falling through. By contrast, NFSv4 and ZFS ACLs use ordered ALLOW/DENY ACEs with richer inheritance flags (file_inherit, dir_inherit) and can conflict with POSIX mask semantics when translated across protocols.
