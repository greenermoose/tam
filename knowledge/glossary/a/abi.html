Guide / Glossary A–Z / Terms beginning with A / ABI - Application Binary Interface

The low-level binary contract that defines how compiled machine code represents data, calls functions, and interacts with libraries or the operating system kernel.

While a human-readable programming interface (API) describes what functions exist in source code, an ABI is the hidden rulebook that compiled programs follow at the machine level. If two pieces of compiled software are like puzzle pieces, the ABI ensures their tabs and slots match—so a program compiled today can safely call a shared library compiled last year without crashing or misreading data.

On Linux, the ABI governs details such as which CPU registers hold function arguments (for example, the System V AMD64 ABI passes the first six integer arguments in rdi, rsi, rdx, rcx, r8, r9), how structs are padded, and how C++ symbol names are mangled. An API can stay identical in source code while an ABI breaks—for instance, adding a field to a public struct in a shared .so library changes its size and offsets, causing existing binaries linked against the old library to corrupt memory unless they are recompiled or the library bumps its SONAME.

If a shared library keeps the exact same function names and parameters in its header file, can an update still break its ABI?

Yes. Changes such as reordering or adding fields to a struct, changing an enum’s underlying size, or switching C++ standard library implementations alter memory layout or symbol mangling at the binary level, breaking already-compiled callers even though their source code still compiles cleanly.

An ABI spans processor-specific calling conventions (register preservation, red zone, stack alignment, return-value passing), object file and dynamic-linking formats (ELF sections, GOT/PLT, symbol versioning via .gnu.version), data-model widths (LP64 vs. LLP64), C++ name mangling and vtable layout (Itanium C++ ABI), and the userspace–kernel boundary (syscall numbers, struct layouts, and signal frames). Because the Linux kernel guarantees a stable userspace syscall ABI while explicitly refusing a stable internal kernel module ABI, out-of-tree modules must be rebuilt against exact kernel headers and CONFIG_* options, whereas ELF shared libraries preserve backward compatibility across minor releases using symbol versioning (such as @@GLIBC_2.34).
