Guide / Glossary A–Z / Terms beginning with W / WASI (WebAssembly System Interface)

WASI (WebAssembly System Interface) is a capability-based system interface that lets sandboxed WebAssembly modules interact safely with files, clocks, and networks outside a web browser.

A WebAssembly program normally runs inside a locked box with no access to your computer. WASI is the set of controlled slots you can open in that box—for example, letting a program read one specific folder you choose without letting it touch any of your other files.

Unlike a typical Linux program, which inherits all permissions of the user running it (so anything alex can read, the program can read unless confined), WASI denies system access by default. A WASI runtime such as Wasmtime grants access only to explicit capabilities passed at launch, like a preopened directory, rather than exposing the whole filesystem.

If you run a WASI module without granting any directory capabilities, can it still read /etc/passwd?

No. WASI uses capability-based security with no ambient authority, so the module has no path-lookup capability for /etc unless the host explicitly hands it a handle to that directory.

Standardized under the Bytecode Alliance, WASI defines a portable syscall ABI for WebAssembly runtimes across two major generations: Preview 1 (wasi_snapshot_preview1), a flat C-like ABI of POSIX-inspired calls (fd_read, path_open) gated by preopened file descriptors and rights bitmasks, and Preview 2, built on the WebAssembly Component Model and WIT (WebAssembly Interface Types) with composable, strongly typed interfaces (wasi:filesystem, wasi:io, wasi:clocks, wasi:http). Capabilities can be attenuated across components without ambient global state, while runtimes bound CPU and memory via linear-memory limits and fuel or epoch-based interruption.
