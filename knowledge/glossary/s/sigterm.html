Guide / Glossary A–Z / Terms beginning with S / SIGTERM (Terminate signal)

SIGTERM (signal 15) is the default, polite termination signal sent by commands like kill to ask a process to shut down.

Think of SIGTERM as asking someone to wrap up their work and leave before locking the building. Unlike a forced shutdown, it gives a program a chance to save open files, close connections, and exit neatly.

Part of Unix signals, SIGTERM (15) is the default signal sent by kill <pid> and by service managers like systemd when stopping a service. Because programs can catch or ignore SIGTERM, a slow or wedged process might take several seconds to exit—or ignore it completely—which is why managers wait for a timeout before escalating to SIGKILL.

Why should you run kill <pid> before reaching for kill -9 <pid>?

kill <pid> sends SIGTERM, allowing the program to flush caches, remove lock files, and close database connections cleanly; kill -9 (SIGKILL) skips all cleanup and risks data corruption.

POSIX signal 15 (SIGTERM), the default signal for kill(1) and systemd.service shutdowns (KillSignal=SIGTERM, escalating to SIGKILL after TimeoutStopSec). Well-behaved daemons catch SIGTERM by setting an atomic flag (sig_atomic_t) or draining a self-pipe or signalfd(2) in their event loop rather than performing non-async-signal-safe cleanup directly inside the handler. Note that PID 1 (init) ignores uncaught termination signals—including SIGTERM—by kernel rule, which is why minimal containers running an app as PID 1 often ignore docker stop unless an init reaper or explicit handler is present.
