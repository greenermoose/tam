Guide / Glossary A–Z / Terms beginning with S / Sandbox

An isolated execution environment that restricts what files, network connections, and system resources a program can access.

A sandbox is like a fenced play area for a program: it can run and do its job inside the fence, but it cannot wander out to read your private documents, change system settings, or talk to the internet unless you specifically allow it.

On Linux, tools like Flatpak, Bubblewrap (bwrap), and web browsers use sandboxes so a bug or malicious file inside one app cannot compromise the rest of your account. Unlike a full virtual machine, a sandbox shares the host Linux kernel and only hides or restricts specific folders, devices, and network access—making it much faster and lighter to start.

If a sandboxed application still runs on the same Linux kernel as the host, how does it stay isolated?

The kernel enforces boundaries per process using features like namespaces (giving the app its own private view of files and processes) and system-call filters (blocking dangerous kernel requests), so the app cannot see or touch host resources outside its allowed scope.

Linux sandboxes compose multiple kernel confinement primitives: mount, PID, network, user, and IPC namespaces isolate resource visibility; seccomp-bpf filters syscalls against an allowlist or denylist at the kernel boundary; Linux capabilities are dropped (PR_CAPBSET_DROP) alongside PR_SET_NO_NEW_PRIVS to prevent privilege escalation via setuid binaries; and LSMs (AppArmor, SELinux) or Landlock enforce path and ABI-level access rules. Trade-offs include syscall-filter maintenance overhead across libc updates, IPC portal latency (e.g., xdg-desktop-portal), and shared-kernel attack surface compared to hardware-virtualized VMs.
