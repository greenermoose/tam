Sysfs (system filesystem)

Sysfs (system filesystem) is a virtual Linux filesystem mounted at /sys that exposes hardware devices, kernel drivers, and tunable attributes as files and directories.

Instead of forcing you to use special hardware tools just to check a laptop battery’s charge or change screen brightness, Linux turns those hardware details into ordinary folders and tiny text files under /sys. Reading one of those files asks the kernel for a live status number, and writing to a writable one sends a setting straight to the device driver—nothing is actually stored on your hard drive.

Mounted at /sys, sysfs complements /proc (which focuses on processes and general kernel stats) and /dev (which exposes raw device nodes for I/O). Tools like udev, lsblk, and power-management daemons read /sys/class, /sys/block, and /sys/devices to discover hardware topology and set attributes such as /sys/class/backlight/*/brightness or /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor. Values written to /sys take effect immediately in RAM and disappear on reboot unless a daemon or udev rule reapplies them.

Why do changes you echo into a file under /sys vanish after a reboot?

sysfs is an in-memory virtual filesystem generated dynamically by the Linux kernel from live device and driver state. Writing to an attribute calls a driver’s store handler in memory rather than saving a configuration file to disk.

Backed by kernfs (decoupled from sysfs in Linux 3.14 to separate VFS dentries and inodes from hotplug lifetimes), sysfs maps kernel kobject hierarchies to directories, kobj_attribute and device_attribute structs to regular files (conventionally holding one PAGE_SIZE-bounded scalar value via show() and store() callbacks), and sysfs_create_link to symlinks encoding bus, class, and driver relationships. Because directories are created and removed dynamically with device_add() and device_del(), udev pairs uevent netlink messages with sysfs uevent files to match rules without races; holding an open file descriptor across device removal remains safe via kernfs_drain active-reference draining, returning -ENODEV rather than a use-after-free.
