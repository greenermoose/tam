Signal

A signal is a short software notification sent to a running program to tell it about an event—such as a user pressing Ctrl+C, a broken pipe, or a request to shut down.

Think of a signal like a tap on a program’s shoulder or a fire alarm in a building. Instead of sending a long message, the operating system sends a simple named alert—like “stop,” “pause,” or “wake up”—and the program either reacts in its own way or follows the system’s default rule.

Every signal has a number, a name (such as SIGTERM or SIGINT), and a default disposition (terminate, ignore, core dump, or stop). Most signals can be caught with a handler, blocked temporarily, or ignored—except SIGKILL and SIGSTOP. Because sending a catchable signal only schedules delivery, kill returning success does not mean the target has finished exiting.

If kill -TERM 1234 succeeds with exit code 0, why might process 1234 still be running a moment later?

kill only queues the signal in the kernel; the process might be catching SIGTERM to flush data, blocking it temporarily, or waiting to be scheduled.

Asynchronous (or hardware-synchronous, such as SIGSEGV and SIGFPE) notifications governed by POSIX delivery, disposition, and masking rules (see signal(7)). Standard signals (1–31) are not queued: multiple pending instances of the same signal coalesce into one bit in the pending mask, whereas POSIX real-time signals (SIGRTMIN–SIGRTMAX) queue with an optional sigval payload. Signal handlers execute on the interrupted thread’s stack (or an alternate stack via sigaltstack) and must only call async-signal-safe functions (signal-safety(7)) to avoid deadlocks on non-reentrant locks like malloc.
