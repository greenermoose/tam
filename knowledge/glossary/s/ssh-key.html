SSH key

A cryptographic key pair used to prove your identity or a server’s identity over SSH without relying on typed passwords.

Think of a matching padlock and key: you can hand copies of your open padlock (the public key) to any server you want to visit, while keeping the one key that opens it (the private key) locked on your own computer. When you connect, the server checks that your computer holds the matching private key, which is both safer and faster than typing a password every time.

On Linux, ssh-keygen -t ed25519 creates a private key (such as ~/.ssh/id_ed25519, which must stay readable only by you with chmod 600) and a public key (id_ed25519.pub) that you append to ~/.ssh/authorized_keys on remote servers. Using ssh-agent lets you unlock a passphrase-protected private key once per session rather than retyping the passphrase on every connection.

Why does ssh refuse to use a private key file if its permissions are 0644?

Permissions of 0644 allow other local users on the system to read your private key. OpenSSH enforces strict permissions (such as 0600) so a misconfigured file cannot silently leak your authentication secret.

SSH public-key authentication (publickey method in RFC 4252) verifies possession of the private key by signing a session-specific payload that includes the session identifier H from key exchange, preventing replay attacks. Modern deployments favor ssh-ed25519 (RFC 8709, compact 256-bit keys with constant-time signing) or FIDO2 hardware-backed sk-ssh-ed25519@openssh.com keys over legacy ssh-rsa (SHA-1 ssh-rsa signatures are disabled by default in modern OpenSSH in favor of rsa-sha2-256/512). Keys can also be wrapped into OpenSSH certificates (ssh-keygen -s) to replace static authorized_keys distribution.
