Guide / Glossary A–Z / Terms beginning with S / Side-channel attack

A side-channel attack steals secret information by observing indirect physical or system behavior—such as timing, power draw, or cache activity—rather than breaking the underlying mathematics.

Imagine someone trying to open a combination lock without knowing the code. Instead of trying every number or breaking the lock, they press the shackle and listen for a faint click that tells them when each dial lands on the right digit. In computing, a side-channel attack does the same thing: it watches clues like how long a password check takes or how much electricity a chip uses to figure out secrets that the software was supposed to keep hidden.

A classic example is a timing attack: if a server compares a secret API token one character at a time and stops immediately on the first mismatch, valid prefixes take slightly longer to reject. By measuring response times across many requests, an attacker can guess the token byte by byte. That is why cryptographic and authentication code uses constant-time comparisons (such as hmac.compare_digest in Python or CRYPTO_memcmp in OpenSSL) that always take the same time regardless of where a mismatch occurs.

Why does replacing == with a constant-time comparison function protect an API token check?

Standard string equality returns early at the first differing byte, leaking how many leading bytes matched via response time; a constant-time comparison checks every byte so execution time reveals nothing about the secret.

Side-channel attacks exploit correlations between secret-dependent control flow or memory access and observable physical/microarchitectural channels outside the formal cryptographic model: remote/local timing, shared CPU caches (Flush+Reload, Prime+Probe), transient speculative execution (Spectre/Meltdown), branch predictors, power consumption (DPA/CPA), or EM/acoustic emanations. Mitigations require eliminating secret-dependent branches and table lookups (constant-time bit-sliced code, avoiding S-box cache indexing), compiler barriers against dead-store/branch optimization, hardware masking/blinding (e.g., RSA base blinding), and OS/microcode isolation such as KPTI and microarchitectural buffer clearing.
