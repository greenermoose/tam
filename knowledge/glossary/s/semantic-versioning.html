Guide / Glossary A–Z / Terms beginning with S / Semantic versioning

Semantic versioning (SemVer) is a three-part version-numbering standard (MAJOR.MINOR.PATCH) that communicates whether a software update breaks compatibility, adds features, or only fixes bugs.

Software version numbers like 2.4.1 are not random. Under semantic versioning, the three numbers tell you how big the change is: bumping the last number (2.4.2) means small bug fixes that should not break anything; bumping the middle number (2.5.0) means new features that still work with your old setup; and bumping the first number (3.0.0) warns you that major changes might break compatibility with older files or plugins.

Package managers (such as npm, Cargo, and Python/PEP 440 ecosystems) rely on SemVer’s MAJOR.MINOR.PATCH contract to resolve dependency ranges like ^1.2.0 (allow minor and patch updates below 2.0.0) or ~1.2.0 (allow patch updates below 1.3.0). Note two common practical caveats: versions starting with 0.y.z signal unstable initial development where any bump may break compatibility, and SemVer only governs a project’s documented public API—not internal behavior or transitive dependencies.

In SemVer, if a library fixes a bug by changing a function’s return type in an incompatible way, which version segment must increase?

MAJOR must increase. Even though the intent was a bug fix, changing the public API in a backwards-incompatible way is a breaking change under SemVer rules.

The SemVer 2.0.0 specification defines a strict grammar and total ordering: MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]. Pre-release identifiers (for example, 1.0.0-alpha.1) have lower precedence than the associated normal version (1.0.0) and are compared dot-separated (numeric identifiers numerically, others lexically in ASCII), whereas +build metadata MUST be ignored when determining version precedence. In dependency solvers, range operators (Cargo’s caret ^0.2.3 treating the leftmost nonzero digit as the breaking boundary, versus strict SemVer) can diverge from upstream intent, and Hyrum’s Law creates an ongoing tension: changes that satisfy a formal API signature can still break downstream consumers relying on observable implementation details.
