Socket

A software endpoint that programs use to send and receive data over a network or between processes on the same machine.

Think of a socket like an electrical wall outlet or a telephone jack: it is the plug-in point where a program connects to the outside world (or to another program) to pass messages back and forth. Your web browser opens a socket to talk to a website, and a chat app opens a socket to receive new messages.

On Linux, a socket is represented by a file descriptor (just like an open file), created with socket(domain, type, protocol)—commonly AF_INET/AF_INET6 for IP networks or AF_UNIX for fast local IPC, and SOCK_STREAM (TCP) or SOCK_DGRAM (UDP). You can inspect active sockets on a system with ss -tulnp (or lsof -i), and you will often see Unix domain sockets as files like /run/dbus/system_bus_socket.

Why do local Linux services like D-Bus or PostgreSQL often use AF_UNIX sockets instead of connecting to 127.0.0.1?

AF_UNIX sockets stay entirely inside the kernel without TCP/IP framing, checksums, or routing overhead, giving lower latency and higher throughput, and they allow filesystem permissions plus passing file descriptors (SCM_RIGHTS) between processes.

In the POSIX and Linux kernel (net/socket.c), a struct socket pairs a VFS file descriptor with a struct sock carrying protocol-specific state machines (such as TCP_ESTABLISHED or TIME_WAIT), sk_buff send/receive queues (SO_SNDBUF/SO_RCVBUF bounded by rmem_max/wmem_max), and epoll waitqueues. Edge cases include EADDRINUSE during TIME_WAIT (mitigated with SO_REUSEADDR), half-open connections requiring keepalives, and SYN backlog exhaustion (SOMAXCONN and tcp_max_syn_backlog).
