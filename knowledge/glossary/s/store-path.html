Store path

A store path is the unique, read-only location where Nix stores the output of a single build.

Imagine a warehouse where every box gets a one-of-a-kind barcode printed from its exact recipe and ingredients. You never open a box to change what is inside; if you want a slightly different version, you pack a brand-new box with a new barcode. A Nix store path is like that barcoded shelf location in /nix/store: it holds one finished program or file, never changes once built, and lets two different versions sit side by side without overwriting each other.

A store path looks like /nix/store/<hash>-<name>, where the hash summarizes all build inputs (source code, compiler, flags, and dependencies) and the name is a human-readable label. Because the path is marked read-only after the build finishes and the hash changes whenever any input changes, different versions of the same package can coexist safely. Tools and environments simply point to the store paths they need via symlinks rather than modifying files in place.

Why can two builds of the same program version end up at different paths in /nix/store?

Because the hash in the store path reflects the full dependency graph and build instructions, not just the program’s version number. If a compiler, a dependent library, or a build flag changed, the inputs differ, so Nix produces a new hash and a separate store path.

In Nix, a store path is a top-level entry under NIX_STORE_DIR (default /nix/store) named <32-char nixbase32 digest>-<name>. For input-addressed derivations, the digest is a truncated SHA-256 hash of the derivation’s inputs and output specification (computed before building); for fixed-output or content-addressed store objects, it derives from the NAR (Nix Archive) serialization of the output itself. The Nix daemon enforces immutability via permissions and optional read-only bind mounts, and tracks runtime references by scanning build outputs for 32-character store-path hashes. That reference graph drives closure computation (nix-store -qR), atomic profile switching, and mark-and-sweep garbage collection, while also explaining why self-references or hardcoded paths in binaries must match valid store hashes.
