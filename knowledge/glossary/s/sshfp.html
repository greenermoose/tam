SSHFP (SSH Fingerprint DNS Record)

A DNS record type that publishes an SSH server’s public-key fingerprint in DNS so clients can verify the host key automatically when DNSSEC is valid.

Normally, the first time you connect to a new server with SSH, your computer asks you to trust its fingerprint by eye. With SSHFP, the domain owner posts that fingerprint in the domain’s official address book (DNS) with a tamper-proof seal, so your SSH client can check it automatically without making you guess.

Setting VerifyHostKeyDNS yes in ~/.ssh/config tells ssh to query SSHFP records for the hostname. If the record matches and the DNS response is authenticated by DNSSEC, ssh accepts the host key without a Trust On First Use (TOFU) prompt; if DNSSEC is missing, ssh still asks you to confirm, showing that a matching SSHFP record was found.

Why is SSHFP only trusted automatically when DNSSEC validation succeeds?

Without DNSSEC, an attacker on the network could spoof both the DNS SSHFP response and the SSH server, defeating the purpose of verifying the host key.

Defined in RFC 4255 (and extended for SHA-256 and ECDSA/Ed25519 in RFC 6594, RFC 7479, and RFC 8709), SSHFP (DNS RR type 44) stores three fields: public-key algorithm (1=RSA, 2=DSA, 3=ECDSA, 4=Ed25519, 6=Ed448), fingerprint hash type (1=SHA-1, 2=SHA-256), and the hex digest. Clients require the AD (Authenticated Data) bit from a validating local stub/recursive resolver (such as systemd-resolved or unbound) or local DNSSEC validation before treating VerifyHostKeyDNS matches as authoritative.
