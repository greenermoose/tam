Guide / Glossary A–Z / Terms beginning with S / Secure Boot

Secure Boot is a UEFI firmware security mechanism that checks cryptographic signatures on bootloaders and operating system kernels before allowing them to execute.

Think of Secure Boot as a bouncer at the door when your computer first powers on. Before the operating system loads, the motherboard’s built-in firmware checks a digital signature on the startup software, much like checking an official seal on a letter. If the software has been tampered with by malware or lacks a trusted signature, the computer refuses to run it and stops before the infection can take hold.

On Linux systems, UEFI Secure Boot sits between firmware initialization and the kernel: the firmware verifies the bootloader (often shim or systemd-boot), which in turn verifies the kernel and any out-of-tree kernel modules when kernel lockdown is active. If you dual-boot or build custom kernels, unsigned kernels or third-party modules (such as proprietary GPU drivers) will fail to load unless you enroll your own Machine Owner Key (MOK) or custom keys, or disable Secure Boot in firmware setup. You can check the current state on Linux with bootctl status or mokutil --sb-state.

Why can installing an unsigned third-party kernel module fail when Secure Boot is enabled?

When Secure Boot is active, the Linux kernel typically enters lockdown mode and enforces module signature verification. Any module not signed by a key trusted by the kernel or MOK database is rejected to prevent unsigned code from running in kernel space.

UEFI Secure Boot relies on four authenticated NVRAM variable databases: the Platform Key (PK, root of trust), Key Exchange Keys (KEK, authorized to update db/dbx), the allowed signature database (db, X.509 certificates or SHA-256 Authenticode hashes), and the forbidden/revocation database (dbx). Firmware verifies PE/COFF Authenticode signatures on EFI binaries against db while rejecting anything matched in dbx. Most Linux distributions avoid requiring firmware db enrollment directly by chaining through a Microsoft-signed shim.efi, which verifies GRUB or systemd-boot and kernels against a vendor certificate or user-enrolled MOK/SBAT policy (mitigating bootkit CVEs without exhausting small NVRAM dbx space). Tools like sbctl alternatively replace vendor keys in Setup Mode with self-managed PK/KEK/db keys, though bricking risk exists on firmware that relies on Microsoft-signed option ROMs during POST.
