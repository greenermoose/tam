SMT (Simultaneous Multithreading)

A CPU hardware feature that lets a single physical processor core execute instructions from two or more independent threads at the same time.

Imagine a chef working at a stove with two cutting boards: while one pot is simmering, the chef chops vegetables for a second dish instead of standing idle. Inside a computer, a single processor core often waits on slow memory. SMT (often called Hyper-Threading on Intel chips) lets that core keep two instruction streams ready so it can use idle parts of the core, appearing to the operating system as two virtual CPUs.

On Linux, each SMT thread appears as a separate logical CPU in /proc/cpuinfo and lscpu (for example, 8 cores with 2 threads per core show 16 CPUs). SMT typically boosts throughput by 15–30% on mixed or memory-bound workloads, though two threads on the same core compete for shared execution units and caches—so CPU-heavy real-time or HPC tasks sometimes disable it via /sys/devices/system/cpu/smt/control.

Why can disabling SMT sometimes improve single-thread latency or security?

Sibling SMT threads share L1/L2 caches, TLBs, and branch predictors on the same physical core. Contention can cause cache evictions that slow latency-sensitive tasks, and shared microarchitectural state creates side-channel exposure (such as MDS or Spectre-style leaks) between untrusted workloads.

SMT duplicates architectural state (registers, instruction pointer, APIC ID) per hardware thread while dynamically sharing superscalar front-end, execution ports, store buffers, TLB, and L1/L2 caches (typically 2-way on x86_64, up to 4- or 8-way on POWER). Linux’s scheduler (kernel/sched/fair.c) models SMT siblings in sched_domain topology to spread tasks across physical cores before packing siblings, and CORE_SCHED (PR_SCHED_CORE) lets untrusted cgroups avoid co-scheduling on the same core to mitigate cross-thread transient-execution side channels.
