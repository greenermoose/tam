Snapshot

A snapshot records the state of stored information at a particular point in time so you can inspect or restore it later.

Think of a snapshot like taking a photograph of your desk before rearranging everything: you can look back at where everything was, or put things back if a change goes wrong. On a computer, a filesystem snapshot freezes a view of your files at a moment in time without immediately copying every byte, though if the physical drive itself fails, a snapshot on that same drive is lost too.

On Linux filesystems like Btrfs or ZFS, a snapshot is fast and uses almost no extra space at first because it shares existing data blocks (extents) with the original subvolume via copy-on-write; space grows only as files change or are deleted. Crucially, Btrfs snapshots do not cross mount points or include nested subvolumes (for example, /home if it is a separate subvolume), so rolling back / leaves /home untouched.

If you delete a 10 GB file after taking a Btrfs snapshot, why doesn’t your free disk space immediately increase by 10 GB?

The snapshot still references those 10 GB of shared data extents. Copy-on-write only unlinks the file from the active subvolume; the underlying blocks cannot be reclaimed until every snapshot referencing them is also deleted.

In Btrfs, a snapshot is itself a first-class subvolume (BTRFS_ROOT_ITEM) initialized with the same root tree generation and shared extent references (BTRFS_EXTENT_ITEM refcounts) as its source, optionally marked read-only (ro) for atomic btrfs send/receive replication. Recovery boundaries depend on subvolume layout, excluded nested subvolumes, and crash or application consistency (such as databases mid-transaction without fsfreeze or write-ahead logging); because snapshots share physical media and metadata trees, independent off-device backups remain necessary.
