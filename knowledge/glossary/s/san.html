Guide / Glossary A–Z / Terms beginning with S / SAN (Subject Alternative Name)

An X.509 certificate extension that lists every hostname, IP address, or other identity a TLS certificate is valid for.

When you visit a secure website, your browser checks its digital ID card (certificate) to make sure you are talking to the real site. The SAN list is the section of that card that names every web address it covers—for example, both example.com and www.example.com—so one certificate can protect several names.

Modern browsers and TLS libraries ignore the older Common Name (CN) field and require the address you typed to match an entry in the SAN extension. You can inspect a site’s SAN entries in Linux with openssl s_client -connect example.com:443 </dev/null | openssl x509 -noout -ext subjectAltName. A wildcard entry like *.example.com matches one subdomain level (mail.example.com) but not deeper levels (a.b.example.com) or the bare apex domain (example.com).

Why does a self-signed certificate with only the Common Name set to localhost fail in modern browsers?

RFC 2818 deprecated CN fallback and modern clients (following CA/Browser Forum Baseline Requirements and RFC 6125/9525) validate hostnames strictly against the SAN extension, rejecting certificates that omit DNS:localhost or IP:127.0.0.1 in SAN.

Defined in RFC 5280 §4.2.1.6 with OID 2.5.29.17, the SubjectAltName extension is an ASN.1 SEQUENCE OF GeneralName supporting dNSName (IA5String), iPAddress (4- or 16-octet raw network-byte-order), uniformResourceIdentifier, and rfc822Name. Name constraints (OID 2.5.29.30) on intermediate CAs restrict permitted or excluded subtrees across these GeneralName types. Edge cases include Punycode (A-label) encoding for internationalized domain names and strict IP literal matching, where connecting by IP requires an iPAddress OCTET STRING rather than a dNSName string.
