Subvolume

A subvolume is an independently managed directory tree inside a Btrfs filesystem.

Imagine a single big storage room divided into separate, labeled closets. From the outside they all share the same floor space, so you never run out of room in one closet while another sits half-empty—yet you can still lock, photograph, or roll back just one closet without disturbing the rest. A Btrfs subvolume works like one of those closets: it feels like a normal folder, but the filesystem can snapshot or manage it on its own.

Unlike a traditional disk partition, a Btrfs subvolume does not have a fixed size; all subvolumes draw dynamically from the same underlying storage pool. Each subvolume can be mounted separately with -o subvol=... (for example, keeping @ for root and @home for user files) and snapshotted independently, so rolling back your system files leaves personal data in @home untouched.

If you take a snapshot of a parent subvolume, does it include a nested subvolume inside it?

No. Btrfs snapshots stop at subvolume boundaries: a snapshot of the parent creates an empty stub directory where the nested subvolume was mounted, rather than copying the nested subvolume’s files.

In Btrfs, each subvolume is a distinct POSIX file-tree B-tree root (tracked in the root tree with an object ID ≥ 256; ID 5 is the top-level FS_TREE) with its own inode number space. A snapshot is simply a copy-on-write clone of a subvolume’s root node at a point in time, meaning creation is O(1) and shares extents until modified. Subvolumes support qgroup (quota) accounting per root ID and incremental replication via btrfs send / btrfs receive (which requires read-only snapshots). Key operational gotchas include cross-subvolume rename() returning EXDEV (or silently falling back in some tools) and snapshot retention pinning old extents so deleted files do not free space until all referencing snapshots are removed.
