Guide / Glossary A–Z / Terms beginning with S / SNI (Server Name Indication)

A TLS handshake extension that lets a client tell the server which hostname it wants to reach before an encrypted HTTPS connection is established.

Imagine an apartment building with one street address (one IP address) and many residents (websites). When you arrive at the front door, you have to say which resident you are visiting so the reception desk can hand you the right visitor badge. SNI does that for HTTPS: your browser names the website at the very start of the connection so the server sends back the matching security certificate.

Without SNI, a single IP address could only serve one TLS certificate cleanly, which was a major bottleneck for IPv4 web hosting and reverse proxies like Nginx or Caddy. Because the traditional TLS ClientHello—including SNI—is sent in plaintext, ISPs and network monitors can still see which domain you are connecting to even though the HTTP request inside is encrypted. You can test SNI behavior on Linux with openssl s_client -connect example.com:443 -servername example.com.

Why can a network observer see which website you visit over HTTPS even though the web page content is encrypted?

In standard TLS, the Server Name Indication (SNI) extension is sent inside the unencrypted ClientHello message so the server knows which certificate to present before encryption keys are negotiated. Only Encrypted ClientHello (ECH) hides it.

Defined in RFC 6066 (Section 3), the server_name extension (type 0x0000) carries a list of HostName entries in ClientHello, enabling name-based virtual hosting prior to ServerHello and Certificate selection. In TLS 1.3, Encrypted ClientHello (ECH) wraps an inner ClientHello containing the true SNI inside an outer ClientHello using an HPKE public key fetched via DNS HTTPS records, preventing passive SNI inspection and active SNI-based filtering—provided the outer SNI and fallback behavior do not leak metadata.
