SONAME (Shared Object Name)

A versioned identifier embedded inside a Linux shared library that tells programs which binary-compatible release of that library they require.

Imagine a power tool that takes “Type-2 batteries.” Even if the battery maker improves the cells inside, anything labeled “Type-2” still fits and works; only if they change the connector shape do they call it “Type-3.” A SONAME is that compatibility label inside a .so library file on Linux, so programs know which version they can safely load.

On Linux, a shared library typically uses three names: the linker name (libfoo.so, a symlink used at compile time with -lfoo), the SONAME (libfoo.so.1, used at runtime by ld.so), and the real file (libfoo.so.1.4.2). When a library makes a breaking ABI change, maintainers bump the SONAME (libfoo.so.1 to libfoo.so.2) so both versions can coexist while dependent packages are rebuilt. You can inspect a library’s SONAME with readelf -d /path/to/libfoo.so | grep SONAME.

Why does upgrading a shared library from 1.2.0 to 1.3.0 (same SONAME) not require recompiling programs that use it?

Keeping the same SONAME (e.g., libfoo.so.1) promises backward ABI compatibility. The dynamic linker (ld.so) looks for the SONAME recorded in the executable’s DT_NEEDED entry and loads the updated library seamlessly.

At static link time, ld reads the DT_SONAME string from the .dynamic section of an input shared object (set via -Wl,-soname,libfoo.so.1) and writes it—not the input filename—into the output binary’s DT_NEEDED array. At execution time, ld-linux.so resolves DT_NEEDED entries via DT_RPATH/DT_RUNPATH, LD_LIBRARY_PATH, and /etc/ld.so.cache (ldconfig creates the SONAME symlinks); if DT_SONAME is omitted, ld falls back to the raw file path, breaking portable runtime resolution.
