Shared library

A shared library is a collection of reusable compiled code that multiple programs can load and share while running.

Instead of copying the same common building blocks—like opening windows, reading text, or drawing fonts—into every single app on your computer, the operating system keeps one copy in a shared library. Many programs can use that single copy at the same time, which saves disk space and memory and lets a single security update fix a bug for every program that relies on it.

On Linux, shared libraries usually have names ending in .so (shared object), such as libc.so.6 or libssl.so.3, and are loaded at startup by the dynamic linker rather than baked into the executable (static linking). You can inspect which shared libraries a program needs with ldd /usr/bin/ls, and if a required library is missing or mismatched, the program fails immediately with an error like error while loading shared libraries. Because the library’s code pages are read-only, the kernel maps the same physical RAM pages into every running process that uses it.

What happens when you update a shared library on disk to patch a security bug while programs are already running?

New programs started after the update load the patched library, while already-running processes keep using the old version mapped into their memory until they are restarted.

An ELF shared object (ET_DYN) is compiled as position-independent code (-fPIC) so ld.so can map it at arbitrary ASLR base addresses while sharing clean text pages across processes and isolating per-process writable data (.data, .bss, GOT) via copy-on-write. Symbol resolution traverses DT_NEEDED entries using RPATH/RUNPATH, LD_LIBRARY_PATH, and /etc/ld.so.cache, patching external calls lazily through the PLT/GOT unless BIND_NOW (-Wl,-z,now + RELRO) enforces eager binding at startup. ABI stability is governed by the DT_SONAME major version and optional ELF symbol versioning.
