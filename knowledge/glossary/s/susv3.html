SUSv3 (Single UNIX Specification v3)

SUSv3 (Single UNIX Specification, Version 3) is the 2001 standard that unified POSIX.1-2001 and the Single UNIX Specification into one shared definition of Unix-like interfaces.

Years ago, different Unix systems had slightly different rules for basic commands and programming tools, making software hard to move from one machine to another. SUSv3 is an official agreement from 2001 that wrote down one common rulebook. Thanks to standards like it, programs written for one Unix-like system—including Linux—can usually be compiled and run on others with minimal changes.

When compiling C programs on Linux, headers hide non-standard extensions unless you ask for them, or hide standard functions unless you declare which standard you target. Defining _XOPEN_SOURCE=600 (or _POSIX_C_SOURCE=200112L for the POSIX subset) tells glibc or musl to expose the SUSv3 / POSIX.1-2001 APIs—such as termios, pthreads, and getaddrinfo()—while keeping code portable across compliant systems.

Why do C source files sometimes define _XOPEN_SOURCE=600 at the top before including headers?

It acts as a feature-test macro telling the C library to expose the interfaces defined by SUSv3 (POSIX.1-2001 plus X/Open extensions) so portable code gets those declarations without accidentally relying on non-standard GNU extensions.

Published jointly by The Open Group and IEEE as IEEE Std 1003.1-2001 / ISO/IEC 9945:2002, SUSv3 merged POSIX.1 (C APIs), POSIX.2 (shell and utilities), and the X/Open System Interface (XSI) extensions into four volumes: Base Definitions, System Interfaces, Shell and Utilities, and Rationale. In glibc and musl, _XOPEN_SOURCE=600 enables SUSv3 Base + XSI symbols (for instance, posix_memalign(), getaddrinfo(), and XSI nftw()/shmget()), whereas _POSIX_C_SOURCE=200112L omits XSI extensions. Note that SUSv3 was later superseded by SUSv4 (POSIX.1-2008, _XOPEN_SOURCE=700) and POSIX.1-2024 (_XOPEN_SOURCE=800).
