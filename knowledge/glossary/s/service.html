Service

A service is a background program managed by the operating system to provide ongoing functionality—such as networking, printing, or logging—without needing an interactive window.

When you open a web browser, you see a window and interact with it directly. A service is the opposite: it runs quietly behind the scenes—for example, keeping your Wi-Fi connected, syncing the system clock, or listening for print jobs—starting automatically when the computer boots and restarting if it ever crashes.

On modern Linux distributions, system and user services are managed by systemd through .service unit files (for example, sshd.service or a user unit started with systemctl --user). Unlike a one-off command you run in a terminal, a managed service has defined dependencies (After=, Requires=), restart policies, and centralized logs captured by journald. You can inspect a service’s state and recent output with systemctl status <name> and journalctl -u <name>.

What is the practical difference between starting a daemon manually in a terminal and starting it as a systemd service?

A manually launched process dies when your shell closes (unless detached) and has no automatic dependency ordering or crash recovery. A systemd service runs in a tracked cgroup, starts in the right boot order, logs to journald, and can restart automatically.

In systemd, a .service unit binds a declarative execution specification to a dedicated kernel cgroup slice (system.slice or user.slice), guaranteeing clean process-tree tracking and teardown without PID-file races. Unit Type= (simple, exec, notify via sd_notify(), forking, oneshot, or dbus) determines when systemd considers activation complete for downstream After= dependents. Services can also be socket-activated (.socket passing file descriptors via LISTEN_FDS) and sandboxed using kernel namespaces, seccomp-BPF filters (SystemCallFilter=), and capability bounding sets (CapabilityBoundingSet=).
