Stream

A stream is a sequence of data that a program reads from or writes to in order, one piece after another.

Think of a stream like water flowing through a pipe or a conveyor belt of letters. Instead of jumping around a whole document like a book, a program handles whatever arrives next in line and sends its results out in order. This lets programs start working right away on incoming data—even if it is huge or still arriving—without waiting to load everything into memory at once.

Every standard Linux command-line program starts with three default streams: standard input (stdin, file descriptor 0) for reading data, standard output (stdout, fd 1) for normal results, and standard error (stderr, fd 2) for diagnostics. In a shell pipeline (cmd1 | cmd2), the shell connects cmd1’s stdout directly to cmd2’s stdin while leaving stderr attached to the terminal so error messages do not corrupt the data flowing downstream.

Why do command-line tools separate standard output from standard error?

Separating them lets you pipe or redirect a program’s normal output into another tool or a file without accidentally mixing in warnings or error messages, which remain visible on the screen unless you explicitly redirect file descriptor 2.

At the POSIX/Linux level, a stream is either an unbuffered kernel byte stream behind a file descriptor (pipes, sockets, character devices) or a user-space buffered FILE * stream in libc (<stdio.h>). Kernel pipes are unidirectional FIFO ring buffers (default capacity 64 KiB on Linux, tunable via F_SETPIPE_SZ) that preserve byte order without preserving record boundaries; writes up to PIPE_BUF (4096 bytes) are guaranteed atomic. User-space stdio adds buffering modes—line-buffered on terminals, block-buffered on pipes and regular files, and unbuffered on stderr—which explains why output from a pipeline can appear delayed until buffers flush or the process exits, and why SIGPIPE (or EPIPE) occurs when writing to a stream whose read end has closed.
