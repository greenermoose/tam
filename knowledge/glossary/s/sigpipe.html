Guide / Glossary A–Z / Terms beginning with S / SIGPIPE (Broken Pipe signal)

SIGPIPE (signal 13) is sent to a process when it tries to write to a pipe, FIFO, or socket whose reading end has already closed.

Imagine shouting instructions through a speaking tube after the listener at the other end has walked away. SIGPIPE is the operating system telling a program “nobody is listening anymore, so stop talking,” which keeps command pipelines fast instead of wasting work.

Part of Unix signals, SIGPIPE (13) is why a pipeline like yes | head -n 5 stops cleanly as soon as head reads five lines and exits: yes receives SIGPIPE on its next write and terminates quietly without printing an error. Network servers, by contrast, usually ignore SIGPIPE so a client disconnecting mid-response does not crash the whole server.

Why do long-running network daemons commonly set SIGPIPE to SIG_IGN?

If a client drops a TCP connection just as the server writes to the socket, default SIGPIPE delivery would terminate the entire server process instead of letting write() fail with EPIPE for that one client.

POSIX signal 13 (SIGPIPE), raised synchronously by the kernel during write(2), send(2), or splice(2) on a pipe, FIFO, or stream socket with no remaining open read file descriptors. If SIGPIPE is masked or set to SIG_IGN, the syscall fails with -1 and sets errno = EPIPE instead of terminating the process; on Linux sockets, passing MSG_NOSIGNAL to send() suppresses SIGPIPE per call without mutating process-wide signal dispositions. Some runtimes (such as Go and Rust binaries) ignore or handle SIGPIPE differently on non-stdio descriptors, which can produce “broken pipe” errors when piped to head.
