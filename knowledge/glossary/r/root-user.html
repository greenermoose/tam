Guide / Glossary A–Z / Terms beginning with R / Root user

The built-in administrative account on Unix-like systems that has unrestricted authority over the operating system.

On a shared computer, ordinary users are kept in their own lanes so one person—or a buggy program—cannot accidentally delete system files or read someone else’s private folders. The root user is the master key holder who can change any setting, install system software, and access any file, which is why you normally use a regular account like alex and only borrow root power when needed.

The kernel identifies the root account by numeric user ID 0 (UID 0), not by the string name root. In daily Linux work, direct root logins are discouraged; instead, an unprivileged user runs specific administrative commands via sudo or graphical authentication prompts via pkexec (Polkit), which leaves an audit trail and limits the blast radius of mistakes.

Why is it safer for alex to run a single command with sudo or pkexec than to stay logged in as root all day?

Every program launched in a root shell inherits full administrative privileges, so a typo or compromised app can wipe system files. Elevating privileges per command limits exposure to that single action and logs who ran it.

In Linux, UID 0 traditionally grants all POSIX capabilities (CAP_SYS_ADMIN, CAP_DAC_OVERRIDE, CAP_NET_ADMIN, etc.), allowing processes to bypass discretionary access control (DAC) checks. However, UID 0 is not omnipotent on modern kernels: mandatory access control frameworks (SELinux, AppArmor), read-only mounts, immutable file flags (chattr +i), user namespaces (where UID 0 inside a container maps to an unprivileged host UID), and kernel lockdown (under Secure Boot, restricting /dev/mem and unsigned kernel modules) still constrain what root can do.
