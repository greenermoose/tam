Guide / Glossary A–Z / Terms beginning with R / Repository

An organized store of installable software packages or a project’s tracked file history.

Think of a repository like a curated library or app catalog. When you install a program on Linux, your system fetches it from a software repository instead of you hunting for installers on random websites. Developers also use code repositories to keep every saved version of a project’s files in one place so they can undo mistakes or collaborate without overwriting each other’s work.

In everyday Linux use, the word “repository” refers to two distinct systems: a package repository (configured for tools like apt, dnf, or pacman) that serves prebuilt software and dependency metadata, and a source repository (such as a Git repo) that stores commits, branches, and history for developers. A third-party package repo must be trusted before you add it because packages from it typically run install scripts with administrator privileges.

Why is adding an untrusted package repository riskier than cloning an untrusted Git repository?

Cloning a Git repository only downloads files onto your disk, whereas installing software from a package repository lets your package manager execute maintainer scripts as root during installation and upgrade.

A package repository pairs signed index metadata (for example, APT Release/InRelease, RPM repomd.xml, or Pacman .db tarballs) with content-verified binary artifacts so clients can resolve dependency graphs and verify integrity before unpacking. A Git repository is a content-addressed object database (blobs, trees, commits, tags) keyed by hash under .git/objects, where named refs and reflogs govern reachability and garbage collection (git gc). Both models rely on cryptographic verification—OpenPGP or Ed25519 signatures on repo metadata and signed tags or commits—to separate transport security from origin authenticity.
