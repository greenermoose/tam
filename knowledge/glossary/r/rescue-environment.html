Rescue environment

A separate, working tool environment used to inspect or repair another operating system that cannot start or function normally.

If your computer’s main system breaks and cannot reach the desktop, you cannot fix it from inside itself—just like you cannot easily repair a car engine while driving down the highway. A rescue environment is a spare, self-contained system (often on a USB stick or a special startup menu entry) that boots up cleanly so you can back up files, undo a bad change, or repair the broken installation.

On Linux, a rescue environment is typically a live USB image, an emergency initramfs shell, or a minimal boot entry that loads its own kernel and utilities into memory without mounting the damaged root filesystem read-write. From it, you can run filesystem checks (fsck), unlock encrypted volumes, mount partitions under /mnt, and enter the installed system with chroot to reinstall a bootloader or fix configuration files.

Why should you run a filesystem check from a rescue environment instead of on the running system?

Repairing a mounted, active root filesystem risks corrupting data because the kernel and running programs are still reading and writing metadata; a rescue environment lets you check the target partition while it is unmounted or read-only.

A rescue environment boots an independent kernel and userspace (often entirely in tmpfs/initramfs or squashfs) with the storage, encryption (dm-crypt/LUKS), LVM/RAID, and filesystem drivers needed to access the target block devices. Recovery workflows commonly bind-mount /dev, /proc, /sys, and EFI variables (/sys/firmware/efi/efivars) before calling chroot or systemd-nspawn so package managers and bootloader installers (such as grub-install or bootctl) can update the target without mixing host and target libraries. A key failure mode is architecture or kernel-feature mismatch—for example, booting in legacy BIOS mode when trying to register an EFI boot variable, which fails because efivars is unavailable.
