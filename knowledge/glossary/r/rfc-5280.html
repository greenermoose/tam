RFC 5280 (X.509 PKI Profile)

The IETF standard that defines how X.509 v3 digital certificates and revocation lists are structured and validated on the internet.

When your browser shows a padlock for an HTTPS website, it checks a digital certificate that proves the site really is who it claims to be. RFC 5280 is the shared rulebook that says what information must be inside those certificates, how they are signed by trusted authorities, and how to check whether a certificate has expired or been canceled.

In practice, RFC 5280 governs the certificate fields and extensions you see when inspecting a TLS certificate with openssl x509. For example, modern browsers match hostnames against the Subject Alternative Name (SAN) extension rather than the older Common Name (CN), and check Basic Constraints to ensure an ordinary website certificate cannot pretend to be a Certificate Authority (CA) and sign other certificates.

Why can a certificate with a matching Common Name still fail browser validation if it lacks a Subject Alternative Name (SAN)?

Modern TLS clients follow RFC 5280’s SAN extension rules (and CA/Browser Forum requirements) and ignore the legacy Common Name for hostname matching, so a missing SAN causes a hostname mismatch error.

IETF RFC 5280 (2008, updating RFC 3280) profiles X.509 v3 certificates and v2 Certificate Revocation Lists (CRLs) using ASN.1 DER encoding, and defines the normative certification path validation algorithm. Verification checks cryptographic signatures along the chain to a trust anchor, validity intervals, Basic Constraints (cA flag and pathLenConstraint), Key Usage and Extended Key Usage, certificate policies, and Name Constraints (which restrict the DNS/IP/email subtrees an intermediate CA may issue for). Edge cases include critical unrecognized extensions—which RFC 5280 requires validators to reject—and revocation latency, where CRLs and OCSP are often supplemented in browsers by short-lived certificates or pushed revocation sets.
