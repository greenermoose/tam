Rollback point

A recorded, known-good system state that you can return to if a change breaks something.

Before you rearrange furniture in a room, taking a quick photo makes it easy to put everything back if the new layout does not work. A rollback point does the same for your computer: it saves a clear reference to how things looked when everything was still working, so you do not have to guess how to undo a bad update.

In practice, a rollback point is one concise line recording the previous Tamlinux source-install stage (or prior bundle on transitional hosts), plus a Snapper filesystem snapshot for privileged changes to boot, login, disk, firmware, or system packages. Recording both before starting means you know the exact stage and snapshot ID to restore instead of searching through logs after a failure.

Why does a rollback point for a kernel or disk change include a Snapper snapshot in addition to the previous cultivar stage?

A cultivar stage rollback only restores Tamlinux’s own managed files. System-wide changes—such as boot, login, disk, firmware, or rootstock package removal—affect files outside the cultivar stage, so a Snapper snapshot is needed to restore the underlying system.

A rollback point defines an explicit recovery contract across independent state layers: the previous Tamlinux source-install stage (or transitional bundle) for cultivar files paired with a copy-on-write Btrfs Snapper snapshot when privileged operations touch boot, login, disk, firmware, or system package removal. Even with both recorded, out-of-band state—such as EFI NVRAM boot entries, firmware flashes, or mutable database files excluded from snapshot subvolumes—falls outside the snapshot boundary and requires separate verification or restoration procedures.
