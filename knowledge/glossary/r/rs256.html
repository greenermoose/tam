RS256 (RSA PKCS#1 v1.5 with SHA-256)

RS256 is an algorithm identifier used in JSON Web Tokens (JWTs) and JSON Web Signatures (JWS) for asymmetric RSA signatures with SHA-256.

When you log in to a service, an authentication server often hands you a signed digital pass (a token). With a shared-password method, every service checking your pass needs the same secret password—meaning any of them could also forge one. RS256 works like a private wax seal paired with a public checker: only the authentication server holds the private key to sign tokens, while any service can use the public key to verify they are genuine.

Widely used in OpenID Connect (OIDC) and OAuth 2.0, RS256 lets independent microservices verify JWTs offline by fetching the identity provider’s public keys from a JWKS endpoint and matching the token’s kid (key ID). Compared with HS256 (symmetric HMAC-SHA256), RS256 avoids distributing a shared signing secret; compared with PS256 (RSA-PSS) or ES256 (ECDSA P-256), RS256 uses older deterministic PKCS#1 v1.5 padding and produces larger signatures.

Why is RS256 preferred over HS256 when multiple independent services need to verify user tokens?

With HS256, every verifying service must hold the shared HMAC secret, so compromising any single service allows an attacker to forge tokens for the entire system. With RS256, only the identity provider holds the private signing key, while verifiers only need the public key.

Defined in RFC 7518 (JWA), RS256 specifies RSASSA-PKCS1-v1_5 with SHA-256 (minimum 2048-bit RSA key). Although PKCS#1 v1.5 signatures do not suffer from Bleichenbacher’s encryption padding oracle, flawed ASN.1/DigestInfo length checks in naive verifiers (Bleichenbacher’s e=3 signature forgery) and the absence of a tight security reduction led newer profiles to favor PS256 (RSA-PSS) or ES256/EdDSA. Critical JWT verifier bugs include accepting alg: "none" and algorithm-confusion attacks where an RS256 public key is misused as an HS256 HMAC secret.
