ROBOT (Return Of Bleichenbacher's Oracle Threat)

A cryptographic vulnerability (Return Of Bleichenbacher’s Oracle Threat) that lets an attacker decrypt RSA-encrypted TLS traffic when a server leaks padding errors.

When you visit a secure website, your browser and the server agree on a secret session key. Older versions of that handshake wrapped the secret in an envelope with strict formatting rules. ROBOT is a flaw where a server accidentally reveals—through a different error message or a tiny delay—whether an altered envelope had valid formatting, letting an attacker guess the secret piece by piece.

ROBOT specifically affects TLS cipher suites that use static RSA key transport (where the client encrypts the premaster secret under the server’s RSA public key using PKCS#1 v1.5 padding). Modern TLS deployments disable RSA key exchange in favor of ephemeral Diffie-Hellman (ECDHE) and use TLS 1.3, which removes static RSA key transport entirely and also provides forward secrecy.

Why does switching from RSA key transport to ECDHE (while still using an RSA certificate for signing) prevent ROBOT?

In ECDHE, the RSA key is only used to sign handshake parameters, never to decrypt a client-chosen secret wrapped in PKCS#1 v1.5 encryption padding. Without RSA decryption of ciphertexts, there is no padding oracle to query.

ROBOT revives Bleichenbacher’s 1998 adaptive chosen-ciphertext attack against PKCS#1 v1.5 RSA encryption in TLS. By sending crafted ciphertexts and observing subtle side channels—distinct TLS alerts, TCP resets, connection timeouts, or microsecond timing differences—an attacker builds a padding validity oracle that narrows the interval of the decrypted integer m mod n until the 48-byte premaster secret is recovered in tens of thousands to millions of queries. Because constant-time PKCS#1 v1.5 decryption (substituting a random fallback secret on bad padding without branching or early-exit timing leaks) is notoriously fragile in C implementations, RFC 8446 (TLS 1.3) dropped RSA key transport altogether.
