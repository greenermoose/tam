JWS (JSON Web Signature)

JWS (JSON Web Signature) is a standard format for wrapping data in a digital signature or message authentication code so a receiver can verify who sent it and that it has not been altered.

Think of a JWS like a letter sealed with a tamper-evident wax stamp: anyone can still read the message inside, but if someone changes even one word, the stamp no longer matches. It matters because apps often send data across untrusted networks and need a quick way to prove the message is genuine.

Most JWT tokens are encoded as a JWS in compact serialization: three Base64URL strings separated by dots (header.payload.signature). Notice that the payload is only Base64URL-encoded, not encrypted—anyone who intercepts a JWS can decode and read its contents, though they cannot forge a valid signature without the secret or private key. If confidentiality is needed, JWE (JSON Web Encryption) is used instead.

Can you hide sensitive user data inside a standard JWS payload without encrypting it?

No. A JWS only guarantees integrity and authenticity; its payload is Base64URL-encoded, which anyone can decode without a key.

Defined in IETF RFC 7515, JWS supports compact serialization (three dot-separated Base64URL segments) and JSON serialization (allowing multiple signatures and unprotected headers), signing the ASCII input ASCII(BASE64URL(UTF8(ProtectedHeader)) || '.' || BASE64URL(Payload)). Supported JWA algorithms (RFC 7518) include symmetric HMAC (HS256) and asymmetric RSA/ECDSA/EdDSA (RS256, ES256, EdDSA). Classic implementation pitfalls include trusting the unverified header’s alg field (enabling alg: none or RS256-to-HS256 key-confusion attacks) and failing to pin expected algorithms and key IDs (kid) on the verifier.
