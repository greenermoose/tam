JIT (Just-In-Time compilation)

Compiling bytecode or scripts into native machine code while a program is running for faster execution.

Normally, software works in one of two ways: either it is translated into CPU instructions ahead of time before you ever run it (like C programs), or an interpreter reads it line by line while it runs (which is flexible, but slower). JIT compilation blends both ideas—it starts running right away, watches which parts of the code get used over and over, and translates those hot spots into fast native CPU instructions on the fly.

You encounter JIT compilers across modern Linux stacks: JavaScript engines (V8, SpiderMonkey), LuaJIT, the JVM (HotSpot), PyPy, and the Linux kernel’s eBPF JIT (net.core.bpf_jit_enable). Compared to pure interpretation, a JIT trades a brief warm-up delay and extra memory for near-native loop speed; compared to ahead-of-time (AOT) compilation, it can optimize for the exact CPU features and runtime types it observes. Because a JIT must write new machine code into memory and then execute it, security-hardened systems enforce W^X (Write XOR Execute)—mapping code pages writable or executable, never both at once—and browsers or sandboxes sometimes disable JIT to reduce attack surface.

Why do hardened environments sometimes disable JIT compilation even though it makes scripts much faster?

JIT engines generate executable machine code at runtime in writable memory. Bugs in the JIT compiler or memory-permission transitions can be abused to turn data into executable shellcode, so security-critical sandboxes sometimes fall back to pure interpretation.

JIT architectures typically tier execution from an interpreter or baseline template compiler to an optimizing compiler (method-based SSA IR like V8 TurboFan/Maglev, or trace-based like LuaJIT) driven by runtime profiling counters and inline caches (ICs) for polymorphic call sites. When speculative assumptions (such as monomorphic types) fail, the runtime triggers deoptimization (OSR or bailout) back to unoptimized frames. On Linux, emitting code requires mmap(..., PROT_WRITE) followed by mprotect(..., PROT_READ | PROT_EXEC) (or dual-mapped memfd_create aliases) to satisfy W^X and SELinux execmem policies, plus instruction-cache invalidation (__builtin___clear_cache or IC IVAU) on non-coherent I-cache architectures like ARM64.
