Guide / Glossary A–Z / Terms beginning with H / HSTS (HTTP Strict Transport Security)

HSTS (HTTP Strict Transport Security) is an HTTP response header instructing browsers to connect to a site only over HTTPS.

Normally, when you type a web address like example.com, your browser first tries the unencrypted HTTP door and waits to be redirected to encrypted HTTPS—leaving a brief moment where someone on the same Wi-Fi could intercept you. HSTS is a sticky rule your browser saves for that site: “Never use unencrypted HTTP here again; go straight to HTTPS every time.”

When a server sends Strict-Transport-Security: max-age=31536000 over HTTPS, the browser caches that policy and internally rewrites future http:// links or typed addresses for that host to https:// before sending any packet, blocking SSL-stripping downgrade attacks and disabling certificate-warning click-throughs. Because browsers ignore HSTS over plain HTTP, a site’s very first visit remains exposed unless it is in the browser’s built-in preload list.

Why doesn’t a server’s HSTS header protect a user’s very first visit if they type http://example.com?

The browser only learns the HSTS policy after receiving the header over a valid HTTPS connection. Until then (trust-on-first-use), an active network attacker can intercept the initial plain HTTP request unless the domain is already in the browser’s HSTS preload list.

Defined in RFC 6797, Strict-Transport-Security accepts max-age=<seconds> (required; 0 clears the cached entry), optional includeSubDomains, and the non-RFC preload token used by browser preload lists (requiring max-age >= 31536000, includeSubDomains, and preload). User agents must ignore the header if received over plaintext HTTP or invalid TLS. Operational pitfalls include includeSubDomains breaking internal or legacy subdomains without valid TLS (with no user bypass), setting a long max-age before verifying all endpoints, and browser partitioning of HSTS state by top-level site to prevent HSTS supercookie tracking.
