Guide / Glossary A–Z / Terms beginning with H / HTTPS (Hypertext Transfer Protocol Secure)

HTTP protected by TLS so web traffic is encrypted and authenticated in transit.

Plain HTTP is like sending a postcard: anyone handling it along the way can read or alter what you wrote. HTTPS puts that message inside a locked, tamper-evident envelope and checks the sender’s ID card before you trust it. That is why browsers use HTTPS for logins, banking, and software downloads.

HTTPS runs HTTP inside a TLS tunnel (typically on TCP port 443 instead of 80), providing confidentiality, integrity, and server authentication via X.509 certificates. On Linux, tools like curl and browsers verify server certificates against the system’s trusted Certificate Authority bundle (such as /etc/ssl/certs); a wrong system clock or an untrusted proxy certificate will trigger connection errors. Websites can also send HSTS headers so browsers refuse to fall back to plain HTTP.

If a website uses HTTPS, does that hide which domain you are visiting from your local network?

No. While the URL path, headers, and page contents are encrypted, standard DNS lookups and the TLS Server Name Indication (SNI) field sent during the initial handshake usually reveal the destination hostname unless Encrypted Client Hello (ECH) and encrypted DNS are used.

HTTPS binds HTTP semantics (HTTP/1.1, HTTP/2 over ALPN h2, or HTTP/3 over QUIC/UDP) to TLS 1.3 (RFC 8446) or legacy TLS 1.2. A full TLS 1.3 handshake completes in 1-RTT with forward-secret ECDHE key exchange; 0-RTT early data trades replay protection for latency and is unsafe for non-idempotent requests. Certificate validation checks the chain to a trust anchor, SAN hostname matching, key usage, and revocation/transparency signals (OCSP stapling, CRLs, CT logs). Operational failure modes include SNI mismatches behind CDNs, middlebox TLS interception failing certificate pinning, and traffic-analysis side channels from packet lengths and timing.
