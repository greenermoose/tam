Guide / Glossary A–Z / Terms beginning with H / HTTP - Hypertext Transfer Protocol

HTTP (Hypertext Transfer Protocol) is the request-and-response protocol that web browsers, command-line tools, and APIs use to fetch and send data over a network.

HTTP works like ordering at a counter: your browser sends a short request (“Please send the page at /news”), and the web server replies with a status (“OK, here it is” or “Not Found”) along with the page or file. Plain HTTP sends everything in the open, whereas HTTPS wraps HTTP in encryption so others on the network cannot read or alter it.

Every HTTP exchange pairs a method (GET, POST, PUT, DELETE) and target URI with headers (Host, Content-Type, Authorization) and an optional body, returning a status code (2xx success, 3xx redirect, 4xx client error, 5xx server error). On Linux, curl -v or curl -I lets you inspect headers and status codes directly. Because HTTP is stateless, logins and sessions rely on cookies or tokens sent in headers.

What is the difference between a 4xx and a 5xx HTTP status code?

4xx codes (such as 404 Not Found or 403 Forbidden) mean the client’s request was invalid, unauthorized, or asked for something missing. 5xx codes (such as 500 or 502) mean the server failed while trying to fulfill a valid request.

RFC 9110 decouples HTTP semantics from wire framing: HTTP/1.1 (RFC 9112) uses text-line framing over TCP and suffers from application-layer head-of-line (HoL) blocking; HTTP/2 (RFC 9113) multiplexes binary frames with HPACK header compression over one TCP connection (still vulnerable to TCP-level HoL blocking on packet loss); HTTP/3 (RFC 9114) runs over QUIC/UDP with QPACK compression, eliminating transport HoL blocking and supporting connection migration. Key operational pitfalls include hop-by-hop vs. end-to-end headers (Connection, Transfer-Encoding), request-smuggling desyncs between proxies parsing Content-Length vs. Transfer-Encoding: chunked, and idempotency/cacheability rules.
