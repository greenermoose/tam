Guide / Glossary A–Z / Terms beginning with H / HS256 (HMAC with SHA-256)

HS256 is the JWS/JWT algorithm identifier for symmetric HMAC-SHA256 signatures.

When a website gives your browser a login pass (token), it adds a digital seal so you cannot edit the pass to pretend you are an administrator. With HS256, the server that creates the pass and the server that checks it both use the exact same secret key. That makes it fast and simple for one service, though you cannot hand that key to untrusted third parties without letting them forge passes too.

In a JWT header ({"alg":"HS256","typ":"JWT"}), HS256 uses symmetric HMAC-SHA256: any party able to verify a token can also mint one because both sides hold the same secret. Contrast with RS256 or ES256, where an auth server signs with a private key and downstream services verify using only a public key. Always enforce the expected algorithm in server configuration rather than trusting the token’s alg field.

Why shouldn’t a service accept whatever alg value arrives inside an incoming JWT header?

If a verifier expects RS256 (public key) but blindly honors alg: "HS256", an attacker can sign a forged token with HMAC using the server’s public RSA key as the secret—or send alg: "none"—bypassing signature checks.

Specified in RFC 7518 (JWA) Section 3.2, HS256 computes HMAC-SHA-256(key, ASCII(BASE64URL(header) || '.' || BASE64URL(payload))) and base64url-encodes the 32-byte tag without padding. RFC 7518 mandates keys of at least 256 bits (32 octets); short or human-chosen secrets allow offline brute-force attacks against captured tokens. Secure verifiers pin the allowed algorithm and key type per key ID (mitigating alg=none, RS256→HS256 key-confusion, and kid injection) and compare the decoded 32-byte MAC in constant time.
