Hard link

An additional directory entry that points directly to the exact same underlying file on disk as another filename.

Imagine a single book in a library that has two different index cards pointing to the same shelf spot. A hard link works like that second index card: both filenames open the exact same file, and changing one changes the other. If you throw away one index card, the book itself stays on the shelf as long as at least one card still points to it.

Created with ln target linkname (without -s), a hard link differs from a symbolic link (symlink): a symlink stores a path string and breaks if the target is moved or deleted, whereas a hard link points directly to the file’s inode number and remains valid if the original name is removed. You can inspect link counts with ls -l (the second column) or stat. Because inode numbers are only unique within one filesystem, hard links cannot cross mount boundaries, and POSIX systems forbid users from hard-linking directories to prevent cycles.

If /home/alex/a.txt and /home/alex/b.txt are hard links to the same file and you run rm /home/alex/a.txt, what happens to the data?

The data remains intact and accessible via b.txt. Removing a name only unlinks that directory entry and decrements the inode’s link count from 2 to 1; the filesystem frees the data blocks only when the link count reaches 0 and no process has the file open.

At the POSIX VFS level, link(2) / linkat(2) atomically inserts a new directory entry (dentry) mapping a name to an existing inode and increments i_nlink. All hard links are peer references—there is no “original” vs. “copy”—and permissions, ownership, and timestamps belong to the inode, not the directory entry (though ctime updates when i_nlink changes). Edge cases include: editors that save via write-temp-and-rename(2) silently break hard links by replacing one name with a new inode; fs.protected_hardlinks=1 on Linux blocks unprivileged users from hard-linking files they do not own or cannot read/write (mitigating setuid/TOCTOU attacks); and open(..., O_TMPFILE) creates an unlinked inode that can later be atomically materialized into a directory via linkat.
