HAMMER2

The default copy-on-write filesystem of DragonFly BSD, designed for fast snapshots, data integrity checks, and multi-machine mirroring.

A filesystem is how an operating system organizes files and folders on a drive. HAMMER2 is the main filesystem used by DragonFly BSD. Instead of overwriting old file data in place—which can leave files half-written if the power goes out—it writes new changes to a fresh spot first, making crashes safer and instant “save points” (snapshots) easy to keep.

In the broader Unix/BSD/Linux family, HAMMER2 sits alongside copy-on-write (CoW) filesystems like Btrfs and ZFS rather than traditional journaling filesystems like ext4. It provides per-block checksums to detect silent data corruption, transparent compression, and zero-cost writable snapshots (called PFS, or Pseudo-Filesystems). Unlike its predecessor HAMMER1—which required periodic manual or cron-driven pruning and reblocking—HAMMER2 handles block reclamation and deduplication incrementally in the background.

Why do copy-on-write filesystems like HAMMER2 create snapshots almost instantaneously without copying all the file data?

A snapshot simply records a pointer to the current root of the filesystem’s metadata tree. Existing data blocks are shared with the live filesystem and are only diverged when later writes allocate new blocks elsewhere.

HAMMER2 uses a radix-tree blockmap topology with 64 KB allocation blocks (sub-divided into 1 KB–64 KB logical blocks) and four rotating volume headers at 2 MB intervals for crash-consistent root commits. Every block reference carries an embedded 64-bit checksum (xxHash64 or SHA-256), and read paths are designed to be lockless across CPUs using immutable CoW trees and fine-grained inode/chain locking for writers. It supports LZ4 and zlib compression, offline/online dedup, and asynchronous multi-master or master-slave PFS mirroring over network sockets—though in practice single-node snapshots and local mirroring are its most mature production paths.
