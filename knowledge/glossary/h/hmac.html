Guide / Glossary A–Z / Terms beginning with H / HMAC (Hash-based Message Authentication Code)

HMAC (Hash-based Message Authentication Code) is a standard way to verify both that a message has not been altered and that it came from someone holding a shared secret key.

Think of HMAC like a wax seal stamped with a private ring: anyone can read the letter, and if even one word is changed the seal no longer matches, yet nobody without the ring can forge a new seal. Unlike a plain file checksum—which anyone can recompute after changing a file—HMAC proves both integrity and sender identity to anyone who shares the secret.

In practice, HMAC pairs a cryptographic hash function (such as SHA-256) with a secret key. A plain sha256sum only catches accidental corruption because an attacker can modify the data and recompute the hash; HMAC blocks forgery unless the attacker also has the key. Unlike asymmetric digital signatures, HMAC is symmetric and very fast, so it is widely used for API request signing, session cookies, and key derivation (HKDF), always using constant-time comparison when checking tags.

Why isn’t hashing secret || message with SHA-256 directly as safe as HMAC?

Merkle–Damgård hashes such as SHA-256 are vulnerable to length-extension attacks: an attacker who knows H(secret || message) and the message length can compute H(secret || message || padding || extra) without knowing the secret. HMAC’s outer hash wraps the inner result, blocking length extension.

RFC 2104 / FIPS 198-1 defines HMAC(K, m) = H((K' XOR opad) || H((K' XOR ipad) || m)), where K' is K zero-padded to the hash block size B (64 bytes for SHA-256, 128 bytes for SHA-512) or hashed with H first if |K| > B, ipad = 0x36 repeated B times, and opad = 0x5c repeated B times. Bellare (2006) proved HMAC is a PRF when the underlying compression function is a dual-PRF, without requiring collision resistance. Key-handling subtleties include avoiding keys longer than B when key separation matters (since K and H(K) yield identical tags), bounding tag truncation per NIST SP 800-107 (typically keeping at least 128 bits), and noting that sponge hashes like SHA-3 have KMAC as a native alternative while still remaining valid inside HMAC.
