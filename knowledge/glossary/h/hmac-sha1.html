Guide / Glossary A–Z / Terms beginning with H / HMAC-SHA1

HMAC-SHA1 is a keyed message authentication code that pairs a secret key with the SHA-1 hash function to verify both data integrity and sender authenticity.

Imagine sealing an envelope with a special wax stamp that only you and your friend know how to make. HMAC-SHA1 creates a short digital stamp from a message and a shared secret key so the receiver can tell if the message was altered—though because SHA-1 is an older recipe, modern systems now prefer stronger versions like HMAC-SHA256.

You still encounter HMAC-SHA1 in legacy SSH configurations, Kerberos tickets, and TOTP/HOTP (RFC 4226/6238) authenticator tokens. Even though HMAC-SHA1 has not suffered the same practical collision breaks as plain SHA-1 (used for file checksums or certificates), OpenSSH and TLS disable or deprioritize it in favor of HMAC-SHA256 or AEAD ciphers such as AES-GCM and ChaCha20-Poly1305.

Why is HMAC-SHA1 still considered much safer than plain SHA-1, even though both are being phased out?

Plain SHA-1 has practical collision attacks because anyone can compute hashes freely, whereas HMAC’s double-hashed keyed construction resists collision attacks without knowing the secret key; however, modern protocols still migrate to SHA-256 or AEAD for long-term cryptographic margin.

Specified in RFC 2104, HMAC-SHA1 computes SHA1((K' XOR opad) || SHA1((K' XOR ipad) || m)), producing a 160-bit (20-byte) MAC tag using SHA-1’s 64-byte block size. While Bellare’s proof shows HMAC security relies on the compression function’s pseudorandomness (PRF) rather than SHA-1’s collision resistance—meaning chosen-prefix SHA-1 collisions do not directly forge HMAC-SHA1 tags—policy standards (NIST SP 800-131A, modern TLS 1.3, and OpenSSH defaults) deprecate it in favor of SHA-2/SHA-3 HMACs or Encrypt-then-MAC / AEAD constructions.
