Hypervisor

Software or firmware that creates and runs virtual machines on shared physical hardware.

A hypervisor divides one physical computer into separate virtual computers, much like splitting a building into locked apartments that share the same foundation. Each virtual machine can run its own operating system, and a crash or mistake inside one stays isolated from the others.

A hypervisor virtualizes CPU, memory, and devices so multiple guest operating systems can run simultaneously. Type 1 hypervisors (such as Linux KVM, Xen, or ESXi) run directly on the hardware or inside the host kernel, while Type 2 hypervisors (such as VirtualBox) run as normal applications on top of a host OS. On Linux, KVM pairs with QEMU to run full virtual machines, which differ from containers because each VM boots its own kernel.

Why can a hypervisor run Windows inside Linux, whereas a Linux container cannot?

A container shares the host’s Linux kernel and only isolates user-space processes, so it can only run binaries compatible with that kernel. A hypervisor virtualizes the hardware itself, allowing each virtual machine to boot and run an entirely separate operating system kernel.

A virtual machine monitor (VMM) leverages hardware virtualization extensions—Intel VT-x (VMX root/non-root operation) or AMD-V—to execute guest code natively while trapping privileged instructions via VM exits. Modern hypervisors use hardware-assisted two-dimensional paging (Intel EPT, AMD RVI/NPT) instead of software shadow page tables to cut TLB/page-fault exit overhead. Device I/O trades off compatibility against throughput across full device emulation, paravirtualized drivers (virtio), and IOMMU-isolated PCIe passthrough (VFIO) or SR-IOV. Memory overcommit (ballooning, KSM) and speculative-execution boundaries (L1TF, Spectre/MDS) require careful host scheduling and mitigation policies.
