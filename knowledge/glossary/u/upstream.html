Guide / Glossary A–Z / Terms beginning with U / Upstream

The original authors, repository, and release stream of a software project, before distributions or vendors adapt and package it.

Think of software like a river: code starts at the source—the original team that writes and maintains a program—and flows “downstream” to Linux distributions, app stores, and vendors that bundle it for you. Calling a project “upstream” simply means referring to those original creators. When a bug is fixed upstream, everyone downstream eventually benefits from the fix.

Distributions often apply downstream patches—to backport a security fix, adjust default paths, or work around a build issue—while waiting for the next upstream release. Because carrying downstream patches creates maintenance work on every upgrade, maintainers try to “upstream” fixes by submitting them back to the original project. When filing a bug report, checking whether the issue reproduces on an unmodified upstream build helps clarify where the fix belongs.

Why do Linux distributions prefer sending bug fixes upstream instead of keeping them as local patches forever?

Local patches must be rebased and re-tested on every new upstream version, and they only help users of that one distribution. Getting a fix accepted upstream eliminates ongoing merge conflicts and benefits the entire ecosystem.

In packaging and source-control workflows, “upstream” denotes the authoritative canonical repository and release tarball or tag stream from which downstream packaging branches, vendor forks, or LTS backport trees diverge. Maintainers track upstream via watch files or cryptographic source hashes, verifying release signatures (PGP/Sigstore) and distinguishing cherry-picked security backports from version bumps to preserve ABI stability within a release series. Conversely, “upstreaming” a patch means conforming to the original project’s coding standards, review process, and CLA/DCO requirements so the delta between downstream and upstream converges to zero.
