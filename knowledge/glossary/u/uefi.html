UEFI - Unified Extensible Firmware Interface

The modern platform firmware interface that initializes hardware when a computer powers on and hands control to an operating system bootloader.

When you press the power button, your operating system is not running yet—first, a small built-in program on the motherboard has to wake up the screen, memory, and storage drives. UEFI is the modern version of that startup firmware, replacing older BIOS screens with a smarter system that understands large disks, mouse-friendly setup menus, and security checks. Tamlinux boot teaching starts at this firmware step.

UEFI reads boot entries stored in motherboard NVRAM (inspectable from Linux with efibootmgr) and launches .efi applications—such as systemd-boot, GRUB, or a Unified Kernel Image—from a FAT32 EFI System Partition (ESP). When a machine fails to boot before Linux starts, clues usually live in UEFI setup menus, Secure Boot settings, and EFI variables rather than Linux logs.

Why does UEFI require the EFI System Partition to be formatted as FAT32 rather than ext4 or Btrfs?

Because the UEFI specification mandates a built-in FAT driver in platform firmware so any motherboard can read the bootloader directly without needing Linux filesystem drivers.

UEFI replaces 16-bit real-mode BIOS interrupts and 512-byte MBR boot sectors with a 32- or 64-bit execution environment, GUID Partition Table (GPT) parsing, and standardized Boot Services and Runtime Services tables. Across SEC, PEI, DXE, and BDS phases, firmware initializes memory and PCIe, verifies PE/COFF .efi binaries against PK/KEK/db/dbx keys when Secure Boot is enabled, and runs the Boot Manager (BootOrder/BootXXXX NVRAM variables, or fallback \EFI\BOOT\BOOTX64.EFI). Once the OS loader calls ExitBootServices(), Boot Services memory is reclaimed and only Runtime Services (clock, reset, and NVRAM access via /sys/firmware/efi/efivars) remain mapped.
