Unix signals (SIGINT, SIGTERM, SIGKILL, SIGSTOP, SIGQUIT, SIGTSTP, SIGPIPE)

Short notifications sent by the kernel or another process to interrupt, pause, or terminate a running program.

When a program is running in the background or stuck in a loop, you need a way to tap it on the shoulder—to ask it to save and quit, pause for a moment, or shut down immediately. Unix signals are those taps on the shoulder. Pressing Ctrl+C in a terminal, for example, sends a polite “please stop” signal, while a force-kill command tells the operating system to end the program on the spot.

Signals are identified by names starting with SIG and sent via terminal shortcuts or tools like kill and pkill. Common signals include SIGINT (Ctrl+C interrupt), SIGTERM (default polite termination), SIGKILL (immediate kernel termination), SIGSTOP (unblockable pause), SIGQUIT (Ctrl+\ quit with core dump), SIGTSTP (Ctrl+Z suspend), and SIGPIPE (broken pipe). Well-behaved services catch SIGTERM to flush buffers and remove lock files before exiting.

Why should you try SIGTERM before SIGKILL when stopping a stuck application?

A process can catch SIGTERM to flush open files, close database transactions, and clean up temporary state. SIGKILL cannot be caught or ignored—the kernel destroys the process immediately, which risks corrupting unsaved data.

POSIX signals (signal(7)) divide into standard signals (1–31, coalesced in a bitmask so duplicate pending signals are not queued) and real-time signals (SIGRTMIN–SIGRTMAX, queued in FIFO order with an optional sigval payload via sigqueue(3)). Processes install handlers with sigaction(2) and control per-thread delivery via pthread_sigmask(3); only SIGKILL and SIGSTOP cannot be caught, blocked, or ignored. Because signal handlers execute asynchronously on the interrupted thread’s stack, they may only call async-signal-safe functions—calling non-reentrant functions like malloc() or printf() risks deadlocks—so robust programs use signalfd(2) or a self-pipe to handle signals inside an event loop.
