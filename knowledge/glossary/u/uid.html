UID - User Identifier

The numeric ID that the operating system uses internally to identify a user account and check what it is allowed to access.

You log in with a name like alex, because names are easy for people to remember. Underneath, however, the system prefers numbers—much like a library card number or employee badge ID. Every file you save and every program you run is stamped with your user number so the system knows who owns it and whether you are allowed to open or change it.

On Linux, names in /etc/passwd map to numeric UIDs: UID 0 is always root, low numbers (typically 1–999) are reserved for system service accounts, and regular login accounts usually start at 1000. You can inspect your current UID with id -u and file ownership with ls -n. Because permissions are stored as numbers on disk, copying files across systems with mismatched UIDs can make files appear owned by the wrong user.

If you rename a user account in /etc/passwd without changing its UID, do that user’s existing files still belong to them?

Yes. Filesystems store numeric UIDs in each file’s inode, not the username string. As long as the UID stays the same, ownership and permissions remain intact and ls -l simply displays the new name.

In the Linux kernel, a process’s struct cred carries four UIDs: real (ruid), effective (euid, checked for most capability and DAC permission decisions), saved set-user-ID (suid), and filesystem UID (fsuid, used for VFS access checks so servers can drop file privileges without altering signal-delivery permissions). With user namespaces (user_namespaces(7)), an unprivileged UID inside a container (for example, 0) maps via /proc/pid/uid_map to an unprivileged host kuid_t, isolating root-equivalent capabilities to the namespace. Unmapped IDs surface as the overflow UID (commonly 65534), and POSIX ACLs or NFS root-squashing exports depend directly on consistent UID mapping.
