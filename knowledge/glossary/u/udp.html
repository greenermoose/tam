UDP - User Datagram Protocol

A lightweight, connectionless Internet transport protocol that sends self-contained messages (datagrams) without handshakes or delivery guarantees.

If TCP is like sending a tracked package where the driver waits for a signature and resends anything lost, UDP is like dropping postcards in a mailbox. There is no setup call beforehand and no receipt afterward—each message simply goes out as fast as possible. That makes UDP ideal for live voice calls, online games, and quick lookups where getting fresh data right away matters more than waiting to resend an old packet.

UDP adds only source and destination port numbers, a length field, and a checksum on top of IP, preserving message boundaries (one sendto() call produces one datagram, unlike TCP’s byte stream) with zero connection state or retransmission. On Linux, DNS queries, NTP time sync, WireGuard VPNs, and QUIC/HTTP/3 all run over UDP, and tools like ss -ulnp list listening UDP sockets.

Why do real-time voice calls and online games prefer UDP over TCP?

TCP’s head-of-line blocking pauses all later data until a lost packet is retransmitted, adding unacceptable latency; UDP lets the application drop stale packets and keep updating with the latest data.

Specified in RFC 768, UDP prepends an 8-byte header (source port, destination port, 16-bit length, 16-bit ones’-complement checksum over a pseudo-header and payload) to an IP packet; the checksum is optional in IPv4 (0 means omitted) but mandatory in IPv6. Because UDP provides no congestion control, ordering, or path-MTU discovery, protocols like QUIC (RFC 9000) and RTP/DTLS implement loss recovery, pacing, and congestion control in user space while clamping payloads to safe MTUs (e.g., ≤ 1200–1280 bytes) to avoid IP fragmentation. Statelessness also exposes unauthenticated UDP services to source-IP spoofing and amplification attacks unless guarded by cookies or rate limits.
