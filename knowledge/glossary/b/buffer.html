Buffer

A temporary holding area in memory where data waits while moving between parts of a system that work at different speeds.

Imagine pouring water from a fast pitcher into a narrow funnel: without the funnel holding some water for a moment, it would spill over. A buffer works the same way inside a computer—it is a short-term waiting area in memory that holds data briefly as it moves between a fast part (like memory) and a slower part (like a disk or network cable) so nothing gets lost or forced to stop and wait.

You encounter buffers across Linux: the kernel’s page cache buffers disk reads and writes so programs do not stall on physical storage for every byte, while shell pipelines (cmd1 | cmd2) use pipe buffers and C stdio uses line or block buffering. In text editors like Vim or Emacs, “buffer” also refers to the in-memory copy of a file you are editing before saving it to disk.

Why does grep output in a pipeline sometimes appear in big chunks instead of line by line?

When standard output goes to a terminal, C programs typically use line buffering (flushing on every newline). When piped to another command or file, stdio switches to block buffering (holding several kilobytes before flushing) for efficiency unless overridden with flags like --line-buffered.

Formally, a buffer is a bounded memory region—often implemented as a ring/circular buffer with producer and consumer indices, or scatter-gather iovec/DMA descriptor rings—providing decoupling, batching, and backpressure/flow control across user space, kernel space, and device memory. Key failure modes include buffer overflows (out-of-bounds writes past fixed stack or heap allocations), bufferbloat (oversized network queues inflating tail latency without improving throughput), and lost updates when dirty kernel page-cache buffers are not flushed via fsync(2) or fdatasync(2) before power loss.
