Bracketed paste

A terminal mode that wraps pasted text in special start and end markers so programs can tell pasted text apart from typed keystrokes.

If you copy several lines from a website and paste them into a terminal, the terminal normally sends those characters as if you typed them very fast—including any Enter keys, which can immediately run commands you did not mean to execute. Bracketed paste fixes this by placing invisible “paste starts here” and “paste ends here” markers around clipboard text. Your shell or editor sees those markers and holds the pasted block on screen so you can review it before pressing Enter.

Modern shells like Bash (5.1+, or with enable-bracketed-paste on in ~/.inputrc), Zsh, and editors like Vim/Neovim enable bracketed paste automatically, keeping multi-line pastes unexecuted until you confirm. By contrast, raw programs like cat do not enable it, and if a full-screen app crashes without turning the mode off, you may see literal ^[[200~ and ^[[201~ markers when pasting until you run reset.

Why can pasting a multi-line snippet into a shell without bracketed paste be dangerous?

Without bracketed paste, the shell cannot distinguish clipboard newlines from you pressing Enter, so every line before the last executes immediately—potentially running unintended or hidden commands from copied web text.

Defined by xterm as private mode DECSET 2004 (enabled via CSI ? 2004 h, disabled via CSI ? 2004 l), bracketed paste instructs the terminal emulator to wrap clipboard payloads in CSI 200 ~ (ESC [ 200 ~) and CSI 201 ~ (ESC [ 201 ~). Robust emulators must strip or neutralize embedded ESC [ 201 ~ sequences (and often ESC/0x03 control bytes) inside the pasted payload so untrusted clipboard data cannot prematurely close the bracket and inject commands; terminal multiplexers like tmux and screen must also track per-pane mode state to forward or emulate 2004 reliably.
