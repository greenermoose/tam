Boot

The process of starting a computer from power-on until the operating system is ready to use.

When you press the power button, a computer does not immediately know how to show your desktop or open files—its working memory starts empty. Booting is the step-by-step wake-up routine where a small built-in helper checks the hardware, finds the operating system on disk, and loads it into memory. It is called “booting” after the old phrase “pulling yourself up by your bootstraps,” because the computer uses a tiny initial program to load a bigger one.

On Linux, booting moves through distinct handoffs: firmware (UEFI or BIOS) initializes hardware, a bootloader loads the kernel and an initial RAM filesystem (initramfs), and the kernel mounts the real root filesystem before starting PID 1 (systemd or another init). Watching where a startup stalls tells you which layer failed—for example, a missing disk prompt before the LUKS passphrase points to initramfs or kernel drivers, whereas a hanging service happens later in user space.

Why does Linux often load an initramfs before mounting the real root filesystem?

The kernel image stays small and generic, so drivers needed to unlock encrypted disks, assemble RAID/LVM, or read specific filesystems may not be built directly into it. The initramfs is a tiny temporary root filesystem loaded into memory by the bootloader that supplies those modules and tools first.

On x86_64 UEFI systems, the firmware executes DXE drivers, reads EFI System Partition (ESP) boot variables (BootOrder, BootNext), and invokes an EFI binary (either a bootloader or a direct EFISTUB/UKI kernel image, optionally verified via Secure Boot PK/KEK/db). The kernel enters at its EFI handover or protected/long-mode entry point, decompresses itself, initializes memory management and ACPI/PCIe/device probing, unpacks the initramfs cpio archive into rootfs (tmpfs/ramfs), and executes /init. After switching root (switch_root / pivot_root) to the persistent root filesystem, PID 1 spawns user-space units; boot-time failures before journald flushes to persistent storage remain only in the kernel ring buffer (dmesg) or early console output.
