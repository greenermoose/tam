BS (Backspace, 0x08)

The ASCII control character 0x08 (Ctrl+H) that moves the terminal cursor one column to the left.

On an old typewriter, pressing backspace moved the carriage back one space so you could strike over a mistake. In terminals, BS (byte 0x08) is that same “step one space left” signal, which you can also send by pressing Ctrl+H. Confusingly, on many modern computers the Backspace key actually sends a different code (DEL, 0x7F) to erase the character behind the cursor, which is why Ctrl+H and Backspace sometimes behave differently in terminal apps.

Part of the C0 control codes, BS (0x08) often collides with Backspace keybindings because modern Linux terminals send DEL (0x7F) for the Backspace key while reserving Ctrl+H for 0x08. When a remote session or serial console prints ^H instead of deleting characters, the terminal’s stty erase setting disagrees with what your keyboard is sending; running stty erase ^H or matching your terminal’s Backspace mode fixes it.

Why does pressing Ctrl+H delete a character in your shell, yet in Emacs or Vim it might open help or move left?

Ctrl+H sends ASCII 0x08 (BS). Shells in line-editing mode often bind both 0x08 and 0x7F to backward-delete, whereas applications like Emacs reserve 0x08 (Ctrl+H) for help and expect the Backspace key to send 0x7F (DEL).

ASCII 0x08 (BS, Ctrl+H) is non-destructive on most video terminals: it moves the active cursor left by one column (stopping at column 1, or wrapping backward only if reverse-wraparound mode DECSET 45 is active) without clearing the cell—unlike DEL (0x7F), which the tty line discipline’s VERASE (termios.c_cc[VERASE]) typically maps to destructive rubout in canonical mode (ICANON). In terminfo, the kbs capability declares whether the Backspace key emits ^H or ^? (0x7F), and mismatches between kbs, emulator settings, and stty erase cause raw ^H/^? echoes or broken TUI keybindings; legacy troff/nroff pipelines also used char BS char overstriking for bolding and _ BS char for underlining.
