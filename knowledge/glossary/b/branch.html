Branch

A movable line of development in version control that lets you work on changes independently from the main history.

Imagine writing a book with a co-author: instead of both of you scribbling on the same draft at once, you make a side copy to test a new chapter while the main copy stays clean and readable. In version control, a branch works the same way—it gives you a separate workspace for a new feature or bug fix without breaking what already works. Once your changes are ready, you can merge them back into the main line.

In Git, switching branches with git switch updates your working directory in place rather than creating a separate folder, and making a new commit moves only the current branch pointer forward. If you check out a commit directly instead of a branch name, Git enters a “detached HEAD” state—any commits you make there are not attached to a branch and can be lost to garbage collection unless you create a branch for them.

Why is creating a branch in Git almost instant even on a huge repository?

A Git branch is just a tiny file (under .git/refs/heads/) holding a commit hash, not a full copy of all project files. Creating one only writes that single pointer.

In Git’s object model, a branch is a mutable reference under refs/heads/<name> storing the SHA-1 or SHA-256 object ID of a tip commit (or packed in .git/packed-refs), with HEAD typically holding a symbolic ref (ref: refs/heads/main). Unlike Subversion branches—which are directory copies inside the repository tree—Git branches are lightweight DAG pointers whose reachability governs git gc pruning; deleting a branch only removes the ref, leaving commits recoverable via reflogs (logs/refs/heads/...) until expiration. Multiple checked-out working directories can also share one object store when parallel edits are needed without switching branches in place.
