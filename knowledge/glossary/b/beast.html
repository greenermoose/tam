BEAST (Browser Exploit Against SSL/TLS)

A 2011 cryptographic attack against TLS 1.0 that exploited predictable initialization vectors in CBC-mode encryption.

When a browser encrypts web traffic in blocks, each block is mixed with the previous one so identical messages don’t look identical. In old TLS 1.0 connections, the starting value (IV) for a new message was predictable—it was just the last piece of the previous message. BEAST showed that an attacker running malicious JavaScript in a browser could guess secret cookies bit by bit by watching how the encrypted blocks changed.

BEAST (Browser Exploit Against SSL/TLS) was a chosen-plaintext attack against CBC-mode cipher suites in TLS 1.0 (notably affecting HTTP session cookies). Mitigations initially included browser-side 1/n-1 record splitting and switching to RC4 (which later proved broken for other reasons), before the ecosystem moved to TLS 1.1+ (explicit random IVs per record) and TLS 1.2/1.3 AEAD ciphers like AES-GCM and ChaCha20-Poly1305.

Why did upgrading from TLS 1.0 to TLS 1.1 stop BEAST even when CBC mode was still used?

TLS 1.1 replaced TLS 1.0’s chained IV (reusing the previous record’s last ciphertext block) with an explicit, unpredictable random IV for every record, preventing the attacker from predicting the next IV before choosing plaintext.

BEAST is a blockwise adaptive chosen-plaintext attack targeting CBC mode’s C_i = E_K(P_i ⊕ C_{i-1}) when IV_{next} = C_{last} is known prior to plaintext submission. By controlling plaintext alignment across a known prefix and a target secret byte (via cross-origin JavaScript/WebSocket requests) and XORing a guess with C_{last} ⊕ C_{target-1}, an attacker verifies the guess by checking whether C_i == C_{target}. TLS 1.1 (RFC 4346) eliminated the oracle via per-record explicit IVs, and TLS 1.3 (RFC 8446) removed CBC cipher suites altogether in favor of AEAD constructions.
