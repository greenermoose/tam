Block device

A block device is a storage device or kernel abstraction that reads and writes data in fixed-size chunks (blocks) at arbitrary addresses.

Think of a block device like a warehouse full of numbered, equal-sized storage boxes: you can jump straight to box #402 to read or replace what is inside without unpacking boxes #1 through #401. Hard drives, SSDs, USB sticks, and disk partitions work this way, unlike a keyboard or serial port (character devices) where data arrives one byte at a time in order.

In Linux, block devices appear under /dev (such as /dev/nvme0n1, /dev/sda1, or /dev/dm-0) with type b in ls -l, and you can inspect their hierarchy, sizes, and sector alignment with lsblk. Unlike character devices, block devices support random seeking, kernel page-cache buffering, and mounting filesystems. Logical layers like LVM, LUKS (dm-crypt), and loop devices (/dev/loop0) also present themselves as block devices so filesystems treat them identically to physical disks.

Why can you mount a filesystem on a block device like /dev/sda1 but not on a character device like /dev/ttyS0?

A filesystem needs random access to jump directly to superblocks, inodes, and directory blocks at arbitrary offsets; block devices support fixed-size random-access I/O and page-cache buffering, whereas character devices only stream bytes sequentially.

In the Linux kernel, block devices are represented by struct block_device and struct gendisk, identified by major/minor numbers and accessed through the multi-queue block layer (blk-mq), which maps per-CPU software submission queues to hardware dispatch queues. I/O requests are encapsulated in struct bio and scheduled (e.g., mq-deadline, bfq, kyber, or none for NVMe) before reaching the driver. Writes are typically buffered through the kernel page cache unless opened with O_DIRECT or flushed via fsync()/BLKFLSBUF, and misaligned I/O relative to physical sector size (e.g., 512e vs. 4Kn) triggers costly read-modify-write cycles in drive firmware.
