BREACH

A side-channel attack that recovers secrets from encrypted HTTPS traffic by exploiting HTTP response compression.

Even when a website uses HTTPS encryption to scramble its messages, the encrypted package still has roughly the same size as the original page. Compression shrinks repeated text—so if an attacker can trick a page into echoing a word they guessed right next to a hidden secret (like a security token), the compressed page becomes slightly smaller when their guess matches part of the secret. By sending many guesses and measuring tiny size differences, BREACH can uncover the secret one character at a time without breaking the encryption.

BREACH differs from the earlier CRIME attack: CRIME targeted TLS-level compression (which TLS 1.3 removed completely), whereas BREACH exploits application-level HTTP compression (such as gzip or br/Brotli) that browsers and servers still use widely. An endpoint is only vulnerable if three conditions hold together: HTTP compression is enabled, the response reflects attacker-controlled input (like a query parameter), and the same response contains a secret (like a CSRF token).

Why didn’t disabling TLS compression in TLS 1.3 stop BREACH?

TLS 1.3 only removed compression at the TLS transport layer. BREACH targets HTTP-layer compression (like gzip or Brotli) applied to the response body before TLS encrypts it, so the compressed length still leaks through the encrypted record size.

BREACH (Browser Reconnaissance and Exfiltration via Adaptive Compression of Hypertext) exploits LZ77 sliding-window back-references in DEFLATE/gzip or Brotli: when attacker-controlled input and a secret co-occur within the 32 KiB LZ77 window, a matching prefix reduces output bit length, observable via TLS ciphertext record sizes (even with AEAD ciphers, which preserve plaintext length modulo padding). Effective mitigations include randomizing secrets per request (e.g., XOR-masking CSRF tokens with a per-response pad), disabling HTTP compression for responses containing secrets, separating user input from secret-bearing endpoints, or length-hiding padding; TLS 1.3 record padding adds overhead and is rarely configured to defeat adaptive compression queries on its own.
