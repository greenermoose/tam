Guide / Glossary A–Z / Terms beginning with P / Package

A package is a named, versioned bundle of software and metadata that a package manager can install, update, and remove.

Think of a package as a labeled shipping box containing a program, its helper files, and instructions for where everything belongs. Instead of you placing dozens of files by hand, the system’s software manager opens the box and tracks what is inside. On Tamlinux you may meet native Arch packages and Nix-built Tamlinux assemblies, so asking which manager owns a file is safer than guessing.

A package manager tracks each package’s files and version, but the command you actually run still depends on your shell’s PATH and any wrapper scripts. Development installs under ~/.local can shadow packaged binaries, so tools like which or type -a help confirm which copy is active. See package versions for how versions are tracked.

If you upgrade a package while the program is already running, does the running process automatically switch to the new version?

No. The running process keeps executing the code already mapped into memory and continues using any unlinked shared libraries until it restarts, even though the package manager has replaced the files on disk.

A package identity (name, epoch/version/release, architecture, or store hash) is distinct from a running process and from an assembly pin. Traditional binary packages bundle a compiled payload, manifest, and maintainer scripts into an archive (e.g., .pkg.tar.zst, .deb, .rpm), whereas functional packages derive immutable outputs from build inputs and hash-indexed paths. Recovery should name the owning manager, immutable outputs, and any mutable state; deployed Tamlinux software should arrive through a recorded assembly rather than an untracked copy from a checkout.
