Guide / Glossary A–Z / Terms beginning with P / PKCE (Proof Key for Code Exchange)

An OAuth 2.0 and OpenID Connect extension that prevents attackers from intercepting and reusing an authorization code.

When you click “Sign in” in an app, it often hands you off to a web browser and then receives a one-time pass back. Without extra protection, another app on your phone or computer could eavesdrop on that return message and steal the pass. PKCE works like a secret claim ticket: the app invents a random secret before you log in, sends a scrambled version to the login server, and later proves it knows the original secret before it can trade the pass for access.

Mobile, desktop, and CLI apps are “public clients” that cannot safely embed a static client_secret because anyone can inspect the binary or script. PKCE replaces that static secret with a fresh per-login SHA-256 challenge so only the process that started the login flow can redeem the authorization code. Current OAuth 2.1 best practices require PKCE with the S256 method for public clients and recommend it for confidential server clients too.

Why is sending a SHA-256 hash (S256) safer than sending the secret itself (plain)?

An attacker who intercepts the initial browser redirect only sees the one-way hash, not the original verifier, so they cannot impersonate the app at the token endpoint.

Defined in IETF RFC 7636, the client generates a high-entropy code_verifier (43–128 characters from the unreserved URI set [A-Za-z0-9-._~], providing at least 256 bits of entropy) and sends code_challenge = BASE64URL(SHA256(ASCII(code_verifier))) with code_challenge_method=S256 on the authorization request. At the token endpoint, the authorization server recomputes the digest and rejects mismatched verifiers, mitigating custom-URI-scheme hijacking and authorization-code injection. PKCE pairs orthogonally with state (CSRF protection) and OIDC nonce (ID-token replay protection).
