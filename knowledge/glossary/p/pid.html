Guide / Glossary A–Z / Terms beginning with P / PID (Process Identifier)

A PID (Process Identifier) is a positive integer assigned by the operating system kernel to identify a running process.

Just as a busy restaurant gives each order a ticket number so the kitchen does not mix up two identical burgers, Linux gives every running program its own number called a PID. Even if you open three terminal windows at once, each one gets a different PID so you can check on or stop a specific one without affecting the others.

On Linux, PID 1 is the init system (such as systemd), and commands like ps, pgrep, top, and kill use PIDs to inspect or signal processes. Crucially, PIDs are temporary: once a process exits and is reaped by its parent, the kernel can eventually reuse that number for a new process. PIDs are also scoped to a PID namespace, so a container’s main process can appear as PID 1 inside the container while holding a different PID on the host.

Why is it unsafe for a script to check whether a PID exists and then run kill on that PID a moment later?

Because PIDs can be reused after a process exits. In the gap between checking and signaling, the original process may terminate and an unrelated process may be assigned the same PID.

In Linux, each task’s pid_t is resolved per PID namespace (a single struct pid maps to distinct numeric IDs across nested namespaces), bounded by kernel.pid_max. Checking /proc/<pid> or kill(pid, 0) before signaling suffers from classic TOCTOU PID-reuse races; modern Linux avoids this with pidfd_open(), pidfd_send_signal(), and CLONE_PIDFD, which bind a file descriptor to the underlying struct pid lifecycle. Note also that userspace “PID” corresponds to the kernel Thread Group ID (TGID), while individual threads have distinct kernel TIDs.
