PEM (Privacy-Enhanced Mail format)

PEM is a plain-text encoding format for cryptographic certificates, keys, and requests that wraps binary data in Base64 between -----BEGIN ...----- and -----END ...----- header lines.

Cryptographic keys and website certificates are naturally compact binary files that look like gibberish in a text editor and can break if pasted into emails or config files. PEM solves this by converting the binary data into ordinary letters and numbers and framing it with clear -----BEGIN ...----- and -----END ...----- labels so both people and programs can tell what is inside.

On Linux, PEM data commonly appears in .pem, .crt, or .key files under /etc/ssl/certs/ or ~/.ssh/. Because it is plain text, you can concatenate a server certificate and intermediate CA certificates into one bundle file, or inspect a file with openssl x509 -in cert.pem -text -noout. Contrast PEM with DER, which is the raw binary form of the same data.

Why can you inspect a .pem file in a text editor and combine a certificate chain in one file, while .der cannot?

PEM encodes binary ASN.1 DER objects as Base64 ASCII text with explicit BEGIN and END boundary markers, making it safe for text editors and allowing multiple blocks to be concatenated sequentially, whereas DER is raw binary.

Standardized by RFC 7468 (superseding legacy RFC 1421–1424 Privacy-Enhanced Mail), a PEM block wraps a Base64-encoded ASN.1 DER payload (wrapped at 64 characters) in matching encapsulation boundaries. Labels disambiguate the ASN.1 schema: CERTIFICATE (X.509), PRIVATE KEY (unencrypted PKCS#8), ENCRYPTED PRIVATE KEY (PKCS#8 with PBES2), RSA PRIVATE KEY (legacy PKCS#1), and CERTIFICATE REQUEST (PKCS#10 CSR). Common failure modes include CRLF vs. LF line endings, trailing whitespace, mismatched labels, and accidentally committing unencrypted PKCS#8 keys because they look like plain text.
