Pull request

A pull request (PR)—called a merge request on some platforms—is a formal proposal on a code-hosting forge to merge commits from one branch into another after review and automated checks.

Imagine writing a new chapter for a shared book on your own copy of the manuscript, then handing it to the editors and saying, “Please check this over and, if it looks good, fold it into the main book.” A pull request does that for software projects: it shows everyone exactly which lines you changed, gives teammates a place to leave comments, and lets maintainers approve the work before it becomes part of the main codebase.

Unlike git merge, which is a local Git command, a pull request is a collaboration workflow on platforms like GitHub, GitLab, or Codeberg. It links a source branch (in the same repo or a fork) to a target branch (such as main), runs continuous-integration (CI) tests, and records review approvals before performing a merge commit, squash merge, or rebase merge. Pushing new commits to the source branch automatically updates the open pull request.

Check: if you open a pull request from your feature branch and a reviewer asks for a small fix, do you need to close it and open a new PR?

No. A pull request tracks the branch reference, so committing the fix and pushing to that same source branch updates the existing PR and re-triggers its checks while preserving the review history.

At the repository level, a pull request is forge metadata binding a base ref, a head ref (often mirrored into read-only server refs such as GitHub’s refs/pull/N/head and speculative refs/pull/N/merge), review states, and required status checks. Merge strategies carry distinct trade-offs: true merge commits preserve branch topology and exact commit hashes; squash merges keep target history linear at the cost of collapsing attribution/bisect granularity; rebase merges preserve linear per-commit history but rewrite commit SHAs, invalidating local clones unless force-pushed with --force-with-lease. In public-fork workflows, CI pipelines must isolate secrets from untrusted PR head code (e.g., avoiding privileged pull_request_target execution on untrusted diffs).
