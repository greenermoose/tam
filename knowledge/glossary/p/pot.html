Pot

In the Tamlinux plant analogy, a pot is the environment that starts or contains a system.

Just as a plant needs a pot to hold its soil and support it, a bootable system needs an outer environment to start it up or hold it in place. In everyday terms, it is whatever sits around the system to get it running.

Depending on context, the analogy can refer to firmware, a boot loader, or a virtual machine envelope. Keeping these roles distinct matters when troubleshooting: firmware initializes hardware, a boot loader hands off to a kernel, and a virtual machine isolates a guest from the host.

Why is it risky to treat a boot loader and a virtual machine as the same kind of “pot” when debugging a startup failure?

They have different failure boundaries: a boot loader runs directly on physical hardware before the OS starts, whereas a virtual machine runs inside a host OS and hypervisor that mediate hardware access and logs.

A conceptual boot or containment role spanning mechanisms with incompatible trust boundaries and interfaces: UEFI firmware (PEI/DXE phases and Secure Boot variable stores), stage-2 boot loaders (reading ESP or /boot), and VMM/hypervisor isolation (guest-host memory and virtio device boundaries). Treat the analogy as orientation only; diagnosing failures requires identifying the exact boundary enforcing control or isolation.
