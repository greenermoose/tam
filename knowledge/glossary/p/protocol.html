Protocol

A protocol is an agreed set of rules that defines how two or more programs, devices, or people exchange information.

Think of a protocol like the rules of a phone call: one person says “Hello,” both take turns speaking, and they agree on a language so neither misunderstands the other. Computers need the same kind of agreement—for example, how to start a conversation, how to ask for a web page, and how to say goodbye—so software written by different people can still work together.

In networking and Linux systems, protocols are layered so each layer solves one job: Ethernet or Wi-Fi moves frames on a local link, IP routes packets across networks, TCP ensures reliable ordered delivery, and HTTP or SSH defines the application messages on top. If either side uses the wrong protocol or port (for instance, speaking plain HTTP to an HTTPS-only server), the connection fails cleanly rather than guessing.

Check: if two programs can reach each other over TCP on port 443, why might their communication still fail?

TCP only guarantees an ordered byte stream; both sides must also agree on the higher-layer protocols—such as TLS versions/ciphers and HTTP/1.1 vs. HTTP/2—or they will not be able to parse each other’s messages.

A communications protocol specifies syntax (wire framing, field encodings, endianness), semantics (the meaning of headers, opcodes, and status codes), and timing/state-machine transitions (handshakes, flow control, retransmissions, and teardown). Protocols are typically versioned and negotiated—either explicitly (TLS ClientHello extensions, ALPN) or via capability discovery—and must handle partial reads, out-of-order delivery, or hostile inputs without state desynchronization. Ambiguities in specification (such as HTTP/1.1 request smuggling via conflicting Content-Length and Transfer-Encoding headers) are a recurring source of interoperability bugs and security vulnerabilities.
