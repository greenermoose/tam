Process

A process is a running instance of a program.

If a program saved on your drive is like a recipe in a book, a process is the act of actually cooking it. Every running process gets its own ID number (PID). Opening two separate windows of the same app means one program on disk is running as two separate processes.

Each process has its own isolated memory, open files, user credentials, and working directory; a shell pipeline like grep foo file | sort starts multiple processes at once. You can inspect processes with ps or top, and control ones you own using signals and job control; see jobs.

If you run the same text editor twice as two separate processes, why doesn’t a crash in one necessarily crash the other?

The kernel gives each process its own isolated virtual address space and execution state, so memory corruption or a fatal signal in one process cannot overwrite the other’s memory.

A kernel-managed execution and resource context (task_struct / thread group), possibly containing multiple threads sharing an address space (mm_struct) and file descriptor table (files_struct). Inspect PID/TGID, credentials, namespaces, cgroup membership, and descriptors rather than equating an executable path with a running instance—PID reuse, zombie (Z) states awaiting waitpid, and uninterruptible sleep (D) mean existence checks are not health checks.
