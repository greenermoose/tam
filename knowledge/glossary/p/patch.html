Patch

A patch is a targeted set of changes applied to software source code or binaries to fix a bug, close a security hole, or add a feature.

Just as a fabric patch mends a tear without replacing the whole jacket, a software patch updates only the lines of a program that need fixing. Developers share patches so they can review exact edits, fix problems quickly, and keep software safe without rewriting everything from scratch.

In Linux and open-source development, a patch is usually a unified diff text file (created with diff -u or git format-patch) showing removed lines prefixed with -, added lines prefixed with +, and a few surrounding lines of context. Linux distributions often carry small patches on top of upstream source tarballs to backport security fixes without upgrading to a whole new version. You apply them with patch or git apply, and if the surrounding code has changed, the tool reports a conflict (.rej file) to resolve manually.

Why do Linux distributions often apply a small security patch to an older package instead of just upgrading to the newest upstream release?

A new upstream release may introduce breaking changes, new dependencies, or behavioral shifts. Backporting a minimal patch fixes the vulnerability while keeping the rest of the software stable and compatible for existing users.

A unified diff patch encodes line-oriented hunks (@@ -start,count +start,count @@) with configurable context lines so patch(1) or git apply can locate target regions even when line numbers shift (fuzzing/offset matching). Beyond source-level text deltas, binary diff tools (e.g., bsdiff) emit compact byte-level deltas for executables and firmware, while Linux kernel live-patching (kpatch / CONFIG_LIVEPATCH) uses ftrace redirection at function entry points to swap patched functions into a running kernel without rebooting—requiring careful handling of data-structure layout changes and per-task consistency models.
