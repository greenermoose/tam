Pin

To pin software is to lock a package, dependency, or input to an exact version or revision so that updates do not change it unexpectedly.

When you install software, it normally grabs the newest version available, which can occasionally change how something works or break a setup that was already working fine. Pinning is like putting a bookmark on one exact edition—telling your system, “Keep using this specific version until I say otherwise.”

Pinning appears across package managers and developer workflows: lockfiles (Cargo.lock, package-lock.json, flake.lock) pin full dependency trees, container images can be pinned by cryptographic digest (@sha256:...) instead of a mutable tag like :latest, and distro tools like apt or pacman support holding or ignoring packages. Pinning improves reproducibility and avoids surprise regressions, though stale pins can block security updates.

Why is pinning a container image by @sha256:... digest stronger than pinning by a tag like :1.2?

Tags are mutable labels that a maintainer can overwrite with a new build at any time, whereas a SHA-256 digest uniquely identifies the exact immutable content of that image.

Pinning spans range constraints in manifests to cryptographic content-addressed pins in lockfiles (such as Nix NAR hashes in flake.lock, crate checksums in Cargo.lock, or OCI manifest digests). Strict pinning makes builds deterministic and auditable across hosts, at the cost of dependency-solver conflicts when transitive requirements diverge and security-patch lag if pins are not routinely refreshed. Pins also fail to guarantee reproducibility if paired with impure build steps that fetch unverified network inputs.
