Guide / Glossary A–Z / Terms beginning with O / OAuth (Open Authorization)

OAuth (Open Authorization) lets an app use another service on your behalf without learning your password. It is a standard for authorization, which grants limited access; OIDC adds a way to prove who you are.

Think of a valet key for a car. It lets a parking attendant drive the car, but it does not open the house or start every door in the building. If you let a printing app fetch your photos, OAuth lets the photo service give the app a limited pass. The app can read the photos you allow, but it never receives your password. You can take that pass away later.

OAuth began in 2006, when developers around Twitter and the social bookmarking site Ma.gnolia wanted one open way for a service to grant access to another app. There was no shared standard, so they drafted one in 2007. OAuth Core 1.0 appeared in December 2007 and was revised as 1.0a in June 2009 after a session-fixation flaw was found.

The main split between the two versions is how an app proves it may use a token. OAuth 1.0 signs every protected request with a secret known to the app. OAuth 2.0 usually sends a bearer token over an encrypted connection; whoever holds the token can use it. That makes OAuth 2.0 easier for app writers, but a stolen token can be used until it expires or is revoked. The two versions are not compatible.

What problem did OAuth solve?

It let a user grant limited access to an app without handing over the password to the user's account on another service. The service gives the app a scoped token instead, which can be revoked later.

The IETF published OAuth 1.0 as informational RFC 5849 in April 2010. A client first obtained a request token, sent the user to authorize it, then exchanged it for an access token. Protected requests carried an oauth_signature made with HMAC-SHA1, RSA-SHA1 or, only over a protected channel, PLAINTEXT. Version 1.0a added an authorization verifier to close a session-fixation weakness.

OAuth 2.0, published as standards-track RFC 6749 in October 2012, replaces OAuth 1.0 but is not backward compatible. An authorization server issues an access token after an authorization grant such as the Authorization Code flow, the Client Credentials flow or the Device Authorization flow. Refresh tokens let a client obtain a new access token without asking the user again. Tokens are often bearer tokens described by RFC 6750 and sent in the HTTP Authorization header, so TLS, short lifetimes, audience checks and revocation matter more than request signatures. Token format and use are split into separate specifications; PKCE and other extensions protect particular client types. OIDC adds the openid scope and a signed ID token for authentication. OAuth 2.1 is an in-progress effort to consolidate OAuth 2.0, bearer tokens, PKCE, native-app and browser-app guidance, and security best practice. OAuth is often expanded as Open Authorization, although the standards themselves use the name OAuth.
