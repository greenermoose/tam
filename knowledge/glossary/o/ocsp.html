OCSP (Online Certificate Status Protocol)

A network protocol for checking whether an X.509 TLS certificate has been revoked before its scheduled expiration date.

Even if a website’s security certificate has not expired yet, it might need to be canceled early—for example, if the site’s private key was stolen. OCSP is how your browser asks the certificate issuer, “Is this certificate still valid right now?” so you do not trust a compromised site.

Classic OCSP has two major drawbacks: your browser leaks which sites you visit to the Certificate Authority (CA), and if the CA’s OCSP responder is slow or unreachable, connections stall or silently fail open (“soft-fail”). OCSP stapling fixes both issues by having the web server fetch a signed, time-stamped OCSP response from the CA and attach (“staple”) it directly inside the TLS handshake—improving speed and protecting user privacy.

How does OCSP stapling protect user privacy compared to standard OCSP?

In standard OCSP, the client contacts the Certificate Authority directly during connection setup, revealing which domain the user is visiting. With OCSP stapling, the web server fetches and caches the CA’s signed status proof and sends it inside the TLS handshake, so the CA never sees individual client IPs.

Defined in RFC 6960 over HTTP, OCSP returns signed responses (good, revoked, or unknown) keyed by certificate serial number and issuer hashes, with thisUpdate/nextUpdate validity windows. Because browsers historically soft-failed on OCSP timeouts (making active revocation checks bypassable by an on-path attacker blocking the responder) and Must-Staple (RFC 7633 TLS Feature extension) saw fragile operational adoption, major browsers and CAs have largely deprecated live OCSP queries in favor of compressed, locally pushed revocation lists such as Mozilla’s CRLite and Chrome’s CRLSets, paired with short-lived certificates.
