Guide / Glossary A–Z / Terms beginning with O / OIDC (OpenID Connect)

OIDC (OpenID Connect) is an identity layer built on top of OAuth 2.0 that lets applications verify who a user is using signed identity tokens.

When you click a “Sign in with …” button on a website, OpenID Connect is usually what makes it work behind the scenes. Instead of creating a brand-new password for every site, you log in with a provider you already trust, and that provider hands the site a tamper-proof digital ID card confirming who you are. The site gets to know it is really you, without ever seeing your password.

People often confuse OAuth 2.0 and OIDC, because OIDC runs on top of OAuth 2.0. Plain OAuth 2.0 handles authorization—issuing an Access Token that says “this app may read alex’s files”—without defining a standard way to prove who alex is. OIDC adds authentication via the openid scope, returning a signed ID Token (a JSON Web Token) and a /userinfo endpoint. In Linux and cloud environments, OIDC is widely used for single sign-on (SSO) to web dashboards, Git forges, and Kubernetes clusters.

How does OIDC differ from plain OAuth 2.0?

OAuth 2.0 only grants an app permission to access resources (authorization) using an Access Token. OIDC adds a standardized identity layer (authentication) on top, issuing a signed ID Token that tells the client who the user actually is.

OpenID Connect Core 1.0 extends OAuth 2.0 (RFC 6749), with Authorization Code Flow plus PKCE (RFC 7636) recommended for both confidential and public clients to prevent authorization-code interception. The ID Token is a JWS-signed (RFC 7515) JWT carrying standard claims (iss, sub, aud, exp, iat, and nonce for replay protection), discovered via /.well-known/openid-configuration and verified against rotating public keys at jwks_uri (RFC 7517). Common implementation vulnerabilities include accepting alg=none or key-confusion attacks, failing to validate aud/iss/nonce, and mistakenly treating an Access Token as an ID Token or vice versa.
