OPA (Open Policy Agent)

OPA (Open Policy Agent) is a general-purpose policy engine that evaluates authorization and compliance rules written in a declarative language called Rego.

Normally, permission rules like “only admins can delete backups” are buried inside each program’s code, so changing a rule means editing and rebuilding every app. OPA moves those rules into one dedicated decision-maker—like a central rulebook clerk that any app can ask, “Is alex allowed to do this right now?” That keeps security rules consistent and easy to update in one place.

In Policy-Based Access Control (PBAC), OPA acts as a decoupled Policy Decision Point (PDP) alongside a Policy Enforcement Point (PEP) such as an API gateway, Envoy proxy, or Kubernetes admission controller. The PEP sends OPA a JSON request describing the actor, action, and resource; OPA evaluates Rego rules against that input and any loaded context data, then returns a decision (such as allow/deny or structured obligations). Because Rego policies are plain text, teams can version-control them and run unit tests with opa test just like application code.

What is the practical benefit of separating OPA (the PDP) from the application or proxy (the PEP)?

Multiple services can share one auditable, version-controlled policy language (Rego) without duplicating authorization logic in different programming languages or redeploying applications just to update a rule.

A CNCF graduated project, OPA evaluates Datalog-inspired, declarative Rego policies over hierarchical JSON data models with built-in support for partial evaluation and WebAssembly compilation (opa build -t wasm). Deployment architectures trade off data freshness against latency: running OPA as a sidecar or daemon over HTTP/gRPC centralizes bundle updates and decision logging at the cost of IPC serialization overhead, whereas embedding compiled Wasm or the Go SDK eliminates network hops but requires propagating external state into the host runtime. Policy authors must also account for Rego’s closed-world assumption, set-unification semantics, and indexability so large rule sets evaluate in bounded time.
