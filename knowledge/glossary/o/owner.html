Owner

An owner is the user account recorded as responsible for a file, directory, or other stored resource.

Think of ownership like a name tag on a locker or a notebook at school. Every file on your computer has an owner—usually the person who created it—so the system knows whose rules to check first when someone tries to open, change, or delete it. Keeping track of ownership helps stop people from accidentally erasing someone else’s work or changing important system settings.

In Linux, every file records both a user owner and a group owner, which you can inspect with ls -l and change with chown. When a process opens a file, the kernel checks the user-owner permission bits only if the process’s user matches the file’s owner; otherwise it checks group or other bits. Creating a file with sudo assigns ownership to root, which is why running commands as an administrator inside your home directory can leave behind files that alex cannot later edit.

If a file has permissions -rw------- owned by alex, can a user in the file’s group read it?

No. Because the group and other permission bits are all unset (---), only the user owner alex (or a privileged process) has read and write access; group membership only grants the group’s permission bits, not the owner’s.

On POSIX filesystems, the inode stores numeric uid_t and gid_t identifiers (i_uid, i_gid in Linux’s VFS), not usernames; name resolution happens in user space via NSS. Access checks compare the process’s effective UID (euid) and filesystem UID (fsuid) against i_uid, falling through to i_gid/supplementary groups or the other class, and never grant “owner” rights if the owner’s own mode bits deny them (e.g., mode 0000, unless bypassed by CAP_DAC_OVERRIDE or CAP_DAC_READ_SEARCH). On FUSE, FAT/exFAT, or UID-mapped mounts (idmapped mounts), ownership may be synthesized or translated at the mount boundary, and POSIX ACLs or LSMs (SELinux, AppArmor) can further restrict an owner.
