Fork

A personal copy of someone else’s code repository that lets you experiment and propose changes independently.

Suppose you find an open-source recipe book online and want to tweak a few ingredients without messing up the original author’s version. A fork gives you your own complete copy of that project under your account, where you are free to make edits—and later ask the original author if they want to pull your improvements back in.

On Git hosting platforms, a fork creates a server-side copy of a repository under your namespace while preserving its commit history. In a typical workflow, you clone your fork as origin, add the original project as a second remote called upstream, commit changes on a branch in your fork, and open a pull request back to upstream. Unlike a branch inside the same repository, a fork works even without write permission to the original repo.

Why do contributors fork a repository instead of just creating a new branch directly in the original repository?

Because external contributors usually lack write permissions to push branches to the upstream repository. Forking gives them a copy under their own account where they have full push access to prepare a pull request.

A server-side Git fork duplicates refs (refs/heads/*, refs/tags/*) into an isolated repository namespace with independent access control, often sharing immutable packfile objects on the host via Git alternates (objects/info/alternates) to avoid storage duplication. Because a fork is a distinct repository rather than a shared branch namespace, its default branch diverges unless explicitly fast-forwarded or rebased from upstream; stale forks are a frequent source of merge conflicts in pull requests. Note also the distinct POSIX fork(2) system call, which clones a running process’s address space using copy-on-write page tables.
