Filter

A command-line program that reads text from standard input, selects or transforms it, and writes the result to standard output.

A filter in the terminal works like a coffee filter or a kitchen sieve: data pours in the top, unwanted parts are held back or reshaped, and only the useful output comes out the bottom. Because filters don’t care where the text came from, you can snap them together like building blocks to clean up messy files or logs.

Classic Unix filters—such as grep (keep matching lines), sort (order lines), uniq (drop adjacent duplicates), cut (pick columns), and sed/awk (rewrite text)—read stdin and write stdout so they chain naturally with pipes (|), as in grep ERROR app.log | sort | uniq -c. Notice that uniq only collapses adjacent duplicates, which is why it almost always follows sort.

Why do filters like grep print error messages to the terminal even when you redirect standard output (> results.txt)?

Well-behaved filters write normal transformed data to standard output (fd 1) and diagnostic or error messages to standard error (fd 2). Redirecting > only captures fd 1, keeping error messages visible instead of corrupting your output file.

A POSIX filter is a stream-oriented process whose composition semantics depend on stdio buffering, exit status, and channel separation (stdout vs. stderr). Standard C FILE* streams switch from line-buffered (on a TTY) to block-buffered (typically 4–8 KiB when connected to a pipe), which can stall real-time tail -f | grep | awk pipelines unless --line-buffered or stdbuf -oL is used. In a shell pipeline, $? reports only the final stage’s exit status unless set -o pipefail is enabled, and upstream filters can terminate early via SIGPIPE when a downstream consumer like head -n 10 closes its read end.
