Flow Control

A mechanism that lets a receiver pause or pace a sender so incoming data does not overflow its buffers.

Think of two people pouring water from a pitcher into a funnel: if the person pouring goes faster than the funnel can drain, water spills over the side. Flow control is the signal the receiving device sends back to say “slow down, my bucket is nearly full,” keeping data from being dropped or lost.

Flow control appears at multiple layers in Linux and networking. On serial lines, hardware flow control uses dedicated RTS/CTS pins for immediate pauses, whereas software flow control injects special ASCII bytes (XOFF / Ctrl-S to pause, XON / Ctrl-Q to resume) into the data stream—which is why pressing Ctrl-S in some terminals appears to freeze output until you press Ctrl-Q. Over networks, TCP uses a sliding receive window to pace the sender.

Why can software flow control (XON/XOFF) corrupt binary file transfers over a serial link if not disabled?

Because XON (0x11) and XOFF (0x13) are ordinary byte values sent inside the same data stream as the payload. If a binary file naturally contains byte 0x13, the receiver misinterprets it as a pause command or strips it, stalling or corrupting the transfer.

Flow control regulates sender rate against receiver buffer capacity (distinct from congestion control, which reacts to bottlenecked intermediate links). In asynchronous UARTs (termios CRTSCTS vs. IXON/IXOFF), hardware RTS/CTS gates the transmitter FIFO within character-time latency, preventing RX FIFO overrun errors without in-band byte escaping. In TCP (RFC 9293), the receiver advertises RCV.WND scaled by the Window Scale option (RFC 7323); if RCV.WND drops to zero, the sender enters persist-timer probing to avoid deadlock from a lost window-update ACK, while Silly Window Syndrome avoidance prevents pathological tiny-segment oscillation.
