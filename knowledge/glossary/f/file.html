File

A named collection of data stored in a filesystem, such as a document, image, or program.

Think of a file like a single sheet or folder of paper with a name written on the tab. Whether it holds a letter, a song, or a photo, giving it a name lets you save it, find it later, copy it, or delete it without mixing it up with anything else on your computer.

In Linux, files live inside directories, and a file’s name is separate from its actual data: a directory simply maps a name to the underlying file object. Following Unix’s “everything is a file” model, not only documents and programs are accessed as files, but also hardware devices (/dev/sda), kernel status (/proc/cpuinfo), and named pipes. Running ls -l shows the object type in the very first character (- for a regular file, d for a directory, l for a symbolic link).

If you delete a file name with rm while a running program still has that file open, what happens to the program’s access?

The program can keep reading and writing the file until it closes it. rm only unlinks the directory entry (the name); the filesystem keeps the underlying data alive until both the link count and all open file-descriptor references drop to zero.

In POSIX and the Linux VFS, a regular file (S_IFREG) is represented by an inode storing metadata (UID/GID, mode, timestamps, size, block extents) and an i_nlink reference count, decoupled from directory entries (dentry objects). Multiple hard links can point to the same inode, and storage reclamation occurs only when i_nlink == 0 and all kernel struct file references are released. Other inode types—directories (S_IFDIR), symbolic links (S_IFLNK), character/block devices (S_IFCHR/S_IFBLK), FIFOs (S_IFIFO), and Unix domain sockets (S_IFSOCK)—share the same namespace and permission model while routing I/O through distinct VFS file_operations tables.
