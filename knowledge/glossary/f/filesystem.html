Guide / Glossary A–Z / Terms beginning with F / Filesystem

The structure and software an operating system uses to organize, name, store, and retrieve data on a storage device or virtual tree.

Without a filesystem, a hard drive or SSD would just be a giant, unlabeled ocean of ones and zeros. A filesystem acts like a library’s catalog and shelving system: it keeps track of where each file begins and ends, what its name is, when it was last changed, and which empty spaces are safe to reuse.

Unlike Windows, which assigns separate drive letters (C:, D:) to each disk, Linux merges every active filesystem into one unified directory tree starting at /, attaching extra drives or USB sticks at mount points (like /mnt or /media). Different filesystems make different trade-offs: ext4 is a reliable general-purpose Linux default, Btrfs and ZFS add snapshots and checksums, and FAT32/exFAT are used on USB drives for cross-platform sharing.

If you mount a USB drive onto /mnt/usb while /mnt/usb already has a file inside it, what happens to that existing file?

It is temporarily hidden—not deleted—for as long as the USB drive is mounted there. Path lookups at /mnt/usb resolve to the mounted filesystem’s root, and the original file reappears as soon as you unmount the drive with umount.

In Linux, the Virtual File System (VFS) layer abstracts concrete implementations behind super_block, inode, dentry, and file operations. On-disk filesystems differ in consistency and layout models: journaling filesystems (ext4, XFS) write metadata or data intent to a write-ahead journal for atomic crash recovery, whereas Copy-on-Write (CoW) filesystems (Btrfs, ZFS) allocate new blocks and atomically swap root tree pointers, enabling cheap snapshots and end-to-end checksums at the cost of fragmentation and write amplification. Synthetic filesystems (tmpfs, procfs, sysfs, overlayfs) implement the same VFS contract without block-device backing.
