Guide / Glossary A–Z / Terms beginning with F / File descriptor

A small non-negative integer that a process uses to identify an open file, pipe, socket, or other input/output resource.

When a program wants to read or write a file, the operating system doesn’t hand the program the whole file path every time. Instead, it opens the file once and gives the program a small claim-ticket number—like 3 or 4. From then on, the program just says “read from ticket 3” or “close ticket 4.”

Every Linux process starts with three standard file descriptors: 0 (standard input, stdin), 1 (standard output, stdout), and 2 (standard error, stderr). Shell redirections like 2>/dev/null or 2>&1 manipulate these numbers before a command runs. You can inspect a running process’s open file descriptors in /proc/<pid>/fd, and hitting the per-process limit (ulimit -n) causes “Too many open files” errors even when disk space is plentiful.

In a shell command like cmd >out.txt 2>&1, why does the order of >out.txt and 2>&1 matter?

Redirections are evaluated left to right. >out.txt first points fd 1 at out.txt, and then 2>&1 duplicates fd 1 into fd 2 so both go to out.txt. Reversing them (2>&1 >out.txt) would point fd 2 at the old stdout (the terminal) before fd 1 is redirected.

Under POSIX and the Linux kernel, a file descriptor is an index into a process’s files_struct (fdtable), pointing to a kernel struct file (the open file description). Because dup()/dup2() and fork() duplicate the fd entry to reference the same struct file, they share the file offset (f_pos) and status flags (O_APPEND, O_NONBLOCK), whereas independent open() calls create distinct struct file instances. Descriptor-level flags—notably FD_CLOEXEC (O_CLOEXEC)—live on the fd table entry rather than struct file, preventing unintended descriptor leaks across execve(). Per-process limits are governed by RLIMIT_NOFILE, while system-wide open struct file instances are bounded by fs.file-max.
