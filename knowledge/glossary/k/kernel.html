Kernel

A kernel is the central software of an operating system that manages hardware and lets programs share CPU, memory, and devices safely.

Think of the kernel like an air-traffic controller for your computer: apps cannot simply grab the disk, network card, or memory whenever they want, or they would collide and overwrite each other. On Tamlinux today that central part is the Linux kernel. When you run a program, the kernel gives it a process identity, memory, and controlled access to disks, network, and displays. See Kernel and processes.

The Linux kernel runs in privileged kernel space, while everyday applications run in isolated user space and request services—like opening a file or sending a packet—through system calls. Drivers may load as modules, but on a monolithic kernel they still execute with full kernel privilege. As a result, a user-space crash kills only one program, whereas a kernel or driver fault can freeze or panic the whole machine.

Why can’t a regular user-space program read another program’s memory directly?

Because the kernel enforces virtual memory isolation with hardware page tables; any cross-process access must go through explicit kernel-mediated mechanisms like pipes, sockets, or shared memory.

User-space programs cross into supervisor mode via architecture-specific system-call traps (such as syscall on x86_64) into the VFS, scheduler, network stack, and memory manager. Process existence is not health: mapped executables can outlive on-disk replacements via open inodes, and uninterruptible sleep (D state) indicates a thread blocked inside kernel I/O that signals cannot wake. Design trade-offs between monolithic and microkernel architectures—performance versus driver isolation—are compared in kernels.
