Keycode

A keycode is a number that identifies a physical key to software, after the keyboard’s own scancode has been translated.

A keycode is like a numbered seat in a theater: it tells the computer which physical button on your keyboard was pressed, not which letter or symbol is printed on it. Separating the key’s position from its meaning lets the same keyboard hardware work with different languages and layouts without rewiring anything.

On Linux, the word “keycode” refers to two different numbering schemes that differ by 8. The Linux kernel assigns KEY_A to 30 and KEY_H to 35 in an input_event from evdev. XKB, X11, and Wayland add 8 to every kernel keycode, so those same keys become 38 and 43 by the time a terminal or desktop app inspects them. Whenever you read a key-debugging log, check which layer printed the number.

Why does pressing the A key show code 30 in evtest but code 38 in xev or wev?

Because evtest reads raw kernel evdev codes, whereas X11 and Wayland (via XKB) add a fixed offset of 8 to preserve compatibility with the legacy X11 keycode range.

Kernel keycodes are defined in linux/input-event-codes.h (KEY_A is 30, and codes extend past 255 for media and special keys). Because X11 historically reserved keycodes 0–7 and used 8–255, XKB and Wayland’s wl_keyboard.key event report evdev + 8, which XKB then maps through the active keymap to a keysym. Notice the boundary: X11 core protocol keycodes are 8-bit (capped at 255), whereas evdev and Wayland support higher codes when the XKB keymap defines them. Remapping can occur at multiple stages: setkeycodes or udev hwdb alters scancode-to-evdev translation, while XKB rules and compositor keymaps alter how the keycode is interpreted.
