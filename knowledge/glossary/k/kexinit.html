KEXINIT (SSH Key Exchange Initialization)

KEXINIT (SSH_MSG_KEXINIT) is the opening negotiation packet in an SSH connection where the client and server advertise the cryptographic algorithms they support.

Think of KEXINIT like two people meeting who speak different languages and each handing over a list of languages they know, ordered from favorite to least favorite. Both sides look at the lists and pick the first match they share so they can start talking securely.

Defined in RFC 4253, both the SSH client and server send an SSH_MSG_KEXINIT packet right after exchanging protocol version banners, and then repeat it whenever the connection rekeys. Each side selects the first algorithm on the client’s list that the server also supports. If you ever see an SSH error like “no matching key exchange method found” or “no matching host key type found,” it means the two KEXINIT lists had no algorithm in common.

What happens when an SSH client and server have no overlapping algorithm in their KEXINIT lists?

Negotiation fails immediately and the SSH connection is closed before authentication can begin, reporting a “no matching … found” error.

SSH_MSG_KEXINIT (packet type 20, RFC 4253 §7.1) carries a 16-byte random cookie followed by ten name-lists: kex_algorithms, server_host_key_algorithms, directional encryption, MAC, compression, and language lists, plus first_kex_packet_follows. Because KEXINIT is sent in cleartext before encryption starts, its exact payload is hashed into the exchange hash H to detect downgrade tampering; OpenSSH’s kex-strict extension (CVE-2023-48795 Terrapin mitigation) additionally resets packet sequence numbers and forbids extraneous transport messages before NEWKEYS.
