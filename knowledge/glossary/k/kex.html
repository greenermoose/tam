KEX (Key Exchange)

KEX (Key Exchange) is the cryptographic handshake step where two parties agree on a shared secret key over an untrusted network without anyone listening in being able to learn it.

Think of KEX like mixing paint colors in public: two people each keep a secret color to themselves, swap a mixed sample, and end up with the exact same final shade that an onlooker cannot easily un-mix. It matters because it lets your browser or SSH client create a private encryption key with a server even when strangers can see every packet on the wire.

Both SSH and TLS run a KEX step—using algorithms like X25519 or post-quantum hybrid ML-KEM+X25519—before encrypting application data. Notice that key exchange alone only creates a secret with whoever is at the other end; it must be paired with server authentication (such as an SSH host key or TLS certificate) so you know you are not exchanging keys with an imposter. Ephemeral KEX also provides forward secrecy: recording encrypted traffic today does not let an attacker decrypt it later even if long-term identity keys leak.

Why isn’t Diffie–Hellman key exchange alone enough to stop a man-in-the-middle attacker?

Because without authentication (like an SSH host key or TLS certificate), an attacker can run separate key exchanges with both the client and server and decrypt every message in between.

Modern protocols use ephemeral Elliptic-Curve Diffie–Hellman (ECDHE, such as Curve25519/X25519 in RFC 7748) or Key Encapsulation Mechanisms (KEMs, such as ML-KEM / FIPS 203) combined in hybrid constructions (e.g., OpenSSH mlkem768x25519-sha256 or TLS 1.3 KeyShare) to resist “harvest now, decrypt later” quantum threats. The raw shared secret is never used directly as a cipher key; instead, a KDF (such as HKDF in TLS 1.3 or SHA-256/512 derivation in SSH RFC 4253) binds the shared secret to the handshake transcript hash to derive directional traffic keys and IVs.
