Guide / Glossary A–Z / Terms beginning with G / GDB (GNU Debugger)

A command-line debugger for inspecting running programs, pausing execution at specific points, and analyzing crashes.

When a program misbehaves or crashes, GDB lets a developer freeze it mid-flight—like pausing a video frame by frame—to see what it was doing right before things went wrong. Instead of guessing from error messages alone, you can check which line of code was running and what values were stored in memory.

In Linux development, GDB reads DWARF debug symbols (typically compiled with -g) to map machine instructions back to source lines and variable names. You can attach to a live process with gdb -p <pid>, launch a binary under GDB, or open a saved core dump to print a call stack (bt) and inspect frames. Unlike print-statement debugging, GDB requires no code edits or recompilation once symbols are available.

Why does running bt in GDB sometimes show only hexadecimal addresses like 0x00401234 in ?? () instead of function names and line numbers?

The binary or its shared libraries were likely stripped of symbol tables and DWARF debug info (or compiled without -g). Without that metadata, GDB can still walk raw stack frames using frame pointers or unwind tables, but it cannot map instruction addresses back to source-level names.

GDB controls target execution via ptrace(2) on Linux (or the GDB Remote Serial Protocol over TCP/serial for gdbserver and kernel KGDB), inserting software breakpoints by overwriting target instructions with trap opcodes (0xCC / INT3 on x86-64) or programming hardware debug registers (DR0–DR3) for watchpoints. Stack unwinding relies on .eh_frame / .debug_frame CFI (Call Frame Information) rather than frame pointers alone, which matters when binaries are built with -fomit-frame-pointer. Multi-threaded debugging coordinates SIGSTOP/SIGTRAP delivery across LWPs, while debuginfod fetches split DWARF/ELF debuginfo on demand by build-id.
