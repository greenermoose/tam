GPT - GUID Partition Table

The modern standard layout for dividing a physical storage drive into separate partitions and recording where each one begins and ends.

Think of a hard drive or SSD like a large notebook that you want to split into sections—one for the operating system, one for your files, and one for recovery. GPT is the table of contents at the front (and backed up at the back) of the notebook that tells the computer exactly where each section starts and stops, replacing the older MBR format that could not handle very large drives or many sections.

GPT replaces the legacy Master Boot Record (MBR), which capped disks at 2 TiB (with 512-byte sectors) and allowed only four primary partitions. On Linux, tools like gdisk, parted, and fdisk inspect and edit GPT layouts, where each partition gets a unique GUID (PARTUUID) as well as a type GUID (such as Linux filesystem or EFI System Partition). Because GPT keeps a backup copy of its table at the end of the disk, recovering from accidental damage to the primary header is often possible—and when cloning or resizing a disk, the backup header must be relocated to the new end of the drive.

Why does a GPT disk still include a small MBR entry at sector 0?

Sector 0 holds a “protective MBR” that marks the entire disk as a single unknown partition. This prevents legacy MBR-only tools from seeing the disk as empty and accidentally overwriting the GPT headers or partitions.

Defined in the UEFI specification, GPT uses 64-bit Logical Block Addressing (LBA), supporting up to 8 ZiB with 512-byte sectors. LBA 0 contains the protective MBR; LBA 1 holds the primary GPT header (signature EFI PART, header CRC32, current/backup LBAs, and partition array CRC32); LBAs 2–33 typically hold 128 partition entries of 128 bytes each (type GUID, unique partition GUID, starting/ending LBA, 64-bit attributes, and UTF-16LE name). The backup entry array and backup header sit at the final LBAs in reverse order. A classic failure mode occurs when a raw image is written to a larger disk: the backup header remains at the old image size rather than the last LBA, causing tools like gdisk or the kernel to warn about a secondary header mismatch until fixed with sgdisk -e.
