Guide / Glossary A–Z / Terms beginning with G / Git

A distributed version-control system that tracks changes to files over time and lets multiple people collaborate on the same codebase.

Git works like an unlimited, smart "save history" for a project folder. Every time you record a milestone, Git remembers what changed, who made the change, and why, so you can experiment on a side copy, compare older versions, or undo mistakes without keeping dozens of folders named "project-final-v2".

Unlike older centralized systems, every Git clone holds the full repository history locally, so committing, branching, and inspecting logs work offline. Changes move through three main areas: the working tree (files on disk), the staging area or index (what you choose to include next), and the local repository (committed snapshots). Branches in Git are lightweight pointers to commits rather than full file copies, making branching and merging fast.

What is the practical difference between staging a file with git add and committing it with git commit?

git add writes the file’s current contents into the index (staging area) as part of the next planned snapshot, without recording history yet. git commit takes whatever is currently in the index and creates a permanent commit object linked to its parent commit(s).

Git models history as a directed acyclic graph (DAG) of immutable, content-addressed objects—blob, tree, commit, and annotated tag—keyed by SHA-1 (or SHA-256 in newer repositories) digests under .git/objects. Named refs (refs/heads/*, refs/tags/*, HEAD) are mutable pointers into this DAG, while the binary .git/index caches stat metadata and tree-entry hashes to avoid re-hashing unchanged files. Loose objects are periodically delta-compressed into .pack/.idx files; because commits store full tree snapshots rather than diffs, merges perform 3-way tree comparisons using the lowest common ancestor (or recursive/ort strategies for criss-cross merges).
