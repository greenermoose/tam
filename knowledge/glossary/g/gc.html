GC (Garbage Collection)

GC (Garbage Collection) is an automatic memory-management mechanism that finds and frees data a program can no longer reach.

When a program runs, it borrows chunks of memory to hold text, lists, and images. In older languages like C, the programmer has to remember to give every single chunk back when done—forgetting causes a memory leak, and giving it back too early causes a crash. Garbage collection works like an automatic cleanup crew: it periodically checks which pieces of data the program still has a path to, and quietly clears away everything else.

Languages such as Python, JavaScript, Go, Lua, and QML include runtime garbage collectors, whereas C and C++ require manual free()/delete or explicit smart-pointer ownership. The same concept also appears in storage systems: for example, Nix’s nix-collect-garbage scans active system profiles and runtime roots to delete unreferenced store paths from /nix/store. In interactive apps, you may notice GC as brief latency spikes (“stop-the-world” pauses) when a runtime scans a large heap.

If a language has garbage collection, can a program still leak memory?

Yes. Garbage collectors only reclaim objects that are unreachable from live references. If a program accidentally keeps old items in a global list, cache, or event listener, those objects remain reachable and will never be freed.

Runtime garbage collectors fall broadly into tracing collectors (mark-sweep, copying, generational, and concurrent/incremental collectors like Go’s tri-color mark-sweep or JVM ZGC) and reference counting (which reclaims deterministically on zero count but requires cycle detection, as in CPython’s cyclic GC). Key trade-offs balance throughput, memory overhead, and tail-latency pause times via write barriers and generational hypotheses (most objects die young). Analogous reachability-based reclamation in package/storage systems (such as nix-collect-garbage or Git’s git gc) marks from GC roots (symlinks, refs, open fds) to prune unreferenced immutable artifacts.
