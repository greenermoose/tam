Guide / Glossary A–Z / Terms beginning with Q / QNX

A commercial, POSIX-compliant real-time microkernel operating system widely used in automotive, medical, and industrial embedded systems.

Unlike general-purpose operating systems where most features share one large core, QNX keeps its core tiny and runs drivers, filesystems, and networking as separate small programs. If one part crashes, it can restart without bringing down the whole system, which is why car dashboards and factory machines rely on it for predictable, on-time responses.

QNX demonstrates that message-passing microkernels can meet strict real-time deadlines while still offering familiar POSIX APIs and shell utilities. Compared with a monolithic Linux kernel, moving drivers into userspace trades some message-passing overhead for strong fault isolation—a crashed network or graphics driver does not panic the kernel.

How does QNX prevent a low-priority process from blocking a high-priority real-time task during IPC?

Its Neutrino microkernel applies priority inheritance across synchronous message passing: when a high-priority client sends a message and blocks waiting for a reply, the server temporarily inherits the client’s priority until it replies.

Built on the Neutrino microkernel, QNX uses synchronous MsgSend/MsgReceive/MsgReply IPC with scatter-gather transfers and deterministic scheduling (FIFO, round-robin, and adaptive partitioning). Because drivers run in isolated userspace address spaces with capability-scoped I/O privileges, fault recovery restarts only the affected resource manager, though crossing address spaces per driver call increases context-switch and TLB pressure relative to in-kernel Linux drivers.
