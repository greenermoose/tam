QUIC

An encrypted, multiplexed transport protocol built on top of UDP (RFC 9000) that powers HTTP/3 for faster, more resilient network connections.

Traditional web connections use TCP, which sends everything in a single line—if one packet gets lost, every file or tab sharing that connection has to wait. QUIC sends multiple independent streams over UDP with encryption always turned on, so losing one packet only pauses that stream and moving from Wi-Fi to cellular does not drop your session.

Unlike TCP plus TLS, where transport and encryption handshakes happen one after another in kernel space, QUIC combines them into a single 1-RTT setup (or 0-RTT for repeat visits) in userspace over UDP port 443. You can inspect QUIC sockets with ss -u, though networks that block or rate-limit UDP 443 cause browsers to fall back to HTTP/2 over TCP.

Why does packet loss on one HTTP/3 stream not stall other streams in the same QUIC connection?

TCP exposes a single ordered byte stream to the application, causing head-of-line blocking when any packet is missing; QUIC tracks stream offsets independently per stream, so other streams can deliver received data immediately.

Defined in RFC 9000 (transport) and RFC 9001 (TLS 1.3 integration), QUIC encrypts headers and payloads—leaving only connection IDs (CIDs) and key-phase/spin bits visible—to prevent middlebox ossification and enable NAT-surviving connection migration. Monotonic packet numbers avoid TCP’s retransmission ambiguity, while trade-offs include higher userspace per-packet CPU overhead unless UDP GSO/GRO (UDP_SEGMENT) or kernel-bypass optimizations are used.
