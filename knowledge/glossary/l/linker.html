Guide / Glossary A–Z / Terms beginning with L / Linker

A program that combines compiled object files and libraries into a single executable program or shared library.

When programmers write software, they often split the code into separate source files—like chapters of a book—and translate each file into machine code on its own. The linker acts like a bookbinder that stitches those separate pieces together, connects every cross-reference between them, and attaches any shared tools the program relies on so the computer can run the finished program as one unit.

On Linux, ld (or lld / gold) is usually invoked automatically by gcc or clang as the final build step. Static linking copies library code directly into the executable, making it larger but self-contained, while dynamic linking leaves references to .so shared libraries resolved at load time by ld.so. Unresolved symbol errors (undefined reference to ...) happen when a function is declared in a header but its compiled object file or -l library flag is missing at link time.

Why can a C program pass compilation with gcc -c yet still fail during linking with an “undefined reference” error?

Compilation (-c) only checks one source file at a time and trusts header declarations that a function exists elsewhere. The linker is the stage that actually matches every call site to its compiled definition across object files and libraries, so a missing object file or omitted -l library only surfaces during linking.

A linker performs two core passes over ELF relocatable objects (ET_REL) and archives: symbol resolution across strong, weak, and common definitions, followed by section merging, virtual-address layout, and relocation patching according to a linker script or default ABI rules. Static archives (.a) are scanned left-to-right and only members satisfying currently undefined symbols are pulled in, which makes link-line dependency order significant unless grouped with --start-group/--end-group. For dynamically linked ELF binaries (ET_EXEC or ET_DYN), the static linker emits .dynsym, PT_INTERP, and PLT/GOT entries so the runtime dynamic linker (ld-linux) can resolve external symbols and apply RELRO or lazy binding.
