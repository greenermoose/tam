Library

A collection of reusable code and data that multiple programs can call instead of rebuilding common tasks from scratch.

When a carpenter builds a house, they do not forge their own nails or mill their own hinges—they use standard hardware made for everyone. In programming, a library is a toolbox of pre-written, tested parts (for math, graphics, or reading compressed files) that any program can plug into, saving effort and avoiding repeated bugs.

On Linux, libraries come in two main forms: static libraries (.a files) baked directly into an executable at build time, and shared libraries (.so files) loaded at runtime by ld-linux.so so multiple programs share one copy in memory. You can inspect a program’s shared library dependencies with ldd.

What is the main trade-off between linking a library statically versus dynamically on Linux?

Static linking embeds the library inside the executable for fewer runtime dependencies, but increases binary size and requires rebuilding the program to pick up security fixes. Dynamic linking shares one .so file in memory across programs, while requiring a compatible version at runtime.

A compiled package of objects and symbols with a defined API/ABI: either an ar archive of relocatable .o files resolved left-to-right by ld, or an ET_DYN ELF shared object compiled with -fPIC and bound at runtime by ld.so via GOT/PLT relocations (lazy or BIND_NOW), DT_NEEDED entries, and SONAME versioning. Engineering concerns include ABI stability (struct layout, symbol visibility via -fvisibility=hidden), search-path precedence (DT_RPATH vs. DT_RUNPATH vs. LD_LIBRARY_PATH), and plugin loading via dlopen()/dlsym().
