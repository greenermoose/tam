Line editor

A line editor changes text by naming lines and giving commands, rather than by moving a cursor around a screen.

Imagine editing a numbered shopping list through an assistant. You do not point at the paper. You say “print line 2”, “delete lines 3 to 5”, or “change every milk to oat milk”, and the assistant edits the list. A line editor works the same way: you give a command and an address, such as 2d to delete line 2, and it acts on the numbered lines held in memory. Because it never needs to draw a whole screen, it works over a slow connection, in a script, or on a terminal that cannot show a full display.

The classic Unix line editors are ed and ex. A command starts with an optional address or range, then a command letter: 2p prints line 2, 1,4d deletes lines 1 through 4, and %s/old/new/g substitutes on every line. The current line moves as commands run, so a sequence of commands can build on the previous one without repeating an address. A line editor is stateful in a way a stream filter such as sed is not: sed reads input, transforms it, and writes output, while ex keeps a buffer, a cursor line, marks, and options across the whole session. Screen editors sit on top of the same idea. vi is a full-screen front end to the ex command language, which is why a colon in vi still accepts s, g, and w commands.

Why can ed-style commands still matter when a full-screen editor exists?

They work without a terminal that can address the screen, they are easy to feed from a script, and they use very little bandwidth. They are also the shared core of the vi family: learning the ex command line explains what vi's colon commands do.

Formally, a line editor is a stateful text buffer with a designated current line, addressed by line number, relative offset, pattern, mark, or $ for the end. POSIX standardizes ex as the line editor and vi as the screen-oriented utility that refers to it for the full command language. The command grammar is [address[,address]]command[arguments]; regular expressions are basic regular expressions, and a global command such as g/pat/cmd iterates over matching lines with implementation-defined handling of line shifts during deletion or movement. Failure behaviour matters in automation: POSIX requires that when standard input is not a terminal, an error must prevent the write and terminate with a nonzero status, so a script fails closed instead of saving a partially edited buffer. Historical ed predates ex and remains useful for very small environments where even a screen editor may be absent.
