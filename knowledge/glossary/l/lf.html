Guide / Glossary A–Z / Terms beginning with L / LF (Line Feed, 0x0A)

The ASCII control character 0x0A (Ctrl+J, written '\n' in C) used as the standard line ending in Linux and Unix text files.

On old mechanical typewriters, starting a new line took two steps: sliding the carriage back to the left margin (Carriage Return) and rolling the paper up one line (Line Feed). Linux and Unix kept things simple by using a single invisible character, Line Feed, to mark the end of a line. Windows uses both characters together, which is why text files moved from Windows sometimes show stray ^M marks in Linux editors.

Part of the C0 control codes, LF (0x0A) contrasts with Windows’ two-byte CRLF (0x0D 0x0A). On Linux, you can convert files with dos2unix or configure Git’s core.autocrlf, while the kernel’s terminal driver automatically translates LF to CRLF when drawing text to a terminal screen.

Why does a shell script saved with Windows (CRLF) line endings often fail on Linux with a “bad interpreter” error?

Linux treats only LF (0x0A) as the line terminator, so the preceding CR (0x0D) byte in a shebang line like #!/bin/sh\r is read as part of the interpreter filename, and no file named /bin/sh\r exists.

ASCII 0x0A (LF, '\n', Ctrl+J) is the POSIX newline terminator. In the kernel TTY layer (N_TTY), termios ICRNL maps incoming 0x0D from terminals to 0x0A for canonical reads, whereas OPOST with ONLCR expands outgoing 0x0A to 0x0D 0x0A so terminal emulators reset the column before advancing a row. Protocols such as HTTP/1.1 and SMTP mandate explicit CRLF, while raw/binary streams must clear ICRNL and ONLCR (as cfmakeraw() does) to avoid silent byte corruption.
