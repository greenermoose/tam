Decoupled versioning

Decoupled versioning is the practice of giving a program’s executable and its content or documentation corpus separate version numbers and release schedules.

Think of a dictionary app on your phone: the app itself might stay at version 2.0 for months because its buttons and search bar work fine, while the word list inside it gets updated every week as new definitions are added. Decoupled versioning lets the tam program and its documentation update independently without rebuilding the whole program for every text edit.

In tam, decoupled versioning lets the C command binary and the knowledge corpus change independently, with each reporting its own version. Fixing a typo or expanding a glossary page does not require bumping the C program’s version, and a bug fix in the CLI does not force a new corpus version.

Why does decoupled versioning separate the command version from the corpus version?

Because knowledge content changes far more often than the C binary. Keeping their versions independent avoids bumping the program version for documentation-only updates and makes it clear whether a release changed the tool or its content.

Decoupled versioning separates the command binary’s ABI and CLI release cadence from the knowledge corpus’s content cadence, resolving the corpus version dynamically from the knowledge root at runtime. This introduces a two-axis compatibility boundary: the binary must remain tolerant of expected corpus directory and metadata layouts (or enforce a minimum format contract) while allowing independent packaging, updates, and provenance tracking for the executable and the HTML tree.
