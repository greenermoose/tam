Guide / Glossary A–Z / Terms beginning with D / DRM (Direct Rendering Manager)

The Linux kernel subsystem that manages graphics hardware, GPU memory, command submission, and display output.

When you play a 3D game, watch a video, or move windows around your desktop, several programs want to use the graphics chip at the same time without stepping on each other’s toes. DRM is the Linux kernel’s traffic controller for graphics: it coordinates who gets to use the GPU, manages its memory, and sends the final picture out to your monitor.

DRM splits graphics into two main jobs: rendering (letting Mesa, Vulkan, or OpenGL apps submit GPU work via /dev/dri/renderD*) and KMS (Kernel Mode Setting, which controls monitor resolutions, refresh rates, and display connectors via /dev/dri/card*). Wayland compositors act as DRM masters on card* to flip framebuffers onto screens, while individual apps only need render nodes. You can inspect DRM connectors and modes in /sys/class/drm/.

Why does Linux expose separate /dev/dri/card0 and /dev/dri/renderD128 device nodes?

card0 includes privileged display mode-setting (KMS) for the compositor, while renderD128 lets unprivileged applications submit GPU compute or 3D rendering work without being able to take over or reconfigure the physical displays.

The DRM subsystem (drivers/gpu/drm/) provides unified infrastructure for GPU drivers (i915, xe, amdgpu, nouveau, msm) while keeping hardware-specific command streams behind driver-private ioctls. Memory allocation and buffer sharing rely on GEM (Graphics Execution Manager) or TTM (Translation Table Manager) paired with dma-buf file descriptors for zero-copy cross-device sharing and dma_fence synchronization primitives. Display output uses the Atomic KMS API (DRM_IOCTL_MODE_ATOMIC), validating and committing CRTC, plane, and connector property state in a single tear-free transaction.
