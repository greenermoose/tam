Dependency

Something a program needs in order to be built or to run.

Most programs do not include every piece of code they need from scratch. Instead, they rely on shared building blocks—such as a tool that draws windows or reads image files—made by others. Think of it like a recipe that assumes you already have flour and salt in the pantry: if a required ingredient is missing, the dish cannot be made.

In Linux package managers and build systems, dependencies are split into runtime dependencies (shared libraries or helper tools needed when executing) and build-time dependencies (compilers, headers, or code generators needed only to produce the binary). Package managers inspect declared version constraints to install missing dependencies automatically, and ldd or ldconfig can show which shared libraries an executable expects at runtime.

Why can removing a single “unused” library package break several unrelated apps?

Because multiple programs often share one runtime dependency; removing it leaves their dynamic linker unable to resolve required symbols at startup.

A dependency is a directed edge in a package or build DAG, annotated with version constraints, optional feature flags, and phase or environment markers. SAT- or PubGrub-style solvers resolve transitive graphs while avoiding diamond-dependency conflicts; in ELF systems, runtime edges correspond to DT_NEEDED entries and SONAMEs (requiring ABI stability across minor updates), whereas immutable stores bind exact content-addressed hashes to eliminate ambient version skew.
