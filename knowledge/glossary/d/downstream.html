Downstream

A project, Linux distribution, or product that receives, adapts, and distributes software originally developed upstream.

Think of software development like a river: code is created at the source (“upstream”) and flows down to the projects that package it for everyday users (“downstream”). For example, the team that writes Firefox is upstream, while a Linux distribution that bundles Firefox into its installer and adds security updates is downstream. Knowing which is which helps you understand where a bug should be reported and fixed.

In Linux, “downstream” is relative to where you stand: Debian is downstream of the Linux kernel and GNU tools, while Ubuntu is downstream of Debian. Downstream maintainers package software for their system’s layout, backport security fixes to older stable versions, and sometimes carry distribution-specific patches. When troubleshooting, checking whether a bug reproduces in an unmodified upstream build tells you whether to file the issue with your distro or with the original authors.

If a program crashes only because of a patch added by your Linux distribution, should you report it upstream or downstream first?

Report it downstream (to your distribution’s bug tracker) first, because the upstream developers do not ship that patch and cannot reproduce or fix distribution-specific modifications.

A downstream integrator maintains a packaging tree, ABI/API compatibility guarantees, and a patch queue (often managed with Quilt or vendor-branched Git) atop upstream tarballs or tags. This introduces classic maintenance trade-offs: cherry-picking security fixes onto a frozen release branch preserves ABI stability for users while accumulating backport drift, whereas rebasing onto newer upstream releases risks breaking dependent packages. Healthy downstreams regularly “upstream” general bug fixes to shrink their delta, leaving only policy, path, or build-system adaptations in the downstream layer.
