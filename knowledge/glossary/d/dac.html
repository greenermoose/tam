Discretionary Access Control (DAC)

An access control model in which the owner of a resource decides who may access it.

If you own a notebook, you decide which friends are allowed to read it or write in it—nobody else sets the rules for your notebook. Under Discretionary Access Control, whoever owns a file or folder on a computer has that same control: they choose which other users can read, edit, or run it.

Standard Unix file permissions (chmod, chown, and read/write/execute bits) and POSIX ACLs (setfacl) are DAC: user alex can grant or revoke access to files alex owns. Unlike Mandatory Access Control (MAC, such as SELinux or AppArmor), DAC lets any program running as alex exercise all of alex’s permissions, including sharing files with others.

Why does Linux pair DAC with Mandatory Access Control (MAC) on security-sensitive systems?

Because DAC trusts every program you run with your full file-sharing authority, a compromised application running as alex could read or expose alex’s private files without breaking any DAC rule. MAC adds system-wide policy boundaries that even the file owner cannot override.

An access-matrix model (Lampson) in which subjects holding ownership or control rights over an object may propagate read, write, or execute rights to other subjects at their discretion. In the Linux VFS (inode_permission()), DAC evaluates uid/gid, mode bits, supplementary groups, and system.posix_acl_access extended attributes, unless bypassed by CAP_DAC_OVERRIDE or CAP_DAC_READ_SEARCH. Its structural limitation is vulnerability to Trojan-horse information flow: because processes inherit the invoking user’s discretionary rights, DAC cannot confine untrusted code from leaking or re-permissioning readable objects, motivating Linux Security Modules (LSM) for MAC enforcement.
