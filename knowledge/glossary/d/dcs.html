DCS (Device Control String)

DCS (Device Control String) is a terminal escape sequence (ESC P ... ESC \) used to carry structured payloads for capability queries and device-level protocols.

Terminals normally display every letter a program sends, so sending a complex package—like asking the terminal what colors it supports or drawing an inline image—needs a wrapper so it doesn’t appear as garbled text. DCS acts like a sealed envelope: ESC P opens the message and ESC \ closes it.

Unlike CSI sequences (ESC [, used for cursor movement and text styling) or OSC sequences (ESC ], used for window titles and clipboards), a Device Control String wraps an arbitrary payload between ESC P and the string terminator ESC \. Common uses include XTGETTCAP terminfo queries and Sixel graphics; inside multiplexers like tmux, nested DCS sequences must be wrapped or allowed via allow-passthrough.

Why would a terminal program use a DCS sequence instead of a CSI sequence?

CSI sequences are built for short, semicolon-separated numeric parameters like cursor coordinates or SGR colors, whereas DCS frames multi-byte or structured payloads (such as XTGETTCAP queries or Sixel pixel streams) between explicit start and string-terminator delimiters.

ECMA-48 / ISO/IEC 6429 Device Control String: 7-bit ESC P (0x1B 0x50) or 8-bit C1 0x90, terminated by String Terminator ST (ESC \ / 0x1B 0x5C or 0x9C; unlike OSC, BEL is non-standard). In a VT state machine (e.g., Paul Williams’ parser), DCS_ENTRY collects parameters and intermediates before transitioning to DCS_PASSTHROUGH until ST, CAN, or SUB. Used by DECRQSS, XTGETTCAP, DECSIXEL, and tmux passthrough; parsers must bound payload buffers and handle aborted sequences to avoid state-desync or memory DoS.
