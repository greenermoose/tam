Dry run

A test execution of a command or procedure that reports what changes it would make without actually applying them.

Before rearranging furniture in a room, you might sketch where everything will go so you do not drag a heavy couch across the floor by mistake. A dry run does the same thing for computer commands: it walks through the steps and prints out what it plans to delete, copy, or install, without touching any real files. That lets you spot a typo before it causes damage.

Many Linux tools provide a --dry-run or -n flag for risky operations—for example, rsync -av --dry-run to preview file deletions and transfers, make -n to print build commands without running them, or git clean -fdn to list untracked files before removing them. Always read the dry-run output carefully, especially paths and delete counts, before re-running without the flag.

If rsync --dry-run succeeds without errors, does that guarantee the real run will also succeed?

No. A dry run skips writing data, so it cannot catch runtime failures that only happen during real I/O—such as running out of disk space mid-transfer or hitting a write-protected destination.

In CLI and infrastructure tooling, a dry run executes argument parsing, dependency resolution, and state-diff planning while stubbing or gating side-effecting syscalls and state commits. Because planning and execution are decoupled, a dry run can exhibit TOCTOU (time-of-check to time-of-use) drift if external state changes before the real run, or miss post-validation failures such as quota exhaustion, lock contention, or server-side admission hooks. In Kubernetes (--dry-run=server) or database migrations, server-side dry runs run full admission and constraint checks inside a rolled-back transaction, narrowing that fidelity gap.
