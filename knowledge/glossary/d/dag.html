DAG (Directed Acyclic Graph)

A dependency graph with one-way arrows and no circular loops, used by package managers, version control, and build tools.

Think of a recipe or a row of dominoes: you have to crack the eggs before you bake the cake, and a step can never depend on itself to finish first. A DAG is a map of steps or items connected by one-way arrows that always move forward and never loop back in a circle.

In Linux and software development, Git commit history (commits pointing to parent commits), Nix store dependencies, and Make or Ninja build targets all form DAGs. Because there are no loops, tools can sort the steps into a valid build order and safely skip or cache unchanged branches. If two packages accidentally depend on each other, the loop breaks the DAG and causes a cycle error.

What guarantee does a DAG give a build tool like Make or Nix that a general graph does not?

Because a DAG has no circular loops, every dependency chain eventually reaches a starting node with no prerequisites. That guarantees the build tool can find a finite, unambiguous order (a topological sort) to build everything without getting stuck in an infinite loop.

A directed graph G = (V, E) containing no directed cycles, which is equivalent to admitting at least one topological ordering of V (computable in O(|V| + |E|) time via Kahn’s algorithm or DFS post-order). In Merkle-DAGs (Git objects, Nix derivations, IPFS), each node is content-addressed by a cryptographic hash of its payload and child references, making cycles infeasible without a hash collision and enabling deduplication and incremental verification. Practical edge cases include diamond dependencies—where multiple paths converge on a shared ancestor, requiring memoization so a target is built only once—and dynamic dependencies where edges are discovered only after executing an earlier build step.
