Exit status

A numeric code a program returns when it finishes to report whether it succeeded or why it failed.

When a command finishes running, it leaves behind a small number like a report card. Zero means everything worked, while any other number means something went wrong—even if the program did not print a long error message.

In Linux shells, the last command’s exit status is held in $?, where 0 means success and 1–255 means failure. Conditionals (if cmd) and chaining operators (&&, ||) test this number rather than printed output. Common conventions include 1 (general error), 2 (invalid usage), 126 (not executable), 127 (command not found), and 128 + N (killed by signal N, such as 130 for SIGINT).

Why does cmd1 && cmd2 skip running cmd2 when cmd1 exits with 1?

The && operator inspects the exit status of cmd1 and runs cmd2 only if cmd1 succeeded (exit status 0). Any nonzero status is treated as failure.

In POSIX waitpid(2), _exit(status) masks the argument to its low 8 bits (status & 0xFF) inside the wait status word, where WIFEXITED(wstatus) is true and WEXITSTATUS(wstatus) extracts the code. Signal termination instead sets WIFSIGNALED(wstatus) with WTERMSIG(wstatus), which shells map to 128 + sig (making it indistinguishable from an explicit exit(130) in $?). Note that waitid(2) preserves the full 32-bit si_status on Linux, and in shell pipelines without pipefail, $? reports only the rightmost command.
