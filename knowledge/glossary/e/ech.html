ECH (Encrypted Client Hello)

A TLS extension that encrypts the ClientHello so observers cannot easily see which website name a client requested.

When you connect to a website over HTTPS, the page contents are encrypted. But in ordinary TLS, the first hello message can still reveal the site name through SNI. ECH hides that name by encrypting the sensitive part of the hello. It is like putting the website name inside the sealed envelope, not just the letter.

ECH protects metadata that normal TLS 1.3 leaves visible, especially the SNI hostname. The client gets the server's ECH public key from DNS HTTPS records, builds an inner ClientHello containing the real destination, and wraps it inside an outer ClientHello. A network observer may still see the IP address and outer connection details, but not the encrypted inner SNI. ECH works best when deployed with encrypted DNS and careful server configuration; otherwise, fallback behavior or DNS leaks can reduce its privacy benefit.

Does ECH make browsing anonymous?

No. It hides the TLS hostname from passive network observers, but the destination IP address, traffic timing, DNS behavior, and account logins can still reveal information.

ECH (RFC-compliant TLS extension work, deployed with HPKE and DNS HTTPS/SVCB configuration) splits the ClientHello into an outer, cleartext-facing message and an encrypted inner ClientHello. The client encrypts the inner message with HPKE using the ECH configuration published by the server or its fronting provider. The outer SNI typically identifies a client-facing cover service; the backend server recovers the true inner SNI after decryption. Deployment challenges include DNS distribution and freshness, retry/config mismatch handling, client-greeting fragmentation across frontends, and interaction with middleboxes that assume plaintext SNI. ECH complements, but does not replace, encrypted DNS and IP-level privacy controls.
