Embedded interpreter

A programming language runtime built directly inside another host application rather than running as a separate program.

Normally, when you run a script, a standalone language program reads and runs it from outside. With an embedded interpreter, the host application—such as a game, text editor, or web server—carries that script engine inside itself, letting users or plugins customize how the app behaves without modifying its main code.

Host programs compiled in C, C++, or Rust often embed a lightweight language like Lua, Python, or JavaScript so plugins and configuration scripts can call back into application functions. Unlike spawning an external subprocess, an embedded interpreter runs in the same process, avoiding startup overhead and letting scripts share in-memory objects directly.

Why embed an interpreter instead of running scripts as separate external commands?

Running in-process avoids the cost of spawning a new process on every call and allows scripts to read and manipulate the host application’s live data structures directly through an API.

Embedding a runtime links its VM (for example liblua or libpython) into the host address space and requires explicit lifecycle management (state creation, stack/reference counting, and teardown), marshaling across the FFI boundary, and careful attention to reentrancy and memory ownership. Because the script shares the host’s process and privileges, sandboxing requires restricting exposed host bindings, enforcing instruction or memory quotas, and guarding against untrusted bytecode or C-extension escapes.
