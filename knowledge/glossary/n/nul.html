Guide / Glossary A–Z / Terms beginning with N / NUL (Null character, 0x00)

The ASCII zero byte (0x00), used to mark the end of a C-style text string and as a padding or no-op character.

Computers store text as a sequence of numbered bytes, and the NUL character is simply the number zero. In many programs, it acts like a stop sign at the end of a sentence—telling the computer “the text ends here, stop reading”—even though nothing visible is printed on the screen.

Part of the C0 control codes, NUL (\0 in C, Ctrl+@ in terminals) is distinct from the digit '0' (0x30) and from a programming language’s NULL pointer. On Linux, NUL is forbidden inside filenames and command-line arguments because kernel system calls accept NUL-terminated C strings; tools like find -print0 and xargs -0 exploit this guarantee to safely pass filenames containing spaces or newlines.

Why is find -print0 | xargs -0 safer than find | xargs for arbitrary filenames?

POSIX filenames can contain spaces, quotes, and even newlines, which break whitespace-delimited pipelines. Because the NUL byte (0x00) is the only byte forbidden in POSIX pathnames, using NUL as the delimiter guarantees filenames are never split mid-name.

In C and POSIX ABIs (execve, open, argv, envp), strings are represented as contiguous byte arrays terminated by 0x00. This design creates a classic vulnerability class—null-byte injection—when a higher-level runtime that allows embedded 0x00 bytes (such as length-prefixed strings in Python, Java, or HTTP parsers) passes unvalidated input to a C library or kernel syscall, causing silent truncation at the first NUL. Terminals and serial lines historically used NUL as time-fill padding and ignore it on output, while storage and IPC formats that must carry arbitrary binary payloads avoid NUL termination in favor of explicit length prefixes.
