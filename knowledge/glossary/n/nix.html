Nix

Nix is a functional package manager that installs software into immutable store paths and can reproduce exact environments (historical on Tamlinux, which has retired Nix).

Most package managers drop files into shared system folders, so upgrading one program can accidentally break another. Nix instead gives every version of a program its own isolated folder in the Nix store, like keeping each tool in its own labeled drawer. Tamlinux uses Nix and Home Manager to deliver recorded assemblies of workstation software. Rolling back a generation restores that assembly; it does not by itself restore every personal file.

Nix evaluates declarative expressions to store paths addressed by cryptographic hashes of their inputs (compilers, libraries, and build scripts), which lets multiple versions of a dependency coexist without conflict. Flakes and flake.lock pin exact input revisions for reproducibility. Tamlinux packaging records assemblies in the packages repository; deploy tools switch generations without rebuilding when promoting stages.

Why does rolling back a Nix or Home Manager generation restore software versions but not your documents?

Generations are symlink trees pointing to immutable packages and managed configuration in the Nix store. Your personal files live in mutable directories (like your home folder) outside the store, so switching generations leaves them untouched.

Nix implements a purely functional build model where derivations (.drv) specify hermetic build sandboxes (isolated mount, PID, and network namespaces on Linux) whose outputs land in /nix/store/<hash>-<name>. Because store paths are content- or input-addressed and mounted read-only, atomic upgrades work by swapping profile symlinks (nix-env / Home Manager generations) rather than mutating binaries in place. Trade-offs include higher disk usage until nix-collect-garbage removes unreferenced store roots, and non-trivial wrapping needed for prebuilt dynamically linked binaries expecting FHS paths like /lib64/ld-linux-x86-64.so.2.
