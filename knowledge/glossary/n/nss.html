Guide / Glossary A–Z / Terms beginning with N / NSS (Name Service Switch)

The Name Service Switch, a Linux/glibc mechanism for choosing where system name lookups come from.

When a program asks "what is the IP address for this name?" or "which user has this ID?", the system may have several possible sources: local files, DNS, or other services. NSS is the switchboard that decides which sources to check, and in what order. On most Linux systems, its rules live in /etc/nsswitch.conf. In Linux system configuration, NSS usually means Name Service Switch, not Mozilla Network Security Services.

NSS databases include passwd, group, hosts, and services. Each line in /etc/nsswitch.conf lists modules, such as hosts: files mdns4_minimal [NOTFOUND=return] dns. Programs that use glibc lookups, such as getent hosts example.com, follow NSS rules. This is why installing nss-mdns can make .local names resolve for ordinary applications, not just Avahi tools.

Why can dig and getent give different answers for the same host name?

dig asks DNS directly. getent uses NSS, so it may consult /etc/hosts, mDNS, DNS, or other configured sources in the order nsswitch.conf specifies.

glibc NSS loads backend modules such as libnss_files.so, libnss_dns.so, or libnss_mdns.so to implement database lookups. Action rules (SUCCESS, NOTFOUND, UNAVAIL, TRYAGAIN) control fallback behavior, which is why module order and status conditions matter for correctness and latency. NSS modules run in the calling process's address space, so they are a security and stability boundary; static linking with glibc also has limited NSS support because modules are dynamically loaded. systemd provides nss-systemd/nss-resolve modules that integrate local users and resolver state into the same lookup path.
