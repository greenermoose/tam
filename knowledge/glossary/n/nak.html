NAK (Negative Acknowledge, 0x15)

An ASCII control code (byte value 0x15, typed with Ctrl+U) originally used to report a failed transmission and also bound in Unix terminals to erase the current input line.

When two devices send data over a noisy wire, the receiver needs a quick way to say “that last chunk arrived garbled, please send it again.” NAK—short for Negative Acknowledge—is that single-character “try again” signal. On a Linux command line, pressing the same key combination (Ctrl+U) tells your shell to wipe out the line you are currently typing so you can start over.

Part of the C0 control codes, NAK (0x15, decimal 21) pairs with ACK (0x06) in serial and file-transfer protocols so a receiver can request retransmission of a bad block. In interactive Unix terminals, the kernel line discipline and Readline bind Ctrl+U to the kill action: in Bash/Readline it deletes from the cursor back to the start of the line, whereas in raw canonical mode (stty) it erases the entire typed line.

Why does pressing Ctrl+U in a terminal erase your typed command instead of inserting a visible symbol?

Because Ctrl+U sends the non-printing control byte 0x15 (NAK), which the terminal line discipline or shell’s line editor intercepts as the “line kill” editing command.

In ASCII/ISO-646, NAK is C0 code 0x15 (binary 0010101, caret notation ^U). Legacy stop-and-wait ARQ protocols such as XMODEM, BISYNC, and Kermit use NAK to signal checksum/CRC failure or to initiate a transfer when the receiver is ready; on Linux TTYs, termios maps c_cc[VKILL] to 0x15 by default (inspectable via stty -a as kill = ^U), so in ICANON mode with ECHOE/ECHOK the kernel driver discards the line buffer without passing 0x15 to the foreground process unless the application switches the TTY to raw/non-canonical mode.
