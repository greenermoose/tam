NX (No-Execute / XD bit)

A hardware memory-protection feature in modern CPUs that marks data regions such as the stack and heap as non-executable.

Normally, a computer’s memory holds both program instructions (code) and information the program works on (data, like text or images). Without NX, a bug could trick the computer into treating user-supplied data as instructions and running it. NX puts a “read/write only, do not run” label on data areas so the CPU refuses to execute them.

Known as NX (AMD), XD (Intel Execute Disable), or XN (ARM Execute Never), this hardware bit enforces the W^X (“Write XOR Execute”) principle: memory pages can be writable or executable, but not both at once. On Linux, ELF binaries carry a PT_GNU_STACK header (inspectable with readelf -l) that tells the kernel whether the stack should be non-executable (RW rather than RWE), blocking classic buffer-overflow shellcode injection and forcing attackers toward harder techniques like Return-Oriented Programming (ROP).

Does enabling NX alone stop all memory-corruption exploits?

No. NX blocks executing injected shellcode on the stack or heap, but attackers can still chain together existing executable code snippets already in memory (such as Return-Oriented Programming, or ROP), which is why NX is paired with ASLR and stack canaries.

On x86_64, NX is controlled by bit 63 (the XD/NX bit) of 4-level/5-level page-table entries (PTEs) and must be enabled via bit 11 (NXE) of the IA32_EFER MSR; fetching an instruction from a page with bit 63 set raises a #PF (Page Fault) with error code bit 4 (I/D = 1, instruction fetch). Edge cases include JIT compilers (browsers, JVM, eBPF JIT) that must allocate PROT_WRITE, emit machine code, and transition pages via mprotect() to PROT_EXEC (subject to SELinux execmem or memfd W^X policies), and legacy binaries with an executable PT_GNU_STACK flag that can silently weaken process protections if READ_IMPLIES_EXEC is triggered.
