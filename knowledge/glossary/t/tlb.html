Guide / Glossary A–Z / Terms beginning with T / TLB (Translation Lookaside Buffer)

A Translation Lookaside Buffer (TLB) is a small, high-speed hardware cache inside the processor that stores recent translations from virtual memory addresses to physical RAM addresses.

Programs use virtual addresses—like room numbers in a building directory—rather than raw locations on memory chips. Looking up the full directory every single time the processor reads data would be slow, so the TLB acts like a sticky note on the processor’s desk holding the handful of room-to-floor translations used most recently.

On each memory access, the Memory Management Unit (MMU) checks the TLB first; a TLB hit resolves the physical frame in a cycle or two, whereas a TLB miss forces a multi-level page-table walk in RAM. Using larger pages (such as 2 MiB or 1 GiB hugepages instead of 4 KiB pages) lets each TLB entry cover more memory, reducing misses in databases or virtual machines—tools like perf stat -e dTLB-load-misses reveal when a workload is thrashing the TLB.

Why can enabling hugepages speed up a memory-heavy program without adding more RAM?

Each TLB slot maps one page regardless of its size. Switching from 4 KiB pages to 2 MiB pages multiplies the memory covered per TLB entry by 512, so working sets that previously overflowed the TLB stay cached and avoid expensive page-table walks.

Modern CPUs split the TLB into per-core L1 instruction/data TLBs (iTLB/dTLB) and a larger unified L2 STLB, tagged with Address Space Identifiers (ASIDs on ARM/RISC-V, PCIDs on x86-64) so context switches need not flush every entry. Entries cache not only the physical frame number but also protection bits (R/W/X, user/supervisor), memory type, and dirty/accessed state. Modifying page tables—such as munmap(), mprotect(), or copy-on-write splits—requires local invlpg or cross-core TLB shootdowns via Inter-Processor Interrupts (IPIs), which can become a scaling bottleneck on many-core Linux systems.
