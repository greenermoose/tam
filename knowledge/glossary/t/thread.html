Thread

The smallest unit of execution that an operating system’s scheduler can run independently inside a program.

Think of a kitchen: the whole restaurant is a program, and each cook working in that kitchen is a thread. All the cooks share the same pantry and counters, so they can pass ingredients to each other quickly, and multiple cooks let the kitchen handle several orders at once. However, if two cooks grab the same pan without coordinating, they can make a mess.

Unlike separate processes—which each have their own isolated memory space—threads inside the same process share virtual memory and open file descriptors, while each thread keeps its own stack, instruction pointer, and CPU registers. On Linux, you can view individual threads of a process with ps -eLf or top -H. Because threads share memory, communication is fast, but missing synchronization can cause data races or deadlocks.

If one thread in a process triggers a segmentation fault (SIGSEGV), what usually happens to the other threads in that process?

The entire process is terminated by default. Because all threads share the same address space and signal disposition, a fatal memory fault or unhandled terminating signal brings down the whole process, not just the offending thread.

On Linux (NPTL 1:1 threading model), user-space pthread threads map directly to kernel task_struct entities created via clone(2) with CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD. Each thread has a distinct kernel TID (gettid()), shared TGID (getpid()), its own kernel and user stacks, and Thread-Local Storage addressed via architecture-specific base registers (%fs on x86_64, TPIDR_EL0 on AArch64). Contention primitives like futex(2) avoid syscalls on the uncontended path, while subtle failure modes include false sharing across 64-byte cache lines, priority inversion, and calling non-async-signal-safe functions after fork() in a multithreaded process.
