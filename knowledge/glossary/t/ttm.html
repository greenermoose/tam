TTM (Translation Table Manager)

The Linux kernel’s Direct Rendering Manager (DRM) memory manager that coordinates buffer placement between discrete GPU video RAM and system memory.

A dedicated graphics card has its own fast video memory, separate from your computer’s main memory. When games, desktops, or video apps need more graphics memory than fits on the card, something has to decide what stays in fast GPU memory and what gets moved out to main RAM. In Linux, TTM is the behind-the-scenes traffic controller in the kernel that shuffles those graphics buffers back and forth so programs keep running.

Discrete GPU drivers such as amdgpu, nouveau, and xe use TTM, whereas simpler unified-memory or display-only drivers often use GEM’s CMA or shmem helpers directly. When VRAM fills up, TTM evicts idle buffer objects across the PCIe bus to GTT (system RAM mapped for GPU access) and migrates them back when needed, which can show up as sudden frame-time spikes or heavy PCIe traffic under memory pressure.

What happens when a game allocates more textures than fit in a discrete GPU’s VRAM under TTM?

TTM evicts less-recently-used buffer objects from VRAM into system RAM (GTT) over PCIe, allowing allocation to succeed at the cost of slower access or migration stalls when evicted buffers are needed again.

Located in drivers/gpu/drm/ttm/, TTM manages struct ttm_buffer_object instances across driver-defined placement domains (TTM_PL_VRAM, TTM_PL_TT for GART/GTT, TTM_PL_SYSTEM), enforcing placement constraints, alignment, and caching attributes (write-combining vs. cached). Eviction and migration are synchronized against GPU command execution via dma_resv reservation objects and dma_fence timelines so buffers are never moved or freed while in flight on a hardware ring. Under heavy oversubscription, LRU eviction combined with ttm_bo_vm page-fault handling can cause buffer thrashing across PCIe or allocation failures when pinned scanout and ring buffers fragment VRAM.
