TCG (Tiny Code Generator)

QEMU’s cross-architecture dynamic binary translator, which lets an emulator run software built for one kind of processor on a completely different kind of processor.

Imagine reading a recipe written in a language you do not speak: a translator reads each step and turns it into instructions you can follow right away. TCG does that for computer processors. It matters because it lets you test or run programs meant for another kind of chip—such as phone or embedded software—on an ordinary desktop computer without needing that physical hardware.

In Linux virtualization with QEMU, TCG is the fallback execution engine when hardware virtualization (KVM) cannot be used—either because the host and guest architectures differ (for example, running an aarch64 guest on an x86_64 host) or because /dev/kvm is unavailable. Because every guest instruction is decoded and translated in software rather than executed directly by the CPU, TCG is much slower than KVM, though multi-threaded TCG (-accel tcg,thread=multi) lets multi-core guests spread work across host cores.

Why would you choose TCG over KVM when both are available on the same machine?

You use TCG when the guest uses a different CPU architecture than the host (such as emulating ARM on x86_64), or when you need deterministic or instrumented execution. KVM only runs guests that match the host’s CPU architecture because it executes guest instructions directly on the physical processor.

TCG is a two-stage retargetable JIT compiler: guest basic blocks (Translation Blocks, TBs) are lifted from target machine code into an architecture-neutral intermediate representation (TCG IR), optimized (constant folding, dead-code elimination, register allocation), and lowered to host machine code in a fixed-size translation cache. Direct TB chaining patches control transfers between translated blocks to avoid returning to the main dispatch loop except across page boundaries or pending interrupts. SoftMMU implements guest virtual-to-physical translation with a per-vCPU software TLB, while qemu-user forwards syscalls to the host kernel and must emit explicit host barriers when emulating weaker memory models (e.g., ARMv8 on TSO x86_64).
