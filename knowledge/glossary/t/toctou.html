TOCTOU (Time-of-Check to Time-of-Use)

TOCTOU (Time-of-Check to Time-of-Use) is a race-condition bug that occurs when a program checks a resource’s state or permissions and then uses it, leaving a window in which an attacker can swap or alter the resource.

Imagine checking that a locked box has your name on it, looking away for a moment, and then reaching in—only to find someone swapped the box while you blinked. In software, if a program checks that a file is safe and then opens it by name a split second later, another program can replace that file in between.

In Linux, classic TOCTOU bugs happen when a privileged script or program runs access() or stat() on a path in a shared directory like /tmp and then calls open() on the same path string. An unprivileged user can race a symlink into place between the two calls, tricking the program into overwriting an unintended file. Using O_NOFOLLOW, mktemp/O_CREAT | O_EXCL, or operating on an already-open file descriptor avoids re-resolving the path.

Why is calling access(path, W_OK) followed by open(path, O_WRONLY) unsafe in a shared directory?

Because the kernel resolves the path string twice—once during access() and again during open(). Between those two syscalls, another process can replace the target with a symlink to a sensitive file, causing open() to act on a different object than the one checked.

Classified as CWE-367, filesystem TOCTOU arises from non-atomic path-name resolution across separate syscalls. Robust mitigation in POSIX/Linux anchors operations to an open directory file descriptor via openat(2), fstatat(2), and renameat2(2), combined with O_NOFOLLOW or openat2(2) resolve flags (RESOLVE_NO_SYMLINKS, RESOLVE_BENEATH) to prevent path-component traversal races. Note that TOCTOU also occurs outside filesystems—for example in double-fetch kernel vulnerabilities where user-space memory is read twice across a validation boundary without copying it into kernel space first.
