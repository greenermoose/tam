IRQ - Interrupt Request

A signal from hardware or a controller telling the processor to pause its current work and handle an urgent event.

An IRQ is like a tap on the CPU’s shoulder. Instead of the processor wasting time constantly asking the keyboard, mouse, or network card, “Do you have anything new yet?”, the device sends an IRQ only when something actually happens—such as a key press or an arriving network packet. The processor briefly pauses what it was doing, runs a small routine to handle the event, and then returns right back to the program you were using.

On Linux, you can inspect active interrupts and how often each CPU core handles them by reading /proc/interrupts. Interrupts come from hardware devices (storage controllers, NICs, timers) and from inter-processor calls (IPIs). When a single device generates millions of events per second (such as a fast 10 Gbps network card), handling every packet via a separate IRQ can overwhelm one CPU core; Linux mitigates this with IRQ affinity (/proc/irq/<n>/smp_affinity), irqbalance, and NAPI polling, which temporarily switches a busy network driver from interrupt-driven mode to batched polling.

Why does Linux sometimes use polling (like NAPI) under heavy network load instead of relying purely on IRQs for every packet?

Each hardware IRQ forces a CPU context save and interrupt-handler entry. At very high packet rates, per-packet interrupts can consume 100% of a core just entering and exiting handlers (interrupt livelock), whereas polling drains a whole ring of packets in one batch.

On modern x86 and ARM64 systems, legacy level- or edge-triggered PIC/IO-APIC pin lines have largely been superseded by PCIe MSI and MSI-X, which deliver interrupts as posted memory writes to the local APIC (or GICv3 ITS) carrying a distinct vector number per queue without shared-line ambiguity. Linux splits interrupt handling into a fast, non-sleeping hardirq top half (request_irq / IRQF_*) and a deferred bottom half (softirqs, tasklets, or threaded IRQs via request_threaded_irq, standard on PREEMPT_RT kernels). Misconfigured IRQ affinity or shared legacy IRQ lines can cause latency spikes, missed real-time deadlines, or nobody cared spurious-interrupt disabling by the kernel.
