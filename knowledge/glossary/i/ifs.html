IFS (Internal Field Separator)

IFS is the shell variable that holds the characters a shell uses as separators when it splits text into words.

Imagine a row of beads with small gaps between them. The gaps let you count the beads as separate things. IFS is the list of characters a shell treats as those gaps. By default the gaps are a space, a tab and a new line. If you change the list to a comma, commas become the gaps and spaces stay inside a word. Follow IFS and splitting for the full story.

In a POSIX shell the default IFS value is the three bytes space, tab and newline. On a fresh shell, printf '%s' "$IFS" | od -An -tx1 prints 20 09 0a. Setting IFS=, makes comma the separator, so an unquoted $line holding one,two,three becomes three fields. Writing "$line" instead stops splitting altogether. The word splitting page shows this with captured output, and the precise rules cover the edge cases.

Why does changing IFS to a comma not split a quoted value?

Quotes mark the expansion as text to keep whole. A shell splits only the results of unquoted expansions, so quoting removes that text from the splitting step.

IFS has three roles: it supplies delimiters for field splitting, it separates values when the special parameter * expands without quotes, and it sets field boundaries for read. POSIX treats space, tab and newline as IFS white space whenever they appear in IFS; other locale white-space characters may also count, which is implementation-defined. A non-whitespace IFS character behaves differently: each one terminates a field, so consecutive delimiters can yield empty fields. If IFS is unset, splitting and read behave as if it held the three default bytes. If IFS is set to an empty string, no splitting happens, although a field made entirely from an empty expansion is still removed. A value containing bytes that are not valid characters gives unspecified results. See POSIX Shell Command Language sections 2.5.3 and 2.6.5, and Bash manual.
