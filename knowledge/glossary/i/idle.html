Guide / Glossary A–Z / Terms beginning with I / Idle

A system state in which no recent user input or active wake inhibitor keeps the session awake.

Idle works like a motion-sensor hallway light: when nobody types or moves the mouse for a while, the computer notices it is not being used and dims the screen, locks for privacy, or goes to sleep to save battery. Apps playing a movie or running a video call can ask the computer to stay awake anyway.

In a desktop session, idle timers track how long it has been since the last keyboard or pointer input and trigger staged actions—dimming, screen locking, display power-off, and suspend. Note the difference between session idle (no user input) and CPU idle (no runnable tasks). Media players, browsers, or CLI tools like systemd-inhibit can hold an inhibitor so the screen does not lock during playback or a long build.

Why does your screen usually stay on while watching a full-screen video even though you are not touching the keyboard or mouse?

The video player or browser registers an idle inhibitor with the compositor or session manager, telling it to pause screen-blanking and lock timers while playback is active.

Idle policy spans compositor protocols and session power management: Wayland compositors implement ext-idle-notify-v1 to signal timeout/resume events to daemons (such as swayidle or hypridle) and idle-inhibit-unstable-v1 to let mapped surfaces suppress timers. System-level sleep and shutdown locks coordinate through systemd-logind D-Bus inhibitors (Inhibit() returns a file descriptor whose closure releases the lock). Common failure modes include audio-only streams lacking a Wayland surface inhibitor, orphaned inhibitor FDs, or races between PrepareForSleep signals and screen-locker frame commits before suspend.
