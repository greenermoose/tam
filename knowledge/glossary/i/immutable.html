Immutable

Unable to be modified after creation; any change produces a separate new version instead of altering the original.

Think of an immutable item like a printed book rather than a whiteboard you erase and scribble over. If you want to change something, you print a new edition while the old copy stays intact. That makes it much easier to undo mistakes or be sure a file was not quietly altered.

In Linux systems with immutable package stores or read-only root filesystems, installed software cannot be edited in place; updates build a new directory or image alongside the old one and switch a link at activation or boot. By contrast, traditional mutable setups overwrite system files directly, which can leave a machine half-updated if a failure interrupts the process.

How do you “update” an immutable package or system image if it cannot be edited in place?

You build a new version in a separate location and switch the active pointer or boot entry to it, leaving the previous immutable version intact for fast rollback.

Immutability binds an object’s identity (often a cryptographic content hash) to its exact byte sequence, enabling lock-free sharing, deduplication, reproducible builds, and atomic activation via symlink flips or OSTree/Btrfs snapshots. Key trade-offs include higher transient storage usage—requiring periodic garbage collection of unreferenced generations—the need to separate mutable state (such as /var and user home directories), and indirection when deploying emergency hotfixes.
