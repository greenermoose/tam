Cgroup (control group)

A Linux kernel feature that organizes processes into groups so their CPU, memory, I/O, and process-count usage can be measured and limited together.

Think of a cgroup as a labeled budget envelope for running programs. Instead of letting one runaway browser tab or background job eat all of your computer’s memory and freeze everything else, the system puts related programs into an envelope with its own spending cap and tracks them as a single unit.

On modern Linux distributions using systemd, every user session, system service (.service), and container runs inside its own cgroup under /sys/fs/cgroup. Unlike classic ulimit settings—which apply per process and can be sidestepped by forking—cgroups apply cumulatively to an entire process tree, making them the foundation for containers and systemd resource limits like MemoryMax= or CPUWeight=.

Why can’t a service bypass a cgroup memory limit by spawning child processes, unlike a per-process ulimit?

Child processes inherit their parent’s cgroup membership, and the cgroup memory controller accounts for the combined usage of all processes in that group against the shared limit.

Linux cgroups v2 (cgroup2 unified hierarchy) replaces cgroups v1’s per-controller trees with a single hierarchy where controllers (cpu, memory, io, pids, cpuset) are enabled downward via cgroup.subtree_control under the no-internal-processes rule (processes may only reside in leaf cgroups, except the root). Memory accounting tracks anonymous pages, page cache, and kernel slab (memory.current, memory.high throttling vs. memory.max OOM trigger, and memory.oom.group for atomic group kills), while systemd delegates subtrees safely via Delegate=yes and Pressure Stall Information (cpu.pressure, memory.pressure) exposes stall metrics for userspace OOM daemons like systemd-oomd.
