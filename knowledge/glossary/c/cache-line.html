Guide / Glossary A–Z / Terms beginning with C / Cache line

A cache line is the fixed-size block of memory transferred as a single unit between main memory and a CPU cache.

When a processor needs a single byte from main memory, it does not fetch just that one byte—it grabs a whole neighboring chunk at once, much like picking up an entire egg carton instead of carrying one egg at a time. That chunk is a cache line, and keeping related data together inside it makes programs noticeably faster.

On most modern x86 and ARM64 Linux systems, a cache line is 64 bytes (some architectures, such as Apple Silicon, use 128 bytes). Reading one byte pulls all 64 bytes into L1/L2/L3 cache, so iterating sequentially through an array hits data already fetched by the previous read (spatial locality). Conversely, if two CPU threads modify separate variables that happen to sit in the same 64-byte cache line, the cores fight over ownership of that line—a slowdown called false sharing. You can check the line size on Linux with getconf LEVEL1_DCACHE_LINESIZE.

Why can two threads updating completely separate variables in a struct still slow each other down?

Because CPU caches track ownership per cache line, not per variable. If both variables share the same 64-byte line, each write invalidates the other core’s copy (false sharing), forcing repeated cache-coherence traffic.

Hardware caches index sets and compare physical or virtual tags at cache-line granularity (typically 64 bytes, 6-bit byte offset). Each line carries coherence state (such as MESI/MOESI: Modified, Exclusive, Shared, Invalid, Owned) plus valid and dirty metadata. Unaligned accesses straddling a line boundary split into two cache lookups and can lose atomicity unless handled by bus or cache-line locks. In concurrent kernel and systems code, hot per-CPU or per-thread fields are padded or aligned (__aligned(SMP_CACHE_BYTES) or alignas(64)) to prevent false sharing, while hardware prefetchers track stride patterns across adjacent lines.
