Checkpoint

A saved state captured before making a system change so you can roll back cleanly if the change fails or breaks something.

Before painting a room, you lay down drop cloths and take a quick photo of where everything goes so you can put it back if something goes wrong. A checkpoint is that “before” save point for your computer: if an update or configuration edit goes badly, you have a known-good state to return to.

Real systems have multiple independent layers—such as a Btrfs filesystem snapshot, bootloader/EFI boot entries, and mutable configuration files—and a checkpoint in one layer does not automatically back up or restore another. For example, rolling back a root filesystem snapshot restores system binaries, but if an EFI partition file or firmware setting changed outside that subvolume, it stays changed.

If you take a filesystem snapshot of / before editing /boot/efi, will rolling back that snapshot undo a broken EFI boot file?

No. /boot/efi is typically a separate FAT32 partition, not part of the / subvolume, so a root filesystem checkpoint does not cover or restore EFI partition contents.

A sound checkpoint requires three properties: boundary specification (identifying which storage volumes, boot partitions, or mutable state stores are in scope), writer quiescence or copy-on-write atomicity (preventing torn multi-file state during capture), and integrity verification of the captured artifact. Checkpoints are taken immediately before mutations of the target layer for short-horizon recovery, whereas long-term fallback relies on an established, tested recovery anchor rather than an unbounded chain of ad-hoc pre-change captures.
