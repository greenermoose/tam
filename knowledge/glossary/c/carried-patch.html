Carried patch

A carried patch is a temporary local code fix maintained on top of an upstream software package until the original project releases the fix itself.

When a piece of software has a bug and the original authors have not released a new version yet, a distribution like Tamlinux may apply its own small repair so users are not stuck waiting. That temporary repair is a carried patch: it is kept around only until the official software includes the fix, at which point it can be safely removed.

A carried patch is published on a public fork, built into a local package, and retired once upstream includes the fix. Carrying patches keeps systems working without waiting months for an upstream release, but every carried patch adds merge and testing work whenever the upstream package updates to a new version.

Why should every carried patch record the upstream version or condition that retires it?

Without a clear retirement condition, temporary fixes are easily forgotten and keep getting re-applied or rebased long after upstream has already solved the problem, creating unnecessary maintenance work and merge conflicts.

A carried patch represents a bounded divergence from upstream source with explicit provenance: a tracked commit on a public fork branch, a local PKGBUILD applying or referencing that revision, and a concrete retirement predicate tied to an upstream release tag or commit merge. Operationally, carrying patches introduces rebase conflict surface during version bumps and ABI drift risk if the patch alters public symbols; keeping patches minimal, upstream-submitted, and version-gated prevents silent long-term fork maintenance.
