Capability

A capability is a fine-grained permission bit that grants a Linux process a specific privileged action without giving it full root power.

Traditionally, Linux had an all-or-nothing rule: either you were a normal user with limited rights, or you were root with total control over the whole machine. Capabilities split that master key into separate smaller keys—so a web server can be given just the key to open a protected network port without getting the keys to erase disks or read everyone’s files.

Linux capabilities divide root’s authority into named flags such as CAP_NET_BIND_SERVICE (bind ports below 1024), CAP_NET_RAW (create raw sockets for tools like ping), and CAP_SYS_ADMIN (broad administrative operations). Instead of making a binary setuid-root, administrators can attach only the needed capability to an executable with setcap cap_net_bind_service=+ep /usr/bin/myserver, inspect it with getcap, or check a running process’s capabilities in /proc/<pid>/status (CapEff, CapPrm).

Why is granting CAP_NET_RAW to /usr/bin/ping safer than making it setuid root?

Setuid root gives the process full superuser power if a bug is exploited, whereas CAP_NET_RAW grants only raw-socket access—limiting the damage if ping is compromised.

Linux capabilities (capabilities(7)) are tracked per thread across five bitmasks in struct cred: Permitted (P), Effective (E), Inheritable (I), Bounding (B), and Ambient (A), alongside securebits flags (such as SECBIT_NO_SETUID_FIXUP). Across execve(2), new masks follow strict transformation rules combining the thread’s I/A/B sets with file capability attributes stored in security.capability extended attributes: unprivileged processes can preserve capabilities across execve only via the Ambient set or file capabilities. User namespaces grant a full capability set inside the namespace while isolating host-namespace checks, though broad capabilities like CAP_SYS_ADMIN or CAP_BPF remain near-root-equivalent on the host.
