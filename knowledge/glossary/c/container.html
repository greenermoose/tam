Guide / Glossary A–Z / Terms beginning with C / Container

A container is an isolated group of processes that carries its own software environment while sharing the host computer’s operating system kernel.

Think of a shipping container on a cargo ship. Every container holds its own packed goods and stays separate from its neighbors, yet all the containers ride on the same ship and use the same engine. On a computer, a container lets an app run with the exact libraries and settings it expects without interfering with the rest of your system—and without needing to boot a whole second operating system.

On Linux, containers (managed by tools like Podman or Docker) feel lightweight because they do not emulate hardware or run a guest kernel the way a full virtual machine does. Instead, the host kernel isolates what a containerized process can see (its own filesystem root, process tree, and network interfaces) and limits how much CPU or memory it can use. Because they share the host kernel, Linux containers can only run Linux binaries compatible with that kernel—not Windows kernels.

How does a Linux container differ from a virtual machine in how it uses the kernel?

A virtual machine boots its own guest OS kernel on virtualized hardware, whereas a container runs normal processes directly on the host’s Linux kernel with isolated views and resource limits.

A Linux container is not a single kernel object; it is a user-space abstraction assembled from kernel primitives: namespaces (mnt, pid, net, ipc, uts, user, cgroup, time) to partition visibility, cgroups v2 to meter and cap CPU, memory, and I/O, OverlayFS (or similar copy-on-write filesystems) to stack an immutable OCI image under a writable upper layer, and security boundaries such as dropped capabilities, seccomp-bpf syscall filters, and LSMs. Because the syscall boundary is shared with the host kernel, a kernel vulnerability inside a container can enable privilege escalation unless mitigated by user namespaces, strict seccomp profiles, or microVM runtimes.
