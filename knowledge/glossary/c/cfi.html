CFI (Control-Flow Integrity)

A compiler and hardware security defense that prevents attackers from redirecting a program’s indirect jumps, function pointers, or returns to unintended code.

When a program runs, it follows a planned map of which function can call or return to which other function. Memory bugs can let an attacker scribble over a return address or function pointer to hijack that path. Control-Flow Integrity acts like guardrails on a highway, checking every turn against the map and stopping the program if it tries to jump somewhere it should not.

On Linux, CFI splits into two halves: forward-edge protection for indirect calls and virtual method tables (such as Clang’s -fsanitize=cfi or KCFI in the Linux kernel), and backward-edge protection for function returns (such as Intel CET shadow stacks or ARM Pointer Authentication). Because backward-edge hardware shadow stacks track exact dynamic return addresses, they are much stricter than static forward-edge checks.

Why is a hardware shadow stack stronger for function returns than a static forward-edge CFI check?

A static check only knows all possible callers of a function, whereas a shadow stack records the exact return address pushed when that specific call was made.

Forward-edge CFI restricts indirect call/jmp targets to equivalence classes derived from the static control-flow graph—often by function-signature type hash (Clang CFI / Linux KCFI) plus hardware landing-pad instructions (ENDBR64 in Intel IBT, BTI on AArch64)—leaving valid-but-unintended targets within the same signature class reachable (COOP/JOP within coarse equivalence sets). Backward-edge CFI pairs a kernel-protected, read-only shadow stack (Intel CET SSP, ARM GCS) or cryptographic pointer authentication codes (ARM PAC) with RET to defeat ROP without the race conditions of software shadow stacks, though dynamic linking (PLT/JITs), setjmp/longjmp, and inline assembly require explicit ABI/compiler annotations to avoid false-positive #CP faults.
