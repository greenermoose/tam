Cache

A cache is a small, fast storage layer that keeps copies of frequently or recently used data closer to where it is needed so future requests finish faster.

A cache works like keeping the tools you use every five minutes on your desk instead of walking down to the basement storage room each time. Because desk space is limited, you only keep what you used recently and put older items back when the desk fills up.

Computing uses caches at many layers: CPU L1/L2/L3 hardware caches sit between registers and RAM, the Linux kernel’s page cache keeps recently read disk blocks in free RAM, and package or web caches store downloaded files locally. Caching speeds up reads when workloads show temporal locality (reusing the same item soon) or spatial locality (using nearby items). The trade-off is staleness: when the underlying data changes, cached copies must be updated or invalidated.

Why does Linux often show very little “free” RAM in free -h even when no large applications are running?

Linux puts unused RAM to work as a disk page cache, keeping recently read files in memory so repeat reads are fast. The kernel reclaims that memory immediately when an application needs it, so check the “available” column rather than “free.”

A cache is a bounded, often set-associative store parameterized by capacity, line or block size, associativity, replacement policy (LRU, PLRU, FIFO, ARC), and write policy (write-through versus write-back with dirty-bit tracking). Cache misses decompose into the 3Cs—compulsory (cold), capacity, and conflict misses—plus coherence misses in multiprocessors. In software and OS design, cache-aware tiling bounds miss rates against L1 or last-level cache capacity, while hardware and kernel caches must also guard against side-channel timing leaks (such as Flush+Reload and Prime+Probe) and stale-data races when DMA bypasses coherence.
