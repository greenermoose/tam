Checksum

A short, fixed-size value calculated from a block of data so you can verify whether the data was altered or corrupted.

A checksum is like counting the total number of pages and words in a package before mailing it, and writing that count on the box. When the box arrives, the receiver recounts—if the numbers do not match, they know something was lost or damaged in transit, even if they cannot tell which exact word changed.

Checksums serve different purposes depending on whether you are guarding against accidental hardware/network glitches or intentional tampering. Fast non-cryptographic checksums like CRC32 (used in Ethernet frames and ZIP files) catch random bit flips, whereas Linux package managers and ISO downloads use cryptographic hashes like SHA-256 (sha256sum) so an attacker cannot craft a malicious file with the same checksum.

Why shouldn’t you rely on CRC32 to verify that a downloaded software installer wasn’t tampered with by an attacker?

CRC32 is linear and designed only to detect accidental bit errors—an attacker can easily modify a file and adjust a few bytes so the CRC32 value stays identical.

Error-detecting codes (internet checksum in RFC 1071, CRC polynomials over GF(2), or xxHash) optimize for hardware/SIMD throughput and burst-error detection but lack preimage and collision resistance. Cryptographic digests (SHA-256, BLAKE2b/BLAKE3) provide collision and second-preimage resistance (~2^(n/2) and ~2^n work respectively), though verifying a plain checksum without an authenticated signature (PGP/minisign) or trusted channel only proves consistency against the published digest, not authenticity; filesystems like Btrfs and ZFS also store per-block checksums (CRC32C, xxHash64, SHA-256) in parent metadata trees to detect silent bit rot and direct self-healing from mirrors.
