CTS-HMAC (Ciphertext Stealing with HMAC)

A Kerberos encryption type that combines AES-CBC encryption with ciphertext stealing and an HMAC integrity tag.

Many encryption methods pack data into fixed-size boxes, which normally forces them to add extra filler bytes when a message does not fill the last box. Ciphertext stealing avoids that wasted space by borrowing a few bytes from the previous box so the encrypted message stays the exact same length. Adding HMAC attaches a tamper-evident seal so Kerberos knows if a login ticket was altered in transit.

On Linux systems using Kerberos (visible in klist -e or /etc/krb5.conf), common encryption types are aes256-cts-hmac-sha1-96 and the newer aes256-cts-hmac-sha384-192. Ciphertext stealing keeps Kerberos tickets compact, while the trailing number (96 or 192) indicates the bit length of the integrity tag appended to each message.

Why does Kerberos use ciphertext stealing instead of standard padding like PKCS#7?

Standard padding expands the ciphertext to the next 16-byte block boundary, adding up to 16 extra bytes per message. Ciphertext stealing borrows bytes from the second-to-last block so the ciphertext matches the plaintext length (for any message longer than one block), saving space in small, frequent network tickets.

Specified in RFC 3962 (aes*-cts-hmac-sha1-96) and RFC 8009 (aes*-cts-hmac-sha256-128, aes*-cts-hmac-sha384-192). Both use AES-CBC with CBC-CS3 ciphertext stealing (the final two blocks are swapped after encryption when the input exceeds one 16-byte block and is not block-aligned). Key derivation splits a base key into independent encryption (Ke) and integrity (Ki) subkeys via DK() using PBKDF2-HMAC-SHA1 (RFC 3962) or KDF-HMAC-SHA2 (RFC 8009). Notably, Kerberos uses an Encrypt-and-MAC construction—HMAC(Ki, confounder || plaintext)—relying on the random 16-byte confounder block and strict decryption-before-MAC-check discipline to avoid padding-oracle leaks, while RFC 8009 retires SHA-1 in favor of SHA-256/SHA-384.
