CTR (Counter mode)

A block-cipher mode that encrypts an incrementing counter to turn a fixed-size block cipher into a stream cipher.

Instead of scrambling each chunk of a file directly, CTR mode uses a secret key and a steadily counting number (1, 2, 3, and so on) to generate a stream of unpredictable bytes, then blends that stream with your data. Because every block’s counter number is known ahead of time, your computer can encrypt or read any part of a file out of order without waiting for earlier parts.

You encounter CTR mode in SSH (aes256-ctr), IPsec, and as the encryption engine inside AES-GCM. It supports parallel processing across CPU cores, random-access reads, and arbitrary message lengths without padding. However, CTR alone does not detect tampering, and reusing the same nonce (starting value) with the same key completely exposes the plaintext.

Why is reusing a nonce in CTR mode catastrophic for confidentiality?

Reusing a nonce with the same key produces the exact same keystream. An attacker who XORs two ciphertexts encrypted with that same keystream cancels the keystream out and recovers the XOR of the two plaintexts, often allowing full message recovery.

Defined in NIST SP 800-38A: for a block cipher E_K of block size b (128 bits for AES), each counter block T_i = IV || i (commonly a 96-bit nonce concatenated with a 32-bit big-endian counter) yields keystream block O_i = E_K(T_i), and ciphertext C_i = P_i XOR O_i (truncated for a partial final block). Key properties and failure modes: (1) Malleability—flipping a bit in C_i flips the identical bit in P_i, so production protocols pair CTR with a MAC (such as GHASH in AES-GCM). (2) Counter wraparound—a 32-bit counter caps a single (K, IV) pair at 2^32 blocks (64 GiB for AES) before colliding with i = 0. (3) Hardware efficiency—decryption uses only the forward cipher E_K, omitting the inverse cipher circuit.
