Clone

Creating a full local copy of a version-control repository, including its commit history, branches, and remote link.

Downloading a single file is like photocopying one page of a book, while cloning a repository is like getting your own complete copy of the entire binder—every past draft, every note, and the address of the original so you can fetch updates later.

Running git clone <url> creates a new directory, downloads the project’s files and history into a hidden .git folder, checks out the default branch, and configures origin so git pull and git push know where to sync. For huge repositories where you only need recent code, git clone --depth 1 performs a shallow clone to save time and disk space.

How does git clone differ from downloading a ZIP archive of a project’s files?

A ZIP archive gives you only a static snapshot of the current files, whereas git clone includes the commit history, branches, and remote link so you can inspect changes, switch branches, and pull future updates.

Internally, git clone negotiates a packfile over HTTPS, SSH (git-upload-pack), or local transport, transferring reachable Git objects (commits, trees, blobs, tags) and refs into .git/objects, initializing .git/refs/remotes/origin/*, and populating the index and working tree for HEAD. Variants alter storage and reachability: --depth N writes a shallow boundary in .git/shallow, --filter=blob:none defers blob fetches in partial clones, --bare omits the working tree for mirrors, and --reference borrows objects via .git/objects/info/alternates (which can break if the source repo prunes objects).
