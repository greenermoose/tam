Core

A core is an independent processing unit inside a CPU that can read and execute program instructions on its own.

If a CPU chip is a kitchen, each core is a separate chef working at their own station. A single-core processor has one chef doing one step at a time, while a multi-core processor has several chefs working simultaneously on different tasks—or splitting a big job into pieces—so your computer stays responsive when multiple apps are open.

Each physical core has its own instruction decoder, execution units, registers, and small private L1/L2 caches, while cores on the same chip usually share a larger L3 cache and system memory. On Linux, tools like nproc, lscpu, or htop often show more “CPUs” than physical cores when Simultaneous Multithreading (SMT, or Hyper-Threading) is enabled, because each physical core presents two logical threads to the scheduler. Note that adding cores only speeds up work that can run in parallel; a single-threaded program still runs on one core at a time.

If lscpu reports 8 CPUs on a 4-core processor, why does that happen?

Simultaneous Multithreading (SMT) lets each of the 4 physical cores expose 2 logical CPUs to Linux, allowing one core’s idle execution units to be shared by two hardware threads.

A modern CPU core is a superscalar, out-of-order execution pipeline with front-end fetch/decode, register renaming, reorder buffer, load/store queues, and private L1I/L1D and L2 caches connected to a shared last-level cache via a ring or mesh coherent interconnect. Hardware cache coherence (e.g., MESIF or MOESI) keeps shared memory consistent across cores, meaning false sharing—two cores writing to distinct variables on the same 64-byte cache line—causes costly cache-line bouncing. Heterogeneous designs (such as big.LITTLE or P-core/E-core) pair cores with differing microarchitectures and frequency-voltage curves, requiring capacity- and energy-aware kernel scheduling.
