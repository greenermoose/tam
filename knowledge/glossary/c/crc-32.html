Guide / Glossary A–Z / Terms beginning with C / CRC-32 (32-bit Cyclic Redundancy Check)

CRC-32 is a standard 32-bit error-detecting checksum used in Ethernet frames, PNG images, ZIP archives, and storage formats to catch accidental data corruption.

Imagine writing down a long phone number and adding a quick verification digit at the end so anyone copying it can spot a typo. CRC-32 does the same thing for digital files, producing a compact 4-byte number from a block of data. When a file is downloaded or read back, the computer recalculates that number; if even one bit was flipped by a glitch or noisy cable, the numbers will not match. It is built to catch accidents, not deliberate tampering.

You encounter CRC-32 constantly in gzip and .zip headers, PNG chunk checks, Ethernet FCS trailers, and filesystem metadata (such as ext4 and Btrfs using the Castagnoli variant, CRC-32C). Unlike cryptographic hashes such as SHA-256, CRC-32 is linear and easy to forge, so it cannot verify software authenticity. On Linux, cksum and Python’s zlib.crc32() compute IEEE 802.3 CRC-32, while modern CPUs accelerate CRC-32C with dedicated hardware instructions.

Why shouldn’t you use CRC-32 to verify that a downloaded ISO image hasn’t been tampered with by an attacker?

CRC-32 is linear over GF(2), so an attacker can modify a file and adjust a few extra bits to produce the exact same 32-bit checksum. Cryptographic hashes like SHA-256 are required to resist intentional tampering.

CRC-32 computes the remainder of a message polynomial over GF(2) divided by a degree-32 generator, guaranteeing detection of all single-bit, double-bit, odd-weight, and ≤32-bit burst errors. Two incompatible polynomials dominate: IEEE 802.3 (0x04C11DB7, reflected 0xEDB88320, with 0xFFFFFFFF pre/post-inversion in Ethernet, ZIP, PNG, and zlib) and Castagnoli (0x1EDC6F41, reflected 0x82F63B78, used in iSCSI, ext4, Btrfs, and NVMe/TCP), which achieves Hamming distance 6 up to 5243 bits and is accelerated via x86 SSE4.2 CRC32 and ARMv8 CRC32C instructions. Fast software implementations use slicing-by-8/16 tables or carryless multiplication (PCLMULQDQ/PMULL).
