Guide / Glossary A–Z / Terms beginning with C / Checkpoint number

A sequence number that Snapper assigns to identify a snapshot within one specific configuration.

Imagine keeping separate numbered photo albums for your house and your car—both albums have a “Photo #5,” so saying just “#5” is ambiguous unless you name the album too. A checkpoint number works the same way: it is the snapshot’s number inside one Snapper configuration, not a unique ID across the whole computer.

When you run snapper -c root list alongside snapper -c home list, both configurations start counting from 0 (the current live subvolume) and increment 1, 2, 3... independently. Passing only a number without -c <config> defaults to the root configuration, which can accidentally inspect or diff the wrong filesystem if you meant /home.

Why is knowing only a checkpoint number like 42 not enough to restore a snapshot on a system with multiple Snapper configs?

Each Snapper configuration maintains its own independent numbering, so 42 could exist in root, home, or both—you must pair the number with its configuration name.

Internally, Snapper stores each snapshot under <subvolume>/.snapshots/<number>/ with info.xml metadata (type single, pre, or post, pre_num pairing, timestamp, cleanup algorithm, and user data) and a Btrfs subvolume at snapshot. Because <number> is scoped solely to that config’s .snapshots directory rather than to a Btrfs subvolume UUID or global counter, commands (snapper -c <config> diff, undochange, delete, or rollback) require the (config, number) tuple, and deleting a pre or post snapshot leaves a dangling pair reference unless handled with range or paired deletion.
