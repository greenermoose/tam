Guide / Glossary A–Z / Terms beginning with C / Character encoding

A rulebook that maps written characters and symbols to numbers and stored byte sequences so computers can save and exchange text.

Computers only store numbers, not letters. A character encoding is like a shared codebook that agrees “65 means A” and “66 means B.” If you open a file using the wrong codebook—for example, a file written with one language’s chart read with another’s—the words turn into garbled symbols (often called mojibake).

On Linux, UTF-8 is the standard encoding because it represents every Unicode character while remaining backward-compatible with 7-bit ASCII for plain English text. When debugging garbled text in terminals or filenames, tools like file -i and iconv help identify or convert legacy encodings such as ISO-8859-1 or Windows-1252, while locale (LANG=en_US.UTF-8) tells programs which encoding to expect.

Why can a valid ISO-8859-1 file containing accented letters like é produce errors or replacement glyphs when read as UTF-8?

In ISO-8859-1, é is a single byte (0xE9), whereas UTF-8 requires a specific multi-byte sequence for non-ASCII characters, so a lone 0xE9 byte is invalid UTF-8.

Unicode separates the coded character set (abstract scalar values U+0000–U+10FFFF excluding surrogates 0xD800–0xDFFF) from the character encoding form/scheme (UTF-8, UTF-16LE/BE, UTF-32) that serializes code points into 8-, 16-, or 32-bit code units. UTF-8 uses self-synchronizing prefix bits (0xxxxxxx for ASCII, 110xxxxx/1110xxxx/11110xxx lead bytes with 10xxxxxx continuation bytes), which prevents mid-stream boundary ambiguity, rejects overlong encodings for security (e.g., preventing 0xC0 0xAF from bypassing / path checks), and avoids byte-order (BOM) ambiguity unlike UTF-16.
