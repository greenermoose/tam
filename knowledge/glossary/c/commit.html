Commit

A commit is a saved snapshot of a project’s files at a specific point in time, used in version control.

Think of a commit like a named save point in a document or a game. Before you try a risky edit, or right after you finish a clean piece of work, you save a snapshot with a short note explaining why you made the change. If something breaks later, you can look back at what changed or return to that saved point.

Unlike simply saving a file, a commit in Git captures the whole tracked project state together with who made it, when, and a message describing the intent. Each commit points back to its parent commit (or parents, after a merge), forming a history you can inspect with git log or compare with git diff. Keeping each commit focused on one logical change makes mistakes much easier to track down and undo.

Why is it better to make small, focused commits instead of one huge commit at the end of the day?

Small commits tie each change to a clear explanation and make it safe to revert, cherry-pick, or bisect a single bug without throwing away unrelated work.

In Git, a commit is an immutable object in the object database addressed by the cryptographic hash of its header and payload. Its payload references a root tree object (representing the full directory snapshot, not a delta), zero or more parent commit hashes, author and committer identities with timestamps, an optional cryptographic signature, and the commit message. Because the hash covers the parent pointers, commits form a Merkle DAG: altering any historical file or metadata changes that commit’s ID and every descendant’s ID.
