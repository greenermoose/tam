CSPRNG (Cryptographically Secure Pseudorandom Number Generator)

A Cryptographically Secure Pseudorandom Number Generator (CSPRNG) is a random-number generator designed so its outputs cannot be predicted even if an attacker observes many past outputs.

Ordinary random-number generators—like the ones used to shuffle cards in a game—only need to look random. If someone watches a few numbers come out, they can often figure out the formula and predict the next one. That would be disastrous for encryption keys, passwords, or login tokens. A CSPRNG is built so that even if an attacker sees millions of numbers it has already produced, they still have no better than a pure guess at what comes next.

On Linux, programs obtain cryptographically secure bytes from the kernel CSPRNG using the getrandom(2) system call (the modern default) or by reading /dev/urandom. The kernel continuously collects unpredictable timing jitter from hardware events (interrupts, CPU RDRAND/RDSEED where present, and timer noise) to seed the generator. Unlike fast non-cryptographic PRNGs such as C’s rand() or Python’s random module (Mersenne Twister), Python’s secrets module and OpenSSL’s RAND_bytes() draw from a CSPRNG.

Why should new Linux programs prefer getrandom(2) over opening /dev/urandom directly?

getrandom(2) blocks until the kernel CSPRNG is initially seeded at early boot and cannot fail due to exhausted file descriptors or missing /dev mounts inside chroots or containers.

A CSPRNG must satisfy both next-bit unpredictability (no polynomial-time distinguisher can predict the next output bit with non-negligible advantage) and backtracking resistance (state compromise does not expose prior outputs). Since Linux 5.18, drivers/char/random.c feeds interrupt/jitter entropy into a BLAKE2s-256 pool that seeds per-CPU ChaCha20-based DRBGs with immediate fast-key-erasure after each output block and periodic reseeding. Once crng_init completes, /dev/random and /dev/urandom share the same ChaCha20 generator, and GRND_RANDOM is a no-op.
