Compositor

A compositor is the program that draws windows on the screen and decides where they go.

Imagine several artists each painting on their own transparent sheet, and one coordinator stacking those sheets onto a single canvas so you see a coherent desktop. On a graphical Linux desktop, the compositor takes each open window’s picture, arranges them, handles focus, and sends your mouse clicks and keystrokes to the right window. If the compositor stops working, windows may freeze or the screen may go blank even though text consoles still work.

On a Wayland desktop—such as Tamlinux, which currently uses Hyprland as its compositor—the compositor implements the Wayland server protocol, manages outputs via KMS/DRM, and schedules client frames. It is distinct from the desktop shell (panels, launchers, and menus) and from individual applications. When diagnosing a blank screen, knowing this split helps you check whether the compositor process itself, its session, or a single client failed.

If your Wayland desktop freezes but switching to a text console still works, what does that tell you?

The Linux kernel and lower-level system are still running; the fault is likely inside the user-space compositor, its display session, or a stuck GPU/client interaction rather than a full system hang.

A Wayland compositor acts as both display server and window manager, owning the DRM master lock and input devices via libinput and seatd or logind. Clients render into shared-memory (wl_shm) or GPU-backed (linux-dmabuf) buffers and commit surfaces atomically; the compositor composites them—via GPU shaders or direct hardware scanout planes—synchronized to vblank events. Unlike X11, Wayland enforces per-client isolation (no global coordinate queries or arbitrary input snooping) and delegates decorations, fractional scaling, and damage tracking through explicit protocol extensions.
