Guide / Security / Protect your computer / Disk encryption and LUKS passphrases

Disk encryption protects data at rest by making stored bytes unreadable without a passphrase or key, so a lost or stolen drive does not expose files directly.

Locking your drive when the machine is off

If someone removes the storage drive from a powered-off laptop, disk encryption scrambles the files on that drive so they look like random noise without the unlock passphrase or key.

Why it matters

Your login password stops someone sitting at a locked screen, while disk encryption protects your files even if the physical laptop or SSD is lost or stolen.

How to think about it

Think of disk encryption as locking the entire filing cabinet while the computer is shut down. Once you unlock the drive at startup, the running system can read files normally until you power off again (or lock the screen while away).

New words

Encryption
Scrambling stored bytes with a secret key so they cannot be read without unlocking them.
LUKS
Linux Unified Key Setup, the standard Linux disk-encryption format used on root and external drives.
Boot
The early startup sequence that unlocks encrypted storage before launching your desktop.

What does disk encryption protect while the machine is running and unlocked?

Much less: once the key is available to the running system, ordinary file and process protections matter again.

LUKS2 architecture, AES-XTS, and TPM2 PCR binding

Reference

LUKS2 stores redundant JSON metadata headers and up to 32 key slots at the start of a block device. Each active key slot wraps the same 256-bit or 512-bit volume master key using a key derived from a passphrase (via Argon2id) or a TPM2-sealed secret.

How it works

The kernel dm-crypt target typically encrypts 512-byte or 4096-byte sectors with AES-XTS-plain64: XTS splits the 512-bit key into two 256-bit AES keys (K1 for block ciphering, K2 for GF(2^128) tweak multiplication by sector number), ensuring identical plaintext blocks in different sectors produce distinct ciphertext without per-sector IV storage overhead.

Edge cases

Malleability without authenticated encryption
Plain AES-XTS provides confidentiality, not integrity: an attacker with repeated physical disk access can flip bits in a 16-byte block (causing localized plaintext corruption). Combining dm-crypt with dm-integrity or dm-verity adds per-sector authentication tags at a storage and IOPS cost.
Evil-maid attacks on unencrypted /boot or EFI
Without Secure Boot and measured-boot TPM2 PCR policies (systemd-cryptenroll --tpm2-pcrs=7+11), an attacker with physical access can tamper with the initramfs on the EFI partition to capture the unlock passphrase.
Research frontier: How do confidential-computing SEV-SNP/TDX memory encryption and hardware inline crypto engines interact with dm-crypt?

Hardware inline encryption engines (OPAL / NVMe crypto) offload XTS from CPU cores, while confidential VMs bind disk-unlock keys to remote hardware attestation over measured boot quotes.
