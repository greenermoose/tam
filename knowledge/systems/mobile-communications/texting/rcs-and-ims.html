RCS (Rich Communication Services) is a carrier messaging service that uses internet-style data connections. It adds chat features such as delivery status, typing indicators, group chat and richer content, while still depending on the mobile network's subscriber system.

Chat with a capability check

Not every phone supports the same chat features. Before starting a rich conversation, the service checks what each phone can do. If both sides support a feature, they use it. If they do not, the service may fall back to an ordinary short or multimedia message.

Why it matters

RCS tries to give carrier messaging some of the features people expect from chat apps, without requiring everyone to install the same app. The capability check is what makes that possible across different phones and carriers.

How to think about it

Think of two people deciding how to talk. One speaks three languages and the other speaks two, so they use a language they both know. RCS checks which "languages" the two phones speak before it sends.

If it goes wrong

You assumed RCS is the same as an internet chat app.
RCS is a carrier service built on IMS. It shares features with apps, but identity, rollout and standards are different.
You assumed all RCS messages are encrypted.
Encryption depends on the participants, clients, carriers and message category. Business bot traffic and SMS fallback are outside the person-to-person encrypted path.

Tamlinux does not enable RCS or choose a messaging client. This page describes the service model so the reader can evaluate claims about chat features and privacy.

Check yourself

Decide your answer before you reveal it.

Why must a reader check whether a conversation fell back to SMS before trusting a privacy claim?

SMS has no standard application-layer end-to-end content encryption. A rich encrypted chat and a fallback short message can appear in the same conversation view but have different protection.

Why is presence different from a delivery receipt?

Presence describes availability; a receipt describes a message event. A contact can be available while a message is delayed, or unavailable while a message was delivered to a device.

How it works

RCS uses the IP Multimedia Subsystem, whose stage-two architecture is defined in 3GPP TS 23.228 and whose SIP/SDP procedures are defined in 3GPP TS 24.229. GSMA's RCC.07 defines the RCS client; RCC.71 defines the Universal Profile, with UP 4.0 published in 2026 as value UP_4.0. The profile includes capability discovery, one-to-one and group chat, file transfer, enriched calling, multi-device behaviour, rich cards for business messaging and spam controls. Capability discovery lets a client learn which features the other side supports before choosing a route.

The Universal Profile now includes end-to-end encryption requirements based on RCC.16. RCC.16 uses MLS (RFC 9420) and HPKE, with key packages distributed via key distribution services. Its scope is person-to-person conversations; chatbot conversations are excluded, and SMS fallback is not encrypted. UP 4.0 requires clients to enable encryption by default unless local regulation prohibits it, but a specification requirement is not the same as universal deployment. Cross-operator and cross-client availability is fast-changing and must be checked against current carrier and client documentation.

Edge cases

  • Fallback can happen inside a single visible conversation. A privacy analysis must ask which transport carried a given message, not only which app displayed it.
  • Business messages and rich cards are valuable for services but are a different trust category from person-to-person chat; a verified brand channel is still a policy signal, not proof of content authenticity.
  • Encrypted RCS messages may not be backed up by the service. That improves content confidentiality but changes recovery expectations when a phone is lost.
  • Rollout differs by country, carrier, client version and regulation. A feature listed in a Universal Profile may not be active for a particular pair of users.

Check yourself

Why is "RCS supports E2EE" a different claim from "this RCS conversation is E2EE"?

The first is a specification capability. The second requires both clients, carriers and key services to support it for that conversation and message category, with no fallback to SMS. Check the deployed path before making the stronger claim.
