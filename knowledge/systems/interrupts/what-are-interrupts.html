Guide / Systems and administration / Interrupts / What interrupts are

A computer does something useful only when events reach the software that can answer them. Interrupts are the usual way those events arrive.

When the CPU is interrupted

A CPU core runs one stream of instructions at a time. If you press a key while a program is running, the program does not notice the key itself. The keyboard sends a signal, and the interrupt makes the CPU pause that program briefly so the kernel can deal with the key press.

Why it matters

Without interrupts, the kernel would have to ask every device over and over whether it needed anything. That would waste time. Interrupts let the kernel wait until something actually happens.

How to think about it

Think of a doorbell. You can keep working on something else instead of checking the door every few seconds. When the bell rings, you note where you were, answer the door, and then carry on with what you were doing.

New words

Interrupt
A signal that pauses current work so the kernel can handle an event.
IRQ
An interrupt request line used by a hardware device.

Why devices signal instead of being polled

Mental model

device -> controller -> CPU -> kernel handler -> program continues

A hardware device raises an IRQ. An interrupt controller decides which CPU core receives it. The CPU saves a little state, runs the kernel's handler, then returns to the program it was running. A timer also interrupts regularly even when no device needs attention; that gives the kernel a chance to decide which task should run next.

Type the command in the sandbox to see the shape of the kernel's interrupt record.

What just happened

  1. /proc/interrupts is a kernel-generated file; reading it does not change the machine.
  2. The first row numbers are interrupt sources. The columns underneath CPU0 and CPU1 count how many times each core handled that source.
  3. The timer row is the regular tick. The i8042 row is the keyboard controller in this sample.

Try it

Read /proc/interrupts on a machine you use. The device names and counts differ, and the counts grow while the machine is running. Watch one row twice with a short gap between reads.

If it goes wrong

A row you expected is not there
Devices and drivers differ between machines. Look for the timer row, which appears on essentially every Linux system.

Check yourself

Why is a timer interrupt useful even when no user presses a key or clicks a mouse?

The kernel needs a regular point at which it can check whether another task should run, update timekeeping, and carry out deferred work. Without a tick it would only react when a device or a program made a request.

Interrupt sources and what the counts mean

Interrupts reach the CPU from hardware IRQ lines, from message-signaled interrupts (MSI and MSI-X) used by modern PCIe devices, from timer hardware, and from inter-processor interrupts (IPIs) sent between CPU cores. Software also enters the kernel through system calls and exceptions, but those are synchronous: they happen because the running instruction asked for them, not because an outside event arrived.

Each row of /proc/interrupts names an interrupt source, and each numeric column is a per-CPU counter. A large and fast-growing count can show a busy device; an uneven distribution can point at IRQ affinity or a missing irqbalance setup. A busy high-speed network interface may switch from one interrupt per packet to batched polling (NAPI) so that the core is not spent entering and leaving handlers. Legacy shared lines can report spurious interrupts; a driver that receives an interrupt it cannot claim can be disabled with a nobody cared message.

Check yourself

Why can polling sometimes be faster than interrupting for a very busy device?

Every interrupt costs a state save and handler entry. At very high event rates those fixed costs dominate. Draining a ring of packets in one polling batch avoids one entry per packet.
