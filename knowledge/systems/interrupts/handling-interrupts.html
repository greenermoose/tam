Guide / Systems and administration / Interrupts / How interrupt handling works

The kernel answers an interrupt in a short, deliberate sequence, then gives the processor back to ordinary work.

What happens when the doorbell rings

When an interrupt arrives, the CPU finishes the instruction it is on, notes where the interrupted program had reached, and starts a small piece of kernel code. That code deals with the urgent part of the event. Then the CPU restores the saved place and the program carries on as if nothing had happened.

Why it matters

The interrupted program does not need to know that a key press or a packet arrived. It simply resumes. That is one reason several programs can appear to run at once on a single CPU core.

How to think about it

Put a bookmark in a book, answer the door, then return to the same line. The bookmark is the CPU's saved state; answering the door is the kernel's handler.

New words

Interrupt
A signal that pauses current work so the kernel can handle an event.
Context switch
Changing which task the processor runs.

From signal back to your program

Goal: you will be able to trace an interrupt through the kernel and say why handlers are kept short.

Mental model

event --> save state --> short handler --> deferred work --> restore or reschedule

The kernel saves the registers of the interrupted task and runs the driver's handler for that interrupt source. A handler must be quick: while it runs, other work on that CPU is delayed. Anything that can wait is marked for later, in a softirq or a threaded handler. Once the urgent part is done, the kernel either restores the interrupted task or, if the scheduler decides another task should run, performs a context switch.

What just happened

The handler did only the work that had to happen immediately: acknowledge the device and record the key. The rest of the path—delivering input, redrawing a window—can happen in ordinary process context, where waiting is allowed.

If it goes wrong

The system feels sluggish while a device is busy
A handler may be doing too much work, or interrupts may be arriving faster than they can be drained. That is a driver or device problem, not a fault in the program you were using.

Check yourself

Why does the kernel defer some work instead of doing all of it inside the interrupt handler?

An interrupt handler runs with ordinary tasks paused and cannot sleep. Long work there delays everything else on that CPU. Moving it to deferred or threaded context keeps the urgent response short and lets the rest run where blocking is allowed.

Interrupt context, top halves and bottom halves

Linux distinguishes process context, where a task is running and may sleep, from interrupt context, which belongs to no task and must not sleep or take a mutex. A hardirq handler (the top half, registered with request_irq) acknowledges and masks the device and queues work. Deferred work runs soon after in softirq context, in a tasklet, or in a threaded interrupt handler registered with request_threaded_irq; PREEMPT_RT kernels thread most interrupt handlers by default. The split keeps worst-case interrupt latency bounded while still completing work promptly.

On x86 and ARM64 systems, an arriving interrupt causes the CPU to save state and jump to an entry point in the kernel. On return, the kernel checks whether a reschedule is needed; a timer interrupt may set that flag, leading to __schedule() and a context switch instead of a direct return to the old task. Per-CPU state such as /proc/interrupts and /proc/softirqs shows where the work is happening.

Check yourself

Why must a hardirq handler avoid waiting for a mutex?

Interrupt context has no task to park on a wait queue. Blocking there would leave the CPU unable to make progress on the very work that the handler was meant to finish. Work that can wait belongs in a threaded handler or a softirq.
