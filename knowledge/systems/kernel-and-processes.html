Computer architecture and hardware systems

What do the kernel and processes do?

The kernel is the core of the operating system that talks directly to your hardware and shares CPU time and memory fairly. Every program you run—your browser, terminal, or desktop bar—runs inside its own isolated process supervised by the kernel.

Why it matters

When something freezes, knowing the boundary between an individual application, a background service, and the kernel underneath tells you whether closing one program is enough or whether the whole system needs attention.

How to think about it

Think of the kernel as an air-traffic controller and each running program as an airplane. Every plane has its own cockpit and flight plan (process), while the controller keeps them from colliding over shared runways, memory, and hardware.

Starting and stopping

Firmware starts the kernel when the computer boots. The kernel stays in charge until you shut down or restart the machine; you do not start or stop it the way you open and close an application.

Waiting and handing back

After startup the kernel does not run your program from beginning to end. It waits for a request from a program or a signal from hardware, does a short piece of work, and then lets a program continue. It repeats that pattern constantly.

Mental model

your program --> syscall --> kernel --> driver --> hardware

Programs ask the kernel for services (open a file, send a packet, map memory). Drivers are kernel code (or modules) that talk to devices. A fault can sit in the program, the kernel path, or the device.

How the kernel starts and stops

Firmware chooses a bootloader, and the bootloader loads the kernel into memory. The kernel sets up hardware, mounts the root filesystem and starts init, the first user-space program. Init then starts the services and login you use. Trace those stages in Boot phases.

Stopping goes the other way. It is not a signal sent to the kernel like any other process: init asks running programs to finish, flushes storage and asks the kernel to halt or restart the machine. The kernel performs the final power action and firmware or hardware takes over again. Sleep is different: the running kernel and memory are preserved, so the kernel has not stopped. See When your computer rests or sleeps.

Worked example

In the sandbox, observe three things: how long the kernel has been running, which process is your shell, and how the kernel records events from devices. Each command reads information only.

Now type cat /proc/interrupts to see the kernel's event counts. Try cat /proc/uptime, printf '%s\n' "$$" or cat /proc/interrupts (or type help).

The values are examples, not readings from your machine. Uptime is seconds since the kernel started; the interrupt counts are per CPU and change while the machine runs.

What just happened

  1. /proc/uptime reported that this kernel had been running since boot. That is why stopping the kernel means ending the whole session, not closing one program.
  2. $$ is the shell's process ID. The kernel uses that number to track that running program.
  3. /proc/interrupts counted times the kernel was called away from whatever was running. The timer row is the regular tick.

The kernel's loop and handoff

The kernel is not one long program that drives yours from start to finish. It waits for an interrupt from hardware or a system call from a program, runs the relevant kernel code briefly, then hands the CPU back. When more than one program is ready, the scheduler chooses which one runs next and the kernel performs a context switch: it saves one task's place and restores another's.

The timer row you just read is one reason this happens regularly. The next two pages follow that path in detail: What interrupts are and How interrupt handling works.

Check yourself

Is the kernel the same thing as a terminal window?

No. The kernel is the central privileged program. A terminal is a program (and window or console) that lets you talk to a shell.

What identifies a running program to the kernel?

Its process ID (PID), among other credentials.

Does the kernel run your program from start to finish?

No. It reacts to system calls and interrupts, runs a short piece of kernel code, then hands the CPU back. If another task should run, the scheduler arranges a context switch first.

What happens when a device needs attention while a program is running?

The CPU saves the program's state and enters a kernel handler. The kernel deals with the event briefly, then resumes that program or switches to another one.

Identity, memory and failure isolation

The kernel schedules threads, isolates address spaces, and mediates devices. Process existence (kill -0) is not health. Open file descriptors can outlive path names. Module and driver faults in a monolithic kernel can take the whole system down; that cost is why Tamlinux watches microkernel research while shipping Linux today.

Starting and stopping the kernel

No user command starts the kernel. Firmware hands a boot image to a bootloader, which loads the kernel; the kernel initialises memory and devices, unpacks initramfs, mounts the root filesystem and executes PID 1. Because PID 1 is the parent of user space, the ordinary shutdown path runs through it: it stops services, syncs filesystems and calls the kernel's reboot system call. That call ends in a restart or power-off operation. There is no signal that kills the kernel while the machine stays up; a kernel panic is the exceptional case where the kernel stops itself because it cannot continue safely.

Why it is an event loop, not one long loop

Each CPU core runs whichever task the scheduler selected and stays in user mode until a system call, exception or interrupt changes the mode. The kernel then executes in that task's context or in interrupt context. On return it checks the need-reschedule flag; timer interrupts and wakeups can cause __schedule() and a context switch instead of a direct return to the previous task. The idle loop runs only when no task is runnable. The kernel's work therefore appears as short pieces spread across processes, not as one program you can follow from top to bottom. Check yourself

Why can an updated on-disk binary leave a running process on old code?

The process keeps its mapped executable pages until it exits and is started again. Path lookup for a new start can see the new file while the old PID still runs the previous mapping.
