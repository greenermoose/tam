Guide / Systems and administration / Memory technology / Volatile memory and CPU caches

Volatile memory loses its data when power is removed. Computers use it for fast working storage because electronic memory can be much faster than disks or flash. CPU caches are small volatile memories placed close to processor cores to hide the delay of main memory.

Fast memory near the work

Your computer's main memory (RAM) is fast compared with a disk, but still slow compared with a CPU. To avoid waiting, the CPU keeps tiny copies of recently used data in caches. The smallest cache, L1, is closest and fastest. L2 is larger and a bit slower. L3 is usually larger still and shared by several cores.

Why it matters

A CPU can do billions of simple operations per second, but only if data arrives quickly enough. Cache hits keep the CPU busy; cache misses make it wait for RAM. This is why memory layout and access patterns can change program speed dramatically.

Key terms

Volatile memory
Memory that needs power to keep its contents. When power is lost, the data is lost.
Cache
A small fast copy of data kept near where it will be used.

DRAM, SRAM, and cache levels

Goal: Understand how volatile memory cells work and why caches are layered.

DRAM: main memory

Dynamic RAM (DRAM) stores each bit as charge in a tiny capacitor connected to a transistor. Because the capacitor leaks, DRAM must be refreshed periodically by reading and rewriting values. DRAM is dense and relatively inexpensive per bit, so it is used for main system memory. Typical access is around 100 ns, which is fast to humans but slow to a CPU. On the 1 ns = 1 second scale, 100 ns is 1 minute 40 seconds.

SRAM: cache memory

Static RAM (SRAM) stores bits using flip-flop circuits made from transistors. It does not need refresh the way DRAM does, and it can be very fast. The trade-off is size and cost: an SRAM cell uses more transistors than a DRAM cell, so SRAM is less dense and more expensive. That makes it ideal for small caches close to CPU cores.

L1 and L2 caches in detail

The CPU cache hierarchy usually has separate L1 instruction and L1 data caches per core. L1 is the smallest and fastest: often tens of kilobytes, with access around 4 cycles or a few nanoseconds. It is optimized for the CPU's immediate needs.

L2 is usually larger, often hundreds of kilobytes to a few megabytes per core on many designs. It is slower than L1 but still much faster than RAM. L2 catches data that does not fit in L1 and acts as a second buffer before going to shared L3 or main memory. Some CPUs have private L2 per core; others share or have different arrangements, but the common pattern is L1 closest/smallest, L2 next.

L3 is larger still, often several to tens of megabytes, and commonly shared among cores on a chip. It helps cores share data and reduces trips to DRAM. Access is slower than L2 but much faster than main memory.

Caches on other chips

CPUs are not the only chips with caches. GPUs have instruction/data caches, texture caches, and shared caches. Disk controllers and SSDs use RAM caches to buffer reads and writes. Network cards have buffers. Even browsers and operating systems use software caches. The same principle applies: keep frequently used data in a faster, closer layer.

Worked example: cache hit versus RAM

Suppose a CPU needs a value that is already in L1 cache: it may get it in about 1 ns. If it misses L1 and L2 but hits L3, it may wait around 40 ns. If it must go to DRAM, it may wait around 100 ns. Using the 1 ns = 1 second scale, that is the difference between 1 second, 40 seconds, and 1 minute 40 seconds for a single access. Repeated millions of times, locality becomes the difference between fast and slow code.

Try it

On Linux, inspect CPU cache sizes with:

$ lscpu | grep cache
$ ls /sys/devices/system/cpu/cpu0/cache/
$ cat /sys/devices/system/cpu/cpu0/cache/index0/size

index0/index1 are often L1 data/instruction caches, with higher indexes for L2/L3 depending on the CPU.

If it goes wrong

A program is slower than expected
It may have poor locality: jumping around memory causes cache misses. Sequential access and compact data structures often work better with caches.
Cache numbers look different across machines
Cache sizes and levels vary by CPU model and generation. Always check the actual system rather than assuming one layout.

Check yourself

Why not make all memory out of SRAM?

SRAM is fast but uses more transistors per bit, making it larger and more expensive. DRAM is denser for main memory, and flash/disk are denser still for persistent storage. The memory hierarchy balances speed, size, cost, and persistence.

How caches work

Caches move data in cache lines, commonly 64 bytes. When the CPU requests a byte, the cache may fetch the whole line from a lower level. This exploits spatial locality: nearby data is likely to be used soon. Temporal locality means recently used data is likely to be used again. Caches use tags to identify which memory address a line belongs to, and replacement policies to decide what to evict when full.

L1 caches are often split into instruction and data caches so instruction fetch and data load/store can proceed in parallel. L1 is commonly virtually indexed, physically tagged to balance speed and correctness. L2 may be unified and private per core. L3 is often a shared last-level cache with coherence protocols such as MESI/MOESI variants to keep cores consistent.

Other cache considerations

Caches improve average performance but make timing less predictable. Cache misses, false sharing, coherence traffic, and prefetch behavior matter in performance-sensitive code. On other chips, GPU caches manage massive parallel access patterns; storage controllers use volatile write caches (sometimes protected by capacitors or batteries) to improve performance but must handle power loss carefully.
