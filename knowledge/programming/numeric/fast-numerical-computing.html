Fast numerical computing

Computer math becomes fast when many numbers are arranged well and the same small operation is repeated without wasted work.

Vectors, matrices and repeated arithmetic

A vector is a list of numbers. A matrix is a rectangular grid of numbers. Linear algebra studies how to combine them. A common operation is the dot product: multiply pairs of numbers from two vectors, then add the results.

Why it matters

Graphics, sound, simulations, search and machine learning all reduce large problems to many vector and matrix operations. Doing one multiplication at a time in a general-purpose loop can be far slower than letting the machine work on several values at once.

How to think about it

Think of washing a large pile of dishes. You can wash one, dry it, put it away, then reach for the next, or you can set up a steady line where each step happens continuously. Fast numerical code builds that line: data arrives in order, the same operation runs on each piece, and results leave without interruption.

New words

Dot product
Multiply matching entries of two vectors and add all the products.
BLAS
A standard library interface for basic vector and matrix operations.
LAPACK
A standard library interface for higher-level matrix problems such as solving systems of equations.
SIMD
One instruction that performs the same operation on several values at once.

Recognise the inner loop

Goal: you will be able to write a small dot product, identify the repeated work, and say which library would replace it in production code.

Worked example

$ python3 -c "a=(1.0,2.0,3.0); b=(4.0,5.0,6.0); print(sum(x*y for x,y in zip(a,b)))"
32.0

Captured on a Linux system with Python 3, 2026-11-24. Your output will match.

What just happened

  1. The loop pairs 1 with 4, 2 with 5 and 3 with 6.
  2. Each pair is multiplied: 4, 10 and 18. The sum is 32.
  3. This tiny loop is the shape of a dot product. A library such as BLAS replaces it with code tuned for the processor, including SIMD instructions and careful memory access.

Try it

In a scratch directory, extend the vectors to ten values and compute the dot product again. Then change one value and predict the new total before you run it.

If it goes wrong

The vectors have different lengths
zip silently stops at the shorter one. In real work, check lengths first so a bug does not become a plausible wrong answer.
The result is not what you expected
Print the products before the sum. An off-by-one pairing or an integer division is easier to see there.

Check yourself

Decide your answer before you reveal it.

Why not just write the loop yourself for a large matrix multiplication?

A correct loop can still be slow. Library kernels reuse loaded values, avoid cache misses, keep the processor pipeline full and use wide instructions. They also handle different shapes and precision without rewriting the algorithm each time.

How it works

A matrix multiplication of an m-by-k matrix and a k-by-n matrix performs m*n*k multiply-add pairs. Reordering those pairs changes how often data is fetched from memory, even though the arithmetic count is the same. BLAS describes operations, not a single implementation; vendors and open-source projects supply tuned kernels that choose blocking, packing and instruction sets at run time. LAPACK builds higher-level factorizations from those kernels.

Main memory is far slower than a processor register, so layout matters. Contiguous access lets hardware prefetch and fill cache lines; strided access wastes transfers. A transposed matrix can be much faster to multiply even though it holds the same values. Fused multiply-add reduces both instruction count and rounding error by performing x times y plus z with a single final rounding.

Advanced usage

$ python3 -c "n=4; print('pairs for 4x4 by 4x4:', n*n*n); print('caches: contiguous stride 1 beats stride 4')"
pairs for 4x4 by 4x4: 64
caches: contiguous stride 1 beats stride 4

Illustrative sequence: the operation count is easy; the memory pattern is where hand-written loops usually lose to a tuned kernel.

Edge cases

  • Low precision can be faster but changes results. Mixed-precision workflows compute in a narrow type and accumulate in a wider one.
  • Parallel reductions do not add in the same order every run, so bitwise-identical results are not guaranteed.
  • BLAS implementations may differ in rounding and exception behaviour. Compare tolerances, not raw bits, when changing libraries.
  • More threads can make a small matrix slower because coordination costs exceed the saved arithmetic.

Check yourself

Two programs compute the same matrix product. One uses a naive triple loop and one calls an optimized BLAS. What should you compare before blaming the library for different last digits?

Check shapes, storage order, accumulation precision, thread count and fused multiply-add use. Different addition order or rounding changes low digits without changing the mathematical result. Benchmark with representative sizes, since small cases may be dominated by setup costs.
