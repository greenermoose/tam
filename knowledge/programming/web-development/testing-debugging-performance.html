Guide / Programming / Web development / Testing, debugging, and performance

Tests tell you when behaviour changes, debugging tells you why it changed, and measurement tells you whether a fix helped.

Three different clues

A test checks an expected result. A stack trace shows the calls that led to a failure. A measurement records time or resource use.

Why it matters

Guessing wastes time. Each clue narrows a different question: what broke, where it broke, and whether the repair worked.

How to think about it

A smoke alarm tells you something is wrong, a map tells you which room to enter, and a stopwatch tells you whether the fix made the journey shorter.

Check yourself

Decide your answer before you reveal it.

Can a passing test prove code is fast?

No. It proves an expected behaviour held; speed needs separate measurement.

Why read a trace before changing code?

It shows which path actually ran, so the fix targets the real cause.

How it works

Tests should fail for a clear reason and stay deterministic. Debugger breakpoints pause execution so state can be inspected. Performance work starts with a representative workload, then measures a baseline and a change under the same conditions. Event-loop latency matters as much as average CPU time in interactive pages.

Edge cases and failure modes

  • Flaky tests hide real regressions.
  • Optimised builds change line numbers and stack shapes.
  • Source maps can misattribute a frame.
  • Microbenchmarks may be optimised away entirely.
