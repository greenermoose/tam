Guide / Programming / Web development / Testing, debugging, and performance

Tests tell you when behaviour changes, debugging tells you why it changed, and measurement tells you whether a fix helped.

What this is

A test is a small program that checks one promise about your code. Debugging is the work of finding where a promise broke. Performance work compares how long something takes before and after a change.

Why it matters

A page can look fine on one computer and fail for another person. Tests and measurements turn “it works for me” into evidence you can repeat.

How to think about it

A test is a smoke alarm: it tells you something is wrong, not where the fire started. A debugger and a trace are the flashlight you use afterwards.

New words

Assertion
A statement that a value must match what you expect.
Stack trace
A list of function calls that led to an error.
Profile
A record of where time was spent while a program ran.

Run a test and read a trace

Goal: you will be able to run a small Node test, read its result, and collect a timing measurement you can repeat.

Learner path: previous: Frameworks and tooling; next: Deployment and Electron desktop apps.

Worked example

$ node --test --test-reporter=dot sum.test.mjs
.
$ node -e "console.error('warning from app')"
warning from app
$ node -e "const t=performance.now(); let s=0; for(let i=0;i<1e6;i++) s+=i; console.log('sum',s,'ms',(performance.now()-t).toFixed(1));"
sum 499999500000 ms 9.5

Captured on 2026-11-24 with Node.js 24.5.0. The test file defined add(a, b) and asserted that add(2, 3) is 5. One dot means one passing test. The loop time depends on your machine; the sum does not.

  1. Run the test before you change code, so you know the starting state.
  2. Send diagnostic text to standard error with console.error, leaving normal output clean.
  3. Time a loop with performance.now, then repeat it; one run is a hint, not a conclusion.

Try it

In a scratch file, write a test that asserts add(4, 5) is 9. Change the expected value to 10, run the test, and read the failure. Restore the correct value and confirm the dot returns.

If it goes wrong

The test runner reports zero tests
Check the filename. Node discovers files ending in .test.mjs or matching its test patterns.
A browser bug cannot be reproduced in Node
Use the browser's built-in developer tools: inspect the console, the network list, and a performance recording. Node does not have a page tree.

Check yourself

Decide your answer before you reveal it.

A test passes but a page is still slow. Why is that not a contradiction?

The test checks correctness of one value; speed is a different property. Add a performance check or a recorded trace that measures the path users take. A function can return the right answer after doing far too much work.

How it works

A browser trace records script, style, layout, paint, and network spans on one timeline. The event loop cannot paint while a long task runs, so a slow handler appears as a block before the next frame. Network timing separates waiting for a reply from downloading it. Field measures such as Web Vitals describe what real visitors experienced; a local profiling run explains a cause but does not replace field data. Tests belong at several sizes: unit checks for pure functions, integration checks for an HTTP boundary, and end-to-end checks for one complete user task.

Advanced usage

test('rejects an empty title', async (t) => {
  await assert.rejects(saveNote({ title: '' }), /title required/);
});

Illustrative snippet: a negative test checks the failure path as well as the happy path. Keep it independent of ordering so it can run in parallel with other tests.

Edge cases and failure modes

  • Timing tests that assert exact milliseconds are flaky on busy machines; assert bounds or compare relative runs.
  • End-to-end suites that share one account can fail from leftover state; create fresh data per run.
  • A stack trace from minified code points at generated files unless source maps are available.
  • Caching can make a second measurement look faster even though the code did not change.

Check yourself

A slow page has a fast server response and a long browser task. Which measurement rules out the network, and what would you inspect next?

Model answer: the network list shows a short time to first byte and small transfer size, so the server and transfer are not the delay. The performance trace then identifies the long task. Inspect its call tree for repeated DOM writes, synchronous parsing, or an oversized framework render before adding caching.
