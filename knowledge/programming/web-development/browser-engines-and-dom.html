Guide / Programming / Web development / Browser engines and the document object model

A browser engine turns page files into a live document that a script can inspect and change.

What this is

A web browser is a program that reads web pages. Its engine builds a tree of the page's parts. That tree is called the document object model, or DOM.

Why it matters

JavaScript does not edit the text file you wrote. It changes the tree in memory, and the browser draws the changed tree on screen.

How to think about it

Imagine a family tree made of page parts. The page has a root, the root has a body, and the body has headings and paragraphs. Script can add a branch or change a label, then the browser repaints that part of the picture.

New words

Engine
The part of a browser that parses, lays out, and paints a page.
Node
One item in the document tree, such as an element or a piece of text.
Rendering
Drawing the finished document on the screen.

Worked example

$ python3 -c "...walk the parsed tree of <main><h1>Hello</h1><p>World</p></main>..."
#document > main
main > h1
main > p

Captured on 2026-11-24 with Python's standard HTML parser. A browser builds a richer tree; this tiny model shows the same parent-child idea.

  1. The parser creates a node for main under the document.
  2. h1 and p become children of main.
  3. In a browser, document.querySelector('h1') finds that node and .textContent reads or changes its words.

Try it

In a browser console, run document.querySelectorAll('p').length on any page. Add a paragraph with the browser's element inspector and run it again.

If it goes wrong

A script runs before the elements exist
Place the <script> at the end of the body, or use defer in the head.
querySelector returns null
No element matched. Check spelling, and remember that a class needs .name while an id needs #name.

Check yourself

Decide your answer before you reveal it.

After a script changes a heading's text, what has changed: the HTML file or the DOM?

The DOM in memory. The source file on disk stays the same. The browser updates its render tree and paints the new text, but nothing is written back unless the page explicitly saves it.

How it works

The parser tokenizes bytes into elements and builds a tree with defined error recovery. CSS is parsed into style rules, then each element's computed style is resolved. Layout assigns boxes and positions; paint records drawing commands; compositing puts layers on screen. A JavaScript change to layout geometry can force a reflow, while a colour change may repaint without reflow. JIT engines optimize repeated script paths, but DOM calls cross a boundary into native browser code and can dominate cost.

Advanced usage

const frag = document.createDocumentFragment();
for (const name of ['Ada', 'Grace', 'Linus']) {
  const li = document.createElement('li');
  li.textContent = name;
  frag.append(li);
}
document.querySelector('#people').append(frag);

Illustrative snippet: build many nodes in a fragment, then insert once. This avoids repeated layout work compared with appending each item directly.

Edge cases and failure modes

  • Reading offsetWidth after a write can force synchronous layout; batch reads before writes.
  • innerHTML with untrusted text creates an injection risk; prefer textContent.
  • Custom elements upgrade after definition, so their state can change after first paint.
  • Shadow DOM scopes styles and hides nodes from ordinary querySelector calls.

Check yourself

A page feels slow while a script adds 10,000 rows one at a time. What evidence points to the DOM boundary, and what change would you try?

Model answer: a profile shows many small style or layout recalculations interleaved with script. Build the rows in a document fragment or virtualized list and insert once; measure again before claiming success.
