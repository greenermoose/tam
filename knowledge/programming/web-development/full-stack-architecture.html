Guide / Programming / Web development / Full-stack web architecture

A full-stack application joins the page a person sees, the program that answers it, and the place its data is kept.

What this is

The browser page asks for information over HTTP. A web server answers with data, often in JSON. The server reads and writes a database, which keeps information between visits.

Why it matters

Keeping page code and stored data apart lets many people use the same application without sharing one another's browser state. The server can enforce rules that a person could otherwise skip.

How to think about it

Picture a library. The page is the catalogue and the reading desk, the server is the librarian, and the database is the stacks. You ask at the desk; the librarian fetches the book; the stacks never come to you.

New words

REST
A style for naming things on a server and using HTTP methods to work with them.
SQL
A language for asking a database for rows and changing them.
Endpoint
A URL on a server that accepts a request and returns a response.

Follow one request

Goal: you will be able to trace one request from a browser-style fetch call to a JSON response and name what each side owns.

Learner path: previous: Node.js and npm; next: Web security.

Worked example

$ node server.mjs
200 application/json {"ok":true,"path":"/api/health"}

Captured on 2026-11-24 with Node.js 24.5.0. server.mjs opened a local HTTP server, returned a JSON object for /api/health, and the same program fetched that address and printed the response.

  1. The client used fetch with a URL for the local server.
  2. The server checked the request path and chose a response.
  3. The response carried status 200, content type application/json, and a short JSON body.

Try it

Change the server to return {"ok":true,"visits":1}. Fetch it again and confirm the printed body changes while the status stays 200. Then request a path the server does not handle and observe the difference.

If it goes wrong

The fetch fails with a connection error
The server is not listening, or the port in the URL is wrong. Start the server first and read its printed port.
The browser can reach the page but not the API
Check the origin and CORS. A server response that looks correct in Node may be hidden from browser script without permission.

Check yourself

Decide your answer before you reveal it.

Why can the server hide a value that the browser page must not show?

The browser runs page code on the reader's machine, so anything sent to it can be read. The server runs where the data lives and can refuse a request or omit fields before replying.

Architecture and trust boundaries

Reference

LayerOwnsTypical failure
Browser clientPresentation, input, local UI stateStale data, unsafe DOM writes
HTTP interfaceURLs, methods, status, headersMismatched method or content type
Application serverRules, authorization, sessionsTrusting client-supplied identity
DatabaseDurable rows and constraintsUnparameterized queries, lost updates

How it works

A REST design names resources as URLs and uses HTTP methods for actions: GET reads, POST creates, PUT replaces, and DELETE removes. A database queried with SQL enforces structure and constraints. The server treats every request as untrusted, checks identity and permission, and returns the smallest useful answer. JWT tokens and server-side sessions are two ways to remember identity; neither makes input safe by itself. A WebSocket upgrades an HTTP connection into a two-way channel when the page needs server-initiated messages.

Advanced usage

const result = await database.query(
  'SELECT id, title FROM notes WHERE owner = $1 ORDER BY id LIMIT $2',
  [userId, 50],
);
response.json({ items: result.rows });

Illustrative snippet: parameters keep values separate from SQL text, and a limit keeps one reply bounded.

Edge cases and failure modes

  • A GET handler that changes state can be replayed by caches or prefetching; use it only for reads.
  • Client-side validation improves feedback but is not a security boundary.
  • Unbounded list responses grow without limit; paginate with stable keys.
  • Two writes to the same row need a transaction or version check to avoid lost updates.

Check yourself

A user edits the price in browser code before submitting an order. What does a correct server do, and why?

Model answer: ignore the submitted price and read it from the product record under a transaction. The client is not a trusted party. The server rechecks identity, permission, and current data before committing. Relying on a hidden form field or a disabled input is not an authorization control.
