Guide / Programming / Web development / Web security

Web security is the practice of treating every input as untrusted and keeping data, identity, and code inside the right boundaries.

What this is

A page can receive text from a person, a URL, or another computer. XSS happens when that text becomes executable code in a page. CSRF happens when a site makes your browser send a request you did not intend.

Why it matters

A browser acts for the person using it. If a site can borrow that trust, it may read private data or change an account without a password.

How to think about it

Treat input like a parcel from an unknown sender. You may open it, but you do not let it plug itself into your electricity or hand it the keys to your house.

New words

HTTPS
HTTP carried inside encryption so a network observer cannot read or change the reply.
SQL injection
Input that changes the meaning of a database query.
Cookie
A small value a server asks the browser to keep and send back.

Keep text as text

Goal: you will be able to show untrusted text without executing it and explain why a salted hash protects stored passwords better than a plain hash.

Learner path: previous: Full-stack web architecture; next: Frameworks and tooling.

Worked example

$ python3 -c "from html import escape; print(escape('<script>alert(1)</script>'))"
<script>alert(1)</script>
$ node -e "const crypto=require('node:crypto'); const salt=crypto.randomBytes(4).toString('hex'); console.log(salt.length, crypto.createHash('sha256').update('hello').digest('hex').slice(0,16));"
8 2cf24dba5fb0a30e

Captured on 2026-11-24 with Python 3.14.8 and Node.js 24.5.0. The salt is random, so your eight-character value will differ; the truncated hash of hello is the same because SHA-256 is deterministic.

  1. Escaping turns < and > into text that the browser displays, not markup it parses.
  2. A salt is random data mixed into password hashing so two people with the same password do not share a stored hash.
  3. The hash shown here illustrates determinism; real password storage uses a deliberately slow function such as Argon2 or bcrypt, not a plain SHA hash.

Try it

Run the escaping command with <img src=x onerror=alert(1)>. Confirm the output contains no executable tag. Then change the Node command to print two hashes of the same word and note that each fresh salt changes the stored value.

If it goes wrong

The browser still runs the script
The text was inserted with innerHTML or an equivalent DOM sink. Use textContent or your framework's escaped output path.
A login works locally but fails after deployment
Check cookie flags, HTTPS, and the site origin. Secure cookies are not sent over plain HTTP.

Check yourself

Decide your answer before you reveal it.

Why is escaping output better than deleting the word script from input?

Escaping works at the place where text becomes page code, and it covers every tag and attribute form. Deleting one word can be bypassed with other tags, event attributes, or encoded characters; it also corrupts harmless input.

How it works

The same-origin policy lets a page read replies only from its own origin unless the server grants an exception with CORS. That policy protects reading, not sending: a form or image request can still leave the browser, which is why CSRF needs its own control. A content security policy narrows which scripts a page may load and where they may send data, limiting the damage of an XSS finding. Passwords are stored as salted hashes made with a slow memory-hard function; a secret sent to a browser is a public value, so API keys belong only on the server.

Advanced usage

Content-Security-Policy: default-src 'self'; script-src 'self';
  connect-src 'self' https://api.example.com; object-src 'none'
Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax; Path=/

Illustrative headers: the first limits script and network destinations; the second keeps a session cookie away from JavaScript and restricts when a browser sends it.

Edge cases and failure modes

  • HttpOnly blocks script access to a cookie but does not stop CSRF.
  • A permissive CORS origin plus credentials can turn a private endpoint into a public one.
  • Framework escaping is context-specific: HTML text, attributes, URLs, and JavaScript strings need different rules.
  • Secrets embedded in a client bundle cannot be kept secret from the person who runs the page.

Check yourself

A bug report says a private API works from curl but the browser blocks it. What evidence separates CORS from authentication?

Model answer: read the response status and headers. A 401 or 403 points at identity or permission. A successful curl reply with browser console text about a missing Access-Control-Allow-Origin header points at CORS: the server replied, but the browser refused to let script read it. Do not loosen authentication to fix a CORS error.
