Guide / Programming / Web development / Web security

Web security treats every input as untrusted and keeps data, identity and code inside the right boundaries. Small mistakes can let one visitor affect another.

Trust nothing from outside

XSS injects script into a page. CSRF makes a browser send an unwanted request. SQL injection changes a database query.

Why it matters

A page may show data from many people. Without boundaries, one person's input can become code, a forged request, or a changed query.

How to think about it

Treat every parcel as unlabeled. Check the address, open it carefully, and never assume the contents are harmless.

What just happened

The escaped line turns angle brackets into character references, so a browser shows the text instead of treating it as a tag. The sample file is authored data; the sandbox is not running a browser or Python. The same idea applies elsewhere, but the escaping rules depend on where the data will go.

Check yourself

Decide your answer before you reveal it.

Why is escaping context-specific?

HTML text, attributes, URLs and SQL each have different rules; one escape does not fit all.

What does HTTPS provide?

Encryption in transit and evidence that you reached the intended site.

How it works

Security depends on untrusted data staying in the right context: text stays text, parameters stay parameters, and credentials travel only over HTTPS. Framework escaping helps, but template holes and unsafe sinks still exist. Parameterised queries prevent SQL structure from being changed by input values.

Edge cases and failure modes

  • HTML sanitisation is harder than escaping because some markup is allowed.
  • CSP reports need monitoring; a policy can silently block assets.
  • CSRF tokens must be tied to the user session.
  • Secrets in client-side code are visible to every visitor.
