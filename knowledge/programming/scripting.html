Guide / Programming / Writing instructions your computer can repeat

A script is a short program you can run again. Careful scripts check their inputs and stop early when a step fails.

A recipe the computer repeats

A script is a text file of commands. A shebang on the first line tells the system which interpreter should read it.

Why it matters

Repeating a task by hand invites typos. A script records the steps so the same work happens the same way each time.

How to think about it

A script is a recipe card. The shebang names the cook; the remaining lines are the steps in order.

What just happened

-e stops on a failed command, -u stops on an unset variable, and pipefail makes a failed pipeline step count as failure. -x prints each step for debugging. The traces are sample output; the sandbox does not execute Bash scripts.

Try it

Think about a script that copies a file then deletes the original. With set -e, a failed copy stops the script before deletion.

What does pipefail add?

A pipeline reports failure if any stage fails, not only the last stage.

Why trace a script with -x?

To see the commands and expansions actually executed while debugging.

How it works

The kernel starts an interpreter through execve(2), which reads the shebang. Strict flags turn silent mistakes into visible failures. A script should define its exit-code contract: zero for success, distinct non-zero values for distinct failures.

Edge cases and failure modes

  • -e is ignored in conditions such as if cmd; then.
  • Arithmetic with an unset variable under -u can still evaluate as zero.
  • A cleanup trap may change the final exit status.
  • POSIX sh lacks arrays and pipefail, so portability needs care.
