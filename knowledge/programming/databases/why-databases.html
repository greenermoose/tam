Guide / Programming / Databases and data storage / Why databases exist

A program often needs to remember facts after it stops running. A database stores those facts in an organised way so the program can find them again.

Facts that outlive one run

You can write facts into a file, but plain text is hard to search as it grows. A database keeps related facts together and lets a program ask for just the ones it needs.

Why it matters

A shopping list in a text file works until you want to know which items cost more than five coins, or let two people edit it at the same time. A database answers questions about selected facts and keeps stored information intact when a program stops or crashes.

How to think about it

Think of a shoebox of paper notes beside a labelled filing cabinet. The notes hold the same information, but the cabinet has drawers and labels so you can pull one folder without reading every sheet.

New words

File
A named place on a disk that holds bytes.
Database
An organised collection of facts managed as one unit.
Table
Facts arranged in rows and columns.
Row
One recorded fact, such as one book.
Query
A question asked of stored data, often written in SQL.

Check yourself

Decide your answer before you reveal it.

Why is matching a CSV line easier than matching a sentence?

A CSV line puts each fact in a known position, so a tool can match one column. In prose the same fact may be phrased in many ways, and a match may hit an unrelated word.

What does it mean for stored facts to be durable?

Once a change is recorded as complete, it survives a later program stop or crash. Durability is about keeping accepted facts, not about how fast they were written.

How it works

A database management system is the program that owns the stored data. Applications send questions and changes to it; it plans the read, checks rules from the schema, and records completed changes. This separation is why one set of facts can serve several programs without each one inventing its own file format.

Edge cases and failure modes

  • With no schema, different writers can use different column orders; a database rejects writes that do not fit its declared structure.
  • Crash consistency is not free: a write must land completely or not at all, which costs extra work on disk.
  • Sharing raises concurrency questions. Two readers are cheap, but overlapping writes need coordination.
  • A small file is still the better tool when data is written once, read as a whole, and never queried selectively.

Check yourself

A program crashes while writing a note to a text file. Why might a database avoid the resulting mess?

A database groups a change into a transaction and makes it visible only when committed. An incomplete change is rolled back, so readers see the old value or the new one, not half a line. A hand-written file has no such boundary unless the program builds one itself.

When is a plain file the better choice?

When the data is small, written once, read as a whole, and never shared or queried selectively. Adding a database then buys structure you do not use while adding setup and operational cost.
