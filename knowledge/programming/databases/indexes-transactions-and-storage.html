Guide / Programming / Databases and data storage / Indexes, transactions and storage

A database must find rows quickly and keep them safe while several programs ask for changes. Indexes, transactions and storage rules are the tools it uses for that work.

Finding and protecting facts

A database index is an extra structure that helps find rows without reading the whole table. A transaction groups changes into one all-or-nothing step.

Why it matters

Looking through every row is fine for ten rows and slow for ten million. An index is like the alphabetical list at the back of a book. Transactions matter because a program may fail halfway through; you do not want half a change left behind.

How to think about it

Imagine a library card catalogue. Adding a new card to the catalogue takes a moment of extra work, but finding a book by title becomes fast. A transaction is like a sealed envelope: it goes into the record whole, or it does not go in at all. A commit seals it; a rollback throws it away.

New words

Database index
A helper structure that speeds up finding rows.
Transaction
A group of changes treated as one unit.
Commit
The step that makes a transaction's changes permanent and visible.
ACID
Four guarantees: atomicity, consistency, isolation and durability.
Partition
A way to split stored data into smaller pieces.

Check yourself

Why not put an index on every column?

Each index costs disk space and extra work on every write. Indexes help reads that match their keys, so columns that are rarely searched usually do not justify that cost.

What does a rollback guarantee?

Changes made in that transaction are discarded, so other readers never see the partial result. Accepted changes from other committed transactions remain.

How it works

Storage is divided into fixed-size pages within the file. The buffer manager keeps hot pages in memory and writes dirty pages later. Under a write-ahead log, the engine records the intended change and flushes that record before it lets a page change reach disk, so a crash can be repaired by replaying or undoing logged work. Multi-version concurrency control keeps older row versions so a reader can finish against one snapshot while a writer proceeds. A query plan may use an ordered B-tree walk or a hash lookup depending on the operator and predicate.

Edge cases and failure modes

  • Isolation anomalies: dirty reads see uncommitted data, non-repeatable reads see changed rows within one transaction, and phantoms are new rows that match an earlier predicate.
  • An index on a low-selectivity column, such as a boolean flag, may be ignored because a scan is cheaper.
  • Weaker durability settings can lose the most recent commits after power loss; stronger settings cost more flushes.
  • Long transactions hold old versions and can bloat storage until they finish.

Check yourself

A read is slow only for queries filtering on one column. What do you inspect first?

Check the query plan and the column's statistics before adding an index. If the plan already uses an index, look at selectivity, stale statistics, or parameter values; an index is not a universal speed-up.

Why can a committed transaction still be absent from a dirty page on disk?

The commit may be durable in the write-ahead log while the changed data page remains in the buffer cache. Recovery replays the log to bring the page up to date, which is why log flush order matters.
