Guide / Programming / Databases and data storage / Very large data sets

Some collections grow too large for one computer to hold or process quickly. This page names the storage and processing ideas used when data is spread across many machines.

When one machine is not enough

A distributed file system stores files across many machines but presents them as one place. Other systems spread rows across machines by a chosen partition. Parquet is a file format that stores columns together. A stream carries events as they happen, while a batch job reads a stored collection all at once.

Why it matters

More machines give more space and more work at once. Copies on different machines also mean the data survives one machine failing.

How to think about it

Picture a large warehouse with many shelves and a catalogue that says which shelf holds each box. A delivery belt brings new parcels while workers also process piles already on the shelves. That is the difference between a stream and a batch, and the catalogue is like partitioning.

New words

Distributed file system
Files spread over several machines: distributed file system.
Partition
A slice of data kept together, often on one machine: partition.
Replication
Extra copies for safety and speed: replication.
Parquet
A column-oriented file format for analytics: Parquet.
Stream
Items arriving over time rather than as a stored pile: stream.
Data lake and data warehouse
Raw files live in a data lake; curated tables live in a data warehouse.

Check yourself

Decide your answer before you reveal it.

Which approach fits a running total of events as they arrive?

A stream processor: it keeps state and updates the total per event. A batch job can recompute the same total later, but only after a stored set is available.

Why store analytics files in Parquet?

A query often reads a few columns across many rows. Keeping each column together lets the engine skip the rest and compress repeated values well.

How it works

Partitioning splits data so work and storage spread across machines; replication keeps copies so a failure does not lose data. Some stores accept eventual consistency, allowing replicas to catch up rather than waiting for every node. Columnar formats such as Parquet group values by column, which suits scans and compression. Query engines push filters down toward the files and shuffle rows only when a join or grouping needs it. A data lake keeps raw files cheaply; a data warehouse serves curated tables for reporting, the OLAP side rather than the OLTP side. Stream processors apply backpressure when consumers cannot keep up, so slow readers do not exhaust the producer.

Edge cases and failure modes

  • Hot partitions overload one machine while others stay idle.
  • Late events arrive after a batch window has closed and need a correction path.
  • Shuffles dominate cost; filtering early is cheaper than moving data.
  • Stream ordering is guaranteed within a partition, not across the whole topic.
  • More replicas improve survival and reads but cost storage and slower writes.

Check yourself

Why might eventual consistency be an acceptable trade?

A system that waits for every replica before acknowledging a write loses availability when a node is slow or offline. Accepting a short window of stale reads keeps the service usable; the application must then tolerate that window.

When does a lake cost more than a warehouse saves?

Raw files are cheap to store but costly to trust without curation. If consumers repeatedly clean the same files and need predictable tables, a warehouse with defined schemas repays its extra storage and pipeline work.
