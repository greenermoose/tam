Guide / Programming / Databases and data storage / IndexedDB

A web browser can keep structured data on the device it runs on. IndexedDB is the browser's own database, designed for web apps that must work without a network.

Storage inside the browser

IndexedDB keeps records in named object stores. Each record has a key, like a label on a box. An index helps find records by another field. A version number describes the layout, and a transaction groups changes so they finish together or not at all.

Why it matters

A web app that stores its notes, drafts or cached lists in the browser can open again without a connection. The data stays on that device, for that site only.

How to think about it

Imagine a small filing cabinet beside your own desk. You can add and find your own cards without asking anybody, but somebody on another computer cannot see them. That is useful for offline work and not a substitute for a shared server.

What just happened

result.txt is a scripted sample transcript, not a browser run and not a measurement from your machine; no browser or database software was started. The script asks to open a database at version 1. The upgrade handler creates an object store whose keyPath takes the key from the id field. A read-write transaction then puts one record. IndexedDB requests are asynchronous: handlers run after the request completes, and web code often wraps them in a promise.

Check yourself

Decide your answer before you reveal it.

Why is a version number needed?

Browsers create or change object stores only during an upgrade. Raising the version tells the browser to run that upgrade once, rather than on every open.

Is IndexedDB a replacement for a server database?

No. It is local to one browser and device, with storage limits and no shared authority. It helps an app work offline, but shared or durable business data still belongs on a server.

How it works

Opening with a higher version starts a versionchange transaction; that is the only place to create or delete object stores and indexes. A key path extracts the key from a stored value, while a key generator can supply one instead. A transaction lists the stores it touches and stays alive only while requests are pending; at an event-loop boundary with nothing outstanding it commits automatically. Requests are ordered within a transaction, and cursors walk records in key order. Values are stored with the structured clone algorithm, so plain data objects work but functions and live DOM nodes do not.

Edge cases and failure modes

  • An open connection in another tab can block a version upgrade until it closes.
  • A transaction used after it auto-commits raises an error; start a new one for later work.
  • Private browsing may discard the data when the session ends.
  • Quota exhaustion fails writes; handle the error rather than assuming unlimited space.
  • Concurrent tabs can observe version changes made by one another.

Check yourself

Why must new object stores be created in an upgrade transaction?

The version acts as a one-time signal that the schema changed. Confining structural changes there prevents two tabs from reshaping the same stores independently.

What breaks if you await unrelated work inside an open transaction?

With no pending IndexedDB requests, the transaction auto-commits. The later request then fails because its transaction is already finished; queue the work as requests instead.
