Guide / Programming / Databases and data storage / SQLite

SQLite is a database that lives inside your program rather than in a separate server. The whole database is one file, which makes it easy to carry, copy and test.

A database in a file

With SQLite, the program reads and writes a file directly. There is no database server to start, and no network address to configure. The file still holds tables of rows, and you still use SQL to ask questions.

Why it matters

For a phone app, a test suite or a small tool on your own machine, a single file is simple to ship and simple to back up. You can copy the file to another computer and the data goes with it.

How to think about it

Think of a notebook that each program can open and edit itself, rather than a library with a desk and a librarian. That is convenient for one worker; many workers writing at once need rules, and SQLite has a lock so only one writer proceeds at a time.

Check yourself

Decide your answer before you reveal it.

Why is SQLite a good fit for tests?

A test can create a private database file, run SQL against the same engine the application uses, then discard the file. There is no server to configure or reset between runs.

What is the main limit of the one-file design?

Only one writer can hold the write lock at a time. Several programs can read together, but heavy concurrent writing belongs in a client/server engine.

How it works

SQLite is a library linked into the application. A statement is compiled into a bytecode program that the virtual machine runs against pages from the database file. The page cache holds those pages; the journal or write-ahead log records enough information to finish or undo a commit after a crash. Locking coordinates processes that open the same file. Because the engine shares the application's process, there is no separate server, no authentication layer of its own and no network protocol.

Edge cases and failure modes

  • Long-lived write locks make other writers wait; use short transactions and a busy timeout.
  • A database on a network filesystem may not honour locking semantics reliably; keep the file on a local filesystem.
  • Without a primary key, row identity depends on the internal rowid, which can change if rows are reorganised.
  • Backing up a live file needs the engine's backup API or a consistent snapshot, not a blind copy during writes.

Check yourself

An application writes heavily from several threads. Why might SQLite be the wrong tool?

Writes serialise on a single lock, so throughput will not scale with threads. A client/server engine with row-level concurrency is a better fit; SQLite still suits per-thread private files or mostly-read workloads.

Why does copying a database file while writes are active need care?

The bytes may represent a moment midway through a commit. SQLite's backup interface takes a consistent copy under its own locks, which a raw file copy cannot guarantee.
