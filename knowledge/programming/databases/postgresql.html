Guide / Programming / Databases and data storage / PostgreSQL

PostgreSQL runs as a server that programs connect to over a network or local socket. Teams choose it when several applications must share one database and rely on strong SQL rules.

One database, many clients

PostgreSQL is a client/server, object-relational database. Programs send SQL to the server, and the server manages the stored tables. A schema groups related tables, while roles say who may read or change them.

Why it matters

A web application, a reporting tool and a background job can all use the same data without copying files between them. Transactions keep each change whole, backups protect it, and replication can keep another copy for recovery.

How to think about it

SQLite is a notebook carried by one program; PostgreSQL is a shared library with a counter and a set of rules. You go to the counter with a request, and the library decides whether your role permits it.

Check yourself

Decide your answer before you reveal it.

When would you choose PostgreSQL over SQLite?

When several applications or users share the same data, need role-based access, and require concurrent writes and central backups. For one application with a private, mostly local file, SQLite is simpler.

What does the REFERENCES clause in the sample schema do?

It declares a foreign key: a checkout's member_id must match a member id. The server can reject writes that would leave that reference pointing nowhere.

How it works

A client authenticates as a role and opens a connection to a database in a cluster. The parser and planner turn SQL into a plan that reads pages through the buffer cache. Multi-version concurrency control gives each statement a snapshot, and the write-ahead log makes commits recoverable and streams changes to replicas. Schemas namespace tables and types; extensions add capabilities without changing the core engine. Backups may be logical dumps or base backups combined with logged changes.

Edge cases and failure modes

  • Connection limits are per cluster; too many idle clients exhaust slots, so applications pool connections.
  • Long transactions delay vacuum and can bloat tables with dead row versions.
  • A replica may lag the primary, so a read from it can be slightly stale.
  • Partition pruning depends on the predicate matching the partition key; an unrelated filter may scan every child.

Check yourself

A reporting query blocks writes and table size keeps growing. What do you check?

Look for long-running transactions holding back vacuum, then check index usage and statistics. A snapshot held open is a common reason dead versions cannot be reclaimed; the fix is to shorten transactions, not to guess at hardware.

Why does a busy service need a connection pool?

Each PostgreSQL connection consumes a server process and a slot. A pool reuses a bounded set of connections so bursts of web requests do not exceed the limit or spend time on repeated setup.
