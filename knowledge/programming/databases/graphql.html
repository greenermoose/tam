Guide / Programming / Databases and data storage / GraphQL

GraphQL lets a client program ask a server for named fields. It is a contract between programs, not a place where data is stored.

Asking for named fields

Instead of receiving one fixed response, a client sends a GraphQL question listing the fields it wants. A schema says which fields exist. Functions called resolvers gather the values, and the answer usually comes back as JSON. A question that reads data is a query; one that changes data is a mutation.

Why it matters

A phone app and a reporting tool can ask the same service for different fields. Neither has to accept a large response built for somebody else, and the service keeps one public description of what is available.

How to think about it

Think of a form at a counter. You tick the fields you need, and the clerk collects exactly those from the filing system behind the desk. The form is GraphQL; the filing system may be any kind of database.

Check yourself

Decide your answer before you reveal it.

Is GraphQL a database?

No. It is an API query language and runtime contract. Resolvers may read a relational server, a document store or another service.

Why validate and authorise fields?

A client chooses the shape of the query, so a service must reject unknown or overly deep selections and check access at the field level. This is the same trust-boundary habit behind preventing SQL injection: never assume the request is friendly.

How it works

A request is parsed, validated against the typed schema and executed field by field. Resolvers may batch and cache lookups within one request to avoid an N+1 pattern, where listing twenty records triggers twenty separate database calls. Introspection lets tools discover the schema, so it can be limited in production. Because each client sends different selection text, HTTP caching is less straightforward than for a fixed endpoint; caches key on the query and variables. Large result sets use pagination, often a cursor, rather than unbounded lists.

Edge cases and failure modes

  • Deeply nested selections can generate unbounded work; depth or cost limits bound it.
  • Field-level authorisation is necessary; authorising only the endpoint is too coarse.
  • Partial success sends data and errors together, which clients must handle.
  • A resolver that reads a slow store can dominate the whole response.
  • Introspection or verbose errors can expose internal types to a client.

Check yourself

Why does batching resolvers matter more than a fast single query?

A selection that repeats one field across many items can issue one backend call per item. Batching collects the keys and performs one call, turning twenty round trips into one; improving each individual call barely helps.

Where does caching become difficult, and what is the usual answer?

Responses vary with the selection text and variables, so a plain URL cache key misses or mixes results. Keys must include the query and variables, or the service can use persisted queries with stable identifiers.
