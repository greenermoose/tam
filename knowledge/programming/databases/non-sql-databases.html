Guide / Programming / Databases and data storage / Non-SQL databases

Not all information fits neatly into tables. Some programs keep whole documents, simple labelled values, wide columns or connections between things instead.

Four shapes of stored data

Many people use NoSQL as a name for databases that do not require a fixed relational schema. A document database keeps whole records, often JSON-like. A key-value database stores a value under a key. A column-family database groups related columns. A graph database stores things and the links between them.

Why it matters

Real records do not all have the same fields. If one entry gains a new field, a document store can keep it without asking every other entry to change. Other families are fast at one particular job, such as finding a value by its key or following links.

How to think about it

A relational table is a printed form with fixed boxes. A document is a note that can grow. A key-value store is a shelf of labelled boxes. A graph is a map of places and roads between them. Each shape makes some questions easy and others awkward.

Check yourself

Decide your answer before you reveal it.

Which family fits a lookup by one known key?

A key-value database: it retrieves a value from its key without scanning every record. A document store is better when you also filter on fields inside the value.

What is gained and lost by flexible fields?

Records can vary and evolve without a table rewrite. The cost is that rules about fields move into the application, and queries must match the chosen indexes.

How it works

Relational systems plan joins from a fixed schema. These families move work elsewhere. A document store embeds related data in one record and indexes chosen fields, so a read can avoid a join. A key-value store uses a key to reach one value quickly. A column-family store groups columns by a partition key and writes them across nodes, with consistency levels that trade immediate agreement for progress when nodes are unavailable. A graph store keeps edges as first-class data so traversal follows links directly. Indexes are still needed; flexible shape is not the same as no design.

Edge cases and failure modes

  • Denormalised records can disagree with one another after a partial update.
  • An access pattern that changes may need a new index or a full data rewrite.
  • Replica lag can return a stale value after a successful write.
  • A hot key concentrates traffic on one node despite a distributed design.
  • Transactions that span many documents or partitions are usually narrower than in a relational server.

Check yourself

When would you keep the relational table instead?

When the same structured facts are queried in many unplanned ways and must agree across rows. Joins, constraints and a fixed schema then do useful work that a document or key-value design must rebuild in application code.

Why does a column-family design begin with the query?

Because rows are laid out around a partition key and clustering columns. A query that does not follow that layout may scatter across nodes, so the access pattern is chosen before the data model is fixed.
