Guide / Programming / Databases and data storage / MySQL and InnoDB

MySQL keeps data in a server that other programs ask questions of. InnoDB is the part of MySQL that stores the data and protects it while many people change it.

Data in named tables

MySQL is a database management system. Programs send it questions written in SQL. The answers arrive as rows from named tables. InnoDB is the usual engine that stores those rows.

Why it matters

A shared server means one copy of the data, with rules about who may change it. InnoDB keeps working after a crash and lets two people edit different rows without losing either change.

How to think about it

Imagine a set of labelled drawers. A drawer is a table, each card in it is a row, and the headings on the card are columns. An index is the sorted card list that lets you find a card without reading the whole drawer.

New words

Database management system
Software that stores data and answers questions about it: database management system.
SQL
The language used to ask a relational database for data: SQL.
Table, row and column
A table is a list of records; a row is one record and a column is one field of every record.
Index
A helper structure that makes finding rows faster: database index.
Transaction
A group of changes treated as one unit: transaction.
Replication
Keeping copies of the same data on other servers: replication.

Check yourself

Decide your answer before you reveal it.

Why does the sample give one name for the Leeds question?

Only one inserted row has city Leeds. The condition filters rows before the name column is returned.

What does a primary key do?

It identifies each row uniquely. InnoDB also uses it to order the stored rows, so choosing it affects both correctness and speed.

How it works

InnoDB stores a table as a B-tree keyed by the primary key; the leaf pages hold the whole row, which is why the clustered key choice matters. A secondary index holds indexed values plus the primary key used to find the row. Pages are cached in the buffer pool. A transaction writes change records to the redo log, so committed work survives a crash; undo records keep earlier versions available for consistent reads, the mechanism usually called MVCC. Locks coordinate writers, and gap locks can block inserts into a range. The storage engine sits below SQL, so MySQL can host engines with different guarantees.

Edge cases and failure modes

  • A table without a declared primary key still gets an internal clustered key.
  • Random or frequently changed primary keys cause page splits and poor space use.
  • Long transactions retain undo versions and can delay cleanup.
  • Rows visible to a read depend on the isolation level and transaction snapshot.
  • Replication copies committed changes, not a single instant across all servers.

Check yourself

Why can a secondary index lookup still touch the clustered index?

Because its leaf entries hold the primary key, not the whole row. Finding the row requires a second lookup in the clustered tree, unless the index covers every requested column.

Which trade-off sits behind choosing a storage engine?

InnoDB buys crash recovery and transactions at the cost of logging, locking and cache memory. An engine without those features can be simpler for work that never needs rollback or concurrent edits.
