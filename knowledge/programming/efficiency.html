Guide / Programming / How software can wait for work efficiently

Software can wait for a notification instead of asking repeatedly whether work arrived. That keeps the processor idle and saves energy.

Doorbell or repeated knocking?

A program that polls checks the same condition again and again. A program that waits is told when something changed. The CPU can then go idle and enter a low-power C-state.

Why it matters

Polling wakes a processor for no reason. On a battery-powered machine, that wasted wakefulness shortens the time between charges.

How to think about it

Checking the door every ten seconds is polling. A doorbell is an event: you sit down until someone rings.

Try it

Imagine a script that sleeps for one second and checks a file each time. Replacing that with a filesystem notification means the script runs only when the file actually changes.

The lock file protects socket creation; the socket itself is the event channel.

Check yourself

Decide your answer before you reveal it.

Why does polling waste energy?

It wakes the processor repeatedly even when nothing changed.

What does an event wait do instead?

It blocks until a kernel notification says the watched descriptor is ready.

How it works

An event-driven program registers interest with the kernel and blocks in a wait call. The kernel marks the descriptor ready and wakes the task. That avoids a timer loop and lets the scheduler keep the CPU in a deep idle state between events.

Edge cases and failure modes

  • Spurious wakeups require rechecking the condition after returning.
  • Level-triggered descriptors can wake repeatedly until drained.
  • Mixing blocking and non-blocking descriptors needs careful state handling.
  • Too many watched descriptors increase registration and teardown cost.
