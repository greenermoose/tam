Guide / Desktop and applications / Typography / When text looks wrong

When text looks wrong, the cause is usually in one layer of the text stack. Identifying the layer first makes the fix smaller, safer, and easier to confirm.

Find the layer before the fix

Text on a screen goes through several steps. A character is chosen, a font is selected, the shape is drawn, and pixels are painted. If any step goes wrong, you may see boxes, the wrong font, odd spacing, blurry letters, or a console that looks nothing like your desktop.

Why it matters

People often reinstall fonts or change random settings when text looks bad. That can hide the real problem. A calm check saves time: first look at what you see, then guess the likely layer, then try one safe check.

How to think about it

Think of printing a sign. If a letter is missing from the stencil, you get a blank box. If the wrong stencil is picked, the style changes. If the stencil is old, the shop may use an outdated copy. If the letters are placed badly, spacing looks strange. If the paint is smudged, the edges look blurry.

New words

Tofu
Empty boxes shown when a font has no glyph for a character.
Font substitution
Using a different font when the requested font or character is not available.
Font cache
Saved font information that programs reuse for speed.
Text shaping
Choosing and positioning glyphs for characters, especially in complex scripts or ligatures.

Not every problem is a font bug. A missing character is different from a blurry pixel. A virtual console also uses a different text path than a graphical terminal, so it can look different on purpose.

Try it

When you see a text problem, write down the symptom before changing anything. Then ask: is a character missing, is the family wrong, is the shape wrong, or are the pixels wrong? That one question usually picks the layer.

If it goes wrong

You refreshed caches but the glyph is still missing.
A cache refresh cannot invent coverage. You need a font that contains the character.
The terminal looks better, but the console still looks wrong.
The Linux virtual console uses its own font path. A desktop terminal setting will not fix it.
Disabling ligatures changed the look but not the meaning.
That is normal. Ligatures are a shaping choice; confirm the underlying characters are still correct.

On Tamlinux, desktop font selection flows through fontconfig and appearance tools described in Typography, fonts and text rendering. The generic family defaults in /usr/share/fontconfig/conf.avail/50-tamlinux.conf are a good place to understand why a monospace or sans-serif request resolves to a particular family.

Check yourself

Decide your answer before you reveal it.

A character becomes a box, but the rest of the line looks fine. Which layer do you check first?

Check glyph coverage first. The selected font may not contain that Unicode character, so the renderer shows tofu.

Why can a desktop terminal and the Linux virtual console show different fonts for the same user?

They use different text paths. A graphical terminal uses desktop font rendering, while the virtual console uses console fonts loaded through tools such as setfont.

How it works

Text rendering failures are often misreported as "font broken". A more precise model separates selection, shaping, and rasterization. Fontconfig resolves a requested pattern to a font file or fallback chain. HarfBuzz turns Unicode text into positioned glyphs, applying font features and script rules. FreeType rasterizes outlines to bitmaps at a given size, DPI, and hinting mode. A console stack can bypass much of this and use bitmap console fonts instead.

Substitution is normal. It becomes a problem when the fallback choice has different metrics, missing style variants, or poor script coverage. Cache staleness is another common but narrow cause: it affects discovery of newly installed or removed fonts, not the shape of already resolved glyphs.

Advanced usage examples

# See which font resolves for a generic family
fc-match -f '%{family}:%{style} %{file}\n' monospace

# Ask fontconfig for a character-capable fallback
fc-match -f '%{family}\n' ':charset=4E2D'

# Refresh user font cache after installing fonts into a user font directory
fc-cache -f ~/.local/share/fonts

# Inspect a console font change in the current session
setfont /usr/share/kbd/consolefonts/ter-132n.psf.gz

These commands are illustrative read-only or session-local checks. Do not treat them as a script to run blindly; confirm paths and scope on your system.

Edge cases and failure modes

  • Metric mismatch: fallback fonts may have different widths, causing misaligned tables or cursor movement in terminal-like layouts.
  • Shaping versus encoding: a missing or incorrect glyph can come from encoding/input issues, not shaping. Verify the code point first.
  • Hinting disagreements: changing hinting can improve small-size Latin text but worsen other scripts or high-DPI rendering.
  • Console limitations: a PSF console font has limited glyph coverage compared with desktop font stacks; missing characters may be expected there.
  • App-specific rendering: two programs can show the same font differently because they use different shaping, hinting, or compositing paths. Compare with a second viewer before changing system-wide settings.

Check yourself

A user reports blurry text only in one application after changing display scale. Why is font substitution an unlikely first cause?

Substitution usually changes family, metrics, or glyph coverage, not clarity in a single scaled application. A scale, hinting, rasterization, or application rendering path issue is more plausible. You would first compare DPI/scale and rendering settings before changing fontconfig rules.

When is refreshing fontconfig caches the right fix, and when is it a distraction?

It is right when a newly installed or removed font is not being discovered. It is a distraction for tofu caused by missing coverage, wrong shaping, poor hinting, or console font limitations, because those problems are not caused by stale discovery metadata.
