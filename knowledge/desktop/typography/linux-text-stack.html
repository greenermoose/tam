Guide / Desktop and applications / Typography / The Linux text stack

A line of text passes through several programs before it reaches the screen. Each one answers a different question: which characters were typed, which font to use, which shapes to draw, and where the pixels go.

A relay race

When you press a key, the computer turns it into a character. Other programs then choose a font family, look up the shapes, arrange them, and colour the pixels. Text appears only after all of those steps have finished.

There is also a simpler route for the text-only console. It uses fixed pictures stored in the kernel and does not go through the desktop's font choices.

Why it matters

When text looks wrong, the useful question is which step made the decision. A missing letter, an odd space and a rough edge usually come from different stages.

How to think about it

Imagine a relay race with a baton. The keyboard runner hands over characters, the font runner chooses a family, the shaping runner arranges shapes, and the drawing runner paints them. If the baton is dropped, you look at the runner who held it last.

New words

If it goes wrong

You expected the desktop font choice to affect the console.
The text-only console does not use Fontconfig, FreeType, HarfBuzz or Pango. It has its own font path.
You expected Unicode to choose a font.
Unicode names characters; font selection happens later and depends on installed families and rules.

Tamlinux sources show that 50-tamlinux.conf assigns sans-serif to Liberation Sans, serif to Liberation Serif and monospace to JetBrainsMono Nerd Font. It also prepends Noto Naskh Arabic for Arabic lang patterns and appends Noto Nastaliq Urdu for Urdu patterns. The commands tam-font-list and tam-font-current use fc-list and fc-match, and the menu offers a font selector built on them.

Check yourself

Decide your answer before you reveal it.

Which tool chooses a font family for a generic request such as monospace?

Fontconfig. It matches a pattern against installed fonts and rules. HarfBuzz receives a chosen font and shapes text; FreeType rasterizes glyphs from it.

Which path uses setfont and PSF files?

The virtual console path: the framebuffer console in the kernel and setfont(8) loading a PSF through the kernel font interface. The graphical application path does not use that route.

How it works

A key event becomes a character through input handling and locale settings. The application stores it as Unicode code points. Fontconfig matches a pattern, applying generic family assignments, language rules and aliases; this is font substitution. The chosen font file supplies a character map, outlines or bitmaps, metrics and feature tables. HarfBuzz looks up glyph IDs and applies substitutions and positioning. Pango divides the text into runs, handles fallback when a font lacks coverage, and lays out lines. The toolkit draws through the rasterizer, and the compositor presents the result. Fontconfig user manual Unicode Standard

FreeType loads outlines, applies hinting and produces a bitmap; Pango and the toolkit use that bitmap at a positioned offset. The shaping result is a list of glyph IDs and advances, not pixels. FreeType documentation HarfBuzz manual Pango reference and rendering pipeline

The console path is separate. fbcon uses built-in bitmaps or a PSF loaded through KDFONTOP by setfont(8). No Fontconfig rule, HarfBuzz feature or FreeType hinting is involved. Similar-looking text can therefore have completely different causes.

fc-list : family | sort -u | head -n 20
fc-match monospace -f '%{family}\n'
hb-shape --font-file=LiberationSans-Regular.ttf --text="office"
ftview LiberationSans-Regular.ttf

The first command lists families, the second reports the match for a generic request, the third prints shaped glyph IDs, and the fourth opens a rasterized view. All four read files or settings without changing them.

Two Tamlinux product sources tie the graphical path together. tam-font-list runs fc-list :spacing=100 -f "%{family[0]}\n", filters emoji, signwriting and Tamlinux Icons, then sorts unique names; it reports monospace families. tam-font-current runs fc-match monospace -f '%{family}\n' | head -n1 | cut -d, -f1, so Fontconfig is the source of truth and the first alias entry is printed. Nerd Fonts such as JetBrainsMono Nerd Font supply extra symbols through their glyph coverage.

A cache rebuild writes files. To study it without touching real settings, point Fontconfig at a configuration and font directory inside a scratch folder:

FONTCONFIG_FILE=/home/alex/scratch/fonts.conf fc-cache -f

Here the scratch configuration is expected to name directories under the same scratch folder. Running fc-cache without that override would write to the normal user cache, which is a user-level change and outside this exercise.

Edge cases and failure modes

  • A locale affects characters and sorting, but it does not select a font by itself.
  • Fallback can split one word across fonts, which breaks ligatures and kerning at the boundary.
  • A stale font cache can hide a newly added family; rebuild it in scratch when testing rules.
  • Emoji and colour glyphs may skip outline rasterization but still need a font and a run.
  • A console font change cannot fix a graphical application, and a graphical font change cannot fix the console.

Check yourself

Why is fc-match a better first check than fc-cache when a generic family resolves oddly?

fc-match reports the decision Fontconfig currently makes and reads only configuration. fc-cache changes cache files. Finding the wrong decision first, then testing a rule change in scratch, keeps the investigation reversible.

What is lost if the graphical path and the console path are treated as one stack?

Diagnostics get aimed at the wrong layer. A console bitmap problem cannot be solved by changing a desktop font family, and a shaping problem cannot be solved by loading a PSF. The two paths share only the idea of drawing text.
