Guide / Desktop and applications / Typography / A typography diagnostic workbench

Text problems are easier when you name what you see and find the layer that owns it. This page gives a small method and a safe place to practise it before touching any real settings.

Name what you see

Sometimes a letter is missing, a word is spaced oddly, or an edge looks rough. Each clue points to a different stage between choosing a font and drawing it.

The method is simple: say what the problem looks like, guess which stage could cause it, look at that stage, and then try one small change. You put the change back if it does not help.

Why it matters

Random changes can hide the original problem. A careful note of the symptom makes it possible to tell whether a fix worked.

How to think about it

Think of a mechanic listening to an engine before opening it. The sound tells them which part to inspect first, so they do not take the whole machine apart.

New words

Symptom
What you actually see, described without guessing the cause.
Layer
One stage of the text path that can be checked on its own.
Tofu
An empty box or missing-glyph shape where a letter should be.
Hinting
Instructions that help outlines meet the pixel grid.

A four-step method

Goal: you will be able to name a symptom, choose a layer, gather read-only evidence, and make one reversible change in a scratch setting.

  1. Name the symptom in one sentence, such as "one letter shows as a box".
  2. Choose a layer: font discovery, selection, text shaping, rasterization or the console.
  3. Gather evidence with commands that only read files and settings.
  4. Change one thing in a scratch copy, compare the result, and restore the original.

If it goes wrong

You treated the samples as real output.
They are simplified stand-ins for a rule file, a cmap excerpt and a shaping transcript. Real checks use the tools in the Expert section.
You changed a setting while investigating.
Undo it and restart from a symptom sentence. One change at a time keeps the evidence readable.

The Tamlinux font configuration file 50-tamlinux.conf assigns generic families and adds language-specific rules. In the graphical path, tam-font-current reports what fc-match monospace resolves and tam-font-list lists monospace families. Those product sources tell you where the selection decision comes from; they do not replace a per-symptom check.

Check yourself

Decide your answer before you reveal it.

A letter shows as a box in one application. Which layer do you check first?

Font selection and coverage. Confirm which family the application chose, then check whether that font maps the code point. A rasterization or hinting change cannot create a missing glyph.

Console text is wrong but graphical text is fine. What does that rule out?

It rules out Fontconfig rules, shaping features and FreeType rasterization for that symptom. The framebuffer console has its own bitmap font path, including setfont.

Reading the samples as evidence

The rule sample says a monospace request is rewritten by prepending another family. That is a font substitution decision, owned by Fontconfig. The cmap sample says one code point is unmapped while others have glyph IDs; with a glyph missing, the likely layer is coverage, not text shaping. The shaping sample shows that a ligature changes a five-glyph run into a three-glyph run; that is a substitution applied before rasterization. Fontconfig user manual HarfBuzz manual

Use a scratch configuration whose directories are under /home/alex/scratch. Keep the original rule file untouched, write one change into the copy, run the check again, then delete the scratch folder. This is the only reversible change the exercise makes, and it writes only inside scratch.

Edge cases and failure modes

  • Two applications can resolve the same generic family differently if they send different language or style properties.
  • A stale cache can make a scratch result look like a rule failure; confirm what the scratch configuration actually lists.
  • Fallback can hide a missing glyph in one application but not another, because the fallback font differs.
  • A console symptom and a desktop symptom can occur together for unrelated reasons; keep two symptom sentences.
  • Changing several rules at once loses the link between a cause and its effect.

Check yourself

Why not start with fc-cache when a family looks wrong?

fc-cache writes cache files and only helps when the cache is stale. First ask fc-match what Fontconfig currently decides. If the decision is wrong for a reason in the rules, test the edited rule in scratch and rebuild that cache there.

What does a console-only symptom rule out, and why?

It rules out the graphical path's selection, shaping and rasterization. The console draws from bitmap arrays or a PSF loaded through setfont; it does not consult Fontconfig, HarfBuzz or FreeType. The layer decision follows the evidence, not the resemblance of the glyphs.
