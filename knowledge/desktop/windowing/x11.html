Guide / Desktop and applications / Windowing systems / How X11 draws windows

X11 is the older display system that Linux desktops used for decades. It still runs legacy applications through XWayland.

What this is

In X11, one program called the X server owns the screen, keyboard and mouse. Applications are X clients: they ask the server to draw and tell it when they need input.

Why it matters

Many older Linux applications and tools still speak X11. When one misbehaves, knowing which part is the server, which part is the application and which part is the window manager tells you where to look.

How to think about it

Imagine a clerk at a drawing board. Applications send the clerk instructions such as "draw this box" or "tell me when a key is pressed". A separate interior decorator moves the finished boxes around and adds title bars.

New words

X server
The program that owns the screen and input devices.
X client
An application that sends drawing requests and receives input.
Window manager
A special client that places windows and draws their frames.
Xlib and XCB
Libraries that applications use to speak the X protocol.

The output is fixed teaching data; the sandbox does not inspect or alter your system.

Try it

In a text terminal, run printf '%s\n' "$DISPLAY". A value such as :0 means X11 clients can find a display. Then run printf '%s\n' "$XDG_SESSION_TYPE": on a modern Wayland session this can say wayland even though DISPLAY is set for compatibility.

If it goes wrong

DISPLAY is empty
No X11 display was named in that shell. A fresh login, a text console or a remote shell may need different setup; do not assume the graphical session is broken.
A window has no title bar
The window manager may be missing, or the application may draw its own decoration. Check the compositor or window manager process before blaming the application.

On Tamlinux: the graphical session is Wayland today. X11 programs run through XWayland, so seeing DISPLAY does not mean the whole desktop is an X11 session.

Check yourself

Decide your answer before you reveal it.

Is the window manager the same thing as the X server?

No. The X server owns the screen and input. The window manager is an application that asks the server to place windows and draw frames. On Wayland those jobs are combined inside the compositor instead.

Reference

Parts of the X11 stack

PartRole
X serverOwns outputs, input devices, fonts and drawing resources; sends events to clients.
X clientAny program that opens a display connection and requests drawing or input.
Xlib / XCBClient libraries that encode and decode the X11 wire protocol. XCB is asynchronous and exposes extensions directly.
Window managerA client that manages top-level windows, focus and decorations.
ICCCM / EWMHConventions that let clients, window managers and desktops agree on properties such as title, state and workspaces.
XWaylandAn X server that runs as a Wayland client to support older X11 applications.

How it works

X11 is a request/event protocol over a byte stream, traditionally a Unix domain socket or a network connection named by DISPLAY. Clients create windows and resources such as pixmaps and graphics contexts, then send requests that the server serialises. Events travel the other way. Extensions add rendering, shape, RandR mode setting and compositing without changing the core protocol.

Advanced usage examples

A remote X11 run can use ssh -X to forward the display through an encrypted tunnel. Bare network transparency is convenient but unsafe by default: a client with display access can usually observe input and windows belonging to other clients. Modern deployments therefore treat X11 forwarding as a compatibility tool, not a general desktop security boundary.

Edge cases and failure modes

  • Any client can ask for global key events or read another window's pixels, which is why screen locks and password fields need special handling.
  • There is no atomic presentation contract equivalent to Wayland's surface commit, so tearing and inconsistent multi-monitor updates are harder to eliminate.
  • Client-side decoration and compositing extensions blurred the old split between server, window manager and application.
  • HiDPI scaling was added through properties and toolkit policy rather than a single core protocol rule.

Check yourself

A legacy program opens a window on a Wayland desktop. What is most likely supplying its X11 display?

Model answer: XWayland. It runs an X server as a Wayland client, translating X11 requests into surfaces for the Wayland compositor. The program can still behave like an X11 client even though the session type is Wayland; global input and screen-capture rules depend on the compositor and portal policy.
