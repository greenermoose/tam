Guide / Desktop and applications / Windowing systems / How Wayland draws windows

Wayland is the protocol that most modern Linux desktops use. In it, the compositor is both the display server and the program that places windows.

What this is

An application draws its own window into a private area of memory and hands the finished picture to the compositor. The compositor decides where that picture appears, what lies on top, and which keyboard or mouse events go to which application.

Why it matters

This arrangement keeps applications separate. One program cannot normally watch every key you press or read the whole screen without the compositor explicitly allowing it.

How to think about it

Think of a gallery with one curator. Each artist paints a canvas, but only the curator hangs the canvases, chooses the lighting and hands visitors' questions to the right artist.

New words

Compositor
The process that presents surfaces and routes input.
wl_surface
The protocol object that represents a drawable surface.
xdg-shell
The extension that turns a surface into an ordinary window with roles such as a toplevel.
XDG desktop portal
A negotiated service for jobs such as choosing a file or capturing the screen.

Try the idea in a sandbox

wayland-1 Try: echo WAYLAND_DISPLAY The socket name identifies a connection endpoint. Native clients connect to the compositor through that socket. Try the command shown above (or type help).

The output is fixed teaching data; the sandbox does not inspect or alter your system.

Try it

In a graphical terminal, run printf '%s\n' "$WAYLAND_DISPLAY" "$XDG_SESSION_TYPE". A value such as wayland-1 plus wayland means native Wayland clients can connect. A blank first line with x11 means you are in an X11 session; see the session-checks page for a fuller read-only check.

If it goes wrong

Screen capture fails in an application
Wayland does not give every client global screen access. Use the compositor's screenshot key or a portal-based tool.
A window has no border drawn by the compositor
Many Wayland toolkits draw their own title bars. That is toolkit policy, not a missing window manager.

On Tamlinux: Hyprland is the current Wayland compositor. The planned tam-pane compositor is intended to replace it later; Sway and wlroots are not planned.

Check yourself

Decide your answer before you reveal it.

Who draws the buttons inside a Wayland application's window: the compositor or the application?

The application, using a toolkit such as GTK or Qt. The compositor places the finished surface, combines it with others and routes input. It does not normally draw widget contents.

How it works

Wayland is an asynchronous object-oriented wire protocol over a Unix domain socket named by WAYLAND_DISPLAY. A client binds globals from the registry, creates objects such as surfaces and seats, and sends requests without waiting for a reply for every one. The compositor owns DRM/KMS outputs, chooses modes, applies surface state at commit time and drives presentation. Extensions are optional globals; a client must negotiate the ones it needs.

Advanced usage examples

A shell panel can use the layer-shell protocol to reserve a strip of an output and anchor widgets to an edge. A remote-desktop client can use portal interfaces instead of reading all pixels directly. Both are protocol negotiations, not built-in rights every client receives.

Edge cases and failure modes

  • Protocol support varies between compositors; an extension that works on one desktop may be absent on another.
  • Client-side decorations mean the visible frame belongs to the application's toolkit, even though the compositor owns the surface.
  • Wayland has no built-in network transparency analogous to X11 forwarding; remote display uses separate protocols.
  • Buffer lifetime matters: a client must not reuse a buffer while the compositor still holds it, so toolkits manage release events.

Check yourself

A screenshot tool cannot read the whole screen in a Wayland session. Is that a bug in the compositor by default?

Model answer: no. Global screen access is deliberately not a basic Wayland right. The compositor exposes screenshot or remote-desktop capability through its own interface or an XDG desktop portal, usually with user consent. A tool that assumes it can read the root window, as on X11, needs a different implementation.
