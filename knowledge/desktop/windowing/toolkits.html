Guide / Desktop and applications / Windowing systems / How graphical toolkits build interfaces

A graphical toolkit is a library that supplies the buttons, menus, text fields and windows inside an application. The display system puts the finished window on the screen; the toolkit decides what is inside it.

What this is

A widget is one reusable interface part, such as a button or a slider. A toolkit collects widgets, layout rules and event handling so an application does not draw every pixel itself.

Why it matters

Two applications on the same desktop can look different because their authors chose different toolkits. When one application's controls behave strangely, the cause may be in the toolkit rather than the compositor.

How to think about it

Think of a toolkit as a box of pre-cut parts. You arrange buttons and labels in the box's layout system, and the toolkit draws them and tells your code when someone clicks.

If it goes wrong

A button looks wrong but the window is placed correctly
Look at the toolkit version, theme or stylesheet before the compositor.
A window appears with no control at all
Look at the application and its toolkit backend; a missing display backend means it may not have drawn a surface.

On Tamlinux: the shell uses Quickshell and Qt Quick, with QML describing its panels and controls. Many applications use GTK or Qt; web-based applications use Electron or a browser engine.

Check yourself

Decide your answer before you reveal it.

A KDE application and a GTK application show different buttons on the same Wayland session. Is the compositor responsible?

No. Each toolkit draws its own widgets inside the application's surface. The compositor places those surfaces, combines them and routes input. Different widget appearance is a toolkit and theme matter.

How it works

A toolkit supplies an event loop, a widget tree, layout, styles, accessibility bridges and backend integration. On Wayland, a toolkit backend connects to protocol globals, creates surfaces, handles configure events and sends buffer releases. On X11, the same toolkit uses an X11 backend. Applications normally see a stable widget API even when the display protocol changes underneath.

Advanced usage examples

A Qt Quick shell can describe a panel declaratively in QML and bind its width to an output geometry exposed by the compositor. A GTK application can use a CSS stylesheet to restyle widgets without changing application logic. Both ultimately commit finished buffers; neither sends raw drawing commands to the display server in the X11 sense.

Edge cases and failure modes

  • Toolkit backends differ in feature support, so global shortcuts, screen capture and translation may need portal negotiation.
  • Client-side decorations belong to the toolkit, not the compositor; theme changes can therefore alter title bars without any display change.
  • Accessibility and input methods depend on both toolkit bridges and compositor or platform services.
  • Web-based applications may look consistent across systems but notice more differences in native settings and permissions.

Check yourself

Why can a toolkit be portable across X11 and Wayland without changing the application's button code?

Model answer: the application talks to a widget API, and the toolkit implements that API over one or more display backends. The backend handles surfaces, events and buffers for X11 or Wayland. Widget layout and callbacks stay the same, though some platform-specific features need negotiation.
