Guide / Desktop and applications / Windowing systems / A short history of windowing systems

A window is a rectangular area on a screen that shows one program while other programs stay nearby. Windowing systems grew from research ideas into the ordinary way people use a computer.

What this is

Early computers usually ran one program at a time on a screen of text. A window lets several programs share the screen: each gets its own rectangle, and you can bring one forward or put it aside.

Why it matters

The window controls you use today, and the arguments about X11 and Wayland, come from choices made decades ago. Knowing that history makes current desktop design easier to understand.

How to think about it

Think of a desk covered with sheets of paper. You can overlap them, move one to the front, and read another without putting the first away. A windowing computer does the same with program output.

New words

Desktop environment
The windows, panels, settings and applications that make up a graphical desktop.
Compositor
The program that places finished windows on the screen.
X11
The older display system that Linux desktops used for many years.
Wayland
The modern display protocol used by most Linux desktops today.

Follow one idea through time

Goal: you will be able to name the main stages that led from shared screens to today's X11 and Wayland desktops.

Learner path: start: A short history of windowing systems; next: How X11 draws windows.

Worked example

Trace the same job, "show two programs at once", through four designs:

  1. A research desktop draws both programs into one screen-sized picture, with a mouse pointer and overlapping rectangles.
  2. X11 puts a display server between programs and the screen. Programs ask that server to draw; a separate window manager places and decorates windows.
  3. GNOME and KDE add a complete desktop environment: panels, settings, icons and core applications on top of X11.
  4. Wayland gives the compositor both jobs. Applications draw their own surface and hand it to the compositor, which places it on screen.

The idea of a window stayed. The owner of the screen changed.

Try it

Look at your current desktop and write down three separate windows, one panel or bar, and which program probably draws each one. Do not change settings; this is an observation exercise.

If it goes wrong

The names blur together
Keep three jobs separate: drawing a window, placing a window, and building the buttons inside it. The pages in this series use that split throughout.
You cannot see several windows
A phone or a single full-screen application still uses a windowing system internally. You just see one surface at a time.

Check yourself

Decide your answer before you reveal it.

Why did overlapping windows need a program to manage them?

Because more than one program draws into the same screen area. Something must decide which rectangle is on top, where it sits, and where keyboard and mouse events go. X11 called that program a window manager; Wayland folds the job into the compositor.

How it works

The important transition is not "graphics got newer" but "who owns the final picture". X11 keeps a display server that owns drawing resources and a window manager that behaves like a privileged client. Wayland makes the compositor the display server, so the same process that places windows also presents buffers and routes input. Desktop environments then layer policy, panels and applications over whichever model they use.

Advanced examples

Compare three lineages: X11's protocol-and-toolkit model; Apple's Quartz and AppKit family; and Windows' USER/GDI and Desktop Window Manager family. Each solves placement, drawing and input, but they divide the work across different libraries and kernel interfaces.

Edge cases and failure modes

  • History is not one straight ladder: overlapping research systems, X11 and commercial desktops developed in parallel.
  • A desktop environment is not a display protocol. GNOME and KDE can sit above different display systems over time.
  • "Client-side decorations" moved title bars into applications and changed what a window manager appears to draw.

Check yourself

If a desktop says it supports both X11 and Wayland sessions, what has actually changed between those sessions?

Model answer: the display protocol and the process that owns presentation changed, not the applications' wish to show windows. In an X11 session a separate X server and window manager handle drawing and placement. In a Wayland session the compositor does both. The desktop shell and toolkits may stay similar, though toolkits choose different backends. Compatibility layers such as XWayland can blur the visible result.
