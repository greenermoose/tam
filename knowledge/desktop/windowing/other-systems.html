Guide / Desktop and applications / Windowing systems / Windowing on other operating systems

Other operating systems also draw windows and route input. They often bundle the jobs that Linux splits between a display protocol, a compositor and a toolkit.

What this is

Microsoft Windows, macOS, iOS and Android all show applications as rectangles or full-screen areas. Each has a part that decides what is on screen, and libraries that applications use to build buttons and menus.

Why it matters

When you move between systems, the words change but the jobs stay familiar. That makes it easier to understand a Linux desktop and to judge cross-platform applications.

How to think about it

Imagine different theatre companies. They all put actors on a stage, but one has a single stage manager, another has a committee, and another builds the set inside each actor's costume. The play still needs somewhere to appear.

New words

Win32
The long-standing Windows application interface for windows, messages and drawing.

The Windows component that composes application windows for display.
Quartz
The macOS graphics and windowing family built on Core Graphics.
SurfaceFlinger
The Android service that combines application surfaces.

If it goes wrong

You treat a toolkit as the operating system
Qt and GTK can run on several systems, so they are not the windowing system itself. Ask who owns the display and input before naming the toolkit.
Phone systems seem unrelated
They still need composition and input routing. They usually show one main surface at a time, with task switching controlled by the system.

On Tamlinux: cross-platform toolkits can make an application feel familiar across Windows, macOS and Linux, but native integration still comes from each desktop's shell, portals and settings.

Check yourself

What job does SurfaceFlinger share with a Wayland compositor?

Both combine finished surfaces from applications into what the screen shows. They differ in protocol, API and policy: Android applications use the Android view or Compose stack and Binder interfaces, while Wayland clients use protocol objects such as wl_surface.

How it works

Windows and macOS expose more of their windowing as an operating-system framework: an application links a platform library and receives messages or events from it. Linux keeps the display protocol separate from the toolkit, so GTK and Qt can talk to X11 or Wayland through backends. Android sits between the two models: it has a system compositor service and a platform UI framework supplied together.

Advanced examples

Research and older systems show other splits. Plan 9's Rio offered a minimal window system built from ordinary files; Haiku's app_server centralised drawing; the Amiga used Intuition and screens. They are useful contrasts because they ask the same questions with different boundaries.

Edge cases and failure modes

  • Modern Windows and macOS also use compositors, so "Linux invented compositing" is false; the difference is where the interface boundary sits.
  • A cross-platform toolkit may look the same while using completely different native accessibility and input paths.
  • Full-screen mobile applications still participate in a windowing system; task switching and system overlays need composition.

Check yourself

Why is comparing "GTK versus Win32" less useful than comparing "who composes and who routes input"?

Model answer: GTK is a widget toolkit and Win32 is a broad platform API; they are not the same layer. The transferable questions are: which process owns the final screen, how an application requests a window, how buffers reach the display, and how input finds the focused application. Those answers map cleanly across X11, Wayland, DWM, Quartz and SurfaceFlinger.
