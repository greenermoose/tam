Guide / Desktop and applications / Windowing systems / Check your graphical session

You can find out which display system a graphical session uses without changing settings. A few environment values and one session query usually give enough evidence.

What this is

A session is the time from login to logout. During it, the desktop, applications and display system run together. A compositor presents windows on Wayland; an X server does the older job on X11.

Why it matters

The same application can behave differently on X11 and Wayland. Knowing the session type helps you choose the right instructions when a window, screenshot or keyboard shortcut misbehaves.

How to think about it

Think of the values as labels on a door. One label says which display protocol the session uses; another says where X11 clients can connect. Both labels can be present at once.

New words

Wayland
The modern display protocol used by most Linux desktops.
X11
The older display system still used by legacy applications.
XWayland
A compatibility X server that runs on a Wayland desktop.
X client
An application that speaks the X11 protocol.

Read the labels

Goal: you will be able to distinguish a Wayland session, an X11 session and an X11 compatibility display using read-only output.

Learner path: back: How graphical toolkits build interfaces; next: From pixels to desktop applications.

Worked example

In a graphical terminal on the session used to check this page, the following command printed:

$ printf 'session=%s wayland=%s display=%s\n' "$XDG_SESSION_TYPE" "$WAYLAND_DISPLAY" "$DISPLAY"
session=wayland wayland=wayland-1 display=:0

That says the session type is Wayland and a native Wayland socket is available. The DISPLAY=:0 value tells X11 applications where to connect; it does not by itself make the session X11. Then:

$ loginctl show-session "$XDG_SESSION_ID" -p Type -p Active -p State
Type=wayland
Active=yes
State=active

The login manager agrees that the session is Wayland and active.

Try it

Run both commands in a terminal inside the graphical desktop, not in a text console or an SSH shell. Compare the result with what you expect from your desktop's compositor. If a value is blank, say so rather than guessing.

If it goes wrong

XDG_SESSION_TYPE is missing
The terminal may have been started outside the graphical login, or an older session manager may not export it. Check the login-manager query instead.
DISPLAY is set but WAYLAND_DISPLAY is blank
You are likely in an X11 session, or in a shell that only inherited X11 variables. Confirm with the login-manager query before deciding.
Both variables are set
This is common on Wayland desktops that run XWayland. Let XDG_SESSION_TYPE and the login manager identify the session.

On Tamlinux: the active desktop uses Hyprland on Wayland today, so a read-only check should show a Wayland session. X11 applications can still run through XWayland.

Check yourself

Decide your answer before you reveal it.

You see DISPLAY=:0 in a terminal. Is the desktop session X11?

Not necessarily. A Wayland desktop that runs XWayland also sets DISPLAY so X11 clients can connect. Check XDG_SESSION_TYPE, WAYLAND_DISPLAY and the login-manager query. On the checked session they identify Wayland even though DISPLAY was present.

How it works

Environment variables are inherited by child processes, so a terminal launched from the graphical session sees the values the session exported. The login manager tracks the same session through its own ID and exposes Type, Active and State as properties. These checks are read-only: they print state and change nothing.

Advanced usage examples

In a script, prefer loginctl show-session "$XDG_SESSION_ID" -p Type --value when a bare value is needed, and keep DISPLAY and WAYLAND_DISPLAY as separate facts. A Wayland-native screenshot tool uses the compositor or a portal; an X11-only tool may use DISPLAY and therefore see XWayland windows only.

Edge cases and failure modes

  • A text console, SSH shell or container may have none of these variables even though another session is graphical.
  • Nested sessions and remote desktops can expose more than one display socket; name the session you actually inspected.
  • XWayland can make an X11 client look native in a screenshot while it remains subject to X11's weaker isolation.
  • These commands identify the display path, not the desktop environment or toolkit inside the windows.

Check yourself

A script sees both WAYLAND_DISPLAY and DISPLAY. Why should it not treat the second variable as proof that the session is X11?

Model answer: because XWayland provides an X11 display inside a Wayland session for compatibility. The session type and login-manager query distinguish the real session. The script should branch on the session type and treat DISPLAY as the address of X11 clients, not as the owner of the screen.
