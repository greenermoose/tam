Guide / Desktop and applications / Windowing systems / Why Linux moved from X11 to Wayland

X11 and Wayland both put application windows on a screen. They differ in who owns the display and in how much one application can observe another.

What changed

X11 uses a separate display server, and applications send it drawing requests. Wayland makes the compositor the display server; applications hand it finished pictures.

Why it matters

The change gives applications less power over the whole screen, removes an old layer from the drawing path, and lets one process coordinate windows and input consistently.

How to think about it

Under X11, many people can give orders to the same clerk. Under Wayland, each person paints a picture and only the curator is allowed to hang pictures or read the room.

New words

X server
The older display server that received drawing requests from applications.
Compositor
The process that presents surfaces and routes input in Wayland.
XWayland
The bridge that lets old X11 applications run on a Wayland desktop.
XDG desktop portal
A deliberate way for applications to request screen capture or a file chooser.

Worked example

Consider a malicious keylogger in each model:

  1. On X11, a client with access to the display can usually request global key events, even when another window has focus.
  2. On Wayland, the compositor sends keyboard events only to the focused client. A keylogger must be given a special compositor interface or run inside the target application.
  3. Screen capture follows the same pattern: X11 offers broad access by default; Wayland uses a compositor decision or a portal, usually with a user prompt.

That is the security argument in one example: remove ambient access to other clients' input and pixels.

If it goes wrong

"Wayland is just a new window manager"
No. The compositor replaces the X server's display duties and the window manager's placement duties. A desktop shell can still sit on top.
"X11 disappeared"
No. XWayland and remote X11 forwarding keep it in use. The default session on most modern Linux desktops changed.

On Tamlinux: Wayland is the session protocol and XWayland supplies compatibility for older clients. Decisions about future compositor work are recorded in public product plans, not inferred from the presence of DISPLAY.

Why did removing global input access matter for Linux desktops?

Because any X11 client could ask to see keys meant for another window. A desktop is a shared workspace with passwords, chat and banking in separate applications. Wayland makes the compositor the single input router, so observing another client requires an explicit interface or user consent.

Why Linux moved

The old X server accumulated extensions while remaining a large, privileged component with a weak isolation boundary between clients. At the same time, compositing, GPU buffers and high-refresh displays made a single presentation manager more attractive. Wayland shrinks the protocol core, makes rendering buffer-based and gives the compositor clear ownership of input, outputs and frame timing. The result is a cleaner security boundary and a better platform for modern effects — not an automatic speed win in every workload.

Advanced usage examples

A Wayland compositor can use DMA-BUF and DRM/KMS atomic updates to present a set of surfaces without copying through a server. A remote desktop session instead goes through a portal and a stream protocol, because raw framebuffer access is not a basic client right.

Edge cases and failure modes

  • Extension differences mean a Wayland feature may exist on one compositor but not another; toolkits detect and degrade.
  • X11 still wins where simple network forwarding of a single program matters more than desktop isolation.
  • Screen-sharing, global shortcuts and input methods needed new negotiated protocols; early Wayland desktops felt incomplete until those arrived.
  • A toolkit can hide the display protocol so well that users see the same window on both systems; the underlying fault boundaries remain different.

Check yourself

An application works on X11 but cannot capture the screen on Wayland. Give a sound diagnosis without calling it a compositor bug.

Model answer: first identify how the application asks for capture. If it reads the X11 root window, that assumption does not exist for native Wayland clients; use the compositor's screenshot mechanism or an XDG desktop portal and expect a consent prompt. If it already uses a portal, check that the compositor exposes the portal and that the user approved the request. Only then suspect a compositor fault.
