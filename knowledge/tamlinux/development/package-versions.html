Understanding the whole system · How software is delivered

A Tamlinux release has its own version, and the tools that make it up have their own versions. Recording the exact choices makes it possible to identify and reproduce a release.

What does a package version name?

A version identifier pins down the exact edition of a program or workstation release. On Tamlinux, both the overall workstation cultivar and individual components carry explicit version numbers tied to recorded source revisions.

Why it matters

An operating system should be reproducible and free from silent drift. Knowing whether you are running a released version or a development build prevents troubleshooting the wrong code and ensures every fix is verified against the exact source.

How to think about it

Think of a cultivar version like the edition number on a book's cover, and component versions like the individual chapter revision numbers listed on the copyright page.

How it works

Advancing software through the Tamlinux lifecycle follows four structured phases:

  1. Component Development and Override: Work in the component checkout on the dev branch. Install a development build directly into the user prefix: Because ~/.local/bin sits first on the shell PATH, this binary immediately overrides the packaged version for interactive testing without root privileges or modifying system files.
  2. Component Verification, Version Bump, and Commit: Verify all unit, integration, and guide tests pass (make test). Bump the component version in source:
    • Binary version: src/version.h (TAM_COMMAND_VERSION).
    • Corpus version: knowledge/version, its only source. A corpus release changes no command source.
    Record AI-assisted work in work/ following AI-BLAME.md (not AI_PROVENANCE.md). Commit only your claimed paths (git commit -m '...' -- <paths>) and push to dev on GitHub. Note the resulting commit hash.
  3. Pinning and Staging a Candidate: Update the component lock to the exact pushed commit hashes, run make preflight and make from the tamlinux checkout to build the complete workstation stage in private staging, and record the resulting manifest digest and candidate version.
  4. Promotion to Test, Run, and Dev Override Cleanup:
    TestOn the developer's explicit "Test" instruction, promote the candidate commit to the test branch (fast-forward only). Install the recorded candidate stage on the target host following the approved deployment procedure.
    Clean up the dev overrideRight after the deploy that delivers the pinned version, remove the development override: Confirm type -a tam points back to /usr/bin/tam.
    RunAfter thorough daily-driver testing, on the developer's explicit "Run" instruction, promote the exact same tested commit to main and promote the identical verified stage to Run.
    ReleaseWhen all planned steps for the version are accepted, tag the release on GitHub with release notes on the developer's explicit "Release" instruction.

Why Tamlinux chose this

Separating product cultivar milestones from independent component versions enables fast, focused iteration on individual utilities without triggering massive system-wide builds. Pinning components via exact Git commit hashes and staged SHA-256 manifests eliminates runtime drift, guaranteeing that any developer or machine building a candidate produces identical software. Placing local development builds first on PATH allows safe, unprivileged testing while maintaining pristine package integrity in the rootstock.
