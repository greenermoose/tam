Keeping track of software versions

This page explains how Tamlinux identifies the software it installs and keeps track of changes.

Before this

Understanding the whole system · How software is delivered

A Tamlinux release has its own version, and the tools that make it up have their own versions. Recording the exact choices makes it possible to identify and reproduce a release.

What does a package version name?

A version identifier pins down the exact edition of a program or workstation release. On Tamlinux, both the overall workstation cultivar and individual components carry explicit version numbers tied to recorded source revisions.

Why it matters

An operating system should be reproducible and free from silent drift. Knowing whether you are running a released version or a development build prevents troubleshooting the wrong code and ensures every fix is verified against the exact source.

How to think about it

Think of a cultivar version like the edition number on a book's cover, and component versions like the individual chapter revision numbers listed on the copyright page.

New words

Package
A bundled piece of software with metadata recording its version and installed files.

Product versions versus component versions

Goal: you will be able to query installed package versions, compare product cultivars with component versions, and inspect active assembly status.

Before you start: open a terminal. Inspecting package versions and deployed assembly status uses read-only commands that require no administrative privileges. See Software packaging and delivery for package management basics.

A version number identifies an exact release of a program. On Tamlinux, cultivar names like KBN WB represent overall workstation milestones, while individual tools like tam have their own version numbers. The cultivar is the Tamlinux software release; it sits on a rootstock (today Arch Linux; Void and a smaller microkernel base are planned). Commands like tam --version query active program versions directly. See distributions and rootstocks for the longer design story.

Mental model

tamlinux source lock (pinned Git commits)
  |-- libtam:         pinned commit
  |-- tam:            pinned commit
  |-- tamlinux:       pinned commit
  +-- tamlinux-tools: pinned commit
            |
            v  (make -> staged manifest with SHA-256 digests)
  Cultivar Install (/usr/bin, /usr/lib/tamlinux/source/):
    /usr/bin/tam
    /usr/lib/tamlinux/source/...
            |
  Local Developer Override (optional, precedes /usr/bin on PATH):
    ~/.local/bin/tam  (make install PREFIX=$HOME/.local)

Tamlinux does not install floating package versions from remote repositories at deploy time. Instead, a dedicated repository named tamlinux-packages serves as the central bill of materials (BOM), locking every dependency down to the exact commit and cryptographic tree hash.

Worked example: Inspect active versions and cultivar

$ tam --version
tam command 0.48.1 (dev 4788787)
knowledge corpus 0.59.0 (dev 4788787)
libtam 0.4.0
Tamlinux cultivar KBN WB 0.6.1

Captured on a Tamlinux workstation, 2026-11-02. Your build hash may differ.

What just happened

  1. tam --version printed the four version tiers of the running environment: the C command binary (0.48.1), the offline knowledge corpus (0.59.0), the shared integration library libtam (0.4.0), and the overall workstation milestone cultivar name and release (KBN WB 0.6.1).
  2. The (dev 4788787) suffix indicates that the command and corpus are executing from a local development build installed in the user prefix (~/.local/bin) matching that Git short hash.
  3. Released cultivar builds omit the (dev ...) suffix and reflect the exact version declared in the active installed cultivar.

Try it

Check which binary your shell resolves first and compare its version:

$ type -a tam
$ tam --version

If ~/.local/bin/tam appears ahead of /usr/bin/tam, you are running a local development override rather than the installed cultivar binary.

If it goes wrong

tam prints (dev ...) suffix unexpectedly
A development build in ~/.local/bin precedes the packaged binary on PATH. Remove it with make -C ~/src/tam uninstall PREFIX=$HOME/.local and run hash -r.
command and corpus versions differ
Tamlinux command and corpus version independently. Content additions in the documentation corpus bump its version without needing a command binary recompile.
Installed binary differs from checkout
The installed tam reads its installed corpus unless TAM_KNOWLEDGE_DIR=knowledge is set explicitly when testing from a source checkout.

On Tamlinux, production software reaches the workstation exclusively through a recorded candidate delivery built from pinned Git sources (or a recorded transitional bundle), never from an unrecorded checkout or copied payload. Development overrides in ~/.local are reversible and removed once the candidate is installed. See the deployment contract.

Check yourself

Decide your answer before you reveal it.

What does (dev ...) indicate when appended to a version number in tam --version?

It indicates that the running executable was compiled and installed locally into ~/.local/bin from the indicated Git commit, overriding the installed cultivar binary in /usr/bin on PATH.

Why do tam command and knowledge corpus maintain independent version numbers?

The command utility (C binary) and documentation corpus develop on separate cadences. Authoring new guide pages or updating documentation increments the corpus version while leaving the compiled command binary untouched.

How it works

Advancing software through the Tamlinux lifecycle follows four structured phases:

  1. Component Development and Override: Work in the component checkout on the dev branch. Install a development build directly into the user prefix: 
    make -C ~/src/tam test
make -C ~/src/tam install PREFIX=$HOME/.local
    Because ~/.local/bin sits first on the shell PATH, this binary immediately overrides the packaged version for interactive testing without root privileges or modifying system files.
  2. Component Verification, Version Bump, and Commit: Verify all unit, integration, and guide tests pass (make test). Bump the component version in source:
    • Binary version: src/version.h (TAM_COMMAND_VERSION).
    • Corpus version: knowledge/version, its only source. A corpus release changes no command source.
    Record AI-assisted work in work/ following AI-BLAME.md (not AI_PROVENANCE.md). Commit only your claimed paths (git commit -m '...' -- <paths>) and push to dev on GitHub. Note the resulting commit hash.
  3. Pinning and Staging a Candidate: Update the component lock to the exact pushed commit hashes, run make preflight and make from the tamlinux checkout to build the complete workstation stage in private staging, and record the resulting manifest digest and candidate version.
  4. Promotion to Test, Run, and Dev Override Cleanup:
    TestOn the developer's explicit "Test" instruction, promote the candidate commit to the test branch (fast-forward only). Install the recorded candidate stage on the target host following the approved deployment procedure.
    Clean up the dev overrideRight after the deploy that delivers the pinned version, remove the development override: 
     make -C ~/src/tam uninstall PREFIX=$HOME/.local hash -r
    Confirm type -a tam points back to /usr/bin/tam.
    RunAfter thorough daily-driver testing, on the developer's explicit "Run" instruction, promote the exact same tested commit to main and promote the identical verified stage to Run.
    ReleaseWhen all planned steps for the version are accepted, tag the release on GitHub with release notes on the developer's explicit "Release" instruction.

Why Tamlinux chose this

Separating product cultivar milestones from independent component versions enables fast, focused iteration on individual utilities without triggering massive system-wide builds. Pinning components via exact Git commit hashes and staged SHA-256 manifests eliminates runtime drift, guaranteeing that any developer or machine building a candidate produces identical software. Placing local development builds first on PATH allows safe, unprivileged testing while maintaining pristine package integrity in the rootstock.
