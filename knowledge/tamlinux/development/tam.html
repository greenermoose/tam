Building and maintaining tam

This page explains how to build and maintain tam, the program that displays this guide. If you just want to learn how to use tam, see Using the tam command. Read on to learn about tam's implementation, build system, and development lifecycle.

Developing Tamlinux · Tools for building programs

tam is the flagship utility for Tamlinux. Fred chose to write it in the C programming language (specifically, the C11 standard) built against the libtam library so it starts quickly, uses little resident memory, and operates completely offline without background daemons. Tam should run reliably on any 64-bit hardware from 2006-era budget laptops up to the latest multi-core, multi-screen desktop workstations.

The tam command architecture

tam is Tamlinux's native, offline knowledge reader and diagnostic tool. Written in C and compiled into a small binary, it opens documentation, manuals, and glossary pages directly in your terminal without needing a web browser or network connection.

Why it matters

Because tam compiles cleanly from source and separates its binary version from its documentation corpus version, contributors can test either a code fix or a documentation edit independently in a user-local directory without touching system files.

How to think about it

Think of tam as a pocket field-guide reader made of two replaceable halves: the binding and lens (the C command) and the pages inside (the HTML knowledge corpus). Either half can be updated on its own schedule.

New words

C11 standard
The ISO/IEC 9899:2011 standard for the C programming language.
Decoupled versioning
A design where the binary executable version and documentation corpus version advance on independent schedules.
Development prefix
A user-owned directory hierarchy (such as ~/.local) used to install and test software without administrator permissions.

Inspect subcommands and compile a local build

Goal: you will be able to inspect installed tam version metadata, compile the standalone C binary from source with Make, and test the newly compiled binary safely without altering system packages.

Before you start: open a terminal inside the tam repository checkout. Compiling locally requires standard developer tools (GCC or Clang, Make, and header libraries). Inspecting versions is read-only. See Terminal and editor ergonomics and Native toolchains and multi-agent workflows for environment prerequisites.

Make is a build automation tool that reads a Makefile to compile source code into executable programs. Running make command compiles only the C executable under build/tam. In terminal sessions, $ represents your shell prompt; do not type it.

The tam repository is organized into two independent workstream lanes: the Command lane (C source code under src/) and the Corpus lane (HTML documentation under knowledge/). Two agents can work concurrently if each claims one lane. The command binary links static libtam (libtam.a) and zlib and dynamically discovers corpus metadata and <meta name="paths"> step graphs at runtime.

Captured on an Arch Linux workstation, 2026-11-02. Your build hash and compile line will differ.

What just happened

  1. ./build/tam --version printed four decoupled version identifiers: the C binary version, the active knowledge corpus version, the foundational libtam version, and the active Tamlinux cultivar (major + minor release) name and version. Tamlinux’s own software is the scion installed on a rootstock (currently Arch Linux, with plans to migrate to Void Linux and later explore a microkernel).
  2. make -C ~/Code/tamlinux/tam command invoked the C compiler (cc) with C11 flags (-std=c11 -O2 -Wall -Wextra -Wpedantic), producing the standalone executable at build/tam linked with libtam and zlib.

Try it

Execute single-lane command tests on the newly built binary to verify CLI arguments and pager navigation without touching the corpus index:

$ make test-command

You can also run the built binary directly with ./build/tam --help to inspect the full list of available subcommands.

If it goes wrong

fatal error: tam/fs.h: No such file or directory
The libtam header files are not installed under /usr/include or your configured LIBTAM_PREFIX (e.g. ~/.local/include). Pass LIBTAM_PREFIX=$HOME/.local when invoking Make.
fatal error: zlib.h: No such file or directory
The zlib compression development headers are missing. On Arch Linux, install native zlib using pacman -S zlib.
build/tam: error while loading shared libraries
Packaged and standard Make builds link static libtam.a directly into build/tam; if testing an override dynamic build, inspect LIBTAM_CFLAGS/LIBTAM_LIBS or ldd ./build/tam.

On Tamlinux, development builds and production releases adhere to strict lifecycle boundaries. Developers and AI coding agents build and test candidates locally in ~/.local/bin and ~/.local/lib, or in transactional generation directories under ~/.local/opt/tam/generations/. Every released Tamlinux version installs its binaries and libraries under /usr/bin and /usr/lib. Production software never reaches the system from ad-hoc checkouts or copied payloads; it arrives solely through recorded candidate deliveries built from pinned Git sources (or recorded transitional bundles). See the Tamlinux package deployment contract.

How it works

  1. C11 Architecture and Sub-5ms Startup: tam is written entirely in ISO C11. It avoids heavy runtimes, JIT compilation pauses, and dynamic module loading. At launch, the binary initializes terminal state via libtam, parses command-line arguments using a single-pass scanner, loads index structures via zero-copy memory mapping or sequential TSV streaming, and draws the first screenful of formatted text in under 5 milliseconds with resident memory below 4 megabytes.
  2. Decoupled Versioning and Dynamic Runtime Resolution: The binary version (src/version.h) is decoupled from the corpus version (knowledge/version). When invoked, src/tam.c discovers the corpus root by checking $TAM_KNOWLEDGE_DIR, followed by the user prefix ~/.local/share/tamlinux/knowledge, and finally the compiled datadir /usr/share/tamlinux/knowledge. It reads knowledge/version dynamically at runtime. This allows documentation fixes and new lessons to land without recompiling the C executable, and guarantees multi-agent concurrency across command and corpus lanes.
  3. Transactional Development Generations and Atomic Switching: tam switch STAGE compiles candidates into isolated, timestamped directories: 
    ~/.local/opt/tam/generations/<version>-<commit>-<hash>/
    Each successful generation writes a local receipt recording source pins, versions, checks, and previous targets. Once verified, the command switches the current symlink atomically. If a candidate fails verification, the active generation is untouched. tam switch --rollback restores the prior generation from local receipts without requiring network connectivity.
  4. The Develop -> Test -> Run -> Release Lifecycle: In Tamlinux, software moves across four disciplined stages governed by the generation and packaging model: 
    Develop (tam.git @ dev)
   │
   ▼  Fast-forward promotion
Test (tam.git @ test ──► pinned in candidate source lock)
   │
   ▼  Workstation acceptance & verification
Run (tam.git @ main ──► promoted verified stage)
   │
   ▼  Cultivar release tag & generation snapshot
Release (Tamlinux release)
    DevelopEngineers and AI coding agents work in one shared clone on dev, claiming paths with tam-work and verifying changes with make check.
    TestCandidate commits are fast-forward promoted to test, pinned in the component lock, and staged with make to produce a digest-verified source stage.
    RunAfter daily-driver acceptance, the tested commit promotes to main. Crucially, package outputs are not rebuilt: the identical byte-for-byte artifacts verified in Test are deployed to Run.
    ReleaseOn explicit developer instruction, accepted commits on main receive paired release tags (e.g. tam-0.31.0-corpus-0.32.1). If defects occur, rollback to the prior recorded source-install stage restores the earlier working state.

Why Fred chose this

A flagship system utility must remain available when the workstation is in distress. By compiling to a standalone C11 binary linked against libtam with zero background daemons, tam operates reliably in single-user recovery consoles even if Wayland compositors, graphics drivers, or package managers are broken. Decoupling command and corpus versioning allows documentation to evolve rapidly without recompilation churn, and the 4-stage lifecycle guarantees byte-for-byte reproducibility from development to release.

Edge cases and failure modes

Dirty working tree during install
make install refuses to proceed if any command or corpus path has uncommitted changes. This prevents partial, untracked development state from polluting installed prefixes.
Forward-compatible metadata parsing
The HTML tag scanner and index generators parse metadata additively. If an older command binary encounters newly added meta attributes (such as kind or skills), it ignores unrecognized fields gracefully without crashing or failing to display page content.
Dynamic library ABI shifts
Because Arch Linux is currently used as the rootstock (which is a rolling-release distribution), system libraries (such as libncursesw or libz) occasionally receive soname updates. Static linkage of libtam.a and clean Make rebuilds against the rootstock's native libraries keep tam small, fast, and aligned with the host system.

Why does the Tamlinux lifecycle mandate that package outputs are NOT rebuilt when promoting from Test to Run?

Rebuilding introduces the possibility of non-deterministic differences, compiler toolchain changes, or unintended timestamp variations. Promoting the exact byte-for-byte package output tested during the Test stage guarantees that what was verified in daily use is identical to what runs in production.

How does the transactional generation architecture in tam switch protect against broken development builds?

Each build compiles into an isolated, timestamped generation directory under ~/.local/opt/tam/generations/. The active generation link (current) is updated atomically only after the candidate passes verification tests and writes a complete receipt. If the build or tests fail, the symlink remains pointing to the previous functional generation, and tam switch --rollback can restore the earlier state without network access.
