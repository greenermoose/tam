Design goals

Tamlinux design goals describe the practical targets that guide how Tamlinux utility programs are built and kept fast, simple, and easy to understand.

What Tamlinux aims for

When you run a small Tamlinux command, it should feel immediate and leave room for the work you actually want to do. Tamlinux design goals keep core tools small, quick, and simple so they work well on old and new computers.

Why it matters

Clear goals help developers make consistent choices. If a tool starts slowly, uses too much memory, or depends on many extra pieces, it becomes harder to trust, harder to fix, and harder to run on modest hardware.

How to think about it

Think of a good hand tool in a workshop: it should be light, ready the moment you pick it up, and simple enough that you can understand how it works. Tamlinux wants its own utility programs to feel that way.

Worked example

Tamlinux gives its tam-* utility programs a clear performance target called the Tamlinux Five: start and exit in 5 milliseconds and use under 5 megabytes of memory. This is a design goal to measure against, not a claim that every command on every system will always hit the same number under every condition.

Why C11 and minimal dependencies help machine intelligence

Machine intelligence works best when the code it reads has clear boundaries. A C11 program that depends only on libc has a small language surface, explicit memory and control flow, and a limited set of external interfaces. There is no large runtime, garbage collector, framework magic, or hidden dependency tree to infer. That makes it easier for an AI agent, static analyzer, or human reviewer to trace what a program does, reproduce its behavior, and verify a fix.

Try it

Pick a small Tamlinux utility and ask three questions: How quickly does it start? How much memory does it use? What does it depend on besides libc? Use those questions as a practical check against the design goals.

If it goes wrong

A command feels slow or heavy
Measure it before drawing conclusions. Startup time and memory use depend on the command, workload, and system. Compare the result to the Tamlinux Five goal and look for unnecessary work or dependencies.
A feature seems to need a large dependency
Check whether the feature belongs in a core tam-* utility or in a different layer. The minimal-dependency goal is strongest for Tamlinux's own utility programs.

How it works

These goals reinforce each other. C11 compiles to native code with predictable runtime behavior. A libc-only dependency set keeps the ABI and runtime surface small. Small, fast programs reduce startup overhead in shells, scripts, keybindings, and agent workflows. The same properties also reduce the amount of implicit context that machine intelligence needs: source files, headers, build flags, and libc behavior are usually enough to understand the program.

The C11 and low-dependency goals do not mean Tamlinux avoids all other languages or libraries everywhere. Desktop components, rootstock packages, and third-party applications may use different toolchains. The design goal applies most strongly to Tamlinux's own utility programs, where startup cost, memory use, auditability, and portability matter most.

Advanced usage

When evaluating a proposed change to a tam-* utility, treat the goals as review questions:

$ time ./build/tam --version
$ /usr/bin/time -v ./build/tam --version
$ ldd ./build/tam

Illustrative checks: measure startup, inspect memory use, and confirm the runtime dependency footprint. Use the measurements appropriate to the program and system under test.

Edge cases

  • Measurement noise: A 5 millisecond target can be affected by cold caches, scheduler noise, or slow storage. Measure repeatedly and report conditions.
  • Necessary exceptions: Some programs may need a carefully chosen library for compression, cryptography, or platform integration. Treat exceptions as explicit design decisions, not defaults.
  • AI assistance is not proof: Machine intelligence can help read and modify simple code, but tests, review, and measured behavior still determine correctness.

Check yourself

Why is "no dependencies other than libc" a design goal rather than a blanket rule for every Tamlinux component?

It gives Tamlinux utility programs a strong default: small, portable, auditable binaries with little runtime overhead. Some components may still need specialized libraries, but those dependencies should be deliberate exceptions because they increase build, runtime, and audit complexity.
