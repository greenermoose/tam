Choosing the Rootstock

This page compares different versions of Linux and explains which ones Tamlinux uses or is considering as its rootstock.

What is a rootstock?

A Linux distribution provides the kernel, system libraries, and core package manager that make a computer boot and run. Tamlinux builds its own desktop and tools on top of an underlying base distribution, which Tamlinux calls the rootstock.

Why it matters

Knowing which rootstock is current, planned, or kept as a fallback ensures that package, update, and recovery instructions always aim at the right underlying system.

How to think about it

Think of the rootstock as the roots and trunk of a fruit tree, and the Tamlinux cultivar as the grafted branches on top. Keeping the two layers distinct makes it possible to change the base deliberately without redesigning the entire workstation.

New words

Rootstock
The underlying base operating system that Tamlinux builds upon (currently Arch Linux).
Cultivar
A named Tamlinux workstation release built on top of a rootstock.

Mental model

A rootstock provides the base operating system on which the Tamlinux scion is installed.

Worked example

The discussion below identifies Arch as the working rootstock, Void as a planned pilot and antiX Core as a fallback.

Every Linux distribution makes its own trade-offs in packaging, init system, release cadence, and architecture. Tamlinux is a workstation environment rather than a new distribution: it is installed onto a rootstock (a base operating system such as Arch Linux, Void Linux, Windows, or macOS) that is installed on a host. Rootstock is a gardening term that Fred uses to explain how Tamlinux works: it is the base operating system on which the Tamlinux scion is grafted so that Tamlinux's software can run properly and bear fruit in the form of applications.

Our goal is to minimize the size of the rootstock and maximize its speed and efficiency. Currently we are using Arch Linux as our rootstock, with plans to migrate to Void Linux in future versions of Tamlinux, and to explore a microkernel beyond that to further reduce the code size of the rootstock and improve its performance per watt.

The current rootstock: Arch Linux

Why Arch todayrolling releases bring current kernels, Mesa, Qt 6, and Wayland protocols, and keep the system maintained without whole-OS reinstalls.
Packagingpacman with simple PKGBUILD recipes. Locally patched packages are served from a dedicated repository listed first in /etc/pacman.conf; see Carried patches.
Why move onArch is built around systemd, while the long-term target is a minimal rootstock without it.

The target: Void Linux

Tamlinux plans to try Void Linux as its minimal rootstock, from step 1.2 of the roadmap:

IndependentVoid is built from scratch, not derived from Debian or Red Hat.
runitVoid uses runit for init and service supervision instead of systemd; see Init and service supervision.
XBPSa package manager written in C, with source packages built cleanly by xbps-src. Tamlinux plans to deliver native xbps-src packages built from the same sources as its Nix package.
glibc and muslVoid offers both C libraries, which allows a measured comparison; see C standard libraries.

The fallback: antiX Core

If Void has a showstopper, Tamlinux will try antiX Linux Core with runit: a systemd-free Debian-based distribution with a long record of running well on older, low-resource hardware.

Other distributions considered

Debianthe upstream of many distributions and a benchmark for packaging standards, but its stable releases move slowly for desktop development.
Alpine Linuxvery small, built on musl and BusyBox; shows how small a rootstock can be, but less suited to a daily graphical workstation.
Puppy Linux and Tiny Coredemonstrations of running entirely from RAM, relevant to hardware longevity.
Gentoosource-based and highly tunable, but full source builds are impractical on older hardware.

For a description of each of these systems and many more, and for the microkernel research planned for Tam 2.0, see the Operating systems reference.

Check yourself

Does selecting Void as a pilot prove it is running on this host?

No. Inspect the host and selected installation rather than inferring it from the plan.

What evidence separates a proposed change from a delivered one?

Inspect the relevant plan, selected package and acceptance evidence; a proposal alone establishes none of those.
