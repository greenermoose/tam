Who can use a file

This page explains how to control who can read, modify, or run files stored on your system.

Understanding file permissions

On a Linux computer, every file and folder has security rules attached to it. These rules are called permissions. Permissions decide who is allowed to open a document, who is allowed to change or delete it, and who is allowed to run a program or script.

Why it matters

Permissions protect your files from accidental damage and prevent unauthorized users or background programs from reading private data. By setting appropriate permissions, you can share a file with collaborators while keeping your personal documents private.

How to think about it

Think of file permissions like keys to rooms in an office building. The person who created the file is the owner (holding the office key). A designated team belongs to the group (holding a shared meeting room key). Everyone else is in the "other" category (allowed in the public lobby, but locked out of private offices).

There are three kinds of actions you can permit or deny:

  • Read (r): viewing or copying the contents of a file.
  • Write (w): modifying the contents, renaming, or deleting the file.
  • Execute (x): running the file as a program or script.

New words

Mode
The combination of read, write, and execute permissions attached to a file.
Owner
The user account that owns a file and controls who may access it.

Worked example

Make a new temporary directory and enter it:

work=$(mktemp -d)
cd "$work"

Now write a two-line test script and check its permissions:

$ printf '%s\n' '#!/bin/sh' 'printf "hello\n"' > hello.sh
$ chmod 600 hello.sh
$ stat -c '%A %a %n' hello.sh
-rw------- 600 hello.sh
$ chmod u+x hello.sh
$ stat -c '%A %a %n' hello.sh
-rwx------ 700 hello.sh
$ ./hello.sh
hello

Captured on Arch Linux, 2026-10-21. GNU stat omits user names, sizes, and timestamps from this format.

What just happened

  1. printf writes a two-line shell script into hello.sh.
  2. chmod 600 sets a private mode: only the owner can read and write.
  3. chmod u+x adds execute permission for the user (owner) without changing group or other access.
  4. stat verifies that mode 600 became 700 (-rwx------).
  5. Running ./hello.sh executes the script and prints hello.

Try it

In your temporary directory, remove execute permission using chmod u-x hello.sh. Inspect the mode with stat -c '%A %a %n' hello.sh, try running ./hello.sh, and notice the error. Then add execute permission back with chmod u+x hello.sh.

If it goes wrong

Permission denied when executing
Check that the file has owner execute permission (-rwx------ or mode 700). Also verify that you typed ./hello.sh to indicate the current directory.
No such file or directory
Check your spelling and use pwd and ls to verify you are still inside the temporary directory.

On Tamlinux, permissions follow standard Linux POSIX rules. The Guide lens filters which explanations and exercises are displayed; it does not change permissions on disk.

Clean up

rm -- hello.sh
cd /tmp
rmdir -- "$work"

Check yourself

Answer before revealing the explanation.

Which command adds execute only for the owner: chmod u+x or chmod a+x?

chmod u+x. The a form changes owner, group, and others; u changes only the owner class.

Does chmod printing no output mean that it failed?

No. A successful chmod command is normally silent. Inspect the mode with stat; an error message or nonzero exit status indicates failure.

Numeric modes, bitmasks, and directory access

Reference: each permission set has three bits: read (4), write (2), execute (1). Modes are three or four octal digits: special bits (setuid 4000, setgid 2000, sticky 1000), user, group, other.

ModeSymbolicMeaning
644rw-r--r--Owner read/write; group and others read-only
755rwxr-xr-xOwner read/write/execute; others read/execute
700rwx------Owner only; private directory or script
1777rwxrwxrwtSticky directory (e.g. /tmp): users delete only their own files

Directory permissions vs file permissions

On directories, the execute bit (x) means search/traversal: the right to enter the directory and access files inside. The read bit (r) allows listing directory entries. Without x, a user cannot access inodes inside even if they know file names.

Illustrative reference

work=$(mktemp -d)
cd "$work"
mkdir -m 700 private
touch private/secret.txt
chmod 600 private/secret.txt
stat -c '%A %a %n' private private/secret.txt

Clean up

rm -- private/secret.txt
rmdir -- private
cd /tmp
rmdir -- "$work"

Check yourself

Answer before revealing the explanation.

Can a user read a file in a directory if they have read permission on the file but no execute (x) on the directory?

No. Directory execute permission is required to traverse into the directory to reach the file's inode.
