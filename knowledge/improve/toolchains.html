Tools for building programs

This page introduces the tools used to build and check computer programs.

Developers use a collection of tools to turn source code, the written instructions for a program, into software they can run and test. This page introduces those tools and how contributors share their work.

Building native C projects with Make

Goal: you will be able to consult project documentation, build native C tools using Make, execute command test suites to reproduce symptoms, and inspect standalone binary versions without root permissions.

Why it matters: Contributing to workstation software or verifying a bug report starts with building and testing code cleanly from source. Tamlinux writes core tools in native C11 against libtam, achieving instantaneous startup times and minimal memory consumption. Knowing how to run Make builds, execute verification suites, and inspect compiled binaries gives you the foundation to reproduce reported issues and verify fixes safely without endangering packaged system files.

Before you start: open a terminal (The Shell and Streams). Review terminal editing (Terminal and Editor Ergonomics). Native compilation requires standard build tools (gcc or clang, make) provided by base packages. All compilation steps run in a local project checkout without requiring administrative privileges.

When compiling software with Make, you do not invoke the compiler directly for every file. Instead, the project's Makefile defines recipes and targets. Typing make test-command builds the binary and runs the automated test suite, printing ok for each verified test assertion.

Worked example: Build native C tools and inspect version output

$ cd ~/src/tam
$ make test-command
tests/run.sh /home/user/src/tam/build/tam
ok - bare invocation prints an introduction and writes no state
ok - additive and legacy index columns preserve existing page metadata
...
All tam command tests passed.
$ build/tam --version
tam command 0.43.2 (dev 7af709d)
knowledge corpus 0.43.0
libtam 0.4.0
Tamlinux cultivar Blue Sparkler 0.5.4

Captured on an Arch Linux workstation, 2026-10-25.

What just happened

  1. make test-command reads the Makefile, invokes the C compiler (gcc or clang) if any source file changed, links against libtam, and runs tests/run.sh.
  2. The binary is compiled with -O2 optimizations and linked against libtam, producing a self-contained executable that starts in milliseconds without an external script runtime.
  3. The command tests run in a test harness verifying argument handling, link navigation, and state isolation without altering the host environment.
  4. build/tam --version confirms the standalone binary executes cleanly, reporting its command version, git commit hash, and component libraries.

Try it

Inspect project documentation and build options in a scratch directory by running make -n command. The -n (dry-run) flag prints every compiler invocation and link command that Make would execute, showing exact flags (-O2, -Wall, -std=c11) without running the build or modifying any files.

If it goes wrong

make: cc: No such file or directory
The native C compiler is not installed. Native toolchains require gcc or clang from the base development package group.
cannot open shared object file: libtam.so
The dynamic linker cannot locate libtam.so at runtime. Verify that the library was built under ~/.local/dev/lib or compiled with -Wl,-rpath pointing to the local library directory.
A test assertion fails with not ok
Record the exact test line and failure message in your issue report. Do not modify system packages to force a test to pass; test failures indicate a code regression or missing local dependency.

Concurrent work in one shared clone

Goal: you will be able to coordinate concurrent development in a single shared Git clone using tam-work path claims, enforce strict commit scoping, and prepare focused changes with verification evidence.

Mental model

One Shared Git Clone (e.g. ~/src/tam)
+-------------------------------------------------------------+
| Agent A (alex): holds claim for scope: knowledge/shell/     |
|   -> edits only files under knowledge/shell/                |
|   -> commits strictly: git commit -m '...' -- knowledge/    |
+-------------------------------------------------------------+
| Agent B (dev): holds claim for scope: src/                  |
|   -> edits only files under src/                            |
|   -> commits strictly: git commit -m '...' -- src/          |
+-------------------------------------------------------------+
| Shared files (ROADMAP.md, Makefile, indexes):               |
|   -> Handed off sequentially; never edited concurrently     |
+-------------------------------------------------------------+

Instead of creating duplicate worktrees or branches for every task, contributors share a single clone. Before editing, each contributor or agent uses tam-work to reserve the specific paths they will change. Multiple sessions can work concurrently in the same repository as long as their claimed scopes do not overlap.

Worked example: Claim paths, make a focused edit, and commit

$ export TAM_WORK_OWNER=alex TAM_WORK_SESSION=fix-docs-1
$ tam-work begin --scope knowledge/shell/jobs.html --note 'Improve job examples'
Claimed alex-1a2b3c4d [active, shared] alex scope=knowledge/shell/jobs.html
$ tam-work status
alex-1a2b3c4d [active, shared] alex scope=knowledge/shell/jobs.html
$ git commit -m 'Improve job examples' -- knowledge/shell/jobs.html
$ tam-work finish --note 'Committed job example update'
Finished alex-1a2b3c4d

Captured on an Arch Linux workstation, 2026-10-25.

  1. export TAM_WORK_OWNER=alex TAM_WORK_SESSION=fix-docs-1 sets session identity so tam-work tracks who owns which paths.
  2. tam-work begin --scope <path> reserves the specified repository-relative paths. If another session holds overlapping paths, the claim is refused.
  3. tam-work status lists all active claims across the clone, allowing contributors to verify that paths are free before editing.
  4. git commit -m '...' -- <path> commits strictly the claimed files. Never run git add ., git add -A, or git commit -a, as they sweep up uncommitted edits from neighbouring sessions.
  5. tam-work finish releases the reservation once changes are committed or abandoned.

Completion task

Claim two distinct files in a shared repository for a bug fix. Fill in the missing option (marked with ___):

tam-work begin ___ src/pager.c ___ tests/run.sh --note 'Fix pager scrolling'

Fill in --scope. Running tam-work begin --scope src/pager.c --scope tests/run.sh --note '...' reserves both paths simultaneously in a single claim transaction.

Independent task

Inspect all active claims across the workstation checkout using tam-work status. If no claims are currently active, verify the command exits cleanly with an empty or clear status report.

Run tam-work status. It lists every active claim, its owner, session ID, and reserved paths. If all work has been finished or released, the output reports no active claims.

On Tamlinux, all development across core repositories (including tam, libtam, and tamlinux) follows the shared clone concurrency model. Git worktrees are explicitly avoided because their setup and merge overhead exceeds small changes, and relative directory paths break when nested in worktrees. Instead, contributors and AI coding agents reserve paths with tam-work, push exclusively to develop, and record all verification evidence with AI provenance.

Why is running git add . or git commit -a strictly forbidden in a shared clone?

In a shared clone, multiple contributors or agents work on different files simultaneously. Indiscriminate commands like git add . stage and commit unfinished files belonging to other sessions. You must always commit strictly your own paths using git commit -m '...' -- <your-paths>.

What should you do if Git reports that .git/index.lock exists?

Wait a moment and retry. Another session is executing a brief Git transaction. Never delete index.lock manually, as doing so can corrupt repository index state.

How it works: Concurrency coordination and independent lanes

When multiple autonomous agents (e.g. Claude Code, Codex, Antigravity, OpenCode) collaborate in a single shared repository checkout, file conflicts and build collisions are avoided through the lane and claim contract:

  1. Lanes: Repositories divide into independent lanes. In tam, the command lane encompasses src/, bin/, completions/, and man/ (built with make command and tested with make test-command). The corpus lane encompasses knowledge/, tools/, and corpus lint tests (built with make corpus and tested with make corpus-and-test).
  2. Disjoint execution: Two agents can develop simultaneously if each claims paths in a separate lane. A command-lane agent editing src/pager.c never conflicts with a corpus-lane agent editing knowledge/improve/zram.html.
  3. Atomic claims: tam-work begin inspects active claims recorded under the workspace lock directory. If any requested path overlaps with an active claim, the command refuses to grant the reservation, preventing concurrent edits.
  4. Git discipline: Every change is committed strictly against claimed paths. Contributors never rebase, reset, stash, switch branches, or amend in the shared clone.
  5. Release and handoff: Once changes are verified with tests and committed, the reservation is released with tam-work finish. Shared files (like ROADMAP.md, Makefile, and docs/plans/) are claimed briefly and handed off sequentially.

Why Tamlinux chose this

Traditional Git branching workflows often isolate developers in long-lived feature branches or heavy Git worktrees. In multi-agent autonomous engineering, creating and synchronizing dozens of separate clones or worktrees creates massive disk bloat, breaks relative cross-repo path assumptions in test harnesses, and delays integration until messy merge conflicts arise. Operating in one shared clone with atomic tam-work path claims allows several AI agents and human contributors to integrate changes continuously on develop with zero disk duplication and zero branch switching friction.

Edge cases and failure modes

  • Lane coupling: When a new feature spans both lanes (such as a new pager rendering tag in src/render.c and the corpus pages that use it in knowledge/), the developer or agent must claim paths in both lanes, keeping version numbers independent.
  • Stale claims after crashes: If an agent or session crashes before calling tam-work finish, its claim reservation remains recorded. A new session must never adopt another agent's claim merely because the tool name matches; claims are released explicitly or cleared after verifying session termination.
  • Compiler architecture portability: Binaries compiled with -march=native contain instructions tailored strictly to the host CPU. If distributed to older processors lacking AVX2, the binary terminates with SIGILL (Illegal Instruction). Distribution packages must target generic x86-64 baselines rather than host-native extensions.
