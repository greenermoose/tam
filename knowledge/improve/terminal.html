Terminal and Editor Ergonomics

Your terminal is the central workbench of a Tamlinux system. Tamlinux pairs an ultra-low-latency Wayland terminal with the micro text editor, delivering intuitive editing, rich Markdown highlighting, and automatic live disk reloading when files are edited by background AI agents.

Intuitive terminal editing with Micro

Goal: you will be able to edit text files and configuration documents in the terminal using standard, universal keyboard shortcuts with the Micro editor.

Why it matters: Many traditional terminal editors require memorizing modal keybindings before you can edit a single line. Micro uses universal keyboard shortcuts like Ctrl+S to save and Ctrl+Q to quit, making terminal document and configuration editing intuitive from your first session.

Before you start: open a terminal (The Shell and Streams). We will edit files in an isolated scratch directory without altering any personal configuration.

When you launch micro filename, the editor takes over your terminal window. The status line at the bottom shows the file name and cursor position. You can click with the mouse to move the cursor or select text. To quit at any time, press Ctrl+Q. If you have unsaved changes, Micro prompts Save changes to filename? (y, n, esc).

Worked example: Create and edit a scratch note

$ scratch=$(mktemp -d)
$ echo "Initial note content" > "$scratch/note.md"
$ micro "$scratch/note.md"
$ cat "$scratch/note.md"
Initial note content
Appended line saved with Ctrl+S.
$ rm -rf "$scratch"

Captured on an Arch Linux workstation, 2026-10-25.

  1. scratch=$(mktemp -d) creates a private temporary directory in /tmp so your work stays contained.
  2. echo "Initial note content" > "$scratch/note.md" writes initial text into a Markdown file.
  3. micro "$scratch/note.md" opens the file in Micro's full-screen terminal interface.
  4. Typing a new line and pressing Ctrl+S writes the updated buffer to disk immediately.
  5. Pressing Ctrl+Q exits the editor cleanly and returns control to your shell prompt.

Try it

Create a temporary file in a scratch directory, open it with micro, press Ctrl+E to open the editor command prompt, type help defaultkeys, and press Enter to browse all standard keyboard shortcuts. Press Ctrl+Q to dismiss the help view.

If it goes wrong

Pressing Ctrl+C does not exit the editor
In Micro, Ctrl+C is the standard shortcut to copy selected text to the clipboard. Press Ctrl+Q to quit.
Micro asks "Save changes to ...? (y, n, esc)" on exit
The buffer has modifications that have not been written to disk. Press y to save, n to discard changes, or Esc to continue editing.
Terminal mouse clicks do not position the cursor
Verify that your terminal emulator supports mouse tracking. Standard foot on Tamlinux supports mouse selection, dragging, and wheel scrolling out of the box.

Multi-agent pair programming and live disk reload

Goal: you will be able to configure Micro's reload setting and coordinate editing between interactive sessions and background scripts or AI agents without edit collisions.

Mental model

Interactive editor (Micro)              Background agent or Git
        |                                          |
        | [holds open buffer]                      | [edits file on disk]
        |                                          v
        | <---- focus returned / stat(2) ------- file updated on disk
        |
        +--> reload "prompt" (default): prompts user to reload or keep
        +--> reload "auto": reloads updated file content immediately

When an autonomous AI agent or background script updates a file that you currently have open in Micro, the on-disk file changes underneath the running editor. When focus returns to Micro or a buffer event occurs, Micro compares the file's modification timestamp and size using stat(2). Under the default prompt setting, Micro displays a warning asking whether to reload. Under auto, Micro immediately reloads the file without interrupting your workflow, preserving your undo history.

Worked example: Configure live reload and observe synchronization

$ scratch=$(mktemp -d)
$ mkdir -p "$scratch/.config/micro"
$ echo '{"reload": "auto"}' > "$scratch/.config/micro/settings.json"
$ echo "Original text" > "$scratch/shared.txt"
$ echo "Appended by agent" >> "$scratch/shared.txt"
$ cat "$scratch/shared.txt"
Original text
Appended by agent
$ rm -rf "$scratch"

Captured on an Arch Linux workstation, 2026-10-25.

  1. mkdir -p "$scratch/.config/micro" creates a local configuration folder for testing.
  2. echo '{"reload": "auto"}' > .../settings.json writes the setting that instructs Micro to reload modified files without prompting.
  3. When an external command or agent appends content to shared.txt, Micro detects the updated timestamp via stat(2) and refreshes the buffer automatically upon regaining focus.
  4. Your cursor position and multi-level undo tree remain intact.

Completion task

Configure Micro to reload externally modified files automatically without asking for confirmation. Complete the configuration command by filling in the missing value (marked with ___):

set reload ___

Fill in auto. Inside Micro, pressing Ctrl+E and executing set reload auto updates ~/.config/micro/settings.json so that buffers reload external modifications immediately without prompting.

Independent task

In a scratch directory, write a minimal Micro settings.json file that sets reload to auto and wordwrap to true, then verify that the JSON syntax is valid using Python's json.tool.

Run scratch=$(mktemp -d) && echo '{"reload": "auto", "wordwrap": true}' > "$scratch/settings.json" && python3 -m json.tool "$scratch/settings.json" && rm -rf "$scratch". It parses and formats the JSON keys cleanly, confirming valid syntax.

How it works: Wayland client/compositor boundaries

Tamlinux standardizes on foot as its primary Wayland terminal emulator. Unlike bloated Electron or heavy VTE/GTK-based terminals that consume over 100MB of memory and take 200ms+ to initialize, foot communicates directly with the Wayland compositor over a UNIX domain stream socket located at $XDG_RUNTIME_DIR/wayland-0 (or wayland-1).

When terminal output arrives from a running command, foot processes the VT escape sequences in an internal grid buffer. It computes the exact bounding rectangle of modified character cells and transmits a wl_surface.damage_buffer request followed by wl_surface.commit. When no output is being generated, the terminal client sends zero Wayland protocol messages and the compositor performs zero redraws, consuming zero GPU cycles.

To verify the compositor/client protocol exchanges directly, you can launch a client with WAYLAND_DEBUG=1, which prints every wire protocol request and event passing between the terminal client and the compositor.

Why Tamlinux chose this

A responsive developer workstation demands that new terminal windows appear instantaneously. Tamlinux enforces a strict sub-10ms startup budget for interactive shells. By keeping ~/.bashrc free of dynamic subshells (such as $(git branch) or slow version-manager hooks on every prompt) and pairing it with foot, terminal windows spawn in approximately 15ms with less than 20MB of resident memory.

Edge cases and failure modes

  • Dynamic prompt overhead: Placing command substitutions like $(git status) inside PS1 in ~/.bashrc spawns child processes on every prompt, inflating startup latency from 6ms to over 80ms. Always compute prompt state asynchronously or use static prompt indicators.
  • Remote terminal definitions: foot sets TERM=foot. When connecting to remote servers that lack the foot-terminfo package, key sequences or backspace may misbehave. Install foot-terminfo on the remote machine or use TERM=xterm-256color as a temporary fallback.
  • Login vs subshell configuration: Place environment variables in ~/.bash_profile or ~/.config/bash/tamlinux/env so they are evaluated once at login rather than re-parsed on every interactive subshell.

Why does placing $(git branch 2>/dev/null) inside ~/.bashrc violate the Tamlinux shell latency budget?

Every time an interactive shell launches or a prompt renders, Bash must fork a child process, execute git, query the filesystem, and capture stdout through an internal pipe. This fork/exec sequence adds 20 to 60 milliseconds of latency, violating the sub-10ms shell startup budget.
