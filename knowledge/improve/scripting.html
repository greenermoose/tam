Writing instructions your computer can repeat

This page explains how to write reusable instructions for your computer.

A script is a set of written instructions that a computer can follow. This page introduces practices that help those instructions work reliably.

The defensive Bash script template

Goal: you will be able to write a defensive Bash script with strict execution flags that catches silent errors, uninitialized variables, and pipeline failures.

Why it matters: Shell scripts can continue after failures and a mistyped or empty path can target an unintended location. Defensive options help detect some errors but have exceptions; validate paths and test failure cases as well.

Before you start: open a terminal. Scripting requires basic familiarity with pipelines (Shell Pipelines) and execution permissions (File Permissions and Ownership). We will test scripts in disposable scratch directories.

A shell script is a plain text file containing terminal commands. The top line (called the shebang, like #!/usr/bin/env bash) tells the operating system which program executes the file. Before you can run a script directly with ./myscript.sh, you must give it execution permissions using chmod +x myscript.sh.

Worked example: Write and run a safe script

Run the entire block in a terminal. It creates one script in a fresh temporary directory and removes that known file and the empty directory afterward.

if scratch=$(mktemp -d); then
    cat > "$scratch/safe-greet.sh" << 'SCRIPT'
#!/usr/bin/env bash
set -euo pipefail
target="${1:-world}"
printf 'Hello, %s!\n' "$target"
SCRIPT
    chmod u+x "$scratch/safe-greet.sh"
    "$scratch/safe-greet.sh" Tamlinux
    rm -- "$scratch/safe-greet.sh"
    rmdir -- "$scratch"
else
    printf '%s\n' 'Could not create a temporary directory.'
fi

On success it prints Hello, Tamlinux!. If cleanup fails, inspect the reported directory; do not remove unexpected contents recursively.

  1. #!/usr/bin/env bash locates the bash executable portably across Nix, Arch, and standard Linux distributions.
  2. set -e (errexit) can exit on a failing command, but has exceptions in conditionals, pipelines and other contexts; consult Bash documentation and test the actual control flow.
  3. set -u (nounset) treats references to unset variables as fatal errors, preventing accidental operations on empty or mistyped paths.
  4. set -o pipefail prevents pipeline masking: the return value of a pipeline is the status of the last command to fail, not the last command executed.
  5. ${1:-world} uses parameter expansion to supply a safe default value if the first argument was omitted.

Try it

Verify that set -u catches uninitialized variables in a temporary scratch directory:

$ scratch=$(mktemp -d)
$ cat << 'EOF' > "$scratch/test-unbound.sh"
#!/usr/bin/env bash
set -euo pipefail
echo "Result: $UNSET_VARIABLE"
EOF
$ chmod +x "$scratch/test-unbound.sh"
$ "$scratch/test-unbound.sh" || true
/tmp/tmp.XUNFNpUmdw/test-unbound.sh: line 3: UNSET_VARIABLE: unbound variable
$ rm -- "$scratch/test-unbound.sh"
$ rmdir -- "$scratch"

Captured on Arch Linux, 2026-10-27. Your temporary path differs. This script stops at the unset variable; read the message and check the name. If creating the temporary directory fails, stop before continuing.

If it goes wrong

unbound variable error
A variable was referenced before being assigned. Check spelling, or provide a default fallback such as ${var:-default}.
Permission denied when running ./script.sh
The script lacks executable permissions. Run chmod +x script.sh.
Script exits immediately on a non-critical command
With set -e, a nonzero status may abort execution depending on context. If a command is expected to return 1 (such as grep without matches), append || true or test it in an if conditional.

Why is set -o pipefail critical when chaining commands like curl -s ... | grep pattern?

Without pipefail, Bash only reports the exit status of the final command in the pipeline (grep). If curl fails due to network disconnection or a 404 error, the pipeline could still return 0 if grep matches an empty string or error message, masking the network failure.

What can set -u detect if a script reads a variable that was never set?

It reports an unbound variable in ordinary expansions. It does not validate an empty but set variable or make destructive operations safe.

Safe argument handling, cleanup traps, and defensive patterns

Goal: you will be able to forward arbitrary argument arrays without word-splitting bugs and use trap handlers while recognizing cleanup failure and termination limits.

Mental model

$*       --> "arg1 arg2 arg3"               (concatenates into single string)
$@       --> arg1 arg2 arg3                 (unquoted: splits on internal whitespace)
"$@"     --> "arg1" "arg with space" "arg3" (preserves exact argument boundaries)
trap ... EXIT --> attempt cleanup when the shell can execute the handler

When handling filenames passed by users, never expand bare $* or unquoted $@. Unquoted expansions split filenames containing spaces (such as "Quarterly Report.pdf") into multiple separate words. Always use double-quoted "$@".

Worked example: Safe argument processing with an exit trap

This example creates a script in one temporary directory. The script creates its own empty temporary directory and attempts to remove it on ordinary shell exit.

if work=$(mktemp -d); then
    cat > "$work/process-files.sh" << 'SCRIPT'
#!/usr/bin/env bash
set -euo pipefail
scratch=$(mktemp -d)
trap 'rmdir -- "$scratch"' EXIT
for file in "$@"; do
    printf 'Processing: %s\n' "$file"
done
SCRIPT
    chmod u+x "$work/process-files.sh"
    "$work/process-files.sh" 'report 2026.txt' 'notes final.md'
    rm -- "$work/process-files.sh"
    rmdir -- "$work"
else
    printf '%s\n' 'Could not create a temporary directory.'
fi

On success it prints the two arguments on separate lines, preserving each space. If cleanup reports an error, inspect the directory before taking further action.

  1. mktemp -d creates a private temporary directory; its location can depend on TMPDIR.
  2. trap 'rmdir -- "$scratch"' EXIT registers a cleanup handler for an empty directory. The handler cannot run after every termination and rmdir refuses a nonempty directory; inspect errors and unexpected contents.
  3. for file in "$@"; do loops over each argument while preserving embedded whitespace.

Does trap ... EXIT execute if the script is abruptly killed with kill -9 <PID>?

No. SIGKILL (signal 9) is handled directly by the kernel and terminates the process immediately without running user-space handlers. An EXIT trap handles ordinary shell exit; signal handling depends on the traps and execution context.

What is the difference between for f in "$@" and for f in $*?

"$@" preserves individual arguments exactly as passed, including spaces. $* without quotes concatenates all arguments and re-splits them across all whitespace, mangling filenames that contain spaces.

How it works: execution environments and descriptors

When Bash runs an external command, it invokes fork() and execve(). File descriptors 0 (stdin), 1 (stdout), and 2 (stderr) are inherited by the child process unless redirected. In subshells (commands enclosed in parentheses ( ... )), the shell forks a child Bash process that inherits environment variables, shell options, and open descriptors, but modifications to variables or traps inside the subshell do not propagate back to the parent.

Under set -e, subshell behavior has subtle rules defined by POSIX: if a command fails inside a subshell that is part of an if, while, or until test, errexit is temporarily disabled for that command list. Tamlinux scripts make conditional checks explicit using if command; then ...; fi rather than relying on uninspected subshell side-effects.

Why Tamlinux chose this

Defensive Bash options and documented exit codes help callers detect failures, but option behavior depends on context. Test failure paths and report errors explicitly.

Edge cases and failure modes

  • Traps inside functions: A trap set inside a function has global shell scope unless set -o functrace and local traps are explicitly enabled. Always declare script-level traps at the top-level script scope.
  • Variable localization: Always declare internal helper variables inside functions using local var="..." to avoid polluting the global execution namespace.
  • Subshell exit codes: Pipelines run in separate subshells in standard Bash. Assignments made inside a cat file | while read -r line; do ...; done loop are lost when the subshell terminates; use process substitution while read -r line; do ...; done < <(cat file) instead.

Explore: Trace execution with bash -x and strace

Trace variable expansions and execution branches of any script using bash -x:

Why will count=0; cat file | while read l; do ((count++)); done; echo $count print 0 even if the file had 10 lines?

In standard Bash, each element of a pipeline runs in a separate child subshell. The while loop incremented count inside a child process whose memory was discarded upon loop completion. The parent shell's count remained 0.
