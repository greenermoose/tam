Physics of Local AI Generation

Running large language models locally provides complete privacy, zero telemetry, and offline availability. However, unlike graphics rendering or video encoding, local autoregressive text generation is fundamentally governed by the physical memory bandwidth of your workstation's RAM subsystem, rather than raw compute TFLOPS.

Beginner: Running local inference with Ollama and tam ask

Summary: Run private, local AI models on your workstation with zero network transmission or API token costs.

Prerequisites: System resources and performance (Resources and Performance).

Command sequence

ollama run qwen2.5:3b "Summarize the Unix philosophy in three bullet points."

Or query your system documentation directly using the grounded ask command:

tam ask "How does Linux pipe standard streams?"

What just happened

  • The model weights reside entirely in local storage and are loaded into system RAM.
  • Computation executes exclusively on your local CPU or integrated/discrete GPU.
  • tam ask grounds model generation strictly in the local Tamlinux knowledge index, enforcing citation sources and refusing to run if no local model server is reachable.

Best practice

Only load models whose size fits within your available physical RAM. Loading a model larger than available RAM causes the operating system to thrash pages to disk, which can lock up the system and collapse token generation from around 20 tokens/sec to less than 0.2 tokens/sec.

Intermediate: Memory bandwidth and token generation rate

Summary: Calculate the theoretical maximum generation speed of any model from your workstation's memory bus bandwidth.

The memory bandwidth law of autoregressive generation

During autoregressive decoding, generating each individual token requires streaming the entire weight tensor of the model through the processor's registers exactly once. Therefore, token throughput is mathematically bounded by:

Tokens / second ≈ Memory Bandwidth (GB/s) / Model Size in RAM (GB) × Efficiency

Where real-world memory controller efficiency typically ranges from 70% to 85%.

Worked example

Consider a 7-billion parameter model quantized to Q4_K_M (consuming ~4.5 GB in RAM) running on a dual-channel DDR5-5600 workstation:

  • Theoretical memory bandwidth: 2 x 64 bits x 5.6 GT/s / 8 = 89.6 GB/s.
  • Sustained effective bandwidth (at ~75% efficiency): about 67.2 GB/s.
  • Maximum theoretical token rate: 67.2 GB/s / 4.5 GB = about 14.9 tokens/second.

Completion task

Calculate the maximum token generation speed for an 8-billion parameter model quantized to Q8_0 (consuming 8.5 GB in RAM) on an ultra-wide memory workstation with 200 GB/s sustained memory bandwidth. Complete the formula below by filling in the missing variable (marked with ___):

Tokens_per_sec = Bandwidth_GBs / ___

Target answer: Model_Size_GB (yielding 200 / 8.5 = about 23.5 tokens/second).

Verification hints

  • Autoregressive inference cannot generate tokens faster than memory can supply weights, regardless of how many CPU cores or GPU compute shaders are idle.
  • To increase token speeds without upgrading hardware, select a smaller parameter model or a more compact quantization format.

Expert: Quantization mechanics, KV cache scaling, and CPU SIMD

Summary: Analyze quantization weight packing (FP16 vs Q4_K_M), context window KV cache memory growth, and CPU SIMD vectorization.

Quantization formats and weight precision

Quantization compresses floating-point weights into low-bit integer representations with minimal perplexity loss:

FormatBits / WeightMemory (7B Model)Perplexity & Quality
FP1616.0~14.0 GBBaseline uncompressed floating-point reference.
Q8_08.5~7.5 GBVirtually zero perplexity loss; ideal when RAM is abundant.
Q4_K_M4.5~4.5 GBTamlinux recommended sweet spot: medium k-quant with 4-bit attention and 6-bit feed-forward tensors.
Q2_K2.6~2.8 GBExtreme compression; noticeable quality degradation on complex reasoning tasks.

KV cache memory scaling

As conversations grow, storing the Key and Value matrices across multi-head attention layers consumes significant memory in addition to static weights:

KV Cache Bytes = 2 × layers × heads × head_dim × context_length × bytes_per_element

For a model with 32 layers, 32 attention heads, 128 head dimensions, and 16-bit precision, an 8,192-token context consumes ~2.1 GB of RAM purely for the KV cache. Enabling 8-bit KV cache quantization (--cache-type-k q8_0 --cache-type-v q8_0 in llama.cpp) cuts this memory overhead in half without impacting reasoning.

CPU vectorization with AVX2 and AVX-512

When running on CPUs, matrix-vector multiplication (GEMV) operations are vectorized using native SIMD intrinsics (AVX2, AVX-512, or ARM NEON). By compiling libtam and inference backends with -march=native, the compiler maps integer multiply-accumulate operations directly into 256-bit or 512-bit wide vector registers, avoiding scalar memory stalls.
