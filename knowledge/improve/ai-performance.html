Physics of Local AI Generation

Running large language models locally provides complete privacy, zero telemetry, and offline availability. However, unlike graphics rendering or video encoding, local autoregressive text generation is fundamentally governed by the physical memory bandwidth of your workstation's RAM subsystem, rather than raw compute TFLOPS.

Run local inference and monitor memory headroom

Goal: you will be able to query local inference status, understand RAM requirements for model weights, and avoid memory exhaustion thrashing.

Why it matters: running models locally guarantees data privacy and offline access without API subscription fees. However, loading a model that exceeds available physical RAM forces the Linux kernel to swap memory pages to disk, causing catastrophic system thrashing where generation speed collapses from 20 tokens/sec to less than 0.2 tokens/sec.

Before you start: open a terminal. Check your available memory using free -h. The tam ask command queries a local inference server without touching any cloud services. See Resources and Performance for memory inspection basics.

Local AI models run entirely on your own processor and memory. The command tam ask requires an active local inference server (such as Ollama). If Ollama is not running, tam ask exits cleanly and suggests using tam search instead. You do not need root privileges to inspect system memory or query documentation.

If it goes wrong

tam: no local model available (Ollama not running)
The local Ollama server process is not active. Start Ollama or use tam search to query offline documentation directly without AI assistance.
System freezes or becomes sluggish after loading a model
The selected model exceeds physical RAM capacity. The Linux kernel is thrashing memory pages to disk swap. Select a smaller quantized model (such as a 1.5B or 3B parameter model).
model not found
The requested model has not been downloaded into Ollama's local storage. Pull the model weights with ollama pull <model> before running inference.

What happens if you attempt to load a 14-billion parameter model (requiring ~9 GiB RAM) on a workstation with only 4 GiB of available RAM?

The operating system runs out of physical memory and begins thrashing pages to swap storage on disk. Token generation collapses from conversational speeds to fractions of a token per second, and the workstation desktop may freeze.

Does running tam ask send your search queries to external third-party cloud servers?

No. tam ask communicates exclusively with a local server on 127.0.0.1:11434 and grounds its answers strictly within the local Tamlinux guide files.

New words

Inference
The process of running inputs through a pre-trained machine learning model to generate predictions or tokens.
Quantization
Compressing model weights from floating-point numbers into low-bit integers (e.g. 4-bit or 8-bit) to reduce RAM usage and bandwidth demands.
Thrashing
A pathological state where the CPU spends almost all its time moving memory pages between physical RAM and disk swap rather than executing code.

Every process must respect its system memory boundaries and allocation mode.

Memory bandwidth and token generation rate

Goal: you will be able to calculate the theoretical maximum token generation rate of any model from memory bus bandwidth and evaluate quantization tradeoffs.

Mental model

+-------------------------------------------------------------+
| Processor (CPU / GPU Cores & Vector Registers)              |
+-------------------------------------------------------------+
          ^                                       |
  Reads full model weights            Streams 1 token output
  (e.g. 4.5 GB) for EVERY token                   v
          |                                  +--------+
+-------------------------------------+      | Output |
| System RAM (e.g. DDR5-5600 Dual Ch) |      | Stream |
| Bandwidth Cap: ~67 GB/s effective   |      +--------+
+-------------------------------------+

During autoregressive decoding, generating each individual token requires streaming the entire weight tensor of the model through the processor's registers exactly once. Therefore, token throughput is mathematically bounded by:

Tokens / second ≈ Memory Bandwidth (GB/s) / Model Size in RAM (GB) × Efficiency

Where real-world memory controller efficiency typically ranges from 70% to 85%.

Worked example: Calculate theoretical token generation rate

Consider a 7-billion parameter model quantized to Q4_K_M (consuming ~4.5 GB in RAM) running on a dual-channel DDR5-5600 workstation:

  • Theoretical memory bandwidth: 2 channels × 64 bits × 5.6 GT/s / 8 = 89.6 GB/s.
  • Sustained effective bandwidth (at ~75% efficiency): 89.6 × 0.75 ≈ 67.2 GB/s.
  • Maximum theoretical token rate: 67.2 GB/s / 4.5 GB ≈ 14.9 tokens/second.

Captured on an Arch Linux workstation, 2026-10-25. Even if the processor has 32 idle compute cores, generation cannot exceed ~15 tokens/sec because the memory bus cannot feed weights any faster.

Independent task

Evaluate whether a 14-billion parameter model quantized to FP16 (consuming 28 GB) can run interactively at greater than 5 tokens/second on a dual-channel DDR4-3200 system (effective bandwidth ~38.4 GB/s).

Divide effective bandwidth (38.4 GB/s) by model size (28 GB): 38.4 / 28 ≈ 1.37 tokens/second. It cannot achieve 5 tokens/second. To reach interactive speed, the model must be quantized to Q4_K_M (~8.5 GB), which yields 38.4 / 8.5 ≈ 4.5 tokens/second, or run on hardware with higher memory bandwidth.

Check yourself

Decide your answer before you reveal it.

Why does upgrading from an 8-core CPU to a 16-core CPU on the same dual-channel motherboard fail to double local LLM generation speed?

Local autoregressive inference is memory-bandwidth bound, not compute bound. Both processors share the exact same physical memory bus channels. Because the bus is already fully saturated streaming model weights, additional CPU cores sit idle waiting for memory transfers.

How does 4-bit quantization (Q4_K_M) double token generation speed compared to uncompressed FP16?

Q4_K_M reduces the memory footprint of each weight from 16 bits to ~4.5 bits. Because the memory controller has to transfer less than a third as many bytes across the bus for every token generated, token throughput increases proportionally.

How it works

As conversations grow, storing the Key and Value matrices across multi-head attention layers consumes significant memory in addition to static weights:

KV Cache Bytes = 2 × layers × heads × head_dim × context_length × bytes_per_element

For a model with 32 layers, 32 attention heads, 128 head dimensions, and 16-bit precision, an 8,192-token context consumes:

2 × 32 × 32 × 128 × 8,192 × 2 bytes = 4,294,967,296 bytes ≈ 4.0 GiB

Enabling 8-bit KV cache quantization (--cache-type-k q8_0 --cache-type-v q8_0 in llama.cpp) cuts this memory overhead in half without impacting reasoning.

When running on CPUs, matrix-vector multiplication (GEMV) operations are vectorized using native SIMD intrinsics (AVX2, AVX-512, or ARM NEON). By compiling libtam and inference backends with -march=native, the compiler maps integer multiply-accumulate operations directly into 256-bit or 512-bit wide vector registers, avoiding scalar memory stalls.

Why Tamlinux chose this

Tamlinux emphasizes lean, local, and grounded AI tooling. By choosing grounded question answering over cloud APIs, users retain complete privacy and offline autonomy. By teaching the memory-bandwidth bounds of hardware, Tamlinux prevents users from chasing expensive CPU upgrades when memory channel width is the true physical constraint.

Edge cases

  • Context window memory exhaustion: In long conversations, the KV cache can grow by several gigabytes, exceeding remaining memory and inducing swap thrashing even when the initial model weights fit comfortably.
  • Memory controller thermal throttling: Continuous tensor streaming generates high sustained write and read loads across memory DIMMs, causing some motherboards to throttle memory clock speeds under prolonged inference.
  • NUMA node traversal penalties: On multi-socket or multi-die processors, accessing weights stored on a remote memory channel introduces substantial latency penalties. Inference runtimes should be pinned to the local NUMA node with numactl.

Check yourself

Why does batch size 1 autoregressive text generation fail to utilize the massive compute TFLOPS of modern GPUs?

At batch size 1, generating each token requires loading every model weight from RAM to compute registers for only one multiply-accumulate operation per weight (arithmetic intensity ≈ 1 FLOP/byte). High-end GPUs have compute-to-memory ratios exceeding 100–200 FLOPs/byte, leaving their compute ALUs idling more than 90% of the time while waiting for memory bus transfers.
