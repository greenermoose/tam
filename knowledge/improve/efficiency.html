How software can wait for work efficiently

This page explains how software can wait for work without repeatedly checking for it.

Repeatedly checking for work can use energy even when nothing needs attention. Programs can instead wait to be notified when something happens.

What wastes idle CPU time?

Naive automation scripts often check status using while true; do check; sleep 1; done loops. Waking up every second prevents modern CPU cores from dropping into low-power package C-states (such as C8 or C10), tripling idle battery drain and generating unnecessary heat even when the laptop lid is closed.

How to think about it

Periodic wakeups keep CPUs out of deep idle. Prefer work that runs when an event arrives instead of polling on a timer.

New words

Context switch
The kernel operation of saving one process's execution state and restoring another to run on a CPU core.
C-state
An operating state of a processor core; C0 is active execution, while higher states (C1 to C10) progressively power down clock domains and caches to conserve energy.

An idle process sleeps in the kernel and consumes zero CPU cycles until an event arrives.

Identifying CPU wakeups and idle efficiency

Goal: you will be able to measure processor wakeups, context switches, and CPU idle percentages using vmstat to verify system efficiency.

Before you start: open a terminal (The Shell and Streams). Review the Progressive Power Ladder for sleep levels and system power management. The monitoring commands here are strictly read-only queries.

When measuring idle system performance, avoid moving the mouse cursor or pressing keys while the benchmark runs. Moving the mouse sends input events that wake up the compositor and inflate interrupt counts. Run the command, wait a few seconds without touching inputs, and observe the numbers.

Mental model

Polling Loop (Naive)                      Event-Driven (inotify)
-------------------                      ----------------------
while true; do                           inotifywait -e modify file.txt
  check_file                                 |
  sleep 1  <-- CPU wakes every second        | [waits for an event]
done                                           v
[Wastes energy, misses changes]          File modified -> kernel wakes script

A polling loop wakes the CPU every interval, even when nothing has changed. If changes occur between sleeps, they can be missed or delayed. In contrast, inotifywait registers an inotify watch in the Linux kernel and calls read(2) on the inotify file descriptor. The waiting process can block until an event (such as modify, create, or delete) is reported. Delivery and application processing take time; measure the actual workload rather than assuming zero CPU use or instant delivery.

Try it

Run vmstat 2 2 to sample over 2-second windows. Observe how leaving the system untouched yields high idle percentages (95%+) and steady context switch rates.

If it goes wrong

Context switches (cs) spike into tens of thousands
A background process or browser tab is actively running a high-frequency polling loop or animation. Identify it using top or htop sorted by CPU usage.
Idle column (id) drops below 80% with no visible apps
A background indexing service, compilation, or misbehaving background daemon is consuming CPU cycles. Inspect active processes with ps aux --sort=-%cpu | head -10.
Command vmstat not found
vmstat is part of the standard procps-ng package included with every base Arch Linux installation.

On Tamlinux, desktop widgets and status monitors (such as fred.* plugins and Quickshell bars) can use events such as Wayland and D-Bus notifications. Whether a particular component polls and how much power it draws require inspection and measurement.

Check yourself

Decide your answer before you reveal it.

Why is the first output line of vmstat 1 3 different from the subsequent lines?

The first line prints system-wide averages accumulated since the machine booted. Only the second and subsequent lines report activity measured over the exact sampling interval (1 second).

What does a low id (idle) percentage in vmstat indicate?

It indicates that processor cores are spending substantial time executing user or system code, preventing the CPU from entering energy-saving sleep states.

How it works: epoll and Wayland event dispatching

Linux provides epoll as an $O(1)$ event multiplexer. Rather than iterating over an array of file descriptors on each check (like $O(N)$ select or poll), epoll_wait(2) sleeps until the Linux kernel's ready-list receives a notification from a device driver, timer, or socket buffer.

Tamlinux desktop components communicate with the display server over a UNIX domain stream socket located at $XDG_RUNTIME_DIR/wayland-0 (or wayland-1). Window title updates, workspace changes, and pointer events are delivered through the Wayland wire protocol:

  1. The application retrieves the Wayland socket file descriptor with wl_display_get_fd().
  2. The descriptor is registered into the process's main epoll instance with EPOLLIN.
  3. The main thread calls epoll_wait(epfd, events, MAX_EVENTS, -1). A timeout of -1 waits without a timeout, subject to events and interruptions.
  4. When the compositor writes state changes, the kernel wakes the process, which calls wl_display_dispatch() to process messages and immediately returns to sleep.

Event-driven interfaces can reduce unnecessary work. Individual components may also use timers or polling; inspect and measure the component of interest.

Why Tamlinux chose this

Reducing unnecessary wakeups is one way to pursue efficiency. CPU idle states, power and fan behavior depend on hardware and the whole workload; compare measurements under controlled conditions before claiming an improvement.

Edge cases and failure modes

  • Inotify queue overflow: If filesystem changes occur faster than user space can consume them, the kernel inotify event queue overflows (IN_Q_OVERFLOW), and intervening events are lost. High-volume watchers must fall back to a full directory scan when an overflow event is received.
  • Epoll thundering herd: If multiple worker threads wait on the same epoll descriptor with EPOLLET (edge-triggered), multiple threads may wake simultaneously for a single event unless EPOLLONESHOT or dedicated per-thread descriptors are used.
  • Timer integration: Avoid creating separate worker threads that sleep. Use timerfd_create(2) to obtain a file descriptor for timer expirations and multiplex it directly within the main epoll loop.

Explore: Inspect active Wayland socket and epoll handles

Inspect active Wayland display sockets in your runtime directory:

$ ls -la "$XDG_RUNTIME_DIR"/wayland-*
srwxr-xr-x 1 user user 0 Oct 25 08:00 /run/user/1000/wayland-1
-rw-r----- 1 user user 0 Oct 25 08:00 /run/user/1000/wayland-1.lock

Notice that the Wayland socket is a UNIX domain stream socket (denoted by s in file permissions). Event-driven clients register this descriptor with epoll to sleep with zero CPU overhead until the compositor sends input or frame events.

Check yourself

Decide your answer before you reveal it.

Why does epoll scale efficiently to thousands of file descriptors while select degrades linearly?

select requires passing an entire descriptor set to the kernel on every call and iterating across all descriptors ($O(N)$). epoll registers descriptors once in kernel memory and returns only the descriptors that are ready ($O(1)$), eliminating per-call memory copies and scans.
