Making better use of working memory

This page explains one way a computer can make better use of its working memory.

When working memory runs short, a computer can move some information elsewhere. ZRAM compresses information in memory to make room; the benefit depends on the information and the machine.

What is ZRAM?

When applications allocate more memory than physical RAM can hold, a traditional system pages data out to mechanical disks or NVMe drives, causing devastating input/output latency spikes and frozen interfaces. ZRAM creates a fast compressed block device in physical memory, compressing idle pages in microseconds via CPU instructions rather than waiting milliseconds for storage disks.

Why it matters

How to think about it

ZRAM compresses pages in RAM as swap. It can absorb memory pressure quickly, but it is not the same as adding physical memory.

New words

ZRAM
A Linux kernel driver that creates a virtual block device in physical RAM where all stored data is compressed on the fly.
Paging
The operating system mechanism that moves chunks of memory (pages) between physical RAM and swap space to manage memory pressure.
Disk thrashing
A severe performance freeze occurring when the system spends more time reading and writing swap pages to disk than executing user instructions.

When system memory is constrained, an inactive process has its anonymous memory pages compressed into ZRAM.

Inspecting active ZRAM swap

Goal: you will be able to query active compressed RAM swap using zramctl, identify compressed versus uncompressed memory metrics, and recognize when ZRAM is protecting your workstation from disk thrashing.

Learning path: Run lean — Start | ← Back | Next →

Before you start: open a terminal (The Shell and Streams). Review basic memory and resource monitoring (Resources and Performance). These inspection commands are completely read-only and do not alter system configuration or running processes.

When running diagnostic commands like zramctl, you do not need administrative or root privileges for read queries. The output displays active devices directly in your terminal. If the command displays a single device like /dev/zram0 mounted at [SWAP], compressed in-RAM swap is active and handling memory pressure automatically.

Disk Swapfile (/swap/swapfile on NVMe/SSD)

The Linux kernel virtual memory subsystem prioritizes swap devices numerically: the device with the highest priority receives swapped pages first. By giving /dev/zram0 priority 100 and disk swap priority 0, the kernel absorbs all initial memory pressure directly in fast, compressed RAM. Only if ZRAM becomes completely saturated does page eviction spill over to persistent disk storage.

Worked example: Inspect compressed RAM swap devices

$ zramctl
NAME       ALGORITHM DISKSIZE  DATA COMPR TOTAL STREAMS MOUNTPOINT
/dev/zram0 zstd         28.3G  6.9M  2.3M    4M         [SWAP]

Captured on an Arch Linux workstation, 2026-10-25. Your output will differ depending on current RAM size and running workloads.

What just happened

  1. zramctl queries the Linux kernel's ZRAM driver and displays configured compressed memory block devices.
  2. NAME (/dev/zram0) is the kernel compressed block device operating directly in physical RAM.
  3. ALGORITHM (zstd) indicates the stream compression engine used to compress inactive memory pages.
  4. DISKSIZE (28.3G) represents the maximum uncompressed swap boundary presented to the operating system's virtual memory manager.
  5. DATA (6.9M) is the original uncompressed volume of memory pages paged into swap.
  6. COMPR (2.3M) and TOTAL (4M) show the actual physical RAM consumed to store that paged data, including compression overhead and memory allocator metadata.
  7. MOUNTPOINT ([SWAP]) confirms the device is actively registered as system swap.

Try it

Inspect your overall system swap and memory summary using swapon --show and free -h. Notice that /dev/zram0 appears as a high-priority swap partition alongside your physical memory counters, confirming that swap operations target RAM rather than disk.

If it goes wrong

zramctl returns nothing (empty output)
No ZRAM device has been configured or initialized by the kernel. Check system service status with systemctl status systemd-zram-setup@zram0.service.
DATA shows 0B and COMPR shows 0B
Your workstation has plenty of free physical RAM, so the kernel has not yet needed to page out any inactive memory. This is healthy and normal under light workloads.
TOTAL exceeds DATA under very small loads
When storing only a few kilobytes of data, allocator tracking overhead and page table structures can momentarily exceed raw compressed data size. As more pages are paged in, compression savings vastly outweigh allocator overhead.

On Tamlinux, ZRAM is managed declaratively via systemd-zram-generator configured in /etc/systemd/zram-generator.conf. Tamlinux configures zram-size = ram using the modern zstd compression algorithm at swap priority 100. This provides approximately 3:1 compression density, ensuring even a fully utilized ZRAM device occupies only about one third of physical RAM while leaving disk swap strictly as a zero-priority emergency fallback.

What is the key difference between DATA and COMPR in zramctl output?

DATA is the original uncompressed size of memory pages paged out by the kernel, while COMPR is the actual physical memory consumed after compressing those pages.

Why is swapping to ZRAM over 100 times faster than traditional disk swap?

ZRAM compresses and decompresses pages directly in physical memory using CPU instructions in microseconds, avoiding the millisecond latency and I/O bottlenecks of physical storage drives.

How it works: The kernel memory writeback path

When anonymous memory pressure increases, the Linux kernel's memory management subsystem reclaims physical pages through the swap abstraction:

  1. The kernel memory management subsystem selects inactive anonymous pages from the LRU (Least Recently Used) list.
  2. The virtual memory manager dispatches block I/O requests to the swap device /dev/zram0.
  3. The ZRAM block device driver intercepts the bio requests and dispatches the memory buffers to multi-threaded compression streams using per-CPU workqueues.
  4. The compressed chunk is allocated into a zsmalloc slab pool. Unlike the kernel's buddy allocator, which operates on power-of-two page alignments (4 KiB, 8 KiB, etc.) and causes severe internal fragmentation for compressed data, zsmalloc groups heterogeneous variable-sized compressed chunks into multi-page clusters (known as zspages), achieving over 90% allocation packing efficiency.

Why Tamlinux chose this

A responsive developer workstation must never experience whole-system lockups when launching heavy compilation toolchains, browser test suites, or local AI inference models. By deploying ZRAM backed by zstd and configured via systemd-zram-generator, Tamlinux expands usable memory capacity by 100% to 200% entirely in RAM. Because ZRAM operations execute at memory bus speeds with zero disk head contention or NVMe queue saturation, the desktop user interface remains fluid even under severe memory pressure.

Edge cases and failure modes

  • Incompressible pages: Certain data types (such as encrypted payloads, compressed archives, or already-compressed media) cannot be compressed further. When zsmalloc determines that compressed output plus metadata equals or exceeds 4096 bytes, the driver stores the page uncompressed to avoid wasting memory.
  • Memory limit exhaustion: If ZRAM reaches its maximum configured memory limit and no secondary disk swap exists, the kernel triggers the Out-Of-Memory (OOM) killer. Tamlinux prevents this by providing a secondary zero-priority disk swapfile for emergency spillover.
  • CPU latency trade-off: While zstd achieves higher compression than lz4, it consumes slightly more CPU instructions during compression. On battery-constrained or low-power embedded processors, lz4 can be selected to minimize CPU energy consumption.

Explore: Inspect kernel zram sysfs attributes directly

Inspect the kernel driver's runtime statistics directly through the /sys/block/zram0/ virtual filesystem:

$ cat /sys/block/zram0/comp_algorithm
lzo-rle lzo lz4 lz4hc [zstd] deflate 842
$ cat /sys/block/zram0/mm_stat
 7237632  2419127  4218880        0 11472896       41        0       62      136

Captured on an Arch Linux workstation, 2026-10-25.

The comp_algorithm file displays available kernel compression engines with the active engine in brackets. mm_stat exposes raw kernel counters: original size, compressed size, allocated memory, memory limit, maximum peak memory used, zero pages count, and recompression counters.

Why does the kernel's traditional buddy allocator cause unacceptable internal fragmentation for compressed RAM swap?

The standard buddy allocator allocates memory only in power-of-two page chunks (e.g. 4 KiB, 8 KiB). Compressed memory pages produce variable, odd-sized chunks (e.g. 1,420 bytes). Allocating a full 4 KiB page to store 1,420 bytes wastes over 65% of the allocated space as internal fragmentation. zsmalloc solves this by clustering heterogeneous compressed chunks tightly into multi-page objects.
