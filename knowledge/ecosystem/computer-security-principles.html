Computer Security Principles and Threat Modeling

What it means for a computer system to be secure, how defenders decide what can go wrong, and the formal models behind operating systems and hardware isolation.

What security actually protects

Before touching commands or code, security starts with three everyday questions about any piece of information—whether it is a diary, a bank balance, or a photo on your laptop:

  • Confidentiality (keeping secrets): only the people you choose can read it.
  • Integrity (preventing tampering): nobody can silently alter it or swap it for a fake.
  • Availability (keeping it usable): you can still open and use it when you need it, without someone locking you out or crashing the machine.

A fourth idea, accountability, asks: if something goes wrong, can we reliably tell who or what performed the action?

Why it matters

No lock is useful if a window next to it is wide open. Before buying locks, you have to ask what you are protecting, who might try to break in, and what tools they might use. That checklist is called a threat model.

How to think about it

Imagine running a small library. You do not give every visitor the master key to the archive room, the cash register, and the front door; each person gets only the key for what they actually need. In computing, that rule is called least privilege: give every user and every program the smallest set of powers needed to do its job, so a single mistake or broken lock does minimal harm.

New words

Threat model
A structured description of what you are protecting, who might attack it, and which paths they could use.
Least privilege
Giving each user or program only the minimum rights needed for its task.
Side-channel attack
Learning a secret indirectly—such as by timing how fast a lock clicks or watching power usage—instead of breaking the lock head-on.

Inspecting trust boundaries, STRIDE, and process isolation

Goal: read a Linux process's kernel isolation flags and practice mapping a feature with a STRIDE threat model.

Before you start: every boundary where data crosses from untrusted input (network, USB drive, unprivileged user) to privileged code (kernel, root service) is a trust boundary. The Trusted Computing Base (TCB) is the set of hardware, firmware, and software components that must work correctly for the security policy to hold.

Worked example

Every Linux process exposes its current privilege and isolation state in /proc/self/status. You can inspect whether a shell is blocked from gaining new privileges (NoNewPrivs) and whether system-call filtering (Seccomp) is active:

$ grep -E '^(Uid|Gid|NoNewPrivs|Seccomp|CapEff):' /proc/self/status
Uid:	1000	1000	1000	1000
Gid:	1000	1000	1000	1000
CapEff:	0000000000000000
NoNewPrivs:	1
Seccomp:	2

Here Uid 1000 is an unprivileged user across all four user-ID slots (real, effective, saved, filesystem), effective capabilities (CapEff) are all zeros, NoNewPrivs: 1 prevents setuid binaries from elevating privileges, and Seccomp: 2 shows filter-mode syscall sandboxing is active.

When reviewing a design, engineers walk each trust boundary with the STRIDE mnemonic:

  • Spoofing: pretending to be another user or server (mitigated by authentication).
  • Tampering: modifying data in transit or on disk (mitigated by integrity checks and MACs).
  • Repudiation: denying an action occurred (mitigated by tamper-evident audit logs and signatures).
  • Information disclosure: leaking secrets (mitigated by encryption and confidentiality controls).
  • Denial of service: exhausting CPU, memory, or bandwidth (mitigated by quotas and rate limits).
  • Elevation of privilege: gaining unauthorized rights (mitigated by least privilege and sandboxing).

Try it

Run grep -E '^(Uid|NoNewPrivs|Seccomp|CapEff):' /proc/self/status in your terminal. In an interactive desktop shell outside a sandbox, NoNewPrivs and Seccomp are typically 0; inside a sandboxed service or container, one or both are non-zero.

If it goes wrong

Confusing encryption with access control
Encrypting a file on disk protects it when the key is absent (for example, a powered-off stolen laptop), not after the operating system unlocks the disk for a running session. Process isolation and file permissions still matter while logged in.
Overlooking TOCTOU races
Checking a file's permissions and then opening it by path creates a Time-of-Check to Time-of-Use (TOCTOU) window where an attacker can swap the path for a symlink. Safe programs open once and operate on the file descriptor (fstat, openat).

On Tamlinux, daily work runs under an unprivileged account, hardware security helpers run only when explicitly invoked, and system-wide updates are isolated to declared package assemblies rather than ad-hoc scripts.

Check yourself

Answer before revealing the explanation.

Why is keeping the Trusted Computing Base (TCB) small a core security goal?

Any bug inside the TCB can defeat the entire security policy. Moving parsers, network handlers, and UI code outside the TCB reduces the code that must be trusted and audited.

Which STRIDE category describes an unprivileged process tricking a privileged helper into overwriting an arbitrary file?

Elevation of privilege (often combined with a Confused Deputy flaw, where the privileged helper acts on the caller's behalf without checking the caller's own rights to the target).

Formal security models, Saltzer–Schroeder principles, and microarchitectural limits

Reference: Saltzer and Schroeder's eight design principles

Saltzer and Schroeder (1975) established the enduring engineering principles for protection mechanisms [Saltzer & Schroeder]:

  1. Economy of mechanism: keep the protection design as small and simple as possible so defects are easy to find.
  2. Fail-safe defaults: base access decisions on permission rather than exclusion; default to deny.
  3. Complete mediation: check every access to every object against the authority database—do not cache unchecked handles across policy changes.
  4. Open design: security must not depend on keeping the mechanism secret (parallel to Kerckhoffs's principle in cryptography).
  5. Separation of privilege: require two independent conditions (two keys) for critical actions where practical.
  6. Least privilege: operate every program and user with the minimal privileges required for the task.
  7. Least common mechanism: minimize mechanisms shared across mutually untrusting users (shared caches, temp directories, predictors) to limit covert channels.
  8. Psychological acceptability: the security interface must match the user's mental model so users do not bypass it.

A reference monitor is the abstract machine mediating all subject-to-object accesses; to be sound it must be tamperproof, always invoked (complete mediation), and small enough to be verified (verifiability).

How it works: Lampson's access matrix, HRU undecidability, and lattice models

Lampson (1971) modeled protection state as a triple (S, O, A): a set of subjects S, objects O, and an access matrix A[s, o] containing rights such as {read, write, own}. Because matrices are sparse, systems implement them either by columns (Access Control Lists, stored on objects) or by rows (Capabilities, unforgeable tokens held by subjects).

Harrison, Ruzzo, and Ullman (HRU, 1976) formalized state transitions over the access matrix as primitive commands. They proved that in general, the safety problem—deciding whether a given configuration can ever leak a right r to an unauthorized subject—is undecidable by reduction from the Halting Problem (though decidable in restricted mono-operational or typed systems such as Take-Grant).

To reason about information flow rather than merely object access, lattice models order security labels (L, <=):

  • Bell–LaPadula (confidentiality) [Bell & LaPadula]: enforces the Simple Security Property (no read up: subject s may read object o only if L(o) <= L(s)) and the *-Property (no write down: s may write o only if L(s) <= L(o)), preventing a compromised high-clearance process from copying secrets to low-clearance files.
  • Biba (integrity, 1977): dual of Bell–LaPadula—no read down (do not taint high-integrity computation with untrusted input) and no write up (untrusted subjects cannot modify high-integrity objects).
  • Clark–Wilson (commercial integrity, 1987): models integrity through well-formed transactions (Transformation Procedures) that move Constrained Data Items from one valid state to another, enforcing separation of duty.
  • Noninterference (Goguen & Meseguer, 1982): defines end-to-end confidentiality semantically: high-level inputs H must have zero observable effect on low-level outputs L. Formally verified kernels such as seL4 prove noninterference and functional correctness down to C/binary semantics, while capability systems such as Capsicum eliminate ambient authority at the OS API layer.

Edge cases and open research problems

Confused Deputy and ambient authority
When a privileged server resolves pathnames or URLs using its own authority rather than the caller's capability, an attacker can redirect the server's privilege against a protected target (Hardy, 1988). Capability-passing APIs bind authority directly to the unforgeable object reference.
Microarchitectural side channels (Spectre, Meltdown, covert timing)
Speculative execution, out-of-order pipelines, and shared CPU caches violate Saltzer–Schroeder's "least common mechanism" at the hardware layer. Transient instructions leave microarchitectural traces measurable via Flush+Reload or Prime+Probe, leaking across kernel/user and VM boundaries even when architectural state is sound. Mitigations include KPTI, retpoline/IBRS, constant-time programming, and hardware partitioning.
Memory safety vs. spatial/temporal isolation
Buffer overflows, use-after-free, and type confusion break the language-level abstraction that OS boundaries assume. Modern mitigations combine type-safe languages (Rust), ASLR, DEP/NX, CFI, PAC, and hardware capability architectures (CHERI), alongside fuzzing and formal verification.
Research frontier: How can capability hardware (CHERI) and formal verification close the gap between OS security models and real processors?

Traditional ISAs enforce isolation only at page-table granularity, leaving intra-process memory corruption unchecked. CHERI extends pointers with architectural bounds and permissions so compartmentalization and least privilege hold inside a single address space, while projects like seL4 and CompCert explore machine-checked proofs across compiler, kernel, and hardware specification boundaries.
