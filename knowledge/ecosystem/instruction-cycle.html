The microarchitectural instruction cycle

This page explains how a computer processor continuously fetches instructions from memory, interprets their binary codes, executes calculations, and records the results.

Every software program on your computer — from a simple shell script to the Linux kernel itself — eventually compiles into a stream of raw binary machine instructions. The processor operates as an automated engine that loops through discrete microarchitectural phases billions of times per second: pulling bytes from cache into registers, decoding binary opcodes into electrical control signals, calculating results in the ALU, and committing values to memory.

The fundamental loop: fetch, decode, and execute

Goal: you will be able to describe the three primary stages of processor execution (Fetch, Decode, Execute) and inspect processor cache structures that deliver instructions to the execution core.

Why it matters: computers do not read entire programs at once. The processor reads small, numbered instructions one step at a time. Understanding this execution loop explains what a program counter is, how branches change code flow, and why fast CPU caches are essential to prevent processor starvation.

Before you start: open a terminal window (The Shell and Streams). The inspection commands in this section read kernel sysfs information without altering hardware state.

New to this? The Instruction Pointer (often called the Program Counter or PC) is a special CPU register that holds the memory address of the next instruction waiting to be executed. As each instruction finishes, the processor automatically advances the pointer to the next instruction in sequence, unless a jump or branch directs it elsewhere.

Worked example: inspect L1 instruction cache attributes

$ cat /sys/devices/system/cpu/cpu0/cache/index1/type
Instruction

$ cat /sys/devices/system/cpu/cpu0/cache/index1/size
32K

$ cat /sys/devices/system/cpu/cpu0/cache/index1/coherency_line_size
64

Captured on a Tamlinux workstation, 2026-11-01.

What just happened

  1. index1 in sysfs exposes the processor core's dedicated Level 1 Instruction Cache (L1i).
  2. The cache size is 32 Kilobytes per core, sitting directly adjacent to the instruction decoder on the silicon die.
  3. The coherency line size is 64 bytes. When the processor fetches an instruction, it pulls a full 64-byte chunk of machine code into L1i, ensuring that subsequent sequential instructions can be fetched with zero wait states.

The basic 3-stage execution cycle

  1. Fetch: The Control Unit uses the address stored in the Instruction Pointer register (e.g. RIP on x86-64 or PC on ARM) to retrieve binary instruction bytes from the Level 1 Instruction Cache into the CPU's internal Instruction Register.
  2. Decode: The hardware decoder inspects the opcode bits. It determines what operation is requested (such as ADD, JUMP, or LOAD), identifies which registers hold the input data, and prepares internal control signals.
  3. Execute: The processor activates the appropriate functional unit (such as the Arithmetic Logic Unit, barrel shifter, or floating-point unit) to perform the computation. The Instruction Pointer is updated to point to the next instruction.

Try it

Query your CPU core execution capabilities and flags using lscpu | grep -i flags. Look for vector execution flags such as avx2, fma, or sse4_2 that provide specialized hardware execution units.

If it goes wrong

/sys/devices/system/cpu/cpu0/cache/index1: No such file or directory
The kernel sysfs interface is unmounted or running inside an unprivileged container. Inspect cache properties using lscpu -C instead.

What role does the Instruction Pointer (or Program Counter) play during the Fetch stage?

It stores the memory address of the next machine instruction. The fetch unit reads the memory or cache at that specific address to pull instruction bytes into the processor.

What happens to the Instruction Pointer when a conditional branch (like an IF statement) evaluates to TRUE?

Instead of advancing sequentially to the next adjacent instruction, the execution unit writes the branch target address directly into the Instruction Pointer, redirecting subsequent fetches to the new code location.

The 5 classic pipeline stages

To maximize throughput, modern processors do not wait for one instruction to complete before starting the next. Instead, they operate like an assembly line divided into 5 classic stages:

  1. Instruction Fetch (IF): Read instruction bytes from L1i cache at the address in PC/RIP. Increment PC by instruction length.
  2. Instruction Decode (ID): Parse opcode, decode operands, and read register values from the Register File.
  3. Execute (EX): The ALU performs arithmetic or computes the effective memory address for load/store instructions.
  4. Memory Access (MEM): If the instruction reads or writes memory (such as mov (%rdi), %rax), access L1d cache. Otherwise, pass the ALU result through unchanged.
  5. Write-Back (WB): Write the computed result or loaded memory value back into the destination register in the Register File.

Worked example: trace a register addition

Instruction: add %rbx, %rax   (Computes: %rax = %rax + %rbx)

Cycle 1 (IF):  Fetch opcode bytes for 'add %rbx, %rax' from L1i cache into Instruction Register.
Cycle 2 (ID):  Decoder identifies ADD opcode; reads 64-bit values from registers %rax and %rbx.
Cycle 3 (EX):  ALU adds both 64-bit integers and computes condition flags (Zero, Sign, Overflow).
Cycle 4 (MEM): No memory access required (idle pipeline stage for this instruction).
Cycle 5 (WB):  The 64-bit sum is written into register %rax; updated condition flags are latched.

Completion task

Identify the pipeline stall that occurs when an instruction requires the result of an immediately preceding instruction that has not yet reached the Write-Back stage. Fill in the missing hazard term (marked with ___):

Instruction 1: mov (%rdi), %rax    (Loads data from memory into %rax)
Instruction 2: add %rax, %rbx      (Depends immediately on %rax)
Hazard type:   ___ hazard

Fill in data (or Read-After-Write / RAW). A data hazard occurs when instructions that exhibit data dependencies overlap in the pipeline. Processors resolve data hazards using forwarding (bypassing the Write-Back stage directly to the ALU) or by inserting pipeline bubbles (stalls).

Independent task

Observe how instruction throughput is measured in Instructions Per Cycle (IPC). Run uptime or inspect load metrics in resources. Calculate how many instructions a 4.0 GHz processor executes in one second if operating at an average IPC of 1.5.

Multiply clock cycles per second by IPC: 4,000,000,000 cycles/sec * 1.5 instructions/cycle = 6,000,000,000 instructions per second (6 billion instructions/sec).

Why does a branch misprediction incur a severe 15-to-20 cycle penalty on modern processors?

Because the pipeline is deeply staged. By the time a branch instruction reaches the Execute stage to determine whether the jump was taken, 15 to 20 subsequent instructions have already been fetched and decoded speculatively. If the prediction was wrong, all those instructions must be discarded, and fetching must restart at the correct address.

What is Operand Forwarding (or Bypassing)?

A hardware optimization where the result of an ALU calculation in the Execute stage is fed directly to the input multiplexer of the next instruction in the following cycle, without waiting for the result to travel through Memory and Write-Back stages.

How it works: the Out-of-Order (OoO) Superscalar pipeline

Modern high-performance x86-64 processors (such as AMD Zen and Intel Core) do not execute instructions strictly in order. Internally, they translate CISC x86 instructions into an internal stream of RISC-like micro-operations (uops) and execute them dynamically:

  1. Instruction Fetch & uop Cache: The Branch Predictor speculates ahead. The fetch unit pulls bytes from L1i cache into the decoders. If the instructions reside in the uop cache (Decoded Stream Buffer), the power-hungry variable-length instruction decoders are bypassed entirely.
  2. Register Renaming: Architectural registers (e.g. 16 general-purpose registers in x86-64) create false data dependencies: Write-After-Read (WAR) and Write-After-Write (WAW). The Register Alias Table renames architectural registers to a pool of over 200 physical registers, dissolving false dependencies.
  3. Out-of-Order Dispatch: uops enter the Reservation Stations. Each cycle, the scheduler checks which uops have all their source operands ready. As soon as operands are available, uops are dispatched to parallel execution ports (multiple integer ALUs, vector SIMD units, branch units, load/store units) regardless of original program order.
  4. In-Order Retirement via Reorder Buffer (ROB): Although instructions execute out of order as fast as hardware permits, the CPU must preserve the illusion of sequential execution. Every uop is tracked by the circular Reorder Buffer. Results are committed to the architectural state strictly in original program order. If an exception occurs (such as a page fault or divide-by-zero) or a branch was mispredicted, all speculative uops younger than the fault are wiped from the pipeline without modifying permanent architectural state (“precise exceptions”).

Why Tamlinux chose this

Understanding microarchitectural retirement and cache structures informs Tamlinux software optimization. In the tam command implementation, critical data structures (such as page search indexes and navigation tables) are laid out contiguously in memory rather than as fragmented pointer trees. Contiguous memory access enables the CPU hardware prefetcher to detect streaming patterns, pulling cache lines into L1 and L2 caches before the execution core even issues load instructions, achieving sub-5 millisecond response times.

Edge cases and failure modes

  • Speculative Execution Side-Channels (Spectre): When the branch predictor speculates down a path that is later rolled back, speculative memory loads leave cache footprint changes. Attackers can measure memory access timing to infer secret cryptographic keys or kernel memory. Mitigations include barrier instructions (lfence), Retpolines, and Indirect Branch Restricted Speculation (IBRS).
  • Denormalized Floating-Point Stalls: When floating-point calculations produce numbers extremely close to zero (denormals), hardware ALUs often cannot process them in single-cycle pipelines and trap to microcode, slowing execution by orders of magnitude.
  • Store-to-Load Forwarding Failure: When a program stores data to memory and immediately loads it back using a mismatched address offset or larger data size, the processor cannot forward the data directly from the Store Buffer to the Load Queue, causing an expensive pipeline stall.

Why must an out-of-order processor retire instructions in strict original program order through a Reorder Buffer (ROB)?

To ensure precise architectural state and precise exception handling. If an instruction causes a hardware exception (such as a page fault), the operating system expects all previous instructions to be completely committed, and no subsequent instructions to have modified memory or registers. The ROB guarantees that results are only made permanent when all prior instructions have completed successfully.
