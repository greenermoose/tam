Carried Patches and Upstream Engagement

Sometimes a third-party package has a bug that Tamlinux cannot wait for upstream to fix. Tamlinux then carries a patch: it runs a rebuilt package with the fix applied, records it publicly, and removes it as soon as upstream ships the fix.

Inspect carried patches and verify local package status

Goal: you will be able to check which packages carry local patches, verify their retirement status, and understand why Tamlinux never edits system files under /usr directly.

Why it matters: third-party software occasionally suffers critical bugs (such as display freezes or compositor crashes) that make daily work impossible. Rather than hacking files directly under /usr (which breaks integrity checks and gets overwritten on update) or freezing updates with IgnorePkg (which silently blocks security fixes), Tamlinux carries visible, audited patches that retire themselves automatically.

Before you start: open a terminal. On Arch Linux, local patches are published to a dedicated repository called [local-patches]. Inspecting patch status uses read-only commands that require no administrative privileges. See Software packaging and delivery for package management basics.

A patch is a small text file describing exact line changes to source code. In Tamlinux, packages with local fixes carry a distinctive version suffix like -1.1. You can inspect local patch status anytime by reading /var/lib/local-patches-upstream/status.

Worked example: Check local patch status

$ cat /var/lib/local-patches-upstream/status
# 2026-10-23T13:40:08-04:00
aquamarine	0.15.1-1.1	extra/0.15.1-1	ok
hyprland	0.56.2-4.1	extra/0.56.2-4	ok
linux	7.2.11.arch1-1.1	core/7.2.11.arch1-1	ok
omarchy	4.0.4-1.3	-	no-upstream

Captured on an Arch Linux workstation, 2026-10-25.

What just happened

  1. Reading /var/lib/local-patches-upstream/status displayed all packages currently served from [local-patches].
  2. Each entry shows the package name, the locally installed version with its patch suffix (e.g. 0.15.1-1.1, 0.56.2-4.1), the current upstream distro version (extra/0.15.1-1), and the comparison verdict (ok).
  3. The verdict ok confirms our local patch is ahead of upstream and still necessary. If upstream releases a newer version, the status changes to warn us to retire or rebase the patch.

Try it

Query pacman to inspect version numbers and verify that locally patched packages show the distinctive decimal release suffix:

$ pacman -Q aquamarine hyprland
aquamarine 0.15.1-1.1
hyprland 0.56.2-4.1

Every patched package also provides a matching -debug package with unstripped symbols and source files, ensuring native crash backtraces remain fully symbolized locally.

If it goes wrong

status file does not exist
The upstream check hook has not run yet. Run /usr/local/bin/local-patches-upstream-check or check installed versions directly with pacman -Q.
status reports upstream-newer
The upstream distribution has shipped an updated package. Check whether the upstream release incorporates the fix; if it does, retire the patch.
pacman reports file exists in filesystem
A file under /usr was manually edited or copied outside of pacman. Never modify files under /usr directly; always build clean packages.

Check yourself

Decide your answer before you reveal it.

Why does Tamlinux never use IgnorePkg in pacman.conf to freeze a package with a known bug?

IgnorePkg freezes the package silently. You stop receiving all future updates and security fixes, and no tool warns you when upstream fixes the bug. Tamlinux uses a local repository that alerts you the moment upstream moves ahead.

What indicates that an installed package contains a local Tamlinux patch?

Its release number has an added decimal suffix, such as 0.15.1-1.1 (where -1 is the upstream release and .1 is the local patch build number).

New words

Carried patch
A local source code fix maintained and applied to an upstream package until upstream releases an official fix.
Upstream
The original authors, maintainers, and official repositories of an open-source project or distribution.
Retirement
Removing a carried patch, local repository package, and guard hooks once upstream includes the fix in an official release.

Every carried package must have a designated configuration owner and recorded origin.

Repository precedence, patch exports, and automated retirement

Goal: you will be able to verify repository order in pacman.conf, inspect patch sets exported from public forks, and explain automated patch retirement mechanisms.

Mental model

/etc/pacman.conf
  |--> [local-patches]  (file:///var/cache/local-patches)  <-- First repository (HIGHEST precedence)
  |--> [core]
  |--> [extra]          (official mirrors)                <-- Downstream repositories

Package Resolution:
  pacman selects package from the FIRST repository that lists it.
  Version arithmetic does NOT override repository order!

Retirement Detection:
  vercmp <local-version> <upstream-version>
  50-local-patches-upstream.hook fires after every transaction.
  If upstream pkgver > local base: status becomes 'upstream-newer' -> Time to retire!

Pacman evaluates repositories strictly in the order they are defined in /etc/pacman.conf. A package in [local-patches] always supersedes an identical package in [extra], even if [extra] has a higher version number. Automated hooks compare versions after every transaction to alert you when upstream catches up.

Worked example: Check repository precedence in pacman.conf

$ grep -A 4 "\[local-patches\]" /etc/pacman.conf
[local-patches]
SigLevel = Optional TrustAll
Server = file:///var/cache/local-patches

[core]

Captured on an Arch Linux workstation, 2026-10-25.

  1. [local-patches] is listed before [core] and [extra].
  2. Because pacman evaluates repositories in order of declaration, any package present in [local-patches] takes precedence over identical package names in official mirrors.
  3. vercmp is used by the post-transaction hook to compare versions: vercmp 0.15.1-1.1 0.15.1-1 evaluates to 1 (local is ahead), while vercmp 0.15.1-1.1 0.15.2-1 evaluates to -1 (upstream is newer; retirement triggered).

Completion task

Fill the gap (marked ___) in the version comparison test to determine whether upstream has released a newer build that requires checking for patch retirement:

vercmp 0.56.2-4.1 ___

Fill in 0.56.2-5 (or 0.56.3-1). When the second argument is newer than the local base, vercmp returns -1, signaling that upstream has shipped a new release and the patch must be audited for retirement or rebase.

Inspect the compiled binary of a patched library to verify that the carried fix is active. For example, verify that aquamarine carries the hotplug disconnect fix using strings /usr/lib/libaquamarine.so.0.15.1 | grep 'Disabled KMS output'.

On Tamlinux, all carried patches are published transparently on public forks at github.com/greenermoose/<project> and indexed in greenermoose/ecosystem-fred-tamlinux. Patches are built with makepkg -Cf as an unprivileged user, accompanied by -debug packages so local crash backtraces retain complete symbols without debuginfod network lookups.

Check yourself

Decide your answer before you reveal it.

If Arch releases hyprland 0.56.3-1 in [extra] while 0.56.2-4.1 is in [local-patches], will pacman -Syu automatically upgrade it?

No! Because [local-patches] is listed first in pacman.conf, pacman satisfies the dependency from [local-patches] and ignores the newer version in [extra]. The post-transaction hook detects that upstream is newer and flags it in the status report so you can test and retire the patch.

Why must /var/cache/local-patches/ be located outside of user home directories?

Pacman drops privileges to the unprivileged alpm user when downloading or reading repository databases. Because user home directories typically have mode 700 permissions, the alpm user cannot traverse them, resulting in "could not open file" errors.

How it works

The complete carried patch lifecycle consists of four stages:

  1. Patch creation on a public fork: The fix is committed to a branch (patch/<slug>) created directly from the upstream release tag that matches the installed package. The commit message includes the bug description, crash evidence, and retirement criteria.
  2. Exporting patches and tuning PKGBUILD: Patches are exported with git format-patch into ~/pkgs/<pkg>/. The PKGBUILD increments pkgrel with a decimal suffix (e.g. pkgrel=4.1), appends patches to source=() and b2sums=(), and applies them in prepare() with patch -Np1.
  3. Building and local publishing: The package is built as an unprivileged user using makepkg -Cf --noconfirm. The -C flag ensures a clean source directory, preventing already-patched errors. The built .pkg.tar.zst and -debug archives are copied to /var/cache/local-patches/ and registered with repo-add.
  4. Automated retirement detection: After every package transaction, local-patches-upstream-check runs vercmp against the official distribution mirrors. When upstream releases a version containing the fix, the patch is retired: the local repository files, hook, and status files are deleted, and pacman synchronizes the official upstream build.

Why Tamlinux chose this

Public open-source pull request queues face high maintainer fatigue and increasing restrictions, including contributor vouch gates and strict bans on AI-assisted contributions (such as Hyprland's policy). Rather than adding review burden to upstream queues where AI-assisted contributions are unwelcome, Tamlinux publishes each fix where it costs upstream nothing: a clean branch on a public fork based on the upstream release tag, indexed in a public registry. Anyone can inspect, verify, or cherry-pick the change.

Edge cases

  • Building from tarball vs git tree: Packages must always be built from upstream source tarballs, never raw git repository checkouts. For example, Hyprland bakes its source GIT_COMMIT_HASH into its plugin ABI validation string; building from git alters this hash and breaks all desktop plugins.
  • Shared library SONAME preservation: Carried patches should not alter exported symbol signatures or increment library SONAMEs, as doing so requires rebuilding all dependent packages.
  • Partial upgrade risk: Running pacman -Sy against local repositories without performing a full system upgrade (pacman -Syu) leaves sync databases newer than installed packages. Always upgrade packages cohesively.

Check yourself

Why does Tamlinux require local patches to be built from upstream release tarballs rather than raw git checkouts?

Certain core components (such as Hyprland) embed the git commit hash directly into their plugin ABI validation strings at compile time. Building from an arbitrary git commit hash changes this ABI signature, causing all compiled desktop plugins (e.g. titlebars, workspaces) to fail ABI checks and refuse to load on session start.
