Choosing the Rootstock

This page compares different versions of Linux and explains which ones Tamlinux uses or is considering as its rootstock.

Compare the rootstock and the plan

Goal: distinguish the current rootstock from the pilot target and fallback.

Mental model

A rootstock provides the core system software on which the Tamlinux cultivar is installed.

Worked example

The discussion below identifies Arch as the working rootstock, Void as a planned pilot and antiX Core as a fallback.

Every Linux distribution makes its own trade-offs in packaging, init system, release cadence, and architecture. Tamlinux is a workstation environment rather than a new distribution: it is installed onto a rootstock that provides the kernel, drivers, and core system software. Rootstock is not a common term, but one that Fred Horch, the Tamlinux developer, made up to explain how Tamlinux works. Fred defines the rootstock to be the set of software that third-parties publish and is necessary to be installed so that the software we write can function properly. The cultivar is all the software in the Tamlinux release that allows the computer to be used effectively and efficiently by both humans and AI agents.

Our goal is to minimize the size of the rootstock and maximize its speed and efficiency. Currently we are using Arch Linux as our rootstock but we plan to migrate to Void Linux in future versions of Tamlinux. Beyond that we are considering a microkernel to further reduce the code size of the rootstock and improve its performance per watt.

The current rootstock: Arch Linux

  • Why Arch today: rolling releases bring current kernels, Mesa, Qt 6, and Wayland protocols, and keep the system maintained without whole-OS reinstalls.
  • Packaging: pacman with simple PKGBUILD recipes. Locally patched packages are served from a dedicated repository listed first in /etc/pacman.conf; see Carried patches.
  • Why move on: Arch is built around systemd, while the long-term target is a minimal rootstock without it.

The target: Void Linux

Tamlinux plans to try Void Linux as its minimal rootstock, from step 1.2 of the roadmap:

  • Independent: Void is built from scratch, not derived from Debian or Red Hat.
  • runit: Void uses runit for init and service supervision instead of systemd; see Init and service supervision.
  • XBPS: a package manager written in C, with source packages built cleanly by xbps-src. Tamlinux plans to deliver native xbps-src packages built from the same sources as its Nix package.
  • glibc and musl: Void offers both C libraries, which allows a measured comparison; see C standard libraries.

The fallback: antiX Core

If Void has a showstopper, Tamlinux will try antiX Linux Core with runit: a systemd-free Debian-based distribution with a long record of running well on older, low-resource hardware.

Other distributions considered

  • Debian: the upstream of many distributions and a benchmark for packaging standards, but its stable releases move slowly for desktop development.
  • Alpine Linux: very small, built on musl and BusyBox; shows how small a rootstock can be, but less suited to a daily graphical workstation.
  • Puppy Linux and Tiny Core: demonstrations of running entirely from RAM, relevant to hardware longevity.
  • Gentoo: source-based and highly tunable, but full source builds are impractical on older hardware.

For a description of each of these systems and many more, and for the microkernel research planned for Tam 2.0, see the Operating systems reference.

Completion task

Sort those three names into current rootstock, pilot and fallback.

Arch is the working rootstock. Void is the planned pilot; antiX Core is the fallback if the pilot has a showstopper.

Independent task

Find the linked rootstock plan and identify what would qualify as a showstopper.

Choosing

Use the installed rootstock's tools for present maintenance; evaluate a pilot against its own evidence.

Troubleshooting

A desired target does not prove hardware, application or recovery support.

On Tamlinux: The Void pilot is planned; Arch remains the working rootstock in the cited product plan.

Check yourself

Does selecting Void as a pilot prove it is running on this host?

No. Inspect the host and selected installation rather than inferring it from the plan.

What evidence separates a proposed change from a delivered one?

Inspect the relevant plan, selected package and acceptance evidence; a proposal alone establishes none of those.
