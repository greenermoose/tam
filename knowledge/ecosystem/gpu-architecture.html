Graphics processing units and CPU-GPU architecture

This page explains how CPUs and GPUs are built differently and how they work together to run modern computers.

In the early days of personal computing, the Central Processing Unit performed every single calculation in the machine, including calculating every pixel on the monitor. Today, modern computers rely on heterogeneous computing: pairing a latency-optimized CPU with a throughput-optimized Graphics Processing Unit (GPU). Understanding this architectural partnership clarifies why dedicated GPUs exist, how massive parallelism works, and how graphics drivers coordinate hardware across system buses.

How does a GPU differ from a CPU?

A modern computer is not a single processor executing instructions in isolation; it is a team of specialized chips. When an application runs slowly or consumes excessive battery power, knowing whether the CPU or GPU is handling the workload helps you diagnose performance bottlenecks and optimize your workflow.

Worked example: inspect your system graphics processor

$ lspci -nnk -d ::0300
05:00.0 VGA compatible controller [0300]: Advanced Micro Devices, Inc. [AMD/ATI] Lucienne [1002:164c] (rev c1)
	Subsystem: Advanced Micro Devices, Inc. [AMD/ATI] Device [1002:1636]
	Kernel driver in use: amdgpu
	Kernel modules: amdgpu

$ ls -l /dev/dri/
total 0
drwxr-xr-x  2 root root         80 Nov  1 11:00 by-path
crw-rw----+ 1 root video  226,   1 Nov  1 11:00 card1
crw-rw-rw-+ 1 root render 226, 128 Nov  1 11:00 renderD128

Captured on a Tamlinux workstation, 2026-11-01. Your processor model, PCI bus identifier, and kernel module will reflect your installed hardware.

What just happened

  1. lspci locates the graphics controller at PCI bus address 05:00.0. It identifies the hardware as an AMD Radeon graphics processor (Lucienne architecture) and confirms that the open-source amdgpu kernel driver is managing the device.
  2. ls -l /dev/dri/ exposes the character device nodes created by the Linux Direct Rendering Manager:
    • card1: The master KMS display node, used by the Wayland compositor to control screen modes and outputs.
    • renderD128: The unprivileged render node, used by applications and games to submit 3D rendering and compute tasks without needing display management rights.

Try it

Run lscpu | grep "Model name" followed by lspci -nnk -d ::0300. Identify how many CPU cores your machine has and compare that with the model name of your graphics controller.

If it goes wrong

lspci: command not found
The pciutils package is missing. On Tamlinux, pciutils is included in the base system rootstock.
Kernel driver in use is missing from lspci output
The Linux kernel did not bind a hardware graphics driver to the chip, causing the system to fall back to basic EFI framebuffers. Verify that your kernel firmware package (such as linux-firmware) is installed.

Why does a computer need both a CPU and a GPU rather than just a faster CPU?

A CPU is designed to execute sequential tasks with deep branch logic as quickly as possible, but it has few cores. A GPU has thousands of cores designed for parallel math. Performing modern 3D graphics or video processing on a CPU alone would overwhelm its cores and grind everyday desktop responsiveness to a halt.

What is the difference between an integrated GPU (iGPU) and a dedicated/discrete GPU (dGPU)?

An integrated GPU is built into the same silicon chip as the CPU and shares system RAM for video memory. A discrete GPU is an independent expansion card installed in a PCIe slot, featuring its own dedicated cooling system, power delivery, and ultra-high-speed Video RAM (VRAM).

How it works: The lifecycle of a rendered frame on Linux

When an application renders a frame and presents it to your screen under Wayland, data flows through a carefully coordinated zero-copy pipeline:

  1. Buffer Allocation (GBM / DMA-BUF): The client requests a graphic buffer from the Generic Buffer Manager (GBM) or Vulkan memory allocator. The kernel graphics driver (via GEM or TTM memory managers) allocates physical VRAM pages and exports a portable file descriptor called a DMA-BUF.
  2. Hardware Rendering: The application issues draw calls through Mesa. Mesa compiles shaders into native GPU machine instructions and constructs a command packet. It passes the command packet to the kernel DRM driver via ioctl(DRM_IOCTL_AMDGPU_CS) (or driver equivalent). The GPU hardware executes the shaders, writing rendered pixels into the allocated DMA-BUF.
  3. Presentation over Wayland: When rendering completes, the client passes the DMA-BUF file descriptor across the Wayland Unix domain socket to the compositor using the linux-dmabuf-v1 protocol, followed by wl_surface.attach and wl_surface.commit.
  4. Compositing and Scanout: The Wayland compositor takes incoming client buffers, composites them into a desktop scene (or directs full-screen buffers straight to a hardware display overlay plane to achieve zero-copy scanout), and issues an atomic modesetting commit (DRM_IOCTL_MODE_ATOMIC_COMMIT).
  5. Page Flip: At the next V-Blank interval, the display timing controller scans out pixels directly from the buffer over the monitor cable.

Why Tamlinux chose this

Tamlinux builds strictly on open-source Linux kernel drivers and upstream Mesa implementations. Proprietary out-of-tree graphics drivers tie the operating system to specific kernel versions, break during routine rolling updates, and complicate debugging. Using open-source Mesa drivers allows Tamlinux to maintain a lean, stable rootstock where graphics updates retire cleanly alongside system packages.

Edge cases and failure modes

  1. GPU Hangs and Recovery: If a shader enters an infinite loop or encounters an illegal memory dereference, the GPU engine locks up. Modern Linux kernel drivers implement hardware watchdog timers. When a ring buffer times out, the driver issues a soft engine reset, resets the faulting GPU block, and returns an error (VK_ERROR_DEVICE_LOST) to the affected process without crashing the entire operating system.
  2. Context Switching Costs in GPGPU: Switching a GPU between graphics rendering tasks (which operate with high-priority V-Sync deadlines) and large compute workloads (such as AI model inference running thousands of iterations) introduces context-switch overhead. Modern GPUs provide dedicated asynchronous compute queues that run compute tasks in parallel alongside graphics rasterization without stalling display updates.

How does DMA-BUF eliminate redundant memory copying between client applications and the Wayland compositor?

In legacy display systems, an application rendered into private memory, copied the pixels to the display server over a socket, and the server copied them again to the graphics card. DMA-BUF passes an open kernel file descriptor representing the physical VRAM allocation. The client renders directly into VRAM, and the compositor reads that exact same VRAM address without a single byte being copied across memory buses.

Why are compute queues kept separate from graphics queues on modern GPUs?

Graphics queues are bound to strict visual deadlines: missing a 16.6 ms (60 Hz) or 8.3 ms (120 Hz) frame window produces visible stuttering. Compute workloads (such as physical simulation or machine learning) can run for hundreds of milliseconds. Separating them into distinct hardware queues allows the GPU scheduler to execute compute tasks asynchronously whenever graphics units have spare execution cycles.
