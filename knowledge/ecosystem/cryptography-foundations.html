Foundations of Cryptography

This page explains how mathematics turns a short secret key into a shield that keeps messages private and proves they have not been altered.

Keeping secrets without hiding the rules

Cryptography is the science of protecting information when untrusted people or computers can watch, copy, or tamper with the messages. Instead of hiding how the system works, modern cryptography publishes the rules in the open and relies only on keeping a secret number, called a key, private.

Why it matters

Every time you check your bank balance, install a software update, or unlock an encrypted laptop, strangers' routers and cables carry your bytes. If the security depended on keeping the software secret, one stolen phone or reverse-engineered program would break security for everyone. Putting all secrecy into an easily replaceable key lets billions of people safely share the same open-source tools.

How to think about it

Think of a physical combination padlock sold in hardware stores. Everyone can buy the same padlock, take it apart, and see how its gears work. That openness does not help a thief open your locker, because only you know your 3-number combination—and if someone peeks at your combination, you can spin the dial to a new one without inventing a new padlock.

To build these locks in software, cryptography uses "clock arithmetic" (also called modular arithmetic): just as 10 o'clock plus 5 hours wraps around to 3 o'clock on a 12-hour clock, computers wrap numbers around a fixed size using remainders. Multiplying or mixing numbers forward is easy, while working backward without the key is astronomically slow.

New words

Encryption
Scrambling readable data into ciphertext so only someone with the right key can read it.
Cipher
The public mathematical recipe used to scramble and unscramble data with a key.
Hash
A fixed-size fingerprint computed from data so any tiny change produces a completely different result.
Authentication
Proving who sent a message or who is trying to sign in.

Generating and testing cryptographic randomness

Goal: you will be able to generate unpredictable random keys from the Linux kernel entropy pool and explain why predictability breaks every cipher.

Before you start: generating random bytes with openssl rand is read-only to the system and safe to run in any terminal.

New to this? The $ sign marks the shell prompt; do not type it. Hexadecimal (base-16) uses digits 0-9 and letters a-f, so two hex characters represent one 8-bit byte.

Worked example

Generate two 128-bit (16-byte) random values using OpenSSL, which reads from the kernel's cryptographic random number generator:

$ openssl rand -hex 16
656fe5d8272a1d3b9bd038cd972aeaf0
$ openssl rand -hex 16
2d358d280579afa3edc8bd324b668a40

Captured on Arch Linux, 2026-11-14; your output will differ every time.

What just happened

  1. openssl rand -hex 16 requested 16 random bytes (128 bits) from the operating system's cryptographic generator (getrandom(2)) and printed them as 32 hexadecimal characters.
  2. Running the exact same command a second time produced a completely unrelated 128-bit value. Even an attacker who saw the first output cannot predict the next bit of the second output.

Try it

Run openssl rand -base64 32 to generate a 256-bit key in Base64, then inspect cat /proc/sys/kernel/random/entropy_avail to see the Linux kernel's current entropy estimate (typically 256 bits on modern kernels).

If it goes wrong

openssl: command not found
Install the openssl package with your native package manager, or read 16 bytes directly with head -c 16 /dev/urandom | od -tx1 -An.
A script uses $RANDOM in Bash for a key
Do not use shell $RANDOM or rand() in C for secrets: they are non-cryptographic linear generators whose entire state can be recovered from a few outputs.

On Tamlinux, kernel getrandom(2) and /dev/urandom draw from a ChaCha20-based CSPRNG seeded from hardware timing, interrupt jitter, and CPU RNG instructions when available; never read /dev/random in scripts expecting it to "have higher quality" on modern Linux, as both interfaces share the same seeded pool.

Check yourself

Decide your answer before you reveal it.

According to Kerckhoffs's principle, what happens if an attacker obtains the exact source code of your encryption program?

Your encrypted messages remain safe as long as your secret key remains secret and unpredictable. Security must never depend on hiding the algorithm.

Why is a 128-bit key considered unguessable by brute force, whereas a 32-bit key is weak?

Each extra bit doubles the search space. A 32-bit key has about 4 billion possibilities (seconds on a laptop), whereas a 128-bit key has 2^128 (~3.4 * 10^38) possibilities.

How it works: from Shannon to computational reductions

Shannon's Perfect Secrecy: A cipher (Gen, Enc, Dec) achieves perfect secrecy if for all messages m_0, m_1 ∈ M and all ciphertexts c ∈ C, Pr[Enc(K, m_0) = c] = Pr[Enc(K, m_1) = c]. Equivalently, ciphertext reveals zero Shannon mutual information: I(M; C) = 0. Shannon's theorem proves this requires |K| ≥ |M| (entropy H(K) ≥ H(M)), which the One-Time Pad (c = m ⊕ k) saturates. Reusing a pad key k leaks c_1 ⊕ c_2 = m_1 ⊕ m_2, catastrophically breaking secrecy.

Computational Security & Reductions: To reuse a short key |k| = λ for gigabytes of data, modern cryptography relaxes unbounded adversaries to PPT adversaries and zero advantage to negl(λ). Security is proved by reduction: show that if an efficient adversary A breaks scheme Π with non-negligible advantage ε(λ), we can wrap A inside a PPT algorithm B that solves a conjectured hard problem (e.g., PRF indistinguishability, integer factoring, CDH/DDH, or Module-LWE) with non-negligible advantage.

Modular Arithmetic & Algebraic Foundations: Many asymmetric schemes operate in the multiplicative group (ℤ_p*, ×) of integers modulo a prime p, or ℤ_N* for composite N = p·q. Under division, a ≡ b (mod n) means n | (a - b). By Fermat's Little Theorem, for prime p and gcd(a, p) = 1, a^(p-1) ≡ 1 (mod p); Euler's theorem generalizes this to a^φ(N) ≡ 1 (mod N) where φ(N) = (p-1)(q-1).

Random Oracle Model (ROM) vs. Standard Model: In the ROM, a hash function H is idealized as a truly random public function queried via an oracle. ROM proofs are tight and practical (e.g., RSA-OAEP, Schnorr/Ed25519), though Canetti–Goldreich–Halevi (1998) proved artificial schemes exist that are secure in the ROM yet insecure under every concrete hash instantiation.

Edge cases and failure modes

  • CSPRNG state compromise & VM snapshots: Cloning a virtual machine or container after boot can duplicate the CSPRNG state if no post-clone reseed (such as VMGenID or kernel getrandom mixing) occurs, causing identical nonces or keys across clones.
  • Concrete vs. asymptotic bounds: A scheme proved secure up to q² / 2^128 fails at q = 2^64 queries (birthday bound) regardless of asymptotic notation; block-size limits (e.g., 64-bit blocks in legacy 3DES/Blowfish, Sweet32) fail far earlier than key-size limits.

Check yourself

Why is IND-CPA alone insufficient for real-world network protocols, and what concrete attack exploits IND-CPA-only encryption?

IND-CPA does not prevent an attacker from modifying ciphertexts in flight or abusing a server as a decryption/padding oracle. Classic CBC-mode padding oracle attacks (Vaudenay, 2002) and malleability attacks against unauthenticated CTR mode exploit IND-CPA schemes to recover full plaintext byte-by-byte without knowing the key. Real protocols require IND-CCA2 / Authenticated Encryption (INT-CTXT).
