Object files, static libraries, and compilation stages

This page explains what object files and static archives are, how they are produced from C source code, and why systems software compiles and links in stages.

When you build software like the tam command or the libtam core foundation, the compiler does not transform human-readable C source files directly into a final program in a single step. Instead, the toolchain breaks the transformation into discrete stages: compiling source files into intermediate object files (.o), bundling reusable object files into static library archives (.a), and linking those components into an executable binary.

From human code to machine instructions

Computer processors cannot directly read human-written programming languages like C. They only understand binary machine code — sequences of numbers that instruct CPU circuits to move data between registers and perform arithmetic. Between the code written by programmers and the program you run in a terminal are intermediate files that make software faster to build, easier to share, and simpler to maintain.

Why it matters

Large software systems consist of dozens or hundreds of individual source files. If every change to a single line required recompiling the entire system from scratch, building software would take minutes or hours instead of milliseconds. Breaking code into individual object files and reusable static archives allows computers to recompile only the files that changed and package common routines so multiple programs can share them without rewriting logic.

How to think about it

Think of source files (.c) as handwritten recipes in a cookbook. An object file (.o) is a single pre-baked dish prepared from one recipe, ready to be served but waiting on the counter. A static archive (.a) is a banquet platter holding many prepared dishes together in one container. The linker is the caterer who inspects the menu requested by the customer, selects only the required dishes from the platters, and plates the final meal.

New words

Compiler
A programming tool (such as GCC or Clang) that translates human-readable source code into machine instructions.
Object file (.o)
The compiled machine code translation of a single source file, complete with function instructions and relocation placeholders, but not yet linked into an executable program.
Static library (.a)
A single archive file bundling multiple object files together with an index of exported symbols, linked directly into executable binaries.
Linker
A program (ld) that combines object files, resolves function references, and assigns final memory addresses to produce a runnable executable or library.

Compiling, inspecting, and archiving object files

Goal: you will be able to compile a standalone C source file into an object file (.o), inspect its symbol table using nm, package object files into a static library archive (.a) using ar, and link the archive into a working executable.

Before you start: open a terminal (The Shell and Streams). The exercises in this section run entirely in a temporary scratch directory and do not alter system packages or workstation settings.

In C compilation commands, the flag -c tells the compiler to compile the source file into an object file without invoking the linker. The output file convention uses the .o extension.

Worked example

$ cd $(mktemp -d /tmp/c_stages.XXXXXX)
$ printf '#include <stdio.h>\nvoid greet(const char *name) { printf("Hello, %%s\\n", name); }\n' > greet.c
$ printf 'void greet(const char *name);\nint main(void) { greet("Tamlinux"); return 0; }\n' > main.c
$ gcc -std=c11 -Wall -Wextra -c greet.c -o greet.o
$ file greet.o
greet.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
$ nm greet.o
                 U printf
0000000000000000 T greet
$ ar rcs libgreet.a greet.o
$ file libgreet.a
libgreet.a: current ar archive
$ gcc -std=c11 -Wall -Wextra main.c -L. -lgreet -o demo
$ ./demo
Hello, Tamlinux

Captured on an Arch Linux workstation, 2026-11-09. Your scratch directory name will differ.

What just happened

  1. gcc -c greet.c -o greet.o compiled the C source into an ELF 64-bit relocatable object file. The machine code for greet() was generated, but memory addresses for external dependencies like printf remain unresolved.
  2. nm greet.o inspected the object file symbol table: T greet marks greet as an exported text (code) symbol defined in this object, while U printf marks printf as an undefined symbol that the linker must resolve later.
  3. ar rcs libgreet.a greet.o packaged the object file into an indexed static library archive. The r flag inserts files, c creates the archive without warning, and s builds an object symbol index.
  4. gcc main.c -L. -lgreet -o demo compiled main.c and instructed the linker to search the current directory (-L.) for a library named libgreet.a (-lgreet), producing a self-contained executable.

Try it

Inspect the table of contents inside the archive using the ar -t command:

$ ar -t libgreet.a
greet.o

Notice that ar behaves like an archiver (similar to tar): it preserves individual .o files inside the .a container along with their symbol indexes. When you are finished, clean up the scratch directory with cd ~ && rm -rf /tmp/c_stages.*.

If it goes wrong

undefined reference to 'greet'
The linker could not find the definition of greet. Ensure that -L. (library search path) and -lgreet (library name) appear after main.c on the compiler command line.
ar: command not found
The GNU binary utilities (binutils) are not installed. Static archive creation requires ar from the standard development package group.

Tamlinux links libtam statically into core utilities like tam. This means the tam binary contains the machine code from libtam.a embedded directly inside itself, eliminating dynamic library lookup overhead and ensuring the guide and recovery tools function even if shared library paths are broken.

What is the difference between an object file (.o) and a static archive (.a)?

An object file (.o) is the compiled machine code of a single source file with unresolved addresses. A static archive (.a) is an archive container holding multiple object files indexed for the linker.

Why does the compiler flag -c stop before running the linker?

The -c flag instructs GCC to compile C source into machine code but halt before linking, allowing developers and build systems like Make to recompile individual files incrementally without producing an incomplete executable.

How it works: Selective static linking

When you link an executable against individual object files (e.g. gcc a.o b.o -o prog), the linker unconditionally copies every section from both object files into the resulting binary. However, when linking against a static library archive (libtam.a), the linker operates selectively:

  1. Undefined symbol queue: The linker maintains an internal list of symbols that have been referenced by object files processed so far but not yet defined.
  2. Archive index lookup: When encountering -ltam (representing libtam.a), the linker searches the archive's internal symbol table index for members that satisfy current undefined symbols.
  3. Granular extraction: The linker extracts only the specific .o members that resolve pending symbols. Any object files inside the archive whose functions are never called are skipped entirely.
  4. Section relocation: For extracted object files, the linker applies relocation entries (.rela.text), replacing relative placeholder offsets with absolute virtual addresses in the executable image.

In Tamlinux's build system, libtam.a packages dozens of utility functions (such as string manipulation, ini parsing, and terminal capability probing). Because of selective static linking, a utility that only uses terminal functions never pays a size penalty for unused ini parsing code.

Advanced inspection: Examining ELF object sections

Inspect the internal ELF sections of an object file using readelf -S:

$ readelf -S greet.o | grep -E '\.text|\.data|\.rodata|\.rela\.text|\.symtab'
  [ 1] .text             PROGBITS         0000000000000000  00000040
  [ 2] .rela.text        RELA             0000000000000000  000001f0
  [ 3] .rodata           PROGBITS         0000000000000000  00000058
  [ 9] .symtab           SYMTAB           0000000000000000  00000108

The .text section holds compiled CPU instructions, .rodata stores the read-only format string literal, .rela.text contains the relocation pointers marking where printf calls must be patched, and .symtab exposes the symbol list to the linker.

Edge cases and linker ordering

  • Command-line argument order: The GNU linker (ld) processes arguments sequentially from left to right. If a library appears before the object file that references its symbols (e.g. gcc -lgreet main.c), the linker will not know that main.o needs symbols from libgreet.a when reading the archive, resulting in undefined reference errors. Static libraries must always follow the object files or sources that call them.
  • Circular archive dependencies: If libfoo.a calls functions in libbar.a and libbar.a also calls functions in libfoo.a, a single pass from left to right cannot resolve both. In such cases, linkers support archive grouping via -Wl,--start-group -lfoo -lbar -Wl,--end-group, instructing the linker to scan both archives iteratively until all symbols are resolved.
  • Duplicate symbol collisions: If two object files in an archive define the same global symbol name, the linker raises a multiple definition error upon inclusion. Libraries prevent namespace collisions by prefixing global symbols with a unique namespace prefix (e.g. tam_ in libtam).

Why must static libraries typically appear after source files on the compiler command line?

Standard Unix linkers process files from left to right in a single pass, resolving only symbols currently on their unresolved list. If an archive appears before the object file that calls its functions, the linker finds no pending unresolved symbols matching the archive, ignores its members, and later encounters unresolved references when reading subsequent object files.
