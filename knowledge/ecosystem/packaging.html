How software is delivered

This page explains how software is collected, installed, and updated in Tamlinux.

Different tools manage different parts of the software. This page explains where each part comes from and how Tamlinux records what it installs.

Query installed packages safely

Goal: you will be able to query an installed package's version and metadata with the native package manager without modifying any system packages.

Why it matters: before reporting an issue or planning an update, you need to know which version of a package is actually installed. Read-only queries cannot break your system, alter package state, or require administrative privileges.

Before you start: open a terminal. On Arch Linux, pacman is the native package manager. Running query operations (-Q) requires no root or administrative privileges and touches no system files. See First steps if you are new to the command line.

A package is a bundle of program files, documentation, and metadata. In pacman, uppercase -Q means "query" what is already installed on your computer. You do not need sudo or pkexec to inspect installed packages.

Worked example: Query an installed package

$ pacman -Q bash
bash 5.3.20-1

Captured on an Arch Linux workstation, 2026-10-25. Your version may differ.

  1. pacman is invoked with the -Q query flag.
  2. bash is the package name being inspected.
  3. 5.3.20-1 reports upstream version 5.3.20 and packaging release 1. Because this is a query, nothing was downloaded or modified.

Try it

Query detailed package information for coreutils using pacman -Qi coreutils. Inspect the Version, Description, and Install Date fields. No packages are modified.

If it goes wrong

package 'foo' was not found
The package is not installed through pacman. It may be provided by Home Manager, Mise, or another tool manager.
error: you cannot perform this operation unless you are root
You used an installation flag such as -S or -R instead of the query flag -Q. Use only -Q for safe, unprivileged queries.

Does running pacman -Q bash require administrator privileges?

No. -Q only reads local package databases in /var/lib/pacman/local/ and requires no root access.

What does the release number (-1) after the package version represent?

The package build revision created by the distribution maintainer, distinct from the upstream software release.

Identify package ownership across layers

Goal: you will be able to identify which package manager supplies an executable and trace ownership across native, workstation, and user tool layers.

Mental model

Base System (Kernel, Drivers, Core OS)   --> Pacman (/usr/bin)
Workstation Assembly (Tamlinux Desktop) --> Nix / Home Manager (/nix/store)
User Toolchains (Developer / Agent CLIs) --> Mise / Home Manager (~/.local/share)

Each command on your system should have one clear owner. Pacman owns the operating system base. Recorded Tamlinux assemblies deliver the graphical desktop through Nix and Home Manager. Fast-moving developer and agent CLIs are owned by Mise or Home Manager user declarations.

Worked example: Trace an executable to its owning package

$ pacman -Qo /usr/bin/git
/usr/bin/git is owned by git 2.56.0-1

Captured on an Arch Linux workstation, 2026-10-25. Your version may differ.

  1. which git locates the executable at /usr/bin/git.
  2. pacman -Qo queries which installed native package owns that exact filesystem path.
  3. Pacman confirms ownership by the git package at release 2.56.0-1.

Tamlinux strictly enforces that product software reaches your session only through a recorded tamlinux-packages assembly via tam-deploy, never from an unrecorded git checkout or raw copied payload. Furthermore, when local package patches are required, Tamlinux builds self-retiring packages in ~/pkgs with a release suffix rather than using IgnorePkg or modifying files under /usr.

Check yourself

Decide your answer before you reveal it.

Why should user developer tools not be installed via system-wide pacman commands?

Mixing fast-moving user developer tools into the system package database creates version lock-in, risks dependency conflicts with system components, and complicates clean rollbacks.

What happens to the base OS when you roll back a Home Manager generation?

Nothing. Home Manager generations operate within the user profile and /nix/store/; base packages managed by pacman remain untouched.

How it works

Tamlinux delivers software by recording package assemblies in tamlinux-packages. Dependencies are pinned in flake.lock, producing deterministic derivations. When deployed via tam-deploy, Home Manager builds a new generation symlink under ~/.local/state/nix/profiles/home-manager. Switching generations updates symlinks in ~/.nix-profile/bin/ atomically. The base OS remains untouched under native pacman governance.

Why Tamlinux chose this

Tamlinux adopts a hybrid package-management model to balance system stability with developer flexibility. Using the distribution's native package manager for the base ensures proper hardware driver integration and kernel lifecycle management. Using declarative Nix flakes and Home Manager for the desktop environment prevents configuration drift, guarantees reproducibility across workstations, and makes every desktop update instantly reversible.

Edge cases

  • ABI drift across layers: if a native package upgrades a core graphics library (such as Mesa or Wayland), running binaries from an older Nix generation may encounter symbol mismatches until rebuilt.
  • PATH shadowing: having multiple versions of a CLI installed across Pacman, Nix, and Mise can cause unexpected execution order; always verify with which -a.
  • Store garbage accumulation: old Nix store paths persist until explicitly collected with nix-collect-garbage.

Check yourself

How does Home Manager rollback differ from a Btrfs filesystem snapshot rollback?

Home Manager rollback updates user-space symlinks to point to an earlier recorded generation under /nix/store/ without rebooting or altering system files. A Btrfs snapshot rollback restores the entire root filesystem state, including system configuration, kernel, and pacman databases.
