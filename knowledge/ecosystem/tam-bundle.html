How tam-bundle installs and rolls back files

This page explains tam-bundle, a small program that installs a set of files as one unit and can put the previous set back in a moment.

tam-bundle is in development. No Tamlinux release uses it yet: today the desktop still arrives through Nix and Home Manager, as How Nix and Home Manager work explains. Tamlinux plans to deliver its own files with tam-bundle instead. Everything on this page that describes Tamlinux using it is a plan.

What is tam-bundle?

A program is rarely one file. It comes with helper programs, pictures, settings and manuals. tam-bundle treats all the files of one version as a single bundle with a name, a version number and a fingerprint. It copies the bundle into place as ordinary files, writes down exactly what it installed, and keeps the previous version whole beside it.

Why it matters

An update that goes wrong is much less frightening when you can undo it at once. Because the old version is kept complete, going back is one command and takes less than a second. Because every file is listed with its fingerprint, you can also ask which version put a file on your computer, and whether anyone has changed it since.

How to think about it

Think of two bookshelves. One holds the books you are reading now. When a new edition arrives, a helper fills an empty shelf with it, checks every book against a list, and only then swaps the two shelves in one movement. Nobody ever sees a shelf that is half old and half new. The old shelf is kept in the back room, so if the new edition disappoints you, the helper swaps them back.

New words

Bundle
All the files of one version of some software, with a name, a version and a fingerprint, treated as one thing.
Slot
The folder a bundle is installed into. The files in use are in its current folder.
Hash
A short fingerprint computed from a file's contents. If one byte changes, the fingerprint changes.
Rollback
Returning to the earlier working version.

Switch between two versions and back

Goal: you will be able to seal two small bundles, switch a private slot between them, roll back, and ask which bundle installed a file.

Before you start: this section needs the tam-bundle command, which no Tamlinux release installs yet. Check with command -v tam-bundle. If it prints nothing, read the example without running it; the program is built from the public tamlinux-tools repository. Everything here happens inside a temporary folder that you own, so it needs no administrator rights and changes nothing else on your computer.

The $ at the start of a line is the prompt; type what follows it. mktemp -d makes a new, empty, private folder and prints its name. The line beginning tb() defines a short shell function, so that tb switch v1 means tam-bundle --slot "$d/slot" --state "$d/state" switch v1: every command then works in the temporary folder.

Mental model

  v1/  (a built tree)                 v2/
    |  tam-bundle seal                  |  tam-bundle seal
    v                                   v
  v1/BUNDLE + v1/MANIFEST             v2/BUNDLE + v2/MANIFEST
    |                                   |
    |  switch: copy into staging,       |
    |  check, then swap in one step     |
    v                                   v
  slot/current/  <--- swap --->  slot/kept/<bundle id>/
                   back: swap again, nothing copied

A bundle id joins the name, the version and the first twelve characters of the bundle's hash, for example demo-1-198a107655aa. The MANIFEST file lists every directory, file and link with its mode and, for a file, its SHA-256 hash. BUNDLE holds the name, version, overall hash and the sources and tools it was built from.

Worked example: two versions, one rollback

$ d=$(mktemp -d); cd "$d"
$ tb() { tam-bundle --slot "$d/slot" --state "$d/state" "$@"; }
$ mkdir -p v1/bin v2/bin
$ printf '#!/bin/sh\necho one\n' > v1/bin/hello
$ printf '#!/bin/sh\necho two\n' > v2/bin/hello
$ chmod 755 v1/bin/hello v2/bin/hello
$ tam-bundle seal v1 --name demo --version 1
sealed v1 as demo-1-198a107655aa (2 entries)
$ tam-bundle seal v2 --name demo --version 2
sealed v2 as demo-2-77c79880491c (2 entries)
$ cat v1/MANIFEST
format 1
d 0755 - bin
f 0755 sha256:f5dd87fa1cf3d592ff0ba84641abfe39bacecaad5e003c74aa181ccb54c2cc9a bin/hello
$ tb switch v1
switched /tmp/tmp.gZGWeCbGMw/slot to demo-1-198a107655aa (from -): 0 files reused, 1 copied
$ tb switch v2
switched /tmp/tmp.gZGWeCbGMw/slot to demo-2-77c79880491c (from demo-1-198a107655aa): 0 files reused, 1 copied
$ slot/current/bin/hello
two
$ tb back
switched /tmp/tmp.gZGWeCbGMw/slot back to demo-1-198a107655aa (from demo-2-77c79880491c)
$ slot/current/bin/hello
one
$ tb status
slot:      /tmp/tmp.gZGWeCbGMw/slot
state:     /tmp/tmp.gZGWeCbGMw/state
live:      demo-1-198a107655aa
previous:  demo-2-77c79880491c
kept:      demo-2-77c79880491c (previous)
last:      2026-11-10T02:45:54Z back demo-1-198a107655aa from demo-2-77c79880491c ok 0.0s
$ tb where $PWD/slot/current/bin/hello
/tmp/tmp.gZGWeCbGMw/slot/current/bin/hello
  bundle:  demo-1-198a107655aa (demo 1)
  record:  f sha256:f5dd87fa1cf3d592ff0ba84641abfe39bacecaad5e003c74aa181ccb54c2cc9a

Captured with tam-bundle 0.4.0 on an Arch Linux workstation, 2026-11-09. Your temporary folder name and times will differ. The file hashes will match if your files match byte for byte; the bundle ids also depend on the tam-bundle version, which BUNDLE records.

What just happened

  1. seal wrote BUNDLE and MANIFEST into each folder. The two entries are the bin directory and the hello file.
  2. The first switch created the slot and made demo-1 live. (from -) means nothing was live before.
  3. The second switch made demo-2 live and moved demo-1's tree to slot/kept/. On a Btrfs filesystem, files that did not change are cloned rather than copied, and the message counts them as reused.
  4. back swapped the kept tree and the live tree. Nothing was copied, which is why a rollback is fast.
  5. status shows what is live, what back would return to, and the last line of the log.
  6. where names the bundle that installed a file and the hash it was installed with.

Try it

In the same temporary folder, run tb check; it reports that the live tree matches. Then change the live file by hand with echo 'echo edited' >> slot/current/bin/hello and run tb check again, then tb switch v2. Read what each one says. When you are done, leave the folder and remove it: cd; rm -r "$d".

If it goes wrong

tam-bundle: command not found
No Tamlinux release installs it yet. Read the example instead, or build it from the public tamlinux-tools repository into a private prefix as its README describes.
the live tree ... has 1 change not made by tam-bundle (listed above)
Someone edited a file in current/. tam-bundle will not hide that change in a kept tree that a later clean-up could delete. Undo the edit, or run the switch again with --save-edits to copy the changed file into the state folder first.
An administrator password prompt appears
You left out --slot, so the command aimed at the system slot /usr/lib/tamlinux and asked for administrator rights. Cancel it; tam-bundle then reports not authorized to change slot /usr/lib/tamlinux (refused or dismissed); nothing was changed. Use the tb function, which passes your own slot.
no previous bundle is recorded
Only one bundle has ever been live in this slot, so there is nothing to go back to.

On Tamlinux, the plan is for the product's own files to live in the slot /usr/lib/tamlinux, with current/bin on your PATH. A small native package per distribution would install tam-bundle itself, outside any bundle, so a broken bundle could never break the tool that rolls it back. tam-deploy would keep deciding what is tested and run, and call tam-bundle to install it. Third-party software stays with the distribution's package manager. None of this is delivered yet.

Check yourself

Decide your answer before you reveal it.

Why does back copy no files?

The previous version is still complete in slot/kept/. Rolling back swaps that folder with current/ in one step, so nothing needs to be copied or rebuilt.

You edited a file in current/ while debugging. Why does the next switch stop instead of carrying on?

A switch moves the old tree to kept/, and pruning can later delete kept trees. Stopping makes sure your edit is noticed: you can undo it, or let --save-edits copy it to the state folder before switching.

Two people seal folders whose files are identical, byte for byte and mode for mode, with the same name and version. Do they get the same bundle id?

Yes, if they also used the same tam-bundle version and recorded the same sources. The hash covers the identity lines and the file list, not the time it was built, so identical inputs give an identical id.

Design, formats and failure handling

tam-bundle is C on libtam, linked statically, with its own version number in the public tamlinux-tools repository. Its manual page is tam-bundle(1): run man tam-bundle where it is installed, or read man/tam-bundle.1 in the repository. The approved design is docs/plans/tam-bundle.md there.

Exit status: 0 success, 1 refused or problems found, 2 usage, 3 switched but a post-install step failed, 4 an interrupted switch needs recover.

How it works

A slot holds current/, kept/<id>/ and, only during a switch, staging.<id>/, all on one filesystem. State lives in /var/lib/tam-bundle/<slot name>/ for a root-owned slot and under $XDG_STATE_HOME/tamlinux/tam-bundle/ otherwise: the lock, the intent file switch, a one-line-per-action log, the keep list, and recorded file status for fast checks.

  1. Stage. Under the slot's lock, write the intent file and sync it. Build staging.<id>/ from the bundle: a file whose hash equals the live file's is cloned from current/ with FICLONE where the filesystem supports it, others are copied and re-hashed. Bundle files are opened with openat2 and RESOLVE_BENEATH, so a link planted in a bundle cannot make a root switch read outside it. One syncfs puts the whole tree on disk before any of it is visible.
  2. Exchange. renameat2(staging, current, RENAME_EXCHANGE) swaps the two directories in one system call, then the slot directory is synced. A program that already has a file open keeps reading the old file.
  3. Record. The displaced tree becomes kept/<old id>/; the log line, file status and "previous" keep entry are written; the intent file is removed last.
  4. Post-install steps. Only names from a fixed list: user-units-reload, qml-cache-purge, shell-restart. A failed step does not undo the switch, because the files are already right and the step can be rerun with after.

Recovery reads the intent file and the live tree's own BUNDLE. If the live tree is still the "from" side, the switch is undone; if it is the "to" side, the switch is finished; if it is neither, nothing is touched and the command stops. Every command that changes the slot does this first, under the lock, because until then the bookkeeping is not trustworthy: after an interrupted back, the tree that was live sits in kept/ under the target's name, and pruning it unrecovered would delete the wrong tree. A dry run only says what recovery would do and exits with status 4. check, where and after read only the live tree, which is always whole, so they answer with a warning; status reports the interrupted switch with exit status 4.

The bundle hash is SHA-256 over BUNDLE without its hash and built lines, followed by MANIFEST. Every record is plain text with a format line; a newer format is refused with the version needed, and older formats keep being read so that rollback to an older release keeps working.

Building. A lock file names each component's repository and full commit. A recipe is data, never a script: build make, an optional output build-only for libraries other components link against, make-vars and after-build. Each commit is exported with git archive; make runs with PREFIX set to the slot's current path inside its own user and mount namespace at fixed paths, with SOURCE_DATE_EPOCH, LC_ALL=C and TZ=UTC, so the same lock gives the same bytes whatever the cache's location. With index man, the manual index is built into the bundle with man-db's mandb, so whatis and apropos match the pages and roll back with them.

Privilege. Run as a user on a root-owned slot, a changing command re-runs itself through /usr/bin/pkexec with its own absolute path; the user's waiting process then runs the session steps. Where no polkit agent runs, as on a text console, run it with sudo and then tam-bundle after in the graphical session.

Advanced usage

Build for the planned product slot from a lock file and local clones, inspect, then switch. Illustrative; it needs recipes and a lock file that no Tamlinux release ships yet.

tam-bundle build recipes tamlinux.lock -o /var/tmp/tamlinux-0.7.0 --version 0.7.0 --repos ~/src
tam-bundle verify /var/tmp/tamlinux-0.7.0
tam-bundle needs /var/tmp/tamlinux-0.7.0
tam-bundle --dry-run switch /var/tmp/tamlinux-0.7.0
tam-bundle switch /var/tmp/tamlinux-0.7.0

Why Tamlinux chose this

Tamlinux needs a coherent set of its own files built from exact commits, marked as one thing, installed as real files, recorded, and switchable with rollback. Nix and Home Manager do that today, but each installed file is a link into a store, Nix brings a build daemon and sockets that Tamlinux otherwise avoids, and a switch evaluates a whole language. Most of what Nix offers, such as complete dependency closures, binary caches and remote builders, Tamlinux does not need, because third-party software comes from the distribution. tam-bundle keeps the parts worth keeping (content hashes, exact pins, whole-tree generations, rollback, recipes as data) and drops the rest. It does not depend on pacman or xbps internals, so the same bundle format can follow Tamlinux to another rootstock.

Edge cases and failure modes

  • One filesystem. The exchange fails with EXDEV across filesystems, and on Btrfs the trees must share a subvolume. Keeping everything under one slot directory guarantees that.
  • Disk use. On Btrfs, unchanged files are clones and a kept tree costs only what differs. Elsewhere each switch copies the tree and each kept tree costs its full size. prune sizes on Btrfs overstate what comes back, because shared extents are freed only when no tree uses them.
  • Long-running programs. A program that opens files by path later, such as a desktop shell loading QML, would read the new tree while running old code. That is what shell-restart is for.
  • Hand edits. check trusts unchanged size, inode, modification time and change time; --full hashes everything. Running mandb as root with the live tree on the manual path rewrites the index, which check then reports as edited.
  • Power loss is not simulated by the tests; correctness relies on the staging syncfs and the directory syncs. Interruption at every step, and SIGKILL at random moments, are tested.
  • Builds need unprivileged user namespaces; where they are turned off, build stops and says so.
  • Host. A bundle built for another host is refused, as is one whose native needs are missing.

Check yourself

Why is the intent file removed last, rather than first?

Its presence is what tells a later command that a switch may be incomplete. Combined with the live tree's own BUNDLE, it decides whether to undo or finish. Removing it first would leave a crash between the exchange and the bookkeeping with no record that bookkeeping was owed.

What would break if tam-bundle itself were shipped inside the product bundle it installs?

A bundle with a broken tam-bundle could switch in, after which the tool needed to roll it back would be the broken one. Shipping it in a separate native package keeps the rollback path independent of what it rolls back.

Why are components built with PREFIX set to current rather than to their kept or staging path?

Paths compiled into a program then always point at the live location. A kept tree is only ever used after it has been exchanged back into current/, so its compiled paths are correct again at that moment, and nothing needs rewriting on rollback.
