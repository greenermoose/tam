Compiler sanitizers, AddressSanitizer, and memory safety in C

This page explains what compiler sanitizers are, how AddressSanitizer (ASan) detects memory errors at runtime, and how native C programs use sanitizers to prevent crashes and security vulnerabilities.

Writing high-performance native systems software in C provides deterministic speed and low memory use, but places full responsibility for memory management on the programmer. In standard C, mistakes such as writing past the boundary of a buffer, using memory after freeing it, or dereferencing invalid pointers do not always crash immediately; they often silently corrupt data. Compiler sanitizers instrument code at build time so runtime errors are detected and diagnosed the instant they occur.

What are compiler sanitizers?

When you run a native command in Tamlinux, the program executes direct CPU instructions and manages its own memory without an interpreter or background garbage collector. Compiler sanitizers are built-in diagnostic tools that monitor how a program touches memory while it runs, catching mistakes immediately during testing before software is released.

Why it matters

In lower-level programming languages like C, a single mistake — such as storing eleven items in a ten-slot list or reading from memory that was already released — can cause subtle bugs. Without sanitizers, these mistakes might remain hidden for months, only causing a crash when special data is encountered or creating security vulnerabilities that attackers could exploit. Sanitizers make invisible memory bugs visible and pinpoint their exact cause.

How to think about it

Think of writing C code like building a high-speed plumbing system. Under normal production, water flows directly through pipes with zero obstruction for maximum speed. Testing with a sanitizer is like injecting bright fluorescent dye into the water and placing sensors at every joint during a factory pressure test: if any pipe leaks or exceeds its boundary by even a single drop, an alarm sounds instantly and the inspector knows the exact fitting that failed.

New words

AddressSanitizer (ASan)
A compiler tool that instruments memory allocations and pointers to catch buffer overflows, use-after-free, and memory corruption during execution.
Sanitizer
A tool built into modern compilers (like GCC and Clang) that inserts runtime checks into a program to catch errors, leaks, or undefined behavior.
Buffer overflow
A condition where a program writes data outside the allocated boundary of a memory block, risking silent data corruption or security breaches.
Compiler flag
A command-line switch passed to GCC or Clang (such as -fsanitize=address) to enable specific language standards, optimizations, or diagnostic instrumentation.

Compile and verify programs with AddressSanitizer

Goal: you will be able to compile a standalone C program with AddressSanitizer flags, run the instrumented binary to detect an invalid memory access, and read the resulting diagnostic report to find the bug.

Before you start: open a terminal window (The Shell and Streams). Native compilation requires standard build tools (gcc or clang) from the base system. All examples in this section use temporary scratch files in user space and do not modify any system configuration.

New to this? To enable AddressSanitizer, pass -fsanitize=address to both the compilation step and the linking step. Always include -g to embed debugging symbols so ASan reports include exact file names and source line numbers.

Worked example: detect a heap buffer overflow with AddressSanitizer

Create a small test file in a temporary scratch directory that allocates space for 10 integers but writes past the end of the buffer:

$ cat << 'EOF' > /tmp/test_overflow.c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    int *arr = malloc(10 * sizeof(int));
    if (!arr) return 1;
    int idx = argc + 10;
    arr[idx] = 42;
    printf("Value: %d\n", arr[idx]);
    free(arr);
    return 0;
}
EOF
$ gcc -std=c11 -fsanitize=address -g /tmp/test_overflow.c -o /tmp/test_overflow
$ /tmp/test_overflow

What just happened

  1. gcc -fsanitize=address -g compiled the C source and linked it against the AddressSanitizer runtime library (libasan).
  2. The program allocated 40 bytes (10 integers × 4 bytes each) on the heap using malloc. ASan placed an invisible poisoned "redzone" around this allocation.
  3. When line 8 attempted to write to arr[11] (offset 44, which is 4 bytes beyond the 40-byte allocation), the compiler-inlined check saw that the target address fell within the poisoned redzone.
  4. AddressSanitizer immediately aborted execution, preventing corrupted data from being read or written.
  5. The error report pinpointed the bug: a heap buffer overflow at line 8 during a 4-byte write, exactly 4 bytes after the 40-byte block allocated at line 5.

Try it

Test how AddressSanitizer catches a use-after-free error. Write a small program that frees a pointer and then attempts to read from it:

$ cat << 'EOF' > /tmp/test_uaf.c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *val = malloc(sizeof(int));
    *val = 100;
    free(val);
    printf("Value after free: %d\n", *val);
    return 0;
}
EOF
$ gcc -std=c11 -fsanitize=address -g /tmp/test_uaf.c -o /tmp/test_uaf
$ /tmp/test_uaf 2>&1 | grep -E "ERROR: AddressSanitizer|READ of size"
==ERROR: AddressSanitizer: heap-use-after-free on address ...
READ of size 4 at ...
$ rm -f /tmp/test_uaf.c /tmp/test_uaf

Observe how ASan identifies the bug as heap-use-after-free, showing both the line where the memory was freed and the line where the invalid read occurred.

If it goes wrong

unrecognized command-line option '-fsanitize=address'
Your compiler is too old or lacks sanitizer support. GCC 4.8 or later and Clang 3.1 or later support AddressSanitizer on x86-64 Linux.
ASan report shows addresses but no line numbers
You omitted the -g flag during compilation. Compile with -g to embed DWARF debugging symbols so ASan can resolve function names, file paths, and line numbers.
Program runs and prints without triggering ASan
The compiler optimizer may have eliminated the unused access or determined that a constant expression has no side effects. Ensure you compile with -O1 or -O0, or pass input via command-line arguments so the compiler cannot optimize away memory operations.

On Tamlinux: core utilities like the tam command and libtam foundational library are regularly verified with -fsanitize=address,undefined during development test runs. This ensures that command parsing, HTML rendering, terminal resizing, and PTY handling remain memory-safe and free from undefined behavior across all supported hardware.

Why must -fsanitize=address be passed to both the compile step and the link step?

The compile step inserts instrumentation instructions before every memory load and store, while the link step links the AddressSanitizer runtime library (libasan) and replaces standard memory allocators (malloc and free) with instrumented versions. Without linking libasan, unresolved symbol errors occur at link time.

How does AddressSanitizer differ from traditional static analysis like -Wall or cppcheck?

Static analysis inspects source code without running it, which cannot catch bugs that depend on runtime inputs, dynamic allocation sizes, or complex pointer aliasing. AddressSanitizer inspects actual memory accesses as the program runs, catching errors that only manifest under specific runtime conditions.

How AddressSanitizer works internally

AddressSanitizer achieves its high performance (~2× slowdown compared to 20–50× for Valgrind) through two primary architectural components:

  1. Shadow Memory Mapping: The virtual address space of the process is divided into application memory and shadow memory. Exactly one-eighth (12.5%) of the address space is reserved for shadow bytes. Every 8 bytes of application memory maps directly to 1 byte in shadow memory via a simple pointer calculation: 
    shadow_address = (app_address >> 3) + SHADOW_OFFSET;
    On x86-64 Linux, SHADOW_OFFSET is typically 0x7fff8000 or 0x00007fff8000. Each shadow byte encodes the state of its corresponding 8 application bytes:
    • 0x00: All 8 bytes are valid and addressable.
    • 0x01 to 0x07: Only the first k bytes are valid (partially addressable tail of a buffer).
    • Negative values (e.g. 0xfa, 0xf1, 0xfd): The memory is completely unaddressable (poisoned). Special byte values distinguish heap redzones (0xfa), stack redzones (0xf1), freed memory (0xfd), and global redzones (0xf9).
  2. Compile-Time Code Instrumentation: Before every memory read or write of size k at address addr, the compiler inserts a fast, inlined check: 
    byte = *( (addr >> 3) + SHADOW_OFFSET );
if (byte != 0 && ( (addr & 7) + k > byte )) {
    __asan_report_error(addr, k, is_write);
}
    Because the check involves only a shift, add, load, and branch, the CPU branch predictor evaluates it in 1–2 cycles on the common (valid) path.
  3. Redzones and Quarantine: The instrumented malloc surrounds every heap allocation with poisoned redzones (typically 16 to 128 bytes). When memory is released via free(), it is not immediately returned to the system allocator; instead, it is placed into a quarantine queue poisoned with 0xfd. This ensures that any subsequent use-after-free access will reliably hit poisoned memory even if other allocations occur immediately afterward.

Runtime environment options: ASAN_OPTIONS

You can control AddressSanitizer behavior without recompiling using the ASAN_OPTIONS environment variable:

$ ASAN_OPTIONS="detect_leaks=0:color=never:abort_on_error=1" ./my_program
OptionDefaultDescription
detect_leaks=0|11Enable or disable LeakSanitizer at program exit. Useful to disable when running inside containers where ptrace is restricted.
abort_on_error=0|10Call abort() instead of _exit() when an error occurs, enabling core dump generation for post-mortem debugging with GDB.
halt_on_error=0|11Halt on the first error. Setting to 0 allows the program to continue executing to detect multiple defects in one run.
quarantine_size_mb=N256Size of the quarantine queue in megabytes for tracking freed memory and catching use-after-free.
symbolize=0|11Demangle and symbolize stack frames using addr2line or an external symbolizer.

Combining sanitizers in development

For systems programming and library development, the recommended compilation flag combination combines AddressSanitizer with UndefinedBehaviorSanitizer:

$ gcc -std=c11 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -g -O1 main.c -o my_tool

This catches both physical memory violations (buffer overruns, use-after-free) and logical undefined behaviors (signed integer overflow, shift out of bounds, null pointer dereferences) in a single unified test run.

Why is AddressSanitizer incompatible with ThreadSanitizer in the same binary?

Both sanitizers require dedicated, conflicting shadow memory layouts and incompatible memory interception mechanisms. ASan uses shadow memory to record byte validity and redzones, whereas TSan uses shadow memory to record thread IDs and clock vectors for synchronization tracking. To test both memory safety and data races, projects maintain separate build targets.

Why does ASan quarantine freed memory rather than immediately returning it to the OS allocator?

If freed memory were immediately reused by another malloc call, a dangling pointer from the first allocation might read or write into the new allocation without triggering a memory fault. The quarantine queue keeps freed memory poisoned for a period of time, ensuring that use-after-free bugs reliably trigger an immediate crash report.
