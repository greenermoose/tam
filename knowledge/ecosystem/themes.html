Color systems, displays and desktop theming

This page explains how computer screens display colors and how desktop themes coordinate visual styling across different programs.

Unlike proprietary operating systems where a single setting controls the visual appearance of all software, a Unix-like desktop is an assembly of independent programs. Terminal emulators, code editors, UI toolkits like GTK and Qt, and desktop shells each store color palettes in their own configuration formats. Understanding how colors and themes work allows you to adjust visual contrast, avoid eye strain, and build robust, efficient desktop environments.

Coordinating colors across your desktop

Goal: you will be able to inspect the active Tamlinux theme, query individual color tokens, and verify that your desktop programs agree on color styling using read-only commands.

Why it matters: reading text on a computer screen for hours requires sufficient contrast between letters and their background. If a terminal window switches to a dark background while an editor remains bright white, or if an interface uses low-contrast gray text on dark gray panels, reading becomes exhausting. A theme coordinates these colors so every window feels coherent, readable, and predictable.

Before you start: open a terminal window. All commands in this section inspect active settings without changing any files.

The $ at the start of a command line represents your shell prompt. Do not type the $. Paths starting with ~ refer to your personal home directory (such as /home/alex).

Worked example: inspect the active theme

$ tam-theme-current
tamarack-dark

$ readlink ~/.local/state/tamlinux/current/theme
/home/alex/.local/state/tamlinux/theme-generations/tamarack-dark.4b1a8f...

$ tam-theme-color background
#131a15

$ tam-theme-color foreground
#e4ece6

Captured on a Tamlinux workstation. Your active theme and generation hashes will match your local configuration.

What just happened

  1. tam-theme-current reads the active theme name recorded in Tamlinux's state directory. The default theme is Tamarack Dark, a high-contrast dark green palette designed specifically for Tamlinux.
  2. readlink inspects the symbolic link at ~/.local/state/tamlinux/current/theme. Tamlinux points this link to an isolated, timestamped theme generation directory containing generated configuration files for all desktop applications.
  3. tam-theme-color extracts specific hexadecimal color values from the active palette, such as the dark background (#131a15) and the light foreground text (#e4ece6).

A theme is a coordinated set of colors, font assignments, and visual parameters (such as window borders and margins). A palette is the specific collection of colors used by a theme. In modern interface design, colors are defined as semantic tokens (such as “background”, “surface”, “primary”, or “danger”) rather than hardcoded RGB numbers, allowing software to adapt cleanly between light and dark modes.

Try it

Run these read-only commands to list all available themes and inspect the colors assigned to the active theme:

tam-theme-list
head -n 12 ~/.local/state/tamlinux/current/theme/colors.toml

The first command lists both bundled system themes (such as tamarack-dark and tamarack-light) and any personal themes installed under ~/.config/tamlinux/themes/. The second command displays the active color table generated for your session.

If it goes wrong

tam-theme-current: command not found
The Tamlinux command suite is not on your PATH. On a Tamlinux workstation, ensure your profile includes ~/.local/share/tamlinux/shell and ~/.nix-profile/bin.
Terminal colors do not match the desktop theme
The terminal emulator was launched before the theme was applied or has a personal configuration override in ~/.config/ that shadows the generated theme.
Text is hard to read due to low contrast
The display brightness or ambient room lighting may be mismatched with your current theme. Switch between dark and light variants using tam-theme-set tamarack-light or tam-theme-set tamarack-dark.

Decide your answer before you reveal it.

Why does Tamlinux store the active theme under ~/.local/state/ rather than directly editing application configs in place?

Storing the active theme in an isolated state directory and linking it allows Tamlinux to perform atomic theme switches and rollbacks. If a theme generation fails or is interrupted, the previous working theme remains intact without corrupting personal configuration files.

What is the difference between a raw hex color and a semantic color token?

A raw hex color (such as #131a15) specifies an exact red, green, and blue light intensity. A semantic token (such as “background” or “danger”) describes the role or purpose of that color in the user interface, allowing the actual color value to change across light and dark modes while keeping the interface logic intact.

Does changing a desktop theme change your personal document files?

No. The theme engine only updates application color schemes, stylesheets, and desktop state links. Personal documents, code repositories, and user files remain completely untouched.

Semantic token
A named design variable (such as “surface” or “accent”) that abstracts a color from its literal RGB value.

Displays, color science and Unix theming protocols

Goal: you will be able to explain the historical development of computer displays and colors, calculate WCAG contrast ratios, and trace how themes are delivered across Arch Linux and Void Linux.

History of computer displays and color in HCI

Early interactive computing in the 1950s and 1960s relied on radar screens and vector displays (such as the TX-0 and DEC PDP-1), where an electron beam traced lines directly between coordinate points. In the 1970s, raster-scan cathode-ray tubes (CRTs) became standard. These displays were monochrome, using specialized phosphor coatings on the inside of the glass tube:

  • P1 Phosphor (Green): Emitted light at 525 nanometers, closely aligning with the peak photopic sensitivity of the human eye (555 nm). Green phosphors allowed characters to be read comfortably at lower beam energies.
  • P4 Phosphor (White): Emitted a broad-spectrum bluish-white light, standard in early television sets and office word processors.
  • P3 and P40 Phosphors (Amber): Emitted light at 590–620 nanometers with longer persistence. In the early 1980s, European occupational health studies (particularly German ergonomics standards) recommended amber displays to reduce eye fatigue and screen flicker under fluorescent office lighting.

Because text terminals were monochrome, early visual emphasis relied on hardware character cell attributes: DEC VT100 terminals supported bold, reverse video, underline, and blinking. In 1976, the ECMA-48 standard (adopted in 1979 as ANSI X3.64) introduced Select Graphic Rendition (SGR) escape sequences. SGR codes 30–37 set text foreground to one of 8 base colors (black, red, green, yellow, blue, magenta, cyan, white), and 40–47 set the background. Pairing these with bold or bright attributes produced the classic 16-color ANSI terminal palette.

Personal computer graphics hardware evolved rapidly through the 1980s:

  • IBM CGA (1981): Supported 16 colors in text mode, but only 4 simultaneous colors in graphics mode from fixed hardware palettes.
  • IBM EGA (1984): Displayed 16 simultaneous colors chosen from a palette of 64 colors.
  • IBM VGA (1987): Introduced the 18-bit Video Graphics Array, displaying 256 simultaneous colors selected from a palette of 262,144 colors using an 8-bit Color Lookup Table (CLUT) inside the digital-to-analog converter (RAMDAC).
  • TrueColor (1990s): Eliminated color lookup tables by dedicating 24 bits per pixel (8 bits each for Red, Green, and Blue), producing 16,777,216 distinct colors.

In 1996, HP and Microsoft standardized sRGB (standard Red Green Blue), matching the color gamut and phosphor behavior of standard CRT monitors under typical office lighting (daylight white point at 6500 Kelvin). CRTs have a non-linear physical response: light intensity is proportional to input voltage raised to a power (with an exponent gamma around 2.2). Digital images and colors are therefore gamma-encoded to compress tonal data efficiently into 8 bits per channel, and must be linearized when computing physical light intensity.

Contrast calculation and accessibility

The human visual system does not perceive all light wavelengths with equal brightness. In 1931, the International Commission on Illumination (CIE) established standard color matching functions. The W3C Web Content Accessibility Guidelines (WCAG 2.1) use this color science to calculate the relative luminance of a color on a scale from 0.0 (pure black) to 1.0 (pure white):

  1. Convert 8-bit sRGB channel values (red, green, and blue numbers between 0 and 255) to floating-point ratios by dividing by 255.
  2. Linearize each channel to remove sRGB gamma encoding: 
      if C_srgb ≤ 0.04045:
      C_linear = C_srgb / 12.92
  else:
      C_linear = ((C_srgb + 0.055) / 1.055) ^ 2.4
  3. Calculate relative luminance using human photopic spectral sensitivity weights: 
      L = 0.2126 * R_linear + 0.7152 * G_linear + 0.0722 * B_linear
    Notice that green accounts for over 71% of perceived luminance, while blue accounts for only 7%.
  4. Calculate the contrast ratio between two colors with luminances L1 and L2 (where L1 is greater than L2): 
      Contrast Ratio = (L1 + 0.05) / (L2 + 0.05)

WCAG 2.1 requires a minimum contrast ratio of 4.5:1 for normal text (Level AA) and 7:1 for high-contrast accessibility (Level AAA). Tamlinux enforces this 4.5:1 mathematical threshold in its theme engine before any theme can be applied.

Mental model: the Unix theming pipeline

   Theme Token Definition (tamarack.toml)
               |
               v
   [Theme Engine (engine.py)]
     ├──> Validates WCAG Contrast (4.5:1 minimum)
     ├──> Generates Staged Theme Directory (~/.local/state/tamlinux/theme-generations/...)
     │     ├── colors.toml, foot.ini, alacritty.toml, gtk4.css, vscode.json
     └──> Atomic Directory Exchange (renameat2 RENAME_EXCHANGE)

         │           │           │             │

     [Foot/TTY]   [GTK 4]     [Qt/QML]     [Editors/Tools]
     (OSC escape  (Adaptive   (Quickshell  (VS Code, Claude,
      sequences)   CSS link)   theme IPC)   Pi, Obsidian)

In Unix, there is no kernel theming subsystem. Theming is federated:

  • Terminal Emulators: Updated via configuration files or dynamically via OSC (Operating System Command) escape sequences. For example, \e]10;#e4ece6\e\\ sets the terminal foreground color, and \e]11;#131a15\e\\ sets the background color.
  • GTK Toolkit: GTK 3 reads settings.ini and CSS files under ~/.config/gtk-3.0/gtk.css. GTK 4.20 introduced adaptive color scheme media queries (@media (prefers-color-scheme: dark)), allowing a single stylesheet to serve both dark and light modes.
  • Qt and QML: Qt applications read QPalette or use platform themes (such as qt5ct / qt6ct). The Tamlinux Quickshell desktop shell reads token values directly from generated QML service files.
  • XDG Desktop Portal: Modern Wayland compositors broadcast dark/light mode preferences across D-Bus via the org.freedesktop.portal.Settings interface using the color-scheme key (1 for dark, 2 for light).

Worked example: query contrast with Python

$ python3 -c '
def lum(c):
    vals = [int(c[i:i+2], 16)/255 for i in (1, 3, 5)]
    lin = [v/12.92 if v <= 0.04045 else ((v+0.055)/1.055)**2.4 for v in vals]
    return 0.2126*lin[0] + 0.7152*lin[1] + 0.0722*lin[2]
bg = lum("#131a15")
fg = lum("#e4ece6")
print("Tamarack Dark Contrast:", round((fg + 0.05) / (bg + 0.05), 2))
'
Tamarack Dark Contrast: 15.34

The calculation proves that Tamarack Dark delivers a contrast ratio of 15.34:1, far exceeding the 4.5:1 accessibility threshold.

Why does the human eye perceive green text as brighter than blue text with the exact same physical energy?

The human retina's photopic spectral sensitivity peaks around 555 nanometers (in the green spectrum). The CIE standard observer weights green at 71.52% of perceived luminance, while blue accounts for only 7.22%.

How does GTK 4.20 allow a single stylesheet to support both dark and light modes?

GTK 4.20 introduced support for the CSS @media (prefers-color-scheme: dark) and @media (prefers-color-scheme: light) media queries, allowing application styles to switch automatically when the desktop color scheme changes.

What challenge does Void Linux face with D-Bus session services compared to Arch Linux?

Void Linux does not use systemd user sessions, so D-Bus services cannot rely on systemd socket activation. The session D-Bus daemon must be explicitly started (typically via dbus-run-session or turnstile) and environment variables like DBUS_SESSION_BUS_ADDRESS must be manually propagated.

Tamlinux theme engine internals, transactional safety and future work

Goal: you will be able to dissect Tamlinux's theme engine, explain atomic directory exchange via Linux renameat2, inspect transactional journal rollbacks, and evaluate code optimizations to minimize runtime overhead.

Dissecting the Tamlinux theme engine

The Tamlinux theme subsystem is implemented in Python under the product repository in tamlinux/desktop/theme/engine.py. The engine is responsible for reading theme templates, generating application configuration files, ensuring WCAG contrast compliance, and publishing updates atomically.

1. Atomic directory exchange with renameat2

When switching themes, updating files one by one would leave the desktop in an inconsistent state where some applications read new colors while others read old ones. If the process is killed midway, the session is corrupted.

Tamlinux avoids this by building the entire theme directory inside a temporary staging location (stage) under ~/.local/state/tamlinux/theme-generations/. Once staging is complete, the engine performs an atomic directory exchange using the Linux renameat2 system call:

import ctypes

libc = ctypes.CDLL(None, use_errno=True)
rename = getattr(libc, 'renameat2', None)
# RENAME_EXCHANGE = 2
# Flags: exchange temporary directory and active destination directory atomically
result = rename(-100, os.fsencode(temporary), -100, os.fsencode(destination), 2)

The flag value 2 corresponds to RENAME_EXCHANGE (introduced in Linux kernel 3.15). The kernel guarantees that the directory swap is instantaneous. Any application opening a file in ~/.local/state/tamlinux/current/theme/ sees either the complete prior generation or the complete new generation—never an empty or partially generated directory.

2. Transactional journaling and rollback

Before any external application configuration is modified (such as GTK CSS, VS Code settings, or Obsidian vaults), the engine wraps the operation in a transaction manager (Journal class):

If an unhandled exception, syntax error, or process interrupt occurs during adapter execution, the transaction context manager intercepts the failure and invokes journal.restore(), returning all user configurations to their exact pre-transaction state.

3. Mathematical contrast enforcement

The engine enforces contrast rules at build time via tamarack_colors(). The algorithm calculates the luminance of every semantic token (foreground, muted, primary, accent, danger, info) against both background and surface:

def luminance(color):
    channels = [int(color[i:i+2], 16) / 255 for i in (1, 3, 5)]
    values = [v / 12.92 if v <= 0.04045 else ((v + 0.055) / 1.055) ** 2.4 for v in channels]
    return sum(a * b for a, b in zip(values, (0.2126, 0.7152, 0.0722)))

def contrast(a, b):
    low, high = sorted((luminance(a), luminance(b)))
    return (high + 0.05) / (low + 0.05)

for fg in ('foreground', 'muted', 'primary', 'accent', 'danger', 'info'):
    for bg in ('background', 'surface'):
        if contrast(tokens[fg], tokens[bg]) < 4.5:
            raise ValueError(f'Tamarack contrast fails for {fg} on {bg}')

Any token failing the 4.5:1 ratio halts execution before any file is written.

4. Direct binary PNG synthesis without dependencies

To avoid adding large dependencies (such as Pillow or ImageMagick) to the Tamlinux cultivar, the theme engine generates solid wallpaper PNGs and preview swatches directly using Python's standard struct and zlib libraries:

def solid_png(color):
    pixel = bytes.fromhex(color[1:])
    def chunk(kind, data):
        return struct.pack('!I', len(data)) + kind + data + struct.pack('!I', zlib.crc32(kind + data))
    return (b'\x89PNG\r\n\x1a\n'
            + chunk(b'IHDR', struct.pack('!IIBBBBB', 1, 1, 8, 2, 0, 0, 0))
            + chunk(b'IDAT', zlib.compress(b'\x00' + pixel))
            + chunk(b'IEND', b''))

This generates a valid 1×1 24-bit TrueColor PNG image with proper PNG headers, chunks, and CRC-32 checksums in under 100 microseconds.

Future work for smaller code and higher efficiency

The current Tamlinux theme system is robust, but there are multiple paths to make it leaner and more efficient:

  1. Consolidating Adapter Subprocesses: In the current implementation, applying a theme executes engine.py, which then loops through a list of adapters (ADAPTERS = ['foot', 'tmux', 'gnome', 'browser', 'pi', 'claude', 't3code', 'vscode', 'obsidian', 'keyboard']), invoking individual shell scripts (e.g. tam-theme-set-foot). Each script forks Python, bash, or sed. Integrating these adapters as internal generator functions inside the engine would eliminate over 20 process forks per theme change.
  2. Lightweight C Theme Engine: Python requires a ~30 MB memory footprint and several tenths of a second of interpreter startup time. The entire theme engine (reading TOML, performing WCAG contrast calculations, calling renameat2, and writing files) could be implemented in roughly 500 lines of standard C using POSIX APIs and a small JSON/TOML parser. This would reduce the memory footprint to under 1 MB and make theme switching nearly instantaneous.
  3. Daemonless Inotify File-Watch Architecture: Currently, the engine explicitly restarts or notifies applications via tam-restart-* and shell commands. In an event-driven architecture, applications and UI panels can watch ~/.local/state/tamlinux/current/theme using Linux inotify. When renameat2 swaps the directory, inotify triggers a directory modified event, allowing each process to reload its styling autonomously without central coordination scripts.
  4. Decoupling from dconf for Void Linux and Microkernels: The current engine checks dconf and refuses to run if GSettings backends are missing. For Void Linux and microkernel targets that do not use GNOME libraries, theming should rely strictly on XDG portal settings or static file symlinks, removing the hard dependency on D-Bus and dconf.

Check yourself

Decide your answer before you reveal it.

Why is renameat2 with RENAME_EXCHANGE superior to deleting an old directory and moving a new one in?

Deleting the old directory and moving the new one introduces a race window where the path does not exist. If any running application attempts to load an asset or read configuration during that window, it fails with a “No such file or directory” error. RENAME_EXCHANGE swaps the two directory inodes atomically in a single kernel operation, eliminating any missing-path window.

How does direct binary PNG generation in Python improve system leanness?

By using standard struct and zlib modules to write raw PNG chunks, Tamlinux generates solid wallpapers and color swatches without installing large third-party graphics libraries (like Pillow) or external image utilities (like ImageMagick), keeping the base rootstock and cultivar minimal.

What is the primary benefit of consolidating adapter shell scripts into the main engine?

It eliminates dozens of process forks (spawning shells, Python interpreters, and command-line utilities for each adapter), reducing disk I/O, CPU context switching, and theme application latency.
