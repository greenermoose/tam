Kernel and processes

This page explains the central program that helps every other program use the computer's hardware.

Meet the kernel and a process

Goal: you will be able to say what a kernel is and name a running process on your machine.

Why it matters: when something freezes, you need to know whether the problem is your program, a service, or the kernel that sits under both.

Before you start: open a terminal. The commands only read information.

Type only the text after the $. Do not type the dollar sign. Silence after some commands can mean success.

Worked example

$ uname -s
Linux
$ printf '%s\n' "$$"
12345

Captured on Arch Linux, 2026-11-02. Your process number will differ.

What just happened

  1. uname -s asked the kernel which kind of system it is; this Tamlinux rootstock answers Linux.
  2. $$ is the shell's own process ID: the number the kernel uses for that running program.

Try it

Run uname -r to see the kernel release string. Record it; do not change packages.

If it goes wrong

command not found
Confirm you are in a normal shell on Tamlinux; uname is part of the core system.

Check yourself

Is the kernel the same thing as a terminal window?

No. The kernel is the central privileged program. A terminal is a program (and window or console) that lets you talk to a shell.

What identifies a running program to the kernel?

Its process ID (PID), among other credentials.

New words

Kernel
Central software that manages hardware and processes.
Process
A running instance of a program.

Syscalls and drivers

Goal: separate a user program, a syscall, and a driver boundary.

Mental model

your program --> syscall --> kernel --> driver --> hardware

Programs ask the kernel for services (open a file, send a packet, map memory). Drivers are kernel code (or modules) that talk to devices. A fault can sit in the program, the kernel path, or the device.

Worked example

$ cat /proc/self/status | head -n 5
Name:	cat
Umask:	0022
State:	R (running)
...

Captured on Arch Linux, 2026-11-02. /proc is a kernel-provided view of process state.

Reading /proc is a userspace view exported by the kernel. It does not by itself prove hardware health.

Choosing

Symptom classFirst evidence
One app misbehavesThat process, its logs, reproduction
Many apps fail the same wayShared service, compositor, or kernel/driver
Machine locks hardKernel/oops evidence, SysRq policy, hardware

On Tamlinux: design comparisons of monolithic vs microkernel live in kernels. Today the rootstock kernel is Linux.

/proc is exported by the kernel for inspection.

Completion task

Classify a single-app hang versus a whole-machine lock using the table above.

Single-app hang starts with that process; whole-machine lock needs kernel/SysRq/hardware evidence.

Independent task

Read /proc/self/status and name two fields you understand.

Name and State are enough to start; leave unknown fields unmarked.

Troubleshooting

Do not unload kernel modules experimentally while learning.

Check yourself

Does a successful file open prove the disk is healthy forever?

No. It shows one successful path at that moment. Later I/O can still fail.

Identity, memory and failure isolation

The kernel schedules threads, isolates address spaces, and mediates devices. Process existence (kill -0) is not health. Open file descriptors can outlive path names. Module and driver faults in a monolithic kernel can take the whole system down; that cost is why Tamlinux watches microkernel research while shipping Linux today.

Explore: compare ps output with /proc/PID/exe for a long-running process after a package update of the same name.

Check yourself

Why can an updated on-disk binary leave a running process on old code?

The process keeps its mapped executable pages until it exits and is started again. Path lookup for a new start can see the new file while the old PID still runs the previous mapping.
