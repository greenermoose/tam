Error detection, correction, and channel reliability

This page explains why physical transmission channels corrupt digital data, how mathematical detection algorithms identify corrupted bits, and how forward error correction and retransmission protocols guarantee reliability across imperfect hardware.

In a purely theoretical world, a wire conveys 1s and 0s with mathematical perfection. In the physical universe, conductors pass through electromagnetic fields, radio waves encounter atmospheric moisture, and microscopic thermal fluctuations agitate electrons inside semiconductors. Communication engineering assumes that every physical medium is inherently hostile and lossy. By appending structured redundant bits to messages — ranging from simple parity bits to multi-dimensional Cyclic Redundancy Checks and Forward Error Correction codes — computers detect errors immediately or reconstruct damaged data in flight without retransmission.

Noise, corrupted bits, and parity verification

Goal: you will be able to explain how physical noise flips bits on communication lines, and calculate even and odd parity bits to detect single-bit errors.

Why it matters: computers control critical real-world systems, from banking transactions and hard drives to automotive brakes and medical monitors. If a cosmic ray, a nearby motor spark, or a loose connector cable causes a 0 to become a 1 unnoticed, a monetary transfer of $100 could silently become $10,000, or a machine code instruction could jump into unmapped memory and crash the kernel. Error detection provides the mathematical safety net that protects digital logic from physical reality.

Before you start: open a terminal window (The Shell and Streams). The commands in this section run standard Python one-liners to calculate parity on ASCII text.

New to this? Think of a parity bit like a quick count verification. If you pack a box with three apples and write "odd number of apples" on the outside tape, the recipient opens the box and counts them. If they count four apples (or two), they instantly know something went wrong during shipment, even without knowing which apple was damaged.

Worked example: calculate even and odd parity for ASCII characters

In standard 7-bit ASCII, the uppercase letter 'A' has binary code 1000001 (two 1s). The letter 'C' has binary code 1000011 (three 1s). Let us calculate the required parity bit for both:

$ python3 -c '
for char in ["A", "C"]:
    bits = f"{ord(char):07b}"
    ones = bits.count("1")
    even_p = 0 if ones % 2 == 0 else 1
    odd_p  = 1 if ones % 2 == 0 else 0
    print(f"Char: {char} | Bits: {bits} (ones: {ones}) | Even parity: {even_p} | Odd parity: {odd_p}")
'
Char: A | Bits: 1000001 (ones: 2) | Even parity: 0 | Odd parity: 1
Char: C | Bits: 1000011 (ones: 3) | Even parity: 1 | Odd parity: 0

Understanding the calculation:

  1. Even Parity Rule: The parity bit is chosen so that the total count of 1s in the complete frame (data bits + parity bit) is an even number. For 'A' (two 1s), parity is 0 (total remains 2). For 'C' (three 1s), parity is 1 (total becomes 4).
  2. Odd Parity Rule: The parity bit is chosen so that the total count of 1s is an odd number. For 'A' (two 1s), parity is 1 (total becomes 3). For 'C' (three 1s), parity is 0 (total remains 3).
  3. Receiver Verification: When the receiver receives the 8 bits, it counts the 1s. If even parity was agreed upon and the count arrives odd, the receiver immediately asserts a parity error flag.

Try it

Compute the parity bit for the lowercase character 'z' (binary 1111010, five 1s) under Even parity. Verify whether an incoming byte with binary 11110101 passes or fails an Even parity check:

$ python3 -c '
bits = "1111010"
ones = bits.count("1")
even_bit = 1 if ones % 2 != 0 else 0
incoming = "11110101"
valid = incoming.count("1") % 2 == 0
print(f"Calculated parity bit: {even_bit} | Incoming valid under Even Parity: {valid}")
'
Calculated parity bit: 1 | Incoming valid under Even Parity: True

If it goes wrong

If parity checking fails to catch an error, remember the fundamental limitation of single-bit parity:

  • The Double-Bit Blind Spot: If electrical noise is severe enough to flip two bits within the same byte (for example, 1000001 becomes 1000111), the number of 1s increases by two. The total count remains even, and the parity check reports that the corrupted byte is completely valid. Single-bit parity detects all single-bit errors, but fails completely on any even number of bit flips.

New words

  • Parity: An error-detection method where an extra binary bit is added to a data sequence to ensure the total number of set bits (1s) is always even or always odd.
  • Bit Flip: An unintentional change in the state of a digital bit from 0 to 1, or 1 to 0, caused by electromagnetic interference, thermal noise, or voltage fluctuations.
  • Payload: The actual meaningful data being transmitted, excluding synchronization bits, headers, and error check codes.

A serial sensor transmits the 7-bit ASCII character 'M' (binary 1001101) using Even parity. What value should the transmitter assign to the parity bit?

The parity bit must be 0. Counting the 1s in 1001101 yields four 1s. Since 4 is already an even number, adding a parity bit of 0 keeps the total count even (four 1s).

Why can simple single-bit parity not detect two simultaneous bit flips in the same character?

Because flipping two bits either increases the count of 1s by 2, decreases it by 2, or keeps it unchanged (if one 0 becomes 1 and one 1 becomes 0). In all three cases, the even/odd mathematical parity of the total sum remains unchanged, completely fooling the receiver's parity check.

Next step

Single-bit parity is sufficient for low-speed serial links, but high-throughput storage and network packets require robust algorithms. In the next section, you will learn how Cyclic Redundancy Checks (CRCs) catch burst errors and how ARQ protocols retransmit lost packets.

Checksums, Cyclic Redundancy Checks (CRC), and ARQ retransmission

Goal: you will be able to implement internet checksums, explain polynomial Cyclic Redundancy Checks (CRC-16 and CRC-32), inspect kernel serial error counters, and analyze Automatic Repeat reQuest (ARQ) retransmission mechanisms.

Mental model: Moving beyond simple parity requires treating data mathematically as long numbers or algebraic polynomials. An Internet Checksum treats data bytes as a series of 16-bit integers and sums them up, appending the inverted total. A Cyclic Redundancy Check goes further: it treats the entire message stream as one giant binary polynomial and divides it by a fixed prime divisor polynomial using modulo-2 arithmetic. The remainder of that division is appended to the packet. If even a single bit or burst of consecutive bits is corrupted along the wire, dividing the received message by the generator polynomial yields a non-zero remainder, instantly exposing the corruption.

Worked example: compute a CRC-32 checksum in Python

Modern Ethernet frames, Wi-Fi packets, SATA storage transfers, and PNG image files use CRC-32 to verify data integrity. The standard IEEE 802.3 generator polynomial produces a 32-bit (4-byte) hexadecimal hash code:

$ python3 -c '
import zlib
msg1 = b"Tamlinux serial bus frame 001"
msg2 = b"Tamlinux serial bus frame 002"  # only one character changed
crc1 = zlib.crc32(msg1)
crc2 = zlib.crc32(msg2)
print(f"Message 1 CRC-32: {crc1:#010x}")
print(f"Message 2 CRC-32: {crc2:#010x}")
'
Message 1 CRC-32: 0x933094c9
Message 2 CRC-32: 0x072d637b

Notice the avalanche effect: altering a single bit in the payload completely scrambles the resulting 32-bit CRC remainder. A receiver recalculating the CRC-32 upon receipt and comparing it against the appended 4 bytes will detect burst errors up to 32 bits long with 100% mathematical certainty, and random errors with a failure rate of less than one in 4.29 billion (1 / 2^32).

Explain the physical difference between an Overrun Error (oe) and a Parity Error (pe). Which one points to a bad cable, and which one points to slow software?

A Parity Error (pe) indicates electrical signal corruption along the physical cable: electrical noise or voltage sag flipped a bit in flight, causing the received parity bit to mismatch the data payload. An Overrun Error (oe) indicates slow software or excessive CPU latency: new character bytes arrived at the hardware UART FIFO buffer before the operating system kernel or user application read the previous bytes, forcing the UART chip to overwrite unread data. Thus, pe indicates cable/signaling failure, while oe indicates buffer starvation or processing bottlenecks.

Automatic Repeat reQuest (ARQ) protocols

Detecting an error is only half the battle; the communication system must recover from it. Most networks implement Automatic Repeat reQuest (ARQ) protocols:

  1. Stop-and-Wait ARQ: The transmitter sends one packet and pauses. It starts a retransmission timer. The receiver verifies the CRC; if valid, it returns an Acknowledgment (ACK). If corrupted, it returns a Negative Acknowledgment (NAK) or drops the packet. The transmitter sends the next packet only upon receiving the ACK. If the timer expires before an ACK arrives, the transmitter re-sends the packet.
    • Limitation: Massive throughput penalty on long-distance or high-latency links, as the channel sits idle waiting for round-trip travel time.
  2. Go-Back-N ARQ: The transmitter uses a sliding window to send multiple packets (e.g. packets 1 through 7) without waiting for individual ACKs. If packet 3 is corrupted and the receiver returns a NAK for 3, the transmitter rewinds and retransmits all packets starting from packet 3 (packets 3, 4, 5, 6, 7), even if packets 4 through 7 were received cleanly.
  3. Selective Repeat ARQ: The most efficient sliding window protocol. The receiver buffers subsequent out-of-order packets (4, 5, 6, 7) into a local queue and specifically requests retransmission of only damaged packet 3. The transmitter resends only packet 3, saving enormous bandwidth. Used by TCP and modern Wi-Fi / LTE MAC layers.

Why does CRC-32 detect burst errors far more effectively than an Internet 16-bit additive checksum?

An additive checksum simply sums numbers together; if one bit flips from 0 to 1 and another bit in the same position flips from 1 to 0 in an adjacent byte, the mathematical sum remains completely unchanged. A CRC uses non-linear binary polynomial division (modulo-2 arithmetic). Every bit position influences multiple positions in the remainder, ensuring that burst errors up to the degree of the generator polynomial (32 bits) cannot cancel each other out.

In high-latency satellite communication, why is Selective Repeat ARQ vastly superior to Stop-and-Wait ARQ?

In satellite communication, round-trip signal propagation delay can exceed 500 milliseconds. Under Stop-and-Wait, the transmitter must send one packet and sit idle for half a second waiting for an ACK, collapsing channel throughput to a tiny fraction of its theoretical capacity. Selective Repeat continuously streams packets to fill the bandwidth-delay product, and only retransmits the specific damaged frames without pausing or discarding healthy packets.

How it works: Coding Theory and Forward Error Correction (FEC)

ARQ protocols provide reliability by retransmitting bad packets. However, in real-time video streaming, deep-space communication (where a round-trip delay to Mars takes 30 minutes), or multi-gigabit server memory buses, retransmission is impossible or unacceptably slow. Forward Error Correction (FEC) solves this problem by adding structured mathematical redundancy that allows the receiver not only to detect an error, but to correct it immediately on the fly without contacting the sender.

  1. Hamming Distance (d_min): The Hamming distance between two binary codewords is the number of bit positions in which they differ. Richard Hamming established fundamental mathematical theorems governing coding distance:
    • To detect e bit errors, a code must have a minimum Hamming distance of: 
        d_min >= e + 1
    • To correct t bit errors, a code must have a minimum Hamming distance of: 
        d_min >= 2 * t + 1
    Because valid codewords are separated by at least 2*t + 1 bits of difference in multidimensional vector space, if fewer than t bits flip, the corrupted codeword is still closer to the original codeword than to any other valid codeword, allowing unambiguous geometric correction.
  2. The Hamming(7,4) Code: Takes 4 data bits (d1, d2, d3, d4) and generates 3 parity bits (p1, p2, p3) to create a 7-bit codeword. The parity bits are placed at bit positions that are powers of 2 (positions 1, 2, and 4), covering overlapping subsets of the data bits:
    • p1 (position 1) covers positions 1, 3, 5, 7.
    • p2 (position 2) covers positions 2, 3, 6, 7.
    • p3 (position 4) covers positions 4, 5, 6, 7.
  3. Syndrome Decoding: When the 7-bit codeword is received, the receiver computes three syndrome bits (s1, s2, s3) by recalculating the parity across the respective subsets.
    • If (s3, s2, s1) == (0, 0, 0), no error occurred.
    • If (s3, s2, s1) != (0, 0, 0), the binary value of the syndrome directly points to the exact bit position (from 1 to 7) that was inverted! The receiver simply flips that bit back, perfectly restoring the original data.

Bit Error Rate (BER)

In physical link engineering, channel quality is quantified by the Bit Error Rate (BER):

BER = Errored_Bits / Total_Bits_Transmitted
  • Standard enterprise copper Ethernet links target a pre-FEC BER of less than 10^-12 (fewer than one error in one trillion bits).
  • Ultra-high-speed PCIe Gen 6 links operating with PAM-4 multi-level signaling operate with a raw pre-FEC BER of 10^-5 to 10^-6. Without FEC, such a link would fail instantly. By applying low-latency FEC hardware decoding at the physical layer, the post-FEC BER is crushed down to less than 10^-27, delivering decades of error-free operation.

Why Tamlinux chose this

Tamlinux prioritizes mathematical verifiability and fault isolation across its system software stack. In high-reliability computing, silent data corruption (cosmic-ray bit flips or degrading transmission lines) is far more dangerous than an outright system panic. By leveraging kernel error counters, hardware ECC reporting via EDAC (Error Detection and Correction), and deterministic checksum algorithms across storage and network layers, Tamlinux ensures that physical channel degradations are exposed to systems operators before data loss occurs.

Edge cases and failure modes

  • Hamming SECDED Triple-Bit Error: A Standard SECDED (Single Error Correction, Double Error Detection) Hamming code with d_min = 4 correctly detects double-bit errors and corrects single-bit errors. However, if three bits flip simultaneously, the syndrome vector can masquerade as a single-bit error pointing to an innocent bit, causing the decoder to flip the wrong bit and silently corrupt data (miscorrection).
  • CRC Collision Aliasing: While CRC-32 detects all single-burst errors up to 32 bits long, a burst error longer than 32 bits has a 1 in 2^32 probability of producing the exact same remainder as the original data. In mission-critical storage, secondary checksums (e.g. SHA-256 in file systems like ZFS or btrfs) prevent CRC collision aliasing.
  • Stop-and-Wait ACK Loss Deadlock: If a transmitter sends a packet and the receiver replies with an ACK, but the ACK packet itself is destroyed by electrical noise along the return wire, the transmitter will time out and retransmit the packet. The receiver must maintain sequence numbers (0 and 1) to recognize that the second packet is a duplicate, rather than appending duplicate data to the application stream.

Explore

Simulate Hamming(7,4) syndrome error correction directly in Python. Observe how flipping bit 5 in a 7-bit codeword causes the syndrome vector to evaluate to binary 5 (101), identifying and fixing the corrupted bit:

$ python3 -c '
# 4 data bits: d = [1, 0, 1, 1] (placed at positions 3, 5, 6, 7)
d1, d2, d3, d4 = 1, 0, 1, 1
p1 = d1 ^ d2 ^ d4  # covers 1, 3, 5, 7
p2 = d1 ^ d3 ^ d4  # covers 2, 3, 6, 7
p3 = d2 ^ d3 ^ d4  # covers 4, 5, 6, 7
codeword = [p1, p2, d1, p3, d2, d3, d4]
print(f"Transmitted codeword: {codeword}")

# Corrupt bit at position 5 (index 4)
received = list(codeword)
received[4] ^= 1
print(f"Received (corrupted at pos 5): {received}")

# Calculate syndrome bits
s1 = received[0] ^ received[2] ^ received[4] ^ received[6]
s2 = received[1] ^ received[2] ^ received[5] ^ received[6]
s3 = received[3] ^ received[4] ^ received[5] ^ received[6]
syndrome = (s3 << 2) | (s2 << 1) | s1
print(f"Calculated syndrome: {syndrome} (binary: {syndrome:03b})")
if syndrome != 0:
    received[syndrome - 1] ^= 1
    print(f"Corrected codeword: {received}")
'
Transmitted codeword: [0, 1, 1, 0, 0, 1, 1]
Received (corrupted at pos 5): [0, 1, 1, 0, 1, 1, 1]
Calculated syndrome: 5 (binary: 101)
Corrected codeword: [0, 1, 1, 0, 0, 1, 1]

If a code has a minimum Hamming distance of d_min = 5, how many bit errors can it guarantee to correct, and how many can it guarantee to detect?

Using the Hamming distance formulas: 1. To correct t errors, d_min >= 2*t + 1. With d_min = 5, 2*t + 1 <= 5 gives t = 2. The code can guarantee correction of up to 2 bit errors. 2. If used for detection only, d_min >= e + 1 gives e = 4. The code can guarantee detection of up to 4 bit errors without correction.
