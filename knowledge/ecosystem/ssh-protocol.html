The SSH Protocol Internals

This page explains how the Secure Shell (SSH) protocol establishes an encrypted, mutually authenticated tunnel for remote terminals and file transfers.

Proving both sides before opening a remote terminal

When you connect to another computer with SSH, two separate checks happen before you ever see a shell prompt: your computer checks that it is talking to the real remote server, and the server checks that you are an authorized user using your SSH key.

Why it matters

Unlike websites, personal servers and lab machines usually do not have commercial X.509 certificates signed by a browser certificate authority. Instead, SSH remembers each server's public host key the first time you connect—a model called Trust On First Use (TOFU)—and warns you loudly if that key ever changes unexpectedly.

How to think about it

Think of SSH as a two-key lockbox inside an armored pipe: first, both machines build the armored pipe and check the server's permanent fingerprint against your saved address book (~/.ssh/known_hosts). Second, once the pipe is sealed, you prove your identity by signing a fresh challenge with your private key—never sending the private key over the wire.

New words

SSH key
An asymmetric key pair used by SSH to authenticate users or identify host machines.
Forward secrecy
Deriving temporary per-session keys so stolen long-term keys cannot decrypt past SSH recordings.

Inspecting OpenSSH key-exchange and cipher algorithms

Goal: you will be able to query the key-exchange (KEX), cipher, and MAC algorithms supported by OpenSSH on your workstation and see how ssh -G resolves client defaults without opening a connection.

Before you start: ssh -Q and ssh -G are completely read-only and never contact a remote host.

What just happened

  1. ssh -Q kex showed both classical (curve25519-sha256) and post-quantum hybrid key exchanges (mlkem768x25519-sha256, sntrup761x25519-sha512).
  2. ssh -G localhost printed the exact preference order your client proposes in SSH_MSG_KEXINIT, preferring AEAD ciphers (chacha20-poly1305@openssh.com, AES-GCM) and Encrypt-then-MAC (-etm) modes.

Try it

Run ssh-keygen -l -f ~/.ssh/id_ed25519.pub (if you have a key) or ssh -vvv localhost true 2>&1 | head -n 30 (only if sshd is enabled) to see the key-exchange negotiation in action. For practical setup and hardening, see SSH keys and remote access.

If it goes wrong

WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
Either the server was legitimately reinstalled/rekeyed, or an active attacker is intercepting the connection. Verify the new host key fingerprint out-of-band before removing the old entry with ssh-keygen -R hostname.
HashKnownHosts yes makes ~/.ssh/known_hosts unreadable
OpenSSH hashes hostnames with HMAC-SHA1 in known_hosts so an attacker who steals your laptop cannot read a list of servers you connect to. Use ssh-keygen -F hostname to look up a host.

On Tamlinux, tam-setup-security-sshd writes drop-in 10-tamlinux-hardening.conf to disable password logins after adding an authorized key, keeping incoming SSH off by default on laptops until explicitly enabled.

Check yourself

Decide your answer before you reveal it.

What is the security weakness of Trust On First Use (TOFU) in SSH?

TOFU detects key changes on all future connections, but if an active attacker intercepts your very first connection when the host key is unknown, you must verify the displayed fingerprint out-of-band (or use SSHFP DNSSEC / SSH certificates) to spot the impersonation.

Why do modern OpenSSH configurations prefer -etm MACs or AEAD ciphers like chacha20-poly1305@openssh.com?

Encrypt-then-MAC and AEAD authenticate the ciphertext (including the encrypted packet length) before decrypting, preventing chosen-ciphertext length-oracle attacks against unauthenticated CBC streams.

RFC 4251–4254 layers, exchange hash binding, and Terrapin

Reference: SSH-2 is a three-layer protocol over TCP: (1) Transport Layer (RFC 4253), (2) User Authentication Protocol (RFC 4252), and (3) Connection Protocol (RFC 4254).

+-------------------------------------------------------------+
| Connection Layer (RFC 4254): Multiplexed Channels           |
|   PTYs, shells, SFTP, TCP port forwarding, agent forwarding |
+-------------------------------------------------------------+
| User Authentication (RFC 4252): "ssh-userauth"              |
|   publickey (signs session_id), sk-ssh-ed25519 (FIDO2)      |
+-------------------------------------------------------------+
| Transport Layer (RFC 4253): Binary Packet Protocol          |
|   Version exchange -> KEXINIT -> ECDH/PQ-Hybrid -> NEWKEYS  |
+-------------------------------------------------------------+

How it works: Transport KEX, Session ID binding, and UserAuth

Binary Packet Protocol & KEX: After exchanging plaintext version banners (SSH-2.0-...), both sides send SSH_MSG_KEXINIT listing algorithm preferences and a 16-byte random cookie. In ephemeral ECDH / hybrid KEX (e.g., mlkem768x25519-sha256), client and server exchange ephemeral public values Q_C, Q_S, compute shared secret K, and compute the exchange hash:

H = SHA-256(V_C || V_S || I_C || I_S || K_S || Q_C || Q_S || K)

where V_C, V_S are version strings, I_C, I_S are full KEXINIT payloads, and K_S is the server's long-term host public key. The server signs H with its host private key, authenticating both the ephemeral exchange and the algorithm negotiation transcript. The first exchange hash H becomes the permanent session identifier (session_id), and encryption/integrity keys are derived as Hash(K || H || "A".."F" || session_id).

User Authentication Binding: Under publickey authentication, the client signs a structured payload containing session_id || SSH_MSG_USERAUTH_REQUEST || user || "ssh-connection" || "publickey" || TRUE || alg || pubkey. Binding the signature to session_id prevents cross-session signature replay even if an attacker intercepts a legitimate authentication attempt.

Edge cases and failure modes

  • Terrapin Prefix-Truncation Attack (CVE-2023-48795): Because SSH packet sequence numbers reset or increment predictably across NEWKEYS, an active MITM could inject or drop packets during plaintext KEX (e.g., stripping SSH_MSG_EXT_INFO to disable signature-algorithm extensions) while keeping ChaCha20-Poly1305 or CBC-EtM sequence counters aligned. OpenSSH and peers mitigated this with strict-kex (kex-strict-c-v00@openssh.com), which forbids extraneous packets during KEX and resets sequence numbers to zero upon NEWKEYS.
  • ssh-agent forwarding hijacking: Forwarding SSH_AUTH_SOCK (ssh -A) exposes a Unix socket on the remote host; any root user or compromised process on that remote host can request signatures from your local agent for the lifetime of the session. Prefer ProxyJump (ssh -J), where the local client authenticates end-to-end without exposing the agent socket.

Check yourself

Why is SSH's publickey authentication signature computed over session_id rather than just a fresh server nonce?

session_id is the exchange hash H of the entire Transport Layer handshake (version strings, KEXINIT lists, server host key K_S, ephemeral shares, and shared secret K). Signing session_id cryptographically binds the client's authentication proof to the exact server host key and encrypted channel, preventing an attacker from relaying a client's signature to a different server or MITM session.
