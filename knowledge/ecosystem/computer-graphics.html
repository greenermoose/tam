Computer graphics and the rendering pipeline

This page explains how computers create, store, and display visual images on a screen.

At its heart, computer graphics bridges abstract mathematical models and physical light emitted by a monitor. Whether rendering a terminal window, a vector font, or a three-dimensional landscape, the computer converts visual descriptions into numbers stored in memory. Understanding this rendering pipeline reveals how pixels are formed, why framebuffers are fundamental, and how modern graphics software coordinates with hardware accelerators.

What is computer graphics?

Every visual element on your screen—every character of text, window border, and icon—is composed of thousands or millions of tiny, colored dots called pixels. When an image appears blurry, when a game stutters, or when a display looks stretched, the issue often traces back to how pixels and memory resolutions are configured. Knowing how your computer stores pixel data helps you troubleshoot display glitches and configure desktop scaling properly.

Framebuffer
A dedicated memory buffer that stores the exact binary color values of every pixel on a screen.
Color depth
The number of bits dedicated to representing the color of a single pixel (such as 8-bit, 24-bit, or 32-bit).

Computer graphics fall into two fundamental paradigms: vector graphics and raster graphics. Vector graphics represent images mathematically using geometric formulas (coordinates, lines, curves, and fills), as seen in SVG files, PostScript printers, and TrueType fonts. Raster graphics represent images as explicit matrices of colored pixels, as seen in PNGs, JPEGs, and the final monitor image. The bridge between the two is rasterization: evaluating which pixels belong inside each geometric shape.

Worked example: query screen resolution and framebuffer parameters

$ cat /sys/class/graphics/fb0/virtual_size
1920,1080

$ cat /sys/class/graphics/fb0/bits_per_pixel
32

$ cat /sys/class/graphics/fb0/name
amdgpudrmfb

Captured on a Tamlinux workstation, 2026-11-01. Your screen resolution and graphics driver name will reflect your specific hardware.

What just happened

  1. virtual_size reports the dimensions of the active framebuffer: 1920 horizontal pixels by 1080 vertical pixels (standard Full HD resolution).
  2. bits_per_pixel shows that the system allocates 32 bits (4 bytes) of memory for each pixel on the screen: 8 bits for Red, 8 bits for Green, 8 bits for Blue, and 8 bits reserved for transparency (Alpha) or memory alignment.
  3. name identifies the kernel framebuffer driver managing this surface: amdgpudrmfb, the Linux Direct Rendering Manager framebuffer for AMD graphics hardware.

A pixel (short for “picture element”) is the smallest addressable unit of color on a digital display. A framebuffer is the designated chunk of memory holding the color values for all pixels. For a 1920 × 1080 screen using 32-bit color, the framebuffer requires exactly 1920 × 1080 × 4 bytes = 8,294,400 bytes (approximately 8 megabytes) of memory for a single complete image.

Try it

Calculate the memory footprint of your display. Multiply your screen width by its height, then multiply by the bytes per pixel (typically 4 for 32-bit color). Divide by 1,048,576 to find the size in megabytes (MB).

If it goes wrong

/sys/class/graphics/fb0: No such file or directory
Your system may be running a pure DRM/KMS kernel driver without legacy fbdev emulation enabled. Check display outputs directly with ls -l /sys/class/drm/.
Resolution appears smaller than your monitor
The display may be running in a fallback low-resolution mode or using desktop scaling. Check compositor status with wlr-randr or hyprctl monitors.

On Tamlinux: the desktop relies on the Wayland protocol, which guarantees tear-free rendering by requiring clients to commit complete frame buffers before the compositor presents them to the display hardware. For older machines lacking hardware 3D support, wlroots compositors can render on the CPU using pixman (WLR_RENDERER=pixman), allowing Tamlinux to run on aging hardware while retaining responsiveness.

What is the difference between a pixel and a framebuffer?

A pixel is an individual dot of light on the physical screen (or a single color coordinate). A framebuffer is the region of computer memory that holds the numerical color values for every pixel on the entire screen.

How many distinct colors can a 24-bit TrueColor pixel represent?

With 8 bits for Red, 8 bits for Green, and 8 bits for Blue, each primary channel has 256 possible intensity levels (2 to the 8th power). Multiplying 256 × 256 × 256 yields 16,777,216 distinct possible colors.

Why does a 32-bit color mode use 4 bytes per pixel if human eyes only see red, green, and blue light?

The extra 8 bits either store an Alpha (transparency) channel for window blending, or act as padding so that each pixel aligns to a natural 32-bit memory boundary, allowing CPU and memory controllers to transfer pixels faster.

How it works: Stride, pitch, and memory alignment

A framebuffer in memory is not a continuous, unbroken grid. Instead, each horizontal scanline must often align to specific hardware memory boundaries (such as 64-byte or 256-byte cache line multiples) to optimize memory bus bursts:

  1. Pitch (Stride): The pitch is the number of actual bytes allocated in memory for one single row of pixels, including any padding bytes added to satisfy hardware alignment requirements. If a 1920-pixel wide screen uses 4 bytes per pixel, its minimum row size is 7,680 bytes. If the graphics hardware requires 256-byte alignment, the pitch becomes 7,680 bytes (7,680 is evenly divisible by 256). If the resolution were 1366 × 768, 1366 × 4 = 5,464 bytes; padding rounds the pitch up to 5,632 bytes.
  2. Pixel Address Formula: To calculate the memory address of a pixel at coordinate (x, y): 
      Address = Framebuffer_Base + (y * Pitch) + (x * Bytes_Per_Pixel)
    Operating systems and compositors map this region using mmap() or pass memory handles directly to GPU hardware controllers via DMA buffers (dma-buf).
  3. Double-Buffering and Page Flipping: If an application drew directly into the active scanout framebuffer, the monitor's raster beam would display partial drawings mid-render, causing visual tearing. Modern graphics systems use double-buffering:
    • Front Buffer: The completed frame currently being scanned out to the physical monitor.
    • Back Buffer: An off-screen buffer where the GPU or software rasterizer renders the next incoming frame.
    • Page Flip: During the vertical blanking interval (V-Blank)—when the display beam moves from bottom to top—the kernel DRM driver adjusts the scanout base register to point to the back buffer, turning it into the new front buffer instantaneously.

Why Tamlinux chose this

Tamlinux avoids monolithic graphics drivers and proprietary display servers. By building upon Linux Direct Rendering Manager (DRM) atomic modesetting, Mesa open-source user-space drivers, and standard Wayland presentation protocols, Tamlinux ensures that window surfaces are isolated from each other for security while eliminating screen tearing. The developer, Fred Horch, prioritized open standards so that the exact same rendering stack operates consistently from lightweight laptops to multi-monitor workstations.

Edge cases and failure modes

  1. Buffer Starvation (Framerate Jitter): If a complex application misses the V-Blank deadline by even a fraction of a millisecond, the display controller repeats the previous front buffer. This drops the effective framerate from 60 Hz to 30 Hz (or 120 Hz to 60 Hz), causing visible stuttering. Modern compositors mitigate this using adaptive sync (FreeSync / G-Sync) or mailbox presentation modes.
  2. Memory Bandwidth Exhaustion: Driving multiple 4K displays at 120 Hz with 10-bit color requires transferring over 50 gigabytes per second across memory buses just to scan out pixels, before any application rendering takes place. On systems with integrated graphics sharing system RAM, scanout traffic can saturate memory channels and degrade CPU performance.

Check yourself

Decide your answer before you reveal it.

Why does pitch (stride) matter when writing software rasterizers or direct-to-framebuffer utilities?

If software assumes that scanlines are tightly packed (width × bytes per pixel) without accounting for pitch padding, calculating pixel addresses using simple multiplication will introduce an offset on every row. By row 10, pixels will shift horizontally, turning the rendered image into an illegible diagonal smear.

How does atomic modesetting in the Linux kernel prevent invalid display configurations?

In legacy KMS, setting resolution, CRTCs, and planes required individual ioctl system calls that executed sequentially. If one parameter failed halfway through, the display was left corrupted. Atomic modesetting (DRM_IOCTL_MODE_ATOMIC_COMMIT) validates the entire state change in one transaction: it either applies all plane, framebuffer, and timing changes synchronously at the next V-Blank, or rolls back cleanly with zero visual disruption.
