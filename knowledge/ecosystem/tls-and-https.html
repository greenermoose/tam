SSL, TLS, and HTTPS

This page explains how SSL and its modern replacement TLS protect web browsing and network connections, and how HTTPS combines HTTP with TLS.

The padlock behind secure websites

When you visit a website whose address starts with https://, your browser uses TLS (Transport Layer Security) to encrypt the connection. Older websites and textbooks often call this SSL (Secure Sockets Layer), which was the original 1990s protocol; SSL had serious design flaws and was retired in favor of TLS.

Why it matters

Plain HTTP sends web pages, passwords, and cookies as readable text across every Wi-Fi access point and internet router between you and the server. HTTPS wraps HTTP inside TLS so eavesdroppers cannot read what you send, attackers cannot silently inject ads or malware into pages in flight, and your browser verifies that the server really owns the domain name in the address bar.

How to think about it

Think of plain HTTP as mailing a postcard: every postal worker along the route can read it or cross out a word. HTTPS puts that postcard inside a tamper-proof armored envelope. Before sending any web page, the browser and server run a quick greeting called a handshake: the server shows its X.509 passport, both sides invent a fresh one-time session key, and only then does the browser ask for the web page.

New words

TLS
Transport Layer Security: the modern protocol that encrypts and authenticates network connections, replacing SSL.
HTTPS
Hypertext Transfer Protocol Secure: standard web traffic (HTTP) carried inside an encrypted TLS tunnel.
Forward secrecy
Using throwaway per-connection keys so stealing a server's long-term key later cannot decrypt past traffic.

Inspecting TLS 1.3 cipher suites and a live handshake

Goal: you will be able to list the TLS 1.3 cipher suites supported by OpenSSL on your machine and read the negotiated protocol version, cipher suite, key-exchange group, and certificate fields of a TLS handshake.

Before you start: listing OpenSSL ciphers is read-only; running a test s_server in a temporary mktemp -d folder lets you inspect a real TLS 1.3 handshake locally without needing internet access.

Worked example

List the three AEAD cipher suites available in TLS 1.3, then run a local loopback TLS 1.3 handshake in a temporary directory:

$ openssl ciphers -v -s -tls1_3
TLS_AES_256_GCM_SHA384         TLSv1.3 Kx=any      Au=any   Enc=AESGCM(256)            Mac=AEAD
TLS_CHACHA20_POLY1305_SHA256   TLSv1.3 Kx=any      Au=any   Enc=CHACHA20/POLY1305(256) Mac=AEAD
TLS_AES_128_GCM_SHA256         TLSv1.3 Kx=any      Au=any   Enc=AESGCM(128)            Mac=AEAD

$ work=$(mktemp -d)
$ openssl req -x509 -newkey rsa:2048 -nodes -keyout "$work/key.pem" -out "$work/cert.pem" -subj "/CN=localhost" -days 1 2>/dev/null
$ openssl s_server -key "$work/key.pem" -cert "$work/cert.pem" -accept 18443 -tls1_3 -quiet >/dev/null 2>&1 &
$ spid=$!
$ sleep 0.3
$ printf 'HEAD / HTTP/1.1\r\nHost: localhost\r\n\r\n' | openssl s_client -connect 127.0.0.1:18443 -tls1_3 -brief

What just happened

  1. openssl ciphers -v -s -tls1_3 showed only AEAD suites: TLS 1.3 removed all unauthenticated CBC, RC4, and static RSA ciphers.
  2. openssl s_client -tls1_3 -brief connected to the local test server, negotiated TLSv1.3 with TLS_AES_256_GCM_SHA384, signed the handshake with rsa_pss_rsae_sha256, and established the shared secret using the post-quantum hybrid group X25519MLKEM768.
  3. verify error:num=18:self-signed certificate appeared because the scratch certificate was not signed by a CA in /etc/ssl/certs/; real browsers abort the connection on this error.

Try it

On an online machine, run curl -vI https://example.com 2>&1 | grep -E 'SSL connection|ALPN|subject:' to observe TLS version, ALPN protocol negotiation (such as h2 for HTTP/2), and certificate verification against the system trust store.

If it goes wrong

verify error:num=20:unable to get local issuer certificate
The server forgot to send an intermediate CA certificate, or your system's ca-certificates bundle is missing or outdated.
no protocols available
The server only speaks retired SSL 3.0 / TLS 1.0–1.1, which modern clients refuse for security.

On Tamlinux, system-wide TLS trust anchors are managed by Arch's ca-certificates package under /etc/ca-certificates/; pacman, curl, and browsers all verify HTTPS chains against that store.

Check yourself

Decide your answer before you reveal it.

Why did TLS 1.3 remove static RSA key exchange?

Static RSA key exchange encrypts the pre-master secret under the server's long-term public key, providing no forward secrecy: anyone recording traffic today could decrypt it years later if the server's private key is stolen.

What does ALPN (Application-Layer Protocol Negotiation) decide during the TLS handshake?

ALPN lets client and server agree on the application protocol carried inside TLS—such as HTTP/2 (h2) or HTTP/1.1 (http/1.1)—without an extra network round trip.

TLS 1.3 RFC 8446 state machine, HKDF key schedule, and HTTPS

Reference: TLS 1.3 (RFC 8446) separates the protocol into the Handshake Protocol (key agreement, server/client authentication, parameter negotiation) and the Record Layer (authenticated symmetric framing). Every TLS 1.3 cipher suite specifies only an AEAD algorithm and an HKDF hash—never key-exchange or signature algorithms, which are negotiated independently via extensions.

How it works: historical attacks, HKDF key schedule, and HTTPS

Why SSL 2.0/3.0 through TLS 1.2 Were Retired/Hardened: Legacy SSL/TLS suffered structural flaws: SSL 3.0's MAC-then-Encrypt CBC padding enabled POODLE (adaptive padding oracle); predictable CBC IVs enabled BEAST; timing differences in MAC verification enabled Lucky13; TLS-level DEFLATE compression leaked secrets via ciphertext length (CRIME / BREACH); export-grade cipher downgrades enabled FREAK and Logjam; and C memory-safety bugs in heartbeat parsing caused Heartbleed. TLS 1.3 eliminates all CBC/RC4/compression/export/static-RSA modes and encrypts all handshake messages after ServerHello.

TLS 1.3 Key Schedule (HKDF): TLS 1.3 derives all traffic keys via HKDF-Extract(salt, IKM) and HKDF-Expand-Label(Secret, Label, TranscriptHash, Length):

  1. Early Secret = HKDF-Extract(0, PSK or 0) → derives client_early_traffic_secret (0-RTT) and derived_secret.
  2. Handshake Secret = HKDF-Extract(derived_secret, (EC)DHE shared secret) → derives client_handshake_traffic_secret and server_handshake_traffic_secret, encrypting certificates and identities against passive observers.
  3. Master Secret = HKDF-Extract(derived_secret, 0) → derives client_application_traffic_secret_0, server_application_traffic_secret_0, exporter_master_secret, and resumption_master_secret.

Every key derivation binds the running Transcript-Hash(ClientHello || ... || Message), preventing downgrade attacks (supplemented by a sentinel value in ServerHello.random when negotiating TLS 1.2/1.1). CertificateVerify signs "TLS 1.3, server CertificateVerify" || 0x00 || Transcript-Hash, cryptographically binding identity to the ephemeral key exchange.

HTTPS & Transport Evolution: HTTP/1.1 pipelines sequentially over TCP; HTTP/2 multiplexes streams over one TLS/TCP connection (still vulnerable to TCP head-of-line blocking); HTTP/3 runs over QUIC (UDP), embedding TLS 1.3 handshake messages directly inside QUIC CRYPTO frames and protecting packet headers/payloads with AEAD keys derived from TLS 1.3 traffic secrets. Web security headers (HSTS to block SSL-stripping, CSP, and Encrypted Client Hello (ECH) to encrypt SNI under a DNS HTTPS-record public key) close metadata and downgrade gaps.

Edge cases and failure modes

  • 0-RTT Early Data Replay: TLS 1.3 allows sending application data in the first flight using a PSK, but 0-RTT data is not forward-secret until the 1-RTT handshake completes and cannot be protected against replay by the TLS layer alone. Servers must reject 0-RTT for non-idempotent HTTP requests (e.g., POST payments).
  • TLS-terminating proxies & middleboxes: Corporate inspection proxies and CDNs terminate TLS, re-encrypting or inspecting plaintext; misconfigured proxies frequently reintroduce weak cipher suites, skip upstream certificate validation, or leak private keys across tenants.

Check yourself

How does TLS 1.3 prevent a downgrade attack from TLS 1.3 to TLS 1.2 even though ServerHello is sent in plaintext?

First, both TLS 1.3 and TLS 1.2 sign the full handshake transcript (so altering ClientHello supported_versions breaks CertificateVerify/Finished). Second, RFC 8446 places a fixed 8-byte magic sentinel in the last 8 bytes of ServerHello.random when a TLS 1.3 server downgrades to TLS 1.2 or 1.1; a TLS 1.3-capable client detects this sentinel and immediately aborts with illegal_parameter.
