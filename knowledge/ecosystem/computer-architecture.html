Computer architecture and hardware systems

This page explains how the physical parts of a computer are organized to store data and execute instructions.

Every digital computer coordinates three primary components: a Central Processing Unit (CPU) to perform calculations, Primary Memory (RAM) to hold active instructions and data, and Secondary Storage (NVMe, SSD, or hard disk) to persist information when powered off. Understanding computer architecture clarifies how data travels across system buses, why cache hierarchies exist, and how instruction set architectures bridge software with silicon.

The computer hardware triad and CPU inspection

Goal: you will be able to identify the primary hardware components of a computer, inspect your processor architecture and cache topology using standard commands, and understand the Von Neumann model.

Why it matters: software does not run in an abstract void; it executes on physical chips constrained by bandwidth, electricity, and the speed of light. Knowing how your CPU and memory communicate helps you recognize hardware limits, write more efficient programs, and understand why certain operations run in nanoseconds while others take milliseconds.

Before you start: open a terminal window (The Shell and Streams). All inspection commands in this section are read-only and require no administrative privileges.

New to this? The $ prompt indicates the shell is ready for a command. Do not type the $. The lscpu command reads hardware data from the Linux kernel without changing any system configuration.

Captured on a Tamlinux workstation, 2026-11-01. Your processor model, core counts, and cache sizes will reflect your specific machine.

What just happened

  1. lscpu reports the fundamental CPU architecture: x86_64 (64-bit x86 extensions), using Little Endian byte ordering (least significant byte stored at the lowest address).
  2. Address sizes shows that the processor uses 48-bit virtual and physical memory addresses, allowing up to 256 terabytes of addressable space.
  3. Thread(s) per core: 2 indicates simultaneous multithreading (SMT), allowing two logical execution contexts to share execution resources on each physical core.
  4. lscpu -C exposes the hardware cache hierarchy: Level 1 has separate Data (L1d, 32 KB) and Instruction (L1i, 32 KB) caches per core; Level 2 (L2, 512 KB per core) is unified; and Level 3 (L3, 4 MB to 8 MB) is shared across cores. All caches use 64-byte coherency lines.

The Von Neumann model

Most modern general-purpose computers follow the Von Neumann architecture, proposed by John von Neumann in 1945. Its key insight is the stored-program concept: program instructions and application data share the same unified memory space. A computer consists of:

  • Central Processing Unit (CPU): containing a Control Unit (which coordinates operations), an Arithmetic Logic Unit (which computes), and Registers (ultra-fast storage on the chip).
  • Main Memory (RAM): an array of addressable storage cells holding both instructions and active data.
  • Buses: sets of parallel electrical conductors connecting the CPU, memory, and input/output devices (address bus, data bus, and control bus).
  • Input and Output (I/O): interfaces to secondary storage, keyboard, display, and network.

Try it

Run lscpu on your terminal without filtering. Identify your CPU family, maximum clock frequency in MHz, and virtualization capabilities.

What is the primary defining characteristic of the Von Neumann architecture?

Program instructions and application data share the same physical memory space and bus system, rather than residing in physically separate memories.

Why does the CPU have separate L1i and L1d caches if the system follows the Von Neumann model?

While main memory is unified (Von Neumann), the CPU core internally uses a modified Harvard architecture at Level 1 cache: separating instruction fetch from data access prevents structural contention between reading instructions and reading variables.

The memory hierarchy and processor families

Goal: you will be able to distinguish memory hierarchy tiers by latency and capacity, trace bus interconnects (PCIe, memory channels), and compare CISC and RISC architectures.

Mental model

        +----------------------------+  Latency    Capacity     Cost
        | CPU Registers (64-bit)     |  < 1 ns     ~1 KB        Highest
        +----------------------------+
        | L1 Cache (Per Core, I & D) |  ~1 ns      ~64 KB
        +----------------------------+
        | L2 Cache (Per Core)        |  ~3-5 ns    ~512 KB - 1 MB
        +----------------------------+
        | L3 Cache (Shared LLC)      |  ~10-20 ns  ~4 MB - 64 MB
        +----------------------------+
        | Main Memory (DDR4/DDR5)    |  ~60-100 ns ~8 GB - 128 GB
        +----------------------------+
        | NVMe SSD Storage (NAND)    |  ~10-50 us  ~500 GB - 4 TB
        +----------------------------+
        | Mechanical HDD / Network   |  ~5-10 ms   ~Terabytes   Lowest

As you move down the hierarchy, storage capacity grows exponentially, cost per gigabyte plummets, but latency jumps by orders of magnitude. A register access takes less than a third of a nanosecond; reading from main memory takes roughly 100 times longer; and retrieving a block from an NVMe SSD takes 100,000 times longer.

Worked example: inspect NUMA topology and cache line parameters

$ cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
64

$ cat /sys/devices/system/cpu/cpu0/cache/index3/size
4M
  1. index0 corresponds to Level 1 Data cache; its coherency line size is 64 bytes. When the CPU requests a single 4-byte integer from RAM, the memory controller fetches all 64 bytes surrounding it.
  2. index3 is the Level 3 Last Level Cache (LLC), shared across all cores on the die.

Fill in nvme (or storage). Running lspci | grep -i nvme lists active Non-Volatile Memory Express solid-state controllers communicating directly with the CPU over high-speed PCIe lanes.

Independent task

Compare the memory bandwidth and latency of your workstation. Inspect your system memory channels and clock speed using dmidecode -t memory (or review memory metrics in resources). Calculate how many 64-byte cache lines fit into your CPU L3 cache.

Divide the total L3 cache size in bytes by 64. For an 8 MB (8,388,608 bytes) L3 cache: 8,388,608 / 64 = 131,072 cache lines. The cache controller indexes and manages these lines to minimize slow trips to main memory.

Why does a Load/Store architecture (RISC) forbid operations like ADD [memory], 5?

In a pure load/store architecture, arithmetic instructions operate strictly on processor registers. Memory can only be accessed through dedicated load and store instructions, keeping the execution pipeline uniform and predictable.

What is spatial locality, and how does the 64-byte cache line exploit it?

Spatial locality is the tendency of programs to access memory locations physically close to recently accessed data. By loading an entire 64-byte line into cache on every memory reference, adjacent array elements or instructions are already in cache for subsequent cycles.

How it works: Direct Memory Access (DMA) and the MMU

When an operating system loads an executable binary or writes data to disk, involving the CPU in every single byte transfer would starve computational tasks. Modern architecture solves this through Direct Memory Access (DMA) and the Memory Management Unit (MMU):

  1. DMA Transfers: The CPU programs the storage controller (such as an NVMe host controller) with memory addresses and block counts, then issues a transfer command. The storage controller takes ownership of the PCIe bus, reading or writing data directly to physical DRAM buffers without CPU intervention. Upon completion, the controller issues a hardware interrupt to signal the kernel.
  2. Virtual Memory Translation (MMU): Every user-space process operates in its own virtual address space. The CPU's hardware MMU translates virtual addresses to physical RAM addresses on every single instruction and data reference using multi-level page tables (e.g., 4-level or 5-level paging on x86-64).
  3. Translation Lookaside Buffer (TLB): Walking page tables in DRAM on every memory access would quadruple memory latency. The MMU relies on an on-die associative cache called the TLB. When a virtual page translation hits the TLB, address resolution takes less than a cycle. On a TLB miss, the hardware page table walker traverses the page hierarchy in memory.
  4. Cache Coherence (MESI): When multiple CPU cores access shared memory, caches must remain coherent. Processors implement protocols like MESI (Modified, Exclusive, Shared, Invalid) over on-die interconnects (such as Intel UPI or AMD Infinity Fabric) to ensure that writes on one core invalidate stale copies in neighbouring caches.

Why Tamlinux chose this

Understanding memory bus bottlenecks directly shapes Tamlinux system engineering. Rather than treating RAM merely as passive storage, Tamlinux configures in-RAM compressed memory (ZRAM) with LZ4 or zstd algorithms. Because the CPU can compress and decompress data at memory bus speeds (tens of gigabytes per second), ZRAM trades a negligible fraction of compute cycles to effectively double workstation memory headroom while completely avoiding the massive latency cliffs (tens of microseconds) of solid-state storage.

Edge cases and failure modes

  • False sharing: When two threads running on different cores modify unrelated variables that happen to share the same 64-byte cache line, the MESI protocol repeatedly invalidates the cache line across both cores. The system spends immense bus bandwidth bouncing cache lines back and forth (“cache ping-pong”) rather than executing useful work.
  • TLB shootdowns: When the Linux kernel reclaims or remaps virtual memory, it must invalidate TLB entries across all CPU cores executing threads of that process. This requires inter-processor interrupts (IPIs) that stall execution across cores.
  • Microarchitectural side-channels: Modern speculative execution engines leave timing traces in shared cache lines (Spectre and Meltdown attacks), requiring operating system mitigations like Kernel Page Table Isolation (KPTI) that introduce modest syscall performance overhead.

How does Direct Memory Access (DMA) interact with CPU caches, and what mechanism ensures consistency?

When a DMA controller writes data from a storage device directly into DRAM, CPU caches might still hold older, stale versions of those memory addresses. On coherent architectures like modern x86 and ARM, the hardware bus interface snoops DMA transactions and automatically invalidates or updates matching cache lines, ensuring processor cores read fresh data without manual cache flushing.
