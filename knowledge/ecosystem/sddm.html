Display Managers: SDDM

This page explains graphical sign-in screens and how they differ from text console login.

SDDM is a display manager: a program that shows a sign-in screen and starts a desktop. Many systems, including current Tamlinux cultivars, sign in on a text screen instead and start the desktop only when asked.

Recognize the login route

Goal: distinguish a graphical sign-in from a text console login.

Before you start: read virtual console and terminal. The examples only read information.

New to this? A console is a full-screen text interface. A prompt asks for input; a password normally does not appear as you type. Do not type the leading dollar sign in examples.

Mental model

A service may start a graphical greeter; authentication opens a user session; a session starts a desktop. A text getty can offer a separate login. None of these observations alone proves the others succeeded.

Worked example: find the service tool

$ command -v systemctl
/usr/bin/systemctl

Captured on Arch Linux, 2026-10-27. Your path may differ. This finds a tool; it does not prove SDDM is installed or running. If available, systemctl status sddm reads its status; press q to leave the display.

Try it

Find the tool on your own machine. If it is available, inspect SDDM's status without changing it. If the service is absent, that result is useful evidence, not proof that login is broken.

If it goes wrong

If the tool is missing or cannot reach the service manager, use the documentation for your system and record the message. A blank screen can have several causes; see recovery.

On Tamlinux: Current cultivars use console-first login: you sign in at a text prompt, then start the graphical desktop with tam-desktop when you want it. SDDM is not packaged on that route. Older installations may still use a graphical greeter; identify the route from evidence before restarting any login service. Do not assume a particular VT or greeter from this guide alone.

Check yourself

Does a missing SDDM service prove a text login cannot work?

No. Text login and graphical login are separate routes.

Does finding systemctl prove SDDM is active?

No. It establishes only that the command is available; inspect the service separately.

Configuration and failure boundaries

Where SDDM is installed, it reads vendor drop-ins in /usr/lib/sddm/sddm.conf.d/, administrator drop-ins in /etc/sddm.conf.d/, then /etc/sddm.conf; later settings override earlier ones. Consult the installed sddm.conf(5) and inspect the selected session entry instead of assuming a fixed session command. The native greeter has username, session and password controls; packaged defaults do not choose a local account or enable automatic login. Authentication uses PAM and session registration may use logind. A greeter, authentication, session launch and compositor are separate failure points.

Do not restart SDDM as an exploratory check: a restart can end graphical sessions. Capture the relevant status and journal first, keep an independent recovery route, and follow a reviewed procedure for any login change.

Check yourself

A greeter accepts credentials but the desktop does not appear. What evidence separates authentication from session launch?

Compare authentication and session journal messages, the registered session, and the selected session entry. An accepted password alone does not establish a successful desktop launch.
