Assembly language programming and machine code

This page explains how assembly language provides human-readable words for the numeric instructions that a processor understands.

While high-level programming languages like C, Rust, or Python let developers write code using familiar mathematical syntax and abstractions, microprocessors can only execute raw binary byte sequences known as machine code. Assembly language is the closest human-readable representation of this machine code: each assembly instruction corresponds directly to one machine operation, giving developers total visibility into CPU registers, memory addresses, and execution flags.

From machine bytes to assembly mnemonics

Goal: you will be able to inspect compiled binary executables, disassemble machine code into human-readable assembly instructions using objdump, and identify the role of an assembler.

Why it matters: when debugging subtle library crashes, optimizing tight performance bottlenecks, or inspecting compiled binaries for security vulnerabilities, looking at high-level source code alone is not enough. Disassembling a binary lets you verify exactly what machine code the compiler generated and what instructions the processor will execute.

Before you start: open a terminal window (The Shell and Streams). The inspection commands in this section read compiled binaries without modifying any files.

New to this? A mnemonic is a short word (like mov for move, add for addition, or jmp for jump) that represents an opcode. A disassembler (like objdump) reads binary bytes from an executable file and translates them back into assembly mnemonics.

Worked example: disassemble machine code in an ELF executable

$ objdump -d -M intel build/tam | grep -A 8 "<_start>:"
0000000000005190 <_start>:
    5190:	f3 0f 1e fa          	endbr64
    5194:	31 ed                	xor    ebp,ebp
    5196:	49 89 d1             	mov    r9,rdx
    5199:	5e                   	pop    rsi
    519a:	48 89 e2             	mov    rdx,rsp
    519d:	48 83 e4 f0          	and    rsp,0xfffffffffffffff0
    51a1:	50                   	push   rax
    51a2:	54                   	push   rsp

Captured on an Arch Linux workstation, 2026-11-01.

What just happened

  1. objdump -d -M intel disassembles the executable section of the build/tam binary using Intel assembly syntax (destination operand first).
  2. The left column (5190:) shows the virtual memory address of the instruction.
  3. The middle column (e.g. 31 ed) shows the raw hexadecimal machine code bytes that the CPU reads.
  4. The right column (xor ebp,ebp) shows the human-readable assembly mnemonic. In x86, XORing a 32-bit register with itself (xor ebp,ebp) clears it to zero in a single compact 2-byte instruction while zero-extending into 64-bit %rbp.
  5. pop rsi retrieves the command-line argument count (argc) from the stack into register %rsi with a single 1-byte opcode: 5e.

Try it

Run objdump -d /bin/ls | head -n 30 to inspect the entry point of the standard ls command. Observe how many bytes each instruction takes.

If it goes wrong

objdump: command not found
The binutils package containing objdump, readelf, as, and ld is not installed. Install standard development utilities from base repositories.
Output uses AT&T syntax instead of Intel
By default, GNU objdump outputs AT&T syntax (source first, with % for registers and $ for constants). Pass -M intel to view Intel syntax (destination first).

What is the difference between an assembler and a compiler?

A compiler translates high-level code (like C or Rust) into assembly code or machine code, often restructuring logic. An assembler translates assembly mnemonics into raw machine code opcodes with a direct one-to-one mapping.

Why do x86-64 instruction lengths vary from 1 byte (like pop rsi) to 15 bytes?

Because x86 is a Complex Instruction Set Computer (CISC) with variable-length instruction encoding: simple operations use short 1-to-2 byte opcodes, while complex operations with prefixes, registers, and 64-bit immediate values require more bytes.

New words

Machine code
The raw binary bytes (opcodes and operands) that a microprocessor's hardware decoders directly execute.
Mnemonic
A symbolic human-readable name for a machine operation, such as mov, add, sub, or jmp.
Register
A small, extremely fast physical storage cell directly inside the CPU core (e.g. %rax, %rdi).
Disassembler
A programming tool that parses binary machine code bytes and outputs equivalent assembly mnemonics.

Register architecture and standalone assembly programs

Goal: you will be able to navigate general-purpose CPU registers, write a standalone x86-64 assembly program, invoke Linux system calls directly without a C runtime, and assemble and link the binary.

Mental model: the x86-64 register hierarchy

64-bit Register: %rax (Bits 0 - 63)
+---------------------------------------------------------------+
|                      |  32-bit: %eax (Bits 0 - 31)            |
|                      +----------------------------------------+
|                      |             | 16-bit: %ax (Bits 0 - 15)|
|                      |             +--------------------------+
|                      |             | %ah (8-15) | %al (0-7)   |
+---------------------------------------------------------------+

General Purpose Registers:
  %rax (Accumulator / Syscall return)     %r8  (General / 5th argument)
  %rbx (Base register / Callee-saved)     %r9  (General / 6th argument)
  %rcx (Counter / 4th argument)           %r10 (Syscall 4th argument)
  %rdx (Data / 3rd argument)              %r11 (Temporary / RFLAGS on syscall)
  %rsi (Source Index / 2nd argument)      %r12 (General / Callee-saved)
  %rdi (Destination Index / 1st argument) %r13 (General / Callee-saved)
  %rbp (Base Pointer / Callee-saved)      %r14 (General / Callee-saved)
  %rsp (Stack Pointer - points to top)    %r15 (General / Callee-saved)

Writing to a 32-bit sub-register (such as mov %eax, 5) automatically zeroes out the upper 32 bits of the full 64-bit register (%rax), preventing stale high-order bits from corrupting calculations.

Worked example: a standalone Linux assembly program

$ task_dir=$(mktemp -d)
$ cat << 'EOF' > "$task_dir/hello.s"
.global _start
.text
_start:
    # write(1, message, 14)
    mov $1, %rax          # syscall number 1: sys_write
    mov $1, %rdi          # file descriptor 1: stdout
    lea message(%rip), %rsi # address of message buffer
    mov $14, %rdx         # string length in bytes
    syscall               # invoke Linux kernel

    # exit(0)
    mov $60, %rax         # syscall number 60: sys_exit
    xor %rdi, %rdi        # exit status 0
    syscall

.data
message:
    .ascii "Hello from asm\n"
EOF

$ as -o "$task_dir/hello.o" "$task_dir/hello.s"
$ ld -o "$task_dir/hello" "$task_dir/hello.o"
$ "$task_dir/hello"
Hello from asm
$ rm -r "$task_dir"
  1. .global _start exports the default ELF entry point symbol that the Linux dynamic linker or kernel jumps to when executing the program.
  2. The syscall instruction transfers control from user mode (Ring 3) to the kernel (Ring 0). The kernel reads the system call number from %rax and arguments from %rdi, %rsi, %rdx.
  3. sys_write (syscall 1) writes 14 bytes from the message address to stdout (file descriptor 1).
  4. sys_exit (syscall 60) cleanly terminates the process with exit code 0.
  5. The assembled binary requires zero external libraries — it does not even link libc. Its final stripped size is less than 1 kilobyte.

Why does writing to a 32-bit register like %eax clear the upper 32 bits of %rax in x86-64?

To eliminate false data dependencies on the upper half of the register. In 64-bit mode, zero-extending 32-bit results prevents older partial-register stall penalties and simplifies hardware register renaming.

What register receives the return value of a function in x86-64 System V ABI?

Register %rax (or %eax for 32-bit integers, %al for 8-bit values). Floating-point results are returned in vector register %xmm0.

How it works: Stack frames and the 128-byte Red Zone

When a function executes, it manages local storage on the hardware stack via the Stack Pointer (%rsp) and Base Pointer (%rbp):

  1. Standard Function Prologue: 
    push %rbp             # Save old caller base pointer
mov  %rsp, %rbp       # Establish new base pointer for this stack frame
sub  $32, %rsp        # Allocate 32 bytes for local stack variables
  2. The 128-Byte Red Zone: The System V AMD64 ABI defines a 128-byte scratch region below the current stack pointer (%rsp - 1 through %rsp - 128) that is guaranteed not to be overwritten by signal handlers or interrupts. Leaf functions (functions that call no other functions) can use this 128-byte zone for local variables without spending instructions to adjust %rsp in a prologue or epilogue.
  3. Function Epilogue: 
    mov  %rbp, %rsp       # Deallocate local stack variables
pop  %rbp             # Restore caller base pointer
ret                   # Pop return address from stack into %rip
    The composite instruction leave can replace mov %rbp, %rsp; pop %rbp.
  4. Position-Independent Code (PIC): Modern Linux executables are built as Position-Independent Executables (PIE). Rather than referencing absolute 64-bit addresses, instructions reference data relative to the Instruction Pointer using RIP-relative addressing (e.g. mov message(%rip), %rax). This allows the Linux kernel's Address Space Layout Randomization (ASLR) to load the executable at a randomized base address in virtual memory, defending against memory exploitation.

Why Tamlinux chose this

Adherence to standard ABI conventions ensures seamless interoperability. In Tamlinux, core utilities compile to standard ELF64 shared libraries and executables. By following standard System V calling conventions, native C functions in libtam can be called directly from assembly, C, Rust, or foreign function interfaces in scripting languages without data marshalling overhead or stack corruption.

Edge cases and failure modes

  • AVX Stack Alignment Crash: Modern vector instructions like movaps (Move Aligned Packed Single-Precision) require memory operands to be aligned on 16-byte boundaries (or 32-byte for AVX2). If a programmer fails to maintain 16-byte stack alignment before calling a function, vector operations inside libc trigger an immediate General Protection Fault (#GP).
  • Red Zone Corruption: If a non-leaf function attempts to use the Red Zone and executes a call instruction, the call pushes the return address onto the stack, immediately overwriting the top 8 bytes of the Red Zone and corrupting local variables.
  • Buffer Overflow Exploitation: Writing past the boundary of a stack-allocated buffer overwrites the saved %rbp and return address stored on the stack. Modern compilers mitigate this by inserting stack canaries (-fstack-protector-strong) that trigger __stack_chk_fail if modified.

Why does the compiler emit lea (%rdi,%rsi), %eax instead of add %esi, %edi; mov %edi, %eax?

The lea (Load Effective Address) instruction can add two registers together and place the result into a separate destination register in a single machine cycle without modifying CPU status flags. This saves both an instruction and prevents unnecessary register copying.
