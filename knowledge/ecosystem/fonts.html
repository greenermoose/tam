Typography, fonts and text rendering

This page explains how text is turned into visible letters on screens, from Linux virtual consoles to graphical desktops.

On Unix-like operating systems, typography is not handled by a single monolithic engine. A small text console uses fixed bitmap grids built into kernel memory, while a graphical desktop coordinates multiple libraries to discover font files, shape complex scripts, and draw sharp vector curves on pixel displays. Knowing how this pipeline works allows you to customize your reading environment, troubleshoot missing characters, and write lean desktop software.

How does Tamlinux render text?

Computers store text as numeric character codes, such as Unicode codepoint U+0041 for the capital letter “A”. A screen, however, is a grid of physical pixels. A font is the bridge between those codes and visible shapes. When a font is missing, misconfigured, or lacks the right glyphs, text becomes unreadable or displays as empty boxes.

Mental model

   Unicode Text String: "Hello World"
               |
               v
   [Fontconfig]  ----> Finds best matching font file (.ttf / .otf)
               |
               v
   [HarfBuzz]    ----> Text Shaping (maps character codes to glyph IDs,
               |       resolves ligatures, and computes (x,y) advances)
               v
   [FreeType]    ----> Rasterization (converts vector outlines into pixel
               |       bitmaps with anti-aliasing and subpixel hinting)
               v
   [UI Toolkit / Window]  (Pango / Qt / Cairo composite pixels to screen)

Modern Linux desktop rendering is split into distinct modular layers:

  • Fontconfig: searches system directories (such as /usr/share/fonts and ~/.local/share/fonts), parses XML configuration rules, and computes mathematical scores to match application font queries to real files on disk.
  • FreeType: loads font files, executes TrueType bytecode or CFF hinting, parses outline coordinates, and rasterizes vector curves into grayscale or subpixel anti-aliased pixel maps.
  • HarfBuzz: the universal text shaping engine. Simple Latin scripts require little shaping, but complex scripts (such as Arabic, Devanagari, or connected cursives) require contextual glyph substitution and positional anchoring. HarfBuzz turns a sequence of Unicode codepoints into positioned glyph indices.
  • Pango / Qt: high-level layout libraries that break paragraphs into lines, handle bidirectional text flow, call HarfBuzz for shaping, and invoke FreeType or Cairo to draw the glyphs onto surfaces.

Worked example: query the active monospace font

$ fc-match monospace
AtkinsonHyperlegibleMono-Regular.ttf: "Atkinson Hyperlegible Mono" "Regular"

$ fc-list : family | grep -i "atkinson" | head -n 3
Atkinson Hyperlegible
Atkinson Hyperlegible Mono
AtkinsonHyperlegibleMono Nerd Font

Captured on a Tamlinux workstation. Your installed versions and font paths may differ.

What just happened

  1. fc-match monospace asks the system font matching library, Fontconfig, which font file will be chosen when an application asks for a generic “monospace” font. It prints the filename, the family name, and the style variant.
  2. fc-list : family lists all font families indexed on your machine. Filtering with grep confirms that the Atkinson family is installed and ready for desktop applications.

A glyph is the particular visual representation of a character. A font file contains a collection of glyphs along with lookup tables that map character codes to those shapes. In a proportional font, each letter takes up only as much width as it needs (such as a wide “W” and a narrow “I”). In a monospace font, every character occupies an identical cell width, which is essential for command-line alignment, code indentation, and terminal applications.

On Tamlinux, the default interface typeface is Atkinson Hyperlegible, designed by the Braille Institute to maximize character distinction for low-vision readers. For terminal and code editors, Tamlinux packages Atkinson Hyperlegible Mono, enhanced with icon glyphs from Nerd Fonts.

Try it

Run these read-only commands to see where font files are stored on disk and check your terminal font family:

fc-match -f "%{file}: %{family} (%{style})\n" monospace
tam-font-current

The first command outputs the absolute file path on disk where the active monospace font is stored. The second command uses Tamlinux's own query tool, tam-font-current, to report the currently configured terminal font family.

If it goes wrong

fc-match: command not found
The Fontconfig utility package is not installed or not on your PATH. On Arch Linux, install it with pacman -S fontconfig; on Void Linux, install it with xbps-install -S fontconfig.
Question marks or empty boxes instead of text
The selected font file lacks glyphs for those Unicode characters. A fallback font must be configured in Fontconfig, or a font with broader coverage (such as Noto Fonts) must be installed.
Terminal text looks squished or misaligned
The terminal emulator is using a proportional font instead of a fixed-pitch monospace font. Terminal grids require strict character-cell widths.

On Tamlinux, Atkinson Hyperlegible serves as the system interface typeface, and Atkinson Hyperlegible Mono (enhanced with Nerd Font symbol glyphs) provides the terminal font. Font defaults are delivered declaratively through ~/.config/fontconfig/conf.d/99-tamlinux-monospace.conf and selected via tam-font-set. Changing a font updates application preferences inside a transactional journal without modifying package files in /usr.

What is the difference between a character and a glyph?

A character is an abstract unit of written language identified by a standard code (such as Unicode U+0041 for “A”). A glyph is the specific visual shape or curve used to draw that character on a display.

Why must terminal emulators use monospace fonts instead of proportional fonts?

Terminal applications organize text in a strict two-dimensional grid of rows and columns. Monospace fonts ensure that every character occupies the exact same rectangular width, keeping columns and table borders properly aligned.

Does Linux have a single, central font server for all programs?

No. Early Unix X11 systems used a network font server, but modern desktop environments use client-side font discovery (Fontconfig) and client-side rasterization (FreeType), meaning each application or UI toolkit renders its own text.

Tamlinux font architecture, table rewriting and leanness

Dissecting the Tamlinux font engine

In Tamlinux, font management is coordinated by the theme engine implemented in Python under the Tamlinux product repository. The primary font management function, font_set, resides in the theme engine and is invoked through the command wrapper tam-font-set:

$ tam-font-set "AtkinsonHyperlegibleMono Nerd Font"

When this command runs, the engine executes the following verification and update transaction:

  1. Validation: The requested family string is sanitized to forbid null bytes and control characters. The engine queries fc-list -f '%{family}\n' and confirms that the requested font is genuinely indexed by Fontconfig before making any changes.
  2. Multi-Target Configuration: Terminal emulators and applications store font preferences in distinct, uncoordinated configuration files. The engine identifies and modifies:
    • ~/.config/alacritty/alacritty.toml (via regex: family = "...")
    • ~/.config/kitty/kitty.conf (via regex: font_family ...)
    • ~/.config/ghostty/config (via regex: font-family = "...")
    • ~/.config/foot/foot.ini (via regex: font=... with colon escaping)
    • ~/.config/fontconfig/conf.d/99-tamlinux-monospace.conf (generating a clean Fontconfig XML override rule)
    • ~/.config/fontconfig/fonts.conf (parsing the existing XML tree with xml.etree.ElementTree, preserving comments, and inserting an include node for conf.d/99-tamlinux-monospace.conf)
  3. Transactional Journaling: Every target file is backed up into ~/.local/state/tamlinux/settings-recovery/font.<id>/ before editing. If any file write or XML parse fails, the entire transaction rolls back to the prior state.
  4. Atomic File Replacement: Files are written to temporary unique paths on the same filesystem and atomically swapped using os.replace, preventing partially written configurations from being read by running processes.
  5. Live Session Reload: The engine issues non-blocking reload commands to the desktop shell and running terminals (tam-restart-terminal, tam-restart-shell) and invokes the hook system via tam-hook font-set <family>.

Binary font table manipulation with rename-font.py

Tamlinux packages curated icons and typography. When rebranding and packaging font assets without upstream license violations or glyph distortion, Tamlinux uses a dedicated table patching script, rename-font.py, built on fontTools.ttLib:

from fontTools.ttLib import TTFont

font = TTFont(source, recalcTimestamp=False)

# OpenType 'name' table record IDs:
# 1: Family name, 3: Unique font ID, 4: Full font name,
# 6: PostScript name, 16: Typographic family, 21: WWS family
identities = {
    1: 'Tamlinux Icons',
    3: 'Tamlinux Icons Regular 1.0',
    4: 'Tamlinux Icons Regular',
    6: 'TamlinuxIcons-Regular',
    16: 'Tamlinux Icons',
    21: 'Tamlinux Icons'
}

for record in font['name'].names:
    if record.nameID in identities:
        record.string = identities[record.nameID].encode(record.getEncoding())

The script also inspects the post table (format 2.0). It updates internal PostScript glyph name mappings while preserving outline data. Crucially, the script asserts that the compiled binary representation of critical glyph tables remains identical:

for table in ('cmap', 'glyf', 'hmtx'):
    assert font[table].compile(font) == result[table].compile(result)

This guarantees that the character-to-glyph index mapping (cmap), the actual glyph vector curves (glyf), and horizontal metrics (hmtx) are completely untouched.

Future work for smaller code and higher efficiency

The current Tamlinux font engine is functional and resilient, but there are clear opportunities to make the code significantly smaller, faster, and more efficient as the system transitions toward Void Linux and microkernel architectures:

  1. Consolidating Multi-Terminal Rewrites: Currently, the Python engine maintains distinct regular expression parsers for Alacritty, Kitty, Ghostty, and Foot. Standardizing on terminals that respect Fontconfig's system monospace alias (or generating a single included configuration file) would eliminate hundreds of lines of brittle regex string parsing.
  2. Minimal C Fontconfig Manipulator: Replacing the Python ElementTree XML manipulation with a lean C tool linking directly to libfontconfig (or generating simple static XML files without tree parsing) would eliminate Python startup overhead and reduce memory consumption from ~30 megabytes to under 500 kilobytes.
  3. Pruning Unused Font Tables: Packaged TrueType and OpenType fonts often contain legacy tables that are unnecessary for modern Wayland compositors:
    • hdmx (horizontal device metrics, redundant when using subpixel rendering)
    • VDMX (vertical device metrics)
    • Legacy TrueType bytecode hinting instructions in fonts rendered on high-DPI (200+ DPI) displays, where grayscale anti-aliasing renders sharp outlines without artificial grid-fitting distortion.
    Pruning these tables with automated build-time scripts can reduce font package sizes by 15–30%.
  4. Precomputed Glyph Metrics in UI Shells: In desktop panels and widgets (such as Quickshell), font measurement during startup causes disk I/O and FreeType face realization. Precomputing and embedding critical character advance tables for the Atkinson font family at compile time allows immediate layout computation with zero cold-start latency.

Explore

Inspect the OpenType tables of a font file installed on your system using read-only command-line tools:

fc-match -f "%{file}\n" monospace

The otfinfo tool (from the lcdf-typetools package) extracts the OpenType name table entries, showing the family, PostScript name, version, and designer credits directly from the binary header.

Check yourself

Decide your answer before you reveal it.

Why does rename-font.py assert that compiled cmap, glyf, and hmtx tables are byte-for-byte identical?

To verify that changing the font's human-readable name metadata did not alter character codepoint mappings (cmap), vector outline geometry (glyf), or character spacing and advance widths (hmtx), ensuring typographic rendering fidelity is perfectly preserved.

What advantage does an atomic file exchange (os.replace) have over writing directly to a configuration file?

Writing directly to a file creates an learner state where the file is partially written or empty. If a reader process (like a terminal emulator or editor) reads the file during that window, it crashes or fails to parse. An atomic exchange swaps the directory entry instantaneously, so readers always see either the complete old file or the complete new file.

How can font subsystem code size be reduced when migrating from Arch Linux to Void Linux?

By removing systemd-specific service dependencies, replacing large Python XML parsing scripts with small C utilities or static include files, and standardizing desktop components to query Fontconfig rather than maintaining separate configuration parsers for individual terminal emulators.
