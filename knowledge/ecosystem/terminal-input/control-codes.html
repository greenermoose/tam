Control characters and the Ctrl key

This page explains the bytes that chords such as Ctrl + A and Ctrl + H produce, and why the same byte can mean different things to different programs.

The Ctrl key writes numbers, not letters

Holding Ctrl and pressing a letter does not type that letter. It sends a small number instead. Ctrl + A sends the number 1, Ctrl + C sends 3, and Ctrl + H sends 8. These small numbers are called control characters.

Each number has a job. Some move the cursor. Some tell the terminal to beep or clear the screen. Some ask the operating system to stop the program. Some are just data that a program reads and interprets for itself.

Why it matters

Control characters are why Ctrl + C stops a command, why Ctrl + D closes a shell, and why Backspace sometimes deletes a character and sometimes does nothing. They also explain why a shortcut that works in one program can fail in another: the byte is the same, but the program reading it gives it a different job.

How to think about it

Imagine a telephone keypad where each key can send either a spoken word or a tone. The Ctrl key switches the keypad into tone mode. The tone itself has no meaning; the receiving office decides whether a tone means "hang up", "redial", or "transfer". A control byte is a tone, and the program at the other end is the office.

New words

ASCII
The old seven-bit character code that gives numbers to letters and to the control characters.
Control character
A code below 0x20, or 0x7F, that usually asks for an action instead of printing a symbol.
Signal
A short notification the kernel sends to a running program, often triggered by a control character.

Predict the byte behind a chord

Goal: you will be able to say which byte a Ctrl chord produces, and tell whether the terminal, the kernel, or the program will act on it.

Worked example

The printf command can write exact byte values. od then shows them in hexadecimal and as visible escapes.

$ printf '\001\002\003\010\011\012\015\033\037\177\n' | od -An -tx1 -c
  01  02  03  08  09  0a  0d  1b  1f  7f  0a
 001 002 003  \b  \t  \n  \r 033 037 177  \n

Captured on Arch Linux, 2026-11-13. Read the two lines together: the first line is hexadecimal, the second is the character or escape name. 0x08 is \b, 0x09 is \t, 0x0A is \n, and 0x7F has no short name, so od prints 177 in octal.

The rule behind the letters is simple. An uppercase letter has an ASCII code from 0x41 to 0x5A. Clear the top three bits by combining the value with 0x1F, and you get 0x01 to 0x1A. So A becomes 1, H becomes 8, and M becomes 13.

Try it

Ask the terminal what its special characters are, then compare two bytes that both claim to be Backspace.

$ stty -a | tr ';' '\n' | grep -E 'erase|kill|eof|intr|susp|werase|lnext'
$ printf '\010' | od -An -tx1 -c
$ printf '\177' | od -An -tx1 -c

stty -a prints the current terminal settings. Look for erase: it names the byte that erases one character. On most Linux terminals it is ^?, which is 0x7F. The two printf lines prove that 0x08 and 0x7F are different bytes even though both are called Backspace in ordinary speech.

If it goes wrong

The terminal stops printing and seems frozen
Ctrl + S is the stop-flow character. Press Ctrl + Q to resume. This is the line discipline, not a crash.
A command disappears and the prompt returns with a job number
Ctrl + Z sent SIGTSTP and stopped the job. Type fg to bring it back, or jobs to list it.
Ctrl + C does not stop a program
The program may be ignoring or handling SIGINT, or it may have put the terminal in raw mode. Try Ctrl + \ for SIGQUIT, then kill by process ID if needed.
Backspace prints ^H instead of deleting
The program is receiving 0x08 and is not treating it as erase. Check stty erase; a raw-mode program must handle the byte itself.

On Tamlinux: the terminal stack follows the usual Linux defaults, so stty reports erase = ^? and intr = ^C in a normal session. Tamlinux does not ship a custom line discipline; changes come from the terminal emulator, the shell, or stty settings in that session.

Check yourself

Decide your answer before you reveal it.

Which byte does Ctrl + H send, and which byte does the Backspace key usually send in foot?

Ctrl + H sends 0x08, the ASCII BS control. foot sends 0x7F for Backspace. They are different bytes, which is why a program can usually tell them apart.

Why can a program not tell Ctrl + I from the Tab key on a legacy terminal?

Both produce the same byte, 0x09. The terminal protocol has no separate code for them in legacy mode. A modern protocol such as the kitty keyboard protocol can report them separately, but only if the program asks for it.

Is Ctrl + C always a request to stop the program?

No. The byte 0x03 is only a signal request when the line discipline has ISIG enabled and the byte matches the intr character. In raw mode the program receives 0x03 as data and may use it for copy, cancel, or anything else.

How it works

For letters, the transformation is the mask code & 0x1F. The same arithmetic covers the punctuation cases that matter: @ is 0x40 and becomes 0x00; [ is 0x5B and becomes 0x1B; \ is 0x5C and becomes 0x1C; ] is 0x5D and becomes 0x1D; ^ is 0x5E and becomes 0x1E; _ is 0x5F and becomes 0x1F.

Ctrl + ? is the exception in ordinary speech. Applying the mask to ? (0x3F) gives 0x1F, but terminals send 0x7F, the DEL code. DEL historically meant "rub out" on paper tape: a frame with every hole punched, which a reader could ignore. Video terminals reused it as the erase key because BS was still needed to move the cursor left for other purposes.

That history created the modern split. The ASCII BS code is 0x08. The rubout code is 0x7F. A terminal can send either when the Backspace key is pressed. xterm exposes the choice through backarrowKey and the DECBKM mode; foot documents that it always sends DEL for Backspace and BS for Ctrl + Backspace, and that it does not implement DECBKM. On the kernel side, stty erase selects which byte the line discipline treats as erase; only one byte can hold that role at a time. In raw mode the line discipline does not erase at all, and the program sees whichever byte arrived.

This is exactly where a key parser can lose information. libtam 0.7.0's tam_key decoder maps both 0x08 and 0x7F to TAM_KEY_BACKSPACE. That is convenient for an editor that only needs a delete action, but it makes Ctrl + H indistinguishable from Backspace. Choosing a keybinding treats that as a design problem rather than a decoding bug.

Advanced usage

These snippets show the same byte under different settings. They are illustrative; run them in a scratch script session if you do not want to change the current terminal.

$ script -qec 'stty erase ^H; stty -a | grep -o "erase = [^;]*"' /dev/null
$ script -qec 'stty erase ^?; stty -a | grep -o "erase = [^;]*"' /dev/null
$ printf '\010\177' | cat -v

cat -v prints control bytes in caret notation, so 0x08 appears as ^H and 0x7F as ^?. The two settings change which byte the line discipline consumes as erase; the bytes on the wire do not change.

Edge cases

  • Both bytes can arrive. A terminal may send 0x08 for Backspace and 0x7F for Delete, or the reverse. A robust program should handle both, or the terminal should be configured consistently.
  • Raw mode bypasses the line discipline. Editors, pagers and full-screen programs call tcsetattr with ICANON and ISIG cleared. They must implement erase, signals and line editing themselves.
  • Meta is not a control byte. Some old terminals set bit 7 of the byte for Alt, producing 0x80 and above. That conflicts with UTF-8, so modern terminals prefix the byte with ESC instead. See Keys inside foot.
  • 8-bit C1 controls. Bytes 0x80 to 0x9F duplicate some ESC sequences in ISO 8859-1, but they are not valid UTF-8. A terminal in UTF-8 mode must not treat a bare 0x9B as CSI.
  • Pasting control bytes. A paste can contain 0x03 or 0x1B. Bracketed paste lets an editor distinguish pasted text from typed keys and avoid executing it as commands.

Check yourself

A user runs stty erase ^H. What now happens when they press Backspace, and what happens when they press Ctrl + H? What does a program in raw mode see?

With erase = ^H, the line discipline consumes 0x08 as the erase character. Backspace still sends whatever the terminal sends: in foot that is 0x7F, which is no longer the erase byte, so it becomes ordinary input and may appear as ^?. Ctrl + H sends 0x08 and now erases a character. A program in raw mode sees both bytes unchanged, because raw mode clears ICANON; it must decide for itself what 0x08 and 0x7F mean. This is why changing erase can appear to fix one program and break another.
