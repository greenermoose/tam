The kernel's line editor

This page explains what the kernel does with the bytes a terminal sends before a program reads them: editing a line, echoing it back, sending signals, and reporting end of input.

The editor you never started

When you type at a shell prompt, the letters appear as you type and nothing runs until you press Enter. Something is collecting and editing that line, and it is not the shell. It is a part of the kernel called the line discipline, attached to your terminal.

The line discipline is why Backspace works before a command runs, why Ctrl + C stops a command, and why Ctrl + D can close a shell. It is a small, quiet editor that sits between the keyboard and every ordinary program.

Why it matters

Most confusing terminal behaviour belongs here. A program that "ignores Backspace" may have switched the line discipline off. A prompt that prints two blank lines for every Enter may have the wrong newline translation. Knowing that this layer exists tells you whether to change the program, the terminal, or the terminal settings.

How to think about it

Think of a receptionist with a notepad. You dictate letters, the receptionist writes them on the pad, crosses out mistakes when you say so, and only hands the page to the manager when you say "done". Some visitors ask the receptionist to step out of the room, and then they speak to the manager directly. That request is what a full-screen program does when it switches to raw mode.

New words

Line discipline
The kernel layer that edits terminal input, echoes it, and turns some characters into signals.
Canonical mode
The usual line-at-a-time mode. Input is edited and delivered after Enter.
Raw mode
A mode in which the line discipline passes bytes straight through with no editing, echoes or signals.
Signal
A short notification the kernel sends to a process, such as SIGINT when you press Ctrl + C.

Read the terminal's settings

Goal: you will be able to read the line discipline's settings, say which byte does what, and explain why a program does not receive a key until you press Enter.

Worked example

The stty command prints and changes the settings of the terminal it is attached to.

Two of these explain very common sights. echo is why you see your typing at all: the terminal does not print your keys, the kernel echoes them. icrnl is why Enter usually reaches a program as 0x0A even though the terminal sent 0x0D.

End of input works by position, not by a byte arriving at the program. At an empty line, Ctrl + D makes a pending read return zero bytes, which a program interprets as end of input. In the middle of a line it hands over the text typed so far without a newline, and the program reads those characters normally.

Try it

Compare what a program receives in canonical mode with what it receives after the line discipline is cleared. Use a scratch window, because raw mode changes your typing.

$ printf 'type a few keys, then Enter\n'
$ cat
$ stty -icanon -echo min 1 time 0
$ od -An -tx1 -c
$ stty sane

In the first cat, nothing arrives until you press Enter. In the raw-mode od, each key arrives immediately, Backspace is no longer an editing command, and Ctrl + C is a byte instead of a signal. Type six or seven keys, press Enter, then press Ctrl + D, and finish with stty sane so the window is usable again.

If it goes wrong

Nothing you type is displayed
echo is off, usually because a program asked for a password or died before restoring the terminal. Type stty sane and press Enter, then reset if needed.
Enter prints a blank line but the command does not run
The program may be waiting for a different terminator, or input translation may be wrong. Check stty -a | grep -E 'icrnl|inlcr|igncr'.
Output stops in the middle of a long listing
Ctrl + S paused the output. Press Ctrl + Q.
A command is stopped instead of terminated
Ctrl + Z sends SIGTSTP, which suspends the job. Use fg to resume it or kill %1 to end it.
stty: standard input: Inappropriate ioctl for device
Standard input is not a terminal, for example in a pipeline or a script run by cron. Redirect from the terminal device, stty -a < /dev/tty, or run it interactively.

On Tamlinux: the line discipline is part of the kernel, so its defaults are the kernel's, not a Tamlinux choice. Tamlinux does not change them globally. Per-session settings come from the shell, from stty, or from whatever program currently owns the terminal.

Check yourself

Decide your answer before you reveal it.

Why does the shell not see your typing until you press Enter?

Because icanon is on. The line discipline buffers input, applies editing such as erase and kill, echoes the result, and delivers the completed line when Enter arrives. The shell reads a whole line at a time.

What is the difference between Ctrl + D at an empty prompt and in the middle of a word?

At an empty line it makes the pending read return zero bytes, which looks like end of input and usually closes the shell. Mid-line it delivers the characters typed so far without a newline, so the shell runs them as a partial line.

Does the terminal send 0x0A when you press Enter?

Usually not. The Enter key sends CR, 0x0D, and icrnl converts it to 0x0A before the program reads it. With icrnl off, the program sees 0x0D, which is a classic cause of strange line endings.

Reference: termios and the N_TTY discipline

The settings come from a struct termios with four flag words and a table of special characters:

struct termios {
    tcflag_t c_iflag;    /* input flags: ICRNL, IXON, IUTF8, ... */
    tcflag_t c_oflag;    /* output flags: OPOST, ONLCR, ... */
    tcflag_t c_cflag;    /* control flags: CS8, CREAD, CLOCAL, ... */
    tcflag_t c_lflag;    /* local flags: ICANON, ISIG, ECHO, IEXTEN, ... */
    cc_t     c_cc[NCCS]; /* VINTR, VQUIT, VERASE, VKILL, VEOF, ... */
    speed_t  c_ispeed;
    speed_t  c_ospeed;
};

How it works

The discipline is implemented in the kernel's N_TTY code, reached through the tty layer for a pseudo-terminal or a real console. In canonical mode it keeps a line buffer, applies erase, word-erase and kill to that buffer, and wakes a reader when a line delimiter arrives. The buffer is bounded; a line longer than the limit is truncated or refused, and the terminal may beep. A reader's read returns at most one line, so a large write by the program does not correspond to one read by the reader.

The special characters are interpreted before the buffer, in this order of precedence:

  1. VLNEXT quotes the following byte, so the next character is inserted literally.
  2. VINTR, VQUIT and VSUSP generate signals when ISIG is set. The signal goes to the foreground process group of the terminal, which is why Ctrl + C reaches the running command and not the shell.
  3. VSTOP and VSTART control output when IXON is set.
  4. VERASE, VWERASE, VKILL and VREPRINT edit the current line when ICANON is set.
  5. VEOF ends the current line without adding a delimiter, and returns zero bytes when the line is empty.

Signals flush the input and output queues unless NOFLSH is set. That is why a partially typed line disappears after Ctrl + C. The signal disposition belongs to the program: it may catch SIGINT, ignore it, or die. SIGQUIT additionally asks for a core dump by default, and SIGTSTP stops the process until it is continued.

Advanced usage

Full-screen programs commonly build their mode with cfmakeraw, then restore the saved settings on exit:

struct termios saved, raw;
tcgetattr(fd, &saved);
raw = saved;
cfmakeraw(&raw);          /* clears ICANON, ISIG, ECHO, IEXTEN, IXON, ICRNL, OPOST */
raw.c_cc[VMIN] = 1;       /* return when one byte is available */
raw.c_cc[VTIME] = 0;      /* no inter-byte timer */
tcsetattr(fd, TCSAFLUSH, &raw);
/* ... read bytes, decode keys, draw ... */
tcsetattr(fd, TCSAFLUSH, &saved);

In non-canonical mode, VMIN and VTIME decide when a read returns: VMIN is the minimum byte count and VTIME is a timeout in tenths of a second. VMIN = 1, VTIME = 0 is a blocking single-byte read, which is what most key decoders want. VMIN = 0, VTIME = n is a timed read, useful for deciding that a lone ESC is the Esc key and not the start of a sequence.

Other parts of the tty layer matter to the same programs:

  • Window size. TIOCGWINSZ and TIOCSWINSZ read and set rows and columns; a change raises SIGWINCH, which a full-screen program handles by redrawing.
  • Foreground group. tcgetpgrp and tcsetpgrp decide which process group receives the signal characters. A background group that reads from the terminal gets SIGTTIN and stops.
  • Flow control. tcflow can pause and resume output, and IXON does the same for the special characters.
  • Pending output. TCSAFLUSH discards unread input, while TCSADRAIN waits for output to drain. Choosing wrongly loses typed characters or leaves bytes for the next reader.

Edge cases

  • No terminal at all. Without a controlling terminal, these ioctls fail with ENOTTY. This is normal for a program run from cron, or for a remote command started without a pseudo-terminal such as ssh -T.
  • UTF-8 erase without IUTF8. With the flag off, one erase removes one byte, so erasing a multi-byte character leaves invalid fragments.
  • Binary data through a terminal. Canonical mode interprets 0x03, 0x04, 0x11 and 0x13 as commands. Binary transfers need raw mode and usually a different transport.
  • Literal CR in input. With ICRNL on, a program cannot receive 0x0D from the keyboard. A protocol that needs it must disable the translation.
  • Password prompts. They clear ECHO and restore it afterwards, which is why an interrupted password prompt can leave typing invisible.
  • Terminal injection. Writing to another terminal's input queue was historically possible through TIOCSTI. Modern kernels restrict it, and a program should not rely on it.
  • Detached processes. A process that keeps a tty open after its session ends can receive SIGHUP. Some programs ignore it; most should exit.

Check yourself

A full-screen editor exits after a crash. The shell prompt returns, but typed characters are not shown, Enter does not run commands, and Ctrl + C prints ^C instead of stopping anything. Explain the state and the safest recovery.

The editor set raw mode and died before restoring the saved settings. ECHO, ICANON and ISIG are still cleared, so the shell's input is not echoed, lines are not assembled, and the signal characters arrive as ordinary bytes. The settings belong to the terminal, so a new program inherits them. Type stty sane followed by Enter, which works even though nothing appears; if the terminal still misbehaves, run reset, or close the terminal window, which destroys the pseudo-terminal and its settings. Do not reinstall the editor: the fault is an interrupted cleanup, not a broken binary.
