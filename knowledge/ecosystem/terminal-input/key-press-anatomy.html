From key press to character

This page follows the letter a and the Backspace key through every layer that gives a key a number or a meaning.

One key, several names

When you press a key, the computer does not receive a letter. It receives a series of numbers, and each layer gives the key a new name. The keyboard names the switch. The kernel names the key. The keyboard layout names the symbol. The terminal names the bytes. The program finally decides what those bytes mean.

Why it matters

When a key types the wrong character, does nothing, or triggers the wrong command, the cause is one of these layers. Knowing the names lets you ask a precise question: did the layout change the symbol, or did the terminal send a different byte? Without the names, every problem looks like "the keyboard is broken".

How to think about it

Think of a parcel with a new label added at each depot. The sender writes a stock number. The first depot writes a route number. The second writes a local address. The final courier writes a door number. Every label is correct for its own depot, but only the last one tells you where the parcel arrives. A key press travels the same way, and the last label is the byte the program reads.

New words

Scancode
The keyboard's own code for a physical key, before the computer applies a layout.
Keycode
A number software uses for a key. The Linux kernel and XKB number keys differently.
Keysym
The symbolic meaning a layout gives a key, such as a, A, or BackSpace.
Character encoding
The rule that turns a character into bytes. ASCII and UTF-8 are common encodings.

Read the chain for one key

Goal: you will be able to trace a key from its hardware code to the byte a program receives, and say which layer owns each number.

Worked example

The xkbcli tool asks the active XKB rules which keycode and modifiers produce a requested keysym. This is the same lookup a Wayland compositor performs.

$ xkbcli how-to-type --layout us a | sed -n '1,8p'
keysym: a (0x0061)

=== Direct access ===

Captured on Arch Linux, 2026-11-13, with xkbcommon 1.13.2. The keycode 38 is the XKB and Wayland number. The kernel's own number for the same key is 30. The difference is the historical X11 offset of 8.

Try it

Ask the layout for three more keys, then confirm the byte for a letter.

$ xkbcli how-to-type --layout us z | sed -n '1,6p'
$ xkbcli how-to-type --layout us 0 | sed -n '1,6p'
$ xkbcli how-to-type --layout us --keysym BackSpace | sed -n '1,8p'
$ printf 'a' | od -An -tx1

Compare the keycode in each answer. Notice that the Backspace keysym has a keycode in the twenties, while a letter has one in the thirties or forties. The numbering is not alphabetical; it follows the physical keyboard matrix.

If it goes wrong

xkbcli: command not found
The tool comes from the libxkbcommon package. The command is optional; the rest of the page still applies.
A different keycode than the table
You are using a different layout, variant, or keyboard model. Add --layout and --variant to match your session, or read the layout from setxkbmap -query.
No such file or directory for a device
Device names such as /dev/input/event0 are not stable. List them with ls -l /dev/input/by-id/ instead of guessing a number.

On Tamlinux: the input chain is the standard Linux one: kernel driver, evdev, compositor, XKB, terminal. Tamlinux does not insert a remapping layer of its own before the compositor, so a standard tool such as xkbcli describes the same path the desktop uses.

Check yourself

Decide your answer before you reveal it.

Is 30 or 38 the Linux kernel keycode for the a key?

30 is the kernel keycode, KEY_A. 38 is the XKB and Wayland keycode, which is the kernel number plus 8. A terminal receives the second number, so a bug report that quotes 38 is usually talking about the compositor side.

Why can the same physical key produce a on one machine and q on another?

The hardware code can be identical while the active keyboard layout maps it to a different keysym. The layout, not the switch, changed. A remap at the XKB layer leaves the kernel keycode untouched.

A program reads the byte 0x61. Which layers has the key press already passed?

All of them up to the terminal encoder: hardware, kernel driver, evdev, compositor, XKB, and the terminal's byte encoder. The program is now at the last layer and sees only the byte, not the key that produced it.

How it works

A USB keyboard does not send letters. It sends a report containing a modifier byte and up to six usage IDs. The usage ID 0x04 means the key in the a position on a US keyboard. The kernel's usbhid driver maps the usage to a Linux keycode, and the input core emits an event through the evdev interface:

struct input_event {
    struct timeval time;   /* timestamp */
    __u16 type;            /* EV_KEY */
    __u16 code;            /* KEY_A = 30 */
    __s32 value;           /* 1 press, 0 release, 2 repeat */
};

On a graphical session, libinput reads those events through the seat manager. The compositor applies its keymap and sends wl_keyboard.key with the value code + 8, plus a wl_keyboard.modifiers event describing Shift, Ctrl, Alt, Meta, Caps Lock and Num Lock. The client passes the keycode and modifier mask to xkb_state_key_get_one_sym, which returns a keysym. The terminal emulator then runs its own encoder: printable keysyms become UTF-8 bytes, cursor keys become escape sequences, and chords may become control bytes.

On a kernel virtual console the compositor is absent. The kernel keyboard driver applies the console keymap directly and, in K_XLATE mode, converts the resulting keysym to bytes or escape sequences for the foreground program. The Linux text console covers that path.

Advanced usage

These commands are illustrative. They read device and layout information; none changes a setting.

$ ls -l /dev/input/by-id/
$ evtest /dev/input/by-id/usb-Example_Keyboard-event-kbd
$ wev
$ xkbcli compile-keymap --layout us | head -20

evtest prints the raw input_event stream, including EV_MSC scan codes when the driver supplies them. wev prints Wayland events for the focused surface, including keycodes and modifier state. xkbcli compile-keymap prints the keymap a compositor would compile from the same rules.

Edge cases

  • Key repeat is a third event value, 2, between press and release. A program that treats every non-zero value as a fresh press will repeat an action while a key is held.
  • Multiple keyboards can have different layouts or be merged into one seat. A keycode is only meaningful together with the device and keymap that produced it.
  • Media and vendor keys may arrive as EV_KEY codes outside the letter range, or as EV_MSC scan codes that no keymap entry covers. They may need a udev hardware database entry or setkeycodes.
  • Compose and dead keys produce a keysym only after a sequence. dead_acute followed by e becomes an e with an acute accent; no single key press carries the final character.
  • Layout groups let one keycode produce different keysyms depending on the selected group. The group is part of the modifier state, so the same keycode is not enough to predict the symbol.
  • Input methods can intercept keys before the application and commit text rather than keysyms. The application then receives composed text, not the original key events.

Check yourself

A user reports that one physical key types z in one window and y in another, while evtest shows the same kernel keycode. Where should you look, and what would you check first?

The kernel and hardware are consistent, so the difference is above evdev. Check the keymap or layout in each client: Wayland clients normally share the compositor's keymap, but a client can compile its own XKB keymap, an X11 application can have a different group, and an input method can compose text. Start with xkbcli how-to-type or setxkbmap -query for the session, then compare the two clients' environments and any per-application layout setting. Do not change the kernel keycode; the evidence says it is not the variable.
