Choosing a keybinding

This page turns the rest of the section into a decision: given a program that needs a command, which key should run it, and how do you know the key will arrive intact?

Pick a key that means one thing

Some keys have one job everywhere. F1 usually means help. The ? key types a question mark in text and often means help in a program that is not asking for text. Other keys are overloaded: Backspace may send one of two different bytes, and Ctrl + H may send the same byte as Backspace.

A good keybinding uses a key with one clear meaning at every layer between the keyboard and the program. A bad one uses a key that another layer has already claimed, or a key whose byte the program cannot tell apart from a different key.

Why it matters

If you choose badly, the command works on your machine and fails on someone else's, or works in one terminal and not another, or opens help every time the reader tries to delete a character. Those failures are hard to diagnose later because the binding looks correct in the source code.

How to think about it

Think of naming a street. A name that already exists in the same town causes mail to go to the wrong place, even though the name itself is fine. A key that already means something in the same layer causes the same confusion. Choose a name that is unused in every layer the letter must pass through.

Work through a real conflict

Goal: you will be able to test a candidate keybinding against the terminal, the line discipline and the shell, and explain the Ctrl + H help conflict in a libtam editor.

Worked example

A text editor built on libtam 0.7.0, named tam-edit and still in development, offers a help command on Ctrl + H. That is the traditional Emacs binding, and it is a trap in a terminal.

Start with what the terminal sends. foot sends 0x7F for Backspace and 0x08 for Ctrl + Backspace; the Linux console also declares 0x7F as its Backspace byte. The terminal database records that byte as kbs.

$ TERM=foot tput kbs | od -An -c
 177
$ infocmp -1 linux | grep -E '^\s+kbs='
	kbs=^?,
$ stty -a | tr ';' '\n' | grep erase
 erase = ^?

Captured on Arch Linux, 2026-11-13. All three agree that Backspace is 0x7F. So far 0x08 looks free.

Now look at what reads the byte. The libtam key decoder in version 0.7.0 maps both 0x08 and 0x7F to the same Backspace event:

/* libtam src/tam_key.c, abbreviated */
case 0x08:
case 0x7f:
    ev.key = TAM_KEY_BACKSPACE;
    break;

That collapse is reasonable for an editor that only needs a delete action, and it keeps Backspace working on terminals that send BS instead of DEL. It also means that after decoding, the editor cannot distinguish Ctrl + H from Backspace. The help command bound to Ctrl + H therefore fires whenever the reader presses Backspace, if the terminal sends 0x08 for Backspace or if the reader presses Ctrl + Backspace.

$ printf 'h\010i\nh\177i\n' | od -c
0000000   h  \b   i  \n   h 177   i  \n

These are different bytes on the wire, but the same event after the decoder. The collision is created by the decoder, not by the terminal.

The shells have already learned this lesson. Bash binds both bytes to the same action and offers no help on either:

$ bind -p | grep -E 'C-h|C-\?'
"\C-h": backward-delete-char
"\C-?": backward-delete-char

nano takes the other route: its help key is Ctrl + G, and Ctrl + H is left to mean Backspace. That is a useful precedent for any terminal program: do not put a command on a byte the reader expects to delete something.

Try it

Check a candidate key at each layer before you adopt it. Choose the chord you are considering and replace C-h below.

$ stty -a | tr ';' '\n' | grep -E 'intr|quit|erase|kill|eof|start|stop|susp|rprnt|werase|lnext|discard'
$ bind -p | grep -F '\C-h'
$ infocmp -1 "$TERM" | grep -E '^\s+(kbs|kcuu1|kf1)='
$ tput kbs | od -An -c

If the chord appears in the first list, the line discipline consumes it before any program sees it. If it appears in the second, the shell consumes it at a prompt. If the byte equals kbs or the first byte of a cursor sequence, the program cannot reliably tell it apart from those keys. A safe choice appears in none of these lists.

If it goes wrong

Help opens when the reader presses Backspace
The decoder collapsed 0x08 and 0x7F, or the terminal sends 0x08 for Backspace. Read kbs, treat that byte as Backspace, and move the command.
The chord never reaches the program
The terminal or the desktop consumed it. Read the terminal's key bindings first, then the compositor's.
The chord works in one terminal and not another
The byte differs, or the terminal reports a different kbs. Test with od in both terminals.
The chord works locally but not over SSH or in a multiplexer
The remote or inner TERM describes a different terminal, or the multiplexer uses the chord itself.

On Tamlinux: a program's keybindings are its own; the system does not reserve control bytes for it. The only fixed points are the kernel's line discipline defaults and the terminal's kbs declaration, both of which a program can read rather than assume.

Check yourself

Decide your answer before you reveal it.

Why is Ctrl + H a poor choice for a help command in a terminal program?

It produces 0x08, the ASCII BS code, which is also what some terminals send for Backspace and what some key decoders map to the same Backspace event. The command then competes with the most common editing key in the program.

What does the kbs capability tell you, and how would you use it?

It names the byte the terminal sends for Backspace. Read it and treat that byte as Backspace; the other byte of the pair can then be used for a different command, or at least reported as a distinct key. Hard-coding either byte assumes a terminal that may not be in use.

Why is F1 a safer choice than Ctrl + I even though both are single key presses?

F1 arrives as a multi-byte escape sequence that no text character and no line-discipline character uses, so it cannot be confused with typing. Ctrl + I is exactly the Tab byte, and Tab is both a text character and a completion key.

How it works

The reason these collisions exist is historical. The C0 control set was designed for teletypes, where 0x08 moved the carriage one position left, 0x0D returned it, and 0x0A advanced the paper. When video terminals arrived, the same bytes were reused for cursor movement and line editing. 0x7F came from paper tape, where a frame with every hole punched marked a character to be ignored, and it became the erase key on terminals that no longer needed BS for cursor movement.

Emacs inherited Ctrl + H as a help prefix from keyboards where BS was the help key on some systems and from the convention that control keys could carry commands. Terminals have never agreed. That is why nano chose Ctrl + G and why modern terminal programs generally avoid Ctrl + H for anything but deletion.

A principled decoder does not guess. It asks the terminal what its Backspace byte is, then uses that answer:

/* Prefer the terminal's declaration over a hard-coded pair. */
const char *kbs = tigetstr("kbs");       /* terminfo, e.g. "\177" or "\010" */
unsigned char bs = kbs ? (unsigned char)kbs[0] : 0x7f;

if (byte == bs) {
    ev.key = TAM_KEY_BACKSPACE;
} else if (byte == 0x08) {
    ev.key = TAM_KEY_CTRL_H;             /* only reachable when bs is not 0x08 */
} else if (byte == 0x7f) {
    ev.key = TAM_KEY_DEL;                /* Ctrl+? or Delete on this terminal */
}

This keeps Backspace working on every terminal and leaves Ctrl + H available exactly where the terminal distinguishes it. On a terminal that declares kbs=^H, Ctrl + H and Backspace are the same byte by definition, and no decoder can separate them; a program that needs a help key there must choose another key.

Two further points complete the design:

  • Ask for the terminal's extended reporting when you need the distinction. modifyOtherKeys and the kitty keyboard protocol can report Ctrl + I separately from Tab, Ctrl + M from Enter, and Ctrl + [ from Esc. They cannot report Ctrl + H separately from a Backspace key that sends kbs, because those are one byte at the source. A protocol fixes ambiguity between chords and keys, not between a chord and the byte the terminal assigns to a physical key.
  • Do not bind a key the terminal consumes. In foot, Ctrl + Shift + C, Ctrl + Shift + V, Ctrl + Shift + R, Ctrl + Shift + N and the font-size chords are terminal bindings by default, so a program cannot receive them. The same applies to compositor shortcuts, which are evaluated even earlier.

Advanced usage

A short checklist for a new binding, from the outside in:

  1. Compositor. Is the chord a desktop shortcut? Test with the window focused and unfocused.
  2. Terminal. Is it in the terminal's own bindings, or does it need a modifier the terminal reserves?
  3. Line discipline. Does it match intr, quit, erase, kill, eof, start, stop, susp, rprnt, werase, lnext or discard? A full-screen program can clear these, but the prompt cannot.
  4. Shell. Is it in bind -p, or in the shell's own keymap for vi mode?
  5. Multiplexer. Is it a prefix or a binding in tmux list-keys?
  6. Transport. Does it survive SSH and a nested terminal, and does the remote terminfo describe the sequence?
  7. Decoding. Is the byte pair ambiguous, such as 0x08 with Backspace, or 0x1B with Esc? If so, does the program read kbs and ask for extended reporting, or avoid the key?
  8. People. Is it reachable one-handed, does it work on the layouts you support, and is it documented in the program's help?

For tam-edit, the resolution that follows from these rules is to stop treating Ctrl + H as available. Help belongs on a key that cannot be a text character and is not a line-discipline character: F1, with ? as an alias when the editor is not accepting text, and a configurable binding for readers who prefer something else. The decoder should still read kbs and report the two bytes separately, because other commands may want the distinction even if help no longer does.

Edge cases

  • Terminals that send BS for Backspace. Some serial consoles and some X11 configurations declare kbs=^H. There Ctrl + H is Backspace, and the program must not bind it to anything else.
  • Users who change erase. stty erase ^H changes what the line discipline erases, but not what the terminal sends. A program in canonical mode then sees a different byte consumed than kbs suggests.
  • Delete versus Backspace. Some keyboards have both keys and send different bytes for each, such as ESC [ 3 ~ for Delete. Do not assume the two are interchangeable.
  • Layouts that move punctuation. A chord defined on a character moves with the layout. A chord defined on a key position does not. Pick deliberately and document which one you mean.
  • Meta and Alt. Alt sends an ESC prefix, so Alt and a letter is the same bytes as Esc followed by that letter. A binding on ESC plus a letter can therefore fire from two different intentions.
  • Terminal multiplexers. tmux may rewrite the sequence for the inner program. A binding that depends on one terminal's exact bytes can break even when the outer terminal is unchanged.
  • Accessibility. Sticky keys and on-screen keyboards change modifier timing and event order. A chord that requires three simultaneous keys is harder to use with those tools.

Check yourself

A reviewer proposes moving the help command to Ctrl + _ because it is unused by the line discipline. Evaluate the proposal and give a better one, with the evidence you would require.

Ctrl + _ is 0x1F, which the line discipline does not claim by default, so the first objection is weaker than for Ctrl + H. But it is still a control byte with existing meanings: Readline binds it to undo, Emacs treats it as undo, and some terminals use it for other purposes. It is also hard to type on layouts where _ requires Shift, and it collides with a common editor action. The stronger choice is a key that is not a text character at all, such as F1, which arrives as an escape sequence and cannot be produced by typing; a ? alias is fine where text entry is inactive. Evidence to require: the byte the terminal sends (checked with od in each supported terminal), the terminal's kbs, the shell's bind -p, the desktop and terminal binding lists, and a test over SSH and in a multiplexer. If the program keeps Ctrl + H for compatibility, it must read kbs and document that the binding is unavailable on terminals whose Backspace is 0x08.
