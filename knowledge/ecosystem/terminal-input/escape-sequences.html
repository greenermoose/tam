Escape sequences

This page explains why one key press can send three or more bytes, how those bytes are structured, and how a program turns them back into "the Up key was pressed".

One key, several bytes

A letter is one byte. Most other keys are not. Press Up in a terminal, and the terminal sends three bytes: escape, then [, then A. Press F1 and it sends three different bytes. This is not an accident. The terminal protocol was designed for machines that had only letters and numbers, so every extra key had to be spelled out with byte sequences.

The escape byte, 0x1B, is the flag that says "the following bytes are a command, not text". A program that sees it knows to keep reading until the command is complete.

Why it matters

When arrow keys stop working, or when pressing Up types ^[[A into a document, the cause is in this encoding or decoding step. The bytes are fine; someone is reading them as text instead of as a key. Knowing the shape of a sequence tells you which program is misreading it.

How to think about it

Think of a train announcement. A single word is a station name. A longer announcement starts with a chime. The chime tells you that the next words are an instruction, not part of the conversation. ESC is the chime, and the bytes after it are the instruction.

New words

Escape sequence
A short instruction that begins with the escape byte, used for keys and for cursor and screen control.
Control sequence
A sequence introduced by ESC [ or by the single byte 0x9B.
Terminfo
A database describing what each terminal sends and expects. Programs read it instead of hard-coding byte strings.

Print the bytes for a key

Goal: you will be able to print the sequence a terminal uses for a key, recognise its parts, and explain why the same key has different bytes in different terminals.

Worked example

tput reads the terminal database and writes the sequence for a named capability. od then shows the bytes.

$ TERM=foot tput kcuu1 | od -An -c
 033   O   A
$ TERM=foot tput kf1 | od -An -c
 033   O   P
$ TERM=foot tput kf5 | od -An -c
 033   [   1   5   ~

Captured on Arch Linux, 2026-11-13. 033 is octal for 0x1B, the escape byte. So Up is ESC O A and F5 is ESC [ 1 5 ~.

Every sequence in this part of the protocol has the same anatomy:

PartBytesMeaning
IntroducerESC [ or ESC OESC [ starts a control sequence; ESC O starts a single-character sequence
Parametersdigits and ;numbers such as a count, a row, or a modifier
Final bytea letter or ~which command it is
Terminatoroften nonethe final byte ends most sequences

So ESC [ 1 5 ~ is a control sequence with the parameter 15 and the final byte ~, which the database assigns to F5. ESC O A uses the shorter form because it carries no parameters.

Curses-style libraries also ask for the sequences that control the screen, because the input and output sides share the same grammar:

$ TERM=foot tput cup 3 5 | od -An -c
 033   [   4   ;   6   H
$ TERM=foot tput civis | od -An -c
 033   [   ?   2   5   l
$ TERM=foot tput sgr0 | od -An -c
 033   (   B 033   [   m

cup moves the cursor; the arguments are zero-based, so row 3 column 5 becomes 4;6. civis hides the cursor with the private parameter ?. sgr0 resets attributes and also leaves the alternate character set. All three are ordinary control sequences, and the terminal is expected to interpret them whenever they appear in its output.

Try it

Compare the same keys across three terminal types.

$ for t in foot xterm-256color linux; do
>   printf '%s: ' "$t"
>   TERM=$t tput kf1 | od -An -c
> done
$ TERM=linux tput khome | od -An -c
$ TERM=linux tput kend | od -An -c

The Linux console sends ESC [ [ A for F1, which is a control sequence whose only parameter-like byte is a second [. Its Home and End are ESC [ 1 ~ and ESC [ 4 ~. A program that hard-codes the foot sequences will fail on the console, which is why programs use the database.

If it goes wrong

Pressing Up inserts ^[[A into a document
The program is treating the bytes as text. It is either not a full-screen program, or it does not recognise the sequence for the current TERM.
Pressing Esc in an editor pauses before acting
A lone 0x1B is also the first byte of every sequence, so the program waits briefly to see whether more bytes follow. The delay is configurable in many editors.
tput: No value for $TERM and no -T specified
TERM is unset, which commonly happens in a cron job or a service. Set TERM explicitly or avoid terminal output in that context.
tput: unknown terminal
The database has no entry with that name, or TERMINFO and TERMINFO_DIRS point somewhere without it. Check echo $TERM and the installed entry.
The screen is full of ^[ and brackets after cat of a binary file
The file contained escape sequences and the terminal executed them. Run reset, and use cat -v for untrusted content.

On Tamlinux: the sequences come from the installed terminfo database and the terminal emulator, not from a Tamlinux convention. foot advertises TERM=foot, and the database entry is the upstream one. Changing TERM by hand to make one program work usually breaks another.

Check yourself

Decide your answer before you reveal it.

Which bytes does the sequence ESC [ 1 ; 5 A contain, and what is the 5 likely to mean?

Escape, [, 1, ;, 5, A. The parameters are 1 and 5; in the xterm convention the second parameter is one plus a modifier bitmask, so 5 means Ctrl and the sequence is Ctrl plus Up.

Why is F1 ESC O P in foot but ESC [ [ A on the Linux console?

They are different terminals with different encodings. The database records both, and a program reads the entry for the current TERM instead of assuming one form.

Can a program tell Esc from Ctrl + [ by looking at the bytes?

No, in the legacy encoding both produce 0x1B. Separate reporting requires an extended protocol, such as modifyOtherKeys or the kitty keyboard protocol, that the program must enable.

Reference: the escape-sequence grammar

The CSI form is defined by ECMA-48 with a fixed byte order: the introducer, then parameter bytes in the range 0x30 to 0x3F, then intermediate bytes in 0x20 to 0x2F, then a final byte in 0x40 to 0x7E. A private parameter begins with a character from < = > ?, which is why cursor visibility is ESC [ ? 25 l. The final byte selects the function: A to D are cursor keys, H is cursor position, m is character attributes, h and l set and reset modes.

Modifiers on cursor keys and function keys use the parameter form 1 ; n, where n is one plus a bitmask: Shift is 1, Alt is 2, Ctrl is 4, so Shift plus Up is ESC [ 1 ; 2 A, Alt plus Up is ESC [ 1 ; 3 A, and Ctrl plus Up is ESC [ 1 ; 5 A. The same convention applies to keys encoded with a numeric final byte, such as ESC [ 15 ; 5 ~ for Ctrl plus F5.

How it works

A terminal emulator has two jobs with this grammar. On the input side it writes the sequences for the keys it decides to encode. On the output side it parses the byte stream from the program and performs the requested actions. Input sequences are the ones a program reads; output sequences are the ones a program writes.

A program that wants key input in raw mode reads bytes and runs a state machine:

  1. Read a byte. If it is not 0x1B, handle it as a character or control byte.
  2. If it is 0x1B, look at the next byte. If there is none within a short timeout, the key was Esc.
  3. If the next byte is [ or O, collect parameter and intermediate bytes until a final byte arrives.
  4. Decode the pair of introducer and final byte, with parameters, into a key symbol. If the sequence is unknown, discard it or pass it through.

The timeout in step 2 is the famous Esc delay. A program cannot know whether 0x1B is a complete key or the start of a longer sequence until either more bytes arrive or a short wait expires. Editors expose the wait as ESCDELAY or an equivalent setting. A program that sets the wait to zero breaks every function key; one that sets it too long makes Esc feel unresponsive. Over slow or jittery SSH links, if 0x1B arrives before the rest of F1 (4F 50 or 5B 5B 41), an early timeout fires Esc and inserts literal OP or [[A into the buffer (or a naive parser decodes 1B 4F as Alt + O followed by P). Robust decoders treat \x1bO (SS3) and \x1b[ (CSI) as unambiguous prefixes that wait longer for sequence completion once the second byte arrives.

Curses libraries avoid most of this decoding work. keypad(TRUE) makes ncurses send smkx, which enables application cursor mode, and then translate the terminal's sequences into KEY_UP, KEY_F(1) and similar constants. That is why the sequence a program receives depends on whether it enabled keypad mode, and why the database records the application-mode form.

Advanced usage

Two extensions carry information the legacy encoding cannot:

  • modifyOtherKeys reports a modified key as ESC [ 27 ; modifier ; code ~, where code is the character code. It disambiguates chords such as Ctrl + I from Tab.
  • The kitty keyboard protocol reports a key as ESC [ code ; modifier u, with optional sub-parameters for event type, alternate keys and associated text. It also reports key release and repeat events.

The output side includes replies that programs must read carefully. A device attributes query returns a sequence such as ESC [ ? 1 ; 2 c, and a cursor position report returns ESC [ row ; col R. These replies are written by the terminal into the same input stream the program reads, so a program that queries the terminal and then reads a key must skip the reply. A program that prints a fake reply can confuse the next reader, which is one reason to distrust escape sequences that arrive from untrusted output rather than from the keyboard.

$ TERM=foot infocmp -1 | grep -E '^\s+(kcuu1|kcud1|kcub1|kcuf1|kf1|kf5|khome|kend)='
$ printf '\033[1;5A' | od -An -tx1 -c
$ printf '\033[1;5A' | cat -v

The first command shows the input capabilities for the current entry; the others show the raw and caret forms of a modified cursor key. None of these change the terminal.

Edge cases

  • 8-bit C1 introducers. 0x9B is a single-byte CSI in ISO 8859-1, but it is not valid UTF-8. In a UTF-8 locale a terminal must not treat a bare 0x9B as CSI, and programs should not send it.
  • Unknown sequences. A program that does not recognise a sequence must consume it fully, or its remainder will be read as text. A robust decoder consumes up to the final byte and discards.
  • Truncated sequences. A read can return part of a sequence. Decoders must buffer across reads, not assume one read contains one key.
  • ESC at end of file. A stream that ends after 0x1B is ambiguous; a decoder must decide whether to report Esc or an error.
  • Output injection. Printing untrusted bytes lets them control the terminal: changing colours, writing to the clipboard through OSC 52, or moving the cursor to disguise text. Use a pager or cat -v, and prefer terminals that restrict risky sequences.
  • Bracketed paste. The mode wraps pasted text in ESC [ 200 ~ and ESC [ 201 ~ so an editor can refuse to interpret pasted control bytes as commands.
  • Mouse reporting. Enabling mouse mode makes the terminal send sequences for clicks and motion, which are input events but not key presses. A program must disable the mode before exiting.
  • Focus events. Some terminals report focus changes as sequences, adding input the program did not ask for unless it enabled the mode.

Check yourself

A terminal application receives the bytes ESC [ 1 ; 2 A and treats them as an unknown sequence, but receives ESC O A correctly. What is the likely design fault, and what would you check before changing the terminal's key encoding?

The decoder understands the SS3 form but not CSI sequences with parameters. ESC [ 1 ; 2 A is Shift plus Up under the xterm modifier convention, while ESC O A is plain Up in application cursor mode. Check the program's decoder: it should parse the introducer, collect parameter bytes, then interpret the final byte with the modifier bitmask. Also check whether the program enabled keypad mode and whether it reads the terminal's capabilities. Changing the terminal's output would only hide the fault and would break other modified keys.
