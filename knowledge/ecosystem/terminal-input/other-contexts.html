Other places keys are handled

This page maps the places that can take a key press before the program you are looking at, and shows how to find out which one took it.

Several programs share one keyboard

You press one key, but several programs are running. The desktop, the terminal window, the shell, an editor, a multiplexer and a remote server may all care about that key. Only one of them gets to act on it.

The rule is usually focus plus priority. The desktop sees every key first and may act on a shortcut. Then the focused window sees it, and the terminal may act on its own shortcuts. Whatever is left is written to the program as bytes. If a program never receives a key you pressed, something earlier in that list took it.

Why it matters

"This shortcut does not work" is rarely one problem. It may be a desktop shortcut, a terminal shortcut, a shell binding, or a missing byte. Without knowing the order, you cannot tell which. With the order, the first test is obvious: find the earliest layer that reacts.

How to think about it

Think of a queue of assistants between you and a specialist. Each assistant may take the paper if it has an instruction for that word. Only the assistants who do not care pass it on. When the specialist says "I never saw it", you ask each assistant in turn.

New words

Keybinding
An instruction that a particular program runs when a key or chord is pressed.
Focus
The window or field that receives typing. Only one has it at a time.
Prefix key
A key that makes the next key a command instead of text, used by tmux and screen.
Readline
The line-editing library used by many shells and interactive programs.

Find the layer that took the key

Goal: you will be able to trace one chord through desktop, terminal, shell and program, and identify which layer consumed it.

Worked example

Take Ctrl + Shift + C. In foot it copies the selection, because foot binds it. The bytes never reach the program in the window.

$ man 5 foot.ini | col -b | grep -A2 '^     clipboard-copy'
     clipboard-copy
	 Copies  the  current  selection  into  the  clipboard.  Default:  Con‐
	 trol+Shift+c XF86Copy.

Now compare with Ctrl + C, which foot does not bind as a shortcut. foot sends 0x03, the line discipline turns it into SIGINT, and the foreground command stops. The same physical C key, with a different modifier set, is handled at a different layer.

The order of the layers is what makes this predictable. A key travels from the compositor inward, and each layer either consumes it or passes it on.

Try it

Test one chord at a time. These commands are read-only and do not change any bindings.

$ bind -p | grep -E '\\C-a|\\C-h|\\C-k|\\C-l' | head
$ cat -v

With cat -v running, press Ctrl + A and then Enter. You see ^A, because cat does not bind Ctrl + A; the byte was passed through. Exit and press Ctrl + A at the prompt: the cursor jumps to the start of the line, because Bash's Readline took it. Then try Ctrl + Shift + C inside cat -v: nothing appears, because foot took it before the program saw anything.

If it goes wrong

A desktop shortcut fires instead of the program
The compositor consumed the chord. Choose a different chord for the program, or change the desktop binding if the program's need is stronger.
A chord does nothing anywhere
Something consumed it silently. Check the terminal's key bindings, then the desktop's, then any multiplexer or editor that is running.
A tmux session ignores normal typing
A prefix key is pending. Press the prefix twice to send it literally, or press Escape to cancel the pending command.
Keys work locally but not over SSH
The remote TERM may name a terminal whose sequences differ, or no terminal was allocated. Check echo $TERM on both sides and whether the session has a tty.
Function keys insert odd characters in a remote session
The remote terminfo entry and the local terminal disagree. Forward the right TERM, or install the matching entry on the server.

On Tamlinux: desktop shortcuts belong to the compositor and are configured in its bindings, while terminal shortcuts belong to foot's own configuration. The two sets are separate, and a chord can appear in both. Check the compositor first, because it sees the key first.

Check yourself

Decide your answer before you reveal it.

Why does Ctrl + Shift + C not stop a running command in foot?

foot binds that chord to copying the selection and consumes it. The program never receives 0x03. Ctrl + C without Shift is not bound by foot, so it reaches the line discipline and becomes SIGINT.

Who handles a key first: the shell or the compositor?

The compositor. It receives the key from the kernel, applies layout and modifier state, and checks its own shortcuts before delivering the key to the focused window. The shell only sees bytes that survive the layers in between.

Does SSH forward key presses to the server?

No. The local terminal turns keys into bytes, and SSH forwards those bytes through a pseudo-terminal on the server. The server's programs read bytes under the server's TERM, so a terminal mismatch changes what the remote program believes about the keyboard.

How it works

On Wayland there is no passive key grab for ordinary clients. The compositor owns the keyboard, decides focus, and sends wl_keyboard.key only to the focused surface. A compositor binding is evaluated before delivery, so an application cannot win against a global shortcut. Some compositors offer a way to exempt a window or to bind a chord only in certain conditions, but the default order stands.

X11 applications under XWayland are different. X11 has XGrabKey, and a grab can take a chord for one client regardless of focus. A misbehaving or misconfigured X11 program can therefore swallow a key for the whole session, which is one reason a "keyboard problem" sometimes disappears when an unrelated window closes.

A terminal emulator is a client like any other. foot receives keycodes and decides between its own bindings and encoding bytes for the program. Its manual notes that key bindings use the translated form of a chord, so Control+Shift+c matches the character the layout produces, while raw-mode bindings match the key position. That distinction matters on layouts where Shift changes the character.

Inside the pty, the line discipline runs next. After that, a shell's Readline consumes its editing chords. A full-screen program clears the discipline's editing and signal handling and parses bytes itself, which is why the same chord can be a signal at the prompt and a command inside an editor.

Remote and multiplexed sessions add their own layer:

  • SSH allocates a pseudo-terminal with -t and forwards bytes. It does not forward keys or layouts. The server's TERM comes from the client's environment, subject to SendEnv and the server's AcceptEnv, and the remote terminfo entry must describe the client terminal.
  • tmux and screen run a terminal emulator of their own on the server side. They publish a TERM value such as tmux-256color or screen-256color, re-encode keys for the inner program, and consume their prefix key before anything else. Extended key reporting must be enabled on both sides to survive the trip.
  • Nested sessions multiply the prefixes: a tmux inside SSH inside foot has two prefix layers and two terminal descriptions, and the inner program sees the innermost one.
  • Web terminals run a terminal emulator in the browser and send its bytes to a server. The browser's own shortcuts still apply first, so a chord can be lost before the emulator sees it.
  • Input methods sit beside the key path. When they are active, they may consume keys to compose text and commit the result, so the application receives text rather than the key that produced it.
  • Accessibility tools can intercept keys globally. Sticky keys change modifier timing, and an on-screen keyboard injects events through a virtual keyboard protocol, which some applications treat differently from real hardware.

Advanced usage

These commands observe each layer without changing it.

$ wev
$ libinput debug-events --show-keycodes
$ bind -p | grep -c .
$ tmux list-keys | head
$ foot --version
$ printf 'TERM=%s\n' "$TERM"

wev shows what reaches a Wayland surface, including keycodes and modifier masks, so it distinguishes "the compositor took it" from "the window received it". libinput debug-events shows the layer below the compositor. bind -p lists Readline bindings, tmux list-keys lists the multiplexer's, and the last two commands identify the terminal and its advertised type.

Edge cases

  • A grab outlives its program. A crashed X11 client can leave a passive grab that persists until the connection closes, which usually happens when the process exits.
  • Layout-dependent bindings. A binding on a character can move when the layout changes; a binding on a key position does not. Decide which one you mean.
  • Terminal shortcuts that shadow control bytes. Binding a chord the terminal already uses makes it unreachable for the program, even if the program has a better use for it.
  • Prefix keys and pasted text. A paste containing the prefix key can trigger a multiplexer command. Bracketed paste does not protect a multiplexer's own prefix handling.
  • Missing pty. A command run without a terminal has no line discipline and no window size. Interactive programs may refuse to start or behave differently.
  • Terminal type mismatch. A remote TERM that names the wrong terminal produces wrong sequences in both directions: keys are misread and screen updates are garbled.
  • Suspended jobs. A stopped job keeps the terminal settings it had at the moment it stopped. Resuming it restores those settings, which can undo a change made in between.

Check yourself

A user reports that Ctrl + Shift + R does nothing in an editor running inside tmux inside foot, although the editor's documentation says it reloads the file. Give an ordered diagnosis.

Start at the outermost layer. In foot, Control+Shift+r starts scrollback search by default, so the chord is probably consumed before the pty; confirm with wev and by testing the same chord in a plain foot window without tmux. If foot passes it, check tmux: it has its own key table, and the chord may be bound or swallowed by the prefix handling; tmux list-keys answers that. Then check whether tmux forwards the extended encoding the editor needs, and whether the inner TERM supports it. Only after those should you look at the editor, for example whether it enabled the keyboard protocol it uses for that chord. Each step names one layer, so the first layer that blocks the chord is the one to change.
