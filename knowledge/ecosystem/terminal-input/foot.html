Keys inside foot

This page follows a key press inside a terminal window: how the compositor delivers it to the foot terminal emulator, and what foot writes to the program that runs in that window.

A window that acts like a text screen

A terminal window is not a text screen. It is a program that pretends to be one. The program is called a terminal emulator, and the one used in this section is foot, which runs on Wayland.

Inside the window you see a shell prompt and the output of commands. The shell does not talk to the keyboard directly. foot reads your key presses, decides which bytes represent them, and hands those bytes to the shell through a private connection called a pseudo-terminal.

Why it matters

Two things can go wrong when you press a key in a terminal window. foot may send a byte you did not expect, or the program may expect a different byte from the one foot sent. The first is the terminal's job; the second is the program's job. This page separates them, so you can tell which one is at fault.

How to think about it

Think of a translator sitting between two people. You speak a key press. The shell understands bytes. foot translates, and its dictionary is not the same as the one used on a text console. If a translation surprises you, ask the translator what it sent, not what you said.

New words

Terminal emulator
A program that behaves like a text terminal inside a graphical window. foot is one; so are Alacritty, Kitty and GNOME Terminal.
Pseudo-terminal
A pair of connected devices that lets one program act as a terminal for another. foot holds the master side; the shell holds the slave side.
Modifier key
A key that changes another key instead of producing a character, such as Shift, Ctrl and Alt.

Ask foot what it sends

Goal: you will be able to predict the bytes foot sends for ordinary keys, Backspace, Ctrl + Backspace, Alt chords, and function keys, and verify the answer inside a terminal window.

Worked example

The terminal database records what a terminal is supposed to send. infocmp prints that record for the foot entry.

$ infocmp -1 foot | grep -E '^\s+(kbs|kcuu1|kcub1|kf1|kf5|khome|kend)='
	kbs=^?,
	kcub1=\EOD,
	kcuu1=\EOA,
	kend=\EOF,
	kf1=\EOP,
	kf5=\E[15~,
	khome=\EOH,

Captured on Arch Linux, 2026-11-13, with foot 1.28.0. \E is the escape byte 0x1B and ^? is 0x7F. So foot sends 0x7F for Backspace, and ESC O A for Up.

There is a qualification that matters for diagnosing real problems. The value of kcuu1 in the database is the sequence used in application cursor mode, which a full-screen program requests. Pressed at an ordinary shell prompt, Up sends ESC [ A. Both are correct; they belong to different modes.

$ tput smkx | od -An -c
 033   [   ?   1   h 033   =
$ TERM=foot tput kcuu1 | od -An -c
 033   O   A

The first command shows the request a program sends to switch the cursor keys into application mode: ESC [ ? 1 h enables the DECCKM mode and ESC = selects application keypad mode. After that request, Up sends ESC O A, which is the sequence kcuu1 names.

Try it

Run this inside foot. The Ctrl + V prefix, called the literal-next character, tells the line discipline to pass the next byte through instead of acting on it. That makes control bytes visible in ordinary typing.

$ cat -v

Then press these keys, pressing Enter after each, and compare with the explanation. End with Ctrl + D.

KeyWhat you seeWhy
Ctrl + V, then Ctrl + A^A0x01 is shown in caret notation
Ctrl + V, then Backspace^?foot sent 0x7F
Ctrl + V, then Ctrl + Backspace^Hfoot sent 0x08
Ctrl + V, then Alt and a^[aAlt is sent as an escape prefix
Ctrl + V, then Up^[[AA three-byte cursor sequence

For exact bytes rather than caret notation, feed the keys to od instead:

$ od -An -tx1 -c

Press a few keys, press Enter, then Ctrl + D. The output shows the bytes foot wrote, including the byte the line discipline added for Enter.

If it goes wrong

Backspace prints ^H and does not delete
You are in a context that receives 0x08, usually because you pressed Ctrl + Backspace, or because the program is in raw mode and does not treat the byte as erase.
cat -v shows nothing until you press Enter
That is canonical mode: the line discipline holds the line until Enter, then hands it to cat. Ctrl + V works because literal-next is handled before the line is complete.
Typing produces strange characters after a raw-mode program exits
The program left the terminal in raw mode. Type stty sane followed by Enter, or run reset. Closing the window also restores a fresh terminal.
infocmp: couldn't open terminfo file foot
The TERM value is different, or the terminfo database does not have the entry. Print echo $TERM and use that name.
Arrow keys insert ^[[A as text
The program is reading bytes but not decoding escape sequences, which happens when a program expects a different terminal type. Check TERM and the program's documentation.

On Tamlinux: foot is the terminal emulator used by the desktop session, and it reads the same Wayland key events as every other application. Tamlinux does not patch foot's key encoder, so the sequences described here match the upstream foot documentation for the installed version.

Check yourself

Decide your answer before you reveal it.

Which byte does foot send when you press Backspace, and which when you press Ctrl + Backspace?

Backspace sends 0x7F, the DEL code. Ctrl + Backspace sends 0x08, the ASCII BS code. foot documents both, and it does not implement the DECBKM mode that would let a program ask for BS instead.

Why does the database say Up is ESC O A when pressing Up at a prompt sends ESC [ A?

The database value describes application cursor mode, which a full-screen program requests by sending ESC [ ? 1 h. At an ordinary prompt that mode is off, so foot uses the normal form ESC [ A. Both sequences are correct in their own mode.

What does pressing Alt and a send?

ESC followed by a, that is 0x1B 0x61. foot prefixes the key with an escape byte instead of setting the high bit of the character.

How it works

foot receives wl_keyboard.key with a Wayland keycode, plus a wl_keyboard.modifiers event carrying the Shift, Ctrl, Alt, Meta, Caps Lock and Num Lock state. It applies the compositor's keymap with xkbcommon and obtains a keysym. From there it chooses one of several encodings:

  • Printable keysym. The character is encoded as UTF-8 and written unchanged. A keysym that is not printable but has a Unicode equivalent is sent as its character when the layout says so.
  • Ctrl with a letter or symbol. The control byte is derived from the character with the mask & 0x1F, so Ctrl + H is 0x08. Ctrl + Space and Ctrl + @ become 0x00; Ctrl + ? becomes 0x7F.
  • Alt with any key. Alt is not a control byte in foot. It prefixes the key's own encoding with ESC, so Alt and a is ESC a and Alt and Up is ESC ESC [ A.
  • Cursor keys, function keys and editing keys. These use fixed sequences, normally the ESC [ form and the ESC O form in application cursor mode. Modified cursor keys use the xterm parameter form, where the modifier is encoded as a number after a semicolon.
  • Backspace. 0x7F. Ctrl + Backspace is 0x08. foot's manual states that DECBKM is not implemented, so a program cannot ask foot to send 0x08 for Backspace through that mode.

The escape byte prefix is why Ctrl + [ and the Esc key are hard to distinguish: both produce 0x1B. A program reads 0x1B and cannot know whether the reader pressed Esc or a chord, unless the terminal reports the chord separately.

Advanced usage

foot implements two mechanisms that remove some of that ambiguity. Both are opt-in: a program must ask, and a program that does not ask sees the legacy bytes.

modifyOtherKeys. The program enables it with CSI > 4 ; 2 m, and foot also has a default level for programs that do not ask. Once enabled, a chord that would otherwise be a single control byte is reported as CSI 27 ; modifier ; code ~, so the reader's exact chord can be recovered. foot's changelog records support from 1.10.0 and states that the default level is 1, with level 0 not supported.

The kitty keyboard protocol. A program enables it with CSI > flags u and can query the current flags with CSI ? u. The flags select progressively more information: disambiguate escape codes, report event types such as press and release, report alternate keys, report all keys as escape codes, and report associated text. foot's changelog records initial support in 1.10.2 and the wider set of flags in 1.10.3. With disambiguation enabled, Ctrl + I and Tab, Ctrl + M and Enter, and Ctrl + [ and Esc become distinguishable, which no legacy encoding can do.

$ infocmp -1 foot | grep -E '^\s+(XM|kmous|Ms|colors|pairs)='
$ man 7 foot-ctlseqs | col -b | grep -n -m 5 -i 'modifyOtherKeys'

The first command reads optional capabilities from the terminfo entry; the second searches foot's control-sequence reference for the keyboard protocols. Neither changes any state.

Edge cases

  • Application cursor mode leaks. A program that sends ESC [ ? 1 h and exits without sending ESC [ ? 1 l leaves the terminal in that mode, so the shell sees ESC O A for Up. A modern shell usually repairs the mode, but a crash may not.
  • Aliased keys. Tab and Ctrl + I are one byte, as are Enter and Ctrl + M. Only the modern protocols separate them.
  • Key repeat is generated by the compositor, and foot sees a stream of press events. A program using the kitty protocol can receive repeat and release events, which changes what "one key press" means.
  • Layout groups and dead keys. The keysym depends on the active group and on pending dead keys. A dead key produces no bytes until the following key completes the character.
  • Input methods. When an input method is active for the window, composed text may arrive through text-input or as committed strings, not as individual key events. The bytes the program reads are then text, not keys.
  • Text bindings and key bindings. foot's configuration can bind a chord to text or to an action. A binding that foot consumes never reaches the program, which looks like a missing keystroke rather than a wrong byte.
  • Bracketed paste. foot supports the bracketed-paste mode, so an editor can tell pasted text from typed keys and avoid executing a pasted 0x03 as a command.

Check yourself

A program running in foot reports that Up arrives as ESC O A in one session and ESC [ A in another, with the same foot version and the same keyboard. What is the most likely explanation, and what would you check before touching the terminfo entry?

The two sessions are in different cursor-key modes. The first program enabled application cursor mode with ESC [ ? 1 h, which is what tput smkx and ncurses' keypad(TRUE) do; the other did not. Check which program is running, whether it calls keypad or sends smkx, and whether a previous program left the mode enabled after exiting. The terminfo entry is not wrong: it records the application-mode sequence, and a correct program either uses the mode it requested or accepts both forms. Changing the database would break the program that does request the mode.
