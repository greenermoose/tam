Serial and parallel communication channels

This page explains how computers send data across serial and parallel channels, and how simplex, half-duplex, and full-duplex communication modes operate.

At the silicon level, data inside a computer consists of patterns of binary bits. To exchange information between separate chips, expansion cards, or external peripherals, those bits must travel across physical communication channels. Understanding the architectural differences between sending bits one by one (serial) versus sending them side-by-side (parallel), why modern computing abandoned wide parallel ribbon cables for high-speed serial lanes, and how devices coordinate transmission directionality clarifies system interconnect design.

How do bits move between parts?

Computer components cannot communicate unless they agree on how data moves. If you connect a half-duplex sensor to a full-duplex port, or mistake a serial terminal for a parallel printer interface, devices cannot understand each other. Recognizing how channels deliver bits helps you select the right cables, configure terminal connections, and troubleshoot communication failures.

Mental model

Synchronous Transmission (Shared Clock Wire):
  Data Line:   ---[ D0 ]---[ D1 ]---[ D2 ]---[ D3 ]--->
  Clock Line:  ___/---\___/---\___/---\___/---\___/---> (Sample strictly on edge)

Asynchronous Transmission (No Clock Wire - Agreed Timing):
  Idle (1) ===\___[ D0 ][ D1 ][ D2 ][ D3 ][ D4 ][ D5 ][ D6 ][ D7 ][ P ]/=== Idle
              Start                                                   Stop
              (Receiver aligns local timer and samples at 1.5, 2.5, 3.5... bit periods)

Clock Skew in Parallel Buses:
  Wire 1: ----[ Bit 0 ]-------> Arrives at t = 1.00 ns  (VALID)
  Wire 2: ------[ Bit 1 ]-----> Arrives at t = 1.05 ns  (SKEW DELAY)
  Wire 3: --------[ Bit 2 ]---> Arrives at t = 1.12 ns  (VIOLATES SETUP TIME)

When sending data, the receiver must know when to sample the line to distinguish a 0 from a 1. Digital communication solves this through two primary timing models:

  • Synchronous communication: A dedicated physical wire carries a pulsating clock signal alongside the data wires. The receiver samples the data wire strictly on the rising or falling edge of that clock pulse. Examples include SPI (Serial Peripheral Interface), I²C, and internal CPU memory buses.
  • Asynchronous communication: There is no separate clock wire. The transmitter and receiver agree in advance on an exact transmission speed (baud rate). The line rests at high voltage (Idle / Mark). When a byte is sent, the transmitter pulls the line low for one bit duration (the Start bit), which resets and aligns the receiver's internal timer. The receiver then samples the line at precise fractional intervals to read the data bits before returning to line reset (the Stop bit). The classic example is the Universal Asynchronous Receiver-Transmitter (UART / RS-232).

If it goes wrong

stty: 'standard input': Inappropriate ioctl for device
The command was run in a non-interactive script or redirected pipe with no attached terminal. Run stty -a < /dev/tty to bind explicitly to your controlling terminal.
Terminal stops echoing typed keys
A crashed command left the terminal in raw no-echo mode. Type stty sane and press Enter (even though characters are invisible) to restore standard full-duplex terminal behavior.

Why did modern computers replace wide parallel ribbon cables with fast serial cables?

At gigahertz frequencies, physical variations in wire length cause clock skew (bits arriving at slightly different times across parallel conductors) and electromagnetic crosstalk between adjacent wires corrupts data. Ultra-fast serial links eliminate clock skew entirely by sending all bits down a single high-speed path.

What happens if both sides attempt to transmit simultaneously on a half-duplex communication channel?

Their electrical signals overlap and interfere on the shared medium, causing a packet collision that corrupts data for both receivers. Devices must detect the collision and wait to retransmit.

What physical requirement enables a communication link to operate in full duplex?

It requires separate, isolated physical pathways for transmission and reception (such as independent Transmit and Receive copper wire pairs or separate optical fibers), allowing concurrent traffic with zero collisions.

How it works: SerDes and Clock Data Recovery (CDR)

High-speed serial links transfer tens of gigabits per second without an external clock line through specialized silicon blocks called Serializer/Deserializers (SerDes):

  1. Parallel-to-Serial Conversion: Inside the transmitter, wide internal data words (e.g. 64 bits from the CPU cache) enter a multiplexing shift register clocked by a Phase-Locked Loop (PLL). The serializer converts the 64 parallel bits into a single sequential high-frequency bit stream.
  2. Line Encoding and DC Balance: If a stream contained long runs of identical bits (e.g. 100 consecutive zeros), the signal would become a flat DC voltage. This would cause two severe problems: receiver AC-coupling capacitors would charge up (causing baseline wander), and the receiver would lose track of clock transitions. Encodings like 8b/10b (mapping 8-bit bytes to 10-bit symbols) or 128b/130b ensure that 0s and 1s are balanced (DC balance) and that voltage transitions occur frequently regardless of payload data.
  3. Differential Transmission: The serial bit stream drives a low-voltage differential signaling driver, launching equal and opposite voltage swings across a matched-impedance trace pair.
  4. Clock Data Recovery (CDR): At the receiving end, an analog Phase-Locked Loop locks onto the frequent voltage transitions of the incoming data stream. The CDR circuit reconstructs the transmitter's exact clock frequency and phase directly from the data edges, eliminating the need for a separate physical clock trace.
  5. Serial-to-Parallel Deserialization: Using the recovered clock, an input shift register deserializes the sequential bits back into 64-bit parallel words, verifying frame alignment tokens and passing clean data to the receiving controller.

Multi-lane aggregation

To scale throughput beyond the limits of a single serial lane, architectures like PCI Express group multiple independent serial transceivers into aggregated link widths (x1, x2, x4, x8, x16). Unlike legacy parallel buses, each PCIe lane possesses its own dedicated differential pair and independent SerDes hardware.

When an operating system transfers data, the PCIe controller stripes bytes round-robin across the active lanes. Because trace lengths between slots and CPU sockets vary slightly on the motherboard, bytes arrive on different lanes with picosecond-scale skew. The receiving PCIe physical layer buffers incoming bytes in per-lane elastic de-skew FIFOs. By detecting predefined synchronization training sequences (ordered sets), the hardware dynamically realigns the bytes across all lanes before presenting the reconstructed packet to the transaction layer, combining massive throughput with zero clock skew vulnerability.

Why Tamlinux chose this

Understanding PCIe lane negotiation and serial console semantics directly impacts Tamlinux systems administration. Headless server recovery, kernel crash debugging via KGDB, and automated virtual machine test suites rely on deterministic serial links. By structuring desktop and diagnostic tools around asynchronous character streams and PCIe sysfs hierarchies, Tamlinux ensures maintainers have direct visibility into hardware link states without proprietary abstraction layers.

Edge cases and failure modes

  • Lane Degradation (PCIe Link Retraining): If physical electrical noise, micro-fractures, or oxidation degrade high-frequency signal integrity on lane 12 of a x16 card, the PCIe root complex will drop the entire link down to x8 or x4 width during retraining. The device continues operating but at significantly reduced bandwidth.
  • UART FIFO Buffer Overrun: When a serial port receives data faster than user-space processes can read it from the kernel input queue, the hardware 16550A UART FIFO buffer (typically 16 to 64 bytes deep) overflows, dropping bytes and asserting an Overrun Error (`oe`) flag in `/proc/tty/driver/serial`.
  • Clock Drift Beyond 2.5% Tolerance: In asynchronous UART communication, receiver clocks must match transmitter clocks within approximately +/- 2.5%. If thermal drift or improper baud divisor register calculation pushes clock mismatch beyond 3%, the receiver samples the Stop bit during the final data bit period, generating continuous Framing Errors (fe).

How does 8b/10b line encoding prevent receiver clock drift and baseline wander in high-speed serial links?

8b/10b encoding maps every 8-bit data byte into a carefully chosen 10-bit symbol. The symbol dictionary guarantees two vital properties: first, it limits the maximum run of consecutive identical bits to five, ensuring frequent voltage transitions so the receiver's Clock Data Recovery (CDR) circuit stays locked to the clock; second, it maintains a running disparity (equal count of 1s and 0s over time), preventing DC charge accumulation on AC-coupling capacitors.
