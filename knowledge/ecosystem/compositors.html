How windows appear on your screen

This page explains the software that puts windows on your screen and lets you interact with them.

Compare compositor roles

Goal: distinguish the current compositor from planned alternatives.

Mental model

A compositor presents application surfaces and manages their placement; a desktop shell supplies surrounding controls.

Worked example

The section below identifies Hyprland as current and Sway as a planned transition.

On Wayland, the compositor is the display server and the window manager in one program. Tamlinux runs on Hyprland today and has selected Sway, built on the wlroots library, as its long-term compositor.

Why Wayland

  • Client isolation: under X11 any client can read other clients' keystrokes and windows; Wayland isolates clients from each other.
  • Tear-free output: clients render into buffers that the compositor presents whole, frame by frame.
  • Per-monitor scaling: mixed resolutions and fractional scales (for example 1.25x) on different monitors.

Why Sway

  • A small C code base: wlroots and Sway are written in C, with a stable i3-compatible IPC that tools and the Tamlinux shell can rely on.
  • Software rendering: wlroots can render on the CPU with pixman (WLR_RENDERER=pixman), which matters for older graphics hardware. Its rendering paths are still to be tested on representative older machines.
  • No systemd required: Sway obtains seat access through seatd and libseat, so it runs without systemd-logind or elogind.
  • A tiling, keyboard-driven desktop: the target is a tiling window system inspired by the UI Omarchy provides.

The transition

The move is staged so that each step can be checked on its own. The first step, making Tamlinux independent of Omarchy on the current Hyprland desktop, is in progress through the 0.4 versions. The Sway steps are planned: Sway integration and packaging at 0.7, physical daily use on Sway at 0.8, and removal of Hyprland at 1.0. Some Sway adapters have been prepared in advance, but none of these steps is delivered.

Reasons for leaving Hyprland:

  • Plugin ABI churn: Hyprland plugins must match the exact compositor build, so routine updates can break them.
  • Carried patches: keeping multi-monitor setups stable has required local patches; see Carried patches.
  • Contribution policy: Hyprland accepts pull requests only from vouched contributors, and its AI usage policy forbids AI involvement in pull requests, issues, and comments. Fixes developed with AI assistance therefore cannot be offered upstream directly.

Other compositors considered

  • niri: a scrollable-tiling compositor in Rust with an intuitive horizontal layout.
  • river: dynamic tiling in Zig, with layouts provided by separate programs.
  • labwc: a stacking compositor on wlroots with Openbox-style configuration.
  • Wayfire: a wlroots compositor known for desktop effects.

Choosing

Use the current compositor for actual behavior; treat future adapters and releases as planned.

Troubleshooting

A blank display can have several causes; the compositor name alone does not diagnose it.

Check yourself

Does a prepared adapter prove the Sway desktop is delivered?

No. Prepared code and an accepted integrated session are distinct.

What evidence separates a proposed change from a delivered one?

Inspect the relevant plan, selected package and acceptance evidence; a proposal alone establishes none of those.
