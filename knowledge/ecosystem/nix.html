How Nix and Home Manager work

This page explains how Nix builds software and how Home Manager uses Nix to create the software and settings in your home directory.

Tamlinux uses these tools to deliver its desktop. You do not need to know them to use Tamlinux, but knowing them makes updates, rollbacks and configuration changes much easier to understand.

What are Nix and Home Manager?

Ordinary package managers replace a program when a new version arrives. Nix keeps each built result in its own directory. That makes it possible to see exactly which files a command uses and to return to an earlier selection when a change causes trouble.

Why it matters

Mental model

flake.nix + flake.lock
        |
        |  evaluation: the Nix language reads the description
        v
   derivation (a precise build recipe with hashed inputs)
        |
        |  build: runs in a sandbox with declared inputs only
        v
   /nix/store/<hash>-<name>  (immutable result)
        |
        |  profile link
        v
   generation N  -->  your commands and configuration files

Read the diagram from top to bottom. The left side is a description written by a person. The right side is what exists on disk. Nix separates the two so that the same description can produce the same result on another machine.

Declarative means you describe the result you want instead of listing the steps to create it. An imperative command such as cp file /etc/ performs one action now. A declarative file says "this file should exist with this content", and the tool works out what to do. Nix is declarative for builds; Home Manager is declarative for your home directory.

The Nix language is a small functional language. A file is one expression, and evaluating the expression produces a value: a number, a string, a list, an attribute set (a collection of named values), or a function. Nix evaluates lazily, which means it computes a value only when something needs it. That is why a large configuration can mention many packages without building all of them at once.

A derivation is the result of evaluating a build description. It records the builder, the arguments, the environment, the source inputs and the other derivations it needs. Nix writes the derivation to the store as a .drv file and computes an output path from it. A build then runs the builder in a sandbox: a restricted environment with the declared inputs and no ordinary network access. The output appears at the computed path. If the same derivation is requested again, Nix can reuse the existing output instead of rebuilding it.

A flake is a directory with a flake.nix file and a flake.lock file. The flake.nix declares inputs (other flakes or source trees) and an outputs function that turns those inputs into packages, modules, checks or other results. The flake.lock records the exact revision and tree hash of every input. Pinning the lock file is what makes a flake reproducible: two machines that use the same lock get the same inputs, even if a branch has moved since.

Home Manager is a library and a command built on Nix. It uses the NixOS module system. A module is a function that declares options (the settings a user may choose) and config (the values those settings should have). Modules are merged, and the result is built into an activation package. Activating that package creates a new generation, links files into your home directory, and runs any activation scripts the modules defined.

Worked example: follow a command into the store

$ nix --version
nix (Determinate Nix 3.22.5) 2.35.2

$ readlink -f ~/.nix-profile

$ home-manager generations | head -n 3
2026-10-29 20:20 : id 14 -> /nix/store/hjv5ndzzkadphxx8wj8x3pzzwz0kvs8f-home-manager-generation (current)
2026-10-29 19:52 : id 13 -> /nix/store/k1ir8w8b2ahblx6s2xmj1ynzzrypwgqg-home-manager-generation
2026-10-29 19:38 : id 12 -> /nix/store/1h48kj4599hk1bg7gxb81s6k5452g08v-home-manager-generation

Captured on an Arch Linux workstation with Determinate Nix, 2026-10-31. Your hashes, dates and generation numbers will differ.

What just happened

  1. nix --version prints the version of the Nix program itself. Nix is the tool that builds and stores software; it is not the same thing as NixOS, a whole operating system built on Nix.
  2. readlink -f follows a chain of symbolic links until it reaches a real directory. The answer begins with /nix/store/, the place where Nix keeps built results.
  3. home-manager generations lists numbered records. Each record points to one built Home Manager configuration. The word (current) marks the one in use now.

A package is a bundle of program files, libraries and data. Nix does not put a package directly into /usr/bin. It builds the package into its own directory under /nix/store/, then creates links that point at it. A link is a small file that names another file or directory; opening the link opens the target.

A store path has three parts: the fixed prefix /nix/store/, a long hash such as c16r82dn5wpsz72imqz86x3sxxap9j6c, and a readable name such as user-environment. The hash is a fingerprint of everything that went into the build. If an input changes, the fingerprint changes, so the new result gets a different directory and the old result is left alone. Store paths are read-only, which is what people mean when they call the store immutable.

A generation is a recorded selection of managed software and settings. Home Manager creates a new generation each time you activate a changed configuration. The older generations stay on disk until they are deliberately removed. Selecting an older one is called a rollback. It changes which software your profile points at; it does not restore your documents or other mutable files.

A profile is a named pointer to one generation. Your shell finds commands through a profile such as ~/.nix-profile. The profile is itself a link: it points to the current generation, and the generation points into the store. Switching generations moves the profile link; it does not rewrite the store.

Try it

Follow the tam command to the file it really runs, and read the profile link target. These commands are read-only.

readlink -f "$(command -v tam)"
readlink ~/.nix-profile

If the first answer begins with /nix/store/, the command is packaged. If it begins under your home directory, it is a development override. The second answer shows the profile link without following it all the way to the store. Your paths and versions will differ from the worked example.

If it goes wrong

nix: command not found
Nix is not installed or is not on your PATH. On a Tamlinux workstation it normally arrives with the desktop delivery. Do not install a second copy from a random script; ask for help or read Software packaging and delivery.
home-manager: command not found
The Home Manager command is missing from your PATH, even if its generations still exist. Check command -v home-manager and the profile path before changing anything.
readlink: /home/alex/.nix-profile: No such file or directory
No Nix profile exists for this account, or the name is different. Do not create one just to finish the example; the read-only lesson can stop here.
Permission denied
The store is read-only by design. Reading is allowed; writing into /nix/store/ is not. Never change permissions on the store to make a command work.

On Tamlinux, pacman owns the rootstock while Nix and Home Manager deliver the cultivar. The public tamlinux-packages flake pins the exact revisions of nixpkgs, Home Manager and each Tamlinux component. Product software reaches your session through a recorded assembly selected by tam-deploy; activating an arbitrary Home Manager generation from a checkout is a development action, not product delivery. A generation rollback returns user software and configuration, not the kernel, boot files or mutable data. See the deployment contract.

Check yourself

Decide your answer before you reveal it.

Why does a new Nix build usually get a different store path instead of replacing the old one?

The path contains a hash of the build inputs. A changed input changes the hash, so the new result is stored separately and the old result remains available. That is what makes generations and rollback possible.

Does rolling back a Home Manager generation restore a document you edited yesterday?

No. A generation selects managed software and configuration. Your documents and other mutable files are outside it and need their own backup or recovery.

What is the difference between a profile and a generation?

A generation is one recorded selection. A profile is the named pointer that says which generation is current. Switching moves the profile pointer to another generation.

How it works

Nix evaluation and Nix building are separate phases. Evaluation reads .nix files and produces values, including derivations. A derivation is a data structure: it names a builder, arguments, environment variables and input derivations. Nix serialises it to a .drv file in the store. Building takes those .drv files and runs the builders in a sandbox. The sandbox has the declared inputs, a private temporary directory and no ordinary network access. The builder writes its result to $out, the output path Nix computed. A fixed-output derivation is the exception that may fetch from the network, because its output hash is declared in advance.

The store is a graph. A store path refers to other store paths: a program's shared libraries, a script's interpreter, a configuration file's source. The set of all paths reachable from one path is its closure. Copying a closure to another machine is enough to run that program, which is why Nix can distribute binary substitutes. A garbage collection root is a link that keeps a path and its closure alive. Profiles and generation links are roots. Removing a generation removes a root; nix-collect-garbage can then delete paths that no remaining root reaches.

A flake adds a standard interface around evaluation. flake.nix has inputs and an outputs function. flake.lock pins each input's revision and narHash, the hash of the unpacked source tree. A flake = false input is a plain source tree rather than a flake: it has no outputs of its own, and Nix exposes it as a store path. An input with inputs.nixpkgs.follows = "nixpkgs" reuses the root flake's nixpkgs instead of fetching a second copy. That keeps one package set and one set of library versions across the whole evaluation.

Home Manager's module system merges declarations from many files. Each module returns an attribute set with optional options and config attributes. An option declaration gives a name, a type, a default and a description. A config definition assigns a value. The module system checks types, merges values according to priority, and produces one final config. Helpers such as lib.mkIf, lib.mkDefault, lib.mkForce and lib.mkMerge control whether and how a value participates in that merge. lib.mkEnableOption is shorthand for a Boolean option that defaults to false.

Home Manager then builds an activation package. The package contains an activate script, a home-files tree of managed files, and a home-path profile of packages. Activation creates a new generation link, switches the profile, links the managed files into your home directory, and runs the activation scripts in dependency order. The order is a directed acyclic graph, or DAG. A script added with lib.hm.dag.entryAfter [ "linkGeneration" ] runs after the named step; entryBefore runs before it. Activation scripts should be idempotent, because they run again on every switch.

The Tamlinux flake, line by line

The flake is deliberately small. It pins inputs, imports the package definitions, and exposes a module, packages and checks.

{
  description = "Pinned Tamlinux packages and reusable user-layer deployment modules";
  inputs = {
    nixpkgs.url = "github:nixos/nixpkgs/<commit>";
    home-manager = {
      url = "github:nix-community/home-manager/<commit>";
      inputs.nixpkgs.follows = "nixpkgs";
    };
    tamlinux = {
      url = "github:greenermoose/tamlinux/<commit>";
      flake = false;
    };
  };
  outputs = inputs@{ self, nixpkgs, home-manager, tamlinux, ... }:
    let
      system = "x86_64-linux";
      pkgs = import nixpkgs { inherit system; };
      components = import ./nix/packages {
        inherit pkgs;
        sources = inputs;
      };
    in {
      homeManagerModules.default = { lib, ... }: {
        imports = [ ./nix/modules ];
        tamlinux.shell.package = lib.mkDefault components.tamlinux-shell;
      };
      packages.${system} = components // {
        default = components.tam;
      };
    };
}

This excerpt leaves out some inputs and outputs so the shape is visible; read the real file for the complete set. inputs is an attribute set of dependencies. The home-manager input declares that its own nixpkgs input follows the root flake's nixpkgs. The Tamlinux product repositories are marked flake = false: they are pinned source trees, not flakes with their own outputs. The outputs function receives the resolved inputs. The pattern inputs@{ self, nixpkgs, home-manager, tamlinux, ... } binds the whole set to inputs and also names the inputs used below. self is the flake's own outputs, which lets a module refer to itself without a circular file import.

The let block defines system, imports nixpkgs with that system, and imports the local package file with the package set and the whole input set. import nixpkgs { inherit system; } works because the Nixpkgs entry point is a function that expects an argument set. components is then an attribute set of built packages. The outputs attribute set exposes a Home Manager module, packages and checks. lib.mkDefault gives the package options a low-priority value so a consumer can override them without editing the flake.

The lock file is the other half of the pin. Each input has an original description and a locked record with owner, repo, rev, lastModified and narHash. The rev names the exact commit; the narHash identifies the exact unpacked tree. A branch name alone would not be reproducible because it can move. Updating an input is a deliberate change to the lock file, reviewed like any other source change.

The package file

nix/packages/default.nix is a function of { pkgs, sources }. It builds the component packages and returns them as an attribute set. The central pattern is stdenv.mkDerivation, the standard Nixpkgs builder for software that uses a conventional build system. The excerpt below is shortened; the real package also handles optional display and session outputs.

libtam = pkgs.stdenv.mkDerivation {
  pname = "libtam";
  version = builtins.head (builtins.match
    ''#define TAM_VERSION_STRING[[:space:]]+"([^"]+)"[[:space:]]*''
    (pkgs.lib.findFirst (pkgs.lib.hasPrefix "#define TAM_VERSION_STRING")
      (throw "Pinned libtam source has no version")
      (pkgs.lib.splitString "\n" (builtins.readFile "${sources.libtam}/include/tam.h"))));
  src = sources.libtam;
  nativeBuildInputs = [ pkgs.pkg-config ];
  buildInputs = [ pkgs.dbus ];
  buildPhase = ''
    runHook preBuild
    make all
    runHook postBuild
  '';
  installPhase = ''
    runHook preInstall
    make install PREFIX="$out"
    runHook postInstall
  '';
  doCheck = true;
  meta.license = pkgs.lib.licenses.gpl3Plus;
};

pname and version name the result. The version is read from the pinned source at evaluation time: builtins.readFile reads the header, lib.splitString splits it into lines, lib.findFirst finds the version line, and builtins.match extracts the captured string. This means the package version cannot drift from the source header without the derivation changing. src is the pinned source tree. nativeBuildInputs are tools used while building; buildInputs are libraries the result needs. The phases run the project's own build and install commands. $out is the output store path. doCheck = true runs the project's tests during the build, and meta.license records the license for tooling and users.

The other components use the same ideas with different helpers. pkgs.runCommand creates a derivation that runs a shell script; it is convenient for copying files into a store tree. passthru attaches extra attributes to a package, such as version, revision and features, without changing the build. builtins.pathExists and builtins.readDir inspect the pinned product source during evaluation, which lets one flake support revisions that have different features. lib.optionalString and lib.optionals include a string or list only when a condition is true. patchShebangs rewrites interpreter lines such as #!/usr/bin/env python3 to the store path of the declared interpreter. wrapProgram creates a small wrapper that sets PATH and other environment variables before running the real program. pkgs.writeText writes a generated text file into the store, and builtins.toJSON turns a Nix value into JSON.

The module file

nix/modules/shell.nix shows the module pattern used throughout the deployment. The file is a function of the module arguments, defines options, and returns configuration guarded by lib.mkIf.

{ config, lib, pkgs, ... }:
let
  cfg = config.tamlinux.shell;
  shell = cfg.package;
in {
  options.tamlinux.shell = {
    enable = lib.mkEnableOption "Tamlinux shell deployment";
    package = lib.mkOption {
      type = lib.types.package;
      description = "Tamlinux shell package built from the recorded assembly.";
    };
  };
  config = lib.mkIf cfg.enable {
    home.packages = [ cfg.commandPackage ];
    home.file.".local/share/tamlinux/shell".source =
      "${shell}/share/tamlinux/shell";
    xdg.configFile."tamlinux/plugins".source =
      "${cfg.pluginPackage}/share/tamlinux/plugins";
    assertions = [
      {
        assertion = shell.passthru.revision == cfg.pluginPackage.passthru.revision;
        message = "Shell and plugins must come from the same product revision.";
      }
    ];
    home.activation.checkPluginOverrides =
      config.lib.dag.entryBefore [ "checkLinkTargets" ] ''
        # Refuse to switch while a development override is active.
        # The real script checks the plugin state directory.
        ...
      '';
  };
}

This excerpt is shortened. { config, lib, pkgs, ... }: is a module function. config is the final merged configuration, lib is the Nixpkgs library, and pkgs is the package set. The ... accepts additional module arguments that Home Manager supplies. The let block names the option subtree and the selected package. options.tamlinux.shell declares the settings. lib.mkEnableOption creates a Boolean option that defaults to false. lib.mkOption declares a typed option; lib.types.package requires a derivation, not an arbitrary string.

The config attribute is active only when cfg.enable is true. home.packages adds a package to the profile. home.file and xdg.configFile create managed links; .source points at a store path, while .text stores literal content and links that file. The assertions list fails evaluation if the shell and plugin package revisions differ, which prevents mixing outputs from different product revisions. home.activation adds a script to the activation DAG; entryBefore [ "checkLinkTargets" ] places it before Home Manager's own link check. The '' string is an indented string, and ''${...} would escape a literal interpolation.

The same module file also declares systemd.user.services.tamlinux-shell. Home Manager turns that attribute set into a user unit. The Unit, Service and Install sections use systemd's own names. WantedBy = [ "graphical-session.target" ] makes the service part of the graphical session. ConditionEnvironment = "WAYLAND_DISPLAY" prevents it from starting without a Wayland session. The service's PATH is assembled from the user's ~/.local/bin, the shell's runtime dependencies and a final /usr/bin fallback, so the shell finds its packaged commands first.

How a change becomes a generation

  1. Edit a .nix file, or update a pinned input in flake.nix and flake.lock. For a product change, the source revision and the assembly record change together.
  2. Run nix flake check to evaluate the flake and build its checks. A check is a derivation; if it builds, the check passes.
  3. Run home-manager build --flake .#name to evaluate the modules and build the activation package without touching your home directory. Inspect the result before activating it.
  4. Run home-manager switch --flake .#name to build and activate. Home Manager creates a new generation, links the managed files and runs the activation scripts.
  5. Verify the result with home-manager generations, readlink -f, command -v and the program's own version output. A successful build is not the same as a verified running system.
  6. If the change is wrong, use home-manager rollback or select the previous generation. Keep the old generation until the new one has survived normal use.

For Tamlinux product delivery, the last steps are owned by tam-deploy. It selects the recorded assembly, verifies that the installed shell, plugins and commands resolve into that assembly's packages, and reports the generation. Do not substitute a direct home-manager switch from a checkout for that recorded selection. Development builds are for testing and are removed after the deploy that delivers the pinned version.

Why Tamlinux chose this

Tamlinux needs two different kinds of ownership. The rootstock, which includes the kernel, drivers and system services, must follow the hardware and the distribution's lifecycle. Pacman is the right owner for that layer. The cultivar, which includes the compositor, shell, plugins, themes and curated desktop applications, changes quickly and must be reproducible across workstations. Nix and Home Manager give that layer a pinned description, atomic generations and an immediate rollback.

The design also keeps the two layers honest. A Nix generation cannot silently change the kernel or a native driver. A native update cannot silently rewrite the desktop description. Each layer has its own record and its own recovery boundary. The cost is real: a second package store, a second package language, more disk use and a steeper learning curve. Tamlinux accepts that cost because the desktop is the part that changes most often and benefits most from reproducible delivery.

Tamlinux is not NixOS. Nix is a package manager that runs on an ordinary Arch Linux rootstock; NixOS is a whole operating system built around Nix. Using Nix and Home Manager does not replace the rootstock or make the kernel declarative. See Describing how a system should be set up for the distinction.

Edge cases and failure modes

  • Purity. Evaluation is pure by default: it cannot read arbitrary environment variables or the current system unless the expression asks for them. builtins.currentSystem is impure; pass system explicitly in a flake. Use --impure only for an experiment, not for a recorded build.
  • Import from derivation. A build that needs the output of another build during evaluation is an import from derivation. It can slow evaluation, break sandbox assumptions and make caching harder. Prefer evaluating data that is already in the source tree.
  • Fixed-output derivations. Network fetches are allowed only when the output hash is declared in advance. A hash mismatch means the source changed or the hash is wrong. Do not disable the check; update the pin and hash deliberately.
  • Garbage collection. Old generations keep their store closures alive. Removing a generation removes a root, and a later nix-collect-garbage may delete paths that only that generation used. Keep the generations you may need for rollback.
  • ABI drift across layers. A native update can replace a core library such as Mesa or Wayland while an older Nix generation still expects the previous application binary interface. Rebuild or return to a matching generation; do not assume that an old store path is compatible with a new host library.
  • PATH shadowing. A development build, a Mise shim, a Nix profile and /usr/bin can all provide the same command. The first match wins. Check the resolved path, not only the version string.
  • Non-NixOS graphics. A program built by Nix may need the host's graphics drivers and vendor configuration. Tamlinux wraps the shell provider to supply its locked Mesa EGL vendor file and DRI directory while leaving child processes with the caller's environment. The wrapper changes only the shell process; it is not a general fix for every Nix-built graphical program.
  • Mutable state. A generation contains software and configuration, not your documents, caches, browser profiles or other changing data. Back up mutable state separately, and do not expect a rollback to undo a document edit.
  • Evaluation cost. A large flake can evaluate many attributes before it builds anything. Lazy evaluation helps, but a broad nix flake show or an unnecessary import can still be slow. Ask for the narrow attribute you need.

Explore

Check yourself

Why does Tamlinux pin nixpkgs and Home Manager to exact commits instead of following their stable branches?

A branch is a moving name. Pinning a commit makes the input identical on every machine and at every later build, so a recorded assembly identifies the exact bytes. Following a branch would make the same description produce different results over time and would break the link between a candidate and its evidence.

What breaks if two components in one Home Manager generation come from different product revisions?

The generation can mix a shell, plugin set and command set that were never tested together. Interfaces, environment variables and file layouts may disagree. Tamlinux asserts that the revisions match so the build fails early instead of producing a plausible but inconsistent session.

When is a direct home-manager switch from a checkout appropriate, and when is it not?

It is appropriate for a developer testing a local change in a disposable environment, with the old generation retained. It is not appropriate as product delivery: Tamlinux product software must arrive through a recorded tamlinux-packages assembly selected by tam-deploy, so the installed bytes and their provenance are known.
