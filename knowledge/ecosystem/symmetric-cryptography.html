Symmetric Cryptography and Authenticated Encryption

This page explains how a single shared secret key scrambles bulk data quickly and seals it against tampering.

Locking and sealing data with one shared key

Symmetric encryption uses the exact same secret key to scramble (encrypt) and unscramble (decrypt) information. Because it relies on fast bitwise operations—shifting, mixing, and adding—it can encrypt gigabytes per second, making it the workhorse behind full-disk encryption, Wi-Fi, and web traffic.

Why it matters

Confidentiality alone is not enough: if an attacker flips a few bits in an encrypted message without being noticed, they could change a bank transfer amount or corrupt a program. Modern symmetric systems therefore pair encryption with a tamper-evident seal so any modification is caught before the data is trusted.

How to think about it

Imagine putting a letter inside a locked steel box (encryption) and wrapping a numbered tamper-evident wax seal around the latch (authentication). Even if someone shakes or dents the box in transit, the broken seal warns you immediately not to trust what is inside.

Also, if you encrypt two identical paragraphs with the same key, you must never produce identical scrambled text—otherwise an eavesdropper sees repeating patterns. Adding a fresh one-time starting number called a nonce (number used once) ensures that encrypting the same message twice yields completely different ciphertext.

Encrypting files and spotting key-derivation headers

Goal: you will be able to encrypt and decrypt a scratch file safely with OpenSSL using AES-256 and PBKDF2 key derivation, and inspect why salting changes the ciphertext.

Before you start: work inside a temporary directory created with mktemp -d so no scratch files remain in your home folder.

Worked example

Create a scratch file, encrypt it with AES-256-CBC and PBKDF2 key derivation, inspect the first 32 bytes of the encrypted file, and decrypt it:

$ work=$(mktemp -d) && cd "$work"
$ printf 'Secret message for Tamlinux.\n' > msg.txt
$ openssl enc -aes-256-cbc -pbkdf2 -salt -in msg.txt -out msg.enc -pass pass:demo-passphrase-2026
$ od -tx1 -N 32 msg.enc
0000000 53 61 6c 74 65 64 5f 5f c5 76 5e 0c 91 95 09 3d
0000020 38 0c 0c 2d 44 97 a2 cc 98 9a 7e ee 7f 62 19 40
0000040
$ openssl enc -d -aes-256-cbc -pbkdf2 -in msg.enc -pass pass:demo-passphrase-2026
Secret message for Tamlinux.
$ rm -rf "$work"

Captured on Arch Linux, 2026-11-14; the random salt and ciphertext bytes will differ on every run.

What just happened

  1. The first 8 bytes of msg.enc (53 61 6c 74 65 64 5f 5f) spell Salted__ in ASCII, followed by an 8-byte random salt (c5 76 5e ...).
  2. -pbkdf2 stretches the passphrase with the random salt to derive both an encryption key and an initialization vector (IV), so encrypting the same file twice with the same passphrase produces different ciphertexts.
  3. Note that openssl enc defaults to unauthenticated modes (CBC) without a MAC; for real file encryption, prefer authenticated tools such as age, gpg, or LUKS2 rather than raw openssl enc.

Try it

In a scratch directory, encrypt the same text twice with -aes-256-cbc -pbkdf2 and compare the outputs with cmp. Never pass real secrets via -pass pass:... on the command line (shell history and ps can see arguments); omit -pass so OpenSSL prompts interactively.

If it goes wrong

bad decrypt error
The passphrase is wrong, the file was truncated, or the decryption command omitted -pbkdf2 when encryption used it.
ECB mode warning or repeated blocks
Never use -aes-256-ecb: ECB encrypts identical 16-byte blocks identically, leaking structure in images and structured files.

On Tamlinux, full-disk encryption (LUKS2) uses aes-xts-plain64 (a tweakable block cipher mode designed for fixed-sector storage where ciphertext cannot expand to hold a MAC tag), while TLS 1.3 and WireGuard use AEAD suites (AES-256-GCM and ChaCha20-Poly1305).

Check yourself

Decide your answer before you reveal it.

Why is ECB (Electronic Codebook) mode unsafe for encrypting anything longer than a single random block?

ECB encrypts each 16-byte plaintext block independently with the same key, so identical plaintext blocks produce identical ciphertext blocks and reveal patterns.

What does AEAD add beyond plain encryption?

AEAD computes an authentication tag over both the ciphertext and any unencrypted associated headers (AAD), so decryption rejects any tampered packet before releasing plaintext.

How it works: AES, ChaCha20, and AEAD

AES (Rijndael) Internals: AES operates on a 4×4 byte state matrix in the finite field GF(2^8) = 𝔽_2[x] / (x^8 + x^4 + x^3 + x + 1). Each round applies four layers: (1) SubBytes, the only nonlinear step, computes the multiplicative inverse in GF(2^8) (mapping 0 to 0) followed by an affine map over 𝔽_2; (2) ShiftRows cyclically shifts row i left by i bytes; (3) MixColumns multiplies each column by a fixed Maximum Distance Separable (MDS) circulant matrix over GF(2^8) (branch number 5, maximizing diffusion); (4) AddRoundKey XORs the round subkey.

ChaCha20 ARX Design: Rather than S-boxes (which risk cache-timing side channels in software without AES-NI), ChaCha20 initializes a 4×4 matrix of 32-bit words (constants "expand 32-byte k", 256-bit key, 32-bit block counter, 96-bit nonce) and applies 20 rounds (10 column + 10 diagonal) of quarter-rounds using only a += b; d ^= a; d <<<= 16 and similar Add-Rotate-XOR steps. Every operation runs in constant time on general-purpose CPUs.

GCM and Poly1305 Authentication: AES-GCM encrypts plaintext with AES-CTR starting at counter 2, then computes GHASH(H, AAD, C) where H = E_K(0^128) by evaluating a polynomial ∑ X_i · H^i in GF(2^128) (irreducible polynomial x^128 + x^7 + x^2 + x + 1) and XORing E_K(nonce || 1). ChaCha20-Poly1305 derives a one-time Poly1305 key from ChaCha20 block 0 and evaluates a polynomial modulo the prime 2^130 - 5 over blocks of AAD and ciphertext.

Cryptanalysis Foundations: Differential cryptanalysis (Biham–Shamir) tracks how input XOR differences ΔX propagate to output differences ΔY with high probability across rounds; linear cryptanalysis (Matsui) finds high-bias linear approximations (α · P) ⊕ (β · C) = (γ · K). Wide-trail design in AES bounds the minimum number of active S-boxes across any 4-round trail to 25, defeating both attacks.

Edge cases and failure modes

  • Nonce reuse in CTR/GCM/ChaCha20: Encrypting two messages under the same (Key, Nonce) immediately leaks C_1 ⊕ C_2 = P_1 ⊕ P_2. Worse, in AES-GCM, nonce reuse lets an attacker recover the GHASH authentication key H via polynomial root-finding in GF(2^128) (Joux's Forbidden Attack), forging arbitrary future tags. Use random 192-bit nonces (XChaCha20) or AES-GCM-SIV when nonce uniqueness cannot be guaranteed.
  • Cache-timing attacks on table-based AES: Software T-table implementations index RAM by secret-dependent bytes, leaking AES keys across shared CPU caches (Bernstein 2005). Production systems must use hardware instructions (AES-NI / ARMv8 Crypto) or constant-time bit-sliced / ARX designs.

Check yourself

Why does nonce reuse in AES-GCM break integrity as well as confidentiality, whereas nonce reuse in CBC mode only leaks the first-block prefix equality?

In AES-GCM, the authentication tag is a polynomial in GF(2^128) masked by E_K(nonce || 1). Subtracting (XORing) two tags generated with the same (K, nonce) cancels the mask E_K(nonce || 1), leaving a polynomial equation in H whose coefficients are known ciphertexts. Solving for H recovers the MAC key permanently. In CBC, reusing an IV leaks equality of identical prefix blocks without exposing any MAC key.
