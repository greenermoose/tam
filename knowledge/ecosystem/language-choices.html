Systems programming philosophy and language choices

This page explains why Tamlinux chooses standard C11 for its core terminal utilities and shared libraries instead of languages like Rust, Go, or C++, and how AI agents help distill ideas from open source projects into fast, self-contained native programs.

Why does language choice matter in Tamlinux?

When you use an operating system, the programs you run every day — such as text editors, guide readers, launchers, and system monitors — are written in different programming languages. Some languages include large automated background machinery, while others compile straight to bare-metal instructions. In Tamlinux, core utilities are written in standard C11 so they start instantly, consume minimal memory, and keep computing fast and responsive.

Why it matters

Tamlinux is designed to run reliably on modern workstations as well as budget laptops from 2006. If basic system tools require large language runtimes, heavy background threads, or dozens of megabytes of memory just to show a help page or launch a journal entry, older hardware slows down and battery life suffers. Writing core utilities in native C11 guarantees that tools start in under 5 milliseconds and use less than 4 megabytes of resident memory, leaving system resources available for what you want to do.

How to think about it

Think of programming languages like different kinds of vehicles. A garbage-collected language like Go is like a tour bus: spacious and convenient with built-in facilities, but heavy and slow to park. Rust is like an armored security truck: exceptionally safe and reinforced against structural damage, but requiring a massive specialized repair facility to maintain. Standard C11 is like a lightweight racing bicycle: streamlined, direct, and possessing zero extra mass. It requires careful balance and attention, but it goes anywhere instantly and can be maintained with simple, universal hand tools.

New words

C11
The international standard for the C language published in 2011, providing modern compile-time checks and alignment without runtime bloat.
Machine code
The native binary instructions that a computer's central processing unit executes directly.
Compiler
A program, such as GCC or Clang, that translates human-readable source code into native machine code.
Standard C Library (libc)
The core system library, such as glibc or musl, that provides basic operating system interfaces for native programs.

Inspect binary footprints, library dependencies, and startup latency

Goal: you will be able to inspect executable section sizes using size, view shared library dependencies with ldd, and verify the minimal runtime footprint of native C11 utilities.

Before you start: open a terminal window (The Shell and Streams). The inspection commands run in user space and do not modify any system configuration.

New to this? Every compiled program links against system libraries and consumes memory when launched. Using size and ldd reveals the physical resource footprint of native C programs compared to programs carrying heavy language runtimes.

Worked example: inspect native binary size and shared libraries

$ size /usr/bin/tam
   text    data     bss     dec     hex filename
 294266    3656     336  298258   48d12 /usr/bin/tam
$ ldd /usr/bin/tam
    linux-vdso.so.1 (0x00007f966f5a8000)
    libz.so.1 => /usr/lib/libz.so.1 (0x00007f966f514000)
    libncursesw.so.6 => /usr/lib/libncursesw.so.6 (0x00007f966f4a3000)
    libc.so.6 => /usr/lib/libc.so.6 (0x00007f966f200000)
    /lib64/ld-linux-x86-64.so.2 => /usr/lib64/ld-linux-x86-64.so.2 (0x00007f966f5aa000)

Captured on an Arch Linux workstation, 2026-11-12.

What just happened

  1. size /usr/bin/tam reports the memory sections of the binary: text (executable code instructions), data (initialized variables), and bss (uninitialized variables). The entire program is under 300 kilobytes.
  2. ldd /usr/bin/tam lists the shared libraries required at runtime. The command links only against libz (decompression), libncursesw (terminal capabilities), and the standard C library (libc.so.6).
  3. Because there is no language runtime, interpreter, or garbage collector thread, the kernel loads and executes the binary in under two milliseconds.

If it goes wrong

ldd: command not found
The dynamic linker utility is part of the standard GNU C Library package (glibc). Ensure standard system development tools are installed.
not a dynamic executable
The binary was linked statically, meaning all necessary library routines are bundled directly into the executable file itself.

On Tamlinux: core utilities avoid language runtimes and heavy dependencies. While desktop automation uses Python 3 and desktop widgets use Quickshell with QML, systems utilities (such as tam, tam-launch-journal, and libtam) are implemented in standard C11. When inspiration is drawn from open source projects written in Go, Rust, or Python, AI assistants extract the algorithmic ideas and re-implement them in C11 rather than importing external language ecosystems.

Why do native C11 programs start in milliseconds compared to programs written in Go or Python?

C11 programs compile directly to native machine code and link only against the standard C library, requiring no interpreter initialization, virtual machine startup, or garbage collection runtime threads before execution begins.

What tool can you use to inspect which dynamic shared libraries an executable links against?

The ldd utility prints the shared objects required by each program or library specified on the command line.

Why Tamlinux chooses C11 over Rust, Go, and C++

Fred Horch, the Tamlinux developer (About Tamlinux), establishes strict guidelines for package languages and tool efficiency. The choice of C11 for core utilities rests on three technical pillars:

  1. Anti-bloat and resource efficiency: Managed runtimes like Go impose an 8–15 megabyte minimum binary floor and spawn background garbage collector and runtime scheduler threads. For high-frequency CLI commands, window manager hooks, and terminal utilities, this overhead wastes CPU cycles and battery energy. C11 executables compiled with -O2 start in milliseconds and use less than 4 megabytes of resident memory.
  2. Toolchain ubiquity and 20-year source longevity: ISO C11 (ISO/IEC 9899:2011) is a mature, frozen standard supported by GCC since version 4.9 and Clang since version 3.1. A C11 program written today will compile cleanly decades from now. In contrast, modern ecosystems like Rust suffer from rapid compiler edition churn, deep transitive dependency graphs (Cargo sprawl), and toolchains exceeding 1.5 gigabytes that cannot run inside minimal rescue environments or chroots.
  3. Zero Foreign Function Interface (FFI) friction: The Linux kernel, POSIX APIs, Wayland protocols, and terminal libraries (such as libncursesw) expose native C application binary interfaces (ABIs). Writing core tools in C11 allows direct invocation of operating system interfaces without foreign language marshalling or wrapper layers.

The AI synthesis workflow: extracting ideas across languages

One of Tamlinux's core engineering principles is to gather good ideas from everywhere (Philosophy and principles). Useful design patterns, data models, and algorithms exist across many programming languages. Rather than adopting an entire language ecosystem and its transitive dependencies, Tamlinux uses AI assistants (Claude Code, Codex, Antigravity, Cursor) under human direction to harvest ideas:

  • Algorithmic extraction: AI agents examine open source projects written in Go, Rust, Python, or Plan 9 C, analyze their core data structures and logic, and strip away framework-specific baggage.
  • Clean C11 implementation: The agent translates the distilled algorithm into standard C11 linked against libtam.
  • Self-contained autonomy: The resulting program has zero external dependencies beyond standard C and system libraries, eliminating the supply-chain security and maintenance burdens of large package registries.
  • Human direction and playful testing: AI agents handle the mechanical drudgery of writing C boilerplate, bounds checks, and test harnesses. The developer directs the architecture, reviews the code, and tests the tools interactively in daily computing.

Addressing C11's safety and library deficits

While C11 provides speed and simplicity, it lacks built-in memory safety and a rich standard collection library. Tamlinux mitigates these limitations with two engineering safeguards:

  • The libtam foundational library: Standalone C library providing safe dynamic strings, bounds-checked dynamic arrays, hash maps, JSON parsing, and atomic filesystem operations, inspired by lightweight libraries like sds and cJSON without the weight of GLib.
  • Strict compiler flags and runtime sanitizers: Tamlinux compiles all C code with -std=c11 -Wall -Wextra -Wpedantic to catch suspicious constructs at build time. During development and testing, code is built with AddressSanitizer (ASan) and UndefinedBehaviorSanitizer (UBSan) to catch buffer overflows, memory leaks, and use-after-free conditions before software is released.

Why doesn't Tamlinux use Rust for its core terminal utilities despite Rust's built-in memory safety?

While Rust guarantees compile-time memory safety, its heavy toolchain (~1.5 GB), deep transitive crate dependencies (Cargo sprawl), and long compilation times conflict with Tamlinux's goals of anti-bloat, 20-year source longevity, and emergency self-reliance on minimal rescue media. Tamlinux achieves memory safety in C11 through pedantic compiler flags, libtam bounds-checked primitives, AddressSanitizer (ASan) in continuous testing, and static assertions.

How does the libtam library support C11 development in Tamlinux?

It provides standard, reusable systems primitives — such as dynamic strings, hash maps, JSON parsing, and atomic file updates — that the standard C library omits, preventing individual utilities from reinventing low-level data structures while keeping binary sizes small.
