The central software that runs a computer

This page explains the central software that helps programs use a computer and its hardware.

The kernel is the central part of an operating system. It manages the hardware and helps programs use it. This page compares different ways to build that central part.

Monolithic kernels

A monolithic kernel runs the scheduler, memory management, file systems, network stack and device drivers together in one privileged address space. Linux and the BSD kernels are monolithic. Linux can load and unload modules while running, but a loaded module still runs inside the kernel with full privilege.

  • Strength: parts of the kernel call each other directly, so common paths such as reading a file or sending a packet are fast.
  • Strength: one large, shared code base attracts hardware vendors. Linux's driver coverage is its biggest practical advantage.
  • Cost: a bug in any driver can corrupt memory anywhere in the kernel. A faulty graphics driver can freeze or crash the whole system.
  • Cost: the code that must be trusted is very large: every driver loaded on the machine.

Microkernels

A microkernel keeps only the mechanisms that need hardware privilege: address spaces, threads, scheduling and interprocess communication (IPC). Device drivers, file systems and the network stack run as separate user-space programs, often called servers, that talk to each other and to applications by passing messages through the kernel.

  • Fault isolation: a crashing driver is an ordinary process. The system can keep running and restart it.
  • Least privilege: each server can be given access only to the devices and memory it needs, so a compromised service reaches less.
  • A small trusted core: the kernel can be small enough to review closely, and in the case of seL4, to prove correct mathematically.
  • Cost: work that is a function call inside a monolithic kernel becomes a message between processes. Each message costs context switches, which the earliest microkernels paid heavily for.
  • Cost: hardware support must be written for each system. In practice this, more than speed, limits most microkernel systems.

The L4 family of microkernels, begun in the 1990s, showed that careful design can make IPC fast, which answered much of the early criticism. The public argument in 1992 between Andrew Tanenbaum, author of MINIX, and Linus Torvalds over whether Linux should have been a microkernel is still often cited; both designs remain in wide use.

What a microkernel does not give you for free

  • Restarting is not recovering. Restarting a crashed file-system server does not restore the data it held in memory, and its clients must be written to reconnect.
  • Isolation needs hardware help. A driver that controls a device able to write anywhere in memory (direct memory access) is only contained if an IOMMU restricts that device.
  • The label is not the measurement. Whether a system is faster, safer or more reliable depends on its implementation, not its category. Tam 2.0 research measures these rather than assuming them.

Hybrid kernels

A hybrid kernel is structured like a microkernel but runs many of its services inside kernel space for speed. Windows NT and Apple's XNU, the kernel of macOS, are usually described as hybrids. The term is loose; it describes where code runs, not a separate theory.

Other designs

  • Exokernels expose hardware resources almost directly and leave abstractions to libraries in each application. They remain mostly research.
  • Unikernels compile one application together with just the operating-system code it needs into a single image, usually to run in a virtual machine.

Where user programs meet the kernel

Programs rarely call the kernel directly. They call a C library, such as glibc or musl on Linux, which makes the system calls; see C standard libraries. POSIX is the standard interface that Unix-like systems share at this level. A system with good POSIX compatibility can run much existing software after recompiling it, even if its kernel is very different from Linux. Tamlinux's design keeps the communication between its own software and the rootstock to standard interfaces like these; see the rootstock and cultivar terms in Terminology. Rootstock is not a common term, but one that Fred Horch, the Tamlinux developer, made up to explain how Tamlinux works: it is the kernel and core system software on which the Tamlinux cultivar is installed. The cultivar is all the software in the Tamlinux release that allows the computer to be used effectively and efficiently by both humans and AI agents. Fred defines the rootstock to be the set of software that third-parties publish and is necessary to be installed so that the software we write can function properly. Our goal is to minimize the size of the rootstock and maximize its speed and efficiency. Currently we are using Arch Linux as our rootstock but we plan to migrate to Void Linux in future versions of Tamlinux. Beyond that we are considering a microkernel to further reduce the code size of the rootstock and improve its performance per watt.

Linux itself moves some work out of the kernel: FUSE lets file systems run as user programs, and VFIO lets a user program drive a device. These narrow the gap for particular cases without changing the overall design.
