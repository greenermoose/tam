The Linux Input Subsystem and evdev

This page explains how Linux receives signals from keyboards, mice, and touchscreens and turns them into events programs can understand.

Every time you press a key, slide a mouse, or tap a touchscreen, physical electrical contacts generate hardware interrupts. The kernel processes these signals and passes them through a unified abstraction called the evdev (event device) subsystem. Instead of every application needing proprietary drivers for every keyboard, mouse, and game controller on earth, Linux provides a standardized stream of timestamped event packets. This architecture guarantees that modern Wayland compositors, terminal emulators, and games handle input safely, predictably, and without background polling daemons.

What is the Linux input subsystem?

When a keyboard stops responding, a mouse jumps unexpectedly, or a new input device is connected, guessing what is wrong wastes time. Knowing how Linux discovers and names input devices allows you to confirm within seconds whether the operating system recognizes your hardware.

New to this? In Linux, hardware devices are represented as special files in the /dev/ directory. Input devices live in /dev/input/ and are named event0, event1, and so on. For security reasons, regular user accounts cannot eavesdrop on raw keystrokes directly from these files; access is restricted to the root user and the input system group.

Mental model

Linux input is structured as a pipeline of layered responsibilities, separating hardware detection, protocol translation, gesture recognition, and window dispatch:

What just happened

  1. The Linux kernel probed connected motherboard ports and USB buses during boot and peripheral attachment.
  2. Kernel drivers bound to each device and registered an event* handler with the evdev subsystem.
  3. The virtual file /proc/bus/input/devices reported the human-readable names and assigned handler numbers.
  4. Udev created persistent symlinks in /dev/input/by-id/, allowing software to reference devices by their vendor and model names rather than unpredictable event numbers.

If it goes wrong

A connected keyboard or mouse does not appear in the list
Check physical cable connections or USB ports. Check the kernel ring buffer using dmesg | grep -i input to see if a hardware fault or power negotiation error occurred during device attachment.
Permission denied when trying to read /dev/input/event*
This is expected security behavior. Unprivileged terminal programs are blocked from reading raw keystrokes to prevent malware from logging passwords. On a Wayland desktop, the compositor receives input and safely directs keystrokes only to the active focused window.

On Tamlinux: the desktop relies completely on the generic evdev and libinput pipeline within the Wayland session. Proprietary vendor input daemons and legacy X11 driver packages are excluded from the system architecture. Keyboard mappings and desktop navigation chords are compiled cleanly through libxkbcommon and dispatched directly by the compositor.

Check yourself

Decide your answer before you reveal it.

Why does Linux provide unified /dev/input/event* interfaces instead of having applications talk directly to USB or PS/2 hardware?

The evdev subsystem provides a standard hardware-independent abstraction. Applications and compositors only need to understand one uniform protocol (struct input_event) rather than implementing custom communication drivers for thousands of distinct hardware models.

Why do persistent symlinks exist in /dev/input/by-id/?

Dynamic kernel event node numbers (like event4 or event8) can change order between boots depending on which device powers on or enumerates first. The symlinks in by-id/ remain consistent across reboots because they are generated from hardware vendor and product serial identifiers.

Kernel input plumbing, ioctls, uinput, and multi-touch protocol

Goal: you will be able to query evdev devices using kernel ioctl(2) calls, configure virtual input devices using uinput, decode Multi-Touch Type B slotted events, and trace Wayland compositor seat handover.

The evdev ioctl interface

User-space programs communicate with /dev/input/event* nodes using standard POSIX read(2) to receive event streams, and ioctl(2) to query hardware capabilities. Core request codes defined in <linux/input.h> include:

  • EVIOCGVERSION(int *version): Returns the driver protocol version (such as 0x010001 for version 1.0.1).
  • EVIOCGID(struct input_id *id): Retrieves the bus type (BUS_USB, BUS_I8042, BUS_BLUETOOTH), vendor ID, product ID, and revision number.
  • EVIOCGNAME(int len): Reads the human-readable product string assigned by the kernel driver.
  • EVIOCGBIT(int ev_type, int max_bytes): Returns a bitmask representing all event types or specific event codes supported by the hardware. For example, passing EV_KEY returns a bitmap where bit N is set if keycode N can be emitted.
  • EVIOCGABS(int abs_axis): Returns a struct input_absinfo detailing minimum value, maximum value, fuzz, flat deadzone, and resolution for absolute axes.
  • EVIOCGRAB(int state): Grants the calling process exclusive ownership of the input device when state is 1. All events are delivered solely to the grabbing file descriptor and hidden from all other readers until released (state = 0). This is used by virtual machine hypervisors and screen lockers.
  • EVIOCREVOKE(int reserved): Revokes access to the device node, causing all subsequent operations from other processes to return ENODEV.

Multi-touch protocol: Type A versus Type B (Slotted)

The Linux kernel supports two distinct multi-touch protocols:

  1. Type A (Anonymous packet): Legacy drivers send all touch contact points sequentially, separated by SYN_MT_REPORT markers and concluded by SYN_REPORT. The receiving application must correlate contacts between successive packets using geometric distance calculations.
  2. Type B (Slotted stateful tracking): Modern touchscreens and touchpads track contacts in hardware or kernel driver state. Each contact point is assigned a persistent numerical slot (ABS_MT_SLOT) and a tracking identifier (ABS_MT_TRACKING_ID):
    • When a finger touches the surface, the driver selects an unused slot and sends ABS_MT_TRACKING_ID with a positive integer.
    • Subsequent packets only emit modified values for that slot (such as ABS_MT_POSITION_X or ABS_MT_POSITION_Y). If a finger remains motionless while another moves, no data is sent for the stationary slot.
    • When the finger lifts from the surface, the driver sends ABS_MT_TRACKING_ID with value -1.
    Type B reduces context switching and CPU overhead by eliminating redundant coordinate transmissions during multi-finger gestures.

Virtual device creation with uinput

The uinput kernel module exposes a character device at /dev/uinput that allows user-space daemons to synthesize virtual input devices. These virtual devices register as standard /dev/input/event* nodes indistinguishable from physical hardware.

The lifecycle of a virtual input device follows seven steps:

  1. Open /dev/uinput in non-blocking write mode (O_WRONLY | O_NONBLOCK).
  2. Configure supported event types using ioctl(fd, UI_SET_EVBIT, EV_KEY).
  3. Configure specific key codes using ioctl(fd, UI_SET_KEYBIT, KEY_A).
  4. Populate a struct uinput_setup with vendor ID, product ID, bus type, and device name string.
  5. Issue ioctl(fd, UI_DEV_SETUP, &setup) followed by ioctl(fd, UI_DEV_CREATE). The kernel assigns a new /dev/input/event* node.
  6. Write binary struct input_event packets to the file descriptor to inject synthetic keystrokes or mouse displacements.
  7. On termination, issue ioctl(fd, UI_DEV_DESTROY) and close the file descriptor.

Wayland seat handover architecture

In the X11 era, the display server ran as root, allowing direct access to /dev/input/event*. In modern Linux and Tamlinux, Wayland compositors (such as Hyprland and Sway) run as unprivileged user processes. Access to input devices is mediated by a seat management daemon (such as seatd or systemd-logind):

  1. When the compositor starts, it establishes an IPC connection (via UNIX domain socket or D-Bus) to the seat manager.
  2. The compositor calls TakeControl to claim the active seat and virtual terminal (VT).
  3. The compositor requests access to individual input devices (e.g. OpenDevice("/dev/input/event4")).
  4. The seat manager checks that the calling session is active and currently foregrounded on the VT. It opens the device node with root privileges and passes the open file descriptor back to the compositor using SCM_RIGHTS control messages over the UNIX socket.
  5. The compositor passes the received file descriptor to libinput for event processing.
  6. When the user switches consoles (e.g. Ctrl + Alt + F2), the seat manager pauses or revokes the input descriptors. This prevents a background compositor from snooping on passwords typed into the foreground virtual console.

Ring buffer overflow and SYN_DROPPED recovery

The kernel evdev driver maintains a fixed-size circular ring buffer for each open file descriptor (typically 64 to 512 events). If a user-space application stalls due to CPU starvation or heavy I/O, the queue fills up. The kernel handles overflow gracefully:

  1. The kernel discards the overflowing event packet.
  2. It sets a flag on the client queue and injects an EV_SYN event with code SYN_DROPPED and value 0.
  3. When the reader resumes reading, libevdev encounters SYN_DROPPED and returns LIBEVDEV_READ_STATUS_SYNC.
  4. Because learner relative motions and key transitions were lost, the reader must not guess. Instead, libevdev queries the full hardware state using EVIOCGKEY, EVIOCGLED, and EVIOCGSW, comparing the kernel's active bitmasks against its internal state and synthesizing synthetic release or press events to resynchronize smoothly.

Check yourself

Decide your answer before you reveal it.

Why is SYN_DROPPED emitted as an EV_SYN packet rather than returning a read error like ENOBUFS?

Returning an error on read(2) would break standard POSIX event loops that treat errors as fatal disconnects. Emitting SYN_DROPPED in-band within the event stream allows the client to detect buffer overflow at the exact moment in time it occurred, discard corrupted partial event sequences, and resynchronize cleanly.

How does the Multi-Touch Type B slotted protocol reduce CPU overhead compared to Type A?

Type A transmits the complete state of every active touch contact on every scan cycle. Type B assigns persistent hardware slots and transmits updates only for contacts whose position or pressure actually changed, dramatically reducing event volume during multi-finger gestures.
