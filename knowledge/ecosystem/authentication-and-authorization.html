Authentication, Authorization, and Linux Access Control

How a computer decides who you are, how it decides what you are allowed to touch, and how Linux enforces those rules from PAM logins down to kernel system calls.

Who you are vs. what you are allowed to do

Every security check has two separate halves that are easy to mix up:

  • Authentication (AuthN): proving who you are—like showing a photo ID or tapping a badge at a building entrance.
  • Authorization (AuthZ): checking what that proven identity is allowed to do—like whether your badge opens only your office floor or also the server room.

Computers usually check your identity using one or more of three kinds of proof, often called factors:

  1. Something you know: a password or PIN.
  2. Something you have: a physical USB security key or a phone holding a secret key.
  3. Something you are: a fingerprint or face scan.

Using two different kinds together—such as a password plus a USB key—is called multi-factor authentication (MFA), because stealing just one factor is no longer enough to impersonate you.

Why it matters

If an app checks who you are but forgets to check what you are allowed to do, any logged-in user can read someone else's private files. Both halves must work together on every request.

How to think about it

Even inside your own laptop, programs run as different workers with different badges. Your web browser does not need the master key to overwrite system files; keeping authentication and authorization distinct lets the operating system confine each program to its own workspace.

New words

Authorization
Deciding whether an authenticated user or program is permitted to perform an action on a resource.
PAM
Pluggable Authentication Modules, the Linux framework that lets login, sudo, and lock screens share password, fingerprint, and hardware-key checks.
Discretionary Access Control (DAC)
An access model where the owner of a file decides who may read, change, or run it.
Mandatory Access Control (MAC)
System-wide rules enforced by the operating system that even a file's owner cannot override.

Inspecting PAM, Linux capabilities, and process credentials

Goal: inspect how Linux represents your user identity, capabilities, and PAM authentication stacks without changing system configuration.

Before you start: Linux separates authentication (handled in user space by PAM or D-Bus helpers like Polkit) from authorization (enforced by the kernel on every file open, socket bind, or syscall).

In a normal desktop shell, Current: = means your shell holds zero elevated Linux capabilities. When a program only needs to bind a low-numbered network port, an administrator can grant just CAP_NET_BIND_SERVICE instead of full root power.

Across larger systems, authorization policies follow distinct models:

  • DAC: file owners set permissions (chmod, POSIX ACLs).
  • MAC: kernel LSMs (SELinux, AppArmor) enforce administrator-locked labels.
  • RBAC (Role-Based Access Control): permissions attach to roles (such as auditor or wheel) rather than individual names.
  • ABAC (Attribute-Based Access Control): rules evaluate subject, resource, and context attributes (time, device posture, network).
  • ReBAC (Relationship-Based Access Control): access follows graph edges (such as "owner of folder containing document", popularized by Google Zanzibar).

Try it

Run id and capsh --print | head -n 4 in your terminal to see your numeric UID, group memberships, and capability sets.

If it goes wrong

Adding a user to a privileged group (like wheel or docker) does not seem to take effect
Group memberships are loaded at login time into the process credential structure. Log out and back in (or start a fresh login session) for new group memberships to apply.
Granting docker group membership casually
A user who can instruct a root-owned daemon to bind-mount / effectively has root access. Prefer rootless containers or explicit sudo wrappers such as tam-sudo-docker.

Tamlinux keeps desktop elevation explicit: sudo and polkit share PAM hardware-token rules when enrolled, while unprivileged user sessions carry zero ambient capabilities.

Check yourself

Answer before revealing the explanation.

What is the difference between authentication and authorization?

Authentication verifies who a principal is (for example, checking a password hash or FIDO2 signature); authorization decides whether that principal is allowed to perform a requested action.

Why are Linux capabilities safer than making a helper binary full root?

Capabilities split root's omnipotence into fine-grained privileges (such as CAP_NET_RAW or CAP_NET_BIND_SERVICE), limiting what a compromised binary can do.

Password KDFs, PAM state machines, Linux credentials, and modern authorization architectures

Reference: credential storage and password KDFs

Local password authentication never stores plaintext passwords. Modern Linux /etc/shadow entries use memory-hard key derivation functions—principally Argon2id (RFC 9106, winner of the Password Hashing Competition) or yescrypt—parameterized by memory cost m, time cost t, and parallelism p alongside a per-user 128-bit random salt. Memory hardness forces GPU/ASIC brute-force crackers to pay DRAM bandwidth and area costs rather than only ALU cycles. Verification must compare derived digests in constant time to avoid timing side channels.

How it works: PAM, Polkit, Linux UIDs, capabilities, seccomp-bpf, and user namespaces

PAM state machine: libpam evaluates four independent stacks per service—auth (verify identity and set credentials), account (expiry, time, host restrictions), session (audit, keyring, mount setup/teardown), and password (token updates). Control flags (required, requisite, sufficient, optional, or bracketed jump syntax [success=1 default=ignore]) compose short-circuiting boolean pipelines. Note that a sufficient hardware module (pam_fprintd or pam_u2f) placed before pam_unix lets hardware touch satisfy auth while preserving password fallback.

Polkit: unprivileged desktop clients talk over D-Bus to privileged system daemons (systemd-logind, NetworkManager, udisks2). Rather than running the UI as root, the daemon queries polkitd with an action ID and subject PID/UID; polkitd evaluates JavaScript/rule policies (/etc/polkit-1/rules.d/) and, when interactive authorization is required, delegates credential verification to a local Polkit authentication agent via PAM.

Linux kernel credential model (struct cred): every task carries four UID/GID tuples: real (uid, who owns the process), effective (euid, checked by most permission checks), saved set-user-ID (suid, allowing temporary privilege drop and re-acquire), and filesystem (fsuid, used for VFS checks by file servers). On execve() of a setuid binary or file with filesystem capabilities (security.capability xattr), the kernel computes new capability sets P' from permitted, inheritable, effective, bounding, and ambient bitmasks unless PR_SET_NO_NEW_PRIVS is set (which irreversibly blocks privilege gain across execve(), enabling unprivileged sandboxes).

Syscall filtering and namespaces: seccomp-bpf attaches a classic BPF bytecode filter to a task that inspects seccomp_data (syscall number, architecture, scalar arguments—never dereferenced pointers, avoiding TOCTOU in the filter) and returns SECCOMP_RET_ALLOW, ERRNO, TRAP, or KILL_PROCESS. User namespaces (CLONE_NEWUSER) map an unprivileged outer UID to UID 0 inside a namespace so containers can hold namespaced capabilities without gaining host privileges—though exposing new kernel attack surface (ioctl, netfilter, overlayfs) inside user namespaces remains a major privilege-escalation vector.

Edge cases and open research problems

OAuth 2.0 / OIDC and ReBAC vs. confused deputies
Distributed authorization separates Identity Providers (IdP) issuing signed JWTs/OIDC tokens from Policy Decision Points (OPA/Rego, Cedar, Zanzibar ReBAC). Subtle failure modes include token-audience confusion, algorithm confusion (alg=none or HS256/RS256 key confusion), and stale revocation caches violating complete mediation.
Capability-based vs. ambient-authority OS designs
POSIX ambient authority ties rights to a global UID namespace, making fine-grained sandboxing awkward. Object-capability systems (Capsicum, seL4, WASI preview 2) bind rights to unforgeable handles, eliminating whole classes of path-traversal and confused-deputy bugs.
Kernel attack surface in unprivileged sandboxes
Features designed to harden apps (user namespaces, eBPF, io_uring) repeatedly introduce kernel memory-corruption bugs reachable by unprivileged processes, driving research into Rust-in-Linux, syscall-surface minimization, and formal verification of access-control hooks (LSMs).
Research frontier: How can distributed authorization systems (Zanzibar/ReBAC, Cedar) guarantee low-latency complete mediation without stale-cache privilege escalation?

Global replication introduces consistency windows where a revoked permission remains cached at a regional PDP. Zanzibar's "zookie" causality tokens bound staleness to at-least-as-fresh-as-write timestamps, while ongoing research explores formal policy verification (SMT-backed analysis in Cedar) and cryptographic capability tokens (Macaroons, Biscuits) that support offline attenuation.
