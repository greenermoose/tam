Cryptographic Hash Functions, SHA, HMAC, and Key Derivation

This page explains how cryptographic hash functions like SHA-256 create compact digital fingerprints, authenticate messages with keys, and stretch passwords safely.

Digital fingerprints that cannot be forged

A cryptographic hash function takes any amount of data—a one-word password, an email, or a multi-gigabyte disk image—and scrambles it into a fixed-length code called a digest. Unlike encryption, hashing is strictly one-way: you cannot reverse a digest back into the original file.

Why it matters

When you download a Linux installation image or install a software package, a single flipped bit (from a noisy wire or an attacker) changes the SHA-256 fingerprint completely. Hashes also protect stored login passwords: systems store a slow hash of your password rather than the password itself.

How to think about it

Think of a hash function as blending ingredients into a smoothie: you can verify that two smoothies match down to the molecule, and changing even one berry turns the whole mixture a different color—but nobody can un-blend the smoothie back into intact fruit.

New words

Hash
A fixed-size digest produced by a one-way mathematical compression function.
HMAC
A keyed hash construction that proves a message came from someone holding a shared secret key.

Computing SHA-256, BLAKE2, SHA-3, and HMAC digests

Goal: you will be able to compute and compare SHA-256, BLAKE2b, SHA-3, and HMAC-SHA256 digests and verify why single-bit changes trigger the avalanche effect.

Before you start: hashing standard input with sha256sum, b2sum, and openssl dgst is read-only and leaves no files behind.

Worked example

Hash hello and hellp (one bit apart in the last letter) with SHA-256, then compute BLAKE2b, SHA3-256, and HMAC-SHA256 on hello:

$ printf 'hello' | sha256sum
2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824  -
$ printf 'hellp' | sha256sum
fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7  -
$ printf 'hello' | b2sum
e4cfa39a3d37be31c59609e807970799caa68a19bfaa15135f165085e01d41a65ba1e1b146aeb6bd0092b49eac214c103ccfa3a365954bbbe52f74a2b3620c94  -
$ printf 'hello' | openssl dgst -sha3-256
SHA3-256(stdin)= 3338be694f50c5f338814986cdf0686453a888b84f424d792af4b9202398f392
$ printf 'hello' | openssl dgst -sha256 -hmac "my-secret-key"
SHA2-256(stdin)= 3ac7fc22f5cbd1aaaea11fac013d3e6f5d894fe2fc51ab98b6d3b1593a45255a

Output is the same on every system.

What just happened

  1. Changing o (ASCII 0x6f) to p (ASCII 0x70)—a single bit flip—changed roughly half of all 256 bits in the SHA-256 output (the avalanche effect).
  2. b2sum outputs a 512-bit BLAKE2b digest, while openssl dgst -sha3-256 uses the Keccak sponge algorithm rather than SHA-2.
  3. Adding -hmac "my-secret-key" mixes a secret key into the hash so only someone with the key can reproduce that tag.

Try it

Run sha256sum /etc/os-release twice to confirm determinism, then verify a downloaded file against a published .sha256 file with sha256sum -c file.sha256.

If it goes wrong

echo "hello" | sha256sum gives a different hash than printf 'hello'
echo appends a trailing newline character (\n), changing the input bytes. Always use printf '%s' when hashing exact strings.
Using SHA-256 directly to store user passwords
SHA-256 is designed to be blazingly fast (billions of hashes per second on GPUs). Always use a salted, memory-hard password KDF such as Argon2id or yescrypt.

On Tamlinux, Arch Linux local password hashes in /etc/shadow use yescrypt via PAM, LUKS2 key slots default to memory-hard Argon2id, and package/assembly verification relies on SHA-256 digests pinned in Nix flakes and tamlinux-packages.

Check yourself

Decide your answer before you reveal it.

Why is a raw SHA-256 hash of a password unsafe for storing login credentials even though SHA-256 is collision-resistant?

SHA-256 is fast and unsalted: attackers can precompute tables for common passwords and test billions of guesses per second on GPUs. Password storage requires per-user random salts and memory-hard work factors (Argon2id, yescrypt, scrypt).

What is the difference between a plain SHA-256 digest and an HMAC-SHA256 tag?

Anyone can compute a plain SHA-256 digest, so it only detects accidental corruption unless delivered over a trusted channel. HMAC requires a secret key, protecting against intentional forgery by an active attacker.

SHA-256, Keccak sponge, collision bounds, HMAC, and Argon2id

Reference: an n-bit cryptographic hash H: {0,1}* → {0,1}^n must satisfy three hardness properties against PPT adversaries:

  • Preimage resistance (one-wayness): given y, finding x with H(x) = y requires ~2^n work.
  • Second-preimage resistance: given x_1, finding x_2 ≠ x_1 with H(x_2) = H(x_1) requires ~2^n work.
  • Collision resistance: finding any pair (x_1, x_2) with x_1 ≠ x_2 and H(x_1) = H(x_2) requires ~2^(n/2) work by the birthday paradox (e.g., 2^128 for SHA-256).

How it works: SHA-256 vs. SHA-3 Sponge

SHA-256 (FIPS 180-4) Internals: Messages are padded with a 1 bit, k zero bits, and a 64-bit big-endian length so total length is a multiple of 512 bits. Each 512-bit block M^(i) is expanded into sixty-four 32-bit words W_0..W_63 using σ_0(x) = ROTR^7(x) ⊕ ROTR^18(x) ⊕ SHR^3(x) and σ_1(x) = ROTR^17(x) ⊕ ROTR^19(x) ⊕ SHR^10(x). Eight 32-bit state registers (a..h)—initialized from the fractional parts of the square roots of the first 8 primes—run 64 rounds using Ch(e,f,g) = (e ∧ f) ⊕ (¬e ∧ g), Maj(a,b,c) = (a ∧ b) ⊕ (a ∧ c) ⊕ (b ∧ c), Σ_0, Σ_1, and round constants K_t (fractional parts of cube roots of the first 64 primes), followed by Davies–Meyer feed-forward addition modulo 2^32.

Length-Extension Attack on Merkle–Damgård: Because SHA-256 outputs its full internal chaining state, an attacker given H(secret || m) and |secret || m| can append padding || m' and continue running the compression function to compute H(secret || m || padding || m') without knowing secret. HMAC defeats this by nesting: HMAC(K, m) = H((K' ⊕ opad) || H((K' ⊕ ipad) || m)), where ipad = 0x36... and opad = 0x5c.... HKDF (RFC 5869) builds a two-stage Extract-then-Expand KDF on top of HMAC.

SHA-3 / Keccak Sponge (FIPS 202): A 1600-bit state (5×5×64 lanes) is partitioned into bitrate r (outer, exposed) and capacity c (inner, hidden; r + c = 1600, with c = 2n for SHA3-n). Input blocks are XORed into the first r bits interleaved with the 24-round Keccak-f[1600] permutation (θ, ρ, π, χ, ι steps), then output blocks are squeezed from the r bits. Because the capacity c is never output directly, sponge hashes resist length-extension attacks natively and are proved indifferentiable from a Random Oracle up to 2^(c/2) queries.

Memory-Hard Password KDFs (Argon2id): Unlike PBKDF2 (low memory, easily parallelized on ASICs/GPUs), Argon2id fills a large 2D memory matrix (e.g., 64 MiB–1 GiB) with pseudo-random dependencies—using data-independent addressing (Argon2i) in early passes to resist cache-timing side channels and data-dependent addressing (Argon2d) in later passes to maximize time-memory tradeoff resistance.

Edge cases and failure modes

  • Truncating hashes & multi-target attacks: Truncating SHA-256 to 128 bits reduces collision resistance to 2^64 (infeasible for security today). Similarly, lacking per-user salts enables multi-target preimage attacks where cracking any one of T targets drops cost by factor T.
  • Comparing MAC tags with == / memcmp: Non-constant-time byte comparison leaks how many leading bytes of a forged MAC match via timing side channels; always use constant-time comparison (e.g., CRYPTO_memcmp).

Check yourself

Why does SHA3-256 not need HMAC to prevent length-extension attacks, whereas SHA-256 does?

SHA-256 outputs its entire 256-bit Merkle-Damgard chaining variable, letting an attacker resume compression from the digest. SHA3-256 uses a 1600-bit Keccak sponge where 512 capacity bits remain hidden inside the internal state and are never emitted; without those capacity bits, an attacker cannot predict the state transition for appended blocks (so KMAC is a simple keyed sponge).
