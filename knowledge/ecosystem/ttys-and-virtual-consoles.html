TTYs, Virtual Consoles, and Terminal Architecture

The terminal is the primary interface for administering and developing on a Tamlinux system. In modern Linux systems, what users call a "terminal" spans three distinct architectural layers: physical serial teleprinters (TTYs), kernel-managed full-screen virtual terminals (VTs or virtual consoles), and software-emulated pseudo-terminals (PTYs). Understanding how these layers interact is essential for navigating the system, rescuing frozen graphical sessions, and understanding how display servers acquire display hardware.

Beginner: Virtual consoles and everyday switching

Summary: Understand what virtual consoles are, how to switch between text consoles and your graphical desktop using hotkeys, and how to use virtual terminals as an emergency escape hatch when an application freezes.

Prerequisites: The Tamlinux Ecosystem and Compositors and Windowing.

What is a virtual console?

A virtual console (also called a virtual terminal or VT) is an independent, full-screen character display managed directly by the Linux kernel. Even when no graphical desktop or windowing system is installed or running, the Linux kernel allocates multiple virtual terminals (typically numbered 1 through 63, backed by device nodes /dev/tty1 through /dev/tty63).

Each virtual terminal maintains its own display buffer, cursor position, keyboard input state, and active process tree. Your physical monitor and keyboard connect to only one virtual console at any given moment; switching consoles instructs the kernel to switch the active screen buffer and keyboard focus.

Switching between virtual consoles

You can switch between virtual consoles at any time using hardware keyboard shortcuts:

  • Switch to a text console: Press Ctrl + Alt + F2 (or F3 through F6). On laptops where function keys share multimedia bindings, hold the Fn key as well (Ctrl + Alt + Fn + F2).
  • Return to the graphical desktop: Press Ctrl + Alt + F1 (or whichever virtual terminal hosts your display manager and Wayland compositor).

On Tamlinux, the display manager (SDDM) and your primary Wayland session typically run on VT1 (/dev/tty1) or VT2 (/dev/tty2). Virtual terminals 3 through 6 run text login prompts (managed by agetty), providing immediate access to clean shell prompts without graphics overhead.

The emergency escape hatch

When a graphical application hangs, a video game deadlocks the GPU, or a Wayland compositor stops responding to keyboard and mouse shortcuts, the Linux kernel's virtual terminal subsystem continues to function. You do not need to press the machine's physical power button or reset switch, which risks filesystem corruption or unwritten cache data.

Follow this escalation sequence to recover calmly:

  1. Drop to a text console: Press Ctrl + Alt + F3. The kernel immediately pauses graphical scanout and presents a text login prompt.
  2. Log in: Type your regular Tamlinux username and password.
  3. Identify the hung process: Run top or search for runaway processes with pgrep: 
    pgrep -l problematic-app
  4. Terminate cleanly: Send a graceful termination request first, allowing the application to save state: 
    kill -TERM <PID>
    If the application does not exit after several seconds, force termination with kill -KILL <PID>.
  5. Return to desktop: Press Ctrl + Alt + F1 to return to your running graphical desktop session.

For system-wide lockups where even virtual console switching does not respond, consult Emergency Disaster Recovery for the Magic SysRq recovery sequence.

Intermediate: The TTY subsystem, line disciplines, and PTYs

Summary: Contrast hardware TTYs, kernel VTs, and software PTYs; understand the role of the terminal line discipline in buffering and signal handling; and inspect terminal sessions with standard utilities.

Prerequisites: Beginner depth, plus basic command-line stream concepts (The Shell and Streams).

The three terminal layers

Unix terminal architecture evolved over decades, preserving a consistent character-stream programming interface across changing hardware technologies:

  1. Physical Teleprinters (TTYs): Historically, electromechanical teleprinters (such as the Teletype Model 33 ASR) connected to computers over serial lines (RS-232, /dev/ttyS0). The kernel driver managed UART baud rates, parity bits, and hardware flow control.
  2. Virtual Terminals (VTs): When personal computers adopted integrated video displays and keyboards, the Linux kernel implemented virtual terminals (/dev/tty1–/dev/tty63). The kernel emulates a DEC VT102 or ANSI terminal in software, rendering glyphs directly into video framebuffers.
  3. Pseudo-Terminals (PTYs): Graphical terminal emulators (such as foot, alacritty, and kitty), terminal multiplexers (tmux), and remote access servers (sshd) cannot bind directly to kernel VT devices. Instead, they allocate a bidirectional software channel called a pseudo-terminal pair:
    • PTY Master: Opened by the emulator process via /dev/ptmx. The emulator writes keyboard input into the master and reads formatted screen updates from it.
    • PTY Slave: Created under /dev/pts/N (such as /dev/pts/0). The user's shell (e.g. bash) and command-line programs open the slave side, behaving identically to a physical hardware terminal.

The line discipline: Canonical vs raw mode

Between any terminal device and the running application sits the kernel's line discipline (specifically N_TTY). The line discipline controls how keystrokes are processed before the application's read() system call receives them:

  • Canonical (Cooked) Mode: The default mode for command-line shells. The kernel buffers input line-by-line. It processes editing keys (Backspace, Delete, Ctrl+U to erase line) inside the kernel and echoes typed characters back to the screen. The application receives nothing until the user presses Enter.
  • Raw Mode: Used by interactive, full-screen terminal programs, including text editors (micro, vim), pagers (tam's internal pager), and system monitors (top). The kernel disables line buffering, character echoing, and key translations. Every keypress is delivered immediately to the application as raw bytes.
  • Signal Generation: In canonical and partially cooked modes, the line discipline intercepts specific control characters and translates them into POSIX signals delivered to the foreground process group:
    • Ctrl + C (\x03) → generates SIGINT (interrupts and cancels the running command).
    • Ctrl + \ (\x1c) → generates SIGQUIT (terminates with core dump).
    • Ctrl + Z (\x1a) → generates SIGTSTP (suspends process and returns to shell job control).
    • Ctrl + D (\x04) → signals End of File (EOF) when sent on an empty input line.

Controlling terminals and session leaders

Every interactive Unix process group belongs to a session, and each session may have an associated controlling terminal. The controlling terminal is accessible through the special character device /dev/tty. Opening /dev/tty always accesses the terminal of the current process, regardless of whether standard input or output have been redirected to files or pipes.

When a session leader closes its controlling terminal (or when a user hangs up an SSH connection or closes a terminal emulator window), the kernel sends a SIGHUP (Hangup) signal to all processes attached to that terminal. Background daemons detach from controlling terminals via setsid() to avoid receiving hangup signals when sessions terminate.

Inspection and control commands

You can inspect and control virtual terminals and pseudo-terminals using standard command-line tools:

# Print the terminal attached to standard input
tty

# Inspect line discipline configuration, baud rate, and control keys
stty -a

# Print the active foreground virtual console number
fgconsole

# Switch virtual terminals from the command line (requires root or seat access)
chvt 1

# Display logged-in users across VTs and pseudo-terminals
w

Expert: Kernel KMS handover, seat management, and troubleshooting

Summary: Explore the kernel VT implementation in drivers/tty/vt/, understand DRM master handover between compositors and text consoles, and trace how seat arbiters manage unprivileged hardware access.

Prerequisites: Intermediate depth, plus familiarity with Wayland compositors (Compositors and Windowing) and display managers (Display Managers: SDDM).

Kernel console architecture: drivers/tty/vt/

Inside the Linux kernel source tree, the virtual terminal subsystem lives in drivers/tty/vt/. It manages terminal state, font tables, character attributes, and hardware console drivers:

  • Terminal Operating Modes: A virtual terminal operates in one of two primary modes:
    • KD_TEXT: The console driver renders text characters using a bitmap font rendered by the framebuffer console (fbcon) or legacy VGA hardware.
    • KD_GRAPHICS: Console text rendering is suspended. The display hardware is surrendered to a userspace graphics process (such as a Wayland compositor or X11 server) for direct GPU scanout.
  • Console Switching Controls: Processes managing graphical sessions use ioctl calls on the VT device (e.g. VT_SETMODE, VT_ACTIVATE, VT_WAITACTIVE) to request notifications when a console switch is requested by the kernel or user.

Seat management and unprivileged hardware access

Historically, Xorg required SUID root permissions to open raw input devices (/dev/input/event*) and direct graphics memory (/dev/dri/card*). Modern Wayland compositors on Tamlinux run entirely unprivileged under the user's UID, mediated by a seat arbiter:

  • Seats: In freedesktop.org architecture, a "seat" represents all hardware devices assigned to a single workstation user (displays, keyboards, mice, and sound cards). The primary physical workstation is designated seat0.
  • Seat Arbiters: Tamlinux uses systemd-logind (on the current Arch base) or seatd (on the target Void base). The seat arbiter runs as a privileged daemon and opens device nodes on behalf of the session compositor.
  • File Descriptor Passing: When Sway or Hyprland starts, it connects to the seat arbiter over a Unix socket or D-Bus. The arbiter verifies that the session is active on the current VT, opens the necessary input and DRM devices, and passes the open file descriptors to the compositor via SCM_RIGHTS socket messages.
  • Session Inactivation: When switching away from the compositor's VT, the seat arbiter automatically revokes or pauses the device file descriptors. This prevents background sessions from snooping keystrokes or accessing GPU memory.

The DRM KMS master handover sequence

Linux Direct Rendering Manager (DRM) enforces an invariant: only one process at a time may act as DRM Master on a display controller (/dev/dri/card*). The DRM Master controls Kernel Mode Setting (KMS), allocating CRTCs, configuring display resolutions, and scheduling page flips.

When you press Ctrl + Alt + F2 to switch from a Wayland session to a text console, the following coordination occurs:

  1. The kernel receives the switch hotkey and sends a VT_PROCESS switch signal to the active session supervisor.
  2. The seat arbiter notifies the Wayland compositor that its session is becoming inactive.
  3. The compositor pauses rendering and issues the DRM_IOCTL_DROP_MASTER ioctl, relinquishing control of the display controller.
  4. The kernel switches the active VT to VT2, sets the terminal mode to KD_TEXT, and activates fbcon, which programs the display controller to render the text login prompt.
  5. When you later press Ctrl + Alt + F1 to return, the reverse sequence executes: fbcon suspends, the target VT is set to KD_GRAPHICS, the compositor receives an activation event, issues DRM_IOCTL_SET_MASTER, restores its display pipelines, and redraws the desktop.

Troubleshooting common VT and console issues

Black screen on virtual console switch
If pressing Ctrl + Alt + F2 produces a blank or unresponsive black screen, the graphics driver has failed the DRM master handover, or the kernel lacks framebuffer console support. Verify that the kernel includes the fbcon driver and that kernel mode setting (KMS) is active. On systems with dual GPUs, verify that the console is assigned to the active video output.
Tiny console fonts on HiDPI displays
On 4K and HiDPI monitors, the default 8x16 pixel console font is difficult to read. Install a high-resolution console font (such as the Terminus font package) and configure /etc/vconsole.conf: 
FONT=ter-v32n
Apply the font immediately without rebooting by running setfont ter-v32n.
Inspecting seat and session status
To verify session state, assigned virtual terminals, and seat status: 
# List active seats and sessions
loginctl list-sessions
loginctl list-seats

# Inspect specific session state and VT assignment
loginctl session-status $(loginctl list-sessions --no-legend | awk '{print $1}')
