Text screens and terminal windows

This page explains ways to type and read text on a computer, with or without a desktop.

A virtual console is a text screen you can use outside the desktop. A terminal is a place to type and read text; a terminal window works inside the desktop.

Recognize a virtual console

Goal: identify a virtual console and its limits as a recovery route.

Why it matters: a text login may remain usable when a graphical application is stuck, but display, kernel or input failures can affect it too.

Before you start: read terminal and virtual console. The example reads a system path.

New to this? A path names a place in the filesystem. Type only what follows the dollar sign and press Enter. Do not switch consoles during an unsaved task.

Worked example

$ ls -d /sys/class/tty/tty0
/sys/class/tty/tty0

Captured on Arch Linux, 2026-10-27. This shows a kernel interface exists; it does not show which console has a login or a desktop. Your system may differ.

Try it

Run the read-only example. Identify the directory shown and compare it with a terminal window's tty output, if the command is available.

If it goes wrong

A missing path or a blank screen does not identify the cause. A graphical session, console display, login service and keyboard are separate dependencies. Use recovery for alternatives.

Check yourself

Does a tty0 path guarantee a usable text login?

No. A display, input and a login service must also work.

Is a terminal window the same as a kernel virtual console?

No. A terminal window normally uses a pseudo-terminal; a virtual console is managed by the kernel.

New words

A kernel manages hardware and processes; a path identifies a filesystem location.

Next step

Read recovery before relying on a console during a fault.

Identify the active route

Goal: distinguish a console device, a login prompt and a graphical session.

Mental model

A kernel VT supplies a console surface; a getty may offer a text login there. A desktop terminal uses a PTY pair: the emulator handles one end and the shell uses the other. A session manager and graphics driver contribute their own state.

Worked example

The example above finds the tty0 interface. In an interactive terminal, tty shows the device attached to standard input. loginctl list-sessions lists registered sessions on systemd hosts. Output varies; neither alone proves a console can display a prompt.

Completion task

Compare the device reported by tty with any registered session. Which identifies the terminal device and which identifies a session?

tty reports the terminal attached to its input; loginctl reports registered sessions. A PTY number does not identify the desktop's VT.

Independent task

Without switching or changing configuration, identify the documented recovery route for your installation and the evidence needed to know which console hosts it.

Choosing

Use a terminal window for ordinary shell work. Use a separately available text console when the desktop cannot be used and the console and input still work. Do not assume a fixed VT number.

Troubleshooting

A blank console may reflect display, driver, input, login-service or kernel failure; a single symptom does not establish which. Record what responds and follow the recovery guide.

On Tamlinux: the 0.5 text-startup design provides a text login and a second console, with the desktop started explicitly. Other installed versions can use graphical login. Check the selected installation rather than assuming F1, F2 or F3 is always the right return key.

Check yourself

Does /dev/pts/0 tell you the desktop's virtual console number?

No. It identifies a pseudo-terminal slave, not the compositor's VT.

Why can a console switch fail during a graphics fault?

Console switching and rendering depend on working kernel, input and display components. A fault can affect any of them.

Further reading

See tty(1), pty(7) and loginctl(1) for devices and sessions; see recovery for fault handling.

Terminal and display boundaries

A PTY is a master/slave pair; programs on the slave use terminal semantics while an emulator drives the master. The line discipline can handle editing and signal characters depending on termios settings: canonical mode ordinarily delivers completed lines, while applications can configure noncanonical input. With signal generation enabled, Ctrl+C requests SIGINT for the foreground process group. A controlling terminal, foreground process group and session have distinct roles; see pty(7) and termios(3).

VT switching may require coordination among the active session, seat manager, display driver and compositor. Failure to display a console is evidence to investigate, not proof of a particular DRM failure. Avoid switching or changing VT modes on a working session merely to diagnose an unrelated fault.

Check yourself

What must you distinguish before attributing a blank VT to a failed compositor?

Check input response, kernel and session state, login availability and display output. Each can fail independently; a blank screen alone cannot identify the failing layer.
