Trying software in a separate computer

This page explains how to try software in a separate simulated computer.

A simulated computer gives you a separate place to try software and system changes. This can help you investigate problems without changing the computer you rely on.

What is virtualization for?

Developing low-level workstation components, system configurations, or installation scripts carries risk. Testing on a primary machine can leave orphaned packages, corrupt boot configurations, or cause data loss. Virtualization and containers provide isolated, disposable environments where experiments run safely without risking your daily-driver setup.

How to think about it

Virtualization lets one computer run another operating system inside simulated hardware. Containers share the host kernel but isolate processes, users, and filesystems.

New words

Virtual machine
An isolated computing environment that emulates physical hardware, running its own complete guest kernel and operating system.
Container
An isolated user-space environment sharing the host Linux kernel, using namespaces and cgroups for process and filesystem boundaries.
Clean-room testing
Testing software and system scripts in an isolated, pristine environment devoid of pre-existing user configurations or non-standard packages.

Every contained workload runs as an isolated process tree under an identifiable configuration owner.

Virtual machines emulate full hardware, booting an independent kernel with its own memory and device drivers. Containers isolate user space using Linux kernel namespaces (PID, mount, network, IPC) and control groups (cgroups), sharing the host kernel for minimal resource overhead and instant startup.

Worked example: Check runtime virtualization and KVM availability

$ systemd-detect-virt
none
$ ls -l /dev/kvm
crw-rw-rw- 1 root kvm 10, 232 Oct 23 14:15 /dev/kvm

Captured on an Arch Linux workstation, 2026-10-25.

What just happened

  1. systemd-detect-virt returned none, confirming that the current shell is executing directly on physical bare-metal hardware rather than within a guest virtual machine or container.
  2. ls -l /dev/kvm confirms that the Kernel-based Virtual Machine (KVM) character device is present with read-write permissions (mode 0666), enabling hardware-accelerated virtualization for QEMU virtual machines.

Try it

Query CPU hardware virtualization extension flags (such as Intel VT-x or AMD-V) using lscpu:

$ lscpu | grep -i Virtualization
Virtualization:                          AMD-V

You can also list all virtualization and container technologies recognized by systemd with systemd-detect-virt --list.

If it goes wrong

systemd-detect-virt prints 'kvm', 'qemu', or 'systemd-nspawn'
The shell is currently running inside a virtual machine or container guest rather than directly on bare metal.
/dev/kvm does not exist or Permission denied
Hardware virtualization (Intel VT-x or AMD-V) is disabled in the system UEFI/BIOS firmware, or the kvm kernel module is not loaded.
systemd-detect-virt exits with code 1
This is expected on bare-metal systems: systemd-detect-virt prints none and returns exit status 1 to allow shell scripts to branch on virtualization presence.

On Tamlinux, all system software and packaging configurations must be reproducible. When developing changes to boot scripts, packaging hooks, or system services, clean-room testing in isolated virtual machines or containers ensures that changes are verified before being proposed or deployed. Check yourself

Decide your answer before you reveal it.

What does systemd-detect-virt output when run on a native, bare-metal workstation?

It outputs none and exits with status 1, indicating that execution is not contained within any virtual machine or container.

Why is hardware acceleration via /dev/kvm critical when running virtual machines in QEMU?

Without KVM hardware acceleration, QEMU must emulate every CPU instruction in software via TCG (Tiny Code Generator), which is orders of magnitude slower. KVM allows guest CPU instructions to execute directly on host processor cores at near-native speed.

How it works

Modern Linux virtualization combines hardware-assisted CPU virtualization with paravirtualized I/O devices:

  1. Hardware-Assisted CPU Execution: The host kernel configures the CPU hardware virtualization extensions (AMD SVM or Intel VMX). When QEMU executes guest code via the KVM_RUN ioctl, the host processor switches into guest mode (executing VMRUN on AMD or VMLAUNCH/VMRESUME on Intel). The guest OS executes unprivileged instructions directly on the physical processor cores at bare-metal speeds.
  2. VM-Exits and Emulation Handling: When the guest OS performs a sensitive operation — such as accessing privileged control registers, executing I/O port instructions, or encountering a page fault on unmapped memory — the CPU halts guest execution and triggers a VM-Exit. Control returns to the KVM kernel module, which either handles the exit directly in kernel space or delegates device emulation to QEMU in user space.
  3. Paravirtualized I/O with Virtio: Emulating legacy hardware controllers (such as IDE disks or Intel e1000 network cards) requires thousands of costly VM-Exits per second. Modern clean-room testing uses Virtio: standardized, cooperative drivers where the guest OS and host hypervisor communicate via shared-memory circular ring buffers (vring). Virtio block devices (virtio-blk) and network devices (virtio-net) batch operations and eliminate unnecessary exits, delivering near-native storage and networking throughput.
  4. Headless Automated Test Harnesses: Automated testing harnesses launch QEMU with a direct kernel boot: 
    qemu-system-x86_64 -m 2048 -enable-kvm -kernel /boot/vmlinuz-linux \
  -initrd /boot/initramfs-linux.img \
  -append "console=ttyS0 earlyprintk=serial,ttyS0,115200" \
  -display none -serial stdio -no-reboot
    Test scripts capture standard output, asserting expected kernel log messages, systemd target milestones, and failure recoveries without graphical dependencies or manual interaction.

Why Tamlinux chose this

Clean-room verification is an essential safety barrier. Testing system-level changes, package hooks, and boot configurations in isolated virtual environments guarantees that regressions are caught before affecting production hardware. By preferring paravirtualized standards like Virtio and standard systemd detection tools, testing workflows remain reproducible, unprivileged, and scriptable.
