Specifying Package Versions in Tamlinux

An operating system release must be reproducible, verifiable, and free from silent runtime drift. Tamlinux achieves this by distinguishing between the top-level Tamlinux product version (the cultivar release) and the independent versions of each individual tool and library that make it up. Every version of Tamlinux is defined by an exact, cryptographically pinned assembly bill of materials.

Product versions versus component versions

Goal: you will be able to query installed package versions, compare product cultivars with component versions, and inspect active assembly status.

Why it matters: an operating system must be reproducible and free from silent drift. Understanding whether you are running a stable candidate or a development build prevents troubleshooting the wrong version and ensures changes are verified against the right code.

Before you start: open a terminal. Inspecting package versions and deployed assembly status uses read-only commands that require no administrative privileges. See Software packaging and delivery for package management basics.

A version number identifies an exact release of a program. On Tamlinux, cultivar names like Blue Sparkler represent overall workstation milestones, while individual tools like tam have their own version numbers. Commands like tam --version query the active program directly.

Worked example: Inspect active versions and cultivar

$ tam --version
tam command 0.43.2 (dev 7279c24)
knowledge corpus 0.43.6 (dev 7279c24)
libtam 0.4.0
Tamlinux cultivar Blue Sparkler 0.5.4

Captured on a Tamlinux workstation, 2026-10-25.

What just happened

  1. tam --version printed the four version tiers of the running environment: the C command binary (0.43.2), the offline knowledge corpus (0.43.6), the shared integration library libtam (0.4.0), and the overall workstation milestone cultivar name and release (Blue Sparkler 0.5.4).
  2. The (dev 7279c24) suffix indicates that the command and corpus are executing from a local development build installed in the user prefix (~/.local/dev/bin) matching Git commit 7279c24.
  3. Packaged production builds omit the (dev ...) suffix and reflect the exact version declared in the active Home Manager assembly generation.

If it goes wrong

tam prints (dev ...) suffix unexpectedly
A development build in ~/.local/dev/bin precedes the packaged binary on PATH. Remove it with make -C ~/src/tam uninstall PREFIX=$HOME/.local/dev and run hash -r.
command and corpus versions differ
Tamlinux command and corpus version independently. Content additions in the documentation corpus bump its version without needing a command binary recompile.
tam-deploy reports command not found
The command path is missing from your environment. Verify that ~/.local/bin is present in your shell PATH variable.

Check yourself

Decide your answer before you reveal it.

What does (dev ...) indicate when appended to a version number in tam --version?

It indicates that the running executable was compiled and installed locally into ~/.local/dev/bin from the indicated Git commit, overriding the packaged Home Manager generation on PATH.

Why do tam command and knowledge corpus maintain independent version numbers?

The command utility (C binary) and documentation corpus develop on separate cadences. Authoring new guide pages or updating documentation increments the corpus version while leaving the compiled command binary untouched.

The assembly repository and pinning architecture

Goal: you will be able to inspect how tamlinux-packages acts as the single source of truth for all software versions, examine flake lock pins, and verify Home Manager store path linkages.

Mental model

tamlinux-packages (flake.nix & flake.lock)
  |-- inputs.nixpkgs        --> Cryptographic commit & narHash (toolchains, Wayland, Qt)
  |-- inputs.tam            --> github:greenermoose/tam/
  |-- inputs.libtam         --> github:greenermoose/libtam/
  |-- inputs.tamlinux       --> github:greenermoose/tamlinux/
  +-- inputs.tamlinux-tools --> github:greenermoose/tamlinux-tools/
            |
            v  (nix build)
  Nix Store Derivations:
    /nix/store/1h8...-tam-0.43.2/bin/tam
    /nix/store/a49...-tamlinux-0.5.4/bin/tam-deploy
            |
            v  (Home Manager Generation Activation)
  User Profile Symlinks (~/.local/bin/):
    ~/.local/bin/tam        --> /nix/store/1h8...-tam-0.43.2/bin/tam
    ~/.local/bin/tam-deploy --> /nix/store/a49...-tamlinux-0.5.4/bin/tam-deploy

Tamlinux does not install floating package versions from remote repositories at deploy time. Instead, a dedicated repository named tamlinux-packages serves as the central bill of materials (BOM), locking every dependency down to the exact commit and cryptographic tree hash.

Worked example: Trace command origin and store links

$ which -a tam
/home/alex/.local/dev/bin/tam
/home/alex/.local/bin/tam
$ ls -l /home/alex/.local/bin/tam
lrwxrwxrwx 1 alex users 68 Oct 25 18:00 /home/alex/.local/bin/tam -> /nix/store/1h8vw7z8kpl9w38h177j2m9f6y19y1v2-tam-0.43.2/bin/tam

Captured on a Tamlinux workstation, 2026-10-25.

  1. which -a tam reveals how the shell resolves the command across the directories in PATH.
  2. The development path ~/.local/dev/bin appears first, enabling rapid testing of local changes without root privileges or Nix store builds.
  3. The packaged production binary sits in ~/.local/bin/tam, which is an immutable symlink pointing directly to its pinned derivation path in /nix/store.

Completion task

Fill the gap (marked ___) in the Nix command used inside tamlinux-packages to update the cryptographic lock for the tam input following a pushed commit:

nix flake lock ___ tam

Fill in --update-input. Running nix flake lock --update-input tam recalculates the Git revision and tree hash (narHash) for only the tam input in flake.lock, preserving all other pinned inputs unchanged.

Independent task

Inspect the inputs defined in a flake assembly by running nix flake metadata or reading flake.nix. Identify the locked revision of libtam and confirm that its derivation in nix/packages/default.nix matches the active library version shown in tam --version.

Run nix flake metadata ~/src/tamlinux-packages or inspect inputs.libtam.url in flake.nix. The URL pins an exact commit hash on github.com/greenermoose/libtam. In nix/packages/default.nix, the derivation declares version = "0.4.0";, matching the active libtam 0.4.0 runtime.

On Tamlinux, all software reaches the workstation exclusively through a recorded tamlinux-packages assembly via tam-deploy, never from a mutable checkout, copied payload, or unrecorded override. Test and Run stages are strictly package-managed, and development overrides in ~/.local/dev are uninstalled immediately upon deployment. See the deployment contract.

Check yourself

Decide your answer before you reveal it.

How does tamlinux-packages ensure that builds are completely reproducible across different machines?

flake.lock records the exact Git commit SHA and cryptographic tree hash (narHash) for all inputs (including nixpkgs, tam, and libtam). Nix guarantees bit-for-bit reproducible outputs by building in isolated sandboxes against those exact locked trees.

Why does a development build in ~/.local/dev/bin take precedence over the packaged binary in ~/.local/bin?

The user's shell configuration places ~/.local/dev/bin before ~/.local/bin in the PATH environment variable. This allows local development binaries to be tested interactively without modifying the packaged Home Manager generation.

How it works

Advancing software through the Tamlinux lifecycle follows four structured phases:

  1. Component Development and Override: Work in the component checkout on the develop branch. Install a development build directly into the user prefix: 
    make -C ~/src/tam test
make -C ~/src/tam install PREFIX=$HOME/.local/dev
    Because ~/.local/dev/bin sits first on the shell PATH, this binary immediately overrides the packaged version for interactive testing without root privileges or Nix store builds.
  2. Component Verification, Version Bump, and Commit: Verify all unit, integration, and guide tests pass (make test). Bump the component version in source:
    • Binary version: src/version.h (TAM_COMMAND_VERSION).
    • Corpus version: knowledge/version, its only source. A corpus release changes no command source.
    Record public AI provenance in AI_PROVENANCE.md. Commit only your claimed paths (git commit -m '...' -- <paths>) and push to develop on GitHub. Note the resulting commit hash.
  3. Assembly Pinning in tamlinux-packages: In ~/src/tamlinux-packages on develop, claim the packaging files with tam-work begin. In flake.nix, update the input URL for tam to the exact pushed commit hash: 
    tam.url = "github:greenermoose/tam/<commit-hash>";
    Update the cryptographic lock: 
    nix flake lock --update-input tam
    In nix/packages/default.nix, update the declared version = "0.43.2"; inside the derivation. Verify the package build and checks using an exclusive claim: 
    nix build .#tam
nix flake check
    Set the candidate Tamlinux letter in VERSION (e.g. 0.5.4-a) following candidate letter rules. Commit and push the updated assembly definition to develop.
  4. Promotion to Test, Run, and Dev Override Cleanup:
    • Test: On the developer's explicit "Test" instruction, promote the candidate commit to the test branch (fast-forward only). Deploy using tam-deploy test.
    • Clean up the dev override: Right after the deploy that delivers the pinned version, remove the development override: 
      make -C ~/src/tam uninstall PREFIX=$HOME/.local/dev
hash -r
      Confirm type -a tam points back to ~/.local/bin/tam.
    • Run: After thorough daily-driver testing, on the developer's explicit "Run" instruction, promote the exact same tested commit to main with tam-deploy run.
    • Release: When all planned steps for the version are accepted, tag the release on GitHub with release notes on the developer's explicit "Release" instruction.

Why Tamlinux chose this

Separating product cultivar milestones from independent component versions enables fast, focused iteration on individual utilities without triggering massive system-wide builds. Pinning components via cryptographic Git hashes and flake.lock eliminates runtime drift, guaranteeing that any developer or machine building a candidate produces identical software. Placing local development builds first on PATH allows safe, unprivileged testing while maintaining pristine package integrity in the underlying operating system.
