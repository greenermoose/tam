Keeping track of software versions

This page explains how Tamlinux identifies the software it installs and keeps track of changes.

A Tamlinux release has its own version, and the tools that make it up have their own versions. Recording the exact choices makes it possible to identify and reproduce a release.

What does a package version name?

An operating system must be reproducible and free from silent drift. Understanding whether you are running a stable candidate or a development build prevents troubleshooting the wrong version and ensures changes are verified against the right code.

How to think about it

A version number identifies an exact release of a program. On Tamlinux, cultivar names like KBN WB represent overall workstation milestones, while individual tools like tam have their own version numbers.

New words

Cultivar
The named Tamlinux product release representing a cohesive set of workstation milestones (for example, KBN WB 0.6.1).
Assembly
The cryptographically locked bill of materials in tamlinux-packages specifying exact revisions of all components.
Generation
An immutable Home Manager configuration state linked from the Nix store into the user profile.

Each deployed package belongs to a specific generation and cultivar with a defined configuration owner.

A version number identifies an exact release of a program. On Tamlinux, cultivar names like KBN WB represent overall workstation milestones, while individual tools like tam have their own version numbers. The cultivar is the Tamlinux software release; it sits on a rootstock (today Arch Linux; Void and a smaller microkernel base are planned). Commands like tam --version query active program versions directly. See distributions and rootstocks for the longer design story.

Mental model

tamlinux-packages (flake.nix & flake.lock)
  |-- inputs.nixpkgs        --> Cryptographic commit & narHash (toolchains, Wayland, Qt)
  |-- inputs.tam            --> github:greenermoose/tam/
  |-- inputs.libtam         --> github:greenermoose/libtam/
  |-- inputs.tamlinux       --> github:greenermoose/tamlinux/
  +-- inputs.tamlinux-tools --> github:greenermoose/tamlinux-tools/
            |
            v  (nix build)
  Nix Store Derivations:
    /nix/store/1h8...-tam-0.43.2/bin/tam
    /nix/store/a49...-tamlinux-0.5.4/bin/tam-deploy
            |
            v  (Home Manager Generation Activation)
  User Profile Symlinks (~/.local/bin/):
    ~/.local/bin/tam        --> /nix/store/1h8...-tam-0.43.2/bin/tam
    ~/.local/bin/tam-deploy --> /nix/store/a49...-tamlinux-0.5.4/bin/tam-deploy

Tamlinux does not install floating package versions from remote repositories at deploy time. Instead, a dedicated repository named tamlinux-packages serves as the central bill of materials (BOM), locking every dependency down to the exact commit and cryptographic tree hash.

Worked example: Inspect active versions and cultivar

$ tam --version
tam command 0.48.1 (dev 4788787)
knowledge corpus 0.59.0 (dev 4788787)
libtam 0.4.0
Tamlinux cultivar KBN WB 0.6.1

Captured on a Tamlinux workstation, 2026-11-02. Your build hash may differ.

What just happened

  1. tam --version printed the four version tiers of the running environment: the C command binary (0.48.1), the offline knowledge corpus (0.59.0), the shared integration library libtam (0.4.0), and the overall workstation milestone cultivar name and release (KBN WB 0.6.1).
  2. The (dev 4788787) suffix indicates that the command and corpus are executing from a local development build installed in the user prefix (~/.local/dev/bin) matching that Git short hash.
  3. Packaged production builds omit the (dev ...) suffix and reflect the exact version declared in the active Home Manager assembly generation.

If it goes wrong

tam prints (dev ...) suffix unexpectedly
A development build in ~/.local/dev/bin precedes the packaged binary on PATH. Remove it with make -C ~/src/tam uninstall PREFIX=$HOME/.local/dev and run hash -r.
command and corpus versions differ
Tamlinux command and corpus version independently. Content additions in the documentation corpus bump its version without needing a command binary recompile.
tam-deploy reports command not found
The command path is missing from your environment. Verify that ~/.local/bin is present in your shell PATH variable.

On Tamlinux, all software reaches the workstation exclusively through a recorded tamlinux-packages assembly via tam-deploy, never from a mutable checkout, copied payload, or unrecorded override. Test and Run stages are strictly package-managed, and development overrides in ~/.local/dev are uninstalled immediately upon deployment. See the deployment contract.

Check yourself

Decide your answer before you reveal it.

What does (dev ...) indicate when appended to a version number in tam --version?

It indicates that the running executable was compiled and installed locally into ~/.local/dev/bin from the indicated Git commit, overriding the packaged Home Manager generation on PATH.

Why do tam command and knowledge corpus maintain independent version numbers?

The command utility (C binary) and documentation corpus develop on separate cadences. Authoring new guide pages or updating documentation increments the corpus version while leaving the compiled command binary untouched.

How it works

Advancing software through the Tamlinux lifecycle follows four structured phases:

  1. Component Development and Override: Work in the component checkout on the develop branch. Install a development build directly into the user prefix: 
    make -C ~/src/tam test
make -C ~/src/tam install PREFIX=$HOME/.local/dev
    Because ~/.local/dev/bin sits first on the shell PATH, this binary immediately overrides the packaged version for interactive testing without root privileges or Nix store builds.
  2. Component Verification, Version Bump, and Commit: Verify all unit, integration, and guide tests pass (make test). Bump the component version in source:
    • Binary version: src/version.h (TAM_COMMAND_VERSION).
    • Corpus version: knowledge/version, its only source. A corpus release changes no command source.
    Record public AI provenance in AI_PROVENANCE.md. Commit only your claimed paths (git commit -m '...' -- <paths>) and push to develop on GitHub. Note the resulting commit hash.
  3. Assembly Pinning in tamlinux-packages: In ~/src/tamlinux-packages on develop, claim the packaging files with tam-work begin. In flake.nix, update the input URL for tam to the exact pushed commit hash: 
    tam.url = "github:greenermoose/tam/<commit-hash>";
    Update the cryptographic lock: 
    nix flake lock --update-input tam
    In nix/packages/default.nix, update the declared version = "0.43.2"; inside the derivation. Verify the package build and checks using an exclusive claim: 
    nix build .#tam
nix flake check
    Set the candidate Tamlinux letter in VERSION (e.g. 0.5.4-a) following candidate letter rules. Commit and push the updated assembly definition to develop.
  4. Promotion to Test, Run, and Dev Override Cleanup:
    • Test: On the developer's explicit "Test" instruction, promote the candidate commit to the test branch (fast-forward only). Deploy using tam-deploy test.
    • Clean up the dev override: Right after the deploy that delivers the pinned version, remove the development override: 
      make -C ~/src/tam uninstall PREFIX=$HOME/.local/dev
hash -r
      Confirm type -a tam points back to ~/.local/bin/tam.
    • Run: After thorough daily-driver testing, on the developer's explicit "Run" instruction, promote the exact same tested commit to main with tam-deploy run.
    • Release: When all planned steps for the version are accepted, tag the release on GitHub with release notes on the developer's explicit "Release" instruction.

Why Tamlinux chose this

Separating product cultivar milestones from independent component versions enables fast, focused iteration on individual utilities without triggering massive system-wide builds. Pinning components via cryptographic Git hashes and flake.lock eliminates runtime drift, guaranteeing that any developer or machine building a candidate produces identical software. Placing local development builds first on PATH allows safe, unprivileged testing while maintaining pristine package integrity in the rootstock.
